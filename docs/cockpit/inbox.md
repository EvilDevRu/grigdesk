# Общий Inbox и каналы

Inbox — отдельный системный плагин и единственная очередь обращений, из которых
создаются задачи B24. Telegram и GitHub Issues — независимые каналы: они владеют
подключением провайдера, ingress, нативным архивом и allowlist, но не владеют общей
очередью, решениями или моделью разбора.

## Три независимых состояния

У каждого канала есть три оси, и UI не смешивает их:

| ось | действие | что меняется |
|---|---|---|
| системный плагин | включить/выключить в настройках | доступны ли страница, routes и network loop канала |
| provider connection | `connect`, `recheck`, `disconnect` на странице канала | credentials, ingress и verified provider identity |
| участие в Inbox | `activate`, `deactivate` на `/inbox` | допускаются ли новые сообщения в общую очередь |

Connect не активирует Inbox. Activate не подключает provider. Обычное выключение общего
плагина Inbox не стирает channel stores и не отключает provider ingress.

`deactivate` атомарно закрывает текущую activation epoch. Сообщения до первой activation
и в промежутке между epochs не становятся backlog после следующего включения. Уже
допущенные unresolved items остаются видимыми. `disconnect` сначала отзывает новый ingress
и leases, ждёт начатые account-scoped операции, закрывает открытую epoch и удаляет только
active credentials; сохранённый namespace остаётся доступен read-only.

Reconnect той же immutable provider identity возвращает тот же `accountRef`, archive,
rules, activation history и decisions, но сам Inbox повторно не активирует. Другой bot
или repository получает новый случайный `accountRef`, пустой allowlist и состояние
`never_activated`.

## HTTP и real-time

- `/inbox`: общая очередь и управление participation;
- `GET /api/inbox`, `/api/inbox/summary`, `/api/inbox/status`;
- `POST /api/inbox/channels/:channel/activate|deactivate`;
- `POST /api/inbox/items/:ref/task|dismiss|reset`;
- SSE `inbox-changed` сообщает, что снимок надо перечитать; payload не является append log;
- навигационный store дополнительно читает summary раз в минуту, потому что Telegram bundle
  может созреть после окна тишины без нового сообщения. Поле `summary.reviewCount` и чип
  на пункте Inbox показывают всю очередь «К разбору», включая ещё не завершившие окно
  тишины; при нуле чип скрыт.

**Очередь считается по нерешённым СООБЩЕНИЯМ, а не по статусу карточки.** Статуса для
этого мало: карточка, разобранная несколькими решениями (две задачи плюс пропуск —
обычный исход разбиения), покрыта целиком, но получает `mixed`. По статусу она висела бы
в «К разбору» вечно, не предлагая ни одной доступной кнопки, а из «Истории» выпадала бы
вовсе. Правило одно на сервер (`actionableItem`) и на вкладки `/inbox`: есть хотя бы одно
сообщение без решения — очередь, нет — история. Такая карточка называется «Разобрано по
частям», а не «Частично разобрано»: последнее обещает незаконченную работу.

`GET /api/inbox` вместе со снимком очереди отдаёт публичное состояние общего
автообработчика (`worker.readiness`). UI не заставляет человека угадывать тишину автомата:
`no_model`, `no_b24`, остановка и недоступность показаны именованным баннером. У каждого
item есть безопасная публичная проекция `autoTask: {enabled, readyAtMs}` — без quota,
policy refs и нативных ID. Пока `readyAtMs` не наступил, карточка показывает обратный
отсчёт и предупреждает, что новое сообщение продлит окно; после него честно пишет, ждёт
ли обращение авторазбора или автомат приостановлен. Ручные кнопки доступны и во время
ожидания: окно тишины ограничивает только автомат.

**Карточка, которую модель читает ПРЯМО СЕЙЧАС, обязана это показывать.** Между сгоревшим
обратным отсчётом и готовым решением проходят минуты (materialize, Whisper, model call), и
раньше всё это время карточка молчала. Воркер держит `worker.judging: {ref, channel,
startedAtMs}`, шлёт `inbox-changed` на входе карточки в разбор и на выходе, а карточка с
совпавшим `ref` показывает «разбирается прямо сейчас» со спиннером — это живое состояние
сильнее расписания. Ручная кнопка на время своего запроса становится «Разбираю и создаю…»:
с настроенной моделью ручная постановка тоже занимает заметные секунды.

Неуспешная подготовка вложений публикуется в `worker.analysisRequired` только как opaque
item ref, безопасный code и время следующей попытки. Карточка прямо сообщает, что
содержимое не разобрано и автозадача не будет создана. Один и тот же revision не запускает
тяжёлый media-анализ каждую минуту: повтор откладывается на шесть часов, а изменение item
снимает блок. Изменение статуса отправляет `inbox-changed`.

Channel adapters page-ят всё activation window до внутреннего safety cap 10 000 native
positions. Public `limit` применяется лишь после decision projection: карточки с
нерешёнными сообщениями не вытесняются разобранными, summary считает полный authoritative scan, а action заново
разрешает item независимо от текущей страницы. Если native rows больше cap, канал становится
degraded и не публикует частичный список — потеря хвоста молча запрещена.

Удалённые `/api/telegram/inbox*`, событие `telegram-inbox`, store `telegram/inbox.json` и
Telegram-owned triage model не поддерживаются: Inbox до этой архитектуры публично не
выпускался, поэтому aliases, importer и dual-read отсутствуют.

## Identity, leases и stores

Provider identity подтверждает сам provider:

~~~text
Telegram = [1, "api.telegram.org", "bot", bot.id]
GitHub   = [1, "github.com", "repository", repository.id]
~~~

Display username, repository name и присланный клиентом ID security identity не являются.
Durable bindings связывают provider identity со случайным `accountRef`. Все Inbox refs
типизированы и включают owner:

~~~text
messageRef = [1, "message", channel, accountRef, sourceId, messageId]
itemRef    = [1, "item",    channel, accountRef, localBundleId]
scopeRef   = [1, "scope",   channel, accountRef, policyScopeId]
~~~

Каждая list/action операция захватывает immutable lease конкретных
`accountRef + generation + stores`. Switch сначала переводит прежнюю generation в
draining, запрещает новые leases и ждёт уже выданные. Перед HTTP response, durable commit
и внешним side effect выполняется generation check; поздний результат прежнего аккаунта
целиком отбрасывается.

Нативная mutation формы дополнительно присылает увиденный `botId`/`repositoryId` как
optimistic CAS. Server никогда не выбирает по нему namespace: он сначала захватывает
immutable lease, сравнивает provider ID с lease и live connection и только затем пишет.
Поэтому старая вкладка не может очистить rules или сменить service chat уже подключённого
другого account даже пустым payload. У Telegram rules есть второй CAS: `GET
/api/telegram/rules` отдаёт canonical `policyFingerprint`, а обычный `PUT` обязан вернуть
exact увиденное значение. Compare и durable atomic write сериализованы внутри account
store; устаревшая форма получает `409 telegram_rules_stale`, а не затирает новую policy.

~~~text
telegram/
  account-bindings.json
  accounts/<accountRef>/
    state.json
    archive/<chatId>/YYYY-MM.ndjson
    rules.json
    bot-settings.json
    inbox-state.json

github/
  account-bindings.json
  accounts/<accountRef>/
    archive/issues.ndjson
    ingress-state.json
    rules.json
    inbox-state.json

server/.state/
  telegram-account-creds.json
  github-creds.json
~~~

Files с credentials имеют режим `0600`; они не лежат в prefs и не попадают в browser DTO.
Runtime открывает только account-aware paths и актуальные owner-bound schemas. Flat stores,
старый credential и старые schemas он не импортирует, не читает и не удаляет.

## Activation и решения

Channel marker содержит нативную монотонную позицию и provider-time boundary. Message
eligible лишь внутри сохранённой epoch одновременно по обеим границам. Это не даёт поздней
доставке старого Telegram update или GitHub webhook перескочить activation за счёт новой
локальной sequence.

`inbox-state.json` имеет строгую owner-bound schema v1. Decision содержит collision-resistant
`decisionId`, version, activation epoch и sorted unique `messageRefs`; пересекающиеся
assignments запрещены. Пересборка bundle не меняет смысл решения: полный coverage даёт
`task`/`skipped`, частичный — `mixed`, отсутствие coverage — `new`.

Task/dismiss принимают только непустой точный subset текущих `new` сообщений. Silent
intersection запрещён. Reset возможен только для `skipped` и требует CAS по
`decisionId + version`; task reset невозможен, потому что B24-задача уже существует.
В интерфейсе это действие называется «Вернуть на разбор»: оно переносит выбранные
пропущенные сообщения из «Истории» обратно в «К разбору» и никогда не удаляет B24-задачу.
При stale CAS клиент перечитывает снимок и показывает обновлённую карточку вместо общей
необъяснимой ошибки.

Перед созданием задачи service проверяет B24 readiness ещё до чтения текста канала, затем
непосредственно перед вызовом B24 повторяет plugin/channel gates, generation, revision,
message contents, assignments, project и policy. Durable task decision записывается только
после B24 success. Если B24 ответил успехом, а commit решения стал неопределённым,
автоматический retry блокируется fail-closed до operator reconciliation.

Вложения выбранных сообщений проходят локальный `InboxAttachmentAnalyzer` до model triage
и до вызова B24. Voice/audio распознаются общим `SpeechRuntime`; video/video note дают
транскрипт и ровно `maxFrames` кадров (по умолчанию четыре).

**Кадры берутся по всей длительности, а не только по сменам сцены.** Детектор сцен
оставлен приоритетом ради смонтированных роликов, но его недобор ВСЕГДА дополняется
равномерной выборкой из середин интервалов (`extractSpanFrames` в
`lib/media/ingest.js`). На записи экрана — а это основной формат багрепорта — детектор
бесполезен: изменение занимает крошечную долю кадра, и порог не помогает (замер на
записи «таблица → активный чекбокс»: `gt(scene,0.4)` и даже `gt(scene,0.1)` дают ноль
кадров). Прежняя схема падала оттуда в «хотя бы первый кадр», то есть модель видела
начало ролика, где действие ещё не началось, и про видео не узнавала ничего: задача
получалась пересказом текста сообщения с упоминанием имени файла. Первый кадр остался
только на случай нечитаемой длительности. Смена алгоритма производных артефактов
обязана поднимать `SCHEMA` анализатора — иначе уже разобранное вложение навсегда
осталось бы с результатом прежнего алгоритма.
Photo/image и растровые BMP/GIF/JPEG/PNG/WebP document/sticker становятся visual inputs
модели. TXT/MD/Markdown/LOG/CSV/JSON/XML/YAML читаются только как bounded strict UTF-8.
PDF, Office, animation, бинарный текст и прочие неподдерживаемые форматы не считаются
разобранными.

Текст Inbox и содержимое вложений считаются недоверенными. Триаж никогда не вызывает
обычный coding `executor.run`: режим `plan` не является sandbox от prompt injection.
Допускается только явно объявленный `runUntrusted` — одноразовый model-only transport без
coding tools, project/user rules, MCP, hooks, session и workspace. Claude запускается в
отдельном временном cwd с пустым набором tools и strict/safe config; Ollama получает прямой
HTTP model call без toolbox. Codex/Kimi до отдельного безопасного transport остаются
fail-closed (`unsafe_model_provider`).

Visual path не попадает ни в prompt, ни в executor. Сервер разрешает realpath только внутри
`mediaDir/inbox-attachment-analysis`, открывает обычный файл без symlink, проверяет размер,
формат и сигнатуру и передаёт адаптеру лишь `{mediaType, base64}`. Выбранная модель обязана
объявить image modality, а transport — конкретный media type и предел изображений; иначе
результат `unsupported_media`, без молчаливого отбрасывания кадров. Эти capability входят и
в живую readiness автомата: несовместимая выбранная модель не показывается как `ready`.

Лимит одного обращения — 12 вложений и 80 МБ суммарно; Telegram дополнительно ограничивает
один файл 20 МБ. Успешный производный результат кэшируется под hash в `mediaDir`, provider
refs, token и native IDs в prompt, B24 и cache не попадают. Fingerprint учитывает текущие
speech-настройки, поэтому смена модели, языка или hotwords не возвращает старый транскрипт.
Cache ограничен 512 МБ и TTL 30 дней; старые временные каталоги удаляются, а key защищён
от GC до завершения анализа и чтения visual inputs моделью. Автомат всегда fail-closed:
неполный разбор оставляет item человеку.

**Причина неразбора обязана быть названа.** Канал возвращает по каждому пропущенному
вложению МАШИННЫЙ код (`file_too_large`, `attachments_too_large`, `too_many_attachments`,
`not_connected`, `download_failed`) плюс числа `sizeBytes`/`limitBytes`, а человеческую
фразу собирает кокпит (`lib/inbox/skip-reason.js`). Свободный текст ошибки провайдера
наружу не идёт вовсе: в него попадает URL с токеном, а показывать его предстоит в браузере
и в описании задачи; подробности остаются в журнале сервера. Список неразобранных вложений
уезжает и в отказ HTTP (`attachments: [{label, reason}]` при `attachment_analysis_required`
и `attachments_skipped`), и в публичное состояние автомата
(`worker.analysisRequired[].attachments`). Без этого «не удалось разобрать» одинаково
выглядело у потолка Bot API в 20 МБ (ожиданием не лечится) и у сетевого сбоя (лечится),
и человек не знал, ждать ли повтора. По той же причине разные тексты: у
`download_failed` фраза прямо зовёт повторить позже.

**До кода `download_failed` дело доходит только после повторов.** Скачивание вложения
идемпотентно (`getFile` и байты ничего не меняют на стороне Телеграма), поэтому канал
выдаёт этим вызовам право на две дополнительные попытки с паузами 0,5 и 1,5 с
(`retries` в `lib/telegram/api.js`). Отказ самого Телеграма (`kind: 'telegram'`:
неверный токен, файл сверх предела) не повторяется никогда — ожиданием он не лечится, а
человек тем временем ждёт ответа формы. Отправка сообщений этого права не получает:
у неё нет idempotency key, и повтор означал бы дубль в чужом чате.

**Ручное создание при неполном разборе идёт через пояснение оператора.** Кнопка «Создать
задачу» отвечает отказом, карточка сразу открывает поле «что имелось в виду», и текст
уезжает полем `operatorNote`. Дальше обращение проходит обычный разбор: пояснение попадает
в prompt триажа отдельным блоком как достоверный источник (человек видел вложение в самом
канале), модель формулирует постановку, и только после этого создаётся задача. Само
пояснение всегда попадает в описание отдельной секцией, рядом с перечнем неразобранных
вложений — исполнитель обязан видеть, что видео не расшифровано и пересказ человека
является единственным источником его содержимого. Пустое пояснение не принимается, автомату
поле запрещено (`invalid_service_call`), а отказ или отсутствие модели ручную постановку не
запирают: суть уже сказана словами. Прежний булев `allowUnanalyzedAttachments` удалён — он
ставил задачу из голого текста сообщений, и обращение «на видео предложение по доработке»
превращалось в задачу без сути.

Автоматическая B24-задача после успешного разбора получает сформулированную моделью
постановку и source URL (для Telegram — ссылку на сообщение, если Telegram позволяет её
построить). Сырой transcript, имя модели и служебная подпись Inbox в описание не попадают;
модель, confidence и причина решения остаются в audit-записи decision.

**Что уезжает файлом на портал, решают две галки плагина Inbox** — `attachPhotos`
(по умолчанию включена) и `attachVideos` (выключена). Разбора вложений они не касаются
вовсе: речь, кадры видео и текстовые документы модель читает всегда, настройка ограничивает
только загрузку исходных байтов в B24. Стороны у неё разные по смыслу: **автомату выдаётся
ТОЛЬКО разрешённое** — человеческого суждения за ним нет, поэтому документы и голосовые он
на портал не отправляет ни при каких галках; **у человека настройка снимает запрещённое**, а
остальные выбранные им файлы прикладываются как раньше, в том числе при постановке задачи
с пояснением оператора. Пояснение — это согласие поставить задачу без машинного пересказа
содержимого, а не согласие залить видео на портал.

Группы считаются по `kind` вложения: фотографии — `photo`/`image` плюс `document`/`sticker`
с растровым расширением (картинка, присланная файлом, остаётся картинкой), видео — `video`,
`video_note` и `animation`. Настройка читается непосредственно перед загрузкой, а не в начале
хода: между materialize и порталом успевают отработать Whisper и model call, и из двух
прочтений верно то, что ближе к side effect.

## Разбиение карточки на несколько задач

**Карточка — это разговор, а не одна просьба.** В неё склеены все сообщения человека за
окно тишины, и в них законно лежат несколько независимых поводов вперемешку с болтовнёй.
Поэтому модель отвечает не одним вердиктом, а **планом разбиения**: массив `statements`,
у каждого — свои номера сообщений (`buildInboxTriagePlanPrompt` нумерует transcript,
`parseInboxTriagePlan` разбирает ответ). Один model call на карточку остаётся один: план
не стоит дороже прежнего вердикта.

Каждая постановка становится отдельным решением на своё точное подмножество сообщений —
тем же `InboxTaskService`, что и кнопки человека. Пять инвариантов:

- **пересечение номеров отвергает весь план**: два решения на одно сообщение запрещены
  контрактом decisions, а молча выбросить лишнее означало бы решить за модель;
- **непокрытые номера законны**: их сообщения остаются `new`, карточка становится `mixed`
  и уходит человеку. Так же ведёт себя обрезанный по лимиту transcript — модель не может
  распределить то, чего не видела, и приписывать ей это нельзя;
- **ворота карточки и ворота повода разные**: статус, cold, возраст и участие канала
  проверяются один раз на карточку, а уверенность и дневная квота — на каждую постановку.
  Квота тикает по ЗАДАЧАМ, а не по обращениям;
- **неуверенный повод не отменяет соседние**: он просто остаётся человеку;
- **первый отказ останавливает разбор карточки целиком**: остаток честно уходит человеку,
  а не едет по уже изменившемуся состоянию.

Разбитая карточка перечитывается перед каждым решением (`_statementContext`): своё решение
меняет `revision`, а ссылка задачи обязана вести на первое сообщение ИМЕННО этого повода —
у разговора и у задачи головы разные. Карточка с единственным поводом на все сообщения
идёт прежним путём, без лишнего чтения.

Второй режим триажа сохранён: `runInboxTriage({mode: 'verdict'})` возвращает один вердикт
и используется при ручной постановке — там подмножество уже выбрал человек, и делить нечего.

**Кнопка «Создать задачу» тоже прогоняет обращение через модель.** Ручной путь зовёт
verdict-триаж для ЛЮБОГО выбора — голого текста, вложений, пояснения оператора — с
признаком `decided` («человек уже решил, что задача нужна: сформулируй постановку»).
Успешная формулировка ложится как у автомата: заголовок и постановка модели вместо сырого
transcript, отдельной строкой ссылка на источник; сырой разбор вложений (расшифровка речи,
прочитанные документы) остаётся отдельной секцией описания, а модель, уверенность и причина
— в audit note решения, не в задаче. Отказ модели ведёт себя по-разному, и это намеренно:
у голого текста и у пояснения оператора суть уже сказана словами, поэтому недоступная или
упавшая модель НЕ запирает ручную постановку — задача уезжает текстом обращения «как есть»
(в журнале сервера это `info`, не ошибка); визуальный инвариант прежний — изображение или
кадры видео, которые модель не прочитала, без пояснения оператора задачей не становятся
(`attachment_analysis_required`). Вердикт `kind: "none"` формулировкой не считается:
человек уже решил ставить задачу, поэтому тело остаётся текстом обращения, а мнение модели
уходит в секцию «Выжимка разбора».

## Telegram

Страница `/telegram` управляет bot token, `recheck`, `disconnect`, long polling, служебным
личным чатом, нативным архивом и allowlist `чат/тема → проект`. Telegram группирует сообщения
по МЕСТУ разговора — тема форума, а где тем нет, сам чат; окно тишины — 600 секунд. Байты вложений
materialize через Bot API лениво: перед автоматическим разбором либо при ручном создании
задачи. До этого в архиве остаётся только provider-owned ссылка на файл.

**Одно обращение = переписка одного места за окно тишины, а не реплика одного участника.**
Автора в ключе склейки нет намеренно (`inboxBundleKeyOf`): просьба и уточнение соседа
принадлежат одному поводу, и разведение их по карточкам ставило бы две задачи там, где
повод один. Живой случай: «когда сделаем пересчёт» и ответ «не раньше ПН» через сорок
секунд в одной теме форума приезжали двумя карточками — ключ нёс автора. Отдельных веток
у reply и media group тоже нет: и ответ, и части альбома лежат в том же месте, а своя ветка
у альбома, наоборот, ОТРЫВАЛА его от текста, отправленного рядом. Прежние ветки
`parent`/`thread-author` вдобавок разъезжались сами: reply на сообщение старше activation
или на остывшую связку получал уникальный ключ `['parent', <старый id>]`, который не
склеивал ничего и при этом отменял склейку по месту — три подряд идущих реплая давали три
карточки и три B24-задачи с потерянным между ними уточнением.

Цена решения названа честно: окно тишины скользящее, поэтому в живой теме, где пишут чаще
чем раз в десять минут, карточка растёт и приезжает длинной. Против этого работает то, что
уже есть, — модель отвечает планом разбиения на несколько задач, а человек выбирает
подмножество сообщений чекбоксами; нерешённые сообщения остаются в очереди.

Границу разговора держит только окно тишины: ответ на сообщение остывшей связки начинает
новое обращение и не дописывается в уже разобранную человеком карточку.

У каждого allowlist-правила есть выключенный по умолчанию opt-in
`notifyTaskCreated`. После успешного создания B24-задачи и durable commit решения общий
`InboxTaskService` просит Telegram channel отправить в exact исходный чат/тему plain-text
ответ с номером задачи, её названием и безопасной ссылкой на портал. Название обязательно:
номер не говорит, ЧТО из разговора уехало в задачу, а после разбиения карточки таких номеров
в чате появляется несколько подряд. Собрала его модель по недоверенному тексту, поэтому оно
схлопывается в одну строку (управляющие символы и переносы — в пробел) и режется по 200
символам; `parse_mode` не отправляется вовсе. При переполнении сообщения первой отбрасывается
ссылка, следом название — номер задачи остаётся всегда.
Это один post-commit path для ручной
и автоматической постановки. Сообщение отвечает на первое выбранное в authoritative порядке
сообщение (`reply_parameters`, для форума также `message_thread_id`); удалённый оригинал не
мешает отправке. Ошибка или timeout Telegram не отменяют уже созданную
задачу. Автоматического retry нет: Bot API не даёт idempotency key, поэтому после
неопределённого timeout повтор мог бы прислать дубль. Гарантированная доставка потребовала бы
отдельного durable outbox; текущий контракт — best effort, at most once.

**Но неудача доставки обязана быть видимой.** Раз повтора нет, сообщить в чат придётся
человеку — а он узнавал об этом только из журнала сервера. Поэтому успешный ответ `task`
несёт `notification: {enabled, sent, reason}`: `enabled: false` значит «правило ответа не
обещало», `sent: false` — «задача создана, ответ не ушёл». Причина словарная
(`unreachable` — не доехали, `rejected` — канал отказал, `failed` — прочее): свободный текст
отказа провайдера несёт URL с токеном и наружу не идёт вовсе. Карточка `/inbox` показывает
это жёлтой плашкой рядом с «Задача создана». Единственный рычаг против моргнувшей сети у
самой отправки — дать первой попытке дойти, поэтому её таймаут равен клиентским 15 с.

У того же rule есть отдельный additive opt-in `agentSearch`. Новый strict store сохраняет
exact owner-bound schema v2 с `accountRef` и verified `botId`. Старый ownerless файл
остаётся рабочим human allowlist, но любой сохранённый в нём `agentSearch` принудительно
читается как `false`: прежнее или пересаженное разрешение нельзя унаследовать. Первый новый
human write либо отдельный explicit agent-search CAS переписывает файл в schema v2;
несовпадение account/bot и malformed v2 дают fail-closed отказ. Новое правило также
нормализуется в `agentSearch: false`; human allowlist и обычный разворот ссылок от него не
зависят. Обычный `PUT /api/telegram/rules` не принимает это поле и при правке
остальных настроек сохраняет opt-in только для exact того же `project + chat/topic` scope.
Переключение доступно отдельной ручкой `PUT /api/telegram/rules/agent-search` с exact rule
ref, boolean `enabled`, `botId` и CAS по `expectedPolicyFingerprint`; включение в UI требует
отдельного подтверждения. Canonical SHA-256 fingerprint включает `accountRef` и всю
нормализованную policy, включая `agentSearch`. Fingerprint/CAS не подменяет будущие durable
policy epoch и `PolicyScopeFence`: до них отзыв не обещает дренирование уже начатого ответа.

Тот же allowlist защищает разворот `t.me`-ссылок в B24, тикете конвейера, чате агента и
триаже. Поддерживаются public `t.me/<username>/<message>`, forum-вариант с thread,
private `t.me/c/<internal>/<message>` и comment links; парсер не угадывает тип чата по
одному URL. Resolution идёт в строгом порядке: account archive → временный
`forwardMessage` в служебную личку с немедленным удалением → именованный отказ без текста
и имени запрещённого чата. Scope проверяется до network и ещё раз по найденному message;
ссылка разрешена только для чата/темы, привязанных к требуемому project.

Служебный чат хранится в namespace конкретного bot. Disconnect его не удаляет; возврат к
тому же bot восстанавливает настройку, новый bot ничего не наследует.

Архивные строки без position journal остаются доступной для разворота ссылок историей,
но не попадают в Inbox. Даже поздняя правка такой строки не превращает её в новое
post-activation обращение.

## GitHub Issues

V1 подключает один repository `github.com` и принимает только `issues/opened`. Один issue —
одно сообщение/item, `settleMs=0`; pull requests, comments, edits и attachments не входят
в v1. Allowlist содержит exact repository owner и выбранный B24 project.

У rule есть отдельный additive opt-in `agentSearch`. Старый файл без поля и новое правило
нормализуются в `agentSearch: false`; человеческий Inbox от него не зависит. Обычный
`PUT /api/github/rules` не принимает это поле и при редактировании kind/B24 сохраняет
его текущее server-owned значение; перенос rule в другой project fail-closed сбрасывает
opt-in. Переключение доступно только отдельной ручкой
`PUT /api/github/rules/agent-search` с exact `repositoryId`, boolean `enabled` и CAS по
`expectedPolicyFingerprint`, полученному из `GET /api/github/rules`. Canonical SHA-256
fingerprint включает account, repository и всю нормализованную policy, в том числе
`agentSearch`; stale форма получает `409 github_rules_stale_policy`. Этот CAS-контракт не
подменяет будущие durable policy epoch и `PolicyScopeFence`: до их появления агентский
поиск по внешнему корпусу не считается готовым к production.

`POST /api/github/connect` проверяет repository через authenticated REST, использует
immutable `repository.id`, создаёт управляемый webhook только на operator-owned HTTPS
callback и завершает connection лишь после signed ping на
`POST /hooks/github/:ingressRef`. HMAC-SHA256 проверяется по exact raw body до JSON parse.
Ingress также сверяет hook ID, target/repository ID, generation и delivery GUID.

Dedupe durable по двум ключам: transport `X-GitHub-Delivery` и semantic
`repository.id + issue.id`. После connect/start и затем раз в пять минут bounded REST
reconciliation восстанавливает потерянные webhook deliveries; pull requests отбрасываются.
При недостижимой сохранённой boundary cursor не продвигается и канал становится degraded.
Issues REST возвращает mutable текущую проекцию: обычный edit уже известного issue является
semantic duplicate/no-op. Первый принятый snapshot остаётся immutable, archive sequence и
activation не двигаются, а повторная reconciliation продолжает работу без ложного conflict.

Disconnect немедленно закрывает локальный ingress, затем удаляет только сохранённый remote
hook. Если GitHub недоступен, состояние становится `remote_cleanup_pending`; повторный
disconnect повторяет cleanup. Operator-only `POST /api/github/force-forget` требует
`{"confirmOrphanHook":true}` и допускает оставшийся remote orphan hook. Account data purge
в v1 отсутствует.

До реального connect оператор задаёт `COCKPIT_GITHUB_WEBHOOK_BASE_URL` как публичный HTTPS
base без query/fragment, создаёт fine-grained PAT для одного repository с Metadata read,
Issues read и Webhooks write, затем выбирает B24 project в rules и явно активирует GitHub
на `/inbox`. Код, тесты и установка сами remote webhook не создают.

## Общий автомат

Единственный `InboxAutoTasks` запускается и останавливается в `app.js`. Модель выбирается
в настройке `triageModel` плагина Inbox и применяется ко всем каналам; собственного
provider HTTP client у Inbox нет. `autoTask`, minimum confidence и daily quota принадлежат
точному allowlist scope канала. Подготовленное содержимое вложений и проверенные visual bytes
входят в тот же model call до решения. Модель отвечает планом разбиения карточки, поэтому
одно обращение может дать несколько задач; правила и инварианты — раздел «Разбиение карточки
на несколько задач». Нет модели, безопасного transport/image capability,
ошибка разбора/materialize/B24, превышенная
quota или любое сомнение оставляют соответствующие сообщения человеку.

Runtime читает модель только из `pluginSettings.inbox.triageModel`. Старый Telegram-owned
ключ не импортируется и не используется как fallback; если он сохранился в prefs, это
неактивное неизвестное поле. Штатные изменяемые ворота (`no_model`, `unsafe_model_provider`,
`unsupported_media`, `no_b24`, выключенный плагин) перепроверяются раз в минуту;
пятиминутный backoff оставлен только техническим ошибкам чтения снимка.
Неполный media-анализ конкретного item имеет отдельный шестичасовой cooldown и остаётся
видимым человеку; это не закрывает fair cursor для остальных обращений.

Лимит model calls на один tick не является лимитом глубины очереди: fair cursor каждой
runtime generation продолжает следующий tick после последнего реально проверенного item.
Поэтому постоянная ошибка или низкая уверенность на первых обращениях не закрывает более
глубокие; account switch сбрасывает cursor вместе с generation.

Исторические аргументы, fixture и последовательность работ сохранены в игнорируемых
рабочих файлах `docs/plans/inbox-github-channel-adr.md` и
`docs/plans/inbox-channels-plan.md`; канонический внедрённый контракт находится здесь.
