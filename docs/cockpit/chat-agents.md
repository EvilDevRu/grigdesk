# Чат с агентами, базы agents/routes, реестр исполнителей

Этот документ описывает **исполнителей интерактивного чата Cockpit**. Автоматический
project/stage failover движка фабрики — отдельный слой с собственным canonical config,
coverage и error policy; он описан в [multi-AI контракте движка](../engine/MULTI-AI.md).
В чате смена provider-а пока явная: пользователь выбирает другую модель, история остаётся,
а несовместимый CLI session context сбрасывается.

## Чат (modules/chat)

- Сервер определяет executor по выбранной модели из `/api/providers`. Claude запускается как
  `claude -p … --output-format stream-json --verbose [--model][--effort][--resume]`;
  Codex — `codex exec --json` / `codex exec resume`. По задаче cwd = первый worktree
  из exact-списка `REPO_COUNT`/`REPO_<i>_*`, остальные передаются через `--add-dir`.
  Для старых песочниц без `REPO_*` совместимо читаются `BE_WT` и `FE_WT`.
  Без задачи cwd = `config.rootDir` (корень репозитория кокпита — исполнитель сразу видит
  корневые AGENTS.md/CLAUDE.md); страница «Агенты» переопределяет его на `agents/`.
  Codex работает в `workspace-write`: пишет в cwd и дополнительные `--add-dir`, но не получает
  полный доступ к хосту. `sandbox_workspace_write.network_access=true` разрешает сетевые
  команды внутри этой песочницы (`gh`, `git`, пакетные менеджеры).
  У продолжения `--sandbox` и `-C` стоят до подкоманды `resume`: это опции родительского
  `codex exec`, после `resume` актуальный CLI их отвергает ещё до запуска хода.
- **Доверенные каталоги** задаются один раз в «Настройки → Исполнители» и хранятся в
  `prefs.trustedDirectories`. Сервер проверяет realpath каждого существующего абсолютного
  каталога, не разрешает `/`, убирает дубли и перед каждым новым ходом добавляет список в
  `extraDirs`. Claude и Codex превращают его в `--add-dir`. У `kimi acp` такого флага нет.
  Запуск Kimi имеет два режима (`config.kimiLaunchMode`, умолчание `host`): в host-режиме
  Kimi — прямой хост-процесс (parity с claude: host fs/config/credentials, permission-система
  самого CLI), и `extraDirs` ему недоступны — доступ за пределами cwd идёт через
  permission-промпты. В contained-режиме sandbox монтирует каталоги writable bind-ом и
  объявляет их сессии через server-owned
  `local.toml` (`[workspace] additional_dir`) в per-run каталоге-маске, заменяющем
  `<projectRoot>/.kimi-code` целиком (kimi-runtime-security.md). Доверенный каталог может
  содержать сам репозиторий cockpit: в contained-режиме server-owned control state внутри
  него (`chats/`, `server/.state`, `.env`, runtime/factory state) прячется пустым read-only
  mount-ом; в host-режиме этой маски нет — как у claude.
  Глобальные `~/.claude` и
  `~/.codex` Cockpit не переписывает, активный ход не меняется — следующий подхватывает
  настройку без рестарта. Поддержку списка объявляет сам адаптер полем
  `trustedDirectories: true | (config) => boolean`; реестр отдаёт вычисленный boolean в
  `/api/providers`, а UI перечисляет имена поддерживающих исполнителей из этого ответа.
  Поэтому новый исполнитель появляется в подписи без ветки по его id во Vue, а Kimi
  автоматически появляется/исчезает при смене contained/host-профиля.
- `contextTokens` — вход последнего model request, то есть активная заполненность контекста.
  Для Claude он приходит из последнего assistant-event **и уезжает в окно ЖИВЬЁМ**, на каждом
  обращении к модели: вторым (необязательным) аргументом `onProgress` → SSE `chat-progress`
  полем `contextTokens` → рантайм-поле `liveContext` в сторе → кольцо, пока идёт ход. В историю
  оно НЕ пишется (`contextTokens` в `slimOf`, запись на каждое обращение стоила бы PUT чата);
  замер поднимается и после F5 — `GET /api/chat/active` отдаёт его вместе с лентой. Исполнитель,
  который замер не сообщает, зовёт `onProgress` одним аргументом, и кольцо живёт как раньше —
  цифрой с прошлого хода. Почему разница не косметическая — см. [грабли](gotchas.md).
  **`contextWindow` claude не сообщает нигде** (проверено и по потоку, и по бинарю CLI): размер
  окна берётся из каталога моделей, и придумывать ему источник в потоке нечего.
  У Codex `turn.completed.usage.input_tokens`
  использовать нельзя: это накопительный расход всех model request в thread, после tool-call он
  ещё раз прибавляет весь вход и легко доходит до миллионов. Codex executor читает последний
  `token_count` своего rollout: `last_token_usage.input_tokens` идёт в `contextTokens`,
  `model_context_window` — в `contextWindow`. Старые GPT-чаты без
  `contextMetric=active-input-v1` не заполняют кольцо ложным числом: точная дуга появится после
  следующего хода. `CONTEXT_WINDOW=200000` во фронте остаётся fallback.
  У Kimi размер снимается локальными ACP-командами после хода (`parseStatus` в
  `server/src/lib/kimi/runtime.js`): 0.31 отдаёт строку `- Context:` в `/status`, с 0.33 её
  вынесли в `/usage` — runtime добирает её второй командой, когда в `/status` размера нет.
- **Prompt cache — отдельная provider-neutral метрика ПОСЛЕДНЕГО model request**, а не часть
  шкалы кольца и не накопительный расход сессии. Executor отдаёт
  `contextCache: { scope: 'request', status, readTokens?, writeTokens?, uncachedTokens? }`,
  где `status` — `reported`, `unavailable` или `not-applicable`. Claude сообщает чтение,
  запись и некэшированный вход; Codex — чтение и некэшированный вход, но не выдумывает
  отсутствующую у CLI запись; Kimi явно отдаёт `unavailable`; у локального Ollama статус
  `not-applicable`, потому что его KV-кэш нельзя приравнивать к тарифицируемому prompt cache.
  Отсутствующее числовое поле означает «provider не сообщил», а не ноль. По одному размеру
  контекста кокпит не делает вывод ни о cache hit, ни о цене: подсказка показывает только
  фактические read/write/uncached, которые пришли в `contextCache`.
- Память агента — в сессиях выбранного CLI. Для Claude/Codex Cockpit хранит `sessionId`
  в записи чата; у Kimi resume id принадлежит отдельному server-owned CAS sidecar-у
  (`ChatSessionBindingStore`), поэтому stale/поддельный PUT браузера не может назначить session.
- **Пустой ответ Claude («пусто»):** `claude -p` может вернуть result без текста — агент завершил ход
  tool-call'ом, который plan-режим запретил (Bash/Write и т.п.), или упёрся в лимит шагов.
  Сервер маппит это в понятное «⚠ …»-сообщение (по `subtype` и `permission_denials`) и пишет
  warn в лог. Типичный триггер: просьба «сделай/запусти/разбери файл» — чат только читает.
- Один Pinia-стор `chat` питает и плавающую панель (ChatPanel, есть на всех страницах, кроме `/chats`), и страницу «Чаты» (ChatsView, телеграм-раскладка: ChatList-сайдбар + ChatSession).
- **Плашки над композером — отдельные компоненты** рядом с `ChatSession.vue`: `StepList.vue` (лента шагов
  хода), `ChatQuestion.vue` (вопрос агента), `ChatPermission.vue` (запрос разрешения / план на
  утверждение). Каждая держит свою разметку, стили и мелкое состояние; ChatSession только решает,
  какую показать, и передаёт ответ в стор. Разрешение и вопрос приходят по SSE в стор глобально —
  компонент показывается, если `chatKey` совпал с открытым чатом (`forThisChat`).

### Лента хода агента (как в чате VS Code)

- У ленты один provider-neutral контракт (`lib/chat/stream-steps.js`): `start`
  (фактическая модель + режим прав), `think`, `text`, `tool` (вызов инструмента с превью по типу:
  команда Bash, файл Read/Write, дифф Edit, запрос Grep…), `res` (результат: ok/ошибка + краткий вывод),
  `note` (ретраи API, компакт). Общий sink ставит timestamp, режет всё длинное и ограничивает
  ход 400 шагами (хранение скользящее, трансляция безусловна — см. [грабли](gotchas.md)).
  Каждый executor держит свой normalizer (`_claude-steps.js`, `_codex-steps.js`,
  `_kimi-steps.js`); новый ИИ добавляет такой же рядом с executor-ом, без условий
  в `modules/chat` или Vue.
- **У размышления свой лимит — `STEP_THINK_LIMIT` 6000 символов** против `STEP_TEXT_LIMIT`
  1200 у остального текста (`STEP_DIFF_LIMIT` 2000 на кусок диффа). Общие 1200 резали
  рассуждение на первом же абзаце, и в ленте оставался огрызок фразы: со стороны это
  выглядело как «размышлений не видно вовсе» — ровно та жалоба, с которой лимит и развели.
  Размышление — единственный шаг, который человек читает целиком, а не проглядывает.
- Путь: `executor run(onStep)` → `modules/chat` → SSE `chat-step {chatKey, step}` → стор копит в
  `sess.steps` → `views/chat/StepList.vue`. Claude читает свой stream-json, Codex — JSONL построчно
  ещё во время работы, а не после завершения процесса. У Codex тип `reasoning` показывает только
  отданное CLI summary (`text`/`summary`); техническое `raw_content` намеренно игнорируется.
  Копия шагов лежит в `activeRuns`, поэтому F5 посреди хода не теряет уже показанное
  (`GET /api/chat/active` отдаёт `steps`).
- **Codex запускается с `-c model_reasoning_summary="detailed"`** (`buildCodexExecArgs`): дефолтное
  summary у CLI короткое, и в ленту приезжала оборванная фраза — не лимит кокпита, а то, что
  отдал сам CLI. Ключ валидируется бинарём (проверено: неизвестное значение → `codex doctor`
  fail), приватную цепочку `raw_content` это не включает. У Kimi ACP отдаёт размышление
  отдельным типом контента (`thought`), у claude — блоками `thinking` потока.
- После ответа лента переезжает в сообщение (`msg.steps`) и показывается свёрнутой строкой
  «Ход агента: N действ. · M размышл.». Дифф правки строит фронт (`shared/diff.js`, LCS по строкам;
  свыше 400 строк — вырожденный «всё убрано / всё добавлено») и показывает В ДВЕ КОЛОНКИ —
  слева «было», справа «стало» (`splitRows`: подряд идущие del/add ставятся друг напротив друга,
  лишние строки получают пустого соседа).
- **Всплывашки держим компактными** — они живут над композером и не должны съедать экран:
  у разрешения кнопки в строке заголовка, команда — блоком с переносами; у вопроса варианты —
  строками с пояснением, поле своего ответа скрыто за пунктом «свой ответ…»; вся плашка
  ограничена по высоте со скроллом (`max-height: 38vh`).
- Время размышления («думал 12 с») считается по `at` соседних шагов — от предыдущего шага к `think`:
  блок размышления приходит уже готовым, поэтому его длительность — это пауза ПЕРЕД ним.
- Подряд идущие одинаковые `note` схлопываются в одну строку с «×N» (ретраи сети идут сериями).

### Диалог: агент задаёт вопрос (AskUserQuestion)

- В headless-режиме сам инструмент отвечать некому: выполненный AskUserQuestion возвращает агенту
  пустое «User has answered your questions: .». Поэтому вопрос перехватывается на уровне
  permission-prompt-tool (он получает `tool_name: AskUserQuestion` с полным списком вариантов),
  а ОТВЕТ пользователя возвращается как `behavior: 'deny'` с текстом в `message` — единственный канал,
  по которому текст доезжает до агента дословно (проверено: агент читает его как результат
  инструмента и продолжает ход).
- Поток: SSE `chat-question {pid, chatKey, questions, at}` → `views/chat/ChatQuestion.vue` (варианты,
  мультивыбор, поле «свой ответ») → `POST /api/chat/permission/:pid {answers}` → сервер собирает текст
  («Ответ пользователя из кокпита: • Заголовок: Вариант»). Пропуск — пустые answers.
- **Возможности канала объявляет исполнитель, а не угадывает всплывашка.** У вопроса есть
  `multiSelect` и `allowFreeText`, и у ACP-моста Kimi оба ложны: `session/request_permission`
  принимает РОВНО ОДИН `optionId` и ничего больше. Пока `allowFreeText` не передавали, окно
  рисовало чекбоксы и поле своего ответа — человек отмечал два варианта и дописывал текст,
  а до агента доезжал один вариант: выбор молча терялся. Теперь такой вопрос показывается
  строкой-подсказкой `hint` («ACP-мост Kimi принимает ровно один вариант»), чекбоксы и поле
  не рисуются вовсе, а если текст всё же введён (другой канал), ответ помечается
  `textDelivered: false` — тем же правилом, что и `commentDelivered` у отказа.
- Из-за этого AskUserQuestion попадает в `permission_denials` результата; в `claude.js` он исключён
  из списка «действия не были разрешены», иначе пустой ответ подменялся бы ложным предупреждением.
- `ExitPlanMode` остаётся обычным разрешением, но в всплывашке показывается как план
  (текст целиком, кнопки «Утвердить план» / «Доработать»).
- **Отказ — с пояснением**: «Отклонить»/«Доработать» открывает модалку с полем текста
  (`promptDialog` в `web/src/shared/ui/confirm.js`; пустое — как раньше, Esc — отмена отказа).
  Пояснение едет в `POST /api/chat/permission/:pid` полем `comment`: у claude оно вкладывается
  в deny-message («Пользователь отправил план на доработку. Что изменить: …») — агент читает
  его прямо в ходе, как ответы на вопросы. **Доезжает ли текст — свойство КАНАЛА, а не
  вендора**: ACP-outcome Kimi текста не несёт, а результат инструмента Ollama несёт, поэтому
  ожидание помечается `acceptsComment` при создании, а ответ — `commentDelivered`. Если текст
  не доехал, фронт отправляет пояснение обычным сообщением в очередь чата. Запись плана
  в переписке дополняется строкой «**Пояснение:** …».
- **Всплывашка одна на всех, вендорных веток в ядре нет.** Ожидание помечается флагом
  `direct`: исполнитель ждёт ответа сам (ACP reverse-RPC у Kimi, цикл инструментов у Ollama),
  без локального HTTP MCP-процесса, как у Claude. От флага зависит только ФОРМА ответа
  (`{allow, comment, remember, choice}` против MCP-JSON), поэтому новый прямой исполнитель
  ничего не добавляет ни в `modules/chat`, ни во фронт. Классификатор авто-режима — общий
  `autoDecision` (`lib/chat/auto-approve.js`) по словарю ACP-действий `toolCall.kind`
  (`read`/`search`/`edit`/`execute`/`delete`); исполнитель обязан лишь назвать свой вызов
  одним из этих типов, а не заводить вторую политику рядом.

#### Что рисует всплывашка разрешения (контракт `input`)

`ChatPermission.vue` показывает не сырой запрос, а РАЗОБРАННЫЙ: `description` (что просят),
`details`/`plan` (шапка запроса), `command`, `file_path`, `diff` (две колонки, тем же
`shared/diff.js`, что и лента) и `choices` — специфические кнопки варианта. JSON остался
последним фоллбэком для незнакомой формы. Раньше фоллбэк был единственным путём: Kimi
приезжал объектом ACP, и человек читал `{"toolCall":{"toolCallId":…}}` вместо «правлю такой-то
файл» — решение принималось вслепую.

Собирает это сам адаптер (`permissionPresentation` в `lib/kimi/runtime.js`), и там два
неочевидных места:

- **ACP-запрос разрешения не несёт ни `kind`, ни аргументов вызова** — только `title` и
  текстовые блоки. Тип действия и команду runtime помнит по `toolCallId` из notification
  `tool_call`/`tool_call_update`; без этого классификатор «Авто» спрашивал бы про каждое
  чтение файла (проверено тестом «тип и команда читаются из восстановленного input»).
- **Правку Kimi отдаёт структурным блоком** `{type:'diff', path, oldText, newText}`, а не
  текстом: пока читались только текстовые блоки, дифф в всплывашку не попадал вовсе.

Обратный ход — три поля ответа, и каждое чем-то оплачено:

| поле | что делает | почему не «политика кокпита» |
|---|---|---|
| `choice` | нажатая кнопка из `choices` едет обратно своим `optionId` | у плана ACP различает «доработать» и «отклонить и выйти»; общего allow/deny для них мало |
| `remember` | «разрешать до конца сессии» → ACP-вариант `allow_always` | галка жила только в памяти вкладки: агент спрашивал снова из каждого окна и после F5 |
| `comment` | пояснение к отказу | ACP-outcome текста не несёт → `commentDelivered: false`, фронт досылает сообщением |

### Режимы прав (`--permission-mode`)

- **Список режимов даёт сам CLI, не хардкод.** Флага нет в `--help`, зато CLI перечисляет
  допустимые значения в ошибке валидации — `claude.js modes()` спрашивает его заведомо неверным
  значением и парсит «Allowed choices are …». Подписи известных режимов и порядок — в
  `MODE_LABELS` (от осторожного к свободному, план первым);
  незнакомый режим показывается как есть.
- Выбор живёт в чате (`sess.mode`) и запоминается как дефолт новых чатов (`defMode`), едет в теле
  запроса и санитайзится на сервере по тому же списку (кэш 10 мин — `modes()` запускает подпроцесс).
  Режим страницы (`pageMode`) остался только дефолтом, когда пользователь ничего не выбрал.
- Что меняется по факту: `manual` — всплывашка на каждое действие (как было), `auto` — безопасное
  делает сам, `acceptEdits` — правит файлы молча, `plan` — только читает и заканчивает планом,
  `dontAsk`/`bypassPermissions` — без подтверждений вовсе.
- **План остаётся в переписке**: при ответе на `ExitPlanMode` фронт добавляет в чат сообщение
  «План — утверждён / на доработку» с его текстом. Всплывашка закрывается, а решение принималось
  по этому тексту — он должен остаться в истории.
- **У каждого исполнителя свой список — это `modes()` его адаптера, а не общий enum.** У Kimi
  четыре пункта: «Спрашивать» (ACP `default`), «Авто» (тоже `default` + классификатор кокпита),
  «План» (ACP `plan`) и **«Без подтверждений» — родной ACP-режим `yolo`**: Kimi не спрашивает
  вовсе. Родной `auto` (решает сам Kimi) кокпит НЕ выставляет: в нём permission reverse RPC
  до кокпита не доходит, всплывашка перестаёт появляться и классификатору нечего решать.
  Полное соответствие режимов и цена каждого — в
  [kimi-runtime-security.md](kimi-runtime-security.md). У Ollama свой список
  (спрашивать некого — см. ниже), у Claude — прочитанный из CLI.

### Автопрокрутка

- Едем вниз на новые сообщения, шаги ленты и всплывашки — но ТОЛЬКО если пользователь и так внизу
  (`atBottom`, порог 120 px, отслеживается по `scroll` контейнера `.cs-body`). Отлистал историю
  вверх — не дёргаем. Отправка своего сообщения принудительно возвращает вниз (как в мессенджерах).
- **Грабля:** прокрутку тянули ещё два места — безусловный `watch` на длину сообщений и `scrollDown()`
  в хвосте `submit()`, который срабатывал ПОСЛЕ ответа агента (то есть спустя десятки секунд) и
  утаскивал вниз того, кто в это время читал историю. Оба убраны: единственная точка — `autoScroll`.

### Что реально ушло в запуск (проверка модели и эффорта)

- `actualModel` — модель из потока (`system/init.model`, точнее — `message.model` ходов). CLI резолвит
  алиасы сам: на 2.1.85 `opus` → `claude-opus-4-6`. Показывается строкой под панелью управления
  («факт: …») и подписью у ответа агента; расхождение с выбранной подсвечивается.
- Уровень эффорта санитайзится по реестру ПЕРЕД запуском: `--effort xhigh` для claude — не «игнор»,
  а падение CLI с ошибкой валидации (`It must be one of: low, medium, high, max`). Неподдерживаемый
  уровень заменяется на `high` и пишется warn в лог.
- **Команды и навыки**: ввод «/» в композере открывает меню CLI-команд, ввод «$» —
  меню нативных навыков Codex (фильтр по мере набора,
  ↑/↓ + Enter/Tab, Esc, клик). Меню двух секций: «Cockpit» (клиентские, на сервер не ходят:
  `/clear` — история+контекст, `/reset` — только контекст, `/new` — новый чат, `/compact` —
  сжатие) и секция исполнителя выбранной модели (цветной бейдж, имя из реестра).
  Список исполнителя — поле `commands?(config)` его адаптера (`server/src/lib/executors/*.js`),
  едет в `/api/providers` (общий 60-секундный кэш; источники cwd-независимы). Состав по
  исполнителям: kimi — статические ACP-команды + скан пользовательских скиллов
  (`<kimiHome>/skills/*/SKILL.md` в host-режиме, `<kimiRuntimeHome>/skills` в contained;
  ACP исполняет их как `/<имя>`, хотя `/help` их не перечисляет); claude — built-ins + скан
  `$CLAUDE_CONFIG_DIR/commands/*.md`; codex — информационный список TUI-команд плюс
  `skills/list` его app-server для включённых user/admin/system-навыков. Repo-навыки
  намеренно исключены из глобального `/api/providers`: его 60-секундный кэш не знает cwd
  конкретного task-chat и иначе показывал бы недоступную команду чужого worktree.
  Дедупликация по имени: команда кокпита глушит провайдерскую, built-in исполнителя — его скилл.
  Пункты `run: 'none'` (у codex это все TUI-команды: `exec` слэш-команды не исполняет)
  показаны серым с hint и не выбираются ни клавиатурой, ни кликом.
  `$skill` уходит обычным model prompt без `slashCommand`: Codex сам раскрывает явное
  упоминание в содержимое `SKILL.md` (синтаксис `$skill-name` — контракт самого CLI).
  Поэтому навык, в отличие от служебной `/`-команды, **уносит приложенные файлы**:
  «разбери вот этот скриншот» — обычный его сценарий, а у служебного хода вложений не
  бывает вовсе. Фильтр меню регистронезависим: имя навыка приходит от Codex как есть,
  и заглавные в нём законны. Канонический user-scope — `$HOME/.agents/skills`;
  устаревший совместимый — `$CODEX_HOME/skills`. Чтение read-only и в 60-секундный
  кэш реестра укладывается (замер живого `skills/list`: около 0,4 с на подъём
  app-server), поэтому отдельного ленивого эндпоинта ему не заводили.
  **Грабля:** класс выделения строки меню — `on`, не `sel` (`.sel::after` в этом же файле рисует шеврон селектов).
- **Провайдерская `/`-команда — служебный ход `slashCommand`**: `runCommand` шлёт
  `chat.send(sid, cmd, [], { slashCommand: cmd })`, без `requestTitle` и без provisional-заголовка.
  Сервер валидирует поле строго по списку `commands()` исполнителя (текст хода = сама команда,
  иначе 400 `unknown_slash_command` — полем нельзя обойти титул-хук/повторы для обычного текста).
  Для такого хода: титул-хук НЕ приклеивается (kimi матчит ACP-команды побуквенно — склейка
  превращала `/status` в «Unknown ACP command»), автоповтор пустого хода отключён и kimi-ветка
  emptyRun НЕ инвалидирует session binding (молчание локальной команды — штатно); пустой вывод
  подменяется плашкой `role: 'note'` («✓ Команда … выполнена локально — вывода нет.»).
  **Грабли, закрытые этим признаком:** claude `/clear` в `-p --resume` молча
  начинает НОВУЮ сессию с пустым stdout → emptyRun → автоповтор → ложный диагноз «нет сети»
  (поэтому `/clear` в списке claude нет вовсе); пустой ответ kimi без признака слёг бы
  в `kimi_empty_response` со сбросом сессии.
- **Автоназвание нового чата — общий хук Cockpit**: первый ход безымянного чата отправляется с
  `requestTitle`; `modules/chat` добавляет provider-neutral служебную инструкцию в тот же запрос.
  Агент возвращает маркер `COCKPIT_CHAT_TITLE` с осмысленным названием ровно из трёх слов,
  сервер валидирует его и вырезает из ответа/живой ленты, а клиент применяет как метаданные чата.
  Отдельного модельного вызова нет. Пока основной ход не завершён, `shared/chat-title.js` показывает
  мгновенный локальный вариант; ответ агента заменяет только его — ручное название и заголовок
  задачи всегда сильнее. Тот же заголовок едет через `chats/pending` после F5/закрытия окна.

### Кольцо контекста, prompt cache и сжатие

- **Кольцо показывает запас рабочего контекста, а не цену хода.** Размер контекста и
  переиспользование prompt cache связаны только наблюдаемым поведением конкретного запроса:
  большой контекст может почти целиком читаться из кэша, а маленький — переписаться после
  изменения префикса. Поэтому у кольца нет тарифной отсечки, а формулировка «ход уже
  подорожал» по одному `contextTokens` запрещена. Историческое наблюдение около 250k и его
  ограничения записаны в [граблях](gotchas.md).
- **Кэш показывается отдельным фактическим блоком** из `contextCache`: доля чтения и
  сообщённые `readTokens`/`writeTokens`/`uncachedTokens` относятся только к последнему
  model request. `unavailable` означает, что исполнитель не отдал телеметрию;
  `not-applicable` — что для него эта метрика не имеет такого смысла. Предупреждать о
  перезаписи можно только по реально пришедшему `writeTokens`, не по размеру контекста и
  не по id provider-а.
- **Собственный автокомпакт CLI привязан к доле окна модели.** Замер по сессиям, где компакт
  реально сработал: окно 200k → сжатие на ~166k, окно 1M → ~959–999k. Отдельная настройка
  кокпита позволяет раньше ограничить рабочий контекст ради управляемого размера и задержки;
  это не тарифная граница и не обещание cache miss.
- **Настройка «Запуски → Сжимать контекст чата при N токенах»** (prefs `chatAutoCompactWindow`,
  дефолт 200 000) кладёт порог туда, где он нужен. Claude получает его переменной
  `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, Codex — config override
  `model_auto_compact_token_limit=N` перед `resume`. Читается перед каждым ходом — правка
  действует сразу, без рестарта. `0` — не вмешиваться, у CLI остаётся собственный порог.
- **У ЭТАПОВ конвейера порог свой** — соседняя настройка и отдельный ключ prefs
  (`stageAutoCompactWindow`): границы рабочего контекста те же, а цена сжатия разная. В чате
  оно рвёт нить разговора с человеком, на этапе — просто ужимает рабочий контекст между вызовами
  инструментов, и трогать его можно смелее. Путь тоже другой: не переменная процесса CLI,
  а `FACTORY_STAGE_AUTO_COMPACT` в запуск движка, дальше `RUNNER_AUTO_COMPACT_WINDOW`
  раннеру — см. `docs/engine/ENGINE.md`. Применяется к новым ЗАХОДАМ, идущий этап
  доработает как есть.
- **Собственный автокомпакт CLI виден в ленте шагом `note`** («Контекст сжат: CLI сжал его сам,
  по порогу (было N ток.)»). Порог CLI проверяет НА ГРАНИЦЕ ХОДА, поэтому сжатие случается в
  начале хода, а весь остаток идёт уже по сжатому контексту: цифра в кольце падает втрое
  посреди работы, и без строки в ленте это читается как «кольцо врёт». Событие —
  `{type:'system', subtype:'compact_boundary', compactMetadata:{trigger, preTokens, durationMs}}`;
  `trigger: 'manual'` (это `/compact`) называется в тексте отдельно. `compactedAt` при этом НЕ
  ставится: после самосжатия размер известен точно (его сообщит ближайшее обращение к модели),
  а подсказка `compactedAt` обещает обратное — «размер покажется после следующего хода».
- **Кольцо ЦЕЛИКОМ — от ближайшей границы контекста, а не от глобального числа:**
  `ctxLimit = min(compact, 80% окна)`, где `compact` равен `chatAutoCompactWindow`, если
  тот больше нуля, иначе `Infinity`.
  Именно преобразование `0 → Infinity` сохраняет смысл настройки «не вмешиваться»:
  выключенное автосжатие не превращает минимум в ноль, и шкалой остаются 80% окна.
  Жёлтая зона начинается на 80% полученного `ctxLimit` (`ChatSession.vue`; порог сжатия
  приезжает в стор вместе с историей — `GET /api/chat/store` отдаёт его полем
  `compactWindow`, а «Настройки» после сохранения обновляют стор сразу).
  Кольцо краснеет там, где случится первое из двух событий: кокпит сожмёт контекст или он
  дойдёт до безопасной границы в 80% окна. Подсказка называет победившую границу поимённо
  («до сжатия» / «до 80% окна»); при равенстве первым называется сжатие. Текст жёлтой зоны
  нейтрален: «порог близко — пора сжать».
  **По тому же порогу считаются дуга и подсказка** (`ctxPct` → `ringDash`, «N из M до
  события»), а окно модели осталось в подсказке справочной строкой. Поэтому для Fable 5
  при 165 172 токенах и стандартном автосжатии 200k кольцо показывает **83% до сжатия**,
  а рядом справочно — окно 1M (сама заполненность окна — 17%). Если автосжатие выключено,
  шкалой станут 80% окна и кольцо покажет около **21% до безопасной границы**. Кэш при этом
  остаётся отдельным блоком фактов последнего запроса. Раньше шкалы были разными: цвет говорил
  одно, форма — другое, и верили форме — см. [грабли](gotchas.md).
  Сторож — `tests/web/chat-task-tooltip.component.test.js`.
- **Клик по кольцу — СЖАТИЕ** (с подтверждением), **Alt+клик — сброс памяти агента**, он же
  `/reset`. Раньше клик делал только второе, причём молча: переписка на экране остаётся (история
  кокпита к сессии CLI не привязана), поэтому «ничего не произошло» — и сброс легко было принять
  за сжатие. Теперь у каждого действия свой вопрос, а результат виден плашкой `role: 'note'`.
  Для Kimi локального `sessionId = null` недостаточно: стор сначала вызывает
  `POST /api/chat/session/reset`, сервер вращает sidecar в пустую generation, и до подтверждения
  reset отправка заморожена. Ошибка reset сохраняет прежнюю session и требует явного повтора.
- **Как устроено сжатие** — `POST /api/chat/compact` и `/api/tasks/:id/compact`, тот же
  `runChat` и та же очередь чата (сжатие — полноценный ход агента, а два CLI на одну сессию
  не живут). План берётся у исполнителя, поле `compaction`:
  - `{ kind: 'native', message: '/compact' }` — CLI понимает слэш-команду и в режиме
    `-p --resume`: в сессии появляются `compact_boundary`/
    `isCompactSummary`, id разговора не меняется. **Грабля:** stdout такого хода ПУСТОЙ (вывод
    команды локальный, в поток не идёт), поэтому текст для ленты подставляет сервер, а повтор
    «пустого хода» для сжатия отключён — иначе второй прогон сжал бы уже сжатое.
  - `{ kind: 'summary' }` (codex и любой новый исполнитель по умолчанию) — родного компакта нет,
    сервер заказывает рабочую выжимку текстом (`SUMMARY_PROMPT`: задача, решения и их причины,
    файлы с путями, что сделано и что осталось). Клиент кладёт её в `pendingSeed`, обнуляет
    `sessionId`, и выжимка уезжает первым блоком СЛЕДУЮЩЕГО сообщения. `pendingSeed` живёт в
    файле истории — иначе F5 превратил бы сжатие в потерю памяти; при провале отправки семя
    возвращается в ожидание.
- **Пока сжатие идёт, чат заморожен, кроме поля ввода** (`frozen` в `ChatSession.vue`): селекты
  задачи/модели/режима, слайдер усилия, «На конвейер» и отправка выключены — ход уже в полёте,
  менять ему модель или задачу поздно, а второй ход на ту же сессию её убьёт. Текстовое поле,
  вложения и диктовка живые: следующее сообщение готовится, пока агент пересказывает разговор.
  Признак работы один — кольцо крутится (у сжатия нет ленты шагов), поэтому на это время дуга
  становится коротким бегунком: полное кольцо при вращении выглядело бы неподвижным.
- **Идёт ли сжатие — знает сервер, а не окно.** Флаг `compact` лежит в `activeRuns`, уезжает
  в `GET /api/chat/active` и в SSE `chat-turn-start`, а окна ставят по нему `compacting`. Раньше
  признак жил ТОЛЬКО в затеявшем окне: на компьютере кольцо крутилось, а планшет, открытый на том
  же чате, не показывал ничего — ни кольца, ни «думает…». Догнать состояние было нечем: у родного
  компакта stdout пуст всегда, значит ни `chat-progress`, ни `chat-step` по нему не идёт, и
  одноразовый `chat-turn-start`, пропущенный в офлайне, был единственным шансом. Отсюда же сверка
  `_loadActive()` — при загрузке и на каждое `hello` (переподключение SSE, рестарт сервера):
  сверяемся ПОЛНОСТЬЮ, как со спросами, иначе после рестарта кольцо крутилось бы вечно. Не трогаем
  только то, по чему из этого окна висит свой незакрытый запрос (`compactInflight`) — его разморозит
  собственный ответ. «Думает…» во время сжатия не показываем нигде: индикатор один — кольцо.
- **Сжатие останавливается кнопкой «стоп»**, как обычный ход (это тот же процесс CLI в `activeRuns`).
  Оборванный ход возвращается обычным ответом с `stopped: true`, и `compact()` обязан его отличать:
  для Claude/Codex контекст остался прежним, а общий путь обнулил бы счётчик и написал
  «контекст сжат». Kimi после cancel не возобновляется: сервер возвращает `sessionReset: true`,
  клиент гасит метрики, а следующий явный ход создаёт чистую session.
- **Точный размер после сжатия не знает никто:** ход сжатия читал ещё старую переписку, поэтому
  его `contextTokens` — это размер ДО. Сервер отдаёт 0, кольцо гаснет, а настоящую цифру измерит
  следующий обычный ход — так и написано в подсказке кольца. В плашке остаётся только размер ДО
  («было N токенов»): это единственное честно известное число.

### Хранилище истории — chats/ в корне проекта

- Файловая часть вынесена в `lib/chat/history-store.js` (`ChatHistoryStore`: scan/save/read,
  атомарная запись, миграция со старой одно-файловой схемы) — модуль `modules/chat` остался
  маршрутами и логикой запуска агента.

- Каждый чат — файл `chats/YYYY-MM/<id>.json` (месяц СОЗДАНИЯ чата — файл не переезжает), мета — `chats/meta.json`, внутри самогитигнор (`*` + `!.gitignore`).
- Запись атомарная (tmp+rename) и только изменившихся чатов (сравнение JSON); битый файл пропускается с warn — теряется один чат, не вся история.
- Миграции одноразовые: localStorage (`cockpit-chat-v2`) → серверный файл → пофайлово; legacy `server/.state/chats.json` переименован в `.migrated`.
- **Присланная копия не замещает серверную, а сливается с ней** (`lib/chat/merge-chat.js`,
  вызывается из `saveOne`). Историю пишет клиент и шлёт чат целиком, поэтому отставшее окно
  (потеряло SSE, уснул планшет, сменился адрес) клало устаревшую ленту поверх свежей и стирало
  ответы, дошедшие до другого устройства. Правило простое: **сервер не теряет сообщений** —
  присланная лента может только дополнять серверную.
  - Ленты сравниваются позиционно (совпавшее начало + разошедшиеся хвосты), а не по времени:
    у отставшего окна `updatedAt` как раз может быть свежее — в него продолжают печатать.
  - Серверный хвост сохраняется целиком, из клиентского добавляется только то, чего в серверном
    нет; кратность учитывается (два одинаковых «Делай» подряд не схлопываются в одно).
  - Метка `role: 'error'` из клиентского хвоста выбрасывается, если в серверном уже есть ответ
    агента: «Failed to fetch» — это про сеть того окна, а не про разговор, и на других
    устройствах ход выглядел проваленным при живом ответе.
  - **Метка обрыва, за которой стоит ответ агента, снимается из ленты целиком**
    (`dropStaleErrors`, применяется и при первом сохранении чата). Обратный порядок того же
    случая: окно записало ошибку РАНЬШЕ, чем агент договорил, а ответ приехал потом и лёг
    следом. В этом случае лента выглядит как `вопрос → ⚠ Failed to fetch → ответ`, хотя ход
    завершился успешно.
    Признак чисто позиционный: после настоящего провала агент не заговорил бы сам — человеку
    пришлось бы переспросить, и между меткой и ответом стоял бы `user`. Гадать по тексту
    ошибки («Failed to fetch», «Load failed», «NetworkError») ненадёжно, поэтому не гадаем.
    Метка в самом конце ленты не трогается: ход ещё идёт, ответ на неё только едет.
    Чистка идёт и по присланной ленте ДО сравнения — иначе окно со старым фронтом (кэш PWA)
    разошлось бы с почищенной серверной копией на первой же метке и вернуло её обратно.
  - Единственное осознанное сокращение — «Очистить чат» (пустая лента): её уважаем. Отдельные
    сообщения в интерфейсе не удаляются, поэтому других легальных сокращений нет.
  - Состояние агента (`sessionId`, все поля context/usage, `pendingSeed`, `compactedAt`) берётся у
    более свежей копии: старый `sessionId` увёл бы агента в забытую сессию, потерянный
    `pendingSeed` — это потерянная память после сжатия.
  - Сохранения одного чата сериализованы очередью (`withChatLock`): два окна, пишущие
    одновременно, читали бы диск до записи друг друга и всё равно теряли хвосты.
- **Обрыв связи окна после начала model POST — не провал хода, и в общую историю он не пишется**
  (`stores/chat.js`, `catch` в `send`). Ход живёт в процессе сервера, а не во вкладке:
  порванный `POST /api/chat` его не останавливает, ответ вернётся через `chats/pending`.
  До model POST действует другая гарантия: чат сначала сохраняется с CAS-revision; stale-ответ
  другого окна безопасно повторяет только `PUT` (до трёх попыток), сохраняя выбранную в
  отправляющем окне модель. Сбой сохранения однозначно означает «агент не стартовал» и
  показывается обычной ошибкой, а не ложной плашкой «ход продолжается». Раньше сюда падала запись
  `role: 'error'`, уезжала в файл истории — и живой ход выглядел проваленным на всех
  устройствах разом. Теперь различаем и фазу, и тип ошибки: локальный флаг `offline`
  поднимается только для сетевого `TypeError`/таймаута после начала model POST; HTTP-ответ
  сервера и любой сбой до этой границы остаются обычной ошибкой в ленте. Плашка
  «📡 Связь с сервером прервалась» в этом окне, в историю не едет (его нет в `slimOf`,
  он в `RUNTIME_KEYS`). Снимается, как только связь дала о себе знать: `hello`, `chat-done`
  или забранный из `pending` ответ. Пока флаг поднят, «думает…» не гасится — правду об
  активных ходах вернёт `_loadActive()`.
  - Если слияние что-то восстановило, сервер шлёт ВТОРОЕ событие `chat-store` — уже без `origin`
    (с задержкой 500 мс) — чтобы неполную ленту перечитало и то окно, которое её прислало:
    своё эхо оно пропускает, а без задержки событие обгоняет ответ на этот же `PUT` и окно
    считает свою копию неотправленной. Проверки — `tests/server/chat-store-merge.test.js`.
- Изменения **разъезжаются сами**: каждая запись помечена `origin` — случайным id окна, — сервер после реальной записи шлёт
  SSE `chat-store` (`{id, archived|gone, origin}`), а остальные окна тянут ровно изменившийся чат
  через `GET /api/chat/store/chat/:id`. Раньше история читалась ровно один раз за загрузку страницы
  (`_load` под `loaded`/`loadPromise`), поэтому разговор, начатый на планшете, появлялся на
  компьютере только после F5. Тянем по одному чату, а не всю историю: меняется всегда один чат,
  а история растёт. Правила приёма:
  - **своё эхо пропускаем** по `origin` — изменение уже в сторе, а перечитывание гонялось бы
    с ещё не уехавшими правками;
  - **несохранённое своё не затираем**: если `slimOf(чат)` разошёлся с тем, что окно последний раз
    успешно записало (`sentChats`), чужую копию не принимаем — наш `_persist` всё равно уедет следом
    и победит, а принятая копия стёрла бы набранный черновик;
  - **объект чата обновляется на месте**, а не подменяется: ссылку на него держат и компоненты,
    и идущий прямо сейчас `send()` — подмена оставила бы ход писать ответ в отцепленный объект;
  - **рантайм-поля берутся у окна** (`RUNTIME_KEYS`: sending/compacting/steps/…), иначе чужая правка
    гасила бы «думает…» и стирала ленту идущего хода;
  - **`chat-turn-start` по неизвестному чату** сам тянет этот чат (и следом `_loadActive`): чат
    завели и сразу отправили сообщение на другом устройстве, и его копия к нам ещё едет.
  - **мета — только дефолты новых чатов** (`defModel/defEffort/defMode`). `activeId` НЕ применяем:
    у каждого устройства своя открытая вкладка, подменять её на чужую — забрать разговор из-под рук.
- На `hello` (связь восстановилась: сон планшета, рестарт сервера) история сверяется целиком —
  `_resyncStore()`: точечные события за время разрыва прошли мимо, и без сверки заведённый в это
  время чат снова ждал бы F5. Правила приёма те же плюс два: **совпавшее не трогаем** (сравнение
  со слепком в `sentChats` — иначе каждое переподключение подменяло бы массивы сообщений и
  перерисовывало открытый чат), и **пропавшее на сервере удаляем только если сервер его видел**
  (`sentChats.has(id)`) — свой новый чат, чья запись ещё едет, не трогаем. Первое `hello` приходит
  сразу за `_load()`, поэтому сверка пропускается, если история моложе 2 с (`storeSyncedAt`).
- Чат из истории может прийти без части полей (запись старой версии, ручная правка файла) —
  `_normalize()` дозаполняет их при загрузке. Для старого Codex-контракта он ещё переносит
  прежний cumulative `contextTokens` в `totalInputTokens` и обнуляет дугу до нового точного
  замера; иначе старые миллионы снова выдавали бы себя за заполненность.
- **Страховочный снимок в браузере** (`localStorage['cockpit-chat-snapshot']`): между «ответ пришёл»
  и «PUT долетел» есть окно, и рестарт сервера в этот момент СЪЕДАЛ последний ответ — следующего
  изменения, на котором стор бы пересохранился, могло не быть (воспроизводилось: 2 сообщения → 1).
  Теперь `_persist` пишет снимок при изменении ПЕРЕПИСКИ, при неудачном PUT идут ретраи с
  нарастающей паузой (1→2→4…→15 с), а `_load` берёт снимок, если он свежее серверной копии
  (сравнение по максимальному `updatedAt` сессий), и сразу возвращает его на сервер. **Ленты
  шагов в снимок не идут** (на большой истории это основная часть объёма): он нужен ради последнего ответа,
  а не ради того, чем агент его добывал. Не влез в квоту — остаются последние 20 чатов целиком.
- **Черновики**: неотправленный текст хранится в самом чате (`sess.draft`, едет на сервер вместе с
  историей), поэтому переживает переключение чатов, F5 и виден в другом окне. В списке чатов
  показывается вместо последнего сообщения с пометкой «черновик:» (как в телеграме). Пишется с
  задержкой 400 мс, дожимается на `beforeunload`/размонтировании, гасится при отправке — иначе
  дебаунс успевал записать уже отправленный текст. `updatedAt` при наборе НЕ трогаем: чат не должен
  прыгать в начало списка от того, что в нём печатают. **Страховочный снимок черновик не пишет**
  (`_persist(false, { snapshot: false })`): этот путь идёт на каждую паузу в наборе и обязан быть
  дешёвым — на нём вкладка и подвисала (см. [грабли](gotchas.md)).
- **Открытие архива не означает восстановление:** клик по архивному разговору только выбирает
  его и показывает переписку на месте; объект остаётся в `archived`, режим архива в списке не
  выключается. В активные чаты тот же объект переезжает лишь по кнопке «Достать из архива» либо
  непосредственно перед отправкой нового сообщения (включая сообщение только с вложением).
  `activeId` поэтому может указывать и на архивный чат, а поиск выбранной сессии и живые SSE-поля
  обязаны смотреть в оба списка. Перенос выполняется до durable save/model POST, чтобы первый же
  продолжающий ход сохранился с `archived: false` и одинаково разъехался по другим окнам.
- **Время запроса** хранится у пользовательской реплики полем `sentAt` (Unix ms), фиксируется до
  durable save и показывается внутри пузыря мелкими часами и минутами, как в мессенджере; полная
  локальная дата доступна в подсказке. `updatedAt` чата для этого не используется — он меняется
  после ответа и синхронизации. Старым репликам без точной метки время не придумывается. Если вопрос
  пришлось восстановить из `chats/pending`, сервер переносит туда исходный `userSentAt`.
- **Аватар в списке — иконка исполнителя** (`ProviderIcon` по модели чата) плюс актуальная
  подпись модели из реестра рядом с названием; буква из названия осталась фоллбэком, пока реестр
  исполнителей не загрузился.
  **Красит знак цветом самого исполнителя список, а не компонент** (`provider.color` → инлайновая
  переменная `--prov` на `.ava`, дальше `color-mix` в CSS): знак остаётся монохромным
  `currentColor`, цвет задаёт место — см. «Знак исполнителя» ниже. Одинаково-серые аватары в
  списке из двадцати строк не различались вовсе: чат искали по подписи модели, а знак работал
  украшением. Фирменные цвета рассчитаны на светлый фон, поэтому на тёмном к знаку подмешивается
  белый, а к заливке и рамке — фон карточки (замер `getComputedStyle` в headless Chrome: контраст
  знака к своей заливке 3.7–7.2:1, попарная различимость знаков ΔE ≥ 23 в Lab). Во время работы
  цвет остаётся исполнительским, а признаком занятости остаётся вращающееся кольцо: общий акцент
  снова сливал бы работающие чаты между собой — ровно тогда, когда их и различают. Чат без знака
  (реестр ещё не приехал) `--prov` не получает и остаётся нейтральным.
  **Полную силу цвета держат ровно три состояния** — открытый чат (`.row.cur`), вставший на
  вопросе (`.row.wait`) и работающий (`.ava.live`); остальные приглушены, иначе список из
  двадцати строк горит ровным ковром и выделять в нём нечего. Приглушение — ОБЕСЦВЕЧИВАНИЕ
  (подмешан нейтральный `--ink-mid`), а не `opacity` и не затемнение: обе «очевидные»
  альтернативы роняют контраст знака к своей заливке ниже порога графики 3:1, причём первым
  всегда Kimi — его фиолетовый и так самый тёмный (замер: `opacity: .72` → 2.98, тёмная
  нейтраль → 2.87). Обесцвечивание, наоборот, контраст поднимает: нейтраль светлее тёмных
  фирменных цветов. У выбранного варианта знак 3.6–5.6:1 к заливке, отличие от полной силы
  ΔE 13.5–18.1 (рядом видно), а различимость исполнителей между собой остаётся ΔE ≥ 26.8 —
  то, ради чего цвет и вводили.
- **Индикация активных агентов**: сервер держит `activeRuns` (chatKey→startedAt/tokens/compact),
  `GET /api/chat/active`; фронт восстанавливает «думает… · N ток.» по нему при загрузке (F5) и на
  каждое `hello` — переподключение SSE и рестарт сервера тоже приводят состояние в порядок,
  включая снятие ходов, умерших, пока связи не было. SSE `chat-progress` тоже поднимает sending,
  `chat-done` гасит во всех окнах. Видно кольцом-спиннером в аватаре чата в списке (бейджи навигации
  заняты непрочитанными, см. ниже); сжатие для списка — такая же занятость чата, отличается подсказка.
- **Непрочитанные чаты** (`sess.unread`, едет в `chats/<id>.json` вместе с историей): метка ставится,
  когда ответ агента пришёл, а на этот чат не смотрели. «Смотрели» — одно правило `chat._visible(id)`
  на весь кокпит: вкладка ОС активна + открыт раздел «Чаты» или плавающая панель + это активный чат;
  по нему же решается, слать ли оповещение (иначе бейдж спорил бы с уведомлением). Ставится в `send()`
  и в `_collectPending()` (ответы, доехавшие пока страницы не было). Снимается сама собой в
  `ChatSession.vue`: компонент рисуется ровно тогда, когда на чат смотрят, — плюс `visibilitychange`
  для ответа, прилетевшего в свёрнутую вкладку. Считает getter `unreadCount` (открытые + архивные:
  чат могли закрыть, пока агент думал). Показывается тремя местами: бейдж на пункте «Чаты» в навигации,
  бейдж на плавающей кнопке чата (`ChatPanel`), точка на аватаре в списке.
- **Оформление ответов агента**: подпись «✳ Агент» + акцентная полоска слева, текст рендерится
  безопасным GFM (`shared/md.js`: ссылки, списки, таблицы и код; raw HTML экранируется,
  опасные URL отбрасываются) — отличимо от системных плашек и пузырей.
- **Файловая ссылка в ответе агента ведёт туда, где файл открывается** — общий резолвер
  `features/code/links.js` (`chatFileLinkHref`): `.md`/`.txt` в просмотрщик документов,
  файл под известным деревом репозитория (`GET /api/code/roots`) — в панель «Код»
  (`data-code-link`, клик кладёт intent `open-file` тем же `launchTool`, что и «Проекты»),
  суффикс `:120` открывает нужную строку. Всё прочее локальное — **текстом**: ссылка не
  имеет права обещать открытие, которого не будет (`resolveHref` вернул `false`). Карта
  деревьев тянется один раз с TTL 60 с; выключенный плагин «Код» или неответивший сервер
  просто оставляют такие ссылки текстом. Подробности и границы — [documents.md](documents.md).
- **Usage-корзины Claude**: каноничный источник — массив `limits` ответа oauth/usage (из него строится
  официальная панель): `session`, `weekly_all`, `weekly_scoped` (+`scope.model.display_name`,
  например «Fable» — модельные недельные ведра приходят сами, хардкода имён нет).
  `extra_usage` — доплата сверх лимитов, отдельный бар с бюджетом («61 из 170 EUR»).
  Верхнеуровневые ведра (`five_hour`…) — только фоллбэк. Сеть до api.anthropic.com флапает
  (VPN): retry ×2 + при сбое отдаются прошлые данные, а не пустота.
- **Usage-корзины Codex**: `codex app-server` → документированный read-only JSON-RPC
  `account/rateLimits/read`. Cockpit создаёт короткое локальное соединение, выполняет
  `initialize`, читает `rateLimitsByLimitId` (либо совместимый `rateLimits`) и завершает
  только свой дочерний процесс. Ни thread, ни turn, ни вызов модели не создаются; файлы
  диалогов не читаются. Имена отдельных модельных семейств приходят от OpenAI и появляются
  в шапке без хардкода и релиза Cockpit. Из того же ответа показываются купленные ChatGPT
  credits. Если `rateLimitResetCredits.availableCount > 0`, появляется подтверждаемая кнопка
  расхода заработанного сброса; `account/rateLimitResetCredit/consume` получает стабильный
  `requestId` как `idempotencyKey`, после успеха лимиты перечитываются. Покупка и
  автопополнение остаются по ссылке на `chatgpt.com/codex/settings/usage`: документированного
  тумблера сверхлимита в Codex app-server нет.
- **Доплата Claude управляется прямо из шапки**: тумблер вкл/выкл и месячный потолок.
  `extra_usage` приходит как account resource с общими контролами, а не как особый тип
  полосы во фронте. Ручки приватные, сняты с бинаря CLI (это его `/usage-credits`):
  `POST/PUT /api/oauth/organizations/<uuid>/{setup_overage_billing, overage_spend_limit}`,
  авторизация — OAuth-токеном хостового CLI, uuid организации из `~/.claude.json`
  (`oauthAccount.organizationUuid`), суммы — в минорных единицах.
  При ПЕРВОМ включении сначала `setup_overage_billing`, потом флаг — иначе доплата не заведена.
  Выключение (`is_enabled:false`) сам CLI не зовёт (у него это только через claude.ai): поле
  в схеме есть, но при отказе API текст ошибки показываем как есть, а рядом всегда висит
  ссылка на claude.ai/settings/usage. Снятие потолка («без ограничения») сознательно не
  поддержано: счёт без верхней границы заводят осознанно на сайте, а не тумблером в шапке.
  Подтверждение спрашивается ВНУТРИ всплывашки: модалка забрала бы фокус, всплывашка
  закрылась бы — и ни вопроса, ни результата человек не увидит.

### Модульное подключение нового ИИ

Реестр сканирует `server/src/lib/executors/*.js`; отдельной регистрации Kimi в Fastify и Vue
не требуется. Адаптер экспортирует базовый контракт `id/name/vendor/color/bin/probe/auth/
seedModels/run`, а при наличии API аккаунта добавляет:

```js
{
  async usage() {
    return {
      state: 'ok',
      bars: [{ key: 'month', label: 'Месяц', pct: 24 }],
      resources: [{
        key: 'balance',
        label: 'Баланс Kimi',
        summary: '12 CNY',
        controls: [
          { id: 'top-up', kind: 'link', label: 'Пополнить', href: 'https://…' },
          {
            id: 'auto-top-up',
            kind: 'toggle',
            label: 'автопополнение',
            value: false,
            action: 'configure-auto-top-up',
            field: 'enabled',
            confirm: { on: { text: '…', label: 'Включить' }, off: { text: '…', label: 'Выключить' } },
          },
        ],
      }],
    };
  },
  usageActions: {
    'configure-auto-top-up': async ({ payload, requestId, config, deps }) => {
      // Адаптер валидирует payload и вызывает только API своего провайдера.
    },
  },
}
```

Ядро нормализует ресурсы, отбрасывает не-HTTPS ссылки и неизвестные controls. Внешний клиент
не может передать произвольный метод: выполняются только ключи из `usageActions` конкретного
адаптера. `requestId` обязателен на границе UI для идемпотентных денежных/расходуемых операций.

**Знак исполнителя — часть подключения, а не украшение.** Иконку рисует
`web/src/shared/ProviderIcon.vue` по `provider.id`; **нет своей ветки — молча включается
фоллбэк «кружок с первой буквой имени»**. В этом и ловушка: пропажа выглядит «почти
нормально», поэтому Ollama прожила с буквой «O» до отдельного вопроса человека. Правила:
монохром через `currentColor` (цвет задаёт место: топбар и настройки берут нейтральный,
список чатов — фирменный `provider.color` самого исполнителя, см. выше),
`aria-hidden`, свой `viewBox`. Официальный знак **допустимо упростить** — заливка рядом со
штриховым claude читается кляксой, поэтому у claude в комментарии написано «упрощённая»,
а голова ламы обведена линией. Соседей уравнивают КАДРОМ, а не размером: `viewBox` у знаков
разный (`0 0 24 24`, `-2 -2 35 36`, `2.3 -0.4 19.4 19.4`), сходятся они по оптической массе.
Проверять замером на трёх реальных размерах — 15 (`AppShell`), 19 (`ChatList`),
20 (`SettingsView`), — а не на одном крупном: детали пропадают именно на 15.
Регрессия — `tests/web/provider-icon.component.test.js`.
- **Недоставленные ответы**: если клиент умер во время работы агента (F5/закрытие вкладки),
  сервер по завершении видит `request.socket.destroyed` и пишет ответ в `chats/pending/<id>.json`
  (+SSE `chat-orphan` живым окнам). Фронт при `_load()` и по этому событию забирает
  GET /api/chat/pending, раскладывает по чатам (dedup по `pid` в сообщении) и подтверждает DELETE'ом.
  Ошибки тоже доезжают (role: error). Навигация внутри SPA ответы не теряет и без этого —
  стор глобальный, запрос переживает переключение чатов/разделов.

### Всплывашка разрешений (аналог permission prompt Claude Code)

- Чат работает в `--permission-mode default`: чтение свободно, на действия (Bash/правки) claude
  спрашивает через `--permission-prompt-tool mcp__cockpit-perm__approve` — мини-MCP
  `lib/chat/permission-mcp.js` (newline-JSON-RPC вручную, без SDK), который держит HTTP-запрос
  к `/api/chat/permission-request`, пока пользователь не ответит.
- Поток: claude → MCP → POST permission-request → SSE `chat-permission {pid,tool,input,chatKey,at}` →
  всплывашка в ChatSession (жёлтая, показывает команду/файл) → POST `/api/chat/permission/:pid`
  {allow, comment?} → `chat-permission-done` закрывает всплывашку во всех окнах.
- **Нюанс:** то, что уже в глобальном allowlist пользователя (~/.claude/settings.json), выполняется
  БЕЗ всплывашки — prompt-tool зовётся только для того, что иначе спросило бы.

### Спрос ВИСИТ, пока не ответишь (без короткого UI-таймаута)

- Было: 4 минуты на ответ, дальше сервер отвечал агенту deny («не ответил — действуй сам»).
  Человек отошёл — агент уезжал дальше по собственному разумению, а выбор пропадал с экрана.
  Теперь ожидание живёт до ответа (потолок `PERM_WAIT_MS` = сутки), снимается только
  «стопом» или концом хода (`dropPending` — иначе чип «ждёт ответа» висел бы вечно).
- Ждать должны ВСЕ три звена, иначе выигрыша нет:
  1. кокпит — держит HTTP-запрос от permission-mcp (см. выше);
  2. **CLI** — `MCP_TOOL_TIMEOUT` в окружении запуска + `timeout` у самого сервера в `--mcp-config`
     (per-server override, «hard wall-clock limit per call»). Без них CLI обрывает вызов
     инструмента своим дефолтом, и агент идёт дальше, пока вопрос ещё висит на экране;
  3. **ход агента** — `execFile` не имеет `timeout`: долгие задачи могут выполняться часами.
     Автоматического лимита длительности у хода нет; прерывание через `ac.abort()` выполняет
     только явная кнопка «стоп».
- `GET /api/chat/waiting` — что висит прямо сейчас. Нужен потому, что SSE доставляет событие
  один раз: после F5 (и во втором окне) всплывашку иначе некому показать. Фронт зовёт его при
  загрузке стора и на каждое `hello` (переподключение SSE) и **синхронизирует список целиком** —
  после рестарта сервера запросы умирают вместе с процессами агентов, и старые записи стали бы фантомами.
- Во фронте висящие спросы — карта `chat.pending` (pid → `{kind: 'perm'|'question', chatKey, …}`),
  а не два одиночных поля: агенты работают в нескольких чатах, и новый спрос не должен затирать
  чужой. Компонент берёт свой через `permFor(chatKey)` / `questionFor(chatKey)`.

### «Требуют вмешательства»: чипы, чтобы вопрос не проехал мимо

- Вопрос агента легко пропустить — работа при этом СТОИТ. Поэтому такой чат отмечается сильнее,
  чем непрочитанный (`waitingChats`/`waitingCount` в сторе — считаются чаты, не запросы):
  бейдж на пункте «Чаты» и на плавающей кнопке чата (жёлтый, пульсирует, перебивает синий бейдж
  непрочитанных), чип «ждёт ответа» + тёплая полоска на строке в списке чатов, и сам чат
  поднимается наверх списка. Плюс системное оповещение в момент спроса, если на чат не смотрят
  (правило `_visible` — то же, что у непрочитанных).
- Чекбокс «Разрешать до конца сессии»: карта chatKey→Set(tool) в памяти вкладки (chat.js,
  `permAutoAllow`) — совпавшие запросы отвечаются allow автоматически, в allowlist ничего не пишется.
- **Живой счётчик токенов**: claude запускается с `--output-format stream-json --verbose`,
  executor суммирует output_tokens по assistant-событиям → onProgress → SSE `chat-progress
  {chatKey, tokens}` → «думает… · N ток.» в чате.
- Перезапуск сервера — ТОЛЬКО `bin/restart` (гасит порт, ждёт освобождения, стартует, health-чек):
  в репо работают параллельные сессии, ручные kill+start ловили EADDRINUSE и рвали чужие чат-запросы.

### UI-контекст: чат знает, где пользователь

- Стор `ui-context` (`web/src/stores/ui-context.js`): страницы репортят детали `set(key, val)`/`clear(key)`
  (маршрут в Routes, таб в Settings…). `chat.send()` прикладывает `{ page, path, details }` из роутера + стора.
- `ToolHost` добавляет безопасный контекст Code (проект, рабочая копия, открытый файл и
  режим `page`/`dock`). Для Terminal наружу уезжают только id и режим представления:
  buffer xterm, вывод PTY и введённые команды в `ui-context` не попадают.
- Сервер (`pageMode`/`contextPrefix` в modules/chat) строит блок `[Контекст кокпита]` перед сообщением: страница,
  подсказка о её данных, детали. Явно указано: контекст задействовать только если просьба к нему относится.
- **Режим страницы «Агенты»** (чат без задачи): cwd = `agents/`, `--permission-mode acceptEdits` —
  «поправь этого агента» реально редактирует `<id>.md`. Остальные страницы — plan (только чтение).

### Вложения (фото) и диктовка

- **Вложения:** кнопка-скрепка, drag&drop на весь чат (оверлей «Отпусти, чтобы приложить»;
  dragenter/leave через счётчик — leave стреляет на каждом дочернем узле) или вставка
  картинки из буфера → сразу `POST /api/chat/upload`
  (multipart) → файл в `chats/attachments/<ts>-<имя>` (гитигнорится вместе с chats/). К сообщению
  клиент прикладывает `attachments: [{file, name}]`; сервер строит пути ТОЛЬКО внутри attachments/
  (защита от traversal/произвольного `--add-dir`), добавляет `--add-dir chats/attachments` и блок
  `[Вложения]` со списком путей — агент смотрит их инструментом Read (vision работает в plan-mode).
  Сообщение без текста, но с вложением — валидно. Превью в истории — `GET /api/chat/attachment/:file`.
- **Диктовка:** движок, язык, качество и словарь — серверные настройки во вкладке «Речь»;
  изменения приезжают всем окнам через SSE. Дефолтный browser-auto показывает промежуточный
  текст во время речи, но до первого `SpeechRecognition.start()` требует явного согласия:
  браузер может обрабатывать звук удалённо. Перед каждым start/retry вкладка повторно
  подтверждает серверу актуальную opaque revision; offline/stale ответ закрывает запуск.
  Browser-local запускается только после
  capability-check/явной установки языкового пакета и никогда не откатывается в auto молча.
  Если Web Speech недоступен, UI один раз объясняет переход на локальный Whisper.
- **Локальный live-путь:** `AudioWorklet` переводит вход в PCM16 mono 16 кГц и посылает его
  в авторизованный same-origin WebSocket `GET /api/chat/transcribe/stream`. Стартовый кадр
  фиксирует protocol v1, `sessionId`, актуальную server-owned `revision` и точный контракт
  `{encoding:"pcm_s16le",sampleRate:16000,channels:1,frameSamples:1600}`; бинарные кадры
  идут с монотонным `uint32 LE seq`, сервер отвечает `ack` и не принимает пропуски или
  повторы. Origin обязан быть буквальной canonical-формой origin запроса без path/query/
  credentials; стартовый JSON должен прийти за 10 с после upgrade. На одну диктовку
  поднимается один non-detached worker с pinned
  `local_files_only` моделью faster-whisper: он запускает один decode после каждых 2 с
  нового звука, использует overlap 1,5 с и rolling window до 30 с, а LocalAgreement
  закрепляет только общий префикс соседних гипотез. Накопившиеся промежуточные запросы
  схлопываются до последнего watermark. Два последовательных пустых/VAD-окна безопасно
  продвигают старую тишину, сохраняя overlap перед возможной поздней речью. Это
  псевдостриминг Whisper, не stateful streaming encoder, поэтому фактическую задержку
  нельзя обещать без замера.
- **Текст и завершение:** cumulative partial показывается только отдельной строкой
  «Слышу…» непосредственно над композером: растущий partial не сдвигает поле ввода и не
  трогает его текст. После успешного непустого `done` итог
  дописывается в textarea ровно один раз и сам не отправляется. Stop делает ограниченный
  по времени drain с tail flush, Esc отменяет незакреплённый результат; до live-`done`
  либо завершения batch fallback отправка и slash-команды заблокированы, само поле
  остаётся редактируемым. Кнопка во время записи становится Stop: вокруг неё пульсирует
  красная подложка; отдельного нижнего индикатора уровня нет, `prefers-reduced-motion`
  отключает анимацию.
- **Аварийное завершение:** полный `MediaRecorder` WebM/Opus пишется параллельно. Если
  AudioWorklet/WebSocket/worker не стартовал, оборвался, не успел завершить drain или
  вернул пустой final, Stop отправляет этот целый файл в прежний
  `POST /api/chat/transcribe`; WebM не режется на независимые timeslice-контейнеры.
  Только preflight без WebSocket, AudioContext или AudioWorklet запускает batch warmup;
  после фактической live-попытки fallback остаётся one-shot. Multipart передаёт тот же
  `streamSessionId`, поэтому runtime отменяет и ждёт child `close` именно этой live-сессии
  до запуска batch, даже если WebSocket-close ещё не обработан; уже начатые отмены тоже
  дожидаются, чужие активные диктовки — нет. Если bounded TERM/KILL не подтвердил `close`,
  slot и workDir остаются в quarantine до настоящего exit. One-shot без correlation
  тоже не запускает вторую модель при таком quarantine, а fail-closed отвечает
  `503 speech_stream_busy`.
  Если `MediaRecorder.onstop` не приходит, watchdog через 2 с продолжает завершение с
  уже собранным WebM.
  Падение локального stream никогда не включает `browser:auto`: потенциально удалённая
  обработка остаётся только явным выбором человека с consent.
- Выбранная Whisper-модель должна быть заранее скачана model job-ом; скрытой сетевой
  загрузки из распознавания нет. CPU/int8 остаётся переносимым путём, в том числе на
  машине с AMD GPU; ускорение CUDA опционально и относится только к NVIDIA, ROCm-пути
  в текущем runtime нет. `maxStreams=2` считает pending/active/cancelling/quarantined
  live-сессии; decode pending, rolling window и Stop/drain ограничены 30 с, server
  live PCM — 5 минутами. После worker `ready` transport idle равен 30 с, hard wall-clock
  session — 6 минутам; тихие PCM-кадры сбрасывают idle timer. Пять минут — не auto-stop:
  полный `MediaRecorder` продолжает recovery-запись до ручного Stop. Клиент ждёт ready
  до 45 с и держит не более 768 КиБ PCM (примерно 24 с, меньше серверных 30 с); это
  защитные отсечки, не latency SLA. Клик Stop сразу запускает единый live-stop, не ждёт
  `MediaRecorder.onstop`; поздний callback переиспользует тот же promise. Cancel во время
  Stop/finishing не выпускает поздние `final`/`done`. Stop, Esc и unmount инвалидируют
  generation и чистят WebSocket, worker, AudioWorklet/AudioContext,
  MediaRecorder и MediaStream; ожидания best-effort close AudioContext и socket
  ограничены 750 мс каждое, поздние события старой сессии не могут дописать текст.
  **Грабля:** getUserMedia требует secure context — по `http://<адрес в локальной сети>`
  микрофон недоступен; работает на localhost или через HTTPS.

## База агентов (modules/agents) — стадии конвейера

- `agents/<id>.md` в корне проекта (самогитигнор): frontmatter (kind/label/sub/key/model/timeout/budget/readonly/optional) + тело-промпт. Формат плоский key: value — парсер свой (`store.js`), не YAML-библиотека.
- CRUD: `GET/POST /api/agents`, `GET/PUT/DELETE /api/agents/:id`, `POST /api/agents/reseed`.
- Пустая база один раз засевается из всех профилей фабрики. Reseed обновляет метаданные
  канонических стадий, сохраняет курируемые `prompt` и `effort`, кастомных агентов не трогает.
- UI: AgentsView (`/agents`) — список + редактор карточки; «Профи»-настройки за тумблером.

## Маршруты (modules/routes)

- **Маршрут — только опубликованный бандл v2** (`~/.factory/routes/<профиль>/`): ревизии
  адресуются хешем СОДЕРЖИМОГО, указатель `catalog/current.json` двигается CAS-ом.
  Редактируемого стора `routes/<профиль>/<id>.json` больше нет: он ничего не исполнял
  (движок читал `profile.sh` и `graph.json`), и вторая «схема» рядом с бандлом только
  путала, чью правку увидит прогон.
- Проекты: `GET/POST /api/profiles`. Проекты фабрики — по `profiles/*/graph.json`,
  заведённые в кокпите — реестром `prefs.projects` (там же их пути репозиториев).
- Каталог: `GET /api/routes/:profile/{current,revisions}`,
  `GET .../catalog/:hash`, `GET .../routes/:id/:hash[/graph]`,
  `PUT .../current` (откат, CAS), `POST .../publish` (`mode: validate|publish`).
- **Собирает бандл сам профиль** — `profiles/<проект>/routes/publish.mjs`; кокпит
  подставляет ровно два аргумента (`--base-dir`, `--expected-catalog-hash`) и показывает
  его JSON как есть. Нет скрипта — нет и кнопки: «дефолтного» проекта у кокпита нет.
- UI: RoutesView (`/routes`) — состав каталога, схема маршрута (тем же `buildV2RouteDef`,
  что рисует «Конвейер» живой задачи), кнопки «Проверить»/«Опубликовать», список ревизий
  с откатом. Редактора схемы здесь нет намеренно: попытка закрепляет хеш, и правка «на лету»
  означала бы, что задача идёт по одному, а показывается другое.

## Исполнители и модели (modules/providers + lib/executors + lib/models-registry)

- **Подключение нового ИИ — модульное:** один файл в `server/src/lib/executors/` (контракт в

  Папка сканируется при старте — ядро (providers, chat)
  про вендоров не знает. Сейчас: `claude.js`, `codex.js` (GPT).
- `GET /api/providers` — `{ id, name, vendor, bin, color, version, auth, authLabel, available, installed, models[], modes[], settings[] }`.
  Тарифной отсечки в описании provider-а нет: факты prompt cache относятся к конкретному
  model request и приходят через `contextCache`, а не через этот каталог.
  Кэш 60с, `?refresh=1`. Топбар рисует иконки (серый = недоступен), настройки → вкладка «Исполнители».
- **Вкладка «Исполнители» — плашка на каждого ИИ, плашки горизонтальным рядом** (grid
  `minmax(340px, 1fr)`, таб шире остальных: `.settings.wide`). В плашке — факты про CLI
  (авторизация, версия, каталог, обновление) и блок **своих настроек исполнителя**; общее
  для всех («показывать все модели», «Перепроверить», доверенные каталоги) — карточками ниже.
- **Свои настройки исполнителя объявляет сам executor** — поле `settings`:
  `[{ id, kind, label, hint?, value, disabled?, note? }]`. Схема приходит от исполнителя,
  выбор человека лежит в prefs (`providerSettings`), склейка — `lib/provider-settings.js`;
  сохранение — `POST /api/providers/:id/settings` (`{ settingId, value }`). Ядро про смысл
  ключа не знает: принимает ТОЛЬКО объявленный id и приводит значение к типу `kind`, поэтому
  чужой ключ в prefs не попадёт. Фронт рисует по `kind` (`stores/providers.saveSetting`,
  оптимистично с откатом).
- **MCP-серверы исполнителя — блок в той же плашке** (как панель «MCP servers» в расширении
  VS Code): секции по области видимости («Свои» — `mcpServers` в `~/.claude.json`, «Проект» —
  `.mcp.json` рабочего каталога и `projects[<путь>].mcpServers`, «claude.ai» — аккаунтные
  коннекторы, определений которых на диске нет вовсе), цветное состояние каждого сервера
  и кнопка «Перепроверить». Источник — новый метод контракта `mcpStatus?(config)`: его
  объявляет сам исполнитель, не объявил — блока нет (у HTTP-исполнителя вроде Ollama
  понятия MCP нет в принципе). У claude метод разбирает текстовый вывод `claude mcp list`
  (`parseClaudeMcpList`), добирает признак «нужна авторизация» из
  `~/.claude/mcp-needs-auth-cache.json` (сам `mcp list` про него молчит и печатает такой
  коннектор как `Connected`) и дополняет список коннекторами аккаунта из
  `claudeAiMcpEverConnected` — их команда показывает не всегда, а секция «claude.ai» должна
  быть полной. Сборка итогового списка — чистая `composeMcpServers`, вся правка состояний
  там. У аккаунтного коннектора состояние `remote` («включён на claude.ai»): локальной
  проверки живости у него нет, и притворяться, что есть, панель не будет.
  **Запрос отдельный и ленивый** — `GET /api/providers/:id/mcp` (кэш 60 с, `?refresh=1`):
  опрос делает живой health-check каждого сервера и стоит секунд, поэтому в общий
  `/api/providers` он не входит — иначе реестр, который дёргает топбар, подорожал бы
  на эти секунды. В записи реестра остаётся только признак `mcp: true` (есть ли что
  показывать). Фронт грузит блок по открытию вкладки (`watchEffect` в `SettingsView`)
  и по кнопке; хранит по исполнителю в `providers.mcp`.
  **Кнопки «переподключить» здесь нет и она не имеет смысла:** кокпит поднимает процесс
  CLI на КАЖДОЕ сообщение, вместе с ним заново стартуют и MCP-серверы — «соединения»,
  которое можно было бы починить между ходами, не существует. Панель отвечает на другой
  вопрос: почему сервер не поднялся (причина отказа целиком) и что для этого сделать.
- **`claude.fastMode` («Ускоренный вывод»)** — объявлен, переключается и хранится; каждый
  headless-запуск получает явное значение через `--settings {"fastMode":…}`. Список моделей
  здесь не дублируется: фактическую доступность, политику организации и списание usage credits
  проверяет установленный Claude CLI.
- **Список моделей Claude — ИЗ БИНАРЯ УСТАНОВЛЕННОГО CLI** (`executors/_claude-catalog.js`):
  бинарь сканируется потоком по regex `claude-(opus|sonnet|haiku|fable)-N(-M)?(\[1m\])?`, tier —
  из семейства и версии. Почему так: захардкоженная подпись версии протухает молча. В историческом
  инциденте реестр показывал «Opus 4.8», а установленный CLI резолвил `opus` в другую версию; бинарь
  знает локально поддерживаемые id и не требует ключей или сети.
  Скан ~0.3 с на 230 МБ, поэтому каталог пересобирается только при смене версии CLI,
  `CATALOG_SCHEMA`, executor-owned ключа окружения и по `?refresh=1`. Для Claude в ключ
  входит хотя бы `CLAUDE_CODE_DISABLE_1M_CONTEXT`: изменение флага после обычного рестарта
  обязано обновить каталог даже при прежней версии бинаря.
  **Свойства модели тот же скан берёт из РЕЕСТРА внутри бинаря, а не выводит из имени.**
  Рядом с каждым id лежит запись вида
  `{id:"claude-fable-5",family:"fable",display_name:"Fable 5",context:{window:1e6,native_1m:!0},`
  `max_output_tokens:{default:64000,upper:128000},capabilities:["effort","xhigh_effort",…]}` —
  оттуда приезжают окно контекста, подпись, потолок вывода и возможности. Прежнее правило
  выводило окно из ИМЕНИ («есть суффикс `[1m]` — миллион, иначе 200k») и потому занижало его
  **всему текущему поколению**: у Fable 5, Opus 5/4.8/4.7 и Sonnet 5 миллион ВСТРОЕННЫЙ
  (`native_1m`), без всякого суффикса. У Fable на 165 172 токенах реальная заполненность
  окна поэтому **17%**, но процент кольца зависит от ближайшего события: со стандартным
  автосжатием 200k это **83% до сжатия**, а не 17% — см. [грабли](gotchas.md).
  Правило резолва повторяет сам CLI: миллион даёт суффикс `[1m]` ЛИБО `native_1m`, а
  `CLAUDE_CODE_DISABLE_1M_CONTEXT` отменяет оба пути; `context.window` — для остальных.
  Bool-диалект совпадает с CLI: выключатель включают только `1|true|yes|on`, а строки
  `0|false|no|off` означают false и не должны случайно спрятать миллион.
  При включённом запрете варианты `[1m]` из селекта уходят совсем: показывать пункт с
  названием «(1M)» и окном 200k нельзя. Их старые exact id остаются в
  `modelRefAliases` базовой 200k-модели, поэтому сохранённый versioned чат не ломается и
  не запускает недоступный режим.
  Чего кокпит не видит: CLI дополнительно срезает окно до 200k, когда у аккаунта заблокированы
  кредиты на 1M (`longContext1mCreditsBlocked`) — этот флаг наружу не отдаётся.
  **Бандл чужого CLI — не контракт, поэтому разбор ограничен ОДНОЙ записью и проверяется
  ПО КАЖДОЙ модели.** Парсер сначала находит точную границу объекта реестра с учётом
  вложенных скобок, строк и escape-последовательностей (4096 символов — только fail-closed
  потолок ОДНОГО объекта), а уже внутри неё ищет `context`, `max_output_tokens` и
  `capabilities`. Слепой фиксированный хвост после id запрещён: если у текущей записи
  исчезнет поле, regex иначе одолжит его у следующей модели и выдаст чужое окно за
  проверенное. Оборванный до потолка объект не парсится вовсе.
  Окно меньше 1000 токенов бракуется — смени бандл запись числа на `1_000_000`, и простой
  regex поймал бы «1». Здоровье не бывает глобальным «распарсилась хотя бы одна»: неполная
  запись помечает непроверенной именно свою модель, не скрывая деградацию за соседними.
  Поля независимы: `contextUnverified`, `nameUnverified`, `maxOutputUnverified` и
  `effortUnverified` показывают, какой кусок не прочитан, а `metadataUnverified` — общий
  машинный признак деградации записи.
  `mergeCatalogModel` при этом сохраняет последние проверенные метаданные этой модели
  (`context`, `name`, `maxOutput`, `capabilities`, `effortGates`), но НЕ снимает признаки
  деградации. `contextUnverified` означает: обновление CLI не имеет права ни заменить
  известный миллион заглушкой 200k, ни выдать старый снимок за свежепроверенный; подсказка
  кольца явно пишет «окно модели N (не подтверждено)». Исключение — явно включённый
  disable-1M: его эффективный cap 200k известен без registry и сильнее старого сохранённого
  миллиона, хотя остальные поля записи всё ещё могут быть непроверенными.
  `effortUnverified` отделён от окна:
  если возможности/гейты конкретной записи не прочитались, ladder блокируется fail-closed
  и слайдер не предлагает потенциально неподдерживаемый `xhigh`, даже когда last-known
  capabilities сохранены в файле. У новой модели без прошлого снимка остаются
  консервативные заглушки с теми же явными признаками. Сторож —
  `tests/server/claude-catalog.test.js`, там же тест по НАСТОЯЩЕМУ установленному CLI:
  он падает в тот день, когда обновление ломает разбор, и пропускается, если CLI не стоит.
- **Список моделей Codex — ИЗ ОФИЦИАЛЬНОГО APP-SERVER** (`model/list`, `includeHidden:true`):
  это модели, доступные именно установленному CLI и текущему ChatGPT-аккаунту, вместе с
  display name, поддерживаемыми effort, default, hidden и рекомендацией `upgrade`. Вызов
  read-only: thread/turn и обращение к модели не создаются, `OPENAI_API_KEY` не нужен.
  Каталог живой (`catalogLive`): сервер перечитывает его при обновлении минутного кэша,
  а открытый UI раз в минуту перечитывает `/api/providers`. Новый rollout появляется без
  релиза Cockpit; кнопка «Перепроверить» делает это немедленно.
- **Ollama — локальный HTTP-исполнитель** (`executors/ollama.js` + `_ollama-client.js`
  + `_ollama-tools.js`): полноценный агентский ход — инструменты, режимы прав, эффорт,
  картинки, — но всё это даёт САМ КОКПИТ. Демон приносит только модель: он не ходит по
  файлам, не спрашивает разрешений и не держит сессию. Слэш-команд и обновления CLI нет
  (`commands`/`updateCmd` не объявлены). Транспорт — HTTP API демона: probe/auth →
  `GET /api/version`; каталог (живой, `catalogLive`) → `GET /api/tags`, окно контекста
  каждой модели — из `POST /api/show` (первый ключ `model_info` на `.context_length`,
  кэш по digest модели; не узнали → 32768), tier — число миллиардов параметров из
  `parameter_size`; ход → `POST /api/chat` со стримом NDJSON (`thinking` → think-шаги
  ленты, `content` → text-шаг раунда, финальный чанк отдаёт
  `prompt_eval_count`/`eval_count` → `contextTokens`, `contextWindow` = num_ctx). Демон
  недоступен → каталог возвращает `null` (реестр оставляет прошлый список), ход падает
  с понятным «демон Ollama не отвечает на <host>».
  - **Что модель умеет, решает она сама** — `capabilities` из того же `/api/tags`
    (старый демон их там не кладёт → добираем из `/api/show`, кэш общий): `tools` включает
    инструменты, `vision` — вложения-картинки, `thinking` — эффорт. Хардкода возможностей
    нет: новая модель включает их фактом своей поддержки. **Эффорт объявлен БИНАРНЫМ**
    (`efforts: ['low','high']` → `think: true|false`): замер показал, что `think:
    "low"|"medium"|"high"` демон принимает без ошибки, но длина рассуждения от уровня не
    зависит — три уровня были бы враньём слайдера. **Эффорт не выбран — поле `think` не
    шлём вовсе**: у думающей модели дефолт демона — думать, и подставленный `false` молча
    отнял бы у неё рассуждения.
  - **Инструменты исполняет кокпит** (`_ollama-tools.js`): `read_file`, `list_dir`, `grep`,
    `write_file`, `edit_file`, `bash` — объявляются полем `tools` запроса, модель возвращает
    `tool_calls`, цикл «ответ → выполнить → снова запрос» крутится в `run()` до ответа без
    вызовов (потолок `MAX_TOOL_CALLS = 40`; на пределе инструменты снимаются и модель просят
    подвести итог — ход не обрывается на полуслове). Результат инструмента режется до
    4000 символов: он уезжает обратно в контекст, а окно локальной модели мало.
  - **Песочница путей — `realpath` внутрь cwd хода или доверенного каталога**
    («Настройки → Исполнители»); симлинк наружу отсекается именно резолвом, а для записи
    в ещё не созданный файл резолвится глубочайший существующий предок. Выход за границу —
    отказ ИНСТРУМЕНТУ (модель читает его и исправляется), а не падение хода.
    **У `bash` границы путей нет** — оболочка дотянется куда угодно; это осознанно (сборка
    и тесты), держится он подтверждением человека и общим fail-closed классификатором.
  - **Режимы прав** — свои (`modes()` → `toolModes()`, спрашивать о них некого): `plan`
    (только чтение), `manual` (подтверждение на каждую правку и команду), `auto`
    (классификатор), `acceptEdits` (правки молча, команды спрашивают), `dontAsk`. Мост
    всплывашки общий — тот же `direct`-путь, что у Kimi (см. выше).
  - **Правила проекта в системном блоке**: перед первым сообщением читаются `AGENTS.md`
    и `CLAUDE.md` рабочего каталога — и ТОЛЬКО они (по 24k символов каждый). Их
    `@`-включения намеренно не раскрываются: весь `docs/` проекта — около 75k токенов,
    то есть порядка двух минут префилла на КАЖДЫЙ ход (замер). Нужный документ модель
    дочитает `read_file` сама, о чём в системном блоке сказано прямо.
  - **Свои настройки из UI** (prefs `providerSettings.ollama`): `host` — адрес демона
    (у всех разный: localhost, локальная сеть, машина за VPN; машинный override — env
    `COCKPIT_OLLAMA_HOST`); `numCtx` — размер контекста (дефолт 32768: собственный дефолт
    Ollama 2048–4096 для разговора ничтожен); `keepAliveMin` — сколько держать модель
    в памяти после хода (дефолт 5, `0` — выгружать сразу; уезжает полем `keep_alive`).
    Плюс три строки-справки `kind: 'info'` (своего контрола нет, фронт рисует подписью
    с пояснением): память машины, что сейчас загружено в демон, и **во что обходится
    выбранный num_ctx в гигабайтах** — вся арифметика была и раньше, её просто никогда
    не показывали человеку. `info` в prefs не пишется (`readonly_setting`): значение
    вычисляется заново каждый раз.
  - **Потолок `numCtx`** `settings(config)` вычисляет async от железа: бюджет KV-кэша =
    свободная VRAM (nvidia-smi, кэш 5 мин) + 60% свободной ОЗУ − веса модели из
    `/api/tags`, делённый на оценку байт/токен из `model_info`
    (`block_count × kv_heads × (key+value) × 2`; `head_count_kv: null` → GQA-эвристика
    `ceil(head_count/4)`), кламп в [2048, context_length] с округлением до 1024; демон
    молчит → 131072. **Уже загруженная модель прибавляется обратно в бюджет**
    (`/api/ps`): её веса и так вычтены из свободной памяти, и без этого оценка уходила
    в минус — см. [грабли](gotchas.md). Та же оценка едет в записях каталога
    (`maxNumCtx`), а `run()` клампит num_ctx по per-model потолку выбранной модели —
    но **не ниже `MIN_AGENT_NUM_CTX = 8192`**: в меньшее окно не влезает даже системный
    блок с правилами и объявлением инструментов. При обрезке — шаг `note` и
    `contextWindow` = фактический num_ctx.
  - **Всплывашка исполнителя в шапке** (`usage()`): подписочных лимитов у локального
    демона нет и не будет, поэтому показываем локальную реальность — полосы занятости
    видеопамяти и ОЗУ, состояние демона (версия + адрес) и ресурс на каждую загруженную
    модель из `/api/ps`: сколько её в VRAM против ОЗУ, фактическое окно контекста, через
    сколько выгрузится, и кнопка «Выгрузить из памяти» (`usageActions['unload-model']` →
    `keep_alive: 0`). Это же мгновенно объясняет, почему первый ход после перерыва долгий.
    Имя модели в ключ ресурса не годится (`qwen3.6:latest` не проходит `[a-z0-9_-]`) —
    ключи `loaded-<N>`, имя живёт в подписи.
  - Демон stateless → историю разговора executor реплеит из server-owned истории чата
    (`opts.chatHistory`; note/error пропускаются, хвостовой дубликат текущего сообщения
    срезается по суффиксу — клиент сохранил его до POST). Сброс памяти и сжатие-выжимкой
    обнуляют sessionId → история не реплеится. Сессия синтетическая `ollama:<chatKey>` —
    кольцо контекста и кнопка сжатия работают штатно (compaction по умолчанию `summary`).
    Рассуждение обратно в контекст не возвращается (моделям qwen это прямо не
    рекомендовано, а места в локальном окне занимает много).
  - **Ограничение осталось одно:** сверх num_ctx Ollama молча обрезает начало разговора —
    следи за кольцом контекста и жми сжатие.
  - **Узлы схем конвейера Ollama не исполняет, и одной настройкой это не включается.**
    Раннеры движка — bash-адаптеры (`engine/lib/runners/*.sh`), они ожидают агентский CLI:
    сессии, структурированный вывод, status-запросы, объявление возможностей. У Ollama
    такого CLI нет (`ollama run` — голый REPL). Реальный путь — тонкая CLI-обёртка над тем
    же циклом инструментов плюс свой раннер; после этой работы она стала дешевле, потому
    что цикл уже написан.
- **В кратком списке Claude — только свежая версия каждого семейства** (`KEEP_VERSIONS = 1`): бинарь
  помнит много исторических id, и без фильтра селект превращается в свалку. Старые версии
  из каталога не выбрасываются, а помечаются `extra: true`. У Codex так помечаются `hidden`
  и модели, для которых сам app-server прислал замену `upgrade`;
  показывать ли их, решает настройка **«Показывать все модели»** (Настройки → Исполнители, prefs
  `showAllModels`, отдаётся вместе с `/api/providers`). Фильтрует фронт — переключение мгновенное,
  за списком на сервер не ходим. Выбранную модель не прячем никогда, иначе селект теряет значение.
  Вариант `[1m]` — не отдельная версия, а форма той же, и идёт вместе с ней.
- **Состав списка задаёт каталог**: чего в нём нет, из реестра уходит (иначе он копит всё, что когда-либо
  видел любой CLI). Переживают пересборку только записи с `custom: true` — ручные, у них же сохраняются
  правки имени/окна/эффортов.
- **Алиасы CLI отдельными пунктами НЕ показываются.** `opus`/`sonnet`/`haiku`, а также
  rollout-алиасы Codex вроде `codex-auto-review` — та же модель под другим
  именем: два пункта на одно и то же путают. Алиас привязан к модели, в
  которую CLI его резолвит, полем `aliases: ['opus']` у самой свежей версии семейства. Сохранённый
  где-то выбор `opus` резолвится в неё и в UI (`providers.resolveModelId` — селект и отправка), и на
  сервере (`modelInfo` ищет и по `aliases`). После обновления бинаря тот же старый выбор сам станет
  Opus 5 — смысл алиаса сохранён, хардкода нет.
  **Но `aliases` — плавающие CLI/legacy-имена, schema-2 `modelRef` по ним НЕ разрешается:**
  versioned ссылка `{provider:'claude', model:'opus'}` притворялась бы закреплённой, хотя
  после обновления переехала бы на другую версию. Для снятых с каталога ТОЧНЫХ id есть
  отдельное поле `modelRefAliases`; resolver проверяет его только внутри уже указанного
  provider-а и возвращает канонический `model.id`.
  **Таким versioned-алиасом стал вариант `[1m]` у модели со ВСТРОЕННЫМ миллионом** (`native_1m`):
  окно у `claude-opus-5` и `claude-opus-5[1m]` одно, поэтому два пункта в селекте — два
  одинаковых выбора. Запись остаётся одна, а снятый exact id лежит в `modelRefAliases`.
  Мигратор истории (`migrateChatModelRecord`) и миграция дефолта тем самым переписывают старый
  `{provider:'claude', model:'claude-opus-5[1m]'}` в базовый id при ближайшем чтении/записи;
  без этого уже versioned чат после сворачивания пункта получал бы `unknown_model`.
  У модели, которой суффикс окно РЕАЛЬНО поднимает (Opus 4.6, Sonnet 4.6: 200k → 1M),
  вариант остаётся отдельным пунктом — решает `context.native_1m` из реестра, а не список
  в коде. При `CLAUDE_CODE_DISABLE_1M_CONTEXT` исключение шире: все `[1m]`-пункты скрыты,
  а их versioned id мигрируют через `modelRefAliases` в соответствующие базовые
  200k-модели.
- **Модель нового чата не фиксируется при создании**: в сессии пусто = «по умолчанию», конкретный id
  берётся из реестра при показе и отправке (`providers.defaultModelId` — сильнейшая не-`extra` у
  доступного исполнителя). Фиксировать при создании нельзя: реестр к тому моменту может быть ещё не
  загружен (из-за этого новый чат открывался на алиасе `opus`).
- **Инвалидация каталога учитывает ВСЕ входы.** `CATALOG_SCHEMA` в `_meta` — версия правил
  отбора: меняется вместе с логикой, иначе у работающих кокпитов останется список, собранный
  по старым правилам. Локальный Claude-каталог пересобирается по версии CLI, схеме и
  executor-owned `catalogCacheKey(config)` — отпечатку влияющего окружения (сейчас это
  состояние `CLAUDE_CODE_DISABLE_1M_CONTEXT`); живой Codex-каталог — ещё и по минутному кэшу.
  Простого рестарта достаточно, чтобы новое значение env вступило в силу: ручной
  `?refresh=1` для этого не требуется.
- **Эффорты обнаруживаются динамически:** Claude — парсингом `claude --help`, Codex — полем
  `supportedReasoningEfforts` каждой модели из `model/list`.
  **У Claude ладдер и гейт — разные оси, и путать их нельзя.** `--help` перечисляет ступени,
  которые понимает CLI (имена и порядок), и живой список по-прежнему перебивает устаревший
  сохранённый — это отдельный инвариант `resolveModelEfforts`. Но принимает ступень не каждая
  модель: `--effort xhigh` на Opus 4.6 не игнорируется, а роняет запуск. Кому что доступно,
  объявляет реестр бинаря (`capabilities`: `effort`, `xhigh_effort`, `max_effort`), а применяет
  необязательный метод контракта `modelEfforts(model, ladder)` — вызывается в
  `getModelsRegistry` рядом с `modelFamily`, для правленных руками (`custom`) записей не
  зовётся. Имена гейтованных ступеней нигде не зашиты: `effortGates` собирается по всему
  реестру из суффикса `_effort`, поэтому новая ступень не потребует правки под каждую модель.
  Модель без возможности `effort` (Haiku 4.5, Sonnet 4.5) получает пустой список — слайдера нет.
- **Обновление CLI — кнопкой в настройках → «Исполнители»** (`POST /api/providers/:id/update`,
  команда — свойство исполнителя `updateCmd`: `claude install latest`, `codex update`). После обновления
  сбрасываются оба кэша, каталог моделей перечитывается у обновлённого исполнителя.
- **Индикатор «вышла новая версия» — есть, автообновления НЕТ.** Сервер раз в 6 часов (и через 30 с
  после старта) спрашивает npm-реестр `registry.npmjs.org/<pkg>/latest` — оба CLI публикуются там под
  тем же номером, что и нативная сборка (`_npm-latest.js`, `executor.latestVersion()`). Результат живёт
  в памяти модуля providers и уезжает в `/api/providers` полями `latest`/`updateAvailable`/`checkedAt`;
  при изменении — SSE `providers-update` (окно подхватывает без F5) и сброс кэша реестра.
  Ручная проверка — `POST /api/providers/check-updates` (кнопка «Проверить обновления»).
  UI: жёлтая точка на иконке исполнителя в топбаре + строка в его тултипе, в настройках — «Доступно
  обновление: X» и подсвеченная кнопка «Обновить». Ставится только по нажатию.
- **Грабли проверки версий:** заголовок `Accept: application/vnd.npm.install-v1+json` на эндпоинте
  `/latest` даёт **406** (abbreviated-формат — только для полного документа пакета). Сеть на стенде
  флапает (VPN): один и тот же запрос то падает, то отвечает за 0.5 с — поэтому три попытки с паузой,
  а пустой ответ НЕ затирает прошлый результат (иначе индикатор гас бы сам по себе).
- **Новые модели Anthropic обнаруживаются сами** (`claude.js discoverModels` → `/v1/models`):
  вотермарк по `created_at` в `_meta` models.json — всё, что свежее и неизвестно, дописывается
  наверх списка (tier выше максимума). Авторизация: `ANTHROPIC_API_KEY` из окружения, либо
  OAuth-токен хостового CLI — ТОЛЬКО при явном опт-ине `COCKPIT_DISCOVER_WITH_CLI_TOKEN=1`
  (без него сервер в чужие креды не лезет). Для Codex общая Platform-ручка `/v1/models`
  намеренно не используется: она не отражает доступ конкретного ChatGPT/Codex-аккаунта.
- **Грабли:** стабильного алиаса `fable` в CLI нет — нужен полный id из локального каталога,
  тогда как `opus`/`sonnet`/`haiku` резолвятся алиасами. Хостовый CLI живёт своей жизнью
  и может отставать от расширения VS Code; именно хостовый бинарь запускает Cockpit.
  `execFile` без закрытия stdin вешает `claude -p` (ждёт ввода → 5-мин таймаут) —
  в executors всегда `child.stdin.end()`. Ожидание вопроса/разрешения управляется суточным
  `PERM_WAIT_MS`, а не прежними короткими таймаутами.
- Чат: селект — optgroup по исполнителям, недоступный ИИ виден, но options disabled. Сервер выбирает
  executor по модели (`providerOfModel`); GPT без бинаря → понятная ошибка «npm i -g @openai/codex && codex login».
- **Смена ИИ внутри чата** (Claude ↔ Codex): sessionId прежнего исполнителя несовместим — фронт
  сбрасывает контекст автоматически (история чата остаётся). Конфликтов между ИИ нет: каждый
  запуск — отдельный процесс, сессии в реестрах своих CLI. Это ручное переключение чата,
  не аварийный failover конвейера.
- Настройки → «Исполнители»: у недоступного показана команда установки (из `executor.install`);
  клик по ней открывает Терминал с уже введённой командой. Команда кладётся в exact-once
  intent-очередь `stores/dock.js` до открытия route/dock; живой Terminal принимает её сразу,
  закрытый создаёт ровно один reconnect, параллельные команды делят connecting socket.
  В PTY текст отправляется только после первого вывода shell и без Enter — запуск остаётся
  за человеком.
  Там же список доверенных каталогов и кнопка «Применить ко всем ИИ».
- Тултипы — единый компонент `shared/ui/HelpTip.vue` (слот-триггер): топбар (исполнители, IP,
  CPU/RAM, хост) и микрофон чата на нём; системные title там больше не используем.
  Проп `toggle` закрепляет всплывашку кликом (повторный клик, клик мимо или Esc — закрывают):
  так сделаны иконки исполнителей в топбаре. Раньше клик по иконке уносил в настройки, и на
  планшете (ховера нет) тап показывал полосы лимитов ровно до перехода на другую страницу —
  прочитать их было нельзя. В настройки теперь ведёт кнопка «Настройки исполнителей»
  внутри самой всплывашки.
- Codex: `codex exec --json` (JSONL), резюме `exec resume <thread_id>`, песочница
  `workspace-write` + сеть + дополнительные `--add-dir` (своей всплывашки разрешений у
  codex-exec нет). JSONL нормализуется в ленту в реальном времени; summary рассуждений
  виден, если его отдал сам CLI. Авторизация = наличие `~/.codex/auth.json`.
- **Не путать**: `/api/agents` — агенты-стадии (промпты), `/api/providers` — LLM-движки, которые их исполняют.

## Авторизация Claude

- Настройки НЕ управляют ключом (форма удалена вместе с `/api/settings/claude*`); чат работает от хостового CLI
  (`claude login`) либо от ключа в `server/.state/claude-auth.json`, если тот был задан раньше (`ClaudeAuthStore` жив).

### Стоп агента

- `POST /api/chat/stop {chatKey}` → `activeRuns.get(chatKey).ac.abort()` →
  дочерний процесс CLI получает сигнал остановки. Ход возвращается не ошибкой, а обычным
  ответом «⏹ Ход остановлен» с уже
  накопленной лентой шагов — в истории видно, что агент успел сделать до стопа (`err.stopped`
  в executor'е, отдельная ветка в catch модуля чата).
- Заодно снимаются висящие запросы разрешений этого чата (`pendingPerms` по `chatKey`): отвечать
  на них уже некому, иначе всплывашка осталась бы на экране после остановки.
- В UI кнопка отправки на время хода превращается в красный квадрат-«стоп» (`.send.stop`) —
  лечит и «агент ушёл не туда», и зависший ход.
- Claude и Codex сохраняют доступный session/thread id оборванного хода, поэтому следующий
  вопрос продолжает тот же разговор. У Codex накопленной ленты шагов нет: `exec --json`
  в текущем executor-е разбирается после завершения процесса.
- Kimi после стопа СОХРАНЯЕТ session: следующий вопрос делает `session/resume` и агент
  продолжает с полным контекстом — работа и память не теряются. На pinned `0.31.1` это было
  невозможно (после `session/cancel` CLI принимал prompt без нового `llm.request`), но
  автоматизированный smoke на `0.33.0` (`tools/kimi-resume-smoke.mjs`, вердикт RESUME_OK) показал, что
  баг исправлен. Страховка на регресс: пустой post-prompt ход по-прежнему вращает binding в
  `sessionId: null` без опасного автоповтора, а повторное сообщение пользователя получает
  «досье прерванного хода» — служебный блок с выжимкой сделанного
  (`lib/chat/stopped-brief.js`, из последнего assistant-сообщения с флагом `stopped`,
  одноразово). Изменения на диске при стопе не откатываются никогда.

### Панель чата — строка состояния, а не форма

Селекты задачи/модели и слайдер эффорта — без своих коробок: подпись-метка (`задача`, `модель`,
`эффорт`), значение, шеврон; между блоками тонкая вертикальная линия. Раскрытому `<select>` всё
равно нужен непрозрачный фон (`option { background: var(--surface) }`), иначе на тёмной теме
системный список нечитаем. На полной странице задача растёт вместе со свободным местом до `620px`,
а полное название показывает общий `HelpTip`; в узкой плавающей панели задача занимает отдельный
первый ряд, поэтому модель, усилие и кольцо контекста не разъезжаются.

Диалог вопроса — строки на всю ширину (отметка · название · пояснение агента справа), а не чипы:
видно, чем варианты отличаются, и попасть мышью проще.

### Размеры раскладки — настройка УСТРОЙСТВА, и их два

Две пропорции страницы «Чаты» человек задаёт сам, потому что правильных значений для всех окон
нет: на планшете список чатов нужен узкий, на большом мониторе — широкий с полным названием, а
длинное задание агенту неудобно набирать в поле на две строки.

| что | где разделитель | ключ localStorage | границы |
|---|---|---|---|
| ширина списка чатов | `ChatsView.vue`, между списком и чатом | `cockpit-chats-list-width` | 220 px … `max(560, 40% ширины)`, но чату остаётся ≥ 420 px |
| высота поля ввода | `ChatSession.vue`, на верхней кромке блока ввода | `cockpit-chat-composer-h` (страница) / `cockpit-chat-panel-composer-h` (панель) | 48/36 px … 46vh |

Пять правил, каждое чем-то оплачено:

- **localStorage, а не серверные prefs** — как ширина дока и дерева «Кода»: серверная настройка
  уехала бы во все окна разом и навязала планшету раскладку монитора;
- **у страницы и плавающей панели РАЗНЫЕ ключи**: в панели поле высотой с половину экрана
  закрыло бы саму переписку;
- **не трогали разделитель — значения нет вовсе.** Пустая настройка означает «решает CSS», и
  умолчание остаётся за медиазапросами (300 px на широком экране, 232 px на планшете-альбоме).
  Поэтому двойной клик по разделителю настройку СТИРАЕТ, а не записывает 300: записанное число
  отняло бы у планшета его более узкое умолчание;
- **потолок высоты поля продублирован в CSS** (`max-height: 46vh` рядом с `COMPOSER_MAX_VH = 0.46`),
  и обе цифры обязаны совпадать. Скрипт не знает про поворот планшета, а поле не имеет права
  закрыть собой переписку; разошедшиеся цифры дают разделителю мёртвый ход — тянешь, число
  меняется, поле стоит (та же грабля, что у разделителя дерева в «Коде»);
- **разделители стоят ПОВЕРХ уже существующих линий** (отрицательные поля у вертикального,
  `position: absolute` у горизонтального) и места в раскладке не занимают: включение ресайза
  не имело права сдвинуть ни одну колонку.

Оба разделителя — `role="separator"` с клавиатурой (стрелки, `Shift` — крупный шаг, `Home`/`End`)
и захватом указателя, поэтому работают и пальцем. Сторож — `tests/web/chat-layout-resize.component.test.js`
(там же проверка совпадения цифр JS и CSS); геометрия отдельно замерена в headless Chrome —
раскладку happy-dom не считает вовсе.
