# Чат с агентами, базы agents/routes, реестр исполнителей

Этот документ описывает **исполнителей интерактивного чата Cockpit**. Автоматический
project/stage failover движка фабрики — отдельный слой с собственным canonical config,
coverage и error policy; он описан в [multi-AI контракте движка](../engine/CODEX.md).
В чате смена provider-а пока явная: пользователь выбирает другую модель, история остаётся,
а несовместимый CLI session context сбрасывается.

## Чат (modules/chat)

- Сервер определяет executor по выбранной модели из `/api/providers`. Claude запускается как
  `claude -p … --output-format stream-json --verbose [--model][--effort][--resume]`;
  Codex — `codex exec --json` / `codex exec resume`. По задаче cwd = первый worktree
  из exact-списка `REPO_COUNT`/`REPO_<i>_*`, остальные передаются через `--add-dir`.
  Для старых песочниц без `REPO_*` совместимо читаются `BE_WT` и `FE_WT`.
  Без задачи cwd = `config.rootDir` (корень репозитория кокпита — исполнитель сразу видит
  корневые AGENTS.md/CLAUDE.md); страница «Агенты» переопределяет его на `agents/`.
  Codex работает в `workspace-write`: пишет в cwd и дополнительные `--add-dir`, но не получает
  полный доступ к хосту. `sandbox_workspace_write.network_access=true` разрешает сетевые
  команды внутри этой песочницы (`gh`, `git`, пакетные менеджеры).
  У продолжения `--sandbox` и `-C` стоят до подкоманды `resume`: это опции родительского
  `codex exec`, после `resume` актуальный CLI их отвергает ещё до запуска хода.
- **Доверенные каталоги** задаются один раз в «Настройки → Исполнители» и хранятся в
  `prefs.trustedDirectories`. Сервер проверяет realpath каждого существующего абсолютного
  каталога, не разрешает `/`, убирает дубли и перед каждым новым ходом добавляет список в
  `extraDirs`. Claude и Codex превращают его в `--add-dir`. У `kimi acp` такого флага нет.
  Запуск Kimi имеет два режима (`config.kimiLaunchMode`, умолчание `host`): в host-режиме
  Kimi — прямой хост-процесс (parity с claude: host fs/config/credentials, permission-система
  самого CLI), и `extraDirs` ему недоступны — доступ за пределами cwd идёт через
  permission-промпты. В contained-режиме sandbox монтирует каталоги writable bind-ом и
  объявляет их сессии через server-owned
  `local.toml` (`[workspace] additional_dir`) в per-run каталоге-маске, заменяющем
  `<projectRoot>/.kimi-code` целиком (kimi-runtime-security.md). Доверенный каталог может
  содержать сам репозиторий cockpit: в contained-режиме server-owned control state внутри
  него (`chats/`, `server/.state`, `.env`, runtime/factory state) прячется пустым read-only
  mount-ом; в host-режиме этой маски нет — как у claude.
  Глобальные `~/.claude` и
  `~/.codex` Cockpit не переписывает, активный ход не меняется — следующий подхватывает
  настройку без рестарта.
- `contextTokens` — вход последнего model request, то есть активная заполненность контекста.
  Для Claude он приходит из последнего assistant-event. У Codex `turn.completed.usage.input_tokens`
  использовать нельзя: это накопительный расход всех model request в thread, после tool-call он
  ещё раз прибавляет весь вход и легко доходит до миллионов. Codex executor читает последний
  `token_count` своего rollout: `last_token_usage.input_tokens` идёт в `contextTokens`,
  `model_context_window` — в `contextWindow`, а накопительные `total_token_usage.input_tokens` и
  `cached_input_tokens` сохраняются отдельно как `totalInputTokens`/`cachedInputTokens` и видны в
  подсказке. Старые GPT-чаты без `contextMetric=active-input-v1` не заполняют кольцо ложным числом:
  точная дуга появится после следующего хода. `CONTEXT_WINDOW=200000` во фронте остаётся fallback.
- Память агента — в сессиях выбранного CLI. Для Claude/Codex Cockpit хранит `sessionId`
  в записи чата; у Kimi resume id принадлежит отдельному server-owned CAS sidecar-у
  (`ChatSessionBindingStore`), поэтому stale/поддельный PUT браузера не может назначить session.
- **Пустой ответ Claude («пусто»):** `claude -p` может вернуть result без текста — агент завершил ход
  tool-call'ом, который plan-режим запретил (Bash/Write и т.п.), или упёрся в лимит шагов.
  Сервер маппит это в понятное «⚠ …»-сообщение (по `subtype` и `permission_denials`) и пишет
  warn в лог. Типичный триггер: просьба «сделай/запусти/разбери файл» — чат только читает.
- Один Pinia-стор `chat` питает и плавающую панель (ChatPanel, есть на всех страницах, кроме `/chats`), и страницу «Чаты» (ChatsView, телеграм-раскладка: ChatList-сайдбар + ChatSession).
- **Плашки над композером — отдельные компоненты** рядом с `ChatSession.vue`: `StepList.vue` (лента шагов
  хода), `ChatQuestion.vue` (вопрос агента), `ChatPermission.vue` (запрос разрешения / план на
  утверждение). Каждая держит свою разметку, стили и мелкое состояние; ChatSession только решает,
  какую показать, и передаёт ответ в стор. Разрешение и вопрос приходят по SSE в стор глобально —
  компонент показывается, если `chatKey` совпал с открытым чатом (`forThisChat`).

### Лента хода агента (как в чате VS Code)

- У ленты один provider-neutral контракт (`lib/chat/stream-steps.js`): `start`
  (фактическая модель + режим прав), `think`, `text`, `tool` (вызов инструмента с превью по типу:
  команда Bash, файл Read/Write, дифф Edit, запрос Grep…), `res` (результат: ok/ошибка + краткий вывод),
  `note` (ретраи API, компакт). Общий sink ставит timestamp, режет всё длинное (1200 симв., 2000 на
  куски диффа) и ограничивает ход 400 шагами. Каждый executor держит свой normalizer
  (`_claude-steps.js`, `_codex-steps.js`); новый ИИ добавляет такой же рядом с executor-ом, без
  условий в `modules/chat` или Vue.
- Путь: `executor run(onStep)` → `modules/chat` → SSE `chat-step {chatKey, step}` → стор копит в
  `sess.steps` → `views/chat/StepList.vue`. Claude читает свой stream-json, Codex — JSONL построчно
  ещё во время работы, а не после завершения процесса. У Codex тип `reasoning` показывает только
  отданное CLI summary (`text`/`summary`); техническое `raw_content` намеренно игнорируется.
  Копия шагов лежит в `activeRuns`, поэтому F5 посреди хода не теряет уже показанное
  (`GET /api/chat/active` отдаёт `steps`).
- После ответа лента переезжает в сообщение (`msg.steps`) и показывается свёрнутой строкой
  «Ход агента: N действ. · M размышл.». Дифф правки строит фронт (`shared/diff.js`, LCS по строкам;
  свыше 400 строк — вырожденный «всё убрано / всё добавлено») и показывает В ДВЕ КОЛОНКИ —
  слева «было», справа «стало» (`splitRows`: подряд идущие del/add ставятся друг напротив друга,
  лишние строки получают пустого соседа).
- **Всплывашки держим компактными** — они живут над композером и не должны съедать экран:
  у разрешения кнопки в строке заголовка, команда — блоком с переносами; у вопроса варианты —
  строками с пояснением, поле своего ответа скрыто за пунктом «свой ответ…»; вся плашка
  ограничена по высоте со скроллом (`max-height: 38vh`).
- Время размышления («думал 12 с») считается по `at` соседних шагов — от предыдущего шага к `think`:
  блок размышления приходит уже готовым, поэтому его длительность — это пауза ПЕРЕД ним.
- Подряд идущие одинаковые `note` схлопываются в одну строку с «×N» (ретраи сети идут сериями).

### Диалог: агент задаёт вопрос (AskUserQuestion)

- В headless-режиме сам инструмент отвечать некому: выполненный AskUserQuestion возвращает агенту
  пустое «User has answered your questions: .». Поэтому вопрос перехватывается на уровне
  permission-prompt-tool (он получает `tool_name: AskUserQuestion` с полным списком вариантов),
  а ОТВЕТ пользователя возвращается как `behavior: 'deny'` с текстом в `message` — единственный канал,
  по которому текст доезжает до агента дословно (проверено: агент читает его как результат
  инструмента и продолжает ход).
- Поток: SSE `chat-question {pid, chatKey, questions, at}` → `views/chat/ChatQuestion.vue` (варианты,
  мультивыбор, поле «свой ответ») → `POST /api/chat/permission/:pid {answers}` → сервер собирает текст
  («Ответ пользователя из кокпита: • Заголовок: Вариант»). Пропуск — пустые answers.
- Из-за этого AskUserQuestion попадает в `permission_denials` результата; в `claude.js` он исключён
  из списка «действия не были разрешены», иначе пустой ответ подменялся бы ложным предупреждением.
- `ExitPlanMode` остаётся обычным разрешением, но в всплывашке показывается как план
  (текст целиком, кнопки «Утвердить план» / «Доработать»).

### Режимы прав (`--permission-mode`)

- **Список режимов даёт сам CLI, не хардкод.** Флага нет в `--help`, зато CLI перечисляет
  допустимые значения в ошибке валидации — `claude.js modes()` спрашивает его заведомо неверным
  значением и парсит «Allowed choices are …». Подписи известных режимов и порядок — в
  `MODE_LABELS` (от осторожного к свободному, план первым);
  незнакомый режим показывается как есть.
- Выбор живёт в чате (`sess.mode`) и запоминается как дефолт новых чатов (`defMode`), едет в теле
  запроса и санитайзится на сервере по тому же списку (кэш 10 мин — `modes()` запускает подпроцесс).
  Режим страницы (`pageMode`) остался только дефолтом, когда пользователь ничего не выбрал.
- Что меняется по факту: `manual` — всплывашка на каждое действие (как было), `auto` — безопасное
  делает сам, `acceptEdits` — правит файлы молча, `plan` — только читает и заканчивает планом,
  `dontAsk`/`bypassPermissions` — без подтверждений вовсе.
- **План остаётся в переписке**: при ответе на `ExitPlanMode` фронт добавляет в чат сообщение
  «План — утверждён / на доработку» с его текстом. Всплывашка закрывается, а решение принималось
  по этому тексту — он должен остаться в истории.

### Автопрокрутка

- Едем вниз на новые сообщения, шаги ленты и всплывашки — но ТОЛЬКО если пользователь и так внизу
  (`atBottom`, порог 120 px, отслеживается по `scroll` контейнера `.cs-body`). Отлистал историю
  вверх — не дёргаем. Отправка своего сообщения принудительно возвращает вниз (как в мессенджерах).
- **Грабля:** прокрутку тянули ещё два места — безусловный `watch` на длину сообщений и `scrollDown()`
  в хвосте `submit()`, который срабатывал ПОСЛЕ ответа агента (то есть спустя десятки секунд) и
  утаскивал вниз того, кто в это время читал историю. Оба убраны: единственная точка — `autoScroll`.

### Что реально ушло в запуск (проверка модели и эффорта)

- `actualModel` — модель из потока (`system/init.model`, точнее — `message.model` ходов). CLI резолвит
  алиасы сам: на 2.1.85 `opus` → `claude-opus-4-6`. Показывается строкой под панелью управления
  («факт: …») и подписью у ответа агента; расхождение с выбранной подсвечивается.
- Уровень эффорта санитайзится по реестру ПЕРЕД запуском: `--effort xhigh` для claude — не «игнор»,
  а падение CLI с ошибкой валидации (`It must be one of: low, medium, high, max`). Неподдерживаемый
  уровень заменяется на `high` и пишется warn в лог.
- **Слэш-команды**: ввод «/» в композере открывает меню с описаниями (фильтр по мере набора,
  ↑/↓ + Enter/Tab, Esc, клик). Команды клиентские, на сервер не ходят: `/clear` — история+контекст,
  `/reset` — только контекст, `/new` — новый чат. Список — const `COMMANDS` в ChatSession.vue.
  **Грабля:** класс выделения строки меню — `on`, не `sel` (`.sel::after` в этом же файле рисует шеврон селектов).
- **Автоназвание нового чата — общий хук Cockpit**: первый ход безымянного чата отправляется с
  `requestTitle`; `modules/chat` добавляет provider-neutral служебную инструкцию в тот же запрос.
  Агент возвращает маркер `COCKPIT_CHAT_TITLE` с осмысленным названием ровно из трёх слов,
  сервер валидирует его и вырезает из ответа/живой ленты, а клиент применяет как метаданные чата.
  Отдельного модельного вызова нет. Пока основной ход не завершён, `shared/chat-title.js` показывает
  мгновенный локальный вариант; ответ агента заменяет только его — ручное название и заголовок
  задачи всегда сильнее. Тот же заголовок едет через `chats/pending` после F5/закрытия окна.

### Кольцо контекста и сжатие (почему без него разговор дорожает вдвадцатеро)

- **Цена хода растёт не от объёма работы, а от размера контекста.** Модель не помнит разговор
  между запросами: каждый запрос — это заново весь контекст на вход. Обычно это дёшево (кэш
  промпта, чтение по 10% цены), но кокпит поднимает процесс CLI **на каждое сообщение**, и выше
  ~250k контекста кэш на новом ходу перестаёт совпадать: из него читается только системный
  промпт (16–21k), а вся переписка пишется в кэш заново — по двойному тарифу вместо десятой
  доли. Разница на одних и тех же токенах — **×20**.
- **Практическая проверка по логам длинных сессий:** после перехода через ~250k полные
  перезаписи начинают доминировать в объёме записи кэша; ниже этого порога они не возникают.
  Поэтому порог автосжатия по умолчанию стоит заметно ниже потолка большого окна модели.
- **Почему не спасал автокомпакт CLI:** он есть и включён по умолчанию, но порог у него —
  доля ОКНА модели. Замер по сессиям, где компакт реально сработал: окно 200k → сжатие на ~166k,
  окно 1M → ~959–999k. Чаты кокпита идут моделью с окном 1M, поэтому в дорогой зоне 250k–950k
  компакт не включается никогда.
- **Настройка «Запуски → Сжимать контекст чата при N токенах»** (prefs `chatAutoCompactWindow`,
  дефолт 200 000) кладёт порог туда, где он нужен. Claude получает его переменной
  `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, Codex — config override
  `model_auto_compact_token_limit=N` перед `resume`. Читается перед каждым ходом — правка
  действует сразу, без рестарта. `0` — не вмешиваться, у CLI остаётся собственный порог.
- **Цвет кольца — от порога сжатия, а не от процента окна и не от вбитого числа:** красное
  на `min(chatAutoCompactWindow, 80% окна модели)`, жёлтое на 80% от этого (`ctxLimit` в
  `ChatSession.vue`; порог приезжает в стор чата вместе с историей — `GET /api/chat/store`
  отдаёт его полем `compactWindow`, а «Настройки» после сохранения обновляют стор сразу).
  Кольцо краснеет ровно там, где кокпит и так сожмёт. Одного процента окна мало: на 1M
  «жёлтые» 60% — это 600k, то есть кольцо молчало ровно в той зоне, где ход стоил в двадцать
  раз дороже. Одного абсолютного числа тоже мало: у модели с окном 200k порог 200k
  недостижим — кольцо осталось бы зелёным до конца разговора, поэтому потолок по окну.
- **Клик по кольцу — СЖАТИЕ** (с подтверждением), **Alt+клик — сброс памяти агента**, он же
  `/reset`. Раньше клик делал только второе, причём молча: переписка на экране остаётся (история
  кокпита к сессии CLI не привязана), поэтому «ничего не произошло» — и сброс легко было принять
  за сжатие. Теперь у каждого действия свой вопрос, а результат виден плашкой `role: 'note'`.
  Для Kimi локального `sessionId = null` недостаточно: стор сначала вызывает
  `POST /api/chat/session/reset`, сервер вращает sidecar в пустую generation, и до подтверждения
  reset отправка заморожена. Ошибка reset сохраняет прежнюю session и требует явного повтора.
- **Как устроено сжатие** — `POST /api/chat/compact` и `/api/tasks/:id/compact`, тот же
  `runChat` и та же очередь чата (сжатие — полноценный ход агента, а два CLI на одну сессию
  не живут). План берётся у исполнителя, поле `compaction`:
  - `{ kind: 'native', message: '/compact' }` — CLI понимает слэш-команду и в режиме
    `-p --resume`: в сессии появляются `compact_boundary`/
    `isCompactSummary`, id разговора не меняется. **Грабля:** stdout такого хода ПУСТОЙ (вывод
    команды локальный, в поток не идёт), поэтому текст для ленты подставляет сервер, а повтор
    «пустого хода» для сжатия отключён — иначе второй прогон сжал бы уже сжатое.
  - `{ kind: 'summary' }` (codex и любой новый исполнитель по умолчанию) — родного компакта нет,
    сервер заказывает рабочую выжимку текстом (`SUMMARY_PROMPT`: задача, решения и их причины,
    файлы с путями, что сделано и что осталось). Клиент кладёт её в `pendingSeed`, обнуляет
    `sessionId`, и выжимка уезжает первым блоком СЛЕДУЮЩЕГО сообщения. `pendingSeed` живёт в
    файле истории — иначе F5 превратил бы сжатие в потерю памяти; при провале отправки семя
    возвращается в ожидание.
- **Пока сжатие идёт, чат заморожен, кроме поля ввода** (`frozen` в `ChatSession.vue`): селекты
  задачи/модели/режима, слайдер усилия, «На конвейер» и отправка выключены — ход уже в полёте,
  менять ему модель или задачу поздно, а второй ход на ту же сессию её убьёт. Текстовое поле,
  вложения и диктовка живые: следующее сообщение готовится, пока агент пересказывает разговор.
  Признак работы один — кольцо крутится (у сжатия нет ленты шагов), поэтому на это время дуга
  становится коротким бегунком: полное кольцо при вращении выглядело бы неподвижным.
- **Идёт ли сжатие — знает сервер, а не окно.** Флаг `compact` лежит в `activeRuns`, уезжает
  в `GET /api/chat/active` и в SSE `chat-turn-start`, а окна ставят по нему `compacting`. Раньше
  признак жил ТОЛЬКО в затеявшем окне: на компьютере кольцо крутилось, а планшет, открытый на том
  же чате, не показывал ничего — ни кольца, ни «думает…». Догнать состояние было нечем: у родного
  компакта stdout пуст всегда, значит ни `chat-progress`, ни `chat-step` по нему не идёт, и
  одноразовый `chat-turn-start`, пропущенный в офлайне, был единственным шансом. Отсюда же сверка
  `_loadActive()` — при загрузке и на каждое `hello` (переподключение SSE, рестарт сервера):
  сверяемся ПОЛНОСТЬЮ, как со спросами, иначе после рестарта кольцо крутилось бы вечно. Не трогаем
  только то, по чему из этого окна висит свой незакрытый запрос (`compactInflight`) — его разморозит
  собственный ответ. «Думает…» во время сжатия не показываем нигде: индикатор один — кольцо.
- **Сжатие останавливается кнопкой «стоп»**, как обычный ход (это тот же процесс CLI в `activeRuns`).
  Оборванный ход возвращается обычным ответом с `stopped: true`, и `compact()` обязан его отличать:
  для Claude/Codex контекст остался прежним, а общий путь обнулил бы счётчик и написал
  «контекст сжат». Kimi после cancel не возобновляется: сервер возвращает `sessionReset: true`,
  клиент гасит метрики, а следующий явный ход создаёт чистую session.
- **Точный размер после сжатия не знает никто:** ход сжатия читал ещё старую переписку, поэтому
  его `contextTokens` — это размер ДО. Сервер отдаёт 0, кольцо гаснет, а настоящую цифру измерит
  следующий обычный ход — так и написано в подсказке кольца. В плашке остаётся только размер ДО
  («было N токенов»): это единственное честно известное число.

### Хранилище истории — chats/ в корне проекта

- Файловая часть вынесена в `lib/chat/history-store.js` (`ChatHistoryStore`: scan/save/read,
  атомарная запись, миграция со старой одно-файловой схемы) — модуль `modules/chat` остался
  маршрутами и логикой запуска агента.

- Каждый чат — файл `chats/YYYY-MM/<id>.json` (месяц СОЗДАНИЯ чата — файл не переезжает), мета — `chats/meta.json`, внутри самогитигнор (`*` + `!.gitignore`).
- Запись атомарная (tmp+rename) и только изменившихся чатов (сравнение JSON); битый файл пропускается с warn — теряется один чат, не вся история.
- Миграции одноразовые: localStorage (`cockpit-chat-v2`) → серверный файл → пофайлово; legacy `server/.state/chats.json` переименован в `.migrated`.
- **Присланная копия не замещает серверную, а сливается с ней** (`lib/chat/merge-chat.js`,
  вызывается из `saveOne`). Историю пишет клиент и шлёт чат целиком, поэтому отставшее окно
  (потеряло SSE, уснул планшет, сменился адрес) клало устаревшую ленту поверх свежей и стирало
  ответы, дошедшие до другого устройства. Правило простое: **сервер не теряет сообщений** —
  присланная лента может только дополнять серверную.
  - Ленты сравниваются позиционно (совпавшее начало + разошедшиеся хвосты), а не по времени:
    у отставшего окна `updatedAt` как раз может быть свежее — в него продолжают печатать.
  - Серверный хвост сохраняется целиком, из клиентского добавляется только то, чего в серверном
    нет; кратность учитывается (два одинаковых «Делай» подряд не схлопываются в одно).
  - Метка `role: 'error'` из клиентского хвоста выбрасывается, если в серверном уже есть ответ
    агента: «Failed to fetch» — это про сеть того окна, а не про разговор, и на других
    устройствах ход выглядел проваленным при живом ответе.
  - **Метка обрыва, за которой стоит ответ агента, снимается из ленты целиком**
    (`dropStaleErrors`, применяется и при первом сохранении чата). Обратный порядок того же
    случая: окно записало ошибку РАНЬШЕ, чем агент договорил, а ответ приехал потом и лёг
    следом. В этом случае лента выглядит как `вопрос → ⚠ Failed to fetch → ответ`, хотя ход
    завершился успешно.
    Признак чисто позиционный: после настоящего провала агент не заговорил бы сам — человеку
    пришлось бы переспросить, и между меткой и ответом стоял бы `user`. Гадать по тексту
    ошибки («Failed to fetch», «Load failed», «NetworkError») ненадёжно, поэтому не гадаем.
    Метка в самом конце ленты не трогается: ход ещё идёт, ответ на неё только едет.
    Чистка идёт и по присланной ленте ДО сравнения — иначе окно со старым фронтом (кэш PWA)
    разошлось бы с почищенной серверной копией на первой же метке и вернуло её обратно.
  - Единственное осознанное сокращение — «Очистить чат» (пустая лента): её уважаем. Отдельные
    сообщения в интерфейсе не удаляются, поэтому других легальных сокращений нет.
  - Состояние агента (`sessionId`, все поля context/usage, `pendingSeed`, `compactedAt`) берётся у
    более свежей копии: старый `sessionId` увёл бы агента в забытую сессию, потерянный
    `pendingSeed` — это потерянная память после сжатия.
  - Сохранения одного чата сериализованы очередью (`withChatLock`): два окна, пишущие
    одновременно, читали бы диск до записи друг друга и всё равно теряли хвосты.
- **Обрыв связи окна после начала model POST — не провал хода, и в общую историю он не пишется**
  (`stores/chat.js`, `catch` в `send`). Ход живёт в процессе сервера, а не во вкладке:
  порванный `POST /api/chat` его не останавливает, ответ вернётся через `chats/pending`.
  До model POST действует другая гарантия: чат сначала сохраняется с CAS-revision; stale-ответ
  другого окна безопасно повторяет только `PUT` (до трёх попыток), сохраняя выбранную в
  отправляющем окне модель. Сбой сохранения однозначно означает «агент не стартовал» и
  показывается обычной ошибкой, а не ложной плашкой «ход продолжается». Раньше сюда падала запись
  `role: 'error'`, уезжала в файл истории — и живой ход выглядел проваленным на всех
  устройствах разом. Теперь различаем и фазу, и тип ошибки: локальный флаг `offline`
  поднимается только для сетевого `TypeError`/таймаута после начала model POST; HTTP-ответ
  сервера и любой сбой до этой границы остаются обычной ошибкой в ленте. Плашка
  «📡 Связь с сервером прервалась» в этом окне, в историю не едет (его нет в `slimOf`,
  он в `RUNTIME_KEYS`). Снимается, как только связь дала о себе знать: `hello`, `chat-done`
  или забранный из `pending` ответ. Пока флаг поднят, «думает…» не гасится — правду об
  активных ходах вернёт `_loadActive()`.
  - Если слияние что-то восстановило, сервер шлёт ВТОРОЕ событие `chat-store` — уже без `origin`
    (с задержкой 500 мс) — чтобы неполную ленту перечитало и то окно, которое её прислало:
    своё эхо оно пропускает, а без задержки событие обгоняет ответ на этот же `PUT` и окно
    считает свою копию неотправленной. Проверки — `tests/server/chat-store-merge.test.js`.
- Изменения **разъезжаются сами**: каждая запись помечена `origin` — случайным id окна, — сервер после реальной записи шлёт
  SSE `chat-store` (`{id, archived|gone, origin}`), а остальные окна тянут ровно изменившийся чат
  через `GET /api/chat/store/chat/:id`. Раньше история читалась ровно один раз за загрузку страницы
  (`_load` под `loaded`/`loadPromise`), поэтому разговор, начатый на планшете, появлялся на
  компьютере только после F5. Тянем по одному чату, а не всю историю: меняется всегда один чат,
  а история растёт. Правила приёма:
  - **своё эхо пропускаем** по `origin` — изменение уже в сторе, а перечитывание гонялось бы
    с ещё не уехавшими правками;
  - **несохранённое своё не затираем**: если `slimOf(чат)` разошёлся с тем, что окно последний раз
    успешно записало (`sentChats`), чужую копию не принимаем — наш `_persist` всё равно уедет следом
    и победит, а принятая копия стёрла бы набранный черновик;
  - **объект чата обновляется на месте**, а не подменяется: ссылку на него держат и компоненты,
    и идущий прямо сейчас `send()` — подмена оставила бы ход писать ответ в отцепленный объект;
  - **рантайм-поля берутся у окна** (`RUNTIME_KEYS`: sending/compacting/steps/…), иначе чужая правка
    гасила бы «думает…» и стирала ленту идущего хода;
  - **`chat-turn-start` по неизвестному чату** сам тянет этот чат (и следом `_loadActive`): чат
    завели и сразу отправили сообщение на другом устройстве, и его копия к нам ещё едет.
  - **мета — только дефолты новых чатов** (`defModel/defEffort/defMode`). `activeId` НЕ применяем:
    у каждого устройства своя открытая вкладка, подменять её на чужую — забрать разговор из-под рук.
- На `hello` (связь восстановилась: сон планшета, рестарт сервера) история сверяется целиком —
  `_resyncStore()`: точечные события за время разрыва прошли мимо, и без сверки заведённый в это
  время чат снова ждал бы F5. Правила приёма те же плюс два: **совпавшее не трогаем** (сравнение
  со слепком в `sentChats` — иначе каждое переподключение подменяло бы массивы сообщений и
  перерисовывало открытый чат), и **пропавшее на сервере удаляем только если сервер его видел**
  (`sentChats.has(id)`) — свой новый чат, чья запись ещё едет, не трогаем. Первое `hello` приходит
  сразу за `_load()`, поэтому сверка пропускается, если история моложе 2 с (`storeSyncedAt`).
- Чат из истории может прийти без части полей (запись старой версии, ручная правка файла) —
  `_normalize()` дозаполняет их при загрузке. Для старого Codex-контракта он ещё переносит
  прежний cumulative `contextTokens` в `totalInputTokens` и обнуляет дугу до нового точного
  замера; иначе старые миллионы снова выдавали бы себя за заполненность.
- **Страховочный снимок в браузере** (`localStorage['cockpit-chat-snapshot']`): между «ответ пришёл»
  и «PUT долетел» есть окно, и рестарт сервера в этот момент СЪЕДАЛ последний ответ — следующего
  изменения, на котором стор бы пересохранился, могло не быть (воспроизводилось: 2 сообщения → 1).
  Теперь каждый `_persist` пишет снимок, при неудачном PUT идут ретраи с нарастающей паузой
  (1→2→4…→15 с), а `_load` берёт снимок, если он свежее серверной копии (сравнение по максимальному
  `updatedAt` сессий), и сразу возвращает его на сервер. Не влез в квоту — пишется усечённая версия
  (последние 30 сообщений на чат).
- **Черновики**: неотправленный текст хранится в самом чате (`sess.draft`, едет на сервер вместе с
  историей), поэтому переживает переключение чатов, F5 и виден в другом окне. В списке чатов
  показывается вместо последнего сообщения с пометкой «черновик:» (как в телеграме). Пишется с
  задержкой 400 мс, дожимается на `beforeunload`/размонтировании, гасится при отправке — иначе
  дебаунс успевал записать уже отправленный текст. `updatedAt` при наборе НЕ трогаем: чат не должен
  прыгать в начало списка от того, что в нём печатают.
- **Аватар в списке — иконка исполнителя** (`ProviderIcon` по модели чата) плюс актуальная
  подпись модели из реестра рядом с названием; буква из названия осталась фоллбэком, пока реестр
  исполнителей не загрузился.
- **Индикация активных агентов**: сервер держит `activeRuns` (chatKey→startedAt/tokens/compact),
  `GET /api/chat/active`; фронт восстанавливает «думает… · N ток.» по нему при загрузке (F5) и на
  каждое `hello` — переподключение SSE и рестарт сервера тоже приводят состояние в порядок,
  включая снятие ходов, умерших, пока связи не было. SSE `chat-progress` тоже поднимает sending,
  `chat-done` гасит во всех окнах. Видно кольцом-спиннером в аватаре чата в списке (бейджи навигации
  заняты непрочитанными, см. ниже); сжатие для списка — такая же занятость чата, отличается подсказка.
- **Непрочитанные чаты** (`sess.unread`, едет в `chats/<id>.json` вместе с историей): метка ставится,
  когда ответ агента пришёл, а на этот чат не смотрели. «Смотрели» — одно правило `chat._visible(id)`
  на весь кокпит: вкладка ОС активна + открыт раздел «Чаты» или плавающая панель + это активный чат;
  по нему же решается, слать ли оповещение (иначе бейдж спорил бы с уведомлением). Ставится в `send()`
  и в `_collectPending()` (ответы, доехавшие пока страницы не было). Снимается сама собой в
  `ChatSession.vue`: компонент рисуется ровно тогда, когда на чат смотрят, — плюс `visibilitychange`
  для ответа, прилетевшего в свёрнутую вкладку. Считает getter `unreadCount` (открытые + архивные:
  чат могли закрыть, пока агент думал). Показывается тремя местами: бейдж на пункте «Чаты» в навигации,
  бейдж на плавающей кнопке чата (`ChatPanel`), точка на аватаре в списке.
- **Оформление ответов агента**: подпись «✳ Агент» + акцентная полоска слева, текст рендерится
  безопасным GFM (`shared/md.js`: ссылки, списки, таблицы и код; raw HTML экранируется,
  опасные URL отбрасываются) — отличимо от системных плашек и пузырей.
- **Usage-корзины Claude**: каноничный источник — массив `limits` ответа oauth/usage (из него строится
  официальная панель): `session`, `weekly_all`, `weekly_scoped` (+`scope.model.display_name`,
  например «Fable» — модельные недельные ведра приходят сами, хардкода имён нет).
  `extra_usage` — доплата сверх лимитов, отдельный бар с бюджетом («61 из 170 EUR»).
  Верхнеуровневые ведра (`five_hour`…) — только фоллбэк. Сеть до api.anthropic.com флапает
  (VPN): retry ×2 + при сбое отдаются прошлые данные, а не пустота.
- **Usage-корзины Codex**: `codex app-server` → документированный read-only JSON-RPC
  `account/rateLimits/read`. Cockpit создаёт короткое локальное соединение, выполняет
  `initialize`, читает `rateLimitsByLimitId` (либо совместимый `rateLimits`) и завершает
  только свой дочерний процесс. Ни thread, ни turn, ни вызов модели не создаются; файлы
  диалогов не читаются. Имена отдельных модельных семейств приходят от OpenAI и появляются
  в шапке без хардкода и релиза Cockpit. Из того же ответа показываются купленные ChatGPT
  credits. Если `rateLimitResetCredits.availableCount > 0`, появляется подтверждаемая кнопка
  расхода заработанного сброса; `account/rateLimitResetCredit/consume` получает стабильный
  `requestId` как `idempotencyKey`, после успеха лимиты перечитываются. Покупка и
  автопополнение остаются по ссылке на `chatgpt.com/codex/settings/usage`: документированного
  тумблера сверхлимита в Codex app-server нет.
- **Доплата Claude управляется прямо из шапки**: тумблер вкл/выкл и месячный потолок.
  `extra_usage` приходит как account resource с общими контролами, а не как особый тип
  полосы во фронте. Ручки приватные, сняты с бинаря CLI (это его `/usage-credits`):
  `POST/PUT /api/oauth/organizations/<uuid>/{setup_overage_billing, overage_spend_limit}`,
  авторизация — OAuth-токеном хостового CLI, uuid организации из `~/.claude.json`
  (`oauthAccount.organizationUuid`), суммы — в минорных единицах.
  При ПЕРВОМ включении сначала `setup_overage_billing`, потом флаг — иначе доплата не заведена.
  Выключение (`is_enabled:false`) сам CLI не зовёт (у него это только через claude.ai): поле
  в схеме есть, но при отказе API текст ошибки показываем как есть, а рядом всегда висит
  ссылка на claude.ai/settings/usage. Снятие потолка («без ограничения») сознательно не
  поддержано: счёт без верхней границы заводят осознанно на сайте, а не тумблером в шапке.
  Подтверждение спрашивается ВНУТРИ всплывашки: модалка забрала бы фокус, всплывашка
  закрылась бы — и ни вопроса, ни результата человек не увидит.

### Модульное подключение нового ИИ

Реестр сканирует `server/src/lib/executors/*.js`; отдельной регистрации Kimi в Fastify и Vue
не требуется. Адаптер экспортирует базовый контракт `id/name/vendor/color/bin/probe/auth/
seedModels/run`, а при наличии API аккаунта добавляет:

```js
{
  async usage() {
    return {
      state: 'ok',
      bars: [{ key: 'month', label: 'Месяц', pct: 24 }],
      resources: [{
        key: 'balance',
        label: 'Баланс Kimi',
        summary: '12 CNY',
        controls: [
          { id: 'top-up', kind: 'link', label: 'Пополнить', href: 'https://…' },
          {
            id: 'auto-top-up',
            kind: 'toggle',
            label: 'автопополнение',
            value: false,
            action: 'configure-auto-top-up',
            field: 'enabled',
            confirm: { on: { text: '…', label: 'Включить' }, off: { text: '…', label: 'Выключить' } },
          },
        ],
      }],
    };
  },
  usageActions: {
    'configure-auto-top-up': async ({ payload, requestId, config, deps }) => {
      // Адаптер валидирует payload и вызывает только API своего провайдера.
    },
  },
}
```

Ядро нормализует ресурсы, отбрасывает не-HTTPS ссылки и неизвестные controls. Внешний клиент
не может передать произвольный метод: выполняются только ключи из `usageActions` конкретного
адаптера. `requestId` обязателен на границе UI для идемпотентных денежных/расходуемых операций.
- **Недоставленные ответы**: если клиент умер во время работы агента (F5/закрытие вкладки),
  сервер по завершении видит `request.socket.destroyed` и пишет ответ в `chats/pending/<id>.json`
  (+SSE `chat-orphan` живым окнам). Фронт при `_load()` и по этому событию забирает
  GET /api/chat/pending, раскладывает по чатам (dedup по `pid` в сообщении) и подтверждает DELETE'ом.
  Ошибки тоже доезжают (role: error). Навигация внутри SPA ответы не теряет и без этого —
  стор глобальный, запрос переживает переключение чатов/разделов.

### Всплывашка разрешений (аналог permission prompt Claude Code)

- Чат работает в `--permission-mode default`: чтение свободно, на действия (Bash/правки) claude
  спрашивает через `--permission-prompt-tool mcp__cockpit-perm__approve` — мини-MCP
  `lib/chat/permission-mcp.js` (newline-JSON-RPC вручную, без SDK), который держит HTTP-запрос
  к `/api/chat/permission-request`, пока пользователь не ответит.
- Поток: claude → MCP → POST permission-request → SSE `chat-permission {pid,tool,input,chatKey,at}` →
  всплывашка в ChatSession (жёлтая, показывает команду/файл) → POST `/api/chat/permission/:pid`
  {allow} → `chat-permission-done` закрывает всплывашку во всех окнах.
- **Нюанс:** то, что уже в глобальном allowlist пользователя (~/.claude/settings.json), выполняется
  БЕЗ всплывашки — prompt-tool зовётся только для того, что иначе спросило бы.

### Спрос ВИСИТ, пока не ответишь (без короткого UI-таймаута)

- Было: 4 минуты на ответ, дальше сервер отвечал агенту deny («не ответил — действуй сам»).
  Человек отошёл — агент уезжал дальше по собственному разумению, а выбор пропадал с экрана.
  Теперь ожидание живёт до ответа (потолок `PERM_WAIT_MS` = сутки), снимается только
  «стопом» или концом хода (`dropPending` — иначе чип «ждёт ответа» висел бы вечно).
- Ждать должны ВСЕ три звена, иначе выигрыша нет:
  1. кокпит — держит HTTP-запрос от permission-mcp (см. выше);
  2. **CLI** — `MCP_TOOL_TIMEOUT` в окружении запуска + `timeout` у самого сервера в `--mcp-config`
     (per-server override, «hard wall-clock limit per call»). Без них CLI обрывает вызов
     инструмента своим дефолтом, и агент идёт дальше, пока вопрос ещё висит на экране;
  3. **ход агента** — `execFile` не имеет `timeout`: долгие задачи могут выполняться часами.
     Автоматического лимита длительности у хода нет; прерывание через `ac.abort()` выполняет
     только явная кнопка «стоп».
- `GET /api/chat/waiting` — что висит прямо сейчас. Нужен потому, что SSE доставляет событие
  один раз: после F5 (и во втором окне) всплывашку иначе некому показать. Фронт зовёт его при
  загрузке стора и на каждое `hello` (переподключение SSE) и **синхронизирует список целиком** —
  после рестарта сервера запросы умирают вместе с процессами агентов, и старые записи стали бы фантомами.
- Во фронте висящие спросы — карта `chat.pending` (pid → `{kind: 'perm'|'question', chatKey, …}`),
  а не два одиночных поля: агенты работают в нескольких чатах, и новый спрос не должен затирать
  чужой. Компонент берёт свой через `permFor(chatKey)` / `questionFor(chatKey)`.

### «Требуют вмешательства»: чипы, чтобы вопрос не проехал мимо

- Вопрос агента легко пропустить — работа при этом СТОИТ. Поэтому такой чат отмечается сильнее,
  чем непрочитанный (`waitingChats`/`waitingCount` в сторе — считаются чаты, не запросы):
  бейдж на пункте «Чаты» и на плавающей кнопке чата (жёлтый, пульсирует, перебивает синий бейдж
  непрочитанных), чип «ждёт ответа» + тёплая полоска на строке в списке чатов, и сам чат
  поднимается наверх списка. Плюс системное оповещение в момент спроса, если на чат не смотрят
  (правило `_visible` — то же, что у непрочитанных).
- Чекбокс «Разрешать до конца сессии»: карта chatKey→Set(tool) в памяти вкладки (chat.js,
  `permAutoAllow`) — совпавшие запросы отвечаются allow автоматически, в allowlist ничего не пишется.
- **Живой счётчик токенов**: claude запускается с `--output-format stream-json --verbose`,
  executor суммирует output_tokens по assistant-событиям → onProgress → SSE `chat-progress
  {chatKey, tokens}` → «думает… · N ток.» в чате.
- Перезапуск сервера — ТОЛЬКО `bin/restart` (гасит порт, ждёт освобождения, стартует, health-чек):
  в репо работают параллельные сессии, ручные kill+start ловили EADDRINUSE и рвали чужие чат-запросы.

### UI-контекст: чат знает, где пользователь

- Стор `ui-context` (`web/src/stores/ui-context.js`): страницы репортят детали `set(key, val)`/`clear(key)`
  (маршрут в Routes, таб в Settings…). `chat.send()` прикладывает `{ page, path, details }` из роутера + стора.
- Сервер (`pageMode`/`contextPrefix` в modules/chat) строит блок `[Контекст кокпита]` перед сообщением: страница,
  подсказка о её данных, детали. Явно указано: контекст задействовать только если просьба к нему относится.
- **Режим страницы «Агенты»** (чат без задачи): cwd = `agents/`, `--permission-mode acceptEdits` —
  «поправь этого агента» реально редактирует `<id>.md`. Остальные страницы — plan (только чтение).

### Вложения (фото) и диктовка

- **Вложения:** кнопка-скрепка, drag&drop на весь чат (оверлей «Отпусти, чтобы приложить»;
  dragenter/leave через счётчик — leave стреляет на каждом дочернем узле) или вставка
  картинки из буфера → сразу `POST /api/chat/upload`
  (multipart) → файл в `chats/attachments/<ts>-<имя>` (гитигнорится вместе с chats/). К сообщению
  клиент прикладывает `attachments: [{file, name}]`; сервер строит пути ТОЛЬКО внутри attachments/
  (защита от traversal/произвольного `--add-dir`), добавляет `--add-dir chats/attachments` и блок
  `[Вложения]` со списком путей — агент смотрит их инструментом Read (vision работает в plan-mode).
  Сообщение без текста, но с вложением — валидно. Превью в истории — `GET /api/chat/attachment/:file`.
- **Диктовка:** кнопка-микрофон (SVG; запись — красный пульс + квадрат-стоп, расшифровка —
  только спиннер на кнопке, без текстов) — MediaRecorder (webm/opus) → `POST /api/chat/transcribe` →
  синхронно ffmpeg→wav→faster-whisper (переиспользует `ingestRecording` из lib/media, модель medium,
  ~14с на 8с речи вкл. загрузку модели) → текст дописывается в поле ввода (не отправляется сам).
  **Грабля:** getUserMedia требует secure context — по http://<tailscale-ip> микрофон недоступен
  (кнопка покажет подсказку); работает на localhost или через https.

## База агентов (modules/agents) — стадии конвейера

- `agents/<id>.md` в корне проекта (самогитигнор): frontmatter (kind/label/sub/key/model/timeout/budget/readonly/optional) + тело-промпт. Формат плоский key: value — парсер свой (`store.js`), не YAML-библиотека.
- CRUD: `GET/POST /api/agents`, `GET/PUT/DELETE /api/agents/:id`, `POST /api/agents/reseed`.
- Пустая база один раз засевается из всех профилей фабрики. Reseed обновляет метаданные
  канонических стадий, сохраняет курируемые `prompt` и `effort`, кастомных агентов не трогает.
- UI: AgentsView (`/agents`) — список + редактор карточки; «Профи»-настройки за тумблером.

## Маршруты (modules/routes)

- **Маршрут — только опубликованный бандл v2** (`~/.factory/routes/<профиль>/`): ревизии
  адресуются хешем СОДЕРЖИМОГО, указатель `catalog/current.json` двигается CAS-ом.
  Редактируемого стора `routes/<профиль>/<id>.json` больше нет: он ничего не исполнял
  (движок читал `profile.sh` и `graph.json`), и вторая «схема» рядом с бандлом только
  путала, чью правку увидит прогон.
- Проекты: `GET/POST /api/profiles`. Проекты фабрики — по `profiles/*/graph.json`,
  заведённые в кокпите — реестром `prefs.projects` (там же их пути репозиториев).
- Каталог: `GET /api/routes/:profile/{current,revisions}`,
  `GET .../catalog/:hash`, `GET .../routes/:id/:hash[/graph]`,
  `PUT .../current` (откат, CAS), `POST .../publish` (`mode: validate|publish`).
- **Собирает бандл сам профиль** — `profiles/<проект>/routes/publish.mjs`; кокпит
  подставляет ровно два аргумента (`--base-dir`, `--expected-catalog-hash`) и показывает
  его JSON как есть. Нет скрипта — нет и кнопки: «дефолтного» проекта у кокпита нет.
- UI: RoutesView (`/routes`) — состав каталога, схема маршрута (тем же `buildV2RouteDef`,
  что рисует «Конвейер» живой задачи), кнопки «Проверить»/«Опубликовать», список ревизий
  с откатом. Редактора схемы здесь нет намеренно: попытка закрепляет хеш, и правка «на лету»
  означала бы, что задача идёт по одному, а показывается другое.

## Исполнители и модели (modules/providers + lib/executors + lib/models-registry)

- **Подключение нового ИИ — модульное:** один файл в `server/src/lib/executors/` (контракт в
  `executors/index.js`: id/name/color/probe/auth/efforts/seedModels/catalog/run). Папка сканируется при
  старте — ядро (providers, chat) про вендоров не знает. Сейчас: `claude.js`, `codex.js` (GPT).
- `GET /api/providers` — `{ id, name, vendor, bin, color, version, auth, authLabel, available, installed, models[], modes[], settings[] }`.
  Кэш 60с, `?refresh=1`. Топбар рисует иконки (серый = недоступен), настройки → вкладка «Исполнители».
- **Вкладка «Исполнители» — плашка на каждого ИИ, плашки горизонтальным рядом** (grid
  `minmax(340px, 1fr)`, таб шире остальных: `.settings.wide`). В плашке — факты про CLI
  (авторизация, версия, каталог, обновление) и блок **своих настроек исполнителя**; общее
  для всех («показывать все модели», «Перепроверить», доверенные каталоги) — карточками ниже.
- **Свои настройки исполнителя объявляет сам executor** — поле `settings`:
  `[{ id, kind, label, hint?, value, disabled?, note? }]`. Схема приходит от исполнителя,
  выбор человека лежит в prefs (`providerSettings`), склейка — `lib/provider-settings.js`;
  сохранение — `POST /api/providers/:id/settings` (`{ settingId, value }`). Ядро про смысл
  ключа не знает: принимает ТОЛЬКО объявленный id и приводит значение к типу `kind`, поэтому
  чужой ключ в prefs не попадёт. Фронт рисует по `kind` (`stores/providers.saveSetting`,
  оптимистично с откатом).
- **`claude.fastMode` («Ускоренный вывод»)** — объявлен, переключается и хранится; каждый
  headless-запуск получает явное значение через `--settings {"fastMode":…}`. Список моделей
  здесь не дублируется: фактическую доступность, политику организации и списание usage credits
  проверяет установленный Claude CLI.
- **Список моделей Claude — ИЗ БИНАРЯ УСТАНОВЛЕННОГО CLI** (`executors/_claude-catalog.js`):
  бинарь сканируется потоком по regex `claude-(opus|sonnet|haiku|fable)-N(-M)?(\[1m\])?`, имя выводится
  из id («claude-opus-4-8» → «Opus 4.8», `[1m]` → «(1M)», context 1 000 000), tier — из семейства и версии.
  Почему так: захардкоженная подпись версии протухает молча. В историческом инциденте реестр
  показывал «Opus 4.8», а установленный CLI резолвил `opus` в другую версию; бинарь знает
  локально поддерживаемые id и не требует ключей или сети.
  Скан ~0.3 с на 230 МБ, гоняется только при смене версии CLI (`_meta[prov].catalogVersion`) и по `?refresh=1`.
- **Список моделей Codex — ИЗ ОФИЦИАЛЬНОГО APP-SERVER** (`model/list`, `includeHidden:true`):
  это модели, доступные именно установленному CLI и текущему ChatGPT-аккаунту, вместе с
  display name, поддерживаемыми effort, default, hidden и рекомендацией `upgrade`. Вызов
  read-only: thread/turn и обращение к модели не создаются, `OPENAI_API_KEY` не нужен.
  Каталог живой (`catalogLive`): сервер перечитывает его при обновлении минутного кэша,
  а открытый UI раз в минуту перечитывает `/api/providers`. Новый rollout появляется без
  релиза Cockpit; кнопка «Перепроверить» делает это немедленно.
- **В кратком списке Claude — только свежая версия каждого семейства** (`KEEP_VERSIONS = 1`): бинарь
  помнит много исторических id, и без фильтра селект превращается в свалку. Старые версии
  из каталога не выбрасываются, а помечаются `extra: true`. У Codex так помечаются `hidden`
  и модели, для которых сам app-server прислал замену `upgrade`;
  показывать ли их, решает настройка **«Показывать все модели»** (Настройки → Исполнители, prefs
  `showAllModels`, отдаётся вместе с `/api/providers`). Фильтрует фронт — переключение мгновенное,
  за списком на сервер не ходим. Выбранную модель не прячем никогда, иначе селект теряет значение.
  Вариант `[1m]` — не отдельная версия, а форма той же, и идёт вместе с ней.
- **Состав списка задаёт каталог**: чего в нём нет, из реестра уходит (иначе он копит всё, что когда-либо
  видел любой CLI). Переживают пересборку только записи с `custom: true` — ручные, у них же сохраняются
  правки имени/окна/эффортов.
- **Алиасы CLI отдельными пунктами НЕ показываются.** `opus`/`sonnet`/`haiku`, а также
  rollout-алиасы Codex вроде `codex-auto-review` — та же модель под другим
  именем: два пункта на одно и то же путают. Алиас привязан к модели, в
  которую CLI его резолвит, полем `aliases: ['opus']` у самой свежей версии семейства. Сохранённый
  где-то выбор `opus` резолвится в неё и в UI (`providers.resolveModelId` — селект и отправка), и на
  сервере (`modelInfo` ищет и по `aliases`). После обновления бинаря тот же старый выбор сам станет
  Opus 5 — смысл алиаса сохранён, хардкода нет.
- **Модель нового чата не фиксируется при создании**: в сессии пусто = «по умолчанию», конкретный id
  берётся из реестра при показе и отправке (`providers.defaultModelId` — сильнейшая не-`extra` у
  доступного исполнителя). Фиксировать при создании нельзя: реестр к тому моменту может быть ещё не
  загружен (из-за этого новый чат открывался на алиасе `opus`).
- **`CATALOG_SCHEMA` в `_meta`** — версия ПРАВИЛ отбора. Меняется вместе с логикой каталога, иначе у
  работающих кокпитов останется список, собранный по старым правилам. Локальный Claude-каталог
  пересобирается по версии CLI и схеме, живой Codex-каталог — ещё и по минутному кэшу.
- **Эффорты обнаруживаются динамически:** Claude — парсингом `claude --help`, Codex — полем
  `supportedReasoningEfforts` каждой модели из `model/list`.
- **Обновление CLI — кнопкой в настройках → «Исполнители»** (`POST /api/providers/:id/update`,
  команда — свойство исполнителя `updateCmd`: `claude install latest`, `codex update`). После обновления
  сбрасываются оба кэша, каталог моделей перечитывается у обновлённого исполнителя.
- **Индикатор «вышла новая версия» — есть, автообновления НЕТ.** Сервер раз в 6 часов (и через 30 с
  после старта) спрашивает npm-реестр `registry.npmjs.org/<pkg>/latest` — оба CLI публикуются там под
  тем же номером, что и нативная сборка (`_npm-latest.js`, `executor.latestVersion()`). Результат живёт
  в памяти модуля providers и уезжает в `/api/providers` полями `latest`/`updateAvailable`/`checkedAt`;
  при изменении — SSE `providers-update` (окно подхватывает без F5) и сброс кэша реестра.
  Ручная проверка — `POST /api/providers/check-updates` (кнопка «Проверить обновления»).
  UI: жёлтая точка на иконке исполнителя в топбаре + строка в его тултипе, в настройках — «Доступно
  обновление: X» и подсвеченная кнопка «Обновить». Ставится только по нажатию.
- **Грабли проверки версий:** заголовок `Accept: application/vnd.npm.install-v1+json` на эндпоинте
  `/latest` даёт **406** (abbreviated-формат — только для полного документа пакета). Сеть на стенде
  флапает (VPN): один и тот же запрос то падает, то отвечает за 0.5 с — поэтому три попытки с паузой,
  а пустой ответ НЕ затирает прошлый результат (иначе индикатор гас бы сам по себе).
- **Новые модели Anthropic обнаруживаются сами** (`claude.js discoverModels` → `/v1/models`):
  вотермарк по `created_at` в `_meta` models.json — всё, что свежее и неизвестно, дописывается
  наверх списка (tier выше максимума). Авторизация: `ANTHROPIC_API_KEY` из окружения, либо
  OAuth-токен хостового CLI — ТОЛЬКО при явном опт-ине `COCKPIT_DISCOVER_WITH_CLI_TOKEN=1`
  (без него сервер в чужие креды не лезет). Для Codex общая Platform-ручка `/v1/models`
  намеренно не используется: она не отражает доступ конкретного ChatGPT/Codex-аккаунта.
- **Грабли:** стабильного алиаса `fable` в CLI нет — нужен полный id из локального каталога,
  тогда как `opus`/`sonnet`/`haiku` резолвятся алиасами. Хостовый CLI живёт своей жизнью
  и может отставать от расширения VS Code; именно хостовый бинарь запускает Cockpit.
  `execFile` без закрытия stdin вешает `claude -p` (ждёт ввода → 5-мин таймаут) —
  в executors всегда `child.stdin.end()`. Ожидание вопроса/разрешения управляется суточным
  `PERM_WAIT_MS`, а не прежними короткими таймаутами.
- Чат: селект — optgroup по исполнителям, недоступный ИИ виден, но options disabled. Сервер выбирает
  executor по модели (`providerOfModel`); GPT без бинаря → понятная ошибка «npm i -g @openai/codex && codex login».
- **Смена ИИ внутри чата** (Claude ↔ Codex): sessionId прежнего исполнителя несовместим — фронт
  сбрасывает контекст автоматически (история чата остаётся). Конфликтов между ИИ нет: каждый
  запуск — отдельный процесс, сессии в реестрах своих CLI. Это ручное переключение чата,
  не аварийный failover конвейера.
- Настройки → «Исполнители»: у недоступного показана команда установки (из `executor.install`);
  клик по ней открывает раздел «Терминал» с уже введённой командой (механизм —
  `sessionStorage['cockpit-term-insert']`, TerminalView печатает её в PTY при коннекте, Enter — за пользователем).
  Там же список доверенных каталогов и кнопка «Применить ко всем ИИ».
- Тултипы — единый компонент `shared/ui/HelpTip.vue` (слот-триггер): топбар (исполнители, IP,
  CPU/RAM, хост) и микрофон чата на нём; системные title там больше не используем.
  Проп `toggle` закрепляет всплывашку кликом (повторный клик, клик мимо или Esc — закрывают):
  так сделаны иконки исполнителей в топбаре. Раньше клик по иконке уносил в настройки, и на
  планшете (ховера нет) тап показывал полосы лимитов ровно до перехода на другую страницу —
  прочитать их было нельзя. В настройки теперь ведёт кнопка «Настройки исполнителей»
  внутри самой всплывашки.
- Codex: `codex exec --json` (JSONL), резюме `exec resume <thread_id>`, песочница
  `workspace-write` + сеть + дополнительные `--add-dir` (своей всплывашки разрешений у
  codex-exec нет). JSONL нормализуется в ленту в реальном времени; summary рассуждений
  виден, если его отдал сам CLI. Авторизация = наличие `~/.codex/auth.json`.
- **Не путать**: `/api/agents` — агенты-стадии (промпты), `/api/providers` — LLM-движки, которые их исполняют.

## Авторизация Claude

- Настройки НЕ управляют ключом (форма удалена вместе с `/api/settings/claude*`); чат работает от хостового CLI
  (`claude login`) либо от ключа в `server/.state/claude-auth.json`, если тот был задан раньше (`ClaudeAuthStore` жив).

### Стоп агента

- `POST /api/chat/stop {chatKey}` → `activeRuns.get(chatKey).ac.abort()` →
  дочерний процесс CLI получает сигнал остановки. Ход возвращается не ошибкой, а обычным
  ответом «⏹ Ход остановлен» с уже
  накопленной лентой шагов — в истории видно, что агент успел сделать до стопа (`err.stopped`
  в executor'е, отдельная ветка в catch модуля чата).
- Заодно снимаются висящие запросы разрешений этого чата (`pendingPerms` по `chatKey`): отвечать
  на них уже некому, иначе всплывашка осталась бы на экране после остановки.
- В UI кнопка отправки на время хода превращается в красный квадрат-«стоп» (`.send.stop`) —
  лечит и «агент ушёл не туда», и зависший ход.
- Claude и Codex сохраняют доступный session/thread id оборванного хода, поэтому следующий
  вопрос продолжает тот же разговор. У Codex накопленной ленты шагов нет: `exec --json`
  в текущем executor-е разбирается после завершения процесса.
- Kimi `0.31.1` после ACP `session/cancel` не resume-ится: живой smoke показал, что CLI принял
  следующий `session/prompt`, но не создал новый `llm.request` и завершил ход пусто. Поэтому stop
  и любой пустой post-prompt ход вращают binding в `sessionId: null`; автоматического повтора
  после принятого prompt нет, пользователь явно повторяет сообщение уже в новой session.

### Панель чата — строка состояния, а не форма

Селекты задачи/модели и слайдер эффорта — без своих коробок: подпись-метка (`задача`, `модель`,
`эффорт`), значение, шеврон; между блоками тонкая вертикальная линия. Раскрытому `<select>` всё
равно нужен непрозрачный фон (`option { background: var(--surface) }`), иначе на тёмной теме
системный список нечитаем. На полной странице задача растёт вместе со свободным местом до `620px`,
а полное название показывает общий `HelpTip`; в узкой плавающей панели задача занимает отдельный
первый ряд, поэтому модель, усилие и кольцо контекста не разъезжаются.

Диалог вопроса — строки на всю ширину (отметка · название · пояснение агента справа), а не чипы:
видно, чем варианты отличаются, и попасть мышью проще.
