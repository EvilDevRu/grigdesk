# План единого паспорта проекта и репозиториев

Статус: **план; реализация не начата**

Дата: **2026-08-01**

## 1. Цель

Сделать проект самостоятельной и понятной сущностью Cockpit:

- проект всегда владеет списком своих репозиториев и путей к ним на машине-мозге;
- `be`, `fe`, `app` и другие части системы являются репозиториями одного проекта, а не
  отдельными проектами;
- профиль фабрики является необязательной настройкой автоматизации и не хранит второй экземпляр
  тех же путей;
- новый проект можно полностью завести из интерфейса, даже если профиля фабрики для него нет;
- существующие профильные проекты, включая `arsenkin`, переезжают без потери путей и без
  одновременной записи в два источника правды.

Первый рабочий релиз должен позволять создать проект, сразу добавить один или несколько
репозиториев, позже изменить их и отдельно видеть, подключён ли к проекту профиль фабрики.

## 2. Проблема сейчас

В текущей реализации смешаны три разных понятия:

1. `server/src/lib/profiles.js` считает проектами объединение каталогов
   `profiles/<id>/graph.json` и записей `prefs.projects`.
2. У проекта с профилем пути читаются из `PROFILE_TRIAGE_REPOS` в `profile.sh` и недоступны для
   редактирования в Cockpit.
3. У проекта без профиля те же пути хранятся в `server/.state/prefs.json` и редактируются на
   странице «Проекты».

Из-за этого одинаковое действие зависит от происхождения проекта. В интерфейсе пользователь
видит проект, но должен знать, существует ли скрытый bash-профиль и какой из двух файлов является
источником правды. Дополнительный симптом смешения — `POST /api/profiles` создаёт не профиль
фабрики, а пустой проект в `prefs.projects`.

На примере `arsenkin` одна карточка проекта должна содержать два репозитория:

```text
arsenkin
  be  /home/evildev/Workspace/arsenkin/be/html
  fe  /home/evildev/Workspace/arsenkin/fe/app/var/www
```

Это не три проекта и не свойства профиля. Профиль `arsenkin` лишь добавляет к этому паспорту
возможность запускать проектные маршруты, поднимать стенды и применять проектные политики.

## 3. Целевая модель

### 3.1. Проект

Проект существует, если у него есть запись в локальном реестре `prefs.projects`. Минимальный
паспорт:

```json
{
  "projects": {
    "arsenkin": {
      "repos": [
        { "key": "be", "dir": "/home/evildev/Workspace/arsenkin/be/html" },
        { "key": "fe", "dir": "/home/evildev/Workspace/arsenkin/fe/app/var/www" }
      ]
    }
  }
}
```

Пути остаются локальными данными машины и не коммитятся. Производные признаки — наличие профиля,
доступность каталога, состояние Git и опубликованные маршруты — в паспорт не записываются, а
вычисляются при чтении.

`key` — короткая пользовательская метка, а не закрытый enum. Cockpit предлагает `be` и `fe` как
примеры, но поддерживает монорепозиторий `app`, мобильный клиент `ios`, инфраструктуру `infra` и
другие составы проекта.

### 3.2. Профиль

Профиль существует независимо, если установлен валидный каталог `profiles/<id>/`. На первом этапе
связь проекта с профилем остаётся детерминированной по одинаковому `id`; отдельное поле-ссылка не
нужно.

Состояния проекта в UI:

- **профиль подключён** — профиль с тем же `id` найден;
- **без профиля** — код проекта доступен, но фабричный запуск, которому нужен профиль, недоступен;
- **профиль требует внимания** — каталог найден, но обязательные файлы или конфигурация невалидны.

Профиль владеет только знаниями исполнения: hooks, стендами, prompt-контекстом, политиками,
исполнителями и маршрутами. `PROFILE_TRIAGE_REPOS` после миграционного периода больше не является
рабочим источником путей.

### 3.3. Репозиторий

Запись репозитория содержит только стабильную метку и абсолютный путь к корню Git-репозитория.
API обзора дополняет её вычисляемыми полями:

```json
{
  "key": "be",
  "dir": "/home/evildev/Workspace/arsenkin/be/html",
  "exists": true,
  "git": true
}
```

Несуществующий путь разрешено сохранить: репозиторий могли ещё не клонировать. Интерфейс обязан
различать как минимум «доступен Git», «каталог существует, но это не Git» и «пути пока нет».

## 4. Целевой интерфейс

### 4.1. Создание проекта

Карточку «Новый проект» заменить явной формой или модальным мастером:

1. Поле **«Идентификатор проекта»** с примером `arsenkin`.
2. Блок **«Репозитории на этой машине»** с первой строкой:
   - **Метка** — `be`, `fe`, `app`;
   - **Абсолютный путь** — `/home/…/Workspace/project/repository`.
3. Кнопка **«Добавить репозиторий»** создаёт дополнительные строки.
4. Основное действие **«Создать проект»** одним запросом сохраняет и паспорт, и репозитории.
5. Вторичное действие **«Создать без репозиториев»** допустимо, но после него карточка получает
   заметное пустое состояние, а не выглядит законченной.

Рядом с путём нужно прямо написать, что это путь на сервере Cockpit, а не папка устройства, с
которого открыт браузер. Нативный browser directory picker использовать нельзя: при удалённом
доступе он выберет каталог телефона или ноутбука пользователя, а не машины-мозга.

После успешного создания проект остаётся на экране с заполненными репозиториями. Двухшаговая
последовательность «создать через `/api/profiles`, затем отдельным PUT записать пути» исчезает.

### 4.2. Карточка существующего проекта

В каждой карточке постоянно видны:

- идентификатор проекта;
- статус профиля: «Профиль подключён» или «Без профиля»;
- список репозиториев с метками, путями и состоянием Git;
- действие **«Изменить репозитории»** для любого проекта, в том числе профильного;
- действие **«Открыть код»**, когда есть хотя бы один доступный Git-репозиторий;
- опубликованные маршруты, если они существуют.

Для пустого проекта вместо малозаметной строки показывается основное действие
**«Добавить первый репозиторий»**. Термин «Пути…» не используется: он не объясняет, что внутри
нужно описать структуру проекта.

Редактор использует те же поля и правила, что мастер создания. Сохранение не должно затирать
другие будущие настройки паспорта проекта.

### 4.3. Профиль не обязателен

Проект без профиля не считается ошибкой. UI объясняет границу возможностей:

- просмотр кода и Git работает по репозиториям проекта;
- опубликованные маршруты можно показывать, если они существуют;
- запуск фабрики, требующий проектного профиля, недоступен с понятной причиной;
- создание полного профиля фабрики из UI не входит в первый релиз.

Автоматически создавать фиктивный `profiles/<id>/` при создании проекта нельзя: полноценный
профиль содержит исполняемые hooks и машинно-зависимую конфигурацию, которые нельзя честно
сгенерировать из одного имени.

## 5. Серверный контракт

### 5.1. Канонические API проектов

Использовать `/api/projects` как единственную пользовательскую поверхность реестра:

```text
GET  /api/projects
POST /api/projects
PUT  /api/projects/:id
```

`POST /api/projects` принимает проект целиком:

```json
{
  "id": "my-project",
  "repos": [
    { "key": "be", "dir": "/srv/my-project/backend" },
    { "key": "fe", "dir": "/srv/my-project/frontend" }
  ]
}
```

`PUT /api/projects/:id` обновляет список репозиториев, сохраняя остальные поля существующей
записи. Для профильного проекта запрет `409 factory_project` удаляется: наличие профиля больше не
меняет владельца данных.

Валидация остаётся серверной:

- `id` и `key` соответствуют действующим безопасным регулярным выражениям;
- ключи уникальны внутри проекта;
- путь абсолютный и нормализованный;
- отсутствующий путь сохраняется, но отражается предупреждением в обзоре;
- повторное создание возвращает `409`, неизвестный проект при изменении — `404`.

`GET /api/projects` возвращает проекты из реестра и отдельно вычисленные данные:

```json
{
  "id": "arsenkin",
  "profile": { "present": true, "valid": true },
  "repos": [],
  "routes": []
}
```

Технический boolean `factory` заменить структурированным состоянием `profile`, чтобы клиенту не
приходилось угадывать, означает ли `factory: false` отсутствие профиля, ошибку профиля или другой
тип проекта.

### 5.2. Устранение ложного API профилей

Все селекторы проектов (`RoutesView`, `ProjectSwitcher` и следующие потребители) переводятся на
`GET /api/projects`. Создание проекта переводится на `POST /api/projects`.

Старые `GET/POST /api/profiles` на один переходный релиз могут остаться совместимыми alias с
предупреждением в серверном логе. После миграции всех внутренних клиентов:

- `GET /api/profiles` должен означать только реально установленные профили;
- `POST /api/profiles` не должен создавать проект;
- создание профиля из браузера не добавляется, пока не определён отдельный безопасный контракт
  генерации и проверки полного профиля.

Параметр `profile` во внутренних контрактах engine и immutable route v2 не переименовывается в
рамках этой работы: это отдельный исполняемый контракт, а не пользовательский реестр проектов.

### 5.3. Единое чтение путей

`server/src/lib/projects.js` становится единственным модулем чтения репозиториев. Функция
`projectRepos()` всегда читает `prefs.projects[id].repos`; ветвления по наличию фабричного профиля
и cache чтения bash-профиля удаляются.

Все потребители переводятся на этот источник:

- плагин «Код»;
- обновление Git перед триажем и фабричным запуском;
- построение prompt-контекста анализа;
- вычисление затронутых репозиториев и протухания анализа;
- любые следующие плагины, которым нужны корни проекта.

`loadTriageProfile()` продолжает читать `PROFILE_CTX`, каталоги агента и маркеры риска, но рабочий
код перестаёт брать из него `repos`. После завершения совместимого периода чтение
`PROFILE_TRIAGE_REPOS` из этой функции удаляется.

## 6. Миграция существующих проектов

Миграция выполняется идемпотентно при запуске сервера до регистрации API-потребителей.

Для каждого найденного фабричного профиля:

1. Если записи `prefs.projects[id]` нет, прочитать legacy `PROFILE_TRIAGE_REPOS` и создать паспорт
   с этими репозиториями.
2. Если профиль прочитать не удалось или переменная пуста, создать пустой паспорт и записать
   диагностическое предупреждение; проект не должен исчезнуть из UI.
3. Если запись проекта уже существует, никогда не перезаписывать её автоматически, даже если
   значения в профиле отличаются.
4. Конфликт показывать в диагностике миграции и, при необходимости, дать явное одноразовое
   действие **«Импортировать пути из профиля»** с предпросмотром замены.
5. Запись выполнять через существующий атомарный `PrefsStore`; повторный запуск не меняет уже
   созданные паспорта.

Для `arsenkin` ожидаемый результат миграции — одна запись проекта с ключами `be` и `fe` и теми же
абсолютными путями, которые до миграции находились в `PROFILE_TRIAGE_REPOS`.

На переходный релиз переменная в `profile.sh` остаётся как резерв для импорта и отката, но рядом
добавляется комментарий о deprecated-статусе. Удалять её из профилей можно только после того, как:

- все профили импортированы;
- серверные потребители больше её не читают;
- тесты подтверждают работу триажа и pre-run Git refresh из паспорта проекта;
- резервная копия локального `prefs.json` проверена.

## 7. План реализации

### Этап 1. Зафиксировать модель и миграцию

1. Добавить чистую нормализацию паспорта проекта и списка репозиториев.
2. Добавить идемпотентный импорт фабричных профилей в `prefs.projects` при старте.
3. Изменить `listProjects()` так, чтобы после bootstrap-миграции реестром проектов были только
   паспорта, а `listFactoryProfiles()` отвечал только за наличие профиля.
4. Сохранить диагностируемый статус профиля как вычисляемое поле, не записывая его в prefs.
5. Покрыть правила отсутствия, конфликта и повторного запуска миграции тестами.

### Этап 2. Сделать API проектов каноническим

1. Перенести создание проекта с `POST /api/profiles` на `POST /api/projects` и принимать
   репозитории в том же запросе.
2. Разрешить `PUT /api/projects/:id` для проектов с профилем.
3. При обновлении менять только `repos`, не заменяя весь объект проекта.
4. Добавить вычисление состояний `exists` и `git` без отказа всего списка из-за одного плохого
   пути.
5. Оставить временный alias старых endpoints и пометить обращения к нему в логах.

### Этап 3. Перевести потребителей на паспорт

1. Удалить чтение профильных путей из `projectRepos()`.
2. Передать репозитории паспорта в analyzer вместо `loadTriageProfile().repos`.
3. Перевести pre-run Git refresh в `modules/factory` на `projectRepos()`.
4. Проверить плагин «Код», анализ задачи, обновление Git и определение затронутых файлов для
   проекта без профиля и проекта с профилем.
5. Убедиться, что исполняемые `profile_v2_*` и `profile_source_roots()` не были случайно смешаны с
   паспортом: это динамические пути worktree и стендов, они остаются в профиле.

### Этап 4. Переделать страницу «Проекты»

1. Объединить создание имени и репозиториев в одну форму.
2. Переименовать «Пути…» в «Изменить репозитории» и добавить заметный CTA пустому проекту.
3. Разрешить тот же редактор для профильных проектов.
4. Показывать отдельный статус профиля и отдельное состояние каждого репозитория.
5. Перевести `RoutesView` и `ProjectSwitcher` с `/api/profiles` на `/api/projects`.
6. После создания выбирать проект общим ключом `cockpit-project`, чтобы переходы в «Код» и
   «Маршруты» открывали нужный контекст.

### Этап 5. Удалить совместимость

1. Поискать обращения к `/api/profiles` и `PROFILE_TRIAGE_REPOS` во всём репозитории и локальных
   профилях.
2. Удалить alias создания проекта через `/api/profiles`, когда внутренних клиентов не осталось.
3. Удалить runtime-чтение `PROFILE_TRIAGE_REPOS`; оставить понятную ошибку миграции для старого
   профиля без паспорта.
4. Обновить `README.md`, `docs/cockpit/architecture.md`, `docs/cockpit/chat-agents.md`,
   `docs/engine/NEW-PROJECT.md` и `docs/engine/PROFILE-CONTRACT.md`.

## 8. Проверка

### 8.1. Серверные тесты

Добавить или обновить тесты для следующих случаев:

- новый проект с `be` и `fe` создаётся одним запросом без профиля;
- проект без репозиториев остаётся видимым после перезапуска;
- репозитории проекта с профилем редактируются через тот же API;
- повторяющийся ключ, относительный путь и плохой `id` отклоняются;
- отсутствующий путь сохраняется и возвращается со статусом `exists: false`;
- существующий не-Git каталог отличается от Git-репозитория;
- изменение `repos` сохраняет остальные поля паспорта;
- первый запуск импортирует `PROFILE_TRIAGE_REPOS`, второй запуск ничего не меняет;
- существующий паспорт имеет приоритет при конфликте с legacy-профилем;
- невалидный профиль создаёт видимый пустой паспорт и диагностическое предупреждение;
- analyzer и factory refresh получают пути из паспорта, а не из bash-профиля;
- плагин «Код» продолжает запрещать путь вне `git worktree list` выбранного репозитория.

### 8.2. Компонентные тесты

Для `ProjectsView.vue` проверить:

- создание проекта с одной и несколькими строками репозиториев;
- явное создание без репозиториев;
- ошибки API остаются в форме и не теряют введённые значения;
- пустой проект показывает «Добавить первый репозиторий»;
- профильный проект показывает статус профиля, но редактор не блокируется;
- состояния Git, не-Git и отсутствующего пути имеют разные подписи и доступны не только цветом;
- «Открыть код» выбирает нужный проект и не показывается при отсутствии доступного Git;
- длинные пути не ломают карточку и полностью доступны в `title`.

### 8.3. Команды

После реализации выполнить минимум:

```bash
npm --prefix server test
npm --prefix web test
npm --prefix web run build
```

Дополнительно прогнать адресные server/integration-тесты анализа и pre-run refresh, потому что
ошибка источника путей способна открыть интерфейс правильно, но отправить фабрику не в тот
репозиторий.

## 9. Ручная матрица приёмки

| Сценарий | Ожидаемый результат |
|---|---|
| Новый проект без профиля, два репозитория | Один проект создаётся одной формой; оба пути сразу видны |
| Новый проект без репозиториев | Проект остаётся видимым и явно просит добавить первый репозиторий |
| Существующий `arsenkin` после миграции | В карточке видны `be` и `fe`, профиль подключён, пути можно изменить |
| Путь ещё не существует | Проект сохраняется; рядом понятное предупреждение «пути пока нет» |
| Путь существует, но это не Git | Видно отдельное предупреждение; кнопка «Открыть код» для него недоступна |
| Профиль добавлен к существующему проекту позже | После обновления статус меняется на «Профиль подключён», пути не переписываются |
| Профиль удалён | Проект и репозитории остаются; фабричный запуск объясняет отсутствие профиля |
| Старый клиент вызывает `/api/profiles` | В переходный период запрос работает и оставляет предупреждение в логе |
| Перезапуск после миграции | В `prefs.projects` нет дублей и пути не меняются |

## 10. Критерии приёмки

- Из интерфейса можно одним сценарием создать проект и описать его `be`, `fe` или произвольные
  репозитории.
- Проект без профиля является штатным состоянием и не исчезает из общих селекторов.
- Наличие профиля не блокирует редактирование репозиториев.
- Для каждого проекта существует ровно один рабочий источник путей — `prefs.projects[id].repos`.
- `PROFILE_TRIAGE_REPOS` не читается рабочими потоками после завершения миграции.
- `POST /api/profiles` больше не маскируется под создание проекта после переходного периода.
- Код, триаж и обновление Git используют один и тот же паспорт проекта.
- Миграция `arsenkin` и остальных установленных профилей идемпотентна и не перезаписывает уже
  настроенные вручную проекты.
- Ошибки пути видны текстом, а не только красной или зелёной точкой.
- Документация последовательно различает проект, репозиторий, профиль и маршрут.

## 11. Не входит в первый релиз

- генерация полного фабричного профиля из браузера;
- редактирование `profile.sh`, hooks, секретов и runner policy на странице «Проекты»;
- перенос динамических worktree-путей и sandbox hooks из профиля в паспорт;
- клонирование Git-репозиториев и ввод Git credentials;
- нативный выбор локальной папки браузера;
- произвольное связывание проекта с профилем другого `id`;
- удаление проекта и политика каскадного удаления маршрутов, истории или задач;
- переименование route v2 и engine-параметров `profile`, не относящихся к реестру Cockpit.

## 12. Порядок выкладки и откат

1. Сначала добавить новый реестр/миграцию и чтение с совместимостью, не меняя UI.
2. Затем перевести серверных потребителей и убедиться, что `arsenkin` проходит триаж и Git refresh
   по импортированным путям.
3. После этого выкатить новый интерфейс и новые endpoints проектов.
4. Совместимость `/api/profiles` и legacy-переменной удалить отдельным изменением после проверки
   журналов обращений.

Откат до конца переходного периода безопасен: legacy `PROFILE_TRIAGE_REPOS` остаётся на месте, а
новый паспорт записан в локальный атомарный `prefs.json`. Миграция не удаляет и не переписывает
профили. Перед первым запуском миграции установщик или оператор должен сохранить резервную копию
`server/.state/prefs.json` с правами, не раскрывающими локальные пути и прочие настройки машины.
