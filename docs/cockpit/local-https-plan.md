## Зачем

Без HTTPS **PWA не существует** ни на планшете, ни на рабочем компе: `navigator.serviceWorker`
доступен только в secure context, исключение сделано лишь для `localhost`. Замер по
`http://<адрес в локальной сети>:8140` дал `'serviceWorker' in navigator === false` — нет ни
установки, ни precache, ни баннера обновления, ни микрофона (`gotchas.md` → «Service Worker
требует secure context»). Значит для окон нужен TLS, и в домашней сети его надо получить без VPS.

Режимов доступа два, и они **не независимы** — это выяснилось при разборе:

| Режим | Как получаем TLS | Состояние |
|---|---|---|
| **Локальная сеть** | свой CA + лист на LAN-адрес, слушает сам Fastify | делаем сейчас |
| **Через шлюз (снаружи)** | Caddy на VPS + два обратных SSH-туннеля | отложено, скрипты есть (`deploy/gateway/`) |

Режимы **уживаются** — но только потому, что http-слушатель на loopback никуда не девается
(этап 0). Шлюз ходит в кокпит по http на `127.0.0.1:8140`
(`deploy/gateway/bootstrap.sh:232,239`) и продолжит ходить туда же; TLS он терминирует сам,
и наш самоподписанный корень ему не нужен.

## Этап 0. Два слушателя: http на loopback, https в сеть

Порт 8140 — это не только UI, это **внутренняя шина**. По нему ходят:

| Кто | Где | Что было бы при «только https» |
|---|---|---|
| **MCP разрешений чата** | `modules/chat/index.js:380` задаёт `COCKPIT_PERM_URL: http://127.0.0.1:8140/api/chat/permission-request`, ходит `lib/chat/permission-mcp.js:12,58` | fetch не проходит → MCP возвращает свой дефолт `deny` → **каждое действие агента в чате автоматически отклоняется**, всплывашка не появляется. Мало `https://`: Node не доверяет своему CA, нужен ещё `NODE_EXTRA_CA_CERTS` в env дочернего процесса |
| **`bin/b24`** | `bin/b24:15` — `BASE="${COCKPIT_URL:-http://localhost:8140}"`, дальше `curl -sf` | отваливается **молча**; задет не только CLI — этап SHIP фабрики постит комментарий в задачу через него (`profiles/arsenkin/profile.sh:667`) |
| **`bin/restart`** | `bin/restart:43` — `curl -sf "http://localhost:$PORT/api/auth/state"` | говорит «сервер не поднялся за 10с», хотя сервер поднят; тот же путь у кнопки в UI при ручном запуске (`modules/system/index.js:32-35`) |
| **Vite dev** | `web/vite.config.js:50-53` — четыре прокси на `http://localhost:8140` | `npm run dev` мёртв |
| **Шлюз** | `deploy/gateway/bootstrap.sh:239` `reverse_proxy 127.0.0.1:$PORT_APP`, `:232` `ask http://127.0.0.1:$PORT_APP/...` | вход снаружи и выдача сертификатов стендам перестают работать; лечится `tls_insecure_skip_verify` — то есть шлюз начинает не проверять то, что мы только что включили |
| **Закладки и иконки PWA** | `deploy/install.sh:38,46`, `README.md:119` | запрос по http в TLS-сокет даёт `ERR_EMPTY_RESPONSE` — выглядит как «сервер умер» |

**Поэтому http-слушатель не выключается — он сужается.** В одном процессе живут два сокета:

| Сокет | Адрес | Кому |
|---|---|---|
| **http** | `127.0.0.1:8140` (и `::1`) — полный доступ | MCP чата, `bin/b24`, `bin/restart`, vite dev, шлюз, браузер на самом мозге |
| **http** | `<LAN>:8140` — **только** `GET /api/settings/tls/{ca.crt,ca.svg}`, всё остальное `301` на https | планшет: забрать корень и приехать на https, не набирая новый адрес |
| **https** | `0.0.0.0:8143` (`COCKPIT_TLS_PORT`) — полный доступ | планшет, рабочий комп, PWA |

Что это даёт, кроме нуля правок в шести местах из таблицы выше:

- **`localhost` — secure context сам по себе.** Браузер на мозге открывает `http://localhost:8140`,
  получает работающий service worker и PWA и **не требует установки корня в системе вообще**.
- **Старые закладки не ломаются**: `http://<LAN>:8140` отвечает редиректом на https, а не
  «пустым ответом». Фраза «редирект http→https невозможен, один порт — одна схема» из первой
  редакции больше не действует.
- **Корень скачивается по http, без экрана предупреждения** (решение 9): по https его пришлось бы
  тянуть через «Всё равно перейти» — то есть ровно через тот экран, который корень и убирает.
- **Естественный fail-open**: битый сертификат гасит только https-сокет, UI остаётся доступен
  с мозга, чинится кнопкой, а не с консоли (решение 6 упрощается).

Цена — примерно 40 строк в `app.js` (второй сервер + перенос upgrade-listeners + фильтр)
и один дополнительный открытый порт.

**Почему https на 8143, а не на 8140 (и наоборот).** Можно было отдать 8140 под https, а http
увести на 8141 — тогда на планшете не меняется порт. Но это правки в шести местах, включая
`bootstrap.sh` на VPS, и старый http-адрес в этом варианте просто мёртв. Выбран обратный порядок:
внутренние клиенты остаются на 8140 нетронутыми, а планшет доезжает на 8143 редиректом — то есть
адрес всё равно не набирают руками. 443-й не берём: порты ниже 1024 требуют root или
`CAP_NET_BIND_SERVICE`, а сервер ходит под обычным пользователем.

**http из сети не отдаёт ни байта данных** — только `301` и публичный корень. То есть «http
ограничен локалом» соблюдается по данным, а не только по букве.

## Ключевые решения и почему

### 1. Сертификат на IP-адрес, а НЕ на доменное имя

`viaGateway()` (`web/src/shared/sandbox.js:42-45`) переключает ссылки на стенды на схему шлюза
`https://p<порт>.<хост>` ровно по условию «протокол https И хост не литеральный адрес».
Дай кокпиту дома имя (`brain.local`) — и все ссылки на стенды поедут на поддомены `p5191.…`,
обслуживать которые дома некому.

С литеральным IP ветка остаётся `http://192.168.3.107:5191`, стенды открываются как сейчас,
DNS заводить не нужно. Переход по такой ссылке — top-level navigation, блокировка смешанного
контента на неё не распространяется (`gotchas.md` → «Адрес стенда»).

**Tailscale в этой схеме не участвует** (решено 2026-08-01). На Android он вытесняет используемый
VPN — активным может быть только одно VPN-приложение (`gotchas.md:302`), а дома он и не нужен.
Значит SAN — только LAN-адрес мозга, `127.0.0.1` и `localhost`; tailnet-адреса (`100.64/10`)
в сертификат не кладём.

### 2. Свой CA + лист, а не одиночный самоподписный сертификат

**При смене адреса перевыпускается только лист, на устройствах ничего переустанавливать не надо** —
они доверяют CA. Одиночный самоподписный пришлось бы разносить заново каждый раз.

Параметры, где ошибиться легко:

- **SAN обязателен, и смотрят только его** — CN браузеры игнорируют полностью;
- для адреса нужна запись типа `IP:192.168.3.107`, `DNS:192.168.3.107` не считается;
- в SAN сразу кладём `IP:127.0.0.1` и `DNS:localhost`. Внутренние клиенты остались на http
  (этап 0), так что критичным это больше не является, но стоит копейки и закрывает два случая:
  открыть `https://localhost:8143` на самом мозге и когда-нибудь перевести на https что-то
  внутреннее, не перевыпуская лист;
- **срок листа 397 дней** (лимит браузеров — 398). Продление не автоматизируем: раз в год человек
  жмёт «Перевыпустить» в настройках, устройства при этом не трогаются — они доверяют CA, а не
  листу. Чтобы это не свалилось внезапно, статус отдаёт `daysLeft`, а UI показывает баннер
  заранее (решение 8 и раздел «Риски»);
- `extendedKeyUsage=serverAuth`, `basicConstraints=CA:FALSE` у листа;
- `basicConstraints=critical,CA:TRUE,pathlen:0` + `keyUsage=critical,keyCertSign,cRLSign` у корня;
- ключи EC P-256, срок CA — 10 лет.

### 3. На корне — name constraints, ключ CA живёт вне репозитория

Корень, установленный на планшет, — самая опасная вещь во всём хозяйстве: его ключом подписывается
сертификат на **любой** домен, и планшет поверит. Поэтому две меры вместо одной надежды на `0600`:

- **`nameConstraints`** на корне — по всем приватным диапазонам сразу, а не по текущей подсети:
  `critical,permitted;IP:10.0.0.0/255.0.0.0,permitted;IP:172.16.0.0/255.240.0.0,permitted;IP:192.168.0.0/255.255.0.0,permitted;IP:127.0.0.1/255.255.255.255,permitted;DNS:localhost`.
  Украденный ключ тогда не подпишет `google.com` — радиус поражения сжимается до домашних адресов.
  Широкий список взят намеренно: смена роутера или провайдера не должна требовать перевыпуска
  **корня** (это обход всех устройств), а публичный интернет он всё равно исключает.
- **Ключ и сертификат CA — в `~/.config/cockpit/ca/` (`0700` на каталоге, `0600` на ключе),
  а не в `server/.state/`.** Причины конкретные: `server/.state` сейчас `drwxrwxr-x`; каталог
  лежит внутри репозитория, поэтому любой `tar` папки утащит ключ; и главное — плагин «Код»
  отдаёт по HTTP любой файл под деревом зарегистрированного репозитория
  (`server/src/modules/code/index.js`, `inside()` фильтрует только выход за корень), то есть
  `GET /api/code/<проект>/file?path=server/.state/tls/ca.key` вернул бы приватный ключ CA в JSON.
  Лист (`key.pem`/`cert.pem`) остаётся в `server/.state/tls/` — его компрометация лечится
  перевыпуском и никуда за пределы дома не распространяется.

Путь к CA — `COCKPIT_TLS_CA_DIR` с этим дефолтом, чтобы ничего не хардкодить.

### 4. Хранение листа — `server/.state/tls/`, `.env` из UI не трогаем

В `.env` лежат ключи API; переписывать его сервером ради тумблера не хочется. Вместо этого
`config.js` получает автоподхват: если `COCKPIT_TLS_KEY`/`COCKPIT_TLS_CERT` пусты, но в
`server/.state/tls/` лежит валидная пара и маркер говорит «включено» — берём их. Env остаётся
приоритетным override (шлюз, ручные случаи).

### 5. Состояние — явный маркер, а не имя файла

Первая редакция предлагала «выключено = переименовать в `*.disabled`». Так делать нельзя:

- переименование двух файлов не атомарно; обрыв посередине даёт «есть cert, нет key» →
  сервер **тихо стартует по http** → cookie уходит без `Secure` → пароль по локалке открытым
  текстом, а UI показывает «включено», потому что файлы на месте;
- `key.pem.disabled` — это приватный ключ, оставленный навсегда под именем, которое не попадает
  ни под один привычный шаблон в бэкапах и `find`.

Правильно: `server/.state/tls/state.json` (`{enabled, issuedAt, notAfter, san, caFingerprint}`),
пишется атомарно (tmp + `rename`). `disable()` — переключить флаг и **удалить** ключ листа
(CA остаётся, лист перевыпускается за секунду). Автоподхват срабатывает, только если маркер
`enabled` **и** пара успешно грузится в `tls.createSecureContext`.

### 6. Автоподхват обязан быть fail-open

`tlsOptions()` (`app.js:70-77`) ловит только ошибку `readFileSync`. Пустой или обрезанный файл
читается успешно, а падает уже `Fastify({ https })` (`app.js:81`) — вне try. `build()` вызывается
top-level await (`app.js:255`), процесс выходит, а в юните `Restart=always` и
`StartLimitIntervalSec=0` — то есть **вечный крэш-луп** (ровно сценарий «7553 падения», записанный
в комментарии юнита), причём вызванный кнопкой в браузере, а чинить его можно только с консоли
мозга: UI лежит.

Схема с двумя слушателями (этап 0) убирает у этого зубы сама: Fastify создаётся **без** `https`,
сертификат уходит в отдельный `https.createServer(...)`, и его падение http-сокета не касается.
Но страховки всё равно нужны, потому что «https молча не поднялся» — тоже плохой исход:

- пара проверяется через `tls.createSecureContext({key, cert})` **до** создания сервера — это ловит
  и битый PEM, и ключ не от этого сертификата;
- при ошибке: источник `.state` → громкий `log.error`, https-сокет не поднимается, http живёт
  (fail-open, чинится из UI с мозга); источник env → падаем как сейчас, это явное намерение
  оператора, тихо игнорировать его нельзя;
- `EADDRINUSE` на 8143 — тоже не повод убивать процесс: логируем и работаем по http;
- `status()` обязан отдавать причину, по которой https не поднялся, чтобы UI показал её текстом,
  а не «включено» при мёртвом сокете;
- запись новых файлов — во временный каталог, проверка, затем `rename`; маркер пишется последним.

### 7. Вход `addresses` валидируется allowlist-ом, openssl зовётся без шелла

`generate({ addresses })` кладёт данные из HTTP-тела в `subjectAltName`. Без валидации это:

- **инъекция в SAN** — `192.168.3.107,DNS:evil.com` даст лист, валидный для чужого домена
  под корнем, которому доверяет планшет (name constraints из решения 3 это гасят, но
  полагаться на один рубеж не стоит);
- **инъекция в `-extfile`** — перевод строки позволяет дописать `basicConstraints=CA:TRUE`
  и превратить «лист» во второй CA; конфиг openssl понимает ещё `$ENV::` и `.include`;
- **RCE**, если реализовать через `sh -c`.

Правила: только `execFile('openssl', [...])` (образец — `promisify(execFile)` в `server/src/lib/git.js:10`;
`modules/factory/index.js:615` с `execFile('sh', ['-c', …])` **не копировать**); каждый элемент
`addresses` через `net.isIP()`, в SAN уходит канонизированный результат, а не исходная строка;
отказ на публичные диапазоны (дома они не нужны и почти наверняка опечатка); лимит ~8 адресов;
типизированная ошибка 400 по образцу `isAllowedGatewayHost` (`modules/gateway/index.js:31-48`).
Плюс лок на генерацию — два параллельных запроса подерутся за `cert.pem` и `.srl`.

### 8. Тумблер показывает состояние, а не «включает»

TLS читается один раз при создании сервера (`app.js:80`), поэтому переключение вступает в силу
**только после перезапуска**. UI обязан писать это прямо и вести на таб «Сервер», иначе получится
классическое «нажал, ничего не изменилось».

«Нужен ли перезапуск» считается сравнением **отпечатка загруженного сертификата** с тем, что лежит
на диске, а не наличием файлов: перевыпуск в тот же путь тоже требует перезапуска. Для этого
`tlsEnabled` и отпечаток нужно пробросить в модуль настроек — сейчас `tlsEnabled` уходит ровно
в один плагин (`app.js:150`), а `settingsModule` (`app.js:240-242`) не получает ни его, ни `authStore`.

### 9. Корень ставим ДО перезапуска — тогда предупреждения не будет ни одного

Два слушателя меняют порядок к лучшему: `ca.crt` существует сразу после генерации, а http-сокет
на 8140 в этот момент ещё работает как раньше. Значит корень можно забрать **до** того, как
поднимется https, — по http, из уже открытого UI, без единого экрана «соединение не защищено»:

1. на планшете, по обычному `http://<адрес>:8140`, жмём «Сгенерировать сертификат»;
2. **там же** — «Скачать корень» и ставим его в системе (решение 10); при желании тем же QR
   его забирает второе устройство;
3. человек перезапускает сервер (кнопка в «Сервере» или `bin/restart`);
4. на планшете обновляем вкладку: `http://<адрес>:8140` отвечает `301` на `https://<адрес>:8143` —
   **адрес не набираем**, порт меняется сам. Корень уже стоит, поэтому открывается чисто:
   `isSecureContext`, service worker, установка PWA;
5. когда всё заработало — «Выйти на всех устройствах» и вход заново (решение 11).

Сессия при этом никуда не девается: cookie `cockpit_sid` host-only и **не разделяется ни по схеме,
ни по порту** (`plugins/auth.js:113-123`), так что пароль на шаге 4 не спросят. Ломать этот
переход автосбросом сессий нельзя — см. решение 11.

Остаточный риск честно: корень едет по http, и MITM в домашней сети может подсунуть свой. Это не
хуже прежнего варианта (там он ехал по https с непроверенным сертификатом, то есть тоже без
защиты), но и не лучше. Митигация та же — **SHA-256 отпечаток корня**
(`openssl x509 -fingerprint -sha256`) показываем в UI, открытом на мозге по `localhost`, и сверяем
с тем, что видно при установке на планшете. Кто хочет исключить риск полностью — переносит файл
с мозга напрямую.

### 10. «Установить на устройство» — файл + инструкция, не кнопка-автомат

Доверие корневому сертификату — решение уровня ОС, из браузера его не выполнить
(`gotchas.md` → «Доступ к кокпиту с других устройств — что уже отвергнуто»). Честный максимум:

- отдать корень файлом (`Content-Type: application/x-x509-ca-cert`,
  `Content-Disposition: attachment; filename="cockpit-ca.crt"` — Android-установщик смотрит на
  расширение);
- **QR прямо на этот файл**, и ведёт он на **http**-адрес (`http://<LAN>:8140/api/settings/tls/ca.crt`) —
  тот, который работает и до перезапуска, и после (этап 0, белый список). Нужен он не планшету,
  на котором открыт UI (там просто ссылка), а **второму устройству**, где кокпит ещё не открывали:
  рабочему компу, телефону. Рисуем на сервере: `qrcode` умеет `toString(url, { type: 'svg' })`
  строкой, без canvas и нативных зависимостей — единственная новая зависимость во всём плане;
- показать отпечаток (решение 9);
- пошаговая инструкция под платформу (Android 11+: файл сам ничего не предложит — Настройки →
  Безопасность → Шифрование и учётные данные → Установить сертификат → **Сертификат ЦС**, потребует
  PIN, останется постоянная плашка «сеть может отслеживаться»; iOS: установить профиль и
  **отдельно** включить полное доверие в «Об этом устройстве → Доверие сертификатам»).

**`ca.crt` отдаём без сессии, но только клиентам из приватных сетей.** Гард закрывает весь `/api`
(`plugins/auth.js:189`), и под ним QR перестаёт быть самодостаточным: устройство, где кокпит
ещё не открывали, получит 401 вместо файла. Сам корень — публичный сертификат, секрета в нём нет;
утекает только список внутренних адресов в SAN. Поэтому добавляем роут в `PUBLIC_API` **точной
строкой** (гард сравнивает `routeOptions.url`, не сырой URL — `plugins/auth.js:185`) и внутри
хендлера проверяем `request.ip`: приватный диапазон или loopback — отдаём файл, иначе 401. Образец
такой проверки в проекте уже есть — `isLocalRequest` (`plugins/auth.js:75`) и `isAllowedGatewayHost`
(`modules/gateway/index.js:31-48`). Наружу через шлюз корень таким образом не уходит.

Рубежа два, и они независимы: **фильтр http-слушателя** (этап 0) решает, что вообще доедет до
Fastify по http из сети, а **`PUBLIC_API` + проверка `request.ip`** — что отдастся без сессии.
Белый список надо держать одним списком в одном модуле и использовать в обоих местах, иначе они
разъедутся: добавили роут в `PUBLIC_API`, забыли в фильтре — по http из сети он молча
редиректится, и «почему QR не работает» ищется полдня.

### 11. Смена origin: что теряется и что надо погасить

`http://IP:8140` и `https://IP:8143` — разные origin, и `localStorage` с Cache Storage между ними
не переезжает (~15 ключей: `cockpit-project`, `cockpit-settings-tab`, `cockpit-sidebar`,
просмотренные задачи доски и т.д.). Потеря копеечная — настройки вида, не данные.

Чего **не** будет, вопреки первой редакции: осиротевшего service worker'а на старом origin.
На `http://IP:8140` он никогда и не регистрировался — это не secure context, с этого весь план
и начался. Чистить «Очистить данные сайта» там нечего.

Сессия, наоборот, **переживёт** — cookie не разделяются ни по схеме, ни по порту. Это
одновременно и удобство (на нём держится решение 9: планшет после перезапуска не вводит пароль),
и проблема: старая cookie выдана без `Secure`, а значит продолжает уходить в том числе на стенды
`http://IP:5191`, где крутится код проверяемого PR.

Поэтому сессии **не сбрасываем автоматически** — ни при генерации, ни на первом старте с TLS:
автосброс выбил бы человека ровно в тот момент, когда он с планшета идёт за корнем, и вернул бы
ввод пароля по непроверенному соединению. Вместо этого UI после успешного включения показывает
подсказку: «когда всё заработает — нажми „Выйти на всех устройствах“ и войди заново, чтобы
не осталось cookie без `Secure`». Кнопка уже есть — `POST /api/auth/logout-all`
(`modules/auth/index.js:162` → `authStore.dropAllSessions()`, `lib/auth-store.js:210`).

### 12. Удалённый режим — пока индикатор, а не тумблер

Включить его из UI нечем: нужны sudo, ssh-ключи, systemd-юниты на двух машинах и сам VPS.
Показываем состояние (`COCKPIT_TRUST_PROXY` задан или нет, живы ли туннели) и что требуется
сделать. Пустой тумблер, который ничего не включает, хуже честной строки состояния.

Правки Caddyfile локальный TLS больше не требует (этап 0): туннель приходит на loopback, где
http как был, так и остался. Единственное, что стоит записать в тот же UI, — что снаружи
кокпит работает через сертификат Let's Encrypt на шлюзе, а домашний корень к этому отношения
не имеет и на устройства ради шлюза ставить его не нужно.

## Реализация

### Этап 1. Генерация и автоподхват (сервер)

`server/src/lib/tls-local.js` — новый модуль:

- `status()` — есть ли CA и лист, откуда взят активный сертификат (env / `.state` / нет), SAN,
  `notAfter` и `daysLeft`, отпечаток CA, список адресов машины, совпадает ли текущий адрес с SAN.
  Разбор сертификата — через встроенный `crypto.X509Certificate`, а не парсинг вывода `openssl`
  (`tests/run-all.sh` заявлен как офлайн-прогон, тянуть туда внешний бинарь для чтения незачем).
  Адреса машины: `os.networkInterfaces()`, **фильтр по имени интерфейса** (`docker*`, `br-*`,
  `veth*`) — поля `scope global` в Node нет, а по диапазону docker-мосты не отсечь: на этой машине
  живут `192.168.48.1` и `192.168.16.1` рядом с настоящим `192.168.3.107`.
- `generate({ addresses })` — валидация по решению 7; CA создаётся при отсутствии (с name
  constraints, решение 3); лист на 397 дней; запись через временный каталог + `rename`;
  `createSecureContext` перед установкой; маркер `state.json` последним; права `0600` на ключи,
  `0700` на каталоги, `0644` на `cert.pem`/`ca.crt`; лок на время работы.
- `caCertificate()` — содержимое корня и его отпечаток.
- `disable({ confirm })` — флаг в маркере + удаление ключа листа.
- Проверка наличия `openssl` — в `status()`, с понятным сообщением, а не `ENOENT` при клике.

`server/src/config.js` — автоподхват `server/.state/tls/{key,cert}.pem` при пустом env,
`COCKPIT_TLS_CA_DIR` с дефолтом `~/.config/cockpit/ca`, `COCKPIT_TLS_PORT` с дефолтом `8143`,
комментарий про приоритет env.

`server/src/app.js` — здесь вся правка этапа 0, и она аккуратная:

- `tlsOptions()` переписать по решению 6 (валидация пары, fail-open для `.state`, fail-closed
  для env), пробросить `tlsEnabled` и отпечаток дальше;
- **Fastify строится без `https`** — `fastify.server` остаётся http-сервером, `@fastify/websocket`
  вешает `onUpgrade` на него как раньше, терминал и SSE на loopback не трогаются вовсе;
- если TLS активен — поднимаем второй сокет: `https.createServer(tls, httpsHandler)`, где
  `httpsHandler` — тот же `fastify.routing`; upgrade переносим списком
  (`for (const l of fastify.server.listeners('upgrade')) httpsServer.on('upgrade', l)`) **после**
  `fastify.ready()`, иначе плагин ещё не зарегистрировал свой хендлер;
- у http-сервера подменяем request-обработчик на обёртку: loopback (`127.0.0.1`, `::1`,
  `::ffff:127.0.0.1` по `req.socket.remoteAddress` — не по заголовкам, их подделывают) → как было;
  путь в белом списке (`ca.crt`, `ca.svg`) → как было; иначе `301` на
  `https://<хост из Host без порта>:<COCKPIT_TLS_PORT><url>`. Фильтр включается **только когда
  https реально поднялся** — иначе редирект уводил бы в никуда и кокпит стал бы недоступен из сети;
- upgrade по http из сети — рвать сокет, а не редиректить: `wss://` браузер сам не подставит,
  а открытый `ws://` на LAN — это PTY-шелл в открытом виде;
- закрывать оба сервера в `onClose`, чтобы `bin/restart` не ловил `EADDRINUSE` на 8143.

Возможных альтернатив было две, обе отклонены: **мультиплексор по первому байту** (`0x16` = TLS)
на одном порту 8140 — красиво снаружи, но требует поднимать Fastify через `serverFactory` и
`ready()` вместо `listen()`, а upgrade-хендлер при этом висит на `net.Server`, который событие
`upgrade` не порождает; и **два независимых Fastify-инстанса** — у каждого своя шина SSE и свои
подписчики, события ушли бы половине клиентов.

**Никаких `192.168.3.107` и `wlp4s0` в коде, дефолтах и фикстурах** — адреса только из
`os.networkInterfaces()` и из тела запроса.

### Этап 2. Эндпоинты

В `server/src/modules/settings/index.js` (ему дополнительно нужен `tlsEnabled` — см. решение 8):

| Метод | Путь | Гард | Что делает |
|---|---|---|---|
| `GET` | `/api/settings/tls` | да | статус: поднялся ли https-сокет сейчас и на каком порту (а если нет — почему, решение 6), что лежит на диске, источник, SAN, `daysLeft`, отпечаток CA, адреса машины, нужен ли перезапуск |

### Этап 3. UI

`web/src/views/SettingsView.vue`, секция `tab === 'access'` — блок «HTTPS в локальной сети»:

- **два факта раздельно**: что реально слушает процесс сейчас (какие сокеты, на каких портах)
  и что лежит на диске (иначе «файлы есть» прочитается как «работает»); если https не поднялся —
  причина текстом, а не молчание;
- на какие адреса выписан, до какого числа, сколько дней осталось; предупреждение при
  `daysLeft < 30` и при несовпадении текущего LAN-адреса с SAN;
- кнопки «Сгенерировать» / «Перевыпустить» / «Выключить» (последняя — с подтверждением);
  при `source === 'env'` кнопки генерации **заблокированы** с пояснением: пути заданы в `.env`,
  и сгенерированное всё равно не подхватится;
- плашка «применится после перезапуска» со ссылкой на таб «Сервер»;
- блок «Установить на устройство»: кнопка «Скачать корень» (основной путь — то устройство, где
  UI уже открыт), **QR на тот же файл** для второго устройства, **отпечаток SHA-256**, инструкции
  Android/iOS/десктоп и порядок из решения 9 прямым текстом — с ударением на «поставь корень
  **до** перезапуска, тогда предупреждения не будет вовсе»;
- строка про адрес: после перезапуска кокпит в сети живёт на `https://<адрес>:8143`, старый
  `http://<адрес>:8140` сам туда перебросит, а на самом мозге остаётся `http://localhost:8140`
  (он secure context, PWA там работает без всякой установки корня);
- после успешного включения — подсказка «выйти на всех устройствах и войти заново» со ссылкой
  на кнопку в этом же табе (решение 11);
- ниже — «Доступ снаружи» строкой состояния (решение 12).

Стили: подраздел обязан повторить у себя `.card`/`.row`/`button`/`.msg`/`.primary` — они объявлены
в `SettingsView.vue` под `<style scoped>` и на дочерние компоненты не действуют
(`gotchas.md` → «Подразделы настроек не наследуют стили»).

## Ручные шаги человека (из UI не делаются)

1. **Резерв DHCP на роутере** для мозга: `192.168.3.107` на `wlp4s0` выдан динамически.
2. **Установка корня** на планшет и рабочий комп — разово на каждое устройство, **до перезапуска
   сервера** (решения 9 и 10): на устройстве с открытым UI кнопкой «Скачать корень», на остальных
   по QR.
3. **Перезапуск сервера** — кнопкой «Настройки → Сервер» или `bin/restart`. Агент из чата кокпита
   это сделать не может: он дочерний процесс этого же сервера.
4. **Корень в хранилища самого мозга — НЕ нужен.** Браузер на мозге ходит на
   `http://localhost:8140` (secure context, PWA работает), а `curl` из `bin/b24`/`bin/restart`,
   MCP разрешений и vite остаются на том же http-сокете. Ставить корень в систему нужно, только
   если хочется открывать на мозге именно `https://<LAN>:8143` — тогда
   `sudo cp ca.crt /usr/local/share/ca-certificates/cockpit-ca.crt && sudo update-ca-certificates`,
   а Chrome и Firefox на Linux смотрят каждый в свой NSS-store
   (`certutil -d sql:$HOME/.pki/nssdb -A -t "C,," -n cockpit-ca -i ca.crt`).
5. **На каждом устройстве после переключения** — снести старую иконку PWA (она ведёт на http-origin).
   Чистить данные сайта не нужно: service worker'а на http-origin никогда не было (решение 11),
   теряются только настройки вида в `localStorage`.
6. **Когда всё заработает** — «Выйти на всех устройствах» и вход заново (решение 11).

## Риски

- **Ключ CA.** Даже с name constraints он остаётся самым чувствительным файлом хозяйства и живёт
  под тем же пользователем, что чат-агенты и PTY-терминал. Меры — решение 3; отзыва нет
  (CRL/OCSP тут не будет), процедура при подозрении одна: удалить корень с устройств и выпустить
  новый.
- **Истечение листа.** Через ~13 месяцев всё встанет одномоментно, и на установленной PWA это
  выглядит необъяснимо (оболочка из кэша есть, запросы падают). Лечение — кнопка «Перевыпустить»
  (устройства не трогаем), а чтобы до неё дошли руки вовремя: `daysLeft` в статусе, баннер
  в «Доступе» при остатке < 30 дней и `log.warn` на старте. Срок CA — 10 лет, но его перевыпуск
  означает обход всех устройств, поэтому про него предупреждать надо заранее и отдельно.
- **Скачивание корня по http (гипотеза, проверять живьём).** Chrome помечает «небезопасные
  загрузки» и в части случаев блокирует их; прямой переход по http-ссылке на файл обычно проходит,
  но предупредить может. Если упрёмся — запасной путь тот же, что и всегда: скачать `ca.crt`
  на мозге и перенести файлом.
- **Второй порт в жизненном цикле.** `bin/restart` ждёт освобождения только 8140
  (`bin/restart:17,22-28`). Процесс один и оба сокета закрываются вместе, поэтому в норме проблемы
  нет, но при зависшем закрытии новый старт упадёт с `EADDRINUSE` на 8143 — а сообщение будет
  про порт, которого скрипт даже не проверял. Митигация: закрывать оба сервера в `onClose`
  и добавить 8143 в ожидание в `bin/restart`.
- **Порт 8143 открыт в сеть.** Это тот же кокпит с тем же гардом, что и раньше на 8140, так что
  новой поверхности атаки не появляется. Но если на мозге когда-нибудь появится фаервол, правило
  придётся заводить на два порта, а не на один.
- **WebAPK (гипотеза, кодом не проверяется).** Для полноценной установки Chrome отдаёт манифест
  серверу-минтеру Google, который до адреса в приватной сети не достучится — установка может
  выродиться в обычный ярлык (`gotchas.md:194-196` отдельно оговаривает, что это не то же самое).
  Проверять живьём; `usePwaStore.canInstall` подтверждает только `beforeinstallprompt`.

## Решено (вопросы закрыты 2026-08-01)

- **Слушателей два: http и https одновременно** (этап 0). http на loopback — полный доступ,
  http из сети — только корень и редирект, https — для устройств. Это отменяет весь объём правок
  внутренних клиентов, делает fail-open естественным, сохраняет старые закладки и снимает
  требование ставить корень на самом мозге.
- **Срок листа — год (397 дней).** Проверять гипотезу, что для локально установленных корней
  лимит 398 дней не действует, не стали: год устраивает, а продление стоит одного клика
  «Перевыпустить».
- **Tailscale — нет.** Ни в SAN, ни в name constraints; см. решение 1.
- **QR — делаем**, зависимость `qrcode` на сервере оправдана: без неё установка корня на планшет
  упирается в ручной ввод адреса, а перенос файла с мозга неудобен. Вместе с QR `ca.crt` уходит
  из-под гарда для клиентов из приватных сетей (решение 10) — иначе QR бессмыслен.
- **Автосброса сессий не будет.** Он ломал бы главный сценарий; вместо него подсказка и
  существующая кнопка «Выйти на всех устройствах» (решение 11).

## Порядок работ

1. Этап 1 (генерация, автоподхват) + **этап 0** (второй сокет и фильтр) — они правятся в одном
   файле и одним заходом; сразу тесты, включая негативы, «поднимается по http при битом
   сертификате» и таблицу фильтра.
2. Этап 2 → 3. Этап 3 → 4. Этап 4.
5. Человек, по шагам решения 9: резерв DHCP → «Сгенерировать» с планшета → **там же скачать и
   поставить корень** → перезапуск сервера → обновить вкладку (редирект на `:8143`, без
   предупреждения) → «Выйти на всех устройствах» и вход заново.
6. Приёмка на планшете: `https://192.168.3.107:8143` открывается **без предупреждения**;
   `isSecureContext === true`, `'serviceWorker' in navigator === true`, появляется кнопка установки;
   после установки — проверить глазами, что это WebAPK (своя иконка, нет адресной строки),
   а не ярлык (риск выше). Отдельно: `http://192.168.3.107:8140` перебрасывает на https,
   а `http://192.168.3.107:8140/api/tasks` из сети данных **не отдаёт**.
7. Проверка, что не сломалось (всё — на неизменённом http-сокете, поэтому должно быть «как было»):
   всплывашка разрешений в чате появляется; `b24 comment` доходит; `bin/restart` не врёт;
   `npm run dev` во фронте живёт; ссылка на стенд открывается; терминал на мозге работает.
