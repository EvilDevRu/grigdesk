Документ рассчитан на последовательное исполнение. Выполняй один этап за раз:
сначала соответствующие проверки, затем небольшая правка, затем повторная проверка.
Не заменяй весь store и не объединяй несколько этапов в большой рефакторинг.

## Результат, который нужно получить

Во время ответа агента пользователь может печатать, прокручивать сообщения и
переключать чаты без повторяющихся пауз от обработки прошлых ходов. Список сохраняет
обычный порядок: ожидающие человека сверху, затем по времени активности.

Четыре источника затрат устраняются отдельно:

1. Служебное сравнение не сериализует тела старых шагов инструментов.
2. Перестановка списка не разбирает Markdown неизменённых превью.
3. Прогресс и новые шаги не разбирают Markdown и ленты прошлых запусков заново.
4. Сохранение не отправляет повторно уже записанные, неизменённые тела шагов.

Уменьшение числа запросов само по себе не означает готовность. Нужно проверить
обработчик события, рендер и отложенное сохранение.

Границы результата: этапы 1–4 устраняют повторную обработку при обновлении интерфейса;
этап 5 — повторную передачу подтверждённых шагов. Первый монтаж, первичная загрузка,
поиск по всей истории, новая большая лента и восстановление после конфликта измеряются
отдельно. Их ускорение не следует автоматически из попадания в кэш.

## Правила исполнения

- Прочитай полностью корневые `AGENTS.md`, `CLAUDE.md` и существующий `CLAUDE.local.md`.
  Перед каждой областью учитывай её ближайшие инструкции и README документации.
- Проверь `git status --short`. Чужие изменения сохраняй; не делай commit, push,
  переключение ветки или остановку чужих процессов.
- Не читай рабочие переписки, cookies и приватное состояние. Производительность
  проверяй на генерируемых данных. Артефакты сохраняй в `.state/artifacts/`.
- Не перезапускай рабочий сервер из хода чата: это оборвёт самого исполнителя.
  Серверный этап проверяется через изолированные тесты; живой перезапуск делает человек.
- Всё общение и пояснения в коде — по-русски. Соблюдай читаемость из `CLAUDE.md`.
  UI controls импортируй через `web/src/ui.ts`; дополнительный EventSource не создавай.
- Не отключай сортировку, поиск, автопрокрутку, сохранение, страховочный снимок,
  восстановление pending или серверные проверки модели и рабочей папки.
- `setTimeout(() => JSON.stringify(всяИстория))` и увеличение debounce не устраняют
  блокировку главного потока. Не используй их как исправление.

## Этап 1. Убрать сериализацию истории из проекции реплик

**Файлы:** `web/src/stores/chatInTurn.ts`, `web/src/stores/chat.js`,

Алгоритм:

1. В `historyMessage` сначала сформируй кандидата тем же способом, что сейчас,

3. Для `receipt`, который может прийти новым объектом с теми же значениями, сравни

4. В `materializeInTurnMessages` оставь нынешний выбор места группы: перед финалом,

## Этап 5. Сохранение переиспользует уже записанные тела шагов

Этот этап меняет серверный контракт. Его выполняй после этапов 1–4, отдельными
частями 5А–5Г. Полный PUT остаётся совместимым вариантом. Перенос истории в Worker
и протокол дельт сообщений в эту задачу не входят. Сначала докажи корректность
подтверждений и конфликтов, затем снижение затрат на длительной серии записей.

### 5А. Отдельный маршрут и подтверждение фактически сохранённых шагов

**Новые предполагаемые файлы:** `shared/chatHistoryStepReuse.ts`,
`shared/chatMessageIdentity.ts`, `server/src/lib/chat/historyStepReuse.ts`.

**Существующие файлы:** `server/src/lib/chat/historyStore.ts`,
`server/src/modules/chat/index.ts` и тесты server.

Введи возможность `historyStepReuseProtocol: 1` в ответе `GET /api/chat/store`.
Полная запись идёт в прежний `PUT /api/chat/store/chat`; сокращённая — только в
новый `PUT /api/chat/store/chat/step-reuse`. Общую логику записи и ответа вынеси
в один обработчик, чтобы CAS, auth и уведомления не разошлись между маршрутами.

Одного capability недостаточно: сервер может смениться между GET и PUT. Старый
маршрут игнорирует неизвестное поле `reuseSteps` и способен записать сообщения
без шагов. Новый URI на старом сервере должен вернуть 404/405 без записи.
**Сокращённое тело никогда не отправляется в старый URI**, даже при retry.

Тело нового PUT содержит прежние `chat`, `archived`, `origin` и обязательное поле:

```text
reuseSteps: {
  protocol: 1,
  baseRevision: number,
  refs: [
    {
      messageIndex: number,
      sourceIndex: number,
      expectedKey: string,
      expectedLength: number
    }
  ]
}
```

`messageIndex` — позиция в присланной истории; `sourceIndex` — позиция в подтверждённой
серверной истории указанной revision. `expectedKey` считается по существующему
`messageKey`: устойчивый id, иначе роль и текст. Позиция различает старые одинаковые
сообщения с разными шагами; поиск первого совпадения по тексту запрещён.

Семантика запроса:

- У сообщения с ref поле `steps` отсутствует. Сервер восстанавливает его из базы
  до слияния. Это не команда удалить ленту; даже `steps: null` вместе с ref запрещён.
- Новые, изменённые и неподтверждённые шаги идут полностью полем `steps`.
- `messages: []` с refs запрещён. Очистка идёт полным старым PUT и сохраняет
  существующие правила stale CAS и защиты канонической истории.
- Без refs используется полный старый PUT. Его прежнюю семантику не меняй.

Оба маршрута на новом сервере дополняют успешный ACK необязательным DTO:

```text
stepReuseAck: {
  protocol: 1,
  revision: number,
  confirmed: [
    { messageIndex: number, sourceIndex: number, expectedKey: string, expectedLength: number }
  ]
}
```

Здесь `sourceIndex` уже указывает в **итоговую сохранённую** историю новой revision.
Подтверждение вычисляется после `mergeChat`, `protectCanonicalMessages` и остальных
преобразований, под тем же lock, по результату durable write либо доказанного no-op.
`stale: false`, `restored: 0`, `dropped: 0` сами по себе не подтверждают ни позиции,
ни шаги. В ACK нет тел шагов или всей переписки.

Для первой версии подтверждай только однозначное позиционное соответствие:
сообщение запроса и сохранённое сообщение на том же индексе имеют тот же ключ,
а массив шагов после восстановления действительно сохранён. Сначала сравни ссылки;
если full PUT дал другой массив, допустимо сравнить его JSON-содержимое на сервере.
Не сериализуй шаги ради подтверждения в браузере. Неоднозначное соответствие, сдвиг
позиции или другое тело шагов оставляют запись без подтверждения. В частности,
новые тела той же длины не равны старым. Отсутствие подтверждения безопасно ведёт
к полной передаче соответствующего массива; не обещай оптимизацию этого случая.

  заверши попытку ошибкой. Следующий штатный retry не повторяет sparse-бесконечность.
- [x] Pending удаляется только после успешного durable ACK; `_saveChatNow` по-прежнему
  дожидается барьера, сохраняя свою ограниченную обработку stale до запуска агента.
  Смена `activeId` не делает все чаты dirty, `needSnapshot` накапливается, шаги
  по-прежнему исключены из страховочного снимка.

Тесты окна через настоящий store и управляемую задержку транспорта:

- [x] Новый чат отправляет полные steps; после подтверждения правка draft даёт refs.
  Загруженный с сервера чат использует refs уже при первой правке; проверь Vue proxy.
- [x] Сервер без capability всегда получает full PUT. Смена сервера после GET даёт
  один полный retry; старый URI ни разу не получает урезанную историю.
- [x] Browser snapshot, неприменённый GET, отсутствие revision и неподтверждённая
  canonical-замена не дают refs. Валидный частичный ACK подтверждает только свои записи.
- [x] Замени массив steps другим той же длины, затем измени тело шага через
  copy-on-write: оба изменения замечает dirty-проверка и сохраняет полным полем.
  Вторая сессия стора не разделяет dirty-сигнатуры/подтверждения первой.
- [x] Между отправкой и ACK измени текст/receipt/steps существующего сообщения через
  финализацию, добавь новое сообщение и измени draft. Первая запись подтверждает
  только прежнее; следующая отправляет всё новое. Не ограничивайся тестом draft.
- [x] Более новый GET или удаление чата во время запроса не откатываются поздним ACK.
  Reconnect с локальными правками не присваивает им серверную revision.
- [x] Named409 и 404/405 дают ровно один full retry; generic409, 400, сеть и ошибка
  самого full retry не запускают этот цикл. Pending остаётся до durable ACK.
- [x] Между sparse-запросом, ответом 409 и full retry измени исторический шаг:
  повтор содержит прежнее тело захваченного снимка, следующая запись — новое.
  Подтверждение первой попытки не подтверждает новый массив и не снимает его dirty.
- [x] `modelRefState` вне снимка не вызывает вечные записи; смена activeId и no-op
  не отправляют даже сокращённый PUT. Барьер запуска и накопление snapshot сохранены.

**Готово:** неизменённые подтверждённые шаги не входят в частый запрос, правки во время
ACK остаются dirty, серверное чтение возвращает полную историю. Конфликт не даёт окну
права откатить чужое состояние или молча объявить несохранённое подтверждённым.

### 5В. Проверить последовательность записей и восстановление

- [x] Приёмник fixture использует тот же серверный resolver и ACK builder, что продукт.
  Добавь интеграционный прогон с настоящим `ChatHistoryStore`/маршрутами и временным
  хранилищем на синтетических данных. Одна самодельная модель merge не доказывает
  совместимость с canonical pipeline.
- [x] После записей и последующего GET сравни полную историю: тексты, порядок,
  идентичность, модели и тела шагов. Аудит выполняется вне измеряемого пути страницы;
  одного количества шагов недостаточно. Перезагрузка новой страницы восстанавливает
  сохранённое состояние, включая финал и receipts.
- [x] Повтори modern и legacy-сценарии в серии: draft, завершённый блок, следующий
  блок, финал с pending, reconnect, архив/возврат и запись второго окна. Серверные
  `syncMessages`, canonical projection и execution-обновления должны действительно
  менять revision, а не только автоматически увеличивать её на каждый PUT.
- [x] Измеряй всё окно от события до ACK, включая отложенную запись. Раздельно укажи
  CPU страницы, время HTTP/сервера, число full/sparse PUT, полных GET, конфликтов,
  объём подтверждённых тел, повторно ушедших по сети, и долю попаданий в refs.
- [x] В стабильной серии после подтверждения старые шаги не отправляются повторно.
  При конфликте допустим один полный fallback на попытку; после валидного ACK
  оптимизация должна восстановиться. Если server revision меняется так часто, что
  каждый следующий PUT снова полный, этап НЕ готов: перед включением пересмотри
  контракт базы и повтори проверку. Не ослабляй CAS без отдельного доказательства.
- [x] Добавь новый ответ с большой лентой: она должна впервые сохраниться полностью.
  Измерь отдельно её копирование/сериализацию, первичную загрузку, conflict fallback
  и server-side сравнение ACK. Не объявляй отсутствие любых длинных задач по одному
  уменьшенному payload; большие новые данные остаются границей этого плана.

### 5Г. Устранить повторную обработку служебного JSON и стоимость fetch

Эта часть добавлена по профилю продуктовой реализации: после быстрого рендера
оставалась повторяющаяся длинная задача отложенной записи.

- [x] Кэшируй отпечаток и JSON страховки по живому реактивному чату. Vue computed
  должен замечать текст, черновик, вложенные receipt/attachments и новые или удалённые
  поля сообщения. Не кэшируй нереактивные источники; замена владельца и архив инвалидируют запись.
- [x] Держи по одной проекции на живой чат, вне Pinia JSON. Удаление, prune, reload
  и dispose освобождают записи. Шаги проверяются отдельной сигнатурой ссылок/длин/версий.
- [x] Собирай прежнюю форму страховки из JSON отдельных чатов, обновляя метаданные
  окна заново. Fallback по квоте сохраняет двадцать последних чатов целиком.
- [x] При обычном автосохранении запиши страховку перед отдельной задачей PUT.
  Очередь берёт свежие данные; flush и durable барьеры остаются немедленными.
- [x] Передавай JSON обоих PUT истории через Blob, сохраняя UTF-8 JSON, Content-Type,
  credentials, снимок до ожидания сети и прежние правила ошибок и повторов.
- [x] Проверь вложенные правки после прогрева, отсутствие чтения тел steps,
  lifecycle кэша, порядок задач, немедленный flush и идентичность тела запросов.
  Повтори полную браузерную серию с наблюдением до ACK; измеряй отдельно JSON и JSON + Blob.

Реализация: `web/src/shared/chatPersistenceProjection.ts`, `web/src/stores/chat.js`,
`web/src/shared/apiClient.ts`. Проверки: `chat-persistence-projection.test.js`,
`api-chat-history-body.test.js` и прежние тесты сохранения. Подробности —
