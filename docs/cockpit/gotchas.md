# Неочевидные места (грабли)

## Таймер задачи: `timer_elapsed` из B24 всегда 0 — считать от `timer_started_at`

**Где:** `web/src/shared/format.js` (`liveTimerSec`), потребители — `TaskModal`, `BoardView`,
`PipelineView`.

`getTodayData` отдаёт `timer_elapsed = 0` даже у задач с `timer_running = true` (проверено:
ноль у всех четырёх идущих). Настоящая точка отсчёта — `timer_started_at`, **Unix в СЕКУНДАХ**
(не мс), адаптер кладёт её в `timerStartedAt` — поле добавляется в `_getDashboard`, в `mapTask`
его нет. Исходно все три места считали `timerElapsed + (now − boardLoadedAt)`, то есть показывали
**возраст открытой вкладки**: задача, взятая в 13:50, после F5 показывала «0:00:40».

У идущего таймера накопленное НЕ прибавляем — если B24 однажды начнёт заполнять `timer_elapsed`,
прибавка даст двойной счёт текущей сессии.

Ещё две особенности того же ответа, на них легко обжечься:
- `timer_running = true` бывает у **нескольких** задач сразу (все «взятые», у кого таймер не
  остановлен), а `activeTimer.task_id` — один. Это разные вещи.
- В `worked_tasks`/`today.hours` идущие задачи **не попадают** — туда падает уже зафиксированное
  время, после остановки таймера. Сверять одно с другим бессмысленно.

## B24Client НЕ потокобезопасен — все вызовы через очередь `_run`

**Где:** `server/src/adapters/b24.js`.

`B24Client` держит общую сессию (куки, `sessid`). Конкурентные запросы (доска поллит
`/dashboard` + параллельный `/users` или мутация) рвут сессию — портал отвечал **«Client Error»**.
Фикс: `B24Adapter._run(fn)` сериализует ВСЕ операции клиента через promise-цепочку. Любой новый
метод адаптера, дёргающий `this.client()`, оборачивать в `this._run(...)`. В одиночку баг не
воспроизводится (гонки нет) — не «оно и так работает».

## Мутации route attempt требуют exact identity

**Где:** `server/src/modules/factory`, `server/src/lib/factory-route-cli.js`.

Cockpit не пишет `tN.pipeline` напрямую: это только UI-проекция immutable ledger. Gate,
goto, abandon и resume вызывают `factory` с точными profile + attempt + node; движок делает
CAS в trusted control root и сам обновляет проекцию. Исторический Python-dashboard работает
только на чтение. Прямой upsert способен нарисовать принятые ворота в UI, не изменив cursor,
поэтому такая «оптимизация» является порчей состояния.

## Контракт запуска — по состоянию, не по stdout

`factory` при ошибке аргументов/профиля/маршрута и занятом task lock возвращает `rc≠0`.
`systemd-run` подтверждает только регистрацию transient service, поэтому старт Cockpit
проверяет по полной pinned identity: `ATTEMPT_ID + ROUTE_HASH + ORCH_PID`, живому unit и
четырём последовательным чтениям. См. `POST /api/tasks/:id/launch`.

## Service Worker кэширует — правки не видны без «Обновить»

PWA (`vite-plugin-pwa`, `registerType: 'prompt'`) кэширует ассеты. После пересборки страница
крутит СТАРУЮ версию, пока не появится баннер «Доступно обновление» → «Обновить» (`usePwaStore`).
При отладке в браузере это выглядит как «правка не применилась» — на самом деле нужно обновить SW.
`index.html` отдаётся с `no-cache`, ассеты (`/assets/*`) — `immutable`.

## Service Worker требует secure context — по `http://<IP>` PWA НЕ существует

Не «работает хуже», а не поднимается вовсе: по спеке `navigator.serviceWorker` доступен только
в secure context, исключение сделано лишь для `localhost`/`127.0.0.1`. Замер с `http://<адрес в локальной сети>:8140`:
`'serviceWorker' in navigator === false`, `isSecureContext === false`. Значит на планшете/рабочем компе
нет ни установки PWA, ни precache, ни баннера обновления, ни оповещений, ни микрофона — а на мозге
через `localhost` всё это работает, поэтому со стороны незаметно.

Следствие для архитектуры: **HTTPS — условие существования PWA на любом окне кроме мозга**,
а не улучшение. Дома его даёт свой корневой сертификат («Настройки → Доступ → Локальный HTTPS»),
снаружи — шлюз на VPS. Нативные оболочки (Electron/Capacitor) для этого НЕ нужны и отвергнуты:
Electron на Android не собирается вообще, а упаковка `dist` внутрь пакета ломает обновления — SW
тянет новую версию только со своего origin, а у упакованного фронта origin локальный (`app://`,
`https://localhost` у Capacitor; на `file://` SW не поддерживается), обновляться неоткуда. Тонкое
окно на remote-адрес мозга + включённый SW даёт и мгновенный старт, и обновления сами.

## Осторожно: проверки окружения гоняются в песочнице с урезанным PATH и сетью

`which <пакет>` и `curl` в этой среде врут — на реальном случае дали ложный вывод «пакет
не установлен», хотя пакет стоял и его демон работал. Существование хостовых пакетов проверять
через `dpkg -l`/`pgrep`/`ip addr`, доступность сети — не по одному упавшему curl. Вывод
песочницы об окружении мозга сам по себе не доказывает ничего.

## Доступ снаружи: шлюз на VPS + два обратных SSH-туннеля

Скрипты: `deploy/gateway/bootstrap.sh` (на VPS) и `deploy/gateway/brain-setup.sh` (на мозге), оба
идемпотентные. Схема:

```
Планшет ─https─► VPS: Caddy ─┬─► 127.0.0.1:18140 → туннель A → мозг 127.0.0.1:8140  (кокпит)
                             └─► 127.0.0.1:18141 → туннель B → мозг 127.0.0.1:8141  (Caddy стендов)
```

**Почему туннель исходящий, а не проброс портов на роутере.** Проброс держится на публичном IP,
которого может не быть (CGNAT у домашних провайдеров — массово), который отбирают при смене тарифа
и которого точно не будет у другого пользователя. Исходящее соединение умеет любая сеть, поэтому
схема не зависит ни от провайдера, ни от NAT, ни от смены сети вообще.

**У шлюза нет UI-тумблера «вкл/выкл».** Установленный внешний путь живёт в DNS, Caddy,
systemd-юнитах туннелей и `.env`; прежний prefs `accessGateway` никогда их не гейтил и только
скрывал визард. Поэтому раздел «Доступ» всегда показывает шлюз по `setup` / `job` /
`publicDomain`, а кнопка «Настроить» раскрывает панель и ничего не включает сама. Пока нет
серверной операции, которая атомарно управляет всей этой связкой, изображать её switch-ом
опасно: выключенная картинка оставляла бы реальный публичный адрес работающим.

**Почему SSH, а не WireGuard.** У мозга свой VPN (`v2rayN` → xray VLESS+REALITY → sing-box как
TUN→SOCKS-мост, default в отдельной таблице `2022`). SSH-туннель — обычное TCP-соединение: он не
создаёт интерфейсов и не пишет маршруты, поэтому задеть VPN ему нечем. WireGuard добавляет
интерфейс и маршруты (безопасен только с `AllowedIPs=10.8.0.0/24`, никогда `0.0.0.0/0`) —
не понадобился, потому что локальный Caddy снял нужду в сетевом маршруте.

**Почему ДВА туннеля.** Одно SSH-соединение мультиплексирует всё в один TCP-поток, поэтому
тяжёлые дев-бандлы стендов придавливали бы SSE и терминал. Изоляция достигается отдельными
соединениями, а НЕ числом проброшенных портов — пробросить 50 портов в одном туннеле не помогает.

**Туннель ходит ЧЕРЕЗ VPN — и пусть ходит (решение человека, 09.08.2026).** Исходящее соединение
к VPS уходит в туннель sing-box: до планшета получается крюк через выходной узел, поверх него
тройная упаковка (TUN + SSH + TLS), и вместе с VPN туннель падает. Напрашивающееся лечение —
правило «IP шлюза → direct» в маршрутизации v2rayN — **отвергнуто и в продукт не возвращается**:
это правка чужого конфига ради латентности, а требование сформулировано как «критично не сломать
VPN». Обе цены приняты сознательно. Падение вместе с VPN укладывается в уже существующую модель:
сам сервер кокпита без VPN тоже не стартует (`deploy/require-vpn.sh`), так что снаружи в этот
момент показывать всё равно нечего.

Из этого следует не «ничего не делать», а **ворота у самих юнитов туннеля**
(`ExecStartPre=…/deploy/require-vpn.sh` в `brain-setup.sh`) — они защищают именно VPN. sing-box
поднимает `singbox_tun` РАНЬШЕ, чем расставляет маршруты, и в это окно ssh успел бы уйти напрямую,
отдав VPS настоящий адрес мозга — то есть утечка мимо туннеля ровно там, где его берегут.
Ordering-таргетом это не лечится (интерфейс уже есть, маршрута ещё нет), проверяется именно
маршрут до пробы. `ExecStartPre` наследует `User=`, а sing-box маршрутизирует по владельцу
сокета — проверка идёт от того же пользователя, что и сам ssh. Оттуда же `StartLimitIntervalSec=0`
и `EnvironmentFile=-<cockpit>/.env`: имя интерфейса не должно иметь второй копии, а лимит стартов
увёл бы юнит в `failed` навсегда при долгом ожидании VPN (при нынешнем `RestartSec=5` дефолтный
лимит не выбирается — это страховка, а не заплатка на баг).

Практическое следствие для диагностики: **`activating` у `cockpit-tunnel-*` при опущенном
sing-box — это ожидание, а не поломка.** В журнале будет строка ворот, юнит поднимется сам.
Поэтому и `tunnel_units_down` в визарде сначала спрашивает те же ворота и только потом
отправляет человека читать `journalctl`. Перезапуски туннеля станут рутиной (каждое моргание
VPN), из-за чего важна пара `ServerAliveInterval=20`/`ServerAliveCountMax=3` на мозге и
`ClientAliveInterval 30`/`ClientAliveCountMax 3` на VPS: без них залипший сеанс держит
проброшенный порт и переподключение падает с «remote port forwarding failed».

**Обязательные опции ssh** (иначе классические грабли обратного проброса): `ExitOnForwardFailure=yes`
(без него ssh «подключён» без проброса, а Caddy стучится в пустоту), `ServerAliveInterval` +
`ClientAliveInterval` на сервере (мёртвый сеанс держит порт, и переподключение падает с
«remote port forwarding failed»).

**Ключ туннеля обрезан по максимуму:** пользователь `cockpit-tunnel` без шелла, а в
`authorized_keys` — `restrict,port-forwarding,permitlisten="127.0.0.1:18140",permitlisten="127.0.0.1:18141"`.
Даже утёкшим ключом нельзя ни зайти, ни пробросить что-то ещё. `GatewayPorts no` держит
проброшенные порты на loopback — из интернета их нет, снаружи только Caddy.

**Почему Caddy, а не nginx.** У nginx каждый наш случай — отдельная правка, и все четыре
выстреливают по умолчанию: буферизация ломает SSE, вебсокету нужны заголовки `Upgrade` руками,
`client_max_body_size` 1 МБ рубит загрузку видео, `proxy_read_timeout` 60 с рвёт долгий ход
агента. Caddy всё это делает верно из коробки и сам берёт сертификат.

## Адреса стендов снаружи — ПОДДОМЕН, не подпуть

`web/src/shared/sandbox.js`: локально (http либо литеральный адрес/localhost) — прямо по порту
`http://<хост>:<порт>`; через шлюз (https + доменное имя) — `https://p<порт>.<хост>`.

Подпуть (`/sandbox/7900/`) не годится принципиально: дев-сервер Vite отдаёт ассеты от корня
(`base: '/'`), под подпутём ломаются и пути, и HMR-вебсокет. На поддомене пути остаются
корневыми и стенд работает как дома.

Порт живёт в ИМЕНИ, потому что наружу открыт только 443. Локальный Caddy на мозге достаёт его
регуляркой из `Host` — **диапазоны ограничены сознательно** (`51[7-9][0-9]`, `80[89][0-9]`):
без ограничения прокси стал бы дверью к любому локальному порту, включая сам кокпит в обход
входа, MySQL и ClickHouse. Стенды своей авторизации не имеют вовсе, поэтому на шлюзе перед ними
стоит `forward_auth` к `/api/auth/state`.

Требует DNS: `<домен>` и `*.<домен>` — обе A-записи на адрес VPS.

**Сертификаты — on-demand, а НЕ wildcard.** Блок `*.<домен>` в Caddyfile выглядит очевидным
решением, но он требует ИМЕННО wildcard-сертификата, а тот выдаётся только через DNS-01 —
то есть на VPS нужен и плагин Caddy под конкретного DNS-провайдера, и постоянно лежащий
там API-токен от всей зоны. Поэтому: кокпит — именованный блок (обычный HTTP-01), стенды —
catch-all `https://` с `tls { on_demand }`, по HTTP-01 на каждое имя. DNS-API не нужен вовсе.
Зона рабочего домена живёт на Cloudflare (08.08.2026), то есть DNS-01 технически доступен —
но выбор остаётся прежним: держать на шлюзе токен, которым правится вся зона, дороже, чем
не иметь его там вовсе. Токен Cloudflare передаётся заново на каждую установку, живёт только
в памяти хода и на VPS не уезжает. Ему нужны `Zone:Read` (найти родительскую зону) и
`DNS:Edit` на одну конкретную зону; готовый шаблон «Edit zone DNS» даёт только второе право.

Выбранный поддомен — выделенная область шлюза. Перед подтверждением кокпит читает все страницы
DNS в этой области и показывает план, а после успешной проверки SSH одним Cloudflare batch
приводит **ровно два owner name** (`<домен>` и буквальный `*.<домен>`) к инварианту: по одной
A-записи на текущий IPv4 VPS, TTL 60, **серое облако** (`proxied: false`). Лишние A, старые
AAAA и CNAME на этих двух именах удаляются; TXT/MX/CAA, соседние и произвольные дочерние имена
не трогаются. NS/DS, HTTPS/SVCB и точные `p<разрешённый-порт>.<домен>` блокируют автоматическую
установку с объяснением: первые нельзя безопасно сносить, а последние перекрывают wildcard,
даже если это всего лишь TXT. Предпросмотр подписан отпечатком batch-плана: если зона успела
измениться до установки, кокпит ничего не удаляет и требует нового подтверждения. После
batch кокпит перечитывает API и проверяет постусловие;
публичный DNS принимается только если A-ответ состоит из одного текущего IP, а AAAA отсутствует.
План не дробится на несколько запросов: для общего атомарного лимита Free-тарифа допускается
не больше 200 мутаций; при большем числе дублей часть нужно сначала удалить вручную.

Оранжевое облако означает Cloudflare-прокси, а с ним возвращаются ровно те
ограничения, из-за которых отвергнут Cloudflare Tunnel (100-секундный потолок ответа,
100 МБ на тело, чужая терминация TLS) — см. раздел о границах вариантов ниже.

Сценарий временного VPS поддерживается повторной установкой: новый запуск заново заменит старый
адрес текущим. Но выключение/удаление VPS само очистить Cloudflare не может — токен намеренно
не хранится. Пока отдельного teardown-действия нет, перед освобождением IP две записи нужно
удалить вручную, иначе домен продолжит указывать на адрес, который провайдер может выдать другому.
При первом переводе старый TTL мог уже попасть в кеш публичных резолверов дольше пяти минут;
после первой успешной синхронизации TTL 60 делает последующие переключения быстрыми.

`on_demand_tls { ask ... }` **обязателен**: без него любой, направив своё имя на наш адрес,
заставит выпускать сертификаты, пока не упрёмся в лимиты Let's Encrypt. Разрешение выдаёт сам
кокпит — `GET /api/gateway/tls-allow?domain=…` (`modules/gateway`, публичный: Caddy зовёт его
до всякой авторизации, данных не отдаёт). Пускает только сам домен и `p<порт>.<домен>` с портом
из разрешённых диапазонов; `isAllowedGatewayHost` прогнан по 15 случаям, включая отказ для
`p8140` (кокпит в обход входа), `p3306`, `p8123`, вложенных меток и подделок вида
`p5191.<домен>.evil.com`.

**Две ошибки, найденные при сборке этой связки** (обе были бы видны только на живом сервере):

1. `forward_auth` нельзя направлять на `/api/auth/state` — тот отвечает **200 и невошедшему**
   (`authenticated: false` в теле), а `forward_auth` смотрит только на код и пускал бы всех.
   Нужен отдельный `GET /api/gateway/authz` под гардом: без сессии 401, с сессией 204 без тела.
2. Сессионная cookie по умолчанию **host-only** — на поддомен стенда браузер её не отправит,
   `forward_auth` не увидит сессию и стенды окажутся недоступны. Нужен явный `Domain=<домен>`
   (`cookieDomain`), но ТОЛЬКО когда запрос пришёл на публичный домен: на localhost cookie
   с чужим `Domain` браузер отбрасывает, и вход сломается молча. Цена — cookie видна всем
   поддоменам; все они наши, а `HttpOnly` не даёт прочитать её из JS.

## Работа за шлюзом: `COCKPIT_TRUST_PROXY` — не `true`, а адрес соседа

`trustProxy` включается только этой переменной и должен содержать ИМЕННО адрес, с которого
приходят запросы (для SSH-туннеля — `127.0.0.1`). С `true` любой клиент назначал бы себе адрес
через `X-Forwarded-For`, обходя и лимит попыток входа, и проверку «настройка только с localhost».

От него зависят две вещи, обе проверены подменой заголовков:

- **Флаг `Secure` у сессионной cookie** — решается ПО ЗАПРОСУ (`isSecureRequest`), а не один раз
  на старте. TLS терминируется на шлюзе: браузер идёт по https, а до нас доезжает http, поэтому
  прежняя привязка к локальному TLS ставила бы cookie без `Secure` именно снаружи. Проверено:
  через шлюз — с `Secure`, локально по http — без (иначе браузер её выбросит и вход сломается).
- **`request.ip` для лимита попыток** — иначе все клиенты схлопнулись бы в адрес шлюза, и первый
  же перебор запер бы вход владельцу. Проверено: 10 неудач с одного адреса → 429, с другого → 401.

## Первичная настройка пароля — только с самой машины

`/api/auth/setup` обязан быть публичным (иначе пароль нечем задать), поэтому на сетевом адресе
им завладел бы первый желающий — вместе с PTY-шеллом. Гард пускает его только при
`isLocalRequest`: loopback-адрес **и** отсутствие любых следов пересылки (`X-Forwarded-*`,
`Forwarded`). Двойная проверка не избыточна — через туннель socket-адрес и есть `127.0.0.1`,
так что одного его мало. Проверено: с подделанным `X-Forwarded-For` или `-Proto` → 403,
чистый локальный запрос → 200.

## Установка «как приложение»: три условия, иконки — отдельный блокер

Standalone-запуск (своя иконка в лончере, отдельная карточка в «недавних», splash, БЕЗ адресной
строки) даёт только настоящая установка PWA — Android собирает WebAPK. Chrome предложит её лишь
когда выполнено всё сразу: **https** + **манифест с иконками 192 и 512** + **живой SW**.

Пункт «Добавить на главный экран» в меню Chrome доступен на любом сайте, включая http, но для
неустанавливаемого сайта делает просто закладку — открывается в браузере с адресной строкой.
Это НЕ то же самое, что установка, и выглядит как сайт.

Иконок в проекте долго не было вовсе (favicon зашит инлайном в `index.html` как `data:`-URI,
`icons` в манифесте отсутствовал) — то есть установка была бы заблокирована даже под https.
Сейчас: `web/public/icon-{96,192,512}.png` + `icon-maskable-512.png`, генератор
`web/scripts/gen-icons.py` (рисует через Pillow — растеризатора SVG в системе нет).
`maskable` обязателен отдельным файлом: Android режет иконку под форму лончера, поэтому рисунок
там вписан в safe zone (~80% полотна), иначе рамку обрезает по краям.

Кнопка установки — своя (`usePwaStore.canInstall` / `install()`, плашка `.instbar` в `AppShell`),
на плашку Chrome не рассчитываем: на Android она показывается по эвристикам и может не появиться.
Событие `beforeinstallprompt` одноразовое на загрузку — слушатель вешается в `main.js` сразу после
монтирования (`initInstall()`), позже уже поздно. В headless-браузере это событие НЕ приходит,
поэтому кнопка проверяется только на живом устройстве.

## Подразделы настроек не наследуют стили `SettingsView` (scoped CSS)

`.card`, `.row`, `button`, `.msg`, `.primary` объявлены в `SettingsView.vue` под `<style scoped>`,
поэтому на вынесенный дочерний компонент (`views/settings/*.vue`) они НЕ действуют — глобальный
только `.muted` (в `styles.css`). Симптом обманчивый: вёрстка выглядит «поехавшей» (текст
наложился на картинку, у карточек нет фона), и кажется, что дело в разметке, а не в отсутствии
правил. Новый подраздел обязан повторить эти классы у себя (сверять с `SettingsView`, чтобы вид
не расходился).

## Вход в кокпит: один пользователь, сессионная cookie, гард на ВЕСЬ /api

`lib/auth-store.js` (учётка + сессии), `plugins/auth.js` (гард), `modules/auth` (эндпоинты),
`views/LoginView.vue` + `stores/auth.js`. Пароль — scrypt-хеш в `server/.state/auth-account.json`
(0600), сессии — в `auth-sessions.json`, поэтому рестарт сервера не выкидывает с планшета.

**Закрыто ВСЁ `/api`, включая GET и upgrade вебсокета** — прежняя модель «читать свободно
в доверенной сети» не годится: кокпит отдаёт историю чатов, дифы, состояние фабрики, а терминал
даёт шелл. Хуки Fastify выполняются и для WS-роутов, поэтому терминал закрыт тем же гардом
(проверено: upgrade без сессии → `401`, а не `101`). Публичны только `/api/auth/{state,login,setup}`
и `/api/health`.

**401 вместо серверного редиректа — сознательно.** Фронт это PWA: редирект на навигации
конфликтует с service worker'ом (тот отдаёт закешированную оболочку вместо страницы логина).
Поэтому статика публична (секретов в ней нет), оболочка грузится всегда и сама показывает вход
по 401. Проверено: отзыв сессии на сервере → приложение само возвращается на экран входа.

**`COCKPIT_TOKEN` УБРАН, не возвращать.** Он обязан был дублироваться во фронт через
`VITE_COCKPIT_TOKEN`, а Vite подставляет env в бандл на сборке — секрет лежал в публичном JS
открытым текстом (проверено сборкой с тестовым значением: значение находится в `index-*.js`).
При открытом чтении это не защита вовсе. Заодно из терминала убран `?token=` — секрет в query
оседает в логах, cookie этого не делает.

**Грабля scrypt:** при `N=32768, r=8` требуется ровно 32 МиБ, и это же дефолтный `maxmem`
в Node → `error:030000AC ... memory limit exceeded`. Передавать `maxmem` явно (у нас 64 МиБ).

**КРИТИЧНО: гард решает по МАТЧЕННОМУ РОУТУ, а не по `request.raw.url`.** Роутер Fastify
декодирует percent-encoding ПЕРЕД сопоставлением, поэтому `/%61pi/terminal` попадает
в обработчик `/api/terminal`. Первая версия гарда сравнивала сырую строку с префиксом `/api/`
— и такой запрос проходил как «статика». Был полный обход входа: анонимно читались
`/api/chat/store` и `/api/tasks`, проходили POST-мутации, а PTY-вебсокет отдавал
`101 Switching Protocols`, то есть шелл на машину без пароля. Правильный источник истины —
`request.routeOptions.url` (шаблон вида `/api/tasks/:id/graph`): он не зависит ни от кодирования,
ни от query, ни от лишних слэшей. Строковые проверки сырого URL для авторизации НЕ использовать.

**`/shots/*` тоже под гардом** (`PROTECTED_STATIC`). Это скриншоты приёмки
тестируемого приложения — данные проектов и содержимое задач; имена предсказуемы
(`t<номер задачи>-…`). Раньше отдавались анонимно (проверено: реальный PNG приходил без сессии).
Публичной остаётся только оболочка `web/dist` — без неё не показать экран входа.

**`trustProxy` НЕ включать без реального прокси.** С ним клиент сам назначает себе
`request.ip` через `X-Forwarded-For`, и лимит попыток входа обходится сменой заголовка
на каждый запрос. TLS терминируется в самом Fastify, прокси перед кокпитом нет.

**`/api/health` не публичный:** отдаёт имя хоста и абсолютные пути (`stateDir`, `factoryHome`),
а экрану входа не нужен — тому достаточно `auth/state`.

**Внутренний токен для дочерних процессов.** `permission-prompt-tool` чата живёт в дочернем
процессе `claude`, cookie у него нет, а достучаться до сервера обязан. Для этого в `app.js`
генерируется `internalToken` (`randomUUID()` на каждый запуск, только в памяти), уезжает в env
дочернего процесса как `COCKPIT_INTERNAL` и принимается гардом в заголовке `X-Cockpit-Internal`.
На диск и в конфиг не попадает.

**Смена пароля сбрасывает все сессии** (украденная cookie перестаёт работать), но текущему
устройству сразу выдаётся новая — иначе владелец выкинул бы сам себя. `setup` доступен ровно
пока пароль не задан: потом только `409`, чтобы никто не переустановил пароль в обход.

**Поллинги надо гасить при потере сессии** (`stopPolling` у board/system, зовётся из `App.vue`):
иначе интервалы молотят в закрытый API и сыпят 401 в консоль на экране входа (было 14 ошибок).

**Баннер обновления PWA обязан быть ВНЕ ветки авторизации** (`shared/ui/UpdateBanner.vue`,
рендерится в `App.vue` рядом с `LoginView`, а НЕ внутри `AppShell`). Иначе: service worker держит
старую сборку, пользователь на экране входа, а кнопки «Обновить» нет — оболочка с баннером
рендерится только после входа, и залипшая версия не лечится из интерфейса. Само обновление
авторизации не требует (работает с SW, `sw.js` — публичная статика). Проверено полным циклом:
новая сборка → `reg.update()` → баннер появился НА ЭКРАНЕ ВХОДА → клик → версия применилась.

**Связка с TLS:** по http пароль уходит открытым текстом, поэтому для доступа вне localhost TLS
обязателен, и от него же зависит флаг `Secure` у cookie (на http его ставить нельзя — браузер
выбросит cookie и вход сломается молча). Экран входа честно предупреждает, когда TLS выключен.

## Доступ к кокпиту с других устройств — границы вариантов

Направление «открыть кокпит на планшете как приложение» откатывалось; часть выводов действует
до сих пор, чтобы не проходить круг заново.

**Выбор решают стенды, а не удобство входа.** Стенды слушают на всех интерфейсах
(`0.0.0.0:5191`, `:5193`, `:8090`…), поэтому вариант с IP-связностью (VPN-клиент на планшете)
открывает их сам собой — ни прокси, ни поддоменов не нужно вовсе.
Вариант «на планшете только браузер» обязан проксировать КАЖДЫЙ порт отдельным именем, отсюда
`p<порт>.<домен>`, ограниченные диапазоны и `forward_auth` у VPS-шлюза. Всё, что даёт один
публичный хост без wildcard, стенды не покрывает в принципе.

- **Свой CA не даёт «автоматически»** — но для СВОИХ устройств этого достаточно, и именно так
  сделано сейчас (см. «Локальный HTTPS» ниже). Установка корня — решение о доверии на уровне ОС,
  из браузера её не выполнить (файл → системные настройки → «Сертификат ЦС» → PIN → предупреждение
  про мониторинг сети). Для «другой человек открыл и поехало» не подходит в принципе; для двух
  своих планшетов — разовый шаг.
  Важная деталь: серверный лист не длиннее **398 дней**, и браузеры смотрят ТОЛЬКО
  в subjectAltName (CN игнорируется).
- **Второй VPN-клиент на планшете — вариант закрыт (решение 08.08.2026).** У мобильной ОС
  активным может быть только ОДНО VPN-приложение, а на планшете постоянно работает свой VPN:
  слот занят. Причина именно в слоте и не зависит от продукта — на самом мозге такой клиент
  со sing-box не конфликтует, пока не забирает default route. Любой новый кандидат этого сорта
  упирается в то же ограничение, обсуждать его заново не нужно.
- **Публичная ссылка одного сервиса** (внешний туннель с доверенным сертификатом, у открывающего
  ноль шагов) — прежнее возражение про открытый наружу PTY снято: весь `/api` за сессией,
  `setup` только с localhost, `COCKPIT_TOKEN` удалён. Закрывают такой путь **стенды**: он даёт
  один хост без wildcard и фиксированный набор портов.
- **Cloudflare Tunnel** — бесплатен и работает за CGNAT, но по этому кокпиту бьёт трижды:
  100-секундный потолок ответа (ошибка 524) режет `POST /api/chat`, который молчит весь ход
  агента; 100 МБ на тело запроса убивают загрузку видео в распознавание; и зона переезжает
  на NS Cloudflare, который вдобавок терминирует TLS и видит переписку, дифы и данные портала
  открытым текстом. Обход таймаута есть только через их WARP-клиент — то есть снова VPN-слот
  на планшете, но уже с посредником в середине.

## Локальный HTTPS: два сокета в одном процессе, а не «переезд на 8143»

Дома PWA не существует без secure context (см. раздел про Service Worker), поэтому кокпит
выпускает свой CA и лист на адрес мозга: «Настройки → Доступ → Локальный HTTPS».
Код — `server/src/lib/tls/local.js` (выпуск), `server/src/lib/tls/https-listener.js` (второй сокет),
`server/src/plugins/http-scope.js` (область http).

**Порт 8140 остаётся http и остаётся полнофункциональным для loopback.** Это не компромисс,
а требование: 8140 — внутренняя шина процесса. По нему ходят permission-tool чата (дочерний
процесс `claude` без cookie), `bin/b24` и SHIP-этап фабрики, `bin/restart` (проверка живости
по `/api/auth/state`), dev-прокси Vite и туннель шлюза с VPS. Переведи 8140 на https — и всё
перечисленное надо чинить в шести местах разом.

Что решает `decideHttpRequest` для запроса, пришедшего на http-сокет:

| условие | решение | почему |
|---|---|---|
| https не поднят | пропустить всё | иначе битый сертификат отрезает кокпит от сети, чинить — с консоли мозга |
| сосед по сокету — loopback | пропустить всё | та самая внутренняя шина |
| путь `/api/settings/tls/ca.{crt,svg}` | пропустить | корень качается по http: по https до его установки браузер ругается |
| `Upgrade:` из сети | разорвать сокет | `ws://` — это PTY-шелл открытым текстом, а `wss://` браузер сам не подставит |
| остальное из сети | `301` на `https://<host>:8143` | |

Грабли, на которые уже наступали или которые обойдены осознанно:

- **Адрес берём из `request.socket.remoteAddress`, а НЕ из `request.ip`.** За шлюзом `request.ip` —
  это клиент из `X-Forwarded-For` (публичный), и запросы туннеля улетали бы в редирект на домашний
  адрес, до которого снаружи не достучаться. Сосед по сокету у туннеля всегда `127.0.0.1`.
  Исключение — выдача `ca.crt`: там проверяется именно `request.ip`, чтобы корень не ушёл наружу.
- **Fastify создаётся БЕЗ опции `https`.** Второй сервер получает тот же роутер через публичную
  `fastify.routing` и **перенесённые слушатели `upgrade`** — `@fastify/websocket` вешает свой
  ровно один на `app.server` при регистрации. Забудешь перенести — терминал по `wss://` молча
  не подключается (тест TLS-SCOPE-04 ловит).
- **Перенос делается ПОСЛЕ `listen()`**: до готовности приложения плагин ещё не повесил upgrade.
- **Провал `listen` на 8143 не роняет процесс.** Под `Restart=always` исключение здесь устроило бы
  вечный крэш-луп. Ошибка возвращается и видна в «Настройки → Доступ».
- **`bin/restart` ждёт освобождения ОБОИХ портов.** Сокеты закрываются не одновременно; новый
  процесс успевал стартовать, пока старый держал 8143 — https молча не поднимался.
- **Флаг `Secure` у cookie корректен сам собой**: `request.protocol` в Fastify — это
  `socket.encrypted`, то есть свойство соединения, а не процесса. Cookie не разделяются ни по
  схеме, ни по порту, поэтому сессия переживает переход `http://IP:8140` → `https://IP:8143`.
- **Сертификат читается ОДИН раз при старте.** Поэтому тумблер режима — это не «включить
  сейчас»: он записывает намерение в prefs, а сокет появляется/исчезает при следующем старте.
  Отсюда честная плашка «нужен перезапуск» (сравнение отпечатка на диске с загруженным).
- **Тумблер режима гасит сокет, а не файлы.** `accessLocalHttps` в prefs читается в `app.js` до
  сборки приложения и решает, что вернёт `lib/tls/source.js`: выключен — `source: 'none'`, https
  не поднимается вовсе. Сертификат и корень при этом остаются на диске, поэтому обратное
  включение не требует ни выпуска, ни повторной установки корня на устройства. Стереть выпущенное
  — отдельная кнопка «Удалить сертификат» (`POST /api/settings/tls/disable`): у «выключить режим»
  и «стереть ключи» разная цена, и путать их в одном контроле нельзя. Тумблер намеренно НЕ гасит
  `COCKPIT_TLS_KEY/CERT`: переменные окружения — настройка машины, а не режим в UI, и человек за
  консолью не ждёт, что галка в браузере их отменит (тесты TLS-SRC-01/02).
- **Ключ корня лежит вне репозитория** (`~/.config/cockpit/ca`, `COCKPIT_TLS_CA_DIR`): плагин
  «Код» отдаёт по HTTP любой файл под деревом проекта, а `server/.state` — внутри дерева.
  На корне стоят `nameConstraints=critical` по приватным диапазонам: украденный ключ не подпишет
  публичный домен.
- **Адреса из тела запроса уходят в SAN и в `-extfile` openssl** — валидируются allowlist-ом
  (`net.isIP` + приватный диапазон), а не «фильтрацией плохого»: `1.2.3.4,DNS:evil.com` дал бы
  лист на чужой домен под доверенным корнем, а перевод строки — второй CA.
- **«Адрес не в сертификате» при правильном сертификате = в адреса машины попал туннель VPN.**
  `localAddresses()` отсекает мосты и туннели ПО ИМЕНИ интерфейса (диапазон не годится:
  docker-мосты живут в тех же приватных сетях), а sing-box зовёт свой интерфейс `singbox_tun` —
  суффиксом, и под префиксный фильтр он не попадал. Его `172.18.0.1` считался адресом мозга,
  которого нет в SAN, и раздел «Доступ» светил жёлтым чипом, хотя лист выписан ровно на тот
  адрес, по которому заходят. Имя туннеля ловится с обеих сторон (`tun`/`tap`/`wg`/`utun`),
  вторым поясом — маска: в /30 и уже клиенту места нет, домашней сети такой маски не бывает.
  Сверять замером: `ip -4 -o addr` против `X509Certificate.subjectAltName`, а не по чипу.
  Сторож — `tests/server/tls-local.test.js` (TLS-GEN-07).
- **QR ведёт на `http://<адрес>:8140/api/settings/tls/ca.crt`**, а не на https. Веди он на https,
  корень пришлось бы качать через то самое предупреждение браузера, которое он и убирает.
- **На мозге ставить корень не нужно**: `http://localhost:8140` — secure context по спеке.

## Адрес стенда: хост берём у мозга, `localhost` подставлять нельзя

`web/src/shared/sandbox.js` (`sandboxUrl(port)`) строит ссылку на песочницу из хоста МОЗГА
(`api.base || location.origin`) и всегда форсит схему `http` — стенды это обычные dev-серверы без TLS.
Раньше в `PipelineView.vue` был хардкод `http://localhost:${fePort}`: на мозге он случайно работал,
а из окна `localhost` — это само устройство-окно, поэтому стенд не открывался.

Схему форсим намеренно: даже когда Cockpit открыт по HTTPS через внешний шлюз, ссылка
на `http://<хост>:5193`
останется рабочей — переход по ссылке это top-level navigation, блокировка смешанного контента
на неё не распространяется (в отличие от iframe — стенд в iframe засунуть не получится).

Отдельный env-оверрайд хоста стендов НЕ добавляли: вывод из хоста мозга + форс `http` покрывает
и прямой `http://<IP>`, и текущий HTTPS-шлюз. Появится другая топология (реверс-прокси на другой
машине) — добавить тогда, а не «на всякий случай».

## Никаких проектных хардкодов в коде

Профиль — из реестра задачи (`registry.PROFILE`), список профилей — сканом
`profiles/*/graph.json` через `config.profilesDir` (`discoverProfiles`),
портал/креды B24 — из «Настроек» (`.state`),
пути (venv, снос стенда, factory bin) — через env (`COCKPIT_*`). Пустой кокпит НЕ знает ни про
конкретный проект, ни про адрес портала. Не возвращать `|| '<имя проекта>'` и подобное.

## Медиа: runtime отдельно от исходников

`server/src/lib/media/` — локальный медиа-конвейер, а `lib/speech/SpeechRuntime` — единый
шов диктовки и видео. Python-venv принадлежит Cockpit и обычно лежит в
`server/.state/media-venv` (gitignore). `deploy/install.sh` идемпотентно создаёт его из
закреплённого `server/requirements-media.txt`; CUDA-вариант после явного выбора дополняет
`requirements-media-cuda.txt`. Установщик атомарно фиксирует абсолютные
`COCKPIT_MEDIA_PYTHON` и `COCKPIT_MEDIA_HF_DIR` в корневом `.env`. Уже заданный собственный
Python не переписывает. Temp для `.env` создаётся с 0600 до записи секретов;
`--no-cuda`/`COCKPIT_MEDIA_CUDA=0` удаляет `nvidia-cublas-cu12` и из старого venv.

Модели whisper живут **не в общем пользовательском кэше**, а в собственном
`COCKPIT_MEDIA_HF_DIR` (`server/.state/hf` по умолчанию). Runtime очищает унаследованные
`HF_HUB_CACHE`/`HUGGINGFACE_HUB_CACHE`, закрепляет каталог и commit revision модели и
работает `local_files_only`: неполный snapshot означает «модель не готова», а не фоновую
загрузку из сети. Скачивание/копирование общего кэша — отдельные отменяемые model jobs в
«Настройки → Речь» с дисковым статусом. `doctor`/speech capabilities проверяют
ffmpeg/ffprobe/venv/faster-whisper, выбранную модель и реальный CUDA canary.

Наличие произвольного `blobs/*.incomplete` само по себе не означает, что pinned snapshot
сломан. `huggingface_hub==1.18.0` создаёт уникальный temp на попытку: отменённый worker
может оставить orphan, а повтор уже успешно положит финальный blob рядом. Готовность
подтверждают local-only resolution точной revision и реальные обязательные файлы snapshot
(включая цели symlink). Superseded temp игнорируется только когда соответствующий финальный
blob уже существует; отсутствующий обязательный файл или temp без финального blob по-прежнему
даёт `cached:false`.

Ручное создание нужно только при обходе установщика:
`python3 -m venv server/.state/media-venv`, затем
`server/.state/media-venv/bin/pip install -r server/requirements-media.txt`; после этого
нужно явно задать оба абсолютных пути в `.env`.
До переноса fallback считался как `<каталог файла>/../.venv/bin/python`: исходный файл
лежал в `src/media/`, и `..` попадал в корень прежнего проекта, а в Cockpit он стал
указывать на `server/src/lib/.venv`, которого не существует. Диктовка отвечала
`spawn .../lib/.venv/bin/python ENOENT` — путь выглядел настоящим, и искали не там.

### Browser speech: `onend` не означает «включить снова»

Web Speech может закончить сессию после паузы. Перезапуск разрешает только FSM чата при
актуальных `desiredActive`, generation и revision настроек: без них поздний `onend` после
Stop, Esc, смены вкладки или смены движка снова включает микрофон. Терминальные ошибки
permission/audio/language не повторяются; `network` и `no-speech` имеют ограниченный
retry с backoff. Промежуточный текст живёт отдельным хвостом и заменяет себя, финальный
добавляется в поле ровно один раз — иначе recognizer затирает ручную правку пользователя.

`browserProcessing=auto` не означает «локально»: конкретный user agent может отправлять
звук своему сервису, поэтому первый `start()` требует явного consent, а каждый start/retry
заново валидирует на сервере его актуальную opaque revision и fail-closed обрывается offline.
`browserProcessing=local` проверяет `SpeechRecognition.available()` и устанавливает пакет
только по явному действию; отсутствие API — «не поддерживается», а не разрешение тихо
перейти в auto. Оба браузерных варианта, MediaRecorder и AudioWorklet требуют secure context.

### Live Whisper — rolling decode, а не WebM-чанки и не настоящий streaming encoder

Локальная диктовка передаёт звук через авторизованный same-origin WebSocket
`/api/chat/transcribe/stream`: `AudioWorklet` ресемплирует вход в PCM16 mono 16 кГц,
стартовый JSON фиксирует protocol v1, `sessionId`, актуальную revision настроек и точный
аудиоконтракт `{encoding:"pcm_s16le",sampleRate:16000,channels:1,frameSamples:1600}`;
бинарные кадры начинаются с `uint32 LE seq`, а сервер подтверждает их `ack`. Upgrade
принимает только действующую сессию и буквальный canonical Origin
`scheme://host[:port]`, равный origin запроса: path, query, credentials и альтернативная
запись стандартного порта не допускаются. Поэтому сравнивать только `URL.origin` без
равенства исходной строки нельзя.
У Vite dev-proxy для `/api` нужны `ws: true` и `rewriteWsOrigin: true`: иначе браузер
честно присылает Origin `:5180`, backend сравнивает его со своим `:8140` и отклоняет
легитимный dev-upgrade. В production оба адреса уже одного origin.
После upgrade клиент обязан прислать стартовый JSON за 10 с: иначе ещё не начавшее
распознавание закрывается по timeout и не удерживает WebSocket без границы.
При backpressure аудио не выбрасывается: в один момент работает один decode, а лишние
запросы схлопываются до последнего watermark.

Дефолтные предохранители сейчас конкретны: `maxStreams=2` считает pending, active,
cancelling и quarantined sessions; decode interval 2 с,
overlap 1,5 с, rolling window 30 с, непродекодированный pending 30 с, принятый live PCM
5 минут и Stop/drain 30 с. После worker `ready` отсутствие новых PCM-кадров 30 с считается
transport idle, а hard wall-clock всей session ограничен 6 минутами. Тихие PCM-кадры
тоже сбрасывают idle timer. Пять минут — server PCM limit, а не auto-stop UI:
`MediaRecorder` продолжает писать recovery blob до ручного Stop. Клиент ждёт server
`ready` до 45 с и ограничивает свою очередь PCM 768 КиБ — примерно 24 с PCM16/16 кГц
mono и намеренно меньше серверных 30 с. Эти числа ограничивают ресурсы и время аварийного
ожидания, но ничего не обещают о time-to-first-partial или final latency.

Нельзя подменять этот путь `MediaRecorder.start(timeslice)` и распознавать каждый WebM/Opus
кусок отдельно. Поздний кусок не обязан иметь самостоятельный container header, а граница
режет слова. Поэтому полный MediaRecorder WebM пишется **параллельно и целиком** только для
аварийного `POST /api/chat/transcribe`, а live-канал получает сырой PCM.

На диктовку живёт отдельный non-detached worker с уже разрешённой pinned revision модели
и `local_files_only=True`; между диктовками он не остаётся. faster-whisper не хранит
stateful encoder cache: worker повторно декодирует rolling-окна с overlap, LocalAgreement
закрепляет общий префикс двух последовательных гипотез, а изменяемый хвост остаётся
partial. Поэтому это псевдостриминг и его latency зависит от RTF машины — цифры появляются
только после живого замера, а не из размера окна в коде. Глобальный resident daemon этапа
4b для этой схемы не нужен и по-прежнему отложен.

Partial живёт только в строке «Слышу…»: писать его в textarea нельзя, иначе следующая
гипотеза затрёт ручную правку. После непустого `done` final дописывается туда ровно один
раз. Stop закрывает вход и делает bounded drain с tail flush; Esc отменяет сессию. Если
live-путь не поднялся, оборвался, не уложился в drain **или завершился пустым final**, Stop
распознаёт сохранённый полный WebM старым batch endpoint. Только preflight-отказ из-за
отсутствия WebSocket, AudioContext или AudioWorklet запускает batch warmup: после
фактической live-попытки fallback идёт one-shot, чтобы не поднимать рядом вторую модель.
Multipart fallback несёт тот же `streamSessionId`: перед batch runtime сам отменяет
именно соответствующую live-сессию и ждёт подтверждённый child `close`, даже если обработчик
закрытия WebSocket ещё не успел начать cleanup. Затем он ждёт уже начатые отмены других
stream workers, но не сериализуется с чужими активными диктовками. Если bounded
stdin EOF → TERM → KILL не дал `close`, ошибка остаётся fail-closed, а slot и workDir
переходят в quarantine до фактического process exit; объявлять PID мёртвым по одному
истёкшему таймеру нельзя. One-shot без correlation при таком quarantine тоже отвечает
`503 speech_stream_busy` и не запускает вторую модель. Авария никогда не включает
`browser:auto`: это могло бы
незаметно отправить голос удалённому сервису без нового явного выбора и consent.

Cleanup тоже обязан быть ограниченным и best-effort. Клик Stop сразу запускает единый
live-stop, не дожидаясь `MediaRecorder.onstop`; поздний recorder callback переиспользует
тот же promise. Tail flush AudioWorklet ждётся до 500 мс, ожидание закрытия
`AudioContext` и WebSocket — до 750 мс каждое, а конкурентные Stop/cancel ждут общий
cleanup barrier. Если `MediaRecorder.onstop` не приходит, watchdog через 2 с продолжает
завершение с уже собранным WebM. Эти отсечки не означают, что модель распознала речь
за то же время. Cancel во время Stop/finishing остаётся отменой: поздний decode после
cleanup barrier не может «воскресить» сессию событием `final`/`done`.

Переносимость здесь означает CPU/int8 CTranslate2: он работает независимо от марки GPU,
поэтому машина с AMD-картой не остаётся без диктовки. Текущий ускоренный backend — только
CUDA/NVIDIA; наличие AMD GPU само по себе ускорения не даёт, ROCm не установлен и не
обещан. На CPU real-time тоже не обещан: если decode медленнее входящего звука, отставание
растёт, после чего bounded drain либо завершит хвост, либо включится batch fallback.

Во время записи сама кнопка микрофона становится Stop и получает красную пульсирующую
подложку; отдельный нижний meter удалён. Анимация — только сигнал состояния, не измеритель
громкости, и отключается через `prefers-reduced-motion`.

Whisper на тишине способен галлюцинировать готовые фразы, поэтому VAD остаётся включён.
При длинной тишине rolling watermark продвигается только после двух последовательных
пустых/VAD-гипотез и сохраняет overlap 1,5 с: иначе 30-секундное окно ложно сработало бы
как backpressure либо pruning мог бы отрезать начало поздней речи.
`hallucination_silence_threshold` сам по себе не помогает без `word_timestamps=True`, а
проектные термины передаются как `hotwords`, не как `initial_prompt`. CUDA capability —
это короткий реальный canary с тем же env, что транскрипция: один импорт не обнаруживает
отсутствующий `libcublas.so.12`, потому что ошибка возникает лишь на первом инференсе.
Вариант CUDA устанавливается воспроизводимо командой `deploy/install.sh --with-cuda`.

## Машинные переменные — только в корневом `.env`, у всех трёх способов запуска

`.env` (gitignore) читают systemd-юнит (`EnvironmentFile=-<cockpit>/.env`), `bin/cockpit` и
`bin/restart` (оба — `node --env-file`). Раньше набор переменных зависел от того, чем подняли
сервер: `bin/restart` подставлял путь к venv распознавания сам (строкой в скрипте), юнит —
нет. Поднятый руками кокпит диктовку распознавал, поднятый systemd (то есть после каждой
перезагрузки) падал с ENOENT, и разница ничем не объяснялась.

Строки `Environment=` в установленном юните не помогают: `deploy/install.sh` перегенерирует
`~/.config/systemd/user/cockpit-server.service` из шаблона на каждом прогоне, правки пропадают.
Синтаксис `.env` — общий знаменатель systemd и `node --env-file`: `KEY=VALUE`, без `export`,
без подстановки `$VAR`, `~` и `%h` (пути только абсолютные). После правки `.env` — перезапуск.

## Сервер — host-native, не контейнеризуется

Командует host-уровнем: `factory bin`, `/proc`, `~/.factory/state`, `docker`. В контейнере
`factory` побежал бы внутри контейнера — модель «мозга» ломается. Поэтому systemd, не Docker.
Фронт (статика) — можно отдельно (nginx/VPS), но по умолчанию его отдаёт сам сервер.

## `ttNNNN.pipeline` — призраки

В `~/.factory/state` есть файлы с двойным префиксом `tt*` (баг двойного `t`). Глоб задач —
строго `^t(\d+)\.pipeline$` (см. `FactoryStateAdapter.listTaskIds`), призраки отсекаются.

## Запуск фабрики — ТОЛЬКО в отдельный systemd-scope (иначе рестарт кокпита убивает прогоны)

Прогон может умереть на этапе BUILD, если сервер кокпита работает под systemd-юнитом
`cockpit-server.service`, а фабрика запущена ручкой `launch` как его потомок и живёт
в cgroup юнита. Когда юнит остановился (рестарт сервера), systemd зачистил cgroup ЦЕЛИКОМ:
TERM демону фабрики и его claude-агенту (в stages.log: «демон остановлен сигналом TERM»).
`nohup`/`setsid` от cgroup-kill НЕ спасают. Фикс в `modules/factory` launch: фабрика
спавнится через `systemd-run --user --collect --unit=factory-tNNNN` — отдельный
transient service, жизнь кокпита её не касается (fallback без systemd — detached spawn
s выводом в `state/tNNNN.launch.log`, не в пайпы). Резюм после смерти оркестратора —
отдельный POST resume с exact attempt; повторный launch существующего прогона запрещён.

**У route-юнита обязателен `KillMode=mixed`.** Дефолтный `control-group` шлёт TERM ВСЕМУ cgroup
разом, а оркестратор по TERM должен успеть три вещи по порядку: остановить раннера, снять
инструментацию из рабочего дерева и только потом умереть. Процессы, которые он запускает уже
внутри обработчика сигнала, при дефолте рождаются в приговорённой группе и умирают сразу:
очистка возвращает 143 (в логе — «date: ошибка записи: Обрыв канала»), задача встаёт в
`STALLED_HUMAN=1`, а инструментация остаётся в
дереве. Аргументы юнита собраны одним местом — `lib/factory-launch.js`, `factoryUnitArgs()`,
их используют оба resume-запуска (после ворот и после `goto`); там же явный
`TimeoutStopSec=120`, чтобы дефолт менеджера не оборвал очистку на середине.

## Два владельца порта 8140: systemd-юнит vs bin/restart

`deploy/install.sh` ставит user-юнит `cockpit-server.service` (Restart=always). Если гонять
сервер руками через `bin/restart` (setsid), юнит уходит в вечный crashloop по EADDRINUSE
(счётчик набил 5000+ рестартов), а в окна свободного порта успевает перехватить порт —
и тогда часть запросов обрабатывает ОН (в одном случае фабричный прогон оказался в его cgroup).
Правило: на время ручной разработки `systemctl --user stop cockpit-server`, боевой режим —
только юнит. Диагноз перехвата: `journalctl --user -u cockpit-server`.

**27.07.2026 это повторилось и обошлось дороже.** Ручной экземпляр (из терминала VS Code,
cgroup `app-code-*.scope`) держал порт часами, юнит намотал **8057** падений. Побочные эффекты,
которые сбивают с толку при диагностике:

- `systemctl --user is-active` показывает `activating`, `MainPID=0` — юнит «как бы поднимается»,
  хотя запросы обслуживает совсем другой процесс. Кто на самом деле на порту, видно только через
  `ss -ltnp | grep :8140`, а его происхождение — через `cat /proc/<pid>/cgroup`
  (`app-code-*.scope` = запущен руками из VS Code, `cockpit-server.service` = боевой юнит).
- Правки серверного кода «не применяются»: ручной экземпляр стартовал до них, а `--watch` в
  бою не используется. Прежде чем решить «фикс не работает», сверь аптайм процесса со временем правки.

**`systemctl restart` эту ситуацию НЕ расшивает:** пока ручной экземпляр жив, юнит всё равно не
займёт порт. Порядок один — погасить владельца порта, дождаться освобождения, и только потом
стартовать юнит. `bin/restart` делает это правильно, но поднимает СВОЙ setsid-процесс, а не юнит:
для боевого режима он не годится.

## `StartLimitIntervalSec=0` в юните кокпита — не украшение

Дефолт systemd — «не больше 5 стартов за 10 секунд». При `RestartSec=5` (тем более при прежних 2с)
лимит выбирается почти мгновенно, и юнит уходит в `failed` НАВСЕГДА, без дальнейших попыток.
С воротами VPN (ниже) это фатально: после перезагрузки туннель поднимается руками и может появиться
через минуты — юнит к тому моменту давно сдался бы, и кокпит не встал бы уже никогда.
Поэтому в `[Unit]` стоит `StartLimitIntervalSec=0` — ждать столько, сколько нужно.

## Кокпит не стартует без VPN (ворота `deploy/require-vpn.sh`)

Требование: сервер не должен подниматься в обход туннеля. У sing-box (из v2rayN) своего
systemd-юнита нет — его запускает GUI через `sudo -S`, поэтому `Requires=` цеплять не за что.
Ворота стоят в `ExecStartPre`: ненулевой код → systemd не запускает сервер и повторит через
`RestartSec`. Когда VPN появится, кокпит поднимется САМ, в пределах 5 секунд.

Проверяется **маршрут**, а не наличие интерфейса:

```
ip route get 1.1.1.1   →   ... dev singbox_tun ...
```

sing-box создаёт `singbox_tun` РАНЬШЕ, чем расставляет правила маршрутизации; в этом окне
интерфейс уже есть, а трафик ещё идёт напрямую — стартовать там означает ровно ту утечку,
ради которой ворота и ставятся. Две тонкости, на которых легко ошибиться:

- у tun-устройств `operstate` = `unknown`, а не `up` (норма ядра). Требование строгого `up`
  не откроет ворота никогда;
- sing-box маршрутизирует **по владельцу сокета** (`uid 1000`, таблица 2022) — проверка обязана
  идти от того же пользователя, что и сервер. Для `systemd --user` это выполняется само.

Чего ворота НЕ гарантируют: маршрут есть ≠ пакеты доходят. Если туннель поднят, а сервер на той
стороне мёртв, кокпит стартует без интернета. Это безопасное направление отказа — трафик уходит
в туннель и там умирает, наружу мимо VPN не течёт.

Строгий режим (гасить кокпит, если туннель пропал на ходу) — закомментированный `BindsTo=` на
device-юнит `sys-subsystem-net-devices-singbox_tun.device` в `[Unit]`. По умолчанию выключен:
при коротком моргании туннеля веб-интерфейс отвалится и оборвёт открытые в нём чаты-агенты.

## Ромб «Песочница» на графе — статус из реальности, не из цепочки

Прогресс сборки стенда пишется в `state/tNNNN.stage` («время|шаг/всего|подпись», 11 шагов,
клон данных — самый долгий). Раньше ромб красился «done», как только тронут любой этап цепочки,
и клик показывал «этап пройден» во время сборки. Теперь `getTaskGraph` выводит статус честно:
порты в env есть → done; идёт сборка при живом демоне → run; демон умер посреди сборки → fail;
пока портов нет, футер карточки конвейера показывает «стенд строится · N/11 · подпись шага».

**Дыра в этой честности (закрыта 27.07.2026).** Все три ветки выше опираются на `tNNNN.stage`.
Если файла нет — статус падал обратно на догадку `computeNodeStatuses` («тронут любой этап
цепочки → песочница done»), и упавший стенд горел ЗЕЛЁНЫМ. Стенда могло не быть вовсе,
а карточка показывала пройденную песочницу и «○ стоит» без причины.

Файл пропадал не случайно: isolated-профиль связывал state прогона симлинком, `up.sh`
снимал ссылку через `rm -f .stage` и писал прогресс обычным файлом, а lifecycle hook после
подъёма повторно создавал симлинк через `ln -sfn`. Он затирал и файл, и строку
`FAILED|подъём упал`, которую кладёт trap. Отметка о падении уничтожалась ровно тогда,
когда была нужна.

Починено с двух сторон: lifecycle hook больше не подменяет настоящий файл ссылкой, а
`getTaskGraph` при отсутствии `.stage` смотрит на журнал (`detectStall`) — встали на подъёме
стенда → ромб `fail`. Статус `fail` до этого доезжал до схемы, но не имел ни метки, ни стиля:
добавлены `MARKS.fail = '✗'` и `.ns-fail`.

**Чинить упавший стенд тоже было нечем (закрыто 27.07.2026).** Падение стало видно, но
единственная кнопка про стенд — «снести стенд» — показывается по известному порту фронта,
а после провала подъёма порта нет: карточка сообщала о затыке и не предлагала выхода.
Отдельной «пересборки стенда» в движке не существует (песочница строится ВНУТРИ прогона),
поэтому `POST /api/tasks/:id/sandbox/retry` делает два шага: `down.sh` (остатки упавшей
попытки — иначе новый подъём падает на гарде «схема db_tNNNN уже существует») и
`startPipeline` — тот же helper, что и у `launch`, режим `resume`. Кнопка живёт
в самой плашке затыка при `stall.stage === 'SANDBOX'`. Вывод сноса возвращается всегда
(`downOutput`): в нём видна причина, по которой подъём упадёт снова.

**Снос из кокпита уносит и worktree задачи (закрыто 03.08.2026).** `down.sh` берёг грязный
worktree («есть незакоммиченные изменения — worktree ОСТАВЛЕН»), а в песочнице задачи работа
незакоммичена ВСЕГДА: агент этапа не коммитит. Значит снос из интерфейса всегда получался
половинчатым — контейнеры, схемы и `t<id>.env` исчезали, каталоги оставались, и следующий
запуск видел состояние `partial` («обнаружена частично созданная песочница; автоматическое
удаление запрещено»), вставая с кодом 75 ещё до первого агента. После сноса стенда и
повторного запуска получался `STALLED_HUMAN=1` с пустым журналом попытки, что снаружи
выглядело как мгновенное падение исполнителя.

Оба кокпитных пути (`sandbox/down` и `sandbox/retry`) сначала закрывают попытку (`abandon`),
то есть работа этапа уже ничья — поэтому они зовут `down.sh` с `FACTORY_DOWN_WORKTREE=force`.
Профиль перед удалением кладёт снимок незакоммиченного в `~/.factory/state/archive/`
(`t<id>.<репозиторий>-<worktree>.patch`, `git add -A` + `git diff --cached --binary`,
накатывается обратно `git apply`) и сносит worktree, только если снимок удался. Ручной
`down.sh` из терминала остаётся бережным (`keep`) — принудительный режим включает лишь
тот, кто нажал кнопку.

В имя патча входит и репозиторий: worktree разных репозиториев могут называться одинаково
(`route-worktree-t<id>`), и при использовании одного basename снимок `repo-a` затирал
снимок `repo-b`. Занятое имя теперь не перезаписывается, а получает индекс (`.2.patch`).

## Колонка чата без `min-width: 0` — длинная команда выталкивает кнопки за экран

**Где:** `web/src/views/chat/ChatSession.vue` (`.cs`), проявляется на странице «Чаты»
(`ChatsView`: `.stage :deep(.cs) { flex: 1 }`).

Флекс-элемент по умолчанию имеет `min-width: auto` — он НЕ сжимается ниже min-content своего
содержимого. Одна длинная неразрывная строка (команда `python3 -c "…"` во всплывашке разрешения
или в ленте шагов) раздувала всю колонку чата: при окне 1400 её ширина становилась 1540, и кнопки
«Разрешить/Отклонить» уезжали за правый край. Коварство в том, что `document.scrollWidth`
переполнения НЕ показывает — страница не скроллится, содержимое просто обрезано, и со стороны
выглядит как «кнопок нет».

Лечится `min-width: 0` на `.cs` (плюс `overflow: hidden` на самой плашке). Проверять замером
`getBoundingClientRect().right` кнопки против ширины окна, а не глазами по скриншоту.

Там же: длинные команды показываем блоком с `white-space: pre-wrap` + `overflow-wrap: anywhere`
и `max-height` со скроллом, а не одной строкой с многоточием — решение о разрешении принимают
по тому, что видно целиком.

**Тот же обрез повторился с другой стороны — кнопками варианта** (2026-08-07). У ACP-плана Kimi
подписи вариантов не слова, а фразы («Approve plan and continue…»), и ряд кнопок в шапке плашки
стоял `flex: none` с `flex-wrap: wrap`. Обёртка при этом не срабатывает НИКОГДА: не сжимаясь,
контейнер получает ширину `max-content`, переносить внутри себя ему нечего. Замер в плавающей
панели (колонка 360 px): `perm.scrollWidth` 475 против `clientWidth` 345, правый край кнопки
«Revise plan» — 475, то есть она целиком за краем и обрезана `overflow: hidden` плашки. Страница
опять не скроллится, поэтому со стороны это «у плана всего одна кнопка».

Лечится тремя правками разом: перенос разрешён самому ряду (`.p-row { flex-wrap: wrap }` —
не влезли, значит кнопки уезжают на вторую строку, оставаясь наверху), ряд кнопок получает право
сжиматься (`flex: 0 1 auto; min-width: 0`), а сама кнопка — `max-width: 100%` с переносом текста.
Проверено замером на 360 / 420 / 1400: `scrollWidth == clientWidth`, правый край каждой кнопки
внутри колонки. Happy-dom это не ловит (в нём нет раскладки) — только настоящий headless Chrome.

## Тултип живёт в `<body>`: `:deep(.ht-tip)` из вызывающего компонента больше не работает

**Где:** `web/src/shared/ui/HelpTip.vue` — единственный тултип кокпита.

Пока подсказка была `position: absolute` внутри страницы, она пряталась: скролл-контейнер
(`.content` шелла, списки, панели чата) обрезал её по своей границе — у полей в верхней части
формы «Агентов» верхние строки уходили под топбар, — а модалки (`z-index: 100/120`) перекрывали.
Латали это точечным пропом `fixed`, то есть каждый вызов должен был сам знать, что он в
скролл-контейнере. Теперь тултип ВСЕГДА телепортируется в `<body>` и позиционируется от вьюпорта
(`z-index: 300` — выше модалок и баннеров): обрезать его нечем, а `place()` поджимает координаты
к экрану и разворачивает подсказку вниз, если сверху не влезает.

Плата: тултип больше не потомок компонента-вызова, поэтому его scoped-CSS (`.my-tip :deep(.ht-tip)`)
мимо — селектор ищет потомка. Ширину и отступы конкретной подсказки задавать пропом
`:tip-style="{ maxWidth: '400px' }"`; `:deep(.ht-tr)` (триггер) по-прежнему работает — он остался
на месте. Положение пересчитывается на скролле, ресайзе и через `ResizeObserver` на самой
подсказке: содержимое всплывашек догружается уже раскрытым (полосы лимитов исполнителей),
и без пересчёта раскрытая вверх подсказка наползала бы на триггер.

Проверять замером, а не глазами: навести и сверить `getBoundingClientRect()` с вьюпортом плюс
`document.elementFromPoint` по центру — перекрытие на скриншоте видно не всегда.

## «Кокпит завис, все запросы (ожидает)» = съеден лимит соединений браузера

Симптом: все fetch в Network стоят «(ожидает)» вечно, SSE `/api/events` при этом жив,
сервер отвечает curl'ом за миллисекунды. Причина: HTTP/1.1 — максимум 6 соединений на
хост во всём браузере; каждый лишний EventSource занимает соединение НАВСЕГДА. Было:
useSse() открывал свой EventSource на каждый вызов (AppShell + PipelineView + пермишены
чата = 3 на вкладку), две вкладки кокпита выедали весь пул. Правило: ОДИН EventSource на
вкладку — синглтон в composables/useSse.js (sseSubscribe), новые SSE-события добавлять
в его EVENT_NAMES, свои EventSource НЕ создавать. Смежное: GET в api-client — таймаут
30с + один повтор (docker-манипуляции со стендами рвут сеть, Chrome вешает fetch).

## «Переписка потёрлась» = PUT истории упёрся в лимит тела, и клиент ретраил молча

Симптом: остановил ход или перезагрузил страницу «Чаты» — и разговор откатился к какому-то
моменту в прошлом. В логах сервера при этом каждые 15 секунд `FST_ERR_CTP_BODY_TOO_LARGE`
(413) на `PUT /api/chat/store`.

Причина: клиент сохранял **весь стор одним телом** — все чаты, включая архив (до 50 штук),
а вместе с ними ленты шагов (`steps` — 70%+ объёма). Когда сумма перевалила за дефолтный
`bodyLimit` fastify (1 МБ), сервер стал отвергать запись целиком. Клиент уходил в ретрай
с паузой 15 с и не сообщал об этом никак — история просто переставала сохраняться, а жила
только в памяти вкладки и в обрезанном localStorage-снимке.

Правила:
- запись истории — **точечная**: одно тело = один чат (`PUT /api/chat/store/chat`), мета
  отдельно. Объём запроса не должен зависеть от того, сколько чатов накоплено;
- `bodyLimit` задан явно в `app.js` (64 МБ) — как страховка, а не как решение;
- **неудача записи обязана быть видимой**: `chat.saveError` → плашка над лентой + одно
  уведомление. Тихий ретрай здесь означает потерю данных, о которой узнают слишком поздно.

Смежное: `sessionId` оборванного хода. Executor ловит `session_id` **из потока** (он есть
в каждом событии, начиная с `init`), а не только из финального `result`, — у остановленного
хода результата нет, и раньше в чат возвращался входной id (у первого хода — пустой).
Клиент затирал им сохранённый, следующий вопрос уходил без `--resume`, и агент не помнил
разговора. Пустой id клиент теперь не принимает.

## «Кольцо контекста врёт» = цифра менялась раз в ход, а CLI сжимал контекст посреди хода

Симптом (замер на живом чате, 2026-08-08): кольцо показывает **448 417** токенов и горит
красным, хотя на самом деле в контексте **126 135**. Втрое, причём в сторону «всё плохо»:
человек видит красное и жмёт сжатие, которое сейчас не нужно.

Причин две, и складываются они ровно в это число:

- **`contextTokens` возвращался ОДИН раз — вместе с ответом хода.** Пока ходы короткие,
  разница незаметна. Но ход бывает длиной в час, и всё это время кольцо показывает цифру
  с конца ПРОШЛОГО хода;
- **собственный автокомпакт CLI срабатывает НА ГРАНИЦЕ хода.** Порог (кокпит задаёт его
  через `CLAUDE_CODE_AUTO_COMPACT_WINDOW`) CLI проверяет перед первым обращением к модели,
  поэтому сжатие случается в начале хода, а весь остаток идёт уже по сжатому контексту.
  В том замере: `compact_boundary` с `preTokens: 451421`, `durationMs: 62912`, дальше
  обращения к модели идут с входом 126 135 → 137 645. То есть кольцо весь ход светилось
  красным по контексту, которого уже не было.

Правила:

- **живой замер идёт вторым аргументом `onProgress`** (`{contextTokens}`) → SSE
  `chat-progress` → рантайм-поле `liveContext` → кольцо, пока `sending`. Рантайм —
  принципиально: `contextTokens` уходит в историю (`slimOf`), и запись на каждое обращение
  к модели стоила бы дебаунс-PUT всего чата (этим путём уже ловили фризы при наборе, см.
  раздел выше). После F5 замер поднимает `GET /api/chat/active`;
- **необязательность аргумента — часть контракта**: codex/kimi/ollama зовут `onProgress`
  одним аргументом, и от них правка не требует ничего. Кто замера не даёт — кольцо живёт
  цифрой прошлого хода, как раньше;
- **границу компакта обязано быть видно в ленте** (`note` «Контекст сжат: CLI сжал его сам,
  по порогу (было N ток.)»). Падение цифры втрое посреди хода без объяснения читается ровно
  как «кольцо врёт» — с этой жалобы всё и началось;
- **`lastTurnInput` на самой границе не трогаем.** Новый размер сообщит ближайшее обращение
  к модели; обнули мы его по событию — и между границей и этим обращением кольцо показывало
  бы пустоту;
- **`contextWindow` claude не сообщает НИГДЕ** — ни в потоке, ни в `result`; проверено и
  поиском по бинарю CLI. Окно берётся из каталога моделей, и выдумывать ему источник
  в потоке не нужно.

Проверки — `tests/server/chat-live-context.test.js` (фальшивый CLI: два обращения к модели
с границей компакта между ними) и `tests/web/chat-live-context.test.js`.

### Вторая серия того же: цифра честная, а форма кольца врёт

Симптом (2026-08-09, чат «HTTP парсер», Opus 5 с окном 1M): CLI ругается «Autocompact is
thrashing» и сжимает контекст по кругу, а кольцо почти пустое — «места ещё дофига».
Замер: 168 158 токенов, в сессии **49 событий `compact_boundary` подряд** по 2–4 минуты
каждое.

Причина — **две разные шкалы у одного индикатора**. Цвет брался от практического порога
`ctxLimit = min(chatAutoCompactWindow, 80% окна)` = 200 000 (то есть 84% — жёлтый), а дуга
и подсказка — от окна модели: 168 158 из 1 000 000 = 17%, кольцо залито на шестую часть.
На окне 200k эти шкалы почти совпадали и расхождения не было видно; на 1M они разъехались
впятеро. **Человек читает форму, а не оттенок** — почти пустое кольцо перевешивает жёлтый
цвет, а подсказка «из 1 000 000» добивает: читается как огромный запас там, где до сжатия
остались проценты.

Правило: **дуга, процент, цвет и подсказка считаются от одного `ctxLimit`.** Окно модели
остаётся в подсказке справочной строкой — как основная шкала оно обещает запас, которого
нет. Сторож — `tests/web/chat-task-tooltip.component.test.js` (проверяет, что при 168k/1M
с порогом 200k кольцо и жёлтое, и залито на 84%, а не на 17%).

Второе, что вскрыл тот же замер, и это уже не про UI: **порог 200k на окне 1M сам по себе
устраивает трэшинг.** Сжатие срабатывает на ~167k, следующие пару ходов набивают контекст
обратно, и цикл повторяется; `cache_read=20 773` против `cache_create=147 383` в хвосте
сессии означает, что кэш промпта не переиспользуется вовсе. Настройка, заведённая ради
экономии (кэш перестаёт совпадать выше ~250k), на модели с большим окном жжёт и время,
и деньги. Порог — решение человека в «Настройки → Запуски», кокпит его не подкручивает
сам; предупреждение CLI про «слишком большой tool output» тут вторично.

## Фризы при наборе в чате = черновик сохранялся тем же тяжёлым путём, что и переписка

Симптом: печатаешь сообщение на странице «Чаты», и вкладка периодически замирает на
доли секунды. Похоже на поллинг, но поллинг тут ни при чём — блокируется главный поток.
Замер (`PerformanceObserver({entryTypes:['longtask']})` на живой странице, история 247 чатов):
**одна задача в 709 мс ровно на паузе в наборе**, то есть на срабатывании дебаунса черновика.

Причина — цепочка, в которой каждое звено само по себе выглядит дешёвым:
`watch(input)` (400 мс) → `chat.setDraft()` → `_persist()` (300 мс) → `write()`, а `write()`
синхронно (а) сериализует ВСЮ историю в страховочный снимок localStorage, (б) кладёт его
через `localStorage.setItem`, ловит `QuotaExceededError` и сериализует ещё раз урезанную
версию, (в) сериализует каждый чат отдельно, чтобы сравнить с картой `sentChats` и понять,
что реально изменилось. На реальной базе это 25 МБ строк, из которых **92% — ленты шагов**
(`msg.steps`), причём для всех трёх задач эти ленты не нужны вовсе.

Правила:

- **шаги не участвуют в служебных копиях.** Снимок пишется без `msg.steps` (25 МБ → 0.6 МБ),
  а «уехало ли на сервер» считается по отпечатку `fingerprintOf`, где лента заменена своим
  числом: шаги append-only и появляются вместе со своим сообщением, поэтому счётчика хватает.
  На сервер шаги едут как обычно — экономим на служебных копиях, не на данных;
- **черновик снимок не пишет вовсе** (`_persist(false, { snapshot: false })`). Снимок закрывает
  окно между «ответ пришёл» и «PUT долетел»; у черновика терять нечего — текст и так перед
  глазами. Флаг `needSnapshot` при этом **накапливается**, а не берётся у последнего вызова:
  иначе правка черновика, попавшая в те же 300 мс дебаунса, отменила бы снимок только что
  полученного ответа;
- **fallback по квоте режет по чатам, а не по сообщениям**: обрезка «последние 30 сообщений
  в каждом чате» оставляла в снимке все 247 чатов и в квоту не влезала, а урезанную версию
  писала второй сериализацией — то есть дорожала ровно там, где должна была спасать.

Проверка: `tests/web/chat-draft-persist.test.js` (снимок без шагов, черновик снимок не пишет,
отпечаток ловит дописанный шаг) плюс повторный замер на живой странице — после правок
длинных задач при наборе **ноль**.

Мораль на будущее: путь, по которому идёт КАЖДОЕ нажатие клавиши, не имеет права зависеть
от размера всей истории. Если дебаунс тянет за собой сериализацию стора — фриз лишь вопрос
того, сколько чатов накопится.

## Маршрут встал «код 78» на узле, который отработал = вердикт command-узла не по контракту

Симптом: конвейер стоит, в `t<TASK>.pipeline` узел числится `running`, `ORCH_PID` пуст,
`STALLED_HUMAN=1`. Нажатие «продолжить» в UI не двигает ничего — в журнале появляется ещё одна
пара строк и всё:

```text
route: узел <имя_узла>: подготовка к исполнению
route: dispatcher остановлен fail-closed (код 78)
```

Причина: `executor=command` исполняется хостом, а его JSON-вердикт движок разбирает уже ПОСЛЕ
работы скрипта. Скрипт успел записать свои артефакты, но форма вердикта не по контракту
(`docs/engine/PROFILE-CONTRACT.md`, раздел про `executor=command`) — парсер
`_route_v2_command_result` отвечает кодом 78, узел не коммитится. Отказ детерминированный:
`resume` упирается в то же место, пока не исправлен скрипт профиля.

Чем отличить от «агент не отчитался»: `t<TASK>.route-v2.log` **пуст** (модель не звалась вовсе),
а артефакты узла на диске свежие, с временем последней попытки. Проверить форму вердикта
напрямую, не гоняя маршрут:

```bash
source engine/lib/route-runtime.sh; _route_v2_command_result /путь/к/result.json; echo $?
```

Реальный случай — маршрут с кворумом нескольких мнений: выпал один провайдер из трёх, кворум
собрался, агрегирующий command-узел посчитал ранги и записал сводки — но вернул `done` с
информационным `findings` про отсутствующего участника. Движок принимает `findings` только при
`failed`, поэтому недоступность **одного** исполнителя останавливала весь конвейер. Там же
пряталась вторая мина: при двух выпавших вердикт `failed` нёс два finding с одинаковым `id` —
движок отвергает и дубли тоже.

## Задача в UI «замирает»: SSE смотрит не в runtime root

Симптом: этап Скептик закончился, конвейер штатно встал у ворот
плана, чип «ждут тебя» в навигации зажёгся — а на схеме Скептик горел работой дальше, до
ручного F5.

Причина исторического инцидента: SSE watcher и движок смотрели в разные state roots,
поэтому запись `GATE_PLAN=waiting` не порождала `state-change`, а страница конвейера
обновлялась только по этому событию. Чип опрашивал состояние отдельно — отсюда
расхождение «чип горит, граф врёт».

После cutover runtime root один: `config.stateDir`; SSE принимает ровно его и не сканирует
исторические каталоги. Любой новый writer обязан использовать тот же root. Проверка —
`tests/server/sse-state.test.js`.

## «Нет событий N мин» на штатной паузе = свежесть считали по чужому `ACTIVE_RUN`

Симптом: конвейер стоит у ворот, всё в порядке, а в модалке этапа — «нет событий 676 мин».
Читается как «агент завис» и толкает человека дёргать прогон.

Причина: `ACTIVE_RUN_<STAGE>` в реестре — **ещё и fencing-токен**, его намеренно не чистят
(сброс эпохи воскресил бы убитый ход прошлой попытки). `readActivity` же брала любой
непустой ключ и показывала свежесть его журнала. Единственным непустым мог остаться
`ACTIVE_RUN_BUILD` от **отменённой позавчерашней попытки** — отсюда 676 минут. Исторические
пути (`ACTIVE_DIR`/`JOURNAL`, `logs/t<TASK>.orch.log`) не спасают, а подменяют цифру
свежестью чужого запуска.

Правила:
- активность считается **только** по ходу, чей этап прямо сейчас `running`;
- для executable route-attempt исторические источники (`ACTIVE_DIR`, `orch.log`) не используются:
  каждый ход обязан зарегистрировать `ACTIVE_RUN`, и его отсутствие означает
  «сейчас никто не пишет», а не «поищи где-нибудь ещё»;
- нет активного хода → `journalAgeSec: null`, а не цифра. Придуманная цифра хуже прочерка.

## «Агент пишет» над намертво вставшим агентом = свежесть журнала считали по mtime

Обратная беда той же плашки, и куда дороже. В одном прогоне браузерная приёмка трижды подряд
простояла по 30 минут на мёртвой странице (стенд отдавали по внешнему адресу мозга,
браузер в контейнере до него не доставал). Всё это время кокпит писал «агент пишет»:
конвейер выглядел работающим, ворота не поднимались, `detectStall` молчал — и заметить
полтора потерянных часа было нечем, кроме сгоревшего лимита этапа постфактум.

Причина: **Claude CLI печатает хартбит каждые 30 секунд на каждый висящий вызов**
(`{"type":"tool_progress","heartbeat":true,"tool_name":…,"elapsed_time_seconds":…}`,
и `timestamp` у такой записи нет). Файл `events.jsonl` от этого всё время свежий, а
осмысленного вывода в нём нет ни строчки. `detectStall` сюда не дотягивается **по
устройству**: он отвечает на «почему конвейер СТОИТ» и возвращает `null`, пока демон жив
и флага остановки нет, — а зависший агент формально работает.

Правила:
- молчание считает `readRunSilence` (`server/src/lib/factory-cli.js`) по последней
  **осмысленной** записи: идём с конца журнала, пока идут хартбиты. Длительность берём
  из самого хартбита — он её и сообщает (`elapsed_time_seconds`), причём по **старшему**
  из висящих вызовов: модель просит инструменты пачкой;
- исполнитель без хартбитов (Codex) даёт хвост из обычных событий, и ответ вырождается в
  прежний возраст файла — от нового исполнителя правило не требует ничего;
- имя висящего вызова обязано доезжать до человека (`silentTool` → «нет событий 28 мин
  (mcp__playwright__browser_click)»): десять минут `Bash` — это сборка, полчаса
  playwright — мёртвый браузер;
- порог один на всех и живёт в настройках (prefs `runSilenceWindow`, дефолт 900 секунд):
  замер по всем прогонам на машине показал, что законное молчание упирается в 600 секунд
  (десятиминутный `Bash` в сборке), а зависший вызов — в потолок MCP, 1800 секунд.
  Сервер порог **не применяет**, отдаёт замер (`silence` в сводке задачи + `silenceWindow`
  в `/api/tasks`): считать «это уже висяк» обязаны одинаково чип, оповещение и карточка;
- **кокпит только зовёт человека, ничего не убивает.** Автоглушение висящего хода — это
  снос работы по косвенному признаку; лимит этапа и так стоит на страже.

Проверки — `tests/server/factory-activity.test.js`, `tests/web/agent-activity.test.js`.

## Модалка этапа переживает сам этап — статус в ней обязан идти за графом

`openStage()` копирует `node.status` и `nodeMeta` в объект модалки. Граф за спиной
обновляется по `state-change`, а копия — нет: открытая на бегущем узле модалка навсегда
оставалась «выполняется сейчас» и продолжала опрашивать `/activity` уже закончившегося
этапа: тот уже закрылся, а модалка всё ещё показывала работу.

Правило: всё, что модалка показывает о состоянии узла, читается из живого графа
(`stageLive` в `PipelineView.vue`). Смена статуса на не-`run` останавливает опрос и гасит
чип активности; мета обновляется всегда — этап дописывает её и после завершения.

## Доделанный маршрут в виде «✖ оборвалась» = сторож ловил формулировку финала v1

`detectStall` (`server/src/lib/stall.js`) отличает нормальный финал от молчаливого
обрыва **по последней строке** `logs/tNNNN.stages.log`. Строка была одна — «конвейер
завершён» из v1. Движок route-v2 пишет другую — «маршрут завершён; SHIP и RETRO
подтверждены» (`engine/bin/factory`), и совпадения не было ни разу: каждый доведённый
до конца прогон показывался как «✖ оборвалась» с советом «запусти заново» поверх уже
закрытой попытки и `RESULT=completed`.

Почему обманывает: `WF_STATUS` в v2 ставится в `running` один раз и больше не
меняется — терминальность несёт attempt-ledger, а не проекция. Так что признаков
«всё хорошо» в реестре сторож не видит, вся развилка висит на одной строке журнала.

Правило: **формулировка финальной строки движка — контракт, а не текст.** Меняешь её
в `engine/bin/factory` — меняй `FINISHED` в `stall.js` тем же заходом. Близкая строка
«маршрут завершён, **но** shared lease не освобождён» под правило не подпадает
намеренно: занятая лиза блокирует следующий прогон по тем же ресурсам, и человек
обязан её увидеть. Поэтому в шаблоне точка с запятой значима.

## Выполненный прогон shared-профиля не уходил с экрана: закрывать было нечем

Кокпит **не архивирует задачу сам** — это осознанно: пока прогон на экране, у него
живые `report.md`, `plan.md` и граф, а архив (`~/.factory/state/archive/`) человек не
листает. Реестр в архив переносит человек кнопкой, и кнопок для этого две:

| у задачи есть | кнопка | что делает |
|---|---|---|
| своя песочница | «⏏ снести стенд» | сносит стенд и архивирует прогон заодно |
| стенда нет | «✓ закрыть задачу» | только архивирует (плюс удаляет пустую ветку) |

Третий случай в это деление не попадал: **shared checkout с внешним стендом**
(`WORKSPACE_MODE=shared` / `STAND_OWNERSHIP=external`).
Сносить чужой стенд кокпиту запрещено (`shared_workspace_lifecycle_forbidden`), значит
первой кнопки нет по определению; а вторая пряталась по условию «нет порта фронта» —
и в shared-режиме порт есть ВСЕГДА, потому что стенд общий и живёт вне задачи.
Доведённый до конца прогон висел на экране навсегда: убрать его было нечем ни одной
кнопкой, ни одним API.

Ловушка в самом условии: «есть порт» молча означало «есть НАША песочница». Правило —
**закрытие разрешено, когда кокпиту нечего сносить: стенда нет ЛИБО стенд не его**
(`canCloseTask` в `PipelineView.vue`). Серверный `/api/tasks/:id/close` shared-режим
умел с самого начала: пропускает гард живого стенда, не трогает ветки
(branch lifecycle к общему рабочему дереву не применяется даже read-only пробой) и
только переносит проекцию реестра в архив.

## «Перейти сюда» без пояснения = агент повторит ту же ошибку

Кнопка возврата на узел писала в журнал попытки одну причину — и та никуда дальше не
шла: агент входил в узел с тем же заданием, что и в прошлый раз. Свободный текст доезжал
до агента только через решение ворот; разбор приходилось класть в черновик хода
(`t<TASK>.tests.checkpoint.md`) руками — то есть мимо журнала, который и есть источник
правды.

Теперь причина возврата и есть указание агенту: поле под кнопками в модалке этапа уезжает
тем же запросом (`POST /api/tasks/:id/stage/:key/running`, тело `{comment}`), сервер кладёт
его причиной события `human-rewind`, движок подмешивает отдельным блоком в промпт того
захода, ради которого узел вернули (детали и правила гашения — `docs/engine/ENGINE.md`,
«Указание человека при возврате на узел»).

Тонкости, которые стоили отладки:

- **Своей кнопки «отправить» у поля нет и быть не должно.** Указание — часть возврата, а не
  отдельное сообщение: агент читает его на входе в узел, писать «в работающий узел» некуда.
  Поэтому поле стоит своей секцией рядом с «▶ Перейти сюда», а не в ряду с чатом и диффом:
  человеку должно быть видно, какая кнопка его отправит.
- **Поле только у исполняемой route-attempt и не у ворот.** Исторический реестр read-only;
  у ворот своё поле, и оно принадлежит отклонению (см. следующий раздел). Текст у них
  раздельный: общий ref переносил бы набранное из одного смысла в другой.
- **Текст санируется на сервере.** Движок валидирует причину жёстко (1–20000 символов,
  переводы строк можно, прочие управляющие нельзя), поэтому вставленный из редактора текст
  с `\r` или табами ронял `goto` с 409 уже после того, как человек его написал. Санитайзер
  `humanComment` (`server/src/modules/factory/index.js`) чинит только заведомо безобидное —
  `\r\n` → `\n`, управляющие → пробел, хвостовые пробелы; **длину он не режет, а отвергает**
  (400 `comment_too_long`).
- **Возврат сбрасывает не только этот узел, но и весь хвост маршрута за ним** (`goto`
  режет `chain[index:]`). Подтверждение обязано говорить именно это: прежнее
  «Принудительно: этап → running?» об этом молчало.

## Поле комментария у ворот обещало доставку, которой при принятии нет

Симптом со стороны человека: у ворот всегда висело поле «Комментарий» над кнопками
«Принять»/«Отклонить». Выглядело оно как канал к агенту при любом решении — в него писали
разбор и жали «Принять». Текст не доезжал никуда.

Так устроен движок, и это правильно: `route_v2_gate_decide` обнуляет `reject_feedback` на
любом исходе, кроме `rejected` (`[[ "$outcome" == rejected ]] || reject_feedback=`). Принятые
ворота ведут маршрут ДАЛЬШЕ, и узла, чей агент прочитал бы указание, у них нет — доставлять
некуда. Гейт `_route_v2_gate_feedback_guard` по той же причине **отказывает** непустому
rejected-пояснению, когда возврат ведёт в узел с `executor != agent`.

Хуже, чем просто «текст пропал»: `v2_gate_commit` проекцию реестра пишет в обоих случаях, то
есть комментарий при принятии оседает в `GATE_*_COMMENT` и потом показывается в модалке узла.
Со старой подписью «Замечание» это выглядело как доставленное агенту замечание — прогоны,
сделанные до правки, такие записи ещё содержат.

Правила:

- **поле принадлежит отклонению, а не воротам вообще**: решение делится на два шага, поле
  раскрывается кнопкой «✗ Отклонить». При «Принять» комментарий не отправляется вовсе —
  пустое поле честнее текста, который движок молча выбросит;
- **подпись у `nodeMeta.comment` зависит от узла и статуса** (`stageCommentLabel` в
  `PipelineView.vue`): у принятых ворот она прямо говорит, что агенту текст не уходил;
- **отказ гейта показывается выходом, а не кодом**: сообщение движка «нельзя доставить»
  означает «возврат ведёт не к агенту», и модалка называет оба пути — отклонить без текста
  либо сначала вернуть конвейер кнопкой «▶ Перейти сюда» на узел нужного агента.

Проверки — `tests/web/pipeline-gate-decision.component.test.js`.

## Замечание человека доезжало до агента огрызком: две независимые обрезки подряд

Симптом: человек отклоняет ворота развёрнутым разбором (что принято, что чинить, что
запрещено трогать, прод-числа), а вернувшийся агент действует так, будто читал только первый
абзац — доопределяет остальное сам и уходит не туда. Ни отказа, ни предупреждения: текст
принимался с виду целиком.

Резали в двух местах, независимо друг от друга:

- **кокпит**, в обеих ручках решения — `String(comment).replace(/\n/g, ' ').slice(0, 500)`;
  многострочный разбор схлопывался в одну строку и рубился по 500-му символу;
- **движок**, `bin/factory` перед валидацией — `"${GATE_COMMENT//$'\n'/ }"`, а сам валидатор
  `_attempt_state_reason` держал `REASON_LIMIT = 500` и запрещал ВСЕ управляющие, включая `\n`.

То есть схлопывание стояло именно затем, чтобы текст прошёл валидатор, — обрезка обслуживала
обрезку. Обоснованием служило «разбор кладётся в файл, в причину идёт ссылка», но агент файл
по ссылке не открывает, пока промпт прямо не велит; на деле ссылка означала «указание
потеряно».

Как сейчас: потолок 20000 символов, `\n` разрешён на всём пути (валидатор `attempt-state.sh`,
валидатор чтения событий `attempt-stage-state.sh`, `bin/factory`), цитата в промпте
префиксуется построчно (`_stage_human_note_block`: `sed 's/^/> /'`), переполнение — 400
`comment_too_long` вместо тихой обрезки. В построчный реестр `t<TASK>.pipeline` (парсится awk,
многострочное значение его сломает) идёт выжимка на 300 символов, `_gate_comment_digest`.

Осталось как есть и обрезкой НЕ является: при **`approve`** комментарий не доезжает до агента
вообще — `human_rewind_note` читает указание только у исхода `rejected`, у принятых ворот нет
узла-получателя (см. раздел выше). Канал «принять причину и приложить указания к реализации»
в движке отсутствует; обходной путь — вписать блок в раздел `## Карта задачи` файла
`t<TASK>.recon.md`, движок вклеивает его в промпт **каждого** узла маршрута
(`_stage_task_map_block`, потолок 16 КБ, режется конец).

Проверки — `tests/server/factory-gate-cursor.test.js` (доставка многострочного замечания и
отказ на переполнении), `tests/engine/unit/attempt-state.sh`.

## «Конвейер встал» при живом этапе: правило линейности гасило сам фронт

Симптом: схема конвейера показывает всё погасшим — ни одного активного узла, — а этап в это
время работает, демон жив, агент пишет в лог. Человек второй раз подряд считает прогон
умершим и идёт его «чинить».

Причина в `computeNodeStatuses` (`server/src/lib/factory-graph.js`). Реестр — вторичная
проекция, и в нём **легально** остаётся `running` у узла, чей заход прервали: TERM демону,
перезапуск хоста, убитый таймаутом процесс. Тогда активных узлов становится два, и включается
правило линейности «оставить более поздний — он и есть реальный фронт». Написано оно было так:

```js
chain.forEach((n, i) => { if (['run', 'wait'].includes(st[n])) st[n] = i < keep ? 'done' : 'pending'; });
```

При `i === keep` условие `i < keep` ложно, и узел, ради сохранения которого правило и
затевалось, уезжал в `pending` вместе с остальными. Гасли **оба**: и застрявший, и живой.

Хуже того, правило «более поздний» ловит только случай ДВУХ активных. Когда призрак остаётся
один (маршрут ушёл вперёд, а идущий этап на повторном заходе всё ещё несёт `done` от прошлого
круга), схема уверенно показывала работу на мёртвом узле — «повис на chairman» при живом build.

Поэтому опорная точка теперь — **курсор trusted-журнала**, а не проекция:
`computeNodeStatuses` принимает `cursorNode` и расставляет фронт по нему (прежнее правило
остаётся запасным — для исторических реестров и нечитаемого ledger), а `getTaskGraph`
досвечивает сам узел курсора: `ready` при живом демоне → `run`, `paused` → `wait`. Реестр
статус узла переписывает по завершении этапа, поэтому без досветки идущий заход не горел бы
вовсе. Остановку поверх этого по-прежнему красит `detectStall`.

Общее правило: «что показывает схема» и «где на самом деле стоит маршрут» — два разных
источника, и при расхождении верен журнал. Проверять так:

```bash
grep -E '^(ORCH_PID|WF_STATUS)=' ~/.factory/state/t<TASK>.pipeline
systemctl --user is-active factory-t<TASK>.service
tail -5 ~/.factory/state/logs/t<TASK>.stages.log
```

Проверки — `tests/server/factory-graph-linearity.test.js`.

## Возврат курсора в зону instrument→proof ломал маршрут насмерть

Симптом: человек отклоняет ворота причины (или возвращает курсор на chairman), прогон
послушно переигрывает промежуточные узлы — по 10-12 минут каждый — и падает на `proof`
с `dispatcher остановлен fail-closed (код 78)`. Ни строки о причине. Возобновление повторяет
то же самое ровно с тем же результатом: 09.08.2026 так сгорели три захода подряд.

Топология: `instrument` открывает транзакцию инструментации и намеренно **не** закрывает её
(`_route_v2_transaction_after`: `if [[ "$node" != instrument ]]`), `proof` работает внутри неё
и закрывает за собой. Поэтому после первого прохода `proof` активной транзакции больше нет, а
переоткрыть её может только `instrument` — и он остаётся `done`, в reset возврата на
промежуточный узел не попадая (`goto` режет `chain[index:]`, а instrument стоит левее).
`_route_v2_transaction_before` для `proof` при закрытой транзакции отдаёт 78 — сознательный
fail-closed: открыть свою транзакцию значит получить дерево без инструментации и мерить не то.

Чинится не отменой fail-closed, а переносом отказа на момент решения человека:
`_route_v2_goto_transaction_guard` (`engine/lib/route-runtime.sh`) при `goto` проверяет, лежит
ли цель в зоне «после instrument, до proof включительно» при закрытой транзакции, и отказывает
кодом 75, называя оба выхода — вернуть на `instrument` (переиграется весь хвост за ним, включая
консилиум) либо вернуть за `proof`, на `translator` и дальше, оставив прошлое доказательство в
силе. Возврат на сам `instrument` разрешён всегда: он открывает транзакцию сам.

Маршрутов без пары instrument/proof гард не касается, и недоступный каталог маршрута в
ложный отказ не превращается.

Проверки — `tests/engine/unit/route-goto-transaction-guard.sh`.

## Старт route engine из кокпита: сервис возвращает 0 всегда, а отказ приходит позже

Три грабли, из-за которых «нажал запуск — вроде поехало», а на деле не поехало ничего.

- **Отказ движка невидим.** Прогон уезжает в transient-**сервис** (`factoryUnitArgs`),
  а не в `--scope`: `systemd-run` регистрирует юнит и возвращает 0 СРАЗУ, поэтому
  `child.on('exit')` рапортует успех даже при `die 78`. Вывод юнита поэтому пишется
  в файл (`--property=StandardOutput=append:<state>/t<id>.launch.log`), исход читается
  из состояния (`ORCH_PID` + `systemctl --user is-active`), а профиль и маршрут сверяются
  синхронным `factory check` ДО любых побочных эффектов. Иначе резервация слота висела бы
  все 45 минут TTL за прогон, которого не было.
- **Сервис не наследует окружение вызывающего.** Ни одной переменной: `FACTORY_SB_K`
  передаётся отдельным `--setenv`, иначе движок выберет слот сам — и вернётся гонка, из-за
  которой резервация вообще появилась. Каталоги состояния переменными НЕ передаются вовсе:
  у движка они аргументы (`--state-dir`, `--routes-dir`, `--control-dir`),
  а скрытого второго runtime root нет.
- **Тикет движок читает после подъёма стенда.** Кривая постановка обернулась бы отказом 78
  через 20–25 минут провижининга, поэтому кокпит валидирует её у себя (`lib/factory-ticket.js`,
  контрактный тест `tests/server/factory-ticket.test.js`): ровно шесть полей, непустые
  `title`/`description`/`sourceUrl`, `taskId` строкой, потолок файла 256 КиБ. Уточнения человека
  и комментарии трекера отдельных полей не имеют (объект exact) — они уезжают в конец
  `description`.

Коды отказа движка человеческим языком: **78** — контракт, аргументы или занятый лок
оркестратора; **73** — flock, уже активная попытка, мёртвый стенд при resume; **75** —
нужен человек: частично созданная песочница, вставшая транзакция, разошедшийся
контракт попытки ИЛИ устаревший CAS (узел ворот/курсора расходится с журналом).

**Немой runner preflight.** Раньше движок писал причину только через `v2_log` в
`logs/tNNNN.stages.log`, а Cockpit получал голый `err.message` от `execFile`: человек
видел командную строку с «код 1» и принимал отказ доступности runner-а за поломку ворот.
Теперь движок пишет в stderr и журнал typed-маркер
`FACTORY_ERROR=runner_preflight_unavailable RUNNERS=<id,…>`, а
`<state>/coverage/<профиль>/host.env` сохраняет список `UNAVAILABLE_RUNNERS`.
Cockpit возвращает `error=runner_preflight_unavailable`, массив `runners` и человеческий
текст. Сам **код 1 ничего такого не доказывает**: shell может вернуть его по другим
причинам, типизация разрешена только по маркеру.

С 04.08.2026 `gate --commit-only` preflight не проходит вовсе: решение человека агентов
не запускает, поэтому доступность CLI к CAS ворот отношения не имеет. `start` и `resume`
остаются fail-closed. У Kimi номер версии отдельно перестал быть гейтом: обновление
фиксируется в metadata запуска, совместимость определяется контрактом, а незнакомая
ошибка остаётся `unknown` без автоматического повтора стадии.

**Тот же урок стоил четвёртой немой попытки на `resume`.** Проверку «поехало ли» имел
только старт: `resumeRouteAttempt` считал успехом регистрацию юнита и отвечал
`{ok:true}`, а `goto`/ворота возвращали 200 с полем `resumed:false`, которое UI ронял
на пол. При расхождении контракта профиля юнит умирал через две секунды
(код 75), и человек четыре раза жал «продолжить», не получая ни строчки. Теперь
продолжение **подтверждается** (`confirmRouteResume`): шесть секунд опроса живости
юнита, затем сверка `ATTEMPT_ID` + `ORCH_PID` из реестра, а причина берётся из журнала
этапов — только то, что дописано ПОСЛЕ нашего запуска (`readLogSince`, смещение
в символах: журнал русский). Живой `ORCH_PID` сам по себе ничего не доказывает —
движок пишет его ДО проверки контракта. `resumed:false` теперь виден человеку плашкой
«Записано, но прогон не поехал: …» (`PipelineView.warnIfNotResumed`): решение в журнале
попытки лежит, а прогон стоит — это разные вещи, и вторую нельзя молчать.

**Ворота, которых маршрут не достиг.** Реестровая проекция опережает журнал:
узел пишет свой статус ДО коммита, и когда диспетчер встал fail-closed сразу после
захода (readonly-сторож нашёл временные файлы узла), реестр уже `done`, а курсор
журнала остался на узле. Доинференс «всё до ворот done → ворота ждут» рисовал ворота
с кнопками, до которых маршрут не дошёл; reject уезжал в CAS, обязанный отказать
кодом 75 («песочница создана частично» — хинт, не имеющий к делу отношения), а упавший
`gate --commit-only` ещё и сбрасывал `STALLED_HUMAN` до проверки CAS — кокпит терял
маркер остановки и вместо «конвейер встал» показывал ложную паузу на воротах. Три
правки: `wait` для ворот route-v2 ставится только по явной записи движка
`GATE_*=waiting` (`factory-graph.js`; доинференс оставлен историческим реестрам v1);
`/api/tasks/:id/gate` сверяет курсор trusted ledger (`cursor` из
`stage-results/runtime.json` — конверт с sha256 по канонической форме движка,
`lib/factory-attempt-ledger.js`) и отвечает `gate_not_current` с узлом, где маршрут
стоит на самом деле; движок снимает `STALLED_HUMAN` только после успешного CAS.

Валидатор курсора обязан повторять не только список состояний, но и их форму:
у `ready`/`paused` есть `currentNode`, а у `stopped` он, наоборот, строго `null`,
и причина завершения лежит в `stop`. Требование узла для всех трёх состояний превращало
штатно завершённую попытку в read-only и прятало обе lifecycle-кнопки карточки.

## «Агент повис» на длинном ходе = лимит ленты глушил не хранение, а трансляцию

`createStepSink` (`lib/chat/stream-steps.js`) выходил из `emit` целиком, как только
накапливал `MAX_CHAT_STEPS` (400): дальше не вызывался `onStep`, значит не уходил ни
SSE `chat-step`, ни копия в `activeRuns`. Ход на 1500 шагов (обычное дело для Codex на
ultra: reasoning + tool + res на каждый вызов) выбирал лимит за час и **дальше работал
для окна беззвучно** — вечное «думает…» без единого нового шага, и не отличить от
настоящего зависания. F5 не помогал: серверная копия хранила ПЕРВЫЕ 400 шагов, то есть
восстанавливала картину часовой давности.

Усугубляет Codex: `onProgress` у него вызывается только на `turn.completed`
(`executors/codex.js`), поэтому счётчик «думает… · N ток.» за ход не тикает ни разу —
других признаков жизни у окна не остаётся. У Claude счётчик живой, там немота ленты
менее заметна.

Теперь лимит ограничивает только **хранение**, и оно скользящее (последние 400) —
и в sink, и в `activeRuns`, и в сторе окна. Трансляция безусловна. Правило на будущее:
буфер и поток — разные вещи, переполнение буфера не имеет права затыкать поток.

Как проверять такое, не гадая: `GET /api/chat/active` показывает `at` последнего шага
(если он застыл, а `~/.codex/sessions/<...>.jsonl` растёт — виноват кокпит, не агент),
а `curl -sN /api/events` покажет, идут ли `chat-step` по этому `chatKey` вообще.

## Ollama: пустой ответ на второй ход = загруженную модель вычли из памяти дважды

Симптом: первый ход после старта демона работает, а следующий возвращает пустой ответ
(в ленте — одно размышление, текста нет), `contextWindow` при этом **2048**.

Причина: `estimateMaxNumCtx` (`executors/_ollama-client.js`) считает бюджет KV-кэша как
«свободная VRAM + 60% свободной ОЗУ − веса модели». Пока модель НЕ загружена, это верно.
Как только демон её поднял, её веса уже вычтены из свободной памяти операционной
системой — и вычитание повторялось вторично. Для 23-гигабайтной модели бюджет уходил
в минус, потолок схлопывался в пол ползунка (2048), `run()` честно ужимал туда `num_ctx`,
а в такое окно не влезает даже системный блок с правилами проекта и объявлением
инструментов. Модель отвечала пустотой, и выглядело это как «сломался исполнитель».

Обе стороны починены:

- **занятое уже загруженной моделью возвращается в бюджет** — `estimateModelMaxNumCtx`
  спрашивает `/api/ps` и передаёт `loaded: {vramBytes, ramBytes}` в оценку (замер живьём:
  потолок 2048 → 71680);
- **`MIN_AGENT_NUM_CTX = 8192` — пол, ниже которого оценка ужимать не имеет права**
  (`executors/ollama.js`). Оценка памяти — эвристика, а при нехватке Ollama доложит часть
  слоёв на процессор, а не упадёт: цена ошибки в меньшую сторону несопоставимо выше, чем
  в большую. Настройку ниже 8192 человек поставить может — пол не поднимает выбранное
  значение, только не даёт **оценке** опустить его.

Проверки — `tests/server/ollama-provider.test.js` (оба случая зафиксированы отдельными
тестами: единица `estimateMaxNumCtx` с `loaded` и ход, где веса больше всей памяти).

## Ollama: уровни `think` принимаются, но не отрабатываются

`think: "low" | "medium" | "high"` демон **принимает без ошибки** — и потому выглядит
поддержанным. Замер на думающей модели: длина рассуждения вышла 360 / 751 / 354 символа,

Смежное, и это важнее: **если эффорт не выбран, поле `think` не отправляется вовсе.**
У думающей модели дефолт демона — думать; подставленный «на всякий случай» `false` молча
отнял бы у неё рассуждения у всех, кто слайдер не трогал.

## Ollama: вся документация проекта в системном промпте = две минуты префилла на ход

Соблазн «положить модели весь `docs/`, раз она локальная и бесплатная» стоит замера:
`docs/cockpit/*.md` — 303 КБ ≈ 75k токенов ≈ **около двух минут префилла на КАЖДЫЙ ход**
(36B MoE, префилл порядка 650 ток/с). Поэтому в системный блок идут только `AGENTS.md`

Модель дочитывает ровно то, что ей понадобилось, а не всё подряд каждый ход.

Там же про холодный старт: `keep_alive` по умолчанию 5 минут, и первый ход после паузы
заново читает веса с диска (для крупной модели — десятки секунд). Это не зависание —
ручка «Держать модель в памяти, минут» в настройках исполнителя, а посмотреть, что

## MCP-серверы: «отвалился» = не поднялся на этом ходу, переподключать нечего

Спрос «сделать кнопку переподключения, а то playwright отваливается» упирается в устройство
запуска: **кокпит поднимает процесс CLI на КАЖДОЕ сообщение**, а MCP-серверы — дочерние
процессы этого CLI. Они стартуют и умирают вместе с ходом, живого соединения между ходами
не существует, чинить в промежутке нечего. «Отвалился» на практике означает «не поднялся
на этом ходу», и лечится причиной отказа, а не повторным коннектом.

Слоёв MCP два, и они лежат в разных местах:

| слой | где определён | что о нём знает кокпит |
|---|---|---|
| файловый | `mcpServers` в `~/.claude.json`, `.mcp.json` проекта, `--mcp-config` | всё: команда запуска, аргументы, env |
| аккаунтный (коннекторы claude.ai) | на стороне аккаунта | только имя (в `claudeAiMcpEverConnected`) — определения на диске НЕТ |

Отсюда правила панели (`mcpStatus` у claude, `parseClaudeMcpList`):

- **`claude mcp list` — единственный источник живости, но НЕ полный список**, причём
  текстовый: машинного формата у команды нет. Разбор идёт по маркеру статуса (« - » + иконка
  либо `Connected`/`Failed`/`Needs …`), а НЕ по последнему « - » в строке: в команде запуска
  дефисов полно (`docker run -i --rm --env-file …`), и половина команды уезжала бы в статус;
- **exit code у неё 0, даже когда сервер не поднялся.** Отказ виден только в тексте, поэтому
  вызов идёт с `anyExit: true`, а решение принимается по разобранным строкам;
- **коннекторы claude.ai она печатает НЕ всегда.** Два замера подряд на одной машине: в
  первом из трёх коннекторов не было ни одного (только файловые bitrix и playwright), во
  втором появился один. Поэтому секция «claude.ai» строится не из вывода команды, а из имён
  в `claudeAiMcpEverConnected` (`~/.claude.json`), а совпавшие по имени схлопываются — иначе
  панель то показывала бы коннекторы, то нет, и в один из заходов дублировала бы их;
- **живость аккаунтного коннектора локально не проверить ничем**, поэтому у него своё
  состояние `remote` («включён на claude.ai», серая точка). Жёлтое «состояние неизвестно»
  над тремя рабочими коннекторами — ложная тревога, а зелёное «подключён» — выдумка;
- **`needs auth` в выводе `mcp list` не отражается вовсе** — этот признак живёт отдельно,
  в `~/.claude/mcp-needs-auth-cache.json`. Мало того, коннектор, которому нужна авторизация,
  команда печатает как **`✔ Connected`** (замер: `claude.ai Google Drive` при живой записи в
  кэше). Соединение и правда есть, инструментов у агента всё равно нет — поэтому кэш
  перебивает статус, а вместе со статусом подменяется и текст: «Нужна авторизация» с
  пояснением «Connected» под ней — противоречие на экране. Провал этим не подменяется
  никогда: упавший процесс входом не лечится;
- **область видимости выводится вычитанием**: имя есть в файлах — «Свои»/«Проект», нет нигде —
  значит аккаунтный коннектор. Спросить об этом CLI напрямую нечем;
- опрос занимает около 4 с (живой health-check каждого сервера), поэтому эндпоинт отдельный
  и ленивый — см. [чат с агентами](chat-agents.md).

**На конвейере файловых MCP нет вообще:** раннер движка запускает claude со
`--strict-mcp-config` (`engine/lib/runners/claude.sh`), то есть ничего из `~/.claude.json`
и `.mcp.json` не грузится. Панель в настройках описывает ЧАТ, а не этапы конвейера — не
переносить её выводы на прогоны.

**Чего в этой истории не нашлось — утечки процессов со стороны кокпита.** Проверка живьём:
каждому живому `claude -p` соответствовал идущий ход из `GET /api/chat/active` (долгий ход
легко принять за мёртвый процесс — я на этом ошибся), а 3,7 ГБ chrome и шесть профилей
`playwright_chromiumdev_profile-*` принадлежали стороннему контейнерному сервису, не
playwright-mcp кокпита. Прежде чем чинить «утечку», сверь PID с активными ходами и
`/proc/<pid>/cgroup` с владельцем — иначе чинишь чужое.

## Веб-тест монтирует SFC дважды — а работает со сторами первого теста

**Где:** `tests/web/*.component.test.js` — все, кто компилирует `.vue` через `compileScript`
и грузит результат как `data:`-модуль.

Симптом обманчивый: второй тест в файле падает, а в дампе DOM стоит разметка с данными
ПЕРВОГО. Выглядит как «компонент не перерисовался» или «стор не сбросился» — и лечить
тянет заглушки, хотя виноват загрузчик модулей.

Механика: заглушки подставляются заменой импортов на `globalThis.__что-то`, и в собранном
модуле это **top-level `const`** — вычисляется один раз при первом импорте. А сам модуль
Node кэширует по URL, то есть по всей строке `data:text/javascript;base64,…`. Байты кода
у двух монтирований одного файла совпадают: `id` (scopeId) в вывод `compileScript` **не
попадает** — его дописывает уже плагин сборщика (проверено на `TaskModal.vue`: две
компиляции с разными `id` дают побайтово равный текст, `data-v-…` в нём нет). Значит второй
`import()` возвращает первый модуль с уже привязанными сторами.

Лечится хвостом-nonce в самом URL — `…base64,${код}#${n}`: фрагмент код не меняет, а ключ
кэша делает разным. Образцы — `tests/web/telegram-connect.component.test.js` и
`telegram-expand.component.test.js`; там же на всякий случай разведены имена pinia-сторов
(`defineStore('…-'+nonce)`), чтобы совпадение id не сложило состояние двух тестов.

**Второе свойство того же загрузчика: у `data:`-модуля нет базового пути.** Любой
оставшийся в скомпилированном SFC относительный импорт падает
`ERR_UNSUPPORTED_RESOLVE_REQUEST`, причём **на этапе импорта модуля**, то есть роняет
не один тест, а весь файл разом — новый `import { useTaskSeenStore } from
'../stores/task-seen.js'` в `TaskModal.vue` погасил оба его компонентных теста, хотя к
проверяемому поведению отношения не имел. Поэтому КАЖДЫЙ импорт вью заменяется
заглушкой прямо в исходнике (`.replace(…, 'const … = globalThis.__…')`), а список замен
обязан идти вровень с импортами компонента: добавили импорт во вью — добавьте замену в
тестах, которые его монтируют.

**Заодно про «проверить замером»:** настоящего headless Chrome в офлайн-наборе нет, а
happy-dom раскладку не считает вовсе — `getBoundingClientRect()` там нули, `scrollWidth`
равен `clientWidth` всегда. Поэтому требования вида «длинная строка не выталкивает колонку»
в наборе проверяются статически — чтением `<style scoped>` компонента на наличие
`min-width: 0` / `overflow-wrap: anywhere` (пример: `TG-UI-05`). Живой замер
`scrollWidth` против `clientWidth` (раздел про колонку чата выше) остаётся ручным шагом
в браузере: статическая проверка стережёт правило от удаления, но не доказывает, что
раскладка сошлась.

## Code/Terminal нельзя монтировать отдельно в route и в правом доке

Оба инструмента stateful: Code держит Monaco, выбранный проект и DOM id, Terminal — xterm,
WebSocket и настоящий PTY. Два экземпляра означают расходящееся состояние, повторные id и
лишнюю shell-сессию; общий флаг «док когда-либо открывали» тоже плох — открытие Code тогда
поднимает невидимый Terminal.

Владелец один: постоянный `shared/layout/ToolHost.vue` в `AppShell`. Route-компоненты
`CodeView.vue`/`TerminalView.vue` — только пустые адаптеры, а `page`, `dock`, `hidden`
переключают CSS стабильного render-site. Lazy mounted-флаг отдельный у каждого registry id.
Док разрешён с 900 px; при переходе на 899 px он закрывается, непоказанные панели
размонтируются, но queued intent сохраняется. Возврат на широкий экран сам PTY не создаёт.
Разворачивание дока не является route-переходом: runtime-флаг `isExpanded` меняет только
ширину того же dock render-site до ширины content-колонки, не трогая
`dock.width`, URL/history, Monaco/xterm и WebSocket. Повторный клик возвращает обычную
ширину; первый Escape из expanded-состояния делает то же, следующий уже скрывает док.
Выбор хранится отдельно в `expandedPreference`/`cockpit-dock-expanded`: `close()` снимает
активный `isExpanded`, чтобы скрытая панель не оставляла `<main>` inert, но следующее
открытие и первое явное открытие после reload восстанавливают выбранную геометрию; сам
док после загрузки не показывается. `resetAllRuntime()` очищает mounted/runtime/intents и
закрывает живые панели обычным unmount, но device-local layout preference не стирает.
Техническое сворачивание при смене route вызывается с `persist: false` и не переписывает
пользовательскую настройку.
Пока content целиком перекрыт, `<main>` исключён из tab-order через `inert`; смена route
сворачивает expanded, но не закрывает живую панель.
У compact Code навигатор остаётся слева от Monaco; его отдельная сохранённая ширина не
должна переиспользовать full-layout или прежний вертикальный split. Ограничение 42%
считается в JS по фактической ширине `.lay` и тем же значением заполняет CSS и
`aria-valuemax`: один CSS-only clamp оставлял невидимый dead range разделителя.

Hide/show Code обязан обновлять данные без промежуточного пустого состояния. Нельзя перед
activation revalidation вызывать `resetState()`, очищать `dirs` или отвязывать Monaco-модель:
projects/repos/root/раскрытые каталоги/file/git перечитываются поверх последнего валидного
снимка, а свежая модель подставляется до освобождения старой. Очищение допустимо только
после ответа, который подтвердил исчезновение project/context/file. Фоновая проверка также
не показывает индикаторы загрузки, меняющие геометрию header или дерева.
На первом открытии async-компонент тоже не должен оставлять пустой slot: его синхронный
loading-компонент повторяет rail/tree/editor-сетку, но остаётся чистым каркасом без импорта
Monaco. Отдельная маленькая плашка «Загрузка…» снова создаст заметный скачок геометрии.

Terminal intent заменяет прежний `sessionStorage`: очередь exact-once принимает команды и
в уже живой socket, и до lazy mount. В состоянии `closed` все ожидающие команды должны
делить один reconnect и отправляться после первого вывода shell без `\n`. Resize xterm —
не косметика: клиент посылает `{t:'resize', cols, rows}`, сервер применяет `TIOCSWINSZ` и
`SIGWINCH`; helper при закрытии WebSocket обязан убрать всю process group.

## Escape закрывает только верхний слой

Dock, tools-popover, модалки, confirm и закреплённые подсказки регистрируются в общем
`shared/ui/layer-stack.js`. Один Escape вызывает `close` ровно одного слоя с максимальным
priority. Не добавлять независимый document-keydown рядом: он закроет несколько слоёв за
одно событие. События из Monaco и xterm помечены `data-escape-owner`; их локальный Escape
не должен красться глобальным стеком.

## Кнопки «Входящих» мертвы, а автомат работает = роутер режет `:param` на 100 символов

Симптом: в `/inbox` любая ручная кнопка («Поставить задачу», «Пропустить», «Вернуть на
разбор») отвечает ошибкой `is exceeding the max param length`, при этом автоматические
задачи создаются исправно. Расхождение сбивает с толку: очередь читается, автомат живой,
значит «Входящие работают» — а человек не может решить ни одного обращения.

Причина: дефолт `maxParamLength` у find-my-way (роутер fastify) — **100 символов**, а
`itemRef` обычной Telegram-карточки — около **220** (versioned tuple → JSON → base64url,
внутри `channel`, `accountRef` и вложенный `localBundleId`). Отказ приходит из роутера
**до** обработчика: `414 FST_ERR_MAX_PARAM_LENGTH`, гейт плагина не спрашивается, лог
модуля пуст. Автомат этого не видит, потому что `InboxAutoTasks` зовёт `InboxTaskService`
внутри процесса, мимо HTTP.

Правила:

- потолок задаётся один раз в `app.js` и **выражается константой кодека**
  (`INBOX_REF_LIMITS.encodedChars`, 8192). Число, вписанное руками, разошлось бы с тем,
  что кодек уже разрешает выдавать;
- **тест с коротким ref ничего не доказывает.** Баг прожил в наборе именно потому, что
  фикстуры дёргали `/api/inbox/items/item-ref/dismiss` — 8 символов вместо 220. Проверка
  обязана строить ref настоящим `encodeInboxRef`, а не выдумывать строку;
- симптом «автомат работает, кнопки нет» вообще стоит читать как «отказ раньше
  обработчика»: гейт плагина, авторизация, роутер. Смотреть `curl -i` на сам путь,
  а не логи модуля.

Сторож — `tests/server/inbox-api.test.js` (пара тестов: тот же запрос даёт 414 на дефолте
и доезжает до `taskService.dismiss` с поднятым лимитом; плюс статическая сверка `app.js`).
