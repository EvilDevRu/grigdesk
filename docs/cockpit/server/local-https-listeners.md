# Локальный HTTPS: два сокета в одном процессе, а не «переезд на 8143»

Дома PWA не существует без secure context (см. раздел про Service Worker), поэтому кокпит
выпускает свой CA и лист на адрес мозга: «Настройки → Доступ → Локальный HTTPS».
Код — `server/src/lib/tls/local.ts` (выпуск), `server/src/lib/tls/httpsListener.ts` (второй сокет),
`server/src/plugins/httpScope.ts` (область http).

**Порт 8140 остаётся http и остаётся полнофункциональным для loopback.** Это не компромисс,
а требование: 8140 — внутренняя шина процесса. По нему ходят permission-tool чата (дочерний
процесс `claude` без cookie), `bin/b24` и SHIP-этап фабрики, `bin/restart` (проверка живости
по `/api/auth/state`), dev-прокси Vite и туннель шлюза с VPS. Переведи 8140 на https — и всё
перечисленное надо чинить в шести местах разом.

Что решает `decideHttpRequest` для запроса, пришедшего на http-сокет:

| условие | решение | почему |
|---|---|---|
| https не поднят | пропустить всё | иначе битый сертификат отрезает кокпит от сети, чинить — с консоли мозга |
| сосед по сокету — loopback | пропустить всё | та самая внутренняя шина |
| путь `/api/settings/tls/ca.{crt,svg}` | пропустить | корень качается по http: по https до его установки браузер ругается |
| `Upgrade:` из сети | разорвать сокет | `ws://` — это PTY-шелл открытым текстом, а `wss://` браузер сам не подставит |
| остальное из сети | `301` на `https://<host>:8143` | |

Грабли, на которые уже наступали или которые обойдены осознанно:

- **Адрес берём из `request.socket.remoteAddress`, а НЕ из `request.ip`.** За шлюзом `request.ip` —
  это клиент из `X-Forwarded-For` (публичный), и запросы туннеля улетали бы в редирект на домашний
  адрес, до которого снаружи не достучаться. Сосед по сокету у туннеля всегда `127.0.0.1`.
  Исключение — выдача `ca.crt`: там проверяется именно `request.ip`, чтобы корень не ушёл наружу.
- **Fastify создаётся БЕЗ опции `https`.** Второй сервер получает тот же роутер через публичную
  `fastify.routing` и **перенесённые слушатели `upgrade`** — `@fastify/websocket` вешает свой
  ровно один на `app.server` при регистрации. Забудешь перенести — терминал по `wss://` молча
  не подключается (тест TLS-SCOPE-04 ловит).
- **Перенос делается ПОСЛЕ `listen()`**: до готовности приложения плагин ещё не повесил upgrade.
- **Провал `listen` на 8143 не роняет процесс.** Под `Restart=always` исключение здесь устроило бы
  вечный крэш-луп. Ошибка возвращается и видна в «Настройки → Доступ».
- **`bin/restart` ждёт освобождения ОБОИХ портов.** Сокеты закрываются не одновременно; новый
  процесс успевал стартовать, пока старый держал 8143 — https молча не поднимался.
- **Флаг `Secure` у cookie корректен сам собой**: `request.protocol` в Fastify — это
  `socket.encrypted`, то есть свойство соединения, а не процесса. Cookie не разделяются ни по
  схеме, ни по порту, поэтому сессия переживает переход `http://IP:8140` → `https://IP:8143`.
- **Сертификат читается ОДИН раз при старте.** Поэтому тумблер режима — это не «включить
  сейчас»: он записывает намерение в prefs, а сокет появляется/исчезает при следующем старте.
  Отсюда честная плашка «нужен перезапуск» (сравнение отпечатка на диске с загруженным).
- **Тумблер режима гасит сокет, а не файлы.** `accessLocalHttps` в prefs читается в `app.js` до
  сборки приложения и решает, что вернёт `lib/tls/source.ts`: выключен — `source: 'none'`, https
  не поднимается вовсе. Сертификат и корень при этом остаются на диске, поэтому обратное
  включение не требует ни выпуска, ни повторной установки корня на устройства. Стереть выпущенное
  — отдельная кнопка «Удалить сертификат» (`POST /api/settings/tls/disable`): у «выключить режим»
  и «стереть ключи» разная цена, и путать их в одном контроле нельзя. Тумблер намеренно НЕ гасит
  `COCKPIT_TLS_KEY/CERT`: переменные окружения — настройка машины, а не режим в UI, и человек за
  консолью не ждёт, что галка в браузере их отменит (тесты TLS-SRC-01/02).
- **Ключ корня лежит вне репозитория** (`~/.config/cockpit/ca`, `COCKPIT_TLS_CA_DIR`): плагин
  «Код» отдаёт по HTTP любой файл под деревом проекта, а `server/.state` — внутри дерева.
  На корне стоят `nameConstraints=critical` по приватным диапазонам: украденный ключ не подпишет
  публичный домен.
- **Адреса из тела запроса уходят в SAN и в `-extfile` openssl** — валидируются allowlist-ом
  (`net.isIP` + приватный диапазон), а не «фильтрацией плохого»: `1.2.3.4,DNS:evil.com` дал бы
  лист на чужой домен под доверенным корнем, а перевод строки — второй CA.
- **«Адрес не в сертификате» при правильном сертификате = в адреса машины попал туннель VPN.**
  `localAddresses()` отсекает мосты и туннели ПО ИМЕНИ интерфейса (диапазон не годится:
  docker-мосты живут в тех же приватных сетях), а имя туннеля может содержать маркер типа
  интерфейса суффиксом и не попадать под один префиксный фильтр. Тогда адрес туннеля считался
  адресом мозга, которого нет в SAN, и раздел «Доступ» светил жёлтым чипом, хотя лист выписан ровно на тот
  адрес, по которому заходят. Имя туннеля ловится с обеих сторон (`tun`/`tap`/`wg`/`utun`),
  вторым поясом — маска: в /30 и уже клиенту места нет, домашней сети такой маски не бывает.
  Сверять замером: `ip -4 -o addr` против `X509Certificate.subjectAltName`, а не по чипу.
  Сторож — `tests/server/tls-local.test.js` (TLS-GEN-07).
- **QR ведёт на `http://<адрес>:8140/api/settings/tls/ca.crt`**, а не на https. Веди он на https,
  корень пришлось бы качать через то самое предупреждение браузера, которое он и убирает.
- **На мозге ставить корень не нужно**: `http://localhost:8140` — secure context по спеке.
