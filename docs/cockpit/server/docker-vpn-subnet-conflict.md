# «Встал агент», «упал прогон», «нет лимитов» — один корень: подсеть docker поверх VPN

Три симптома, которые выглядят как три разные поломки в трёх разных местах:

- прогон конвейера умирает через минуту после старта: `OAuth request … failed: Client
  network socket disconnected before secure TLS connection was established`;
- живой агент замолкает на десять минут посреди этапа — TCP-сокет к API `ESTAB`,
  очереди пусты, keepalive тикает, ответа нет;
- в шапке периодически «Не удалось получить лимиты».

Диагноз тянет то к провайдеру модели, то к самому исполнителю, то к движку. А причина
одна и лежит ниже всего этого: **docker-мост и VPN-туннель делят один диапазон адресов.**
Туннель обычно поднимает крошечную `/30`, docker-сеть проекта — широкую `/16` поверх неё.
Префикс `/30` длиннее, поэтому перехватывает первые адреса; IPAM же выдаёт контейнерам
низший свободный. В результате контейнер садится на адрес ШЛЮЗА туннеля, и часть
исходящего трафика хоста уходит не туда — рвётся на TLS-хендшейке или зависает.

Проверка ровно в две команды, обе не гадают:

```bash
ip -4 -o addr | awk '{print $2, $4}'   # два интерфейса с ОДНИМ адресом = оно
ip neigh show <адрес шлюза туннеля>    # висит на dev br-… = докер занял служебный адрес
```

Лечится на стороне docker, не VPN: контейнерам задаются статические адреса вне зоны
туннеля, а сети — `ip_range`, из которого IPAM выдаёт автоадреса. Одной статики мало:
освобождённый адрес занимает следующий поднятый контейнер. Конкретные диапазоны и
команды принадлежат локальному проекту и живут в его документации, а не здесь.

Мораль для диагностики: **прежде чем чинить исполнителя, проверь, что под ним не дерутся
за адреса две сети.** Симптом всегда указывает на верхний слой — на модель, на CLI, на
провайдера, — потому что именно там он проявляется. Отсюда же практическое следствие для
кокпита: сетевой сбой обязан переживаться повтором с паузой, иначе моргание туннеля
показывается человеку как отказ аккаунта (см. [повтор с паузой](../pipeline/retry-backoff.md)).
