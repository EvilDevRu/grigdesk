# Программная правка .env — только через общий писатель

Файл `.env` в папке данных читают сервер, окно, CLI, systemd (`EnvironmentFile=`),
`node --env-file` (`bin/cockpit`, `deploy/restart.sh`) и человек. Код кокпита правит его одним модулем
`server/src/lib/envFile.ts`. Окно «Ключи доступа» в карточках исполнителей
пишет через `updateEnvFile`. Второй самописный writer заводить нельзя.
У двух писателей не было бы общей очереди, и параллельные правки теряли бы друг друга.

## Что гарантирует `updateEnvFile(path, { KEY: value | null })`

- Меняются только строки названных переменных. Остальные байты остаются как были:
  комментарии, пустые строки, порядок, кавычки соседей, CRLF, BOM и хвост без перевода
  строки.
- Задание заменяет **последнее** присваивание имени: оно действует и у systemd, и у Node.
  Новое имя дописывается в конец. Если строка уже точно задаёт то же значение (`KEY=v`,
  `KEY="v"`, `KEY='v'`), файл не переписывается. Строка с хвостом `KEY=v # заметка`
  переписывается: Node читает её как `v`, а systemd — вместе с хвостом.
- `null` удаляет **все** присваивания имени, иначе ожило бы более раннее. Закомментированные
  строки `# KEY=…` не трогаются.
- Значение пишется без кавычек и только из символов `A-Z a-z 0-9 . _ ~ + / = : @ % , -`.
  Пустое значение допустимо. Пробел, кавычки, `#`, `$`, `\` и `;` отклоняются: проверено, что
  Node обрезает `x#y` до `x`, а systemd 249 читает `QUOTED="x y"  # c` как `x y# c`. Сообщение
  об ошибке называет переменную, но не значение.
- Запись атомарна: временный файл рядом, права прежнего файла (новый — `0600`), `fsync`,
  rename и `fsync` каталога. Правки одного файла внутри процесса идут очередью. Если файл
  изменился между чтением и заменой, правка перечитывает его до трёх раз, затем отказывает
  с `env_file_conflict`.
- Символическая ссылка остаётся ссылкой: правится её цель. Висячая ссылка, жёсткие ссылки,
  чужой владелец и файл больше 1 МиБ — отказ `env_file_not_regular` / `env_file_too_large`.

## Когда файл не правится вовсе

Если хотя бы одну строку systemd и Node могут разделить по-разному, правка отказывает с
`env_file_unsupported` и номером строки, а файл остаётся нетронутым:

- значение в кавычках не закрывается на той же строке (у Node многострочные кавычки);
- строка, в том числе комментарий, кончается на `\` (у systemd это перенос);
- экранированная кавычка перед закрывающей или кавычки в хвосте после неё;
- строка — не комментарий (`#`, `;`), не пустая и не `KEY=VALUE` / `export KEY=VALUE`;
- файл не в UTF-8.

Без этого правка соседней переменной могла бы попасть внутрь чужого многострочного значения.
Человек правит такую строку руками, после чего правка из кокпита снова работает.

## Окружение процесса

Модуль только пишет файл. Перенести значения в `process.env` без перезапуска — отдельное
решение вызывающего: `applyEnvChanges(changes)`. Окно ключей так и делает: исполнители
читают ключ из окружения на каждом ходе. Машинные параметры запуска читаются
при старте и применяются после ручного перезапуска.

`previewEnvFile` строит те же байты без записи: перенос проверяет допустимость изменений
до первого перемещения. Выбор файла и запрещённые ключи — [папка данных](data-home.md).

Тесты: `tests/server/env-file.test.js`.
