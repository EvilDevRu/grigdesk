# Единая папка данных Кокпита

Кокпит хранит настройки и рабочие данные вне дерева кода. По умолчанию это
`~/.cockpit`; непустая переменная окружения `COCKPIT_HOME` выбирает другую папку.
Общее правило реализовано в `shared/runtime/dataHome.ts` и `deploy/lib/runtime-env.sh`.

Путь должен быть абсолютным, состоять из латинских букв, цифр и символов
`. _ + - / @ , = :`, не быть `/` и не содержать сегментов `.` или `..`.
Конечные `/` удаляются. Умолчание также проверяется: если домашний каталог содержит
пробелы или другие символы, задайте подходящую `COCKPIT_HOME`, например
`/home/user/cockpit-data`. Папка не должна совпадать с домашним каталогом,
лежать внутри кода или содержать его.

Папка считается явной, только если заданное нормализованное значение отличается от
`<домашний каталог>/.cockpit`. Поэтому переданное сервером детям умолчание остаётся
неявным. Сервер создаёт папку и `state/` с правами 0700, приводит существующие права
к 0700 и передаёт детям канонический путь через `COCKPIT_HOME`.

## Раскладка

Пути в таблице относительны папке данных. Имена файлов прежнего состояния сервера
сохраняются; индивидуальные переменные `COCKPIT_*_DIR` и `*_PATH` продолжают работать.

## Что остаётся снаружи

- Фабрика: `~/.factory`, каталоги `profiles/` и `routes/` в коде, homes исполнителей
  внутри factory state. Попытки сохраняют абсолютный канонический `routesDir`;
  перенос требует отдельного изменения движка и связанных рабочих копий git.
- Установленное окно и `runtime.json` в `~/.local/share/cockpit/desktop`, каталог
  данных окна `~/.config/Кокпит`: это клиентская программа.
- Разработка: Android SDK, Gradle, загрузки, ключи подписи APK и состояние DevLink. Неиспользуемые каталоги прежней конфигурации не удаляются.
- Сборки и ресурсы кода: `node_modules`, `web/dist`, runtime DeepSeek,
  `server/seed/agents`, `third_party`, `bin/cockpit-relay`, `desktop/release`.
  Обновлятель получает отдельный `--work-root <код>/.state` для временной копии git.
- Homes внешних исполнителей: `~/.claude`, `~/.codex`, `~/.kimi-code`.

## Папка артефактов

`artifacts/` — рабочая папка агентов и инструментов вне дерева кода; явная
`COCKPIT_ARTIFACTS_DIR` важнее (`artifactsPath` в `shared/runtime/dataHome.ts`, `config.artifactsDir`).
Сервер создаёт её с правами 0700 и добавляет к каждому ходу чата как дополнительную папку с
правом записи; в видимом списке папок хода она скрыта, как каталог вложений. Kimi её не получает:
его изоляция не пускает каталоги папки данных. Картинки из неё показываются в чате, документы
открываются. Скрипты проверок и тесты берут базу через `artifactsPath`; сторож памяти передаёт
тестам настоящую `COCKPIT_ARTIFACTS_DIR`, хотя `COCKPIT_HOME` у них временная. Прежняя
`<код>/.state/artifacts` в выдаче картинок допускается ради старых сообщений.

## Настройки и окно

Все читатели выбирают `COCKPIT_ENV_FILE`, иначе `<папка данных>/.env`:
сервер, окно, CLI, запускалки, установщик речи и Vite при разработке. Юнит получает
выбранный путь в `EnvironmentFile`. Сборка Vite этот файл ради порта не читает.

`COCKPIT_HOME` и `COCKPIT_ENV_FILE` внутри файла запрещены, даже с пустым значением:
файл не может выбирать собственное место. Сервер отказывает с кодом 78,
CLI и bash — с кодом 1, окно сообщает ошибку описания установки.
Присутствующая переменная окружения, даже пустая, важнее значения файла.
Сервер читает файл до конфигурации; импорт `config.ts` сам данных не читает и не пишет.
`NODE_OPTIONS` и `NODE_EXTRA_CA_CERTS` для самого процесса требуют загрузки окружения
до запуска Node: через окно, юнит или `bin/cockpit`.

Изменения делает [общий писатель](env-file-writer.md), в том числе через совместимую
ссылку из дерева кода. Ключи исполнителей, сохранённые окном, применяются сразу;
ручная правка машинных настроек требует перезапуска.

Перенос добавляет отсутствующие `COCKPIT_UI_RELEASES_DIR` и `COCKPIT_LOG` с новыми
путями: их понимает старая сборка окна. После установки новой сборки эти добавленные
ключи можно удалить. Новое окно читает descriptor версии 1 (`root`, `node`) либо 2
(`root`, `node`, `home`). Во второй версии `home` важнее окружения окна. Установщик
сначала пишет версию 1, заменяет AppImage, затем при явной папке пишет версию 2.

## Перенос

Команда запускается человеком из папки кода, при закрытом окне и остановленном сервере:

```bash
node tools/moveDataHome.mts
node tools/moveDataHome.mts --apply
```

Без флага она только показывает план и условия. `--apply` переносит, `--back`
возвращает данные, `--drop-links` убирает совместимые ссылки. Код 0 означает успех
или отсутствие работы; 1 — невыполненное условие либо ошибку шага; 2 — неверные
аргументы или защиту от случайного запуска. Изменяющие режимы запрещены при
`CLAUDECODE`, подменённом `HOME` и папке внутри `os.tmpdir()`; тестовые опции
`--code-root` и `--home` принимаются только вместе и только внутри `os.tmpdir()`.

План требует: нет сервера на порту и процесса сервера этой копии; служба и окно
остановлены; нет установки плагина, незавершённой публикации DeepSeek и активного
обновления. Задание в `restarting` без замка и без живого воркера не мешает: его подтвердит
сервер после переноса. Процессы того же пользователя не должны держать исходники данных через
cwd, executable, argv, открытые файлы или отображения памяти. Процессы, закрытые от владельца
(ssh-agent, менеджер паролей, служебные процессы сессии), проверяются только по аргументам и
называются в плане. Сервер этой копии узнаётся и по относительному `src/app.ts` вместе с cwd.
Отсутствие systemctl допустимо; ошибка связи с пользовательской шиной означает отказ.

Источники и назначение должны быть на одном диске, родитель папки — существовать,
пути — не пересекаться. Назначение допускается пустым, со следами прежнего запуска
или журналом прерванного переноса. Произвольные данные запрещают слияние. Перезапись
`.env` и известных JSON проверяется до первого перемещения; `.env` с жёсткими ссылками,
больше 1 МиБ или чужого владельца останавливает план. Активные `factory-t*`
и внутренние ссылки, которые могут повиснуть, показываются предупреждениями.

Перенос переименовывает каталоги, сохраняет отслеживаемые заглушки в дереве кода,
делает приватную копию `.env` в `state/env.before-move` и переписывает абсолютные
пути внутри перенесённых источников. Для JSON это `state/prefs.json`,
`state/showcase-browser/browser.json` и `state/sandboxes/*.json`; остальные данные
произвольно не переписываются. В выводе нет значений секретов.

Каждое действие записывается в атомарный журнал до и после изменения. `.move-lock`
содержит pid и время старта процесса; повтор после сбоя продолжает работу по фактам
на диске. Следы запуска сохраняются отдельно и затем вливаются с защитой имён.
На старых местах остаются абсолютные ссылки `<код>/.env` и `<код>/server/.state`.
Повтор завершённого `--apply` ничего не меняет; если в коде снова появились данные (плагин
в разработке, `.env` по старой инструкции), команда называет их и просит перенести вручную или
удалить. На чистой копии создаётся только папка. Копия `env.before-move`, оставшаяся в
`<код>/server/.state` после возврата, останавливает новый перенос до ручной сверки.

`--back` проверяет остановку и свободные места возврата, возвращает всю раскладку,
снимает свои ссылки и сохраняет заглушки. Если `.env` не менялся после переноса,
возвращаются прежние байты и права; иначе сохраняются новые настройки, пути
переписываются обратно, а исходная копия остаётся для человека. Два добавленных
ключа удаляются лишь при неизменных значениях. Пустая папка и журнал удаляются.
После возврата нужны прежний код, сборка окна и при необходимости прежний юнит.

Через несколько дней работы `--drop-links` удаляет две ссылки, только если журнал
завершён, установленный юнит (даже выключенный) уже не читает старую `.env`, установлена
сборка окна, знающая папку данных (метка `data-home` рядом с AppImage ставит
`cockpit desktop install`), нет активных `factory-t*`, известные JSON и `.env` не содержат
прежних путей. Чужие ссылки и обычные файлы не удаляются.
Ключи настроек этот режим не меняет. Для обновления одного юнита служит
`deploy/install.sh --unit-only`: запись шаблона и daemon-reload без сборок и запуска.

## Ранний старт и блокировка

Первый синхронный импорт приложения проверяет путь и старую раскладку, затем создаёт
папку, канонизирует путь, читает `.env` и берёт блокировку. При неявной папке
оставшиеся данные в коде, неверная совместимая ссылка либо незавершённый журнал
переноса дают код 78 с командами переноса или возврата. Вторая копия репозитория
(git worktree, где `.git` — файл) без своей явной `COCKPIT_HOME` не стартует: иначе стенд
при закрытом окне поднялся бы на настоящих данных. Журнал старой сборки окна в
`<код>/server/.state` (`cockpit-server.log*`) старой раскладкой не считается. Проверка
размещения пути действует и при явной папке.

`server/scripts/dataHomeCheck.mts` проверяет те же условия без создания файлов
и запуска сервера: код 0 — можно продолжать, 78 — отказ с причиной. Пишущие
запускалки вызывают его до действий. Юнит содержит `RestartPreventExitStatus=78`.
До переноса после обновления кода сервер не перезапускать и окно не закрывать.

`state/server.lock` создаётся атомарно с правами 0600 и содержит `pid`, `starttime`,
`root`, `startedAt`. Совпадение pid и времени старта из `/proc` подтверждает владельца;
если `/proc` недоступен, живой pid считается владельцем. Второй сервер ждёт до
`COCKPIT_LOCK_WAIT_MS` (по умолчанию 15 секунд), затем выходит с кодом 78.
Мёртвая или повреждённая блокировка переименовывается в уникальное имя, сверяется и
заменяется новой. При выходе сервер снимает только собственную блокировку;
после SIGKILL её разбирает следующий старт. `restart.sh` ждёт выхода PID до 45 секунд,
а не только освобождения порта.

## Команды и тесты

До переноса старые CLI-токен и `.env` читает только CLI `cockpit`: пока в папке данных
нет токена или файла настроек, а на старом месте — настоящий каталог или файл. Пустая папка,
созданная раньше времени, это чтение не отрезает. `b24` старую раскладку не читает
([команда b24](../b24/binary-cli.md)): с явными `COCKPIT_URL` и `COCKPIT_TOKEN` папка данных
ему не нужна, без токена он отказывает до HTTP-запроса и называет ожидаемый путь.

Сторож памяти создаёт временную `COCKPIT_HOME`, проверяет её и удаляет после прогона.
Он же снимает `COCKPIT_ENV_FILE`, `COCKPIT_UI_RELEASES_DIR` и `COCKPIT_LOG`, которые сервер
передаёт агентам из `.env`. Фикстуры сервера задают собственные HOME и COCKPIT_HOME внутри
`os.tmpdir()`; песочницы CLI и ярлыка наследуют окружение, но заменяют HOME, XDG и
COCKPIT_HOME. Проверки systemd используют
заглушки. Ядро переноса при `NODE_TEST_CONTEXT` дополнительно запрещает реальные
пути. Сканер миграции кода исключает корневые каталоги данных до обхода; сторож
`data-home-paths` проверяет построение путей только в исходниках.

## Ограничения

- Старые тексты чатов и комментарии Б24 сохраняют абсолютные пути вложений. После
  переноса они указывают на прежнее место; превью по имени файла работают.
- Рабочую папку чата внутри прежних `plugins/` или `3d/` нужно выбрать заново; рабочая
  папка Kimi в режиме contained внутри папки данных отклоняется.
- Файлы `.env` внутри рабочей папки Kimi contained не маскируются (маскируются только
  каталоги): копия со своей явной `COCKPIT_HOME` и настоящим `<копия>/.env` видна агенту.
- Перенесённые `bin/pip` и `activate` venv содержат прежние пути и после уборки ссылок
  не работают; вызов через `bin/python` работает, включая `bin/python -m pip`.
- Собственные файлы плагинов (запускалки, конфигурации в `state/plugins/<id>`) перенос не
  переписывает. Абсолютный путь к прежнему `<код>/plugins/<id>` ломается сразу: ссылки
  совместимости для `plugins/` нет. После переноса такие места находит
  `rg -l '<код>/plugins/' <папка>/state/plugins <папка>/plugins`.
- Записи процессов заданий (`identity.cmdline`, `process.cmdline`), рабочие файлы завершённых
  заданий и `task.mediaHfDir` старых заданий речи сохраняют прежние пути. Это история:
  на работу и на `--drop-links` она не влияет.
- Перенос и работа на реальных данных требуют действий владельца. Тесты проверяют
  временные фикстуры; они не означают, что данные установленной копии уже перенесены.
