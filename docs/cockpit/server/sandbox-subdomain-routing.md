# Адреса стендов снаружи — ПОДДОМЕН, не подпуть

`web/src/shared/sandbox.js`: локально (http либо литеральный адрес/localhost) — прямо по порту
`http://<хост>:<порт>`; через шлюз (https + доменное имя) — `https://p<порт>.<хост>`.

Подпуть (`/sandbox/7900/`) не годится принципиально: дев-сервер Vite отдаёт ассеты от корня
(`base: '/'`), под подпутём ломаются и пути, и HMR-вебсокет. На поддомене пути остаются
корневыми и стенд работает как дома.

Порт живёт в ИМЕНИ, потому что наружу открыт только 443. Локальный Caddy на мозге достаёт его
регуляркой из `Host` — **диапазоны ограничены сознательно** (`51[7-9][0-9]`, `80[89][0-9]`):
без ограничения прокси стал бы дверью к любому локальному порту, включая сам кокпит в обход
входа, внутренние БД и административные сервисы. Стенды своей авторизации не имеют вовсе, поэтому на шлюзе перед ними
стоит `forward_auth` к `/api/auth/state`.

Требует DNS: `<домен>` и `*.<домен>` — обе A-записи на адрес VPS.

**Сертификаты — on-demand, а НЕ wildcard.** Блок `*.<домен>` в Caddyfile выглядит очевидным
решением, но он требует ИМЕННО wildcard-сертификата, а тот выдаётся только через DNS-01 —
то есть на VPS нужен и плагин Caddy под конкретного DNS-провайдера, и постоянно лежащий
там API-токен от всей зоны. Поэтому: кокпит — именованный блок (обычный HTTP-01), стенды —
catch-all `https://` с `tls { on_demand }`, по HTTP-01 на каждое имя. DNS-API не нужен вовсе.
Поддерживаемый DNS-провайдер технически позволяет DNS-01, но выбор остаётся прежним: держать
на шлюзе токен, которым правится вся зона, дороже, чем
не иметь его там вовсе. Токен Cloudflare передаётся заново на каждую установку, живёт только
в памяти хода и на VPS не уезжает. Ему нужны `Zone:Read` (найти родительскую зону) и
`DNS:Edit` на одну конкретную зону; готовый шаблон «Edit zone DNS» даёт только второе право.
В редакторе токена это две разные строки: `Zone → Zone → Read` и `Zone → DNS → Edit`.
Частая ошибка — оставить во второй строке `Zone → Zone → Edit`: визуально похоже, но права
редактировать DNS-записи такое разрешение не даёт, поэтому API закономерно отвечает 403.

Выбранный поддомен — выделенная область шлюза. Перед подтверждением кокпит читает все страницы
DNS в этой области и показывает план, а после успешной проверки SSH одним Cloudflare batch
приводит **ровно два owner name** (`<домен>` и буквальный `*.<домен>`) к инварианту: по одной
A-записи на текущий IPv4 VPS, TTL 60, **серое облако** (`proxied: false`). Лишние A, старые
AAAA и CNAME на этих двух именах удаляются; TXT/MX/CAA, соседние и произвольные дочерние имена
не трогаются. NS/DS, HTTPS/SVCB и точные `p<разрешённый-порт>.<домен>` блокируют автоматическую
установку с объяснением: первые нельзя безопасно сносить, а последние перекрывают wildcard,
даже если это всего лишь TXT. Предпросмотр подписан отпечатком batch-плана: если зона успела
измениться до установки, кокпит ничего не удаляет и требует нового подтверждения. После
batch кокпит перечитывает API и проверяет постусловие;
публичный DNS принимается только если A-ответ состоит из одного текущего IP, а AAAA отсутствует.
Публичная проверка идёт через DNS-over-HTTPS Cloudflare и Google, а не через `node:dns`:
c-ares шлёт запрос без EDNS, и такой запрос у рекурсивного резолвера может попасть в отдельный
отрицательный кеш старого NXDOMAIN. В регрессионном сценарии authoritative DNS и DoH уже видели новые
записи, но no-EDNS-кеш держал отсутствие по SOA ещё до 30 минут — пяти минут визарда заведомо
не хватало. Ошибка любого из двух DoH-провайдеров остаётся fail-closed: сбой запроса не считается
доказательством отсутствия AAAA.
План не дробится на несколько запросов: для общего атомарного лимита Free-тарифа допускается
не больше 200 мутаций; при большем числе дублей часть нужно сначала удалить вручную.

Оранжевое облако означает Cloudflare-прокси, а с ним возвращаются ровно те
ограничения, из-за которых отвергнут Cloudflare Tunnel (100-секундный потолок ответа,
100 МБ на тело, чужая терминация TLS) — см. раздел о границах вариантов ниже.

Сценарий временного VPS поддерживается повторной установкой: новый запуск заново заменит старый
адрес текущим. Но выключение/удаление VPS само очистить Cloudflare не может — токен намеренно
не хранится. Пока отдельного teardown-действия нет, перед освобождением IP две записи нужно
удалить вручную, иначе домен продолжит указывать на адрес, который провайдер может выдать другому.
При первом переводе старый TTL мог уже попасть в кеш публичных резолверов дольше пяти минут;
после первой успешной синхронизации TTL 60 делает последующие переключения быстрыми.

`on_demand_tls { ask ... }` **обязателен**: без него любой, направив своё имя на наш адрес,
заставит выпускать сертификаты, пока не упрёмся в лимиты Let's Encrypt. Разрешение выдаёт сам
кокпит — `GET /api/gateway/tls-allow?domain=…` (`modules/gateway`, публичный: Caddy зовёт его
до всякой авторизации, данных не отдаёт). Пускает только сам домен и `p<порт>.<домен>` с портом
из разрешённых диапазонов; `isAllowedGatewayHost` прогнан по 15 случаям, включая отказ для
`p8140` (кокпит в обход входа), `p3306`, `p8123`, вложенных меток и подделок вида
`p5191.<домен>.evil.com`.

**Две ошибки, найденные при сборке этой связки** (обе были бы видны только на живом сервере):

1. `forward_auth` нельзя направлять на `/api/auth/state` — тот отвечает **200 и невошедшему**
   (`authenticated: false` в теле), а `forward_auth` смотрит только на код и пускал бы всех.
   Нужен отдельный `GET /api/gateway/authz` под гардом: без сессии 401, с сессией 204 без тела.
2. Сессионная cookie по умолчанию **host-only** — на поддомен стенда браузер её не отправит,
   `forward_auth` не увидит сессию и стенды окажутся недоступны. Нужен явный `Domain=<домен>`
   (`cookieDomain`), но ТОЛЬКО когда запрос пришёл на публичный домен: на localhost cookie
   с чужим `Domain` браузер отбрасывает, и вход сломается молча. Цена — cookie видна всем
   поддоменам; все они наши, а `HttpOnly` не даёт прочитать её из JS.
