# Команда b24: один исполняемый файл, настройки, коды выхода и установка

Команда `b24` нужна навыкам, хукам агентов и этапу SHIP фабрики. Исходник — TypeScript-пакет
`b24/` (код в `b24/src`); сборка превращает его в один исполняемый файл Node SEA `bin/b24` —
ELF для Linux x64 на закреплённом официальном Node 24.21.0. Готовому файлу не нужны
установленные Node, curl и jq; лицензия Node вшита в него (`b24 --license`). С порталом команда
не говорит: каждый запрос идёт в локальный HTTP API Cockpit
([граница B24](integration-boundary.md)). Команды и поля задачи — в
[CLI для агента и оператора](agent-and-operator-cli.md).

## Сборка

`npm --prefix b24 run build` собирает `<код>/bin/b24`; нужны esbuild и postject из
devDependencies пакета (`npm --prefix b24 ci --include=dev`). Порядок шагов:

1. Платформа, кроме Linux x64, — отказ.
2. Архив Node берётся из кэша `b24/.cache` и при каждой сборке сверяется с SHA256 из
   `b24/build/node-runtime.json`. Нет архива или сумма не совпала — загрузка с nodejs.org:
   до пяти попыток с паузой 10 с, срок одной загрузки 120 с; в кэш попадает только архив с
   верной суммой.
3. Путь назначения ещё отслеживается git — отказ: файл около 120 МиБ ушёл бы в коммит.
4. esbuild собирает один CommonJS-bundle; любое предупреждение — отказ.
5. Закреплённый Node готовит blob SEA, postject внедряет его в копию того же Node. Конфигурация
   SEA запрещает расширять аргументы Node (`execArgvExtension: none`): `NODE_OPTIONS` готовый
   файл не применяет.
6. Готовый файл запускается с `--version` в пустом окружении; вывод обязан совпасть с версией
   пакета и закреплённого Node.
7. Публикация атомарна: копия рядом с целью, права 0755, rename. При любом отказе прежний
   `bin/b24` остаётся целым.

Сборщик печатает путь, размер и SHA256 результата. Неверные аргументы — код 2, отказ сборки —
код 1 и `Сборка b24 не удалась: <причина>`. Флаги `--out-dir <каталог>` и
`--cache-dir <каталог>` заменяют умолчания `bin/` и `b24/.cache/`; относительный путь считается
от текущего каталога процесса, а `npm run` запускает сборщик из `b24/`. Промежуточные файлы
живут в `<кэш>/build-*` и удаляются после сборки. git не отслеживает `bin/b24`, временные
`bin/.b24-*.tmp` и `b24/.cache/`.

## Запуск из дерева кода

`bin/cockpit b24 …` исполняет собранный `bin/b24`, если он есть и исполняемый, а без него —
исходник `node b24/src/main.ts …` на Node из PATH (^22.19.0 либо >=24.0.0). Готовый файл
запускается через `exec`: если он завершился с ошибкой, исходник не запускается, и мутация не
повторяется.

Агенты получают `<код>/bin` первым в PATH и зовут `b24` по имени; ссылка `~/.local/bin/b24`
ведёт на тот же файл. Пока файл не собран, команды `b24` по имени нет, а `bin/cockpit b24 …`
работает через исходник.

`--help` (`-h`), `--version` и `--license` допустимы только единственным аргументом и не читают
настройки. `b24 --version` печатает версию пакета и исполняющего Node.

## Адрес и токен

- Заданы оба `COCKPIT_URL` и `COCKPIT_TOKEN` — папка данных и файлы не читаются; даже неверная
  `COCKPIT_HOME` не мешает.
- Иначе читается файл настроек `COCKPIT_ENV_FILE`, без неё — `<папка данных>/.env`
  (по умолчанию `~/.cockpit/.env`). Файл разбирается как данные (`util.parseEnv`): нет файла —
  пустой набор, другой отказ чтения — код 1 с путём. Ключи `COCKPIT_HOME` и `COCKPIT_ENV_FILE`
  в файле запрещены.
- Адрес — `COCKPIT_URL`, иначе `http://localhost:<порт>`, где порт — `COCKPIT_PORT`,
  по умолчанию 8140. `COCKPIT_URL` — HTTP(S) без учётных данных, query и fragment; конечные `/`
  убираются. Неверный адрес или порт — код 1 до HTTP.
- Токен — `COCKPIT_TOKEN`, иначе содержимое файла `COCKPIT_CLI_TOKEN_PATH`, по умолчанию
  `<папка данных>/state/cli-token`; пробелы и переводы строк по краям файла обрезаются.
- Экспортированные переменные важнее файла. Пустые `COCKPIT_PORT` и `COCKPIT_CLI_TOKEN_PATH`
  в окружении тоже перекрывают файл и дают умолчание; `COCKPIT_URL` и `COCKPIT_TOKEN` из файла
  не берутся.
- Правило общее с `cockpit status`: `resolveRuntimeSettings` в `shared/runtime/runtimeSettings.ts`,
  папка данных — `shared/runtime/dataHome.ts` ([единая папка данных](../server/data-home.md)).
- Старую раскладку (`<код>/.env`, `<код>/server/.state/cli-token`) b24 не читает; у CLI
  `cockpit` переходное чтение пока осталось.

## Запросы, вывод и коды выхода

Каждая команда — один HTTP-запрос к `/api/b24/…` с заголовком `X-Cockpit-Token`; `start <id>` —
renew с подавлением его ошибки, затем timer/start. Транспорт — `node:http` / `node:https` с
собственным агентом на каждый запрос, созданным без `proxyEnv`. Прокси не используются:
`HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, их варианты в нижнем регистре и `NODE_USE_ENV_PROXY`
не влияют на запрос. Повторов и переходов по redirect нет. Собственный срок простоя сокета —
300 с, столько же, сколько прежнее ожидание заголовков и очередной порции тела во fetch Node.
После ответа или отказа агент закрывается, процесс не ждёт освобождения соединений.

| Исход | Код | Вывод |
| --- | --- | --- |
| HTTP 2xx | 0 | тело ответа в stdout байт в байт |
| HTTP вне 2xx, в том числе 3xx | 22 | `Запрос к Cockpit завершился ошибкой HTTP <код>: <причина>` |
| Сетевой отказ, обрыв тела ответа | 22 | `Не удалось связаться с Cockpit.` |
| Заголовки или порция тела не пришли за 300 с | 22 | операция могла выполниться: проверить результат перед повтором |
| Нет токена | 1 | `Нет токена: <путь>.` до HTTP |
| Неверные настройки, не прочитан stdin `create` | 1 | причина до HTTP |
| Неверные аргументы | 2 | причина и справка |

При отказе stdout пуст, а причина по-русски — в stderr. Причина HTTP-отказа — поле `message`
JSON-тела сервера: читается не больше 64 КиБ тела, каждое вхождение токена соединения заменяется
на `***` до обрезки, управляющие символы C0, DEL и C1 — пробелом. Причина ограничена 500 знаками
с многоточием при обрезке. Неверный JSON, другой Content-Type и тело больше 64 КиБ дают пустую
причину. Без поля `message` сообщение кончается кодом HTTP (`… ошибкой HTTP <код>.`);
остальное тело не показывается. Простой 300 с, в том числе при чтении тела HTTP-отказа,
даёт предупреждение о возможно выполненной операции: мутация уже могла выполниться на сервере.
Успешное тело читается целиком до записи, поэтому обрыв после статуса
200 даёт пустой stdout и код 22. Закрытый получатель stdout (EPIPE) отказом не считается, другая
ошибка записи — код 1.

Прежняя bash-обёртка на `curl -sf` давала 22 только на HTTP ≥ 400, 7 на отказ соединения и 0 с
телом на 3xx; неизвестная команда завершалась кодом 1.

## Установка и обновление

`deploy/install.sh` вызывает `cockpit_install_b24_cli` из `deploy/lib/b24-cli.sh`:

- `npm ci --include=dev` в `b24/` выполняется, если нет `b24/node_modules/esbuild` или
  `b24/node_modules/postject`: до пяти попыток с паузой 10 с;
- сборка выполняется всегда, даже при готовом `bin/b24`;
- если пакеты уже были и сборка не удалась, helper предупреждает, выполняет `ci` с теми же
  пятью попытками и повторяет сборку один раз. После `ci`, уже выполненного в этом вызове,
  нового повтора нет; окончательный отказ `ci` или сборки возвращает код 1;
- после проверки, что `bin/b24` появился и исполняемый, ссылка `~/.local/bin/b24 → <код>/bin/b24`
  заменяется атомарно; обычный файл или каталог на её месте не перезаписывается — предупреждение;
- отказ шага b24 не прерывает установку: прежняя ссылка остаётся, установщик печатает команду
  повтора `bash "<код>/deploy/lib/b24-cli.sh" "<код>" ~/.local/bin`, которая собирает файл
  и создаёт ссылку. В напечатанной команде все пути абсолютные и экранированы через `printf %q`,
  поэтому её можно выполнить из любого каталога, в том числе при пробелах в путях;
- `--unit-only` b24 не трогает.

Здесь `<код>` — абсолютный путь к корню Cockpit. Прямой запуск `deploy/lib/b24-cli.sh`
вызывает helper с переданными аргументами и возвращает его код; `source` только определяет функции.

Встроенное обновление (кнопка «Обновить», `cockpit-update-worker`) b24 не собирает. Переход на
выпуск с собранным b24 убирает из дерева прежнюю bash-обёртку, поэтому после такого обновления
нужен `deploy/install.sh` или `bash "<код>/deploy/lib/b24-cli.sh" "<код>" ~/.local/bin`.
Последующие обновления тоже оставляют прежний `bin/b24` до пересборки.

b24 — часть серверной поставки: навыки и хуки агентов работают там, где сервер. Установщик окна
b24 не собирает.

## Проверки

- `npm --prefix b24 test` — проверка типов пакета вместе с `tests/b24`, затем
  `tests/b24/*.test.mts` через сторож памяти. Входит в `tests/run-all.sh`; нужны devDependencies
  пакета (`npm --prefix b24 ci --include=dev`).
- `npm --prefix b24 run test:sea` — медленный набор `tests/b24/sea`, в run-all не входит. Он
  собирает свежий файл во временный каталог (архив Node копируется из `b24/.cache` или
  скачивается) и проверяет его: запуск копии без исходников с пустым PATH, игнорирование
  `NODE_OPTIONS`, обход прокси при `NODE_USE_ENV_PROXY=1`, запросы через loopback, настройки
  папки данных, коды отказов и сохранность
  прежнего результата при неудачной сборке.
- `COCKPIT_B24_TEST_BINARY=<файл>` — абсолютный путь к исполняемому файлу — проверяет его
  вместо свежей сборки; после прогона сверяется, что файл не изменился.
- Ветки `bin/cockpit b24` проверяет `tests/cli/entry.test.mts`
  ([песочница единой команды](../testing/cli-sandbox.md)), шаг установщика —
  `tests/b24/install.test.mts` с заглушкой npm, состав `bin/` — `tests/docs/bin-layout.test.mts`.
