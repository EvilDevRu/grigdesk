# Интеграция Битрикс24

Cockpit — единственный владелец портальной сессии Битрикс24. Доска, мутации, агенты и
хуки обращаются к порталу через сервер Cockpit или локальный `bin/b24`; отдельный процесс
не должен читать креды и перезаписывать основной cookie jar.

## Авторизация и слои

Официальный REST/вебхук для этой установки недоступен. `B24Client` входит как браузер:
отправляет форму `/salary/?login=yes`, хранит сессионные cookies и использует
`bitrix_sessid` для CSRF. `USER_REMEMBER=Y` делает сессию долгоживущей. При сетевом сбое,
потере авторизации или протухшем sessid клиент выполняет ограниченные ретраи, а не
бесконечный цикл.

- `server/src/lib/b24/b24-client.js` — протокол портала, cookies, задачи, таймеры,
  комментарии, файлы и статусы.
- `server/src/adapters/b24.js` — ленивый клиент и обязательная promise-очередь `_run`.
  Клиент не потокобезопасен: параллельные операции с общей сессией приводили к
  `Client Error`. Подробность инцидента хранится в [gotchas.md](gotchas.md).
- `server/src/modules/b24/index.js` — локальный HTTP API Cockpit.
- `server/src/lib/b24/creds-store.js` — credentials из `server/.state/b24-creds.json`
  с режимом `0600`; менять и проверять их нужно через «Настройки → Битрикс24».
- `bin/b24` — CLI поверх локального HTTP-порта. Токен берётся из `COCKPIT_TOKEN` либо
  `server/.state/cli-token`.

Локальное расширение резервного dashboard может использовать отдельный cookie-файл.
Это допустимо только при полной изоляции от основного cookie jar Cockpit; конкретная
реализация и её путь документируются внутри соответствующего профиля.

## CLI для агента и оператора

Доступные команды:

```text
b24 dashboard
b24 task <id>
b24 comment <id> <текст>
b24 timer <id> start|pause|stop
b24 start <id>
b24 complete <id>
b24 renew <id>
b24 create                 # JSON читается из stdin
b24 users [запрос]
```

Просьба «поставь задачу в Битриксе» выполняется сразу через `b24 create`, без поиска
другого API и без предварительной проверки сессии:

```bash
b24 create <<'JSON'
{"title":"Краткий заголовок","description":"Суть, шаги и проверяемые кейсы","priority":1}
JSON
```

Текст задачи содержит конкретные ID, URL и даты, если они известны, но не содержит код
или неподтверждённые гипотезы о причине, если человек их не просил. После успеха достаточно
вернуть номер или ссылку задачи.

Поля создания:

- `priority`: `0` низкий, `1` средний, `2` высокий; поддерживаются и словесные алиасы.
- `responsibleId`: обычно не передавать либо передавать `null` — клиент подставит текущего
  пользователя. Значение `0` не является дефолтом и уходит на портал буквально; портал
  отвечает ошибкой о несуществующем исполнителе, а `curl -sf` скрывает тело и завершает
  команду кодом 22. Свой ID виден в `b24 dashboard`, другого исполнителя нужно сначала
  найти через `b24 users <запрос>`. Конкретные пользовательские ID не хардкодятся.
- `groupId`: пропуск, `null` или `0` означает задачу без группы.
- `createdById`: без явной необходимости не передавать — портал использует владельца сессии.
- `images`: список файлов, которые клиент сначала загрузит на диск портала.

Проверка валидности приоритета выполняется до входа и загрузки файлов. Ошибка авторизации
или портала возвращается самой командой; отдельный профилактический запрос не нужен.

## HTTP API Cockpit

Читающие маршруты:

- `GET /api/b24/dashboard`, `/api/b24/task/:id`, `/api/b24/task/:id/comments`;
- `GET /api/b24/users?q=...` — ростер для выбора ответственного;
- `GET /api/b24/groups` — доступные активные проекты/рабочие группы для выбора
  `GROUP_ID` задачи (`{groups: [{id, name, type}]}`).

Мутации:

- `POST /api/b24/tasks`;
- `PUT /api/b24/task/:id` — частичное обновление основных полей;
- `POST /api/b24/task/:id/comment`;
- `POST /api/b24/task/:id/timer/:action`;
- `POST /api/b24/task/:id/complete`;
- `POST /api/b24/task/:id/renew`.

`B24Client.deleteTask` существует, но HTTP и CLI намеренно его не публикуют.

### Редактирование задачи

Карточка `TaskModal` редактирует заголовок, описание, исполнителя, проект и приоритет,
не уводя человека на портал. Для исполнителя и проекта она использует те же серверные
справочники `/users` и `/groups`, что формы постановки задач. Текущее значение остаётся
в селекте даже после исчезновения сотрудника или проекта из активного справочника.

Тело `PUT /api/b24/task/:id` — частичный объект из полей `title`, `description`,
`responsibleId`, `groupId`, `priority`. Неизменённые поля браузер не присылает, а сервер
отклоняет неизвестные: это не даёт очищенному отображению HTML-описания затереть исходник
при правке одного заголовка. Пустая строка `description` очищает описание, `groupId: null`
снимает проект, приоритет `0` остаётся значимым низким приоритетом. Пустой набор изменений,
пустой заголовок, неизвестные поля и невалидные ID получают `400 b24_bad_request` до сети.

После успешного `tasks.task.update` маршрут заново читает задачу и разворачивает Telegram-
ссылки, поэтому ответ совпадает с DTO обычного `GET /api/b24/task/:id`. Стор заменяет им
кеш деталей и перечитывает доску. Если изменилась постановка уже оценённой задачи, UI
не запускает модель самовольно, а явно предлагает человеку нажать «Переоценить».

Комментарий пишет и конвейер: если профиль перечисляет `task-comment` в
`profile_delivery_actions` (см. `docs/engine/PROFILE-CONTRACT.md`), Cockpit запускает
publish-маршруты с `--task-comment`, и узел `ship` после создания/обновления PR
оставляет в задаче комментарий со ссылками на них. Действие закреплено в immutable
delivery contract попытки; маршрутам без `ship` и профилям без этого действия в хуке
оно не выдаётся.

## Личное состояние задач: избранное, полка и просмотренное

Все три механизма — **свойство человека, а не задачи**: в портал они не пишутся вовсе, живут в
state кокпита и потому одинаковы на всех его окнах. Открыл задачу на компьютере — на
планшете она перестала быть новой; localStorage такого не умеет, отсюда серверное
хранение.

| метка | API | файл state |
|---|---|---|
| избранное («звезда») | `GET /api/b24/task-favorites`, `PUT`/`DELETE .../:taskId` | `task-favorites.json` |
| полка («жду событие») | `GET /api/b24/task-shelf`, `PUT`/`DELETE .../:taskId` | `task-shelf.json` |
| просмотрено («новая») | `GET`/`POST /api/b24/task-seen` | `task-seen.json` |

Общее устройство (`lib/task-{favorites,shelf,seen}-{store,service}.js`, модули
`modules/task-{favorites,shelf,seen}/`):

- **scope клиент не выбирает** — он выводится из текущей портальной сессии
  (`b24AccountScope` = sha256 от нормализованного адреса портала и id пользователя) и
  наружу отдаётся только opaque-хешем. Попросить чужой набор нечем; смена аккаунта
  портала сама даёт другой набор, а не подмешивает метки прежнего.
- Файл — `{schemaVersion, scopes: {<scope>: {revision, …}}}` в `server/.state` (0600),
  запись атомарная (tmp+rename) и под общей promise-очередью: rename защищает от обрыва,
  но не от lost update при двух окнах разом.
- Ответ всегда полный снимок с `revision`; клиент применяет его только если снимок
  свежее (`applySnapshot`), иначе поздний ответ уже неактуального запроса вернул бы
  стёртую метку. Оба чтения отдаются с `Cache-Control: no-store`.
- Отказы названы поимённо: `400 bad_task_id`/`bad_request`, `503 b24_identity_unavailable`
  (не смогли определить пользователя портала), `503 task_seen_unavailable` (сохранённое
  не изменено), `503 task_shelf_unavailable` (полка не прочитана и не перезаписана).
  Кап набора отметок — 2000 задач, кап одного запроса — 1000 id; к полке эти два
  лимита не относятся, её entry ограничен собственной строгой схемой.

Полка хранит entry `{taskId,title,addedAt,reason,snapshot}`. `addedAt`, scope и revision
назначает сервер; PUT принимает `createIfMissing`, поэтому ручная/автоматическая постановка
создаёт запись, а acknowledge карточки обновляет только существующую. Удаляет запись только
DELETE: событие и просмотр ничего не снимают, а поздний acknowledge после DELETE её не
воскрешает. Ответ каждого GET/PUT/DELETE — полный `{scope,revision,entries}` с `no-store`.
Состояние готового триажа в `snapshot.analysis.state` называется `done`, как в самом
`Analyzer`; `finished` оставлен для совместимости с ранними снимками полки.
Запись и временный файл имеют режим 0600, commit идёт атомарным tmp+rename под одной
promise-очередью. Выключение плагина закрывает API живым `plugin_disabled`, но файл не
меняет; после включения прежний список возвращается. Полка не читает и не меняет
`task-favorites`: звезда и ожидание законно существуют одновременно.

**Базовая линия `initialized` — главный инвариант «новых».** Пустой набор отметок означает
«сервер ещё не ответил», а не «ни одной задачи не открывали»: без этого различия первое
же появление метки объявило бы новыми все давние задачи разом. Поэтому `initialized`
поднимает ТОЛЬКО запрос с `baseline: true`, и делает его ровно одно место — `board.load()`
после первого успешного ответа портала (`markBaselineSeen`; пустая доска тоже базовая
линия — иначе флаг не поднялся бы никогда). Во фронте это геттер `ready = loaded &&
initialized`, и от него зависит всё: метка «новая» в строке, счётчик «новые N», фильтр
«только новые» (кнопка `disabled`, пока отметки грузятся) и `unseenCount` чипа доски
(`shared/board-activity.js` принимает `{ ready }` третьим аргументом).

Снимается метка **только открытием карточки задачи** (`TaskModal` → `seen.markSeen([id])`) —
заход на доску не считается просмотром, иначе метка гасла бы у всего списка сразу.
Отказ отметки на показ задачи не влияет: действие возвращает `false` и не бросает, а
человек видит плашку с кнопкой «Повторить» над списком.

## Протокол портала

- Дашборд задач приходит из `/local/ajax/dashboard.php?action=getTodayData`; месячная
  статистика и графики извлекаются из HTML `/salary/`.
- `getTaskDetails` не отдаёт вложения и комментарии. Они парсятся из HTML страницы задачи:
  файлы — из `#task-detail-files`, комментарии — из блоков `record-TASK_*`; системные
  комментарии помечены `mpl-comment-aux`.
- Ростер приходит через `getAvailableUsers`, поиск по имени выполняется локально по всем
  токенам запроса.
- Проекты для селекта задачи приходят через сессионный
  `socialnetwork.api.workgroup.list`: только активные и неархивные, по 50 элементов
  с навигацией `nav=page-N-size-50`. Результат кешируется на время жизни `B24Client`;
  форма показывает человеку имя, а сохраняет числовой `groupId`.
- Создание использует `tasks.task.add` и form-urlencoded поля. Проверка `priority !== null`
  принципиальна: нулевой приоритет валиден.
- Редактирование использует `tasks.task.update` и передаёт только явно изменённые поля.
  Для снятия проекта в `fields[GROUP_ID]` уходит `0`; пустое описание передаётся буквально,
  а не пропускается. CSRF-ретрай повторяет только update-запрос.
- Файлы загружаются сырыми чанками до 10 МБ через `ui.fileuploader.upload` и
  `disk.uf.integration.diskUploaderController`. `serverFileId` вида `n<objectId>` идёт в
  `UF_TASK_WEBDAV_FILES` задачи либо `UF_FORUM_MESSAGE_DOC` комментария.
- Комментарий отправляется через `bitrix:forum.comments` с `signedParameters` со страницы
  задачи. Текст обязателен даже при наличии вложения; комментарий уведомляет участников.
- Таймер использует `/local/ajax/task_timer.php` с действиями `start`, `pause`, `stop`.
- `complete` сначала явно останавливает таймер и только затем вызывает
  `tasks.task.complete`: портальный автостоп ненадёжен и может не записать время в журнал.
- На сданной или завершённой задаче перед запуском таймера нужен `tasks.task.renew`.
  Без renew портал может вернуть старый `started_at`, хотя таймер реально не идёт.
- Публичные ссылки Яндекс.Диска разрешаются через cloud-api; прямые изображения
  скачиваются. Закрытые Telegram-ссылки и видео этим путём не загружаются.

## Статусы и приоритет обработки

Коды портала: `2` — ждёт выполнения, `3` — выполняется, `4` — сдана и ждёт приёмки
постановщиком, `5` — завершена, `6` — отложена, `7` — отклонена. Для статуса 4 действие
принадлежит постановщику, а не ответственному.

`describeStatus` вычисляет, требуется ли действие текущего пользователя. Триаж сортирует
задачи так: требующие действия → ручной `custom_priority` → горящие → просроченные →
обычный приоритет по убыванию → дедлайн → ID.
