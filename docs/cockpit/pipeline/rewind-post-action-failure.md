# Возврат курсора записан, а человек видит отказ: пост-шаг goto ронял решение

Симптом: в модалке узла человек пишет указание агенту, жмёт «▶ Перейти сюда» — и
получает ошибку. Плашка остановки остаётся прежней, узел по-прежнему «вернул решение
человеку», прогон стоит. Читается как «кнопка не работает, текст никуда не ушёл»,
и человек жмёт её снова.

На деле возврат **состоялся**: событие `human-rewind` записано в immutable журнал
попытки вместе с полным текстом, курсор перешёл `stopped → ready`. Упал пост-шаг,
идущий уже ПОСЛЕ решения, — телеметрия визита узла:

```bash
if [[ -n "${FACTORY_LIFECYCLE_NODE_VISIT_ID:-}" ]]; then
  stage_hash=$(v2_lifecycle_latest_stage_hash "$EXPECTED_ATTEMPT") || return   # молча
  runtime_lifecycle_node_visit_finish_v2 … >/dev/null || return               # молча
fi
```

Оба `|| return` были без `v2_log`, поэтому в `logs/t<TASK>.stages.log` не появлялось
НИ ОДНОЙ строки — обычный первый признак «движок даже не звался». Дальше срабатывала
цепочка: кокпит превращает любой ненулевой код в `409 goto_rejected`, **не выполняет
resume**, а `route_v2_project_latest_reset` до реестра не доходит — проекция остаётся
старой, и UI честно рисует прежний затык поверх принятого решения.

Правило: **всё, что идёт после записи решения в журнал попытки, не вправе это решение
отменить.** Возврат зафиксирован в immutable ledger, курсор сдвинут, lifecycle человека
закрыт — потерянная строка телеметрии дешевле потерянного решения. Отказ аналитики
теперь называется в журнале и обход продолжается; провал `route_v2_project_latest_reset`
остаётся настоящим отказом (без проекции UI показывает прошлое состояние).

Как узнать этот случай за один взгляд, не читая код: сравни журнал этапов с журналом
попытки. Строк нет, а событие есть — значит упал пост-шаг, и работа сделана:

```bash
tail -3 ~/.factory/state/logs/t<TASK>.stages.log
python3 -c "import json;print(json.load(open('runtime.json'))['runtime']['cursor'])" \
  # …/control/protocol-v2/tasks/t<TASK>/attempts/<attempt>/stage-results/runtime.json
```

`cursor.state == "ready"` при видимом на экране затыке означает, что возврат уже принят
и нажимать «Перейти сюда» второй раз не нужно — нужен **resume**. Повторное нажатие
запишет второй такой же `human-rewind`: не сломает, но засорит журнал попытки.

Сторож — `tests/engine/unit/route-goto-telemetry-nonfatal.sh` (статический: правка живёт
внутри большой `v2_admin_main`, изолированно её не вызвать, а регресс возвращается одной
строкой).

Смежное: у `abandon` телеметрия идёт ДО `attempt_state_abandon_v2`, поэтому при её
отказе попытка ещё не закрыта. Историческая ссылка вопроса на уже завершённый визит
не должна попадать в текущий контекст административной команды: иначе первая команда
закрывает вопрос, затем падает на повторном завершении визита, а вторая проходит.
