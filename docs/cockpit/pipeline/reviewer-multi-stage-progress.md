# Проверяющий, который ведёт этапы, встаёт на третьем проходе: сторож топтания считает этап неснятым замечанием

Маршрут из двух узлов «проверяющий ставит задание → исполнитель делает → проверяющий
принимает или возвращает» напрашивается и для длинной работы: проверяющий принимает этап
и отдаёт следующий тем же `failed` с новыми находками. Движок так работать не даёт. Его
сторожа топтания написаны для цикла «исправь закрытый список дефектов», и следующий этап
для них неотличим от замечания, которое ремонт не снял.

Замер — настоящие `scope_expansion_reason` и `no_progress_reason` из python-блока
`engine/lib/attempt-stage-state.sh` на серии вердиктов проверяющего, с лимитами typed
verdict из `route-runtime.sh` (`no_progress_limit=2`, `hard_rewind_limit=6`):

| Как проверяющий ведёт этапы | Где встаёт маршрут |
|---|---|
| все этапы объявлены на первом проходе, исполнитель закрывает по одному | 3-й проход: «ремонт не снимает замечания» — будущие этапы пережили два ремонта |
| каждый проход приносит следующий этап | 3-й проход: «замкнутый набор замечаний расширен новыми id» — допуск на расширение один |
| владелец возврата сменился `build` → `tests` | 2-й проход: «сменил владельца», хотя обе ветки ведут к одному исполнителю |

Сверху — потолки: 6 автоматических возвратов в серии после решения человека и 10 в один
узел за попытку, причём последний решение человека не обнуляет. Значит, пока движок не
различает «этап принят» и «замечание не снято», одна попытка такого маршрута вмещает не
больше двух заходов исполнителя, дальше остановка ждёт человека.

Вторая ловушка той же схемы — переход по отказу самого исполнителя. Честный частичный
результат («закрыл два замечания из четырёх») исполнитель сдаёт `failed`, и если
маршрут ведёт `failed` исполнителя в `stop: human`, попытка встаёт после первого же
этапа: отчёт исполнителя проверяющему снова несёт человек. Для маршрута, где решения
принимает проверяющий, отказ исполнителя по продукту (`build`, `tests`, `plan`) должен
вести к проверяющему через `next`, а к человеку — только `environment`. Схема это
допускает: `next` вперёд по `sequence` разрешён и для `failed`, а `productFailure`
тогда стоит держать нулём — слепой повтор исполнителя тратит заход, который лучше
отдать проверке.
