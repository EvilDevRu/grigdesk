# Цикл ведущего и исполнителя пересекает несколько контрактов runtime

Ниже — ограничения движка, проверенные по исходникам. Они нужны при изменении автоматических
возвратов. Режим «цикл» (поле маршрута `loop`) построен с их учётом — контракт в
`docs/engine/ENGINE.md`, раздел «Режим „цикл“». О поведении сторожей —
[многоэтапный проверяющий](reviewer-multi-stage-progress.md).

## Событие возврата определяет и счётчик, и границу серии

В `engine/lib/attempt-stage-state.sh` функция `automatic_rewind_count` считает только
`kind=commit` с `action.rewind`, исключая rejected ворот. Любой `human-rewind`, в том числе
с машинным actor, очищает историю `automatic_rewind_verdicts`, но не прибавляет общий счётчик.
Поэтому перенос такого механизма на автоматическое продолжение после бюджета даст бесплатную
передачу исполнителю и одновременно сбросит сторожа серии.

Для обычной дуги `prepare-commit` сначала проверяет прогресс, затем предел серии, затем общий
бюджет; последние два дают один stop `rewind-limit`. Дуга lead → worker режима `loop`
проверяет границу этапа и общий потолок кругов; совпадение или уточнение findings её не
останавливает. Replay проверяет записанные события и переходы,
но не пересчитывает исторические решения сторожей. Введение новых kinds/полей требует правки
строгой схемы событий, курсора и readers, а не только функции выбора следующего узла.

Повторная сдача подавляется также по `same_last_commit` и `human_rewind_note`. При новом
способе повторно войти в тот же узел важно отличить новый визит с тем же исходом от crash retry
одного коммита. Проекции findings, notes, stage-results, времени и lifecycle читают виды событий
собственными фильтрами: неизвестное событие не становится новым визитом автоматически.

## Находки и отчёт имеют разные границы

`findings-ledger` хранит находки по sourceNode; done одного узла закрывает только его находки.
Принятие проверяющим результата автора само по себе не закрывает typed findings автора.
Failed с полным typed-набором закрывает прежние блокеры того же источника по исчезновению id;
это декларация проверяющего, не машинное доказательство исправления.

`deferred` в `run-state.sh`, `stage-result.sh` и `factory-context` означает замечание вне цели
задачи. Исход failed только с такими находками выпрямляется в done. Для будущей обязательной
работы этот статус не подходит.

В `factory-context` путь artifacts.report изменяемый, а stageResults содержит node, outcome и
sequence. Наличие файла по известному пути само по себе не удостоверяет, что это отчёт последнего
визита. Проверка свежести передачи требует отдельной связи с выполнением и его доказательствами.

Номер круга визит не различает: ручной возврат на исполнителя круг не прибавляет, и отчёт,
закрытый на запись после сдачи, перегородил бы повторный заход (`Permission denied` у
раннера). Поэтому имя отчёта вычисляется по журналу на каждый визит — `report.r<круг>.md`,
повторный `report.r<круг>.v<визит>.md`, — а `exhausted` визитом с результатом не считается.
Recover уносит все `t<TASK>.*` предшественницы в `state-artifacts` попытки (закрытые на
запись файлы переносятся `mv` без труда); архив кокпита при сносе стенда уносит отчёты
визитов по шаблону имени — иначе новая попытка той же задачи упёрлась бы в свой первый круг.

## У разных слоёв разные пределы

Основной `engine/bin/factory` вызывает `route_v2_dispatch_until_pause` с пределом 64 шага.
`engine/bin/factory-context` принимает не более 1000 stageResults и отдаёт в контекст узла
последние 120 (счёт опущенных — `evidence.stageResultsOmitted`). Симулятор `editor-step` в
`engine/lib/route_model.py` ограничивает stepIndex числом 200. Увеличение бюджета автоматических
возвратов не увеличивает эти пределы, а дополнительный вход проверяющего тоже расходует шаг.

Editor-step моделирует переходы и числовые бюджеты, но не получает историю typed findings и
не рассчитывает no-progress. Изменение только Python не расширяет строгие DTO/HTTP:
их определяют `shared/pipeline/routesEditorContracts.ts` и `server/src/modules/routes/editorApi.ts`.
Roundtrip маршрута также проходит shared-парсер, серверную схему и операции редактора над id.
Поле `loopMaxRounds` прошло все три слоя (1..300); предел шагов сценария цикла — 1200.

## Одна строка argv и env — не больше 128 КиБ

Ядро Linux ограничивает каждую строку аргумента и переменной окружения 128 КиБ
(`MAX_ARG_STRLEN`), весь набор — `ARG_MAX` (при стеке 8 МиБ — 2 МиБ). Переполнение даёт
`Argument list too long` (errno 7) в момент exec, а не при сборке значения в bash. Это
касается трёх растущих потоков:

- проекция находок для `factory-context`: при 12 этапах по 16 находок в 300 кириллических
  символов она занимает около 157 КБ — поэтому launcher отдаёт её файлом;
- промпт узла: `engine/lib/runner-launcher.sh` запускает раннер как
  `setsid bash runner-bridge.sh … "$prompt"`, то есть весь промпт — одна строка argv для
  любого раннера. Переполнение видно только в `stderr.log` запуска, а маршрут встаёт
  `exhausted` с классом «unknown». Поэтому история находок в контексте цикла ограничена;
- переменные `FACTORY_STAGE_OPEN_FINDINGS`/`FACTORY_STAGE_DEFERRED_FINDINGS`: в них уходит
  не больше записей, чем показывают блоки промпта (50 и 30).

Замер на настоящем launcher (7 этапов по 20 находок в 400 символов, журнал 143 КБ):
промпт ведущего с 20 открытыми и 16 закрытыми находками — около 82 КБ; без ограничения
истории 120 закрытых дали бы больше 128 КиБ. Каждая открытая находка такого размера
добавляет около 2 КБ (JSON контекста и блок промпта). Открытые находки ограничены
вердиктом (до 32 на узел), но на верхней границе у обоих узлов цикла и при длинной
постановке запас до 128 КиБ исчезает — это отдельный вопрос транспорта промпта.

Замер на живом прогоне (93-й круг, длинная постановка): промпт исполнителя — 112 КБ, из них
список результатов этапов (191 запись) — 17 КБ, около 90 байт на запись и двух записей на
круг. Без ограничения этого списка запаса до 128 КиБ хватало бы примерно на сотню кругов,
поэтому при потолке 300 в контекст идут только последние 120 записей.

## `IFS=$'\t' read` схлопывает пустые поля

TAB — пробельный символ IFS, поэтому ведущие и повторные пустые поля при чтении строки
пропадают: строка «TAB 3» даёт первой переменной `3`, второй — пустоту. Так обычный маршрут
без ведущего цикла получал `LOOP_MODE=1`. Отсутствие значения в выводе для bash выражают явным
маркером (`-`) или ставят поле последним.

## Остановка читается несколькими потребителями

Серверный `factoryAttemptLedger.ts` проверяет cursor/события, `stall.ts` распознаёт причины,
граф и сводка передают их в интерфейс. `factoryArbiter.ts` допускает автоматический разбор
no-progress, rewind-limit и части human. Новый бюджет или собственный механизм перепланирования
нужно согласовать со всеми этими потребителями: новое имя остановки само по себе не задаёт,
кто вправе её продолжать.

Ещё один потребитель — lifecycle-аналитика, и её контракт закрыт. Писатель
`engine/lib/attempt-lifecycle-state.sh` сверяет details каждого события с
`schemas/analytics/lifecycle-event.schema.json`, а `route-runtime.sh` прерывает визит узла,
если начало визита не записалось. Причину визита `_route_v2_lifecycle_stage_edge` выводит из
последнего события журнала попытки: `human-rewind` → `human_rewind`, rejected с возвратом →
`gate_rejected`, любой другой `action.rewind` → `route_rewind`, иначе `forward_transition`.
Причину ожидания человека задаёт `v2_lifecycle_begin_human_for_stop` в `engine/bin/factory`:
незнакомый вид остановки получает `operator_requested`. Новый вид события или остановки
без правки этих функций и enum схемы либо запишется под чужой причиной, либо не пройдёт
проверку схемы.

Каталог и промпты закреплены в attempt; resume их не обновляет. Recover создаёт новую попытку
после abandon и переносит старые выходы этапов в карантин. Передача прежнего результата новой
попытке требует сохранённых входов, а не надежды на старые изменяемые пути.
Recover копирует прежний immutable ticket дословно; новый ticket-json разрешён только start.
Сохранение файлов снаружи само по себе не передаёт новой попытке ссылки на них. Если входную
постановку нужно дополнить, существующий прямой путь — новая задача с явными входами в ticket.
