# Первый снос после вопроса человеку должен закрывать попытку

Кнопки сноса стенда в карточке задачи и в конвейере вызывают один
`POST /api/tasks/:id/sandbox/down`. Перед удалением инфраструктуры сервер выполняет
штатный `factory abandon` с exact profile/attempt. Разное поведение первого и второго
нажатия само по себе не доказывает различия API-путей.

## Историческая связь вопроса и текущий визит

При обычной остановке `failed → human` визит узла уже имеет `node_visit_finished`,
а последующий `human_intervention_started` сохраняет его `nodeVisitId` для связи
с вопросом. Наличие этого поля у вопроса не означает, что визит ещё открыт.

Раньше `runtime_lifecycle_resolve_open_human_v2` восстанавливал identity вопроса
прямо в окружении административной команды. Решение человека записывалось, но
команда наследовала уже закрытый визит. `abandon` затем пытался завершить его ещё раз
без таймера текущего процесса и выходил с кодом 78 до terminal CAS. Второе нажатие
находило уже закрытый вопрос, не наследовало этот визит и завершало снос.

Проверка предыдущей открытой сессии может перед этим вывести
`runtime analytics: open orchestrator session is unavailable`: для неё отсутствие
открытой сессии — ожидаемый код 3. Такой ранний stderr маскировал настоящий отказ
повторного закрытия визита при сборке сообщения Cockpit.

## Правило и проверка

Закрытие вопроса восстанавливает историческую identity в изолированном вызове,
сохраняя сессию текущего писателя. Только событие решения использует прежний визит;
контекст вызывающей команды и её живой визит не меняются. Hash записанного события
возвращается вызывающему процессу. Отсутствие вопроса идемпотентно; ошибки reader
и append по-прежнему возвращают отказ.

Регрессия — `tests/engine/unit/runtime-analytics-reconciliation.sh`: закрытый визит
с открытым вопросом, первая запись abandon, повтор без второго решения, сохранение
нового живого визита при resume и завершение каждого визита ровно один раз.
