# Причина остановки ищется в ОКНЕ текущего захода, а не по всему журналу

`logs/t<TASK>.stages.log` ведётся месяцами и переживает любое число прогонов. Пока
`detectStall` (`server/src/lib/stall.ts`) шёл с конца до первого совпадения без границы,
причиной объявлялась любая строка за всю историю задачи — даже та, после которой маршрут
прошёл десяток узлов.

Два живых случая 28.08.2026, обе задачи в этот момент ждали решения у ворот приёмки
(`GATE_ACCEPT=waiting`):

- у первой карточка показывала «среда профиля не готова (код 73)» с подсказкой про
  shared-стенд. Строка №5 журнала, написана за **25 дней** до того;
- у второй — снятый тремя часами ранее `no-progress`: человек вернул курсор, маршрут
  переиграл двенадцать узлов и дошёл до приёмки.

Второй случай хуже первого, и не косметикой. По `stall.stop` гейтится **арбитр** — и
кнопка в плашке, и автоматический вотчер. То есть автомат пошёл бы разбирать давно снятый
тупик и вернул бы курсор назад по уже сделанной работе, потратив на это живого агента.
Заодно ложный `found` перебивал ветку «пауза у ворот — не затык»: штатное ожидание
человека показывалось красным.

Граница окна — последнее событие, доказывающее, что маршрут **поехал дальше**
(`PROGRESS_RE`): заход в узел, зафиксированное решение ворот, возврат курсора человеком
либо движком при восстановлении инструментации. Всё, что раньше него, принадлежит прошлым
заходам. Нет ни одного такого события — окном остаётся весь журнал: сузить его нечем, а
там это безопасно.

Правило шире одного модуля: **любая диагностика по накопительному журналу обязана назвать
своё окно.** Журнал задачи — не состояние, а история; «последнее совпадение» в нём не
означает «текущее». Сторож — `tests/server/stall-window.test.js`.
