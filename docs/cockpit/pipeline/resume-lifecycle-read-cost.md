# Подтверждение resume и стоимость строгого чтения lifecycle

После «Продолжить» сообщение «оркестратор не подтвердил запуск попытки» может означать,
что движок ещё поднимается. При resume `v2_lifecycle_begin_session` и закрытие human
intervention выполняются до публикации identity оркестратора в реестр. Эти операции
читают lifecycle-журнал целиком; init существующего ledger, поиск сессии, append и
reconciliation могут добавлять проходы. Их число зависит от ветки восстановления.

## Окно подтверждения

`confirmRouteResume` сначала выдерживает `settleMs = 6000`: опрашивает живость юнита,
чтобы регистрация `systemd-run` и ещё живой PID не скрыли быстрый отказ движка.
Затем создаётся отдельный deadline `confirmMs = 120000` и начинается опрос identity.
Номинальная сумма окон — около 126 секунд. Асинхронные `identity`, `unitAlive` и `reason`
не имеют общего timeout внутри функции; успешная identity проверяется до deadline.
Поэтому сумма окон не задаёт жёсткую верхнюю границу функции или HTTP-запроса.

Неопределённый реестр и отсутствие живого оркестратора повторно проверяются до deadline.
Смерть юнита возвращает `exited` при очередной проверке живости. Чужая непустая попытка
возвращает `unconfirmed` при первом чтении после settle. Исчерпание второго окна сохраняет
прежнюю причину из журнала либо текст «оркестратор не подтвердил запуск попытки».
Этот путь общий для продолжения, ворот и возврата курсора.

Новое окно server-кода применяется после ручного перезапуска кокпита. POST в web API
не получает стандартный timeout GET, но это не гарантия для любого клиента или прокси:
ограничения проверяются для конкретного транспорта.

## Стоимость валидатора

Каждое чтение и append по-прежнему полностью проверяют события, каноническую запись,
hash chain и согласованность identity. Формат ledger, manifest, tail и recovery не меняются.
В `attempt-lifecycle-state.py` сокращена работа внутри строгой schema-проверки:

- `oneOf` выбирает кандидатов по общему обязательному полю с чистым `const`; текущие
  40 верхних веток различаются `kind`. Таблица сохраняет все ветки с одинаковой константой,
  затем считает все совпадения: допустимо ровно одно. Неподходящие union обходятся полностью.
- Канонические байты `const`/`enum` и планы выбора хранятся только в памяти одного
  `Contract`. Схема неизменна всю его жизнь; значение события проверяется каждый раз.
- Суррогаты Unicode ищутся регулярным выражением вместо посимвольного Python-цикла.

Для текущей корректной неизменной схемы сохраняются принятие/отказ, `LifecycleFailure.name`
и `.code` в `Contract.validate`, `validate_event` и `parse_event_line`, а также успешные
результаты и canonical bytes. Первая диагностика некорректного входа может отличаться:
пропущенная заведомо неподходящая ветка раньше могла найти другое нарушение первой.
Произвольные повреждённые схемы и изменение схемы после построения кэшей не входят в эту
гарантию. Глобальная canonical-проверка в `Contract.validate` не добавляется.

Новый Python загружается следующими lifecycle-процессами из этого checkout. Уже загруженный
модуль завершает работу со старой версией; внешняя копия движка обновляется отдельно.

## Проверка и измерение

Регрессия `tests/engine/unit/attempt-lifecycle-validator.sh` проверяет 40 видов событий,
853 входа корпуса и 12 сценариев строк ledger, fallback, дубликаты дискриминаторов,
кэши констант, различение boolean/integer/null и все code points D800–DFFF.
Публичные пути постоянно сравниваются с полным перебором `oneOf`. При внедрении тот же
корпус дополнительно совпал с независимым снимком всей исходной реализации.
Серверные тесты закрепляют готовность identity на 60-й и 125-й секундах и завершение
неопределённости на 126 000 мс детерминированных часов.

Измерение 12.10.2026: синтетические неизменяемые ledger из публичных fixtures, сначала
`route_selected`, затем циклические события остальных 38 видов без recovery. Для каждого
размера выполнен один прогрев и три последовательных чтения каждой версией через
`python3 -I … --segment-bytes 16777216 read …`; приведены медианы wall-clock.
Оба reader-а во всех запусках вернули 0, ожидаемое число строк и одинаковые bytes (`cmp`).

| Событий | Размер active segment, байт | Исходная версия, с | Новая версия, с |
|---|---:|---:|---:|
| 2000 | 2 266 342 | 3,36 | 1,64 |
| 3000 | 3 401 640 | 5,44 | 2,53 |

Условия: Python 3.10.12, Linux x86_64, 16 логических CPU; минутная load average во время
замера около 18–22. Хеши входов и исходников проверены; журнал не изменялся между чтениями.
Это измерение одного синтетического `read`, без порогового теста скорости и без обещания
ускорить полный resume в такой же пропорции.

Историческая репетиция 11.10.2026 на сохранённом журнале примерно из 2070 событий дала
3,59 → 1,25 секунды для `read`. Это отдельный пример автора первоначального измерения;
его данные здесь повторно не читались и гарантией времени будущего resume не являются.
