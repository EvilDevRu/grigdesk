# План человеческим языком: исправление замечаний в PR

Статус: частично реализовано, не готово к release

Дата: 2026-07-29

Точка остановки 2026-07-30, карта реализованных файлов и порядок безопасного продолжения:
[pr-review-handoff.md](./pr-review-handoff.md).

## Что уже работает, а что ещё нет

Этот документ одновременно описывает целевой пользовательский процесс и оставшуюся работу.
Поэтому формулировки ниже в будущем времени нельзя читать как отчёт о готовой production-функции.
Источником правды о покрытии служит `tests/docs/review-test-manifest.test.mjs`: `required` означает,
что конкретная гарантия уже имеет исполняемый тест, а `planned` — что гарантия ещё не доказана
полностью.

| Состояние | Что входит |
|---|---|
| Реализовано и покрыто offline-тестами | Привязка GitHub-репозитория к Project; устойчивые ID и версии замечаний; GraphQL pagination и отбрасывание несогласованного снимка; сохраняемый watcher с rate-limit; контракты анализатора и «Переводчика»; серверное хранилище review-run; часть человеческих ворот; страница `/reviews`, безопасный Markdown и чип; локальная публикация точного fork ref с Git CAS |
| Экспериментально | Разбор descriptor review-маршрута из Factory profile; структурированный BUILD/REVIEW через tool-free model adapter; локальные worktree; disposable VERIFY и сравнение baseline/candidate; восстановление отдельных crash-сценариев |
| Planned и блокирует release | Настоящий review executor через Factory; provisioning companion-репозиториев и runtime-песочницы; изоляция контейнеров, БД, Redis и портов; browser/Playwright со скриншотами; CPU/RAM/PID/disk limits; полный crash/retry matrix; оставшиеся freshness, UI, security и queue-критерии из manifest |

`review-factory-route` сейчас проверяет только чтение и валидацию descriptor. Он не доказывает,
что Factory реально выполнил маршрут, поднял песочницу или браузер. Пока executor, sandbox,
browser-проверки и resource isolation не реализованы и не переведены из `planned`, production-
профили не должны включать review-маршрут, а `canFix` должен оставаться `false`. Смотреть и
анализировать PR при этом можно.

Обычный offline suite намеренно проходит при наличии `planned`: это позволяет продолжать TDD
по этапам. Отдельный release-gate запускается с `COCKPIT_REVIEW_RELEASE_GATE=1` и обязан падать,
пока в manifest остаётся хотя бы один `planned` ID.

## Коротко

В Cockpit появится отдельный раздел `Ревью`. В нём будут видны замечания из открытых Pull
Request, даже если все песочницы снесены и на странице конвейера нет активных задач.

В сайдбаре рядом с разделом появится чип с количеством PR, которые требуют внимания. Cockpit
будет сам проверять GitHub в фоне. Когда появится новое или изменённое замечание, он:

1. привяжет его к проекту и точной версии PR;
2. технически разберёт замечание в режиме только для чтения;
3. передаст результат отдельному «Переводчику»;
4. покажет человеческую рекомендацию: стоит ли это делать, почему и какое решение требуется.

Cockpit один раз связывает проект с его GitHub-репозиториями. После этого он понимает:

- к какому проекту относится PR;
- frontend это или backend;
- какой профиль Factory использовать;
- из какой ветки брать код;
- какую отдельную песочницу поднять.

Обнаружение и объяснение замечаний автоматические. Изменение кода, принятие продуктовых решений
и публикация остаются под контролем человека. Каждый PR исправляется отдельно. Ветки и
песочницы разных PR никогда не смешиваются.

## Что появится в интерфейсе

### В разделе «Проекты»

У каждого репозитория проекта появится блок GitHub:

- какой GitHub-репозиторий к нему привязан;
- доступен ли GitHub с этой машины;
- умеет ли профиль проекта исправлять замечания;
- включено ли автоматическое наблюдение и когда оно сработало в последний раз;
- сколько сейчас открыто PR и сколько из них требуют внимания;
- кнопка `Проверить сейчас` на случай, если ждать следующего фонового обновления не хочется;
- кнопка `Открыть ревью`.

Привязка настраивается один раз. Cockpit может предложить её на основании `git remote`, но
сохранит только после подтверждения. В дальнейшем он использует сохранённую привязку, а не
пытается каждый раз угадать проект заново.

После подтверждения привязки автоматическое наблюдение и автоанализ включаются для репозитория.
Их можно отключить в настройках проекта, не удаляя саму привязку.

Если адрес удалённого репозитория изменился, Cockpit покажет расхождение и не запустит работу,
пока привязка не будет подтверждена снова.

### Новый раздел «Ревью»

Раздел `/reviews` будет доступен постоянно, независимо от песочниц и обычного конвейера.

В нём будут:

- проекты и их репозитории;
- открытые PR;
- полные тексты замечаний;
- ссылки на исходные комментарии GitHub;
- файл и строка для комментариев к коду;
- состояние каждого замечания;
- автоматическая рекомендация и её понятное объяснение;
- время последней проверки и состояние автоанализа;
- история прошлых попыток исправления;
- очередь запущенных PR;
- отчёты, тесты и скриншоты;
- кнопки принятия и публикации результата.

### Чип в сайдбаре

Чип у пункта `Ревью` показывает количество разных PR, требующих внимания, а не количество
комментариев. Если в одном PR появилось пять замечаний, на чипе добавляется `1`, а не `5`.

PR считается требующим внимания, если:

- появилось новое замечание, его разбор ещё выполняется или уже готов, но не прочитан;
- агент просит продуктовое решение;
- автоматический разбор не удался;
- ранее подготовленная работа устарела из-за изменения PR.

Цвет показывает самое важное состояние:

- синий — появилось новое замечание или готов новый разбор;
- жёлтый — требуется решение человека;
- красный — разбор не удался или подготовленный результат устарел.

Если у PR сразу несколько состояний, действует приоритет `красный → жёлтый → синий`.

Синее уведомление снимается только после того, как карточка успешно загружена и Cockpit
сохранил на сервере номер прочитанной версии. Поэтому обновление страницы или вторая вкладка не
возвращают уже прочитанное уведомление. Жёлтое или красное остаётся, пока причина не устранена.
Закрытый PR и закрытое замечание перестают требовать внимания, а запоздавший ответ анализатора
не может вернуть их в чип.

SSE используется только как сигнал «данные изменились». После сигнала и после переподключения
клиент заново получает актуальный снимок с сервера, поэтому потерянное или повторное событие не
ломает число и цвет чипа.

## Как будет проходить работа

### 1. Cockpit сам замечает изменения

Серверный наблюдатель проверяет привязанные репозитории при запуске Cockpit и затем через
настраиваемый интервал, например раз в пять минут. Кнопка `Проверить сейчас` запускает ту же
проверку вручную, но для обычной работы нажимать её не требуется.

Автоматическое обновление работает, пока запущен сервер Cockpit. После перезапуска он сначала
догоняет изменения, которые появились во время простоя, а затем возвращается к интервалу.

Cockpit без участия ИИ получает из GitHub:

- общие тексты ревью;
- комментарии к конкретным строкам;
- ответы внутри обсуждений;
- обычные комментарии к PR;
- состояние замечания: открыто, закрыто или устарело;
- текущую ветку и точную версию кода PR.

Тексты не обрезаются. Закрытые и устаревшие замечания остаются в истории, но не предлагаются
как новая работа.

Каждый снимок привязан к точному head SHA PR и версии комментариев. Если ничего не изменилось,
Cockpit не вызывает агента повторно. Несколько комментариев, пришедших почти одновременно,
собираются в один пакет, чтобы не запускать отдельный анализ на каждый.

Номер PR и локальный номер комментария сами по себе не считаются идентификатором. Cockpit хранит
полный ключ из GitHub repository ID, PR node ID, типа замечания, thread node ID при его наличии и
comment node ID. Версия дополнительно включает head SHA, состояние обсуждения, время изменения и
хеш текста. Результат принимается только для той же версии; запоздавший анализ старого текста
сохраняется в истории, но не становится текущим.

Опрос GitHub не создаёт песочницу. Для технического разбора используется только GitHub diff и,
если нужен контекст, временный снимок исходников точного SHA в режиме только для чтения. Этот
снимок нельзя использовать для исправления или публикации.

Одновременно для одного репозитория выполняется не больше одного запроса. Ручная проверка не
обходит общий GitHub rate limit. Срок следующей разрешённой попытки сохраняется на диске, поэтому
рестарт не создаёт шквал запросов.

### 2. Агент автоматически готовит понятную рекомендацию

Разбор состоит из двух независимых этапов.

Сначала технический анализатор изучает исходный комментарий, diff и относящийся к нему код. Он
ничего не изменяет и сохраняет структурированный результат:

- что именно просит ревьюер;
- относится ли замечание к текущему коду;
- рекомендация: `Стоит исправить`, `Не стоит исправлять`, `Уже исправлено`,
  `Достаточно ответить`, `Нужно решение` или `Не уверен`;
- технические доказательства;
- ожидаемое изменение;
- риски и уровень уверенности;
- предложение, как проверить готовый результат.

Решение, уверенность, доказательства и риски имеют стабильные коды. Это позволяет машине
проверить, что следующий этап не поменял смысл, а не пытаться сравнивать два свободных текста.

Затем отдельный этап `Переводчик` получает только этот структурированный результат, без истории
рассуждений и без доступа к исходникам. По тому же принципу, что уже используется в Cockpit для
перевода планов, он превращает технический разбор в короткую карточку:

```text
Что просит ревьюер:
Стоит ли делать:
Почему:
Что изменится:
Какие есть риски:
Что нужно решить тебе:
```

Термины и идентификаторы допускаются только там, где без них нельзя, и сразу объясняются.
Переводчик не имеет права скрывать неуверенность анализатора, придумывать доказательства или
самостоятельно принимать продуктовое решение.

Оба этапа запускаются в новой сессии для конкретного PR. Анализатор видит только разрешённый
read-only снимок с запретом чувствительных путей и не получает домашний каталог,
GitHub-учётные данные, соседние worktree или инструменты публикации. Переводчик запускается
вообще без инструментов и получает только разрешённые поля технического артефакта. Текст
комментария и код считаются недоверенными инструкциями.

Если один из этапов упал, исходный комментарий всё равно остаётся виден. PR получает понятный
статус `Не удалось разобрать`, причину и кнопку повторного анализа.

### 3. Ты определяешь, что делать

Для каждого замечания выбирается одно действие:

- `Исправить` — агенту разрешено менять код;
- `Ответить` — код менять не нужно;
- `Пропустить` — замечание осознанно не выполняется, причина сохраняется;
- `Нужно решение` — без твоего выбора работа не запускается.

Для исправления указывается простой критерий готовности: например, какой тест должен пройти
или какое поведение нужно проверить в браузере.

ИИ может предложить вариант, но не может сам принять продуктовое решение. Например, он не
сможет самостоятельно отключить удаление тегов только потому, что считает это разумным.

Можно подтвердить рекомендации сразу для нескольких PR, но каждый из них всё равно создаст
отдельную работу.

Подтверждение хранится на сервере вместе с точной версией снимка и выбранным объёмом работы.
Скрытая кнопка не считается защитой: прямой API-запрос не сможет запустить работу без
действующего подтверждения.

### 4. Создаётся отдельный запуск

После подтверждения Cockpit создаёт внутренний запуск именно для этого PR.

Он не переиспользует старое состояние задачи и не перезаписывает историю первоначального
конвейера. Повторное ревью того же PR создаёт новую попытку с собственной историей.

### 5. Подготавливается чистый код

Cockpit повторно проверяет GitHub и берёт точную версию ветки PR.

Для неё создаются:

- отдельная временная ветка исправления;
- отдельный worktree;
- отдельное место для журналов и скриншотов;
- отдельная песочница.

Существующая локальная ветка `task-N` не удаляется и не используется как исходная версия. Это
важно, потому что в ней могут лежать незапушенные черновики от предыдущей работы.

Если PR относится к frontend, frontend берётся из ветки этого PR, а backend — из обычной
зафиксированной основной ветки. Ветка другого незамёрженного PR вместо backend или frontend
не подставляется.

### 6. Агент исправляет только выбранные пункты

Агент получает:

- полный исходный комментарий;
- ссылку на него;
- утверждённое действие;
- ожидаемый результат;
- точную рабочую копию PR.

Он не получает замечания соседнего PR и не имеет права расширять согласованный объём работы.

До приёмки агент не может пушить код, отвечать в GitHub или закрывать обсуждения.

### 7. Результат проверяется

Проверка состоит из нескольких независимых частей:

- соответствует ли изменение замечанию;
- не появились ли посторонние файлы;
- проходит ли нужный тест;
- собирается ли production-версия;
- не добавились ли новые ошибки lint или type-check;
- работает ли пользовательский сценарий в браузере;
- нет ли новых ошибок в консоли;
- не вышло ли исправление за согласованные границы.

Старые ошибки проекта сравниваются с состоянием PR до исправления. Они не выдаются за новую
поломку.

Если проверку невозможно запустить из-за сети, Docker или инструмента, она помечается как
`Не проверено` с причиной, а не как успешно пройденная.

### 8. Ты принимаешь результат

Cockpit показывает таблицу:

| Замечание | Что изменено | Как проверено | Результат | Оставшийся риск |
|---|---|---|---|---|

Проваленная обязательная проверка не позволяет принять работу. Непроверенный риск можно принять
только отдельным явным действием.

Песочница остаётся доступной, чтобы результат можно было посмотреть вручную.

Приёмка привязана к отпечатку исходного снимка, согласованного объёма, точного дерева изменённого
кода и отчёта проверок. Любое изменение файла или повторная проверка с другим результатом
аннулирует старую приёмку.

### 9. Код публикуется

После приёмки появляется отдельная кнопка `Опубликовать`.

Перед публикацией Cockpit ещё раз проверяет:

- PR всё ещё открыт;
- его ветка не изменилась;
- замечания не были изменены;
- не появились новые замечания;
- все обязательные проверки прошли;
- публикуется только код этого PR.

После этого создаётся один коммит и выполняется обычный push в существующую ветку PR. Force push
не используется.

Операция публикации имеет постоянный idempotency key. Два одновременных запроса или повтор после
сетевого обрыва сначала сверяют удалённый ref и не могут создать второй коммит. Для PR из fork
публикация идёт именно в head-репозиторий и head-ветку, а не в одноимённую ветку основного
репозитория.

В первой версии Cockpit не отвечает автоматически на комментарии и не закрывает обсуждения.
Это можно добавить позже, когда основной процесс будет обкатан.

## Что происходит, если PR изменился во время работы

Cockpit проверяет актуальность трижды:

1. когда ты утверждаешь список исправлений;
2. перед тем как агент начнёт менять код;
3. непосредственно перед публикацией.

Если ветка, текст замечания или список открытых замечаний изменились, текущая попытка получает
статус `Устарела`.

Она ничего не пушит. Из свежего состояния создаётся новая попытка, а старый отчёт сохраняется.

## Как обрабатываются несколько PR

На странице `Ревью` можно выбрать несколько PR и поставить их в очередь.

Это не объединяет их:

- у каждого свой запуск;
- у каждого своя ветка;
- у каждого свой worktree;
- у каждого своя песочница;
- у каждого свои проверки и приёмка;
- каждый публикуется отдельно.

В первой версии они выполняются по одному. Это проще, безопаснее и не перегружает машину.

Если два PR меняют один файл, Cockpit только предупреждает об этом. Он не пытается собрать их
вместе. После merge первого второй нужно обновить относительно основной ветки и проверить заново
в собственной песочнице.

Если один PR вообще невозможно проверить без другого незамёрженного PR, работа останавливается
с понятной причиной. Автоматически смешивать их всё равно нельзя.

## Что будет, если все песочницы снесены

Ничего особенного:

1. `Проекты` и `Ревью` продолжают работать;
2. фоновые обновления, разбор и чип продолжают работать;
3. после запуска конкретного PR Cockpit создаёт для него новую песочницу с нуля;
4. если свободного ресурса нет, PR остаётся в очереди;
5. упавшая песочница сохраняется для диагностики;
6. успешная песочница остаётся до явного нажатия `Снести`.

Песочница никогда не используется как источник информации о том, какие PR существуют.

## Как Cockpit поймёт, какой конвейер запускать

Связь строится так:

```text
GitHub PR
  → подтверждённый GitHub-репозиторий
  → репозиторий внутри Project
  → профиль Factory этого Project
  → маршрут исправления замечаний
```

Номер исходной задачи берётся из ветки по правилу проекта, например `task-7800`.

Если Cockpit не смог однозначно определить хотя бы одно звено, он не выбирает маршрут
самостоятельно. PR будет показан как `Не настроен` с объяснением, чего не хватает.

## Что войдёт в первую версию

- настройка GitHub-репозиториев в `Проектах`;
- автоматическое фоновое обновление и кнопка `Проверить сейчас`;
- раздел `/reviews`;
- чип с количеством PR, требующих внимания;
- полные замечания без обрезания;
- автоматический технический разбор новых и изменённых замечаний;
- отдельный перевод разбора на человеческий язык;
- понятное состояние ошибки и повторный анализ;
- ручной выбор действий;
- очередь нескольких PR по одному;
- отдельный запуск и песочница каждого PR;
- исправление кода;
- тесты, сборка, lint и браузер;
- отчёт и ручная приёмка;
- отдельная ручная публикация.

## Что сознательно откладываем

- автоматическое исправление без подтверждения человека;
- автоматический push;
- автоматические ответы и закрытие обсуждений;
- внешние уведомления по почте, Slack или Telegram;
- CLI;
- GitHub App и webhook;
- общий сервис для всей команды;
- параллельное исправление нескольких PR;
- использование локальных черновых коммитов.

Фоновый опрос через текущую GitHub-авторизацию входит в первую версию. Webhook можно добавить
позже для почти мгновенной реакции и снижения числа запросов, не меняя пользовательский процесс.

## Порядок реализации

### Этап 0. Подготовить доказуемый тестовый контур

Добавить manifest обнаружения тестов, DOM/component harness, локальные bare Git fixtures и
межпроцессный race harness. `RB-01` должен стать зелёным. Остальные blockers сначала отмечаются
как `planned`, а перед кодом соответствующего этапа переводятся в `required` и дают ожидаемый
красный тест.

Результат: ни одна критическая гарантия не сможет остаться вне общего test runner или быть
подменена fake-проверкой.

### Этап 1. Связать проекты с GitHub

Добавить в `Проекты` явную настройку GitHub для каждого репозитория и проверку доступа.

Результат: Cockpit надёжно знает, к какому проекту относится PR.

### Этап 2. Показать входящие ревью

Добавить получение полного снимка PR, кнопку `Проверить сейчас` и страницу `/reviews`.

Результат: при нуле песочниц видны все полные замечания.

### Этап 3. Добавить автоматическое наблюдение и чип

Добавить сохраняемую очередь фоновых проверок, сравнение снимков, группировку близких событий и
обновление интерфейса без перезагрузки.

Результат: новые замечания сами появляются в `Ревью`, а сайдбар показывает число PR, требующих
внимания.

### Этап 4. Добавить анализатор и «Переводчик»

Сначала технический этап только для чтения формирует проверяемый структурированный вывод. Затем
отдельный переводчик превращает его в понятную карточку.

Результат: по каждому новому замечанию автоматически видно, стоит ли его выполнять и почему.

### Этап 5. Отделить review-запуски от задач

Добавить собственную идентичность и хранилище каждой попытки исправления. Старые конвейеры задач
остаются нетронутыми.

Результат: повторное ревью не портит историю `t7800` и других задач.

### Этап 6. Создавать изолированную рабочую среду

Для каждого запуска создавать worktree и песочницу от точной версии PR.

Результат: локальные черновики и соседние PR не попадают в исправление.

### Этап 7. Подключить исправление и проверки

Добавить этапы планирования, исправления, независимого ревью, автоматических проверок и браузера.

Результат: Cockpit показывает доказательства по каждому замечанию.

### Этап 8. Добавить ручную публикацию

После приёмки повторно проверять актуальность PR и выполнять безопасный push.

Результат: невозможно случайно отправить устаревший или непроверенный код.

### Этап 9. Добавить очередь нескольких PR

Несколько выбранных PR запускаются по одному и не используют общие ресурсы.

Результат: можно обработать текущий набор замечаний без ручного запуска каждого конвейера.

### После обкатки

Добавить webhook, внешние уведомления, подготовку ответов и при необходимости CLI или командную
GitHub-интеграцию. Автоматическое исправление и публикацию без человеческих ворот не включать
просто как продолжение этой версии: для них потребуется отдельное решение о рисках и правах.

## Какие тесты нужны по TDD

Каждый этап реализации начинается не с кода, а с красного теста на пользовательскую гарантию.

Рабочий цикл:

1. Написать тест, который падает по правильной причине.
2. Сделать минимальную реализацию, чтобы он позеленел.
3. Добавить граничные случаи.
4. Упростить код, не меняя поведения.
5. Запустить тесты затронутой подсистемы.
6. Перед завершением этапа запустить весь offline suite.

Тестировать нужно публичное поведение и инварианты. Проверка конкретной внутренней функции
допустима только там, где она защищает формат состояния, блокировку или безопасность.

У каждой гарантии ниже есть постоянный идентификатор. Он должен входить в имя соответствующего
subtest, чтобы критерий готовности можно было связать с реально запущенной проверкой.

Используются четыре уровня:

- `contract` — схема данных, валидатор, автомат состояний и права;
- `integration` — настоящий Fastify через `inject`, временная файловая система и локальные
  Git-репозитории;
- `race` — отдельные процессы, общий state, барьеры и управляемые сбои;
- `component/browser` — реальный путь Vue-компонента, Markdown-рендера и SSE.

Fake-адаптер разрешён для GitHub API и модели, но не должен подменять Git, файловые блокировки,
серверные ворота или DOM там, где проверяется их настоящее поведение.

### Блокирующие тесты до кода функции

До реализации соответствующего участка сначала должны существовать и падать по ожидаемой
причине:

| ID | Что обязано быть доказано |
|---|---|
| `RB-01` | Все review-тесты действительно обнаруживаются командами общего offline suite |
| `RB-02` | Стабильный ключ и версия не позволяют прикрепить результат к другому PR |
| `RB-03` | Два процесса не владеют одной job, а просроченный владелец не может записать результат |
| `RB-04` | Scope, приёмку и публикацию нельзя обойти прямым API-запросом |
| `RB-05` | Настоящий Git публикует точный ref head-репозитория и отвергает гонку |
| `RB-06` | Анализатор и переводчик изолированы от секретов, сети и соседнего PR |
| `RB-07` | Недоверенный GitHub/LLM-текст не исполняется, а review API и SSE закрыты авторизацией |

`tests/docs/review-test-manifest.test.mjs` хранит для каждого test ID путь, runner, этап и статус
`planned|required`. Перед реализацией этапа его тесты переводятся в `required`. Проверка
подтверждает, что каждый required-файл существует и действительно попадает под существующий glob
или runner, а ID находится именно в имени исполняемого `test`/subtest, а не просто упомянут
комментарием или fixture. Наличие файла без его фактического запуска не считается покрытием.
`planned` может указывать на ещё не созданный файл и не ломает обычный suite. К релизу отдельный
`COCKPIT_REVIEW_RELEASE_GATE=1` запрещает любые planned-записи.

### 1. Связь Project с GitHub

Сначала написать тесты, которые доказывают:

- `MAP-01`: проект и его репозитории доступны при полном отсутствии задач и песочниц;
- `MAP-02`: SSH- и HTTPS-адреса одного GitHub-репозитория распознаются одинаково;
- `MAP-03`: найденная через `git remote` привязка не применяется без подтверждения человека;
- `MAP-04`: подтверждённая привязка сохраняется после перезапуска Cockpit;
- `MAP-05`: изменение `git remote` показывает расхождение и блокирует запуск;
- `MAP-06`: два проекта с одинаковой GitHub-привязкой дают явную ошибку неоднозначности;
- `MAP-07`: проект без review-маршрута позволяет смотреть PR, но не запускать исправление;
- `MAP-08`: путь фабричного проекта остаётся read-only и не копируется в настройки Cockpit.

До прохождения этих тестов GitHub-синхронизацию реализовывать нельзя: иначе PR может попасть
не в тот проект.

### 2. Получение замечаний

Использовать синтетические ответы GitHub, а не реальные приватные PR.

Красные тесты должны покрыть:

- `SYNC-01`: несколько страниц GraphQL pagination, длинные тексты и все типы замечаний —
  review body, inline threads, ответы и обычные комментарии к PR;
- `SYNC-02`: resolved, outdated и закрытые замечания сохраняются в истории, но не становятся
  новой работой;
- `SYNC-03`: повторная синхронизация не создаёт дублей, а изменение текста создаёт новую версию
  того же замечания;
- `SYNC-04` (`RB-02`): два репозитория с одинаковым номером PR и совпадающими числовыми comment
  ID не смешиваются;
- `SYNC-05` (`RB-02`): ключ различает review body, thread и обычный PR comment, даже если их
  локальные ID совпали;
- `SYNC-06` (`RB-02`): анализ версии `v1` уже выполняется, приходит `v2`, `v2` завершается
  раньше; текущим остаётся только `v2`;
- `SYNC-07` (`RB-02`): пакетный ответ с неизвестным, пропущенным, повторным или относящимся к
  другому PR item ID отклоняется целиком и ничего не перепривязывает;
- `SYNC-08`: перед первой страницей запомнены head SHA и PR updatedAt, а после последней они
  прочитаны повторно; изменение между страницами отбрасывает весь кандидатный снимок и запускает
  согласованный повтор;
- `SYNC-09`: GraphQL `200` с частичными `errors` не считается успешной синхронизацией и не
  заменяет прошлый снимок;
- `SYNC-10`: отсутствие GitHub-авторизации, сеть и rate limit не стирают предыдущие данные;
- `SYNC-11`: debug-журнал содержит технические ID и коды ошибок, но не приватный текст
  комментариев и не GitHub-токен.

Fixture должен быть вымышленным, но по форме повторять реальные ответы GitHub.

### 3. Автоматическое наблюдение

До фонового таймера написать тесты:

- `WATCH-01`: после запуска проверяются только подтверждённые и включённые репозитории;
- `WATCH-02`: кнопка `Проверить сейчас` использует ту же очередь, что и таймер, и не создаёт
  второй inflight-запрос;
- `WATCH-03`: неизменившийся снимок не создаёт job и model call;
- `WATCH-04`: новый или изменённый комментарий создаёт одну job, а близкие события одного PR
  объединяются в один пакет;
- `WATCH-05`: изменение head SHA делает старый анализ устаревшим;
- `WATCH-06`: resolve/close отменяет ожидающую job; поздний анализ отбрасывается и не запускает
  переводчик;
- `WATCH-07`: событие `reviews-change` отправляется только после зафиксированного изменения;
- `WATCH-08`: опрос и анализ не создают runtime-песочницу.

В тестах часы должны быть управляемыми: реального ожидания пяти минут быть не должно.

Rate-limit проверяется отдельно с fake clock:

- `WATCH-RATE-01`: долгий запрос пересекает два тика и ручную проверку, но inflight остаётся один;
- `WATCH-RATE-02`: `Retry-After`, primary rate-limit reset и secondary rate limit устанавливают
  общий срок ожидания для отпечатка GitHub-учётных данных, а не только одного репозитория;
- `WATCH-RATE-03`: срок и число попыток сохраняются после рестарта, jitter управляется тестом;
- `WATCH-RATE-04`: пока действует общий срок, ручная кнопка показывает причину ожидания и не
  обходит лимит;
- `WATCH-RATE-05`: после исчерпания трёх автоматических попыток job становится терминально
  ошибочной; только явный ручной повтор сбрасывает бюджет.

Гонка планировщиков проверяется не двумя объектами в одном процессе, а отдельными процессами с
общим временным state:

- `WATCH-RACE-01` (`RB-03`): два процесса одновременно проходят барьер claim, но lease получает
  только один;
- `WATCH-RACE-02` (`RB-03`): первый процесс убит после claim, lease истекает, второй завершает
  job, а запоздавший первый не может записать результат со старым fencing token;
- `WATCH-RACE-03` (`RB-03`): сбой до и после атомарной записи не создаёт две текущие версии;
- `WATCH-RACE-04`: в state не хранится сам GitHub-токен — только безопасный отпечаток владельца
  общего rate-limit.

### 4. Технический анализатор

Контракт анализатора сначала фиксируется схемой результата и fake-моделью. Тесты должны доказать:

- `ANALYZE-01`: вход содержит полный комментарий, GitHub diff и read-only снимок точного head SHA;
- `ANALYZE-02`: артефакт сохраняет полный item key, версию, SHA и revision схемы/prompt;
- `ANALYZE-03`: решение — enum из `Стоит исправить`, `Не стоит исправлять`, `Уже исправлено`,
  `Достаточно ответить`, `Нужно решение`, `Не уверен`;
- `ANALYZE-04`: confidence — enum, а evidence и risk — объекты со стабильными ID; рекомендация
  ссылается только на существующие ID;
- `ANALYZE-05`: неизвестный ID, дубли, отсутствие обязательного поля или лишнее действие
  отклоняют ответ до изменения текущего состояния;
- `ANALYZE-06`: продуктовый fixture ожидает `Нужно решение`, а fixture без доказательств —
  `Не уверен`;
- `ANALYZE-07`: изменение SHA или версии замечания инвалидирует артефакт посредством CAS;
- `ANALYZE-08`: ошибка не скрывает исходный текст, а повтор неизменившегося входа не создаёт
  второй актуальный артефакт;
- `ANALYZE-09`: retry budget и причина терминальной ошибки видны пользователю.

Offline-тесты не вызывают настоящую модель. Они подают управляемые структурированные ответы через
fake-адаптер и проверяют схему, переходы состояния и права. Fake не считается доказательством
качества рассуждений настоящей модели: качество классификации проверяется только отдельным
синтетическим corpus-canary.

### 5. «Переводчик» на человеческий язык

До подключения настоящего переводчика написать контрактные тесты:

- `TRANSLATE-01`: сериализованный запрос содержит только whitelisted поля технического разбора,
  но не код, diff, raw comment, секреты и внутреннюю историю рассуждений;
- `TRANSLATE-02`: карточка содержит поля `Что просит ревьюер`, `Стоит ли делать`, `Почему`,
  `Что изменится`, `Какие есть риски` и `Что нужно решить тебе`;
- `TRANSLATE-03`: ответ обязан вернуть без изменения decision ID, confidence ID и наборы
  evidence/risk ID;
- `TRANSLATE-04`: неизвестный ID, повышение confidence, смена решения или превращение
  `Нужно решение` в готовый выбор детерминированно отклоняются;
- `TRANSLATE-05`: текст может объяснять только переданные evidence/risk ID и не может добавить
  новый факт как доказанный;
- `TRANSLATE-06`: пустой или невалидный перевод не заменяет прошлую карточку;
- `TRANSLATE-07`: новый перевод той же версии заменяет только представление, оставляя
  технический артефакт побайтово неизменным;
- `TRANSLATE-08`: при ошибке видны технический статус, понятная причина и ручной повтор.

Автоматически проверяются формат и сохранение смысла. Естественность русского текста отдельно
проверяется canary-примерами, потому что её нельзя честно доказать одним строковым сравнением.
Требование «термин объяснён обычными словами» проверяется на синтетическом корпусе вручную, а не
выдаётся за строгий unit-тест.

### 6. Выбор замечаний и решение человека

До формы scope написать тесты:

- `GATE-01`: `Исправить` разрешает включить пункт в работу;
- `GATE-02`: `Ответить` не даёт пишущих прав, `Пропустить` требует причины;
- `GATE-03`: `Нужно решение` блокирует запуск, и агент не может заменить его на `Исправить`;
- `GATE-04`: изменение инструкции, снимка или исходного комментария отменяет утверждение;
- `GATE-05`: в запуск попадают только явно утверждённые пункты;
- `GATE-06` (`RB-04`): прямой POST запуска при `Нужно решение`, без scope approval или с
  approval другой версии получает отказ и не создаёт worktree, ветку или job BUILD;
- `GATE-07` (`RB-04`): приёмка хранит digest из snapshot, scope, candidate tree и verify report;
- `GATE-08` (`RB-04`): изменение файла, amend кандидата или новый verify report после приёмки
  аннулируют её и запрещают прямой POST публикации;
- `GATE-09`: UI скрывает или блокирует действие по тому же серверному состоянию, но серверный
  тест остаётся главным доказательством.

Отдельный тест должен проверять продуктовый вопрос: рекомендация агента существует, но без
решения человека пишущий этап не начинается.

### 7. Независимая история review-запусков

Это обязательный набор тестов до подключения Factory:

- `RUN-01`: review-запуск не создаёт и не меняет `t<TASK>.pipeline`, а архив первоначальной
  задачи остаётся побайтово неизменным;
- `RUN-02`: две попытки одного PR получают разные внутренние идентификаторы и каталоги;
- `RUN-03`: состояние одной попытки и поздний ответ старого этапа не принимаются новой попыткой;
- `RUN-04`: одновременно нельзя создать две активные пишущие попытки одного PR;
- `RUN-05`: после рестарта незавершённая попытка восстанавливается только по правилам crash-матрицы;
- `RUN-06`: неизвестный результат публикации не запускается повторно автоматически;
- `RUN-07`: битый файл одной попытки изолирован и не ломает список остальных;
- `RUN-08`: запись состояния атомарна, содержит schema version и не принимает старый fencing token.

Для этих тестов использовать временный каталог состояния. Настоящий `~/.factory` они трогать
не должны.

### 8. Изоляция ветки, worktree и песочницы

Перед созданием реальной песочницы написать тесты:

- `ISOLATE-01`: worktree начинается с точного head SHA PR, а локальная `task-N` с
  дополнительными коммитами не используется;
- `ISOLATE-02`: второй PR получает другой worktree, candidate branch и sandbox namespace;
- `ISOLATE-03`: companion-репозиторий берётся из зафиксированной основной ветки, но не из ветки
  другого незамёрженного PR;
- `ISOLATE-04`: два запуска не получают одинаковые базы, Redis, контейнеры или порты;
- `ISOLATE-05`: занятый ресурс оставляет запуск в очереди, ошибка provisioning сохраняет
  окружение для диагностики;
- `ISOLATE-06`: успешная проверка не сносит песочницу, а ручной снос удаляет только ресурсы
  выбранного запуска;
- `ISOLATE-07`: property-тест генерирует набор PR с одинаковыми именами веток, номерами и
  пересекающимися файлами; все разрешённые refs, paths и namespaces входят в allowlist и
  попарно различны.

Хрупкого grep-теста «в коде нет integration-ветки» не будет. Гарантия доказывается наблюдаемыми
refs и ресурсами `ISOLATE-07`.

### 9. Права пишущего и проверяющих этапов

До запуска настоящего агента зафиксировать тестами:

- `SEC-01`: технический анализатор, TRANSLATOR, PLAN и REVIEW фактически не могут менять файлы;
- `SEC-02`: BUILD может писать только в worktree своего запуска и не видит соседний worktree;
- `SEC-03`: агент не может выполнить `git push`, GitHub mutation или вызвать host publisher;
- `SEC-04`: проверочный этап, изменивший файл, считается проваленным;
- `SEC-05`: host publisher недоступен до действующей приёмки;
- `SEC-06` (`RB-06`): комментарий и код с инструкциями прочитать `.env`, `~/.config/gh`,
  соседний worktree, выполнить `curl`, push и mutation получают отказ фактического execution
  envelope;
- `SEC-07` (`RB-06`): каждый PR анализируется новой сессией; идентификатор, prompt, ответ и лог
  второго PR не содержат данных первого;
- `SEC-08` (`RB-06`): окружение анализатора содержит только точный read-only snapshot,
  allowlisted переменные и файловую политику с запретом `.env`, credential/config paths и
  домашнего каталога, без произвольной исходящей сети для инструментов;
- `SEC-09` (`RB-06`): переводчик запускается без инструментов, а записанный request совпадает с
  whitelist структурированных полей;
- `SEC-10`: prompt, model request, результат и debug-журнал не содержат GitHub-токенов и
  содержимого файлов-ловушек.
- `SEC-COOKIE-01`: ограниченный gateway token нельзя использовать как полную сессию Cockpit;
- `SEC-COOKIE-02`: полная session cookie остаётся host-only, а родительский `Domain` получает
  только ограниченная gateway cookie;
- `SEC-COOKIE-03`: gateway cookie разрешает только `forward_auth` и не открывает review API;
- `SEC-COOKIE-04`: старая domain-cookie мигрируется в host-only session без повторного входа;
- `SEC-COOKIE-05`: reverse proxy удаляет обе служебные Cockpit cookie перед передачей запроса
  недоверенному backend стенда.

Текстовая инструкция агенту не считается защитой. Тест должен проверять фактическую командную
политику, окружение, сетевые возможности и файловые границы. Доступ runner к API самой модели
отделён от отсутствия сетевых инструментов у агента.

### 10. Проверки и сравнение с исходным состоянием

Перед реализацией VERIFY подготовить fixtures:

- `VERIFY-F01`: lint уже красный до исправления и остаётся таким же после него;
- `VERIFY-F02`: после исправления появляется новая lint-ошибка;
- `VERIFY-F03`: targeted test сначала падает, затем проходит;
- `VERIFY-F04`: production build падает;
- `VERIFY-F05`: type-check содержит старый долг и одну новую ошибку;
- `VERIFY-F06`: браузерный сценарий прошёл со скриншотом;
- `VERIFY-F07`: браузер не смог стартовать;
- `VERIFY-F08`: в консоли появилась новая ошибка;
- `VERIFY-F09`: в worktree появился случайный файл.

Тесты должны доказать:

- `VERIFY-01`: старый долг показывается отдельно и не считается новой регрессией;
- `VERIFY-02`: новая ошибка или обязательная проваленная проверка блокирует приёмку;
- `VERIFY-03`: пропущенная проверка не становится зелёной;
- `VERIFY-04`: пропущенный риск требует отдельного подтверждения;
- `VERIFY-05`: итоговая таблица связывает замечание, diff, проверку и результат;
- `VERIFY-06`: отчёт содержит digest точного candidate tree, и изменение дерева делает отчёт
  неприменимым.
- `SEC-VERIFY-01`: disposable VERIFY tree материализуется только из tracked candidate tree;
  ignored `.env`, `node_modules` и другие файлы рабочего каталога в него не копируются.

### 11. Защита от устаревшего PR

Для каждого контрольного момента нужен отдельный тест:

- `FRESH-01`: head SHA изменился до утверждения scope или начала исправления;
- `FRESH-02`: появился новый thread до начала исправления;
- `FRESH-03`: выбранный комментарий изменили или закрыли во время BUILD;
- `FRESH-04`: новый комментарий появился перед публикацией;
- `FRESH-05`: PR закрыли или изменили head-ветку перед публикацией;
- `FRESH-06`: пропало право push;
- `FRESH-07`: старый model result, VERIFY или acceptance приходит после новой версии и
  отклоняется по CAS;
- `FRESH-08`: поздний результат закрытого PR сохраняется только в диагностической истории и не
  возвращает PR в чип.

Во всех случаях запуск становится `Устарел` или `Заблокирован`, ничего не пушит и сохраняет
готовый локальный результат.

### 12. Безопасная публикация

До реализации кнопки `Опубликовать` написать тесты:

- `PUBLISH-01` (`RB-04`): прямой запрос до приёмки, с красной проверкой или с неверным acceptance
  digest запрещён;
- `PUBLISH-02` (`RB-04`): два одновременных запроса получают один durable operation и создают
  максимум один коммит;
- `PUBLISH-03` (`RB-05`): локальные bare `base.git` и `fork.git` содержат одноимённую ветку,
  но PR принадлежит fork; меняется только точный head ref в `fork.git`;
- `PUBLISH-04` (`RB-05`): candidate commit является продолжением сохранённого head SHA и
  публикуется с точным compare-and-swap
  `--force-with-lease=<ref>:<expected SHA>`; lease разрешает fast-forward только
  если remote ref всё ещё равен сохранённой версии;
- `PUBLISH-05` (`RB-05`): после freshness-check удалённый ref продвигается другим процессом;
  push отвергается, запуск становится `Устарел`, локальный кандидат сохраняется;
- `PUBLISH-06`: сетевой обрыв после успешного обновления ref переводит операцию в
  `Результат неизвестен`; повтор сначала сверяет remote SHA и не создаёт второй коммит;
- `PUBLISH-07`: base, другой PR и другие ветки остаются побайтово/по ref неизменными;
- `PUBLISH-08`: удаление head ref, закрытие PR и пропажа push-доступа дают блокировку без
  изменения удалённых refs;
- `PUBLISH-09`: первая версия не отвечает и не закрывает review threads.

GitHub API в offline suite подменяется управляемым адаптером. Git не подменяется: эти тесты
создают временные рабочие и bare-репозитории и выполняют настоящий локальный `git push` без сети.
Wrapper журналирует аргументы и доказывает наличие exact `--force-with-lease` для ожидаемого ref
и SHA. Это не «разрешение переписать ветку»: несовпадение remote SHA обязано отклонить push.
Реальный удалённый GitHub push в автоматическом наборе запрещён.

### 13. Страница «Ревью» и чип

До компонентов интерфейса написать web-тесты:

- `UI-01`: `/reviews` открывается при пустом `/api/tasks`, а проект без GitHub-привязки
  показывает действие настройки;
- `UI-02`: reducer чипа считает разные PR, а не комментарии: пять замечаний одного PR дают `1`,
  два PR разных проектов дают `2`;
- `UI-03`: таблица всех сочетаний проверяет приоритет `красный → жёлтый → синий`;
- `UI-04`: PR входит в чип сразу после получения замечания; read-version снимает только синий
  статус, но не нерешённый жёлтый или красный;
- `UI-05`: close/resolve снимает внимание, а поздний анализ не возвращает его;
- `UI-06`: два таба получают одинаковый серверный read-version;
- `UI-07`: повтор, потеря и перестановка SSE не меняют счётчик сами по себе; reconnect и F5
  обязательно получают полный snapshot;
- `UI-08`: карточка показывает полный комментарий, рекомендацию, причину, изменение, риск и
  требуемое решение, а ошибка анализатора не скрывает исходник;
- `UI-09`: выбор двух PR создаёт два будущих запуска, а статус, scope, отчёты и скриншоты не
  пересекаются;
- `UI-10`: `Нужно решение` блокирует запуск, `Устарел` объясняет изменение, публикация появляется
  только после приёмки;
- `UI-11`: после обновления страницы сохраняются scope, очередь и история.

Безопасность проверяется через реальный путь отображения:

- `UI-SEC-01` (`RB-07`): raw comment, имя автора и перевод содержат `<img onerror>`, `<script>`,
  HTML entities и `javascript:`/`data:` URL; смонтированный компонент не содержит исполняемых
  обработчиков или опасных ссылок;
- `UI-SEC-02`: карточка использует существующий `web/src/shared/md.js`, а не отдельный
  непроверенный рендерер;
- `API-SEC-01` (`RB-07`): неавторизованные GET `/api/reviews`, review mutations и
  `/api/events` получают `401` через настоящий Fastify auth plugin;
- `API-SEC-02` (`RB-07`): ответы с review-текстом и SSE имеют `Cache-Control: no-store`;
- `API-SEC-03`: logout очищает review-данные из памяти клиентского store и не оставляет их в
  localStorage/sessionStorage; серверная история при этом не удаляется.

Сейчас `npm --prefix web test` запускает только `node:test` без DOM. Поэтому UI-этап начинается
с добавления `@vue/test-utils` и `happy-dom` для component-тестов. Один локальный Playwright-тест
с fake API/SSE проверяет mount `/reviews`, reconnect и обновление без перезагрузки. Оба уровня
обязательно подключаются к `npm --prefix web test`; поиск строк по исходникам не считается
component-тестом.

### 14. Очередь и восстановление

Перед поддержкой нескольких PR написать тесты:

- `QUEUE-01`: при concurrency `1` второй PR ждёт завершения пишущей работы первого;
- `QUEUE-02`: read-only анализ имеет отдельную очередь и не получает ресурс пишущей песочницы;
- `QUEUE-03`: отсутствие ресурса не теряет очередь, а две команды одного PR схлопываются;
- `QUEUE-04`: отмена ожидающего PR не затрагивает выполняющийся;
- `QUEUE-05`: падение одного PR не останавливает остальные;
- `QUEUE-06`: песочница завершённого PR не назначается следующему;
- `QUEUE-07`: пересекающиеся файлы дают предупреждение, но не объединяют ветки;
- `QUEUE-08`: restart разрешает только действие из crash-матрицы ниже.

Фраза «продолжить с безопасного места» заменяется явной матрицей:

| Момент сбоя | Единственное допустимое восстановление |
|---|---|
| До durable enqueue | Команду можно принять заново |
| После enqueue, до claim | Job может получить один владелец |
| Во время analysis/translation | Повтор после lease и в пределах retry budget |
| Во время provisioning | Сначала сверить и изолированно убрать неполные ресурсы либо запросить человека |
| После BUILD commit, до записи состояния | Найти exact candidate commit; не писать повторно поверх worktree |
| После VERIFY | Применить отчёт только к тому же candidate tree либо проверить заново |
| После acceptance | Сохранить её только при полном совпадении acceptance digest |
| Во время push, до известного ответа | Сверить remote ref; не повторять push вслепую |
| После remote ref update, до локальной записи | Reconcile по remote SHA и завершить ту же operation |

`RECOVER-01` запускает эту матрицу как table-driven integration-тест. `RECOVER-RACE-01` повторяет
границы claim и записи в отдельных процессах с fencing token.

## Что остаётся только canary-проверкой

Offline suite не должен:

- обращаться к реальному GitHub;
- читать реальные приватные комментарии;
- выполнять model call;
- поднимать настоящий Docker sandbox;
- менять ветки рабочего или удалённого проекта;
- делать push куда-либо, кроме временного локального bare fixture;
- отвечать в review threads.

Отдельный явный host canary проверяет:

- действующую `gh`-авторизацию;
- получение PR из отдельного тестового GitHub-репозитория с синтетическими комментариями;
- фоновое обнаружение нового тестового замечания;
- создание настоящего worktree;
- provisioning песочницы;
- технический разбор выбранным ИИ;
- понятность и верность текста «Переводчика» на наборе эталонных примеров;
- обновление списка и чипа без перезагрузки страницы;
- реальные команды проекта;
- браузерный сценарий.

Canary запускается только явно. Для model-canary фиксируются provider, model, prompt revision и
версия синтетического корпуса; ручная оценка понятности записывается отдельно и не подменяется
точным сравнением строк. Реальные приватные PR в canary не используются.

Первый canary выполняется без публикации. Реальный push разрешается только в выделенный тестовый
репозиторий после нескольких успешных прогонов и отдельного подтверждения. Canary не становится
обязательным offline gate и не делает suite нестабильным из-за сети или смены модели.

## Условие завершения каждого этапа

Этап реализации считается законченным, только если:

1. новый тест сначала был красным;
2. targeted-набор стал зелёным;
3. добавлены отрицательные и аварийные случаи;
4. `review-test-manifest` подтверждает, что новый файл реально запускается;
5. все required `RB-*` текущего и прошлых этапов зелёные и ни один обязательный тест не skipped;
6. race-тесты повторены с управляемыми разными interleaving;
7. полный offline suite проходит;
8. документация соответствует фактическому поведению;
9. для внешней интеграции отдельно записано, что проверено только canary.

Основные команды:

```bash
npm --prefix server test
npm --prefix web test
bash tests/engine/run-offline.sh
bash tests/run-all.sh
```

## Как это будет выглядеть на текущих PR

1. В проекте `arsenkin` подтверждаются GitHub-репозитории frontend и backend.
2. Cockpit сам находит PR #705–710; в сайдбаре появляется число PR, требующих внимания.
3. Новые замечания автоматически разбираются и появляются в `/reviews` с понятными
   рекомендациями.
4. Для каждого спорного пункта выбирается решение.
5. Все готовые PR ставятся в очередь.
6. Cockpit по одному создаёт для них отдельные рабочие среды и песочницы.
7. Каждый PR получает собственный отчёт.
8. После приёмки каждый PR публикуется своей кнопкой.
9. PR с пересекающимися файлами после merge предыдущего обновляется и проверяется повторно.

## Когда можно считать первую версию готовой

`READY-*` ниже — производные критерии, а не отдельные test IDs. Они не получают собственных
строк `required` в manifest и не могут стать зелёными от одного теста с именем `READY-*`.
Release-отчёт вычисляет их из перечисленных ordinary IDs; если хотя бы один из них `planned`
или красный, весь соответствующий `READY-*` остаётся незавершённым.

- `READY-00` (`RB-01`–`RB-07`): все release blockers зелёные, manifest не содержит planned
  записей и обязательных skipped-тестов;
- `READY-01` (`MAP-01`, `UI-01`): PR видны при полном отсутствии песочниц;
- `READY-02` (`MAP-02`–`MAP-08`): проект и маршрут определяются без сообщения в чат;
- `READY-03` (`WATCH-01`–`WATCH-08`): новые замечания появляются автоматически;
- `READY-04` (`UI-02`–`UI-07`): чип считает PR и восстанавливается после потери SSE;
- `READY-05` (`SYNC-01`–`SYNC-11`): комментарии полные, согласованные и не смешиваются;
- `READY-06` (`ANALYZE-01`–`ANALYZE-09`, `TRANSLATE-01`–`TRANSLATE-08`): новый комментарий
  получает проверяемый технический разбор и понятную рекомендацию без изменения смысла;
- `READY-07` (`WATCH-03`, `WATCH-RATE-01`–`WATCH-RATE-05`,
  `WATCH-RACE-01`–`WATCH-RACE-04`): неизменившийся PR не тратит model call, лимиты, рестарты и
  два процесса не создают дубли;
- `READY-08` (`RUN-01`–`RUN-08`): старые конвейеры задач не изменяются;
- `READY-09` (`ISOLATE-01`–`ISOLATE-07`): PR не используют общую ветку, worktree или песочницу;
- `READY-10` (`SEC-01`–`SEC-10`, `SEC-COOKIE-01`–`SEC-COOKIE-05`, `SEC-VERIFY-01`,
  `UI-SEC-01`–`UI-SEC-02`, `API-SEC-01`–`API-SEC-03`): недоверенный текст не получает секреты,
  инструменты или возможность выполнить код в интерфейсе;
- `READY-11` (`GATE-01`–`GATE-09`): спорный пункт нельзя исправить без серверного решения
  человека;
- `READY-12` (`FRESH-01`–`FRESH-08`): изменение PR блокирует устаревшую работу и публикацию;
- `READY-13` (`VERIFY-01`–`VERIFY-06`): по замечанию видны изменение, проверка и точный digest;
- `READY-14` (`PUBLISH-01`–`PUBLISH-09`): push идёт в точный head ref и невозможен без приёмки;
- `READY-15` (`ISOLATE-05`, `ISOLATE-06`): песочница сносится только вручную;
- `READY-16` (`QUEUE-01`–`QUEUE-08`, `RECOVER-01`, `RECOVER-RACE-01`): рестарт не теряет очередь
  и выполняет только разрешённое crash-матрицей действие.

Готовность нельзя отметить вручную одной демонстрацией. Для каждого `READY-*` CI-отчёт должен
содержать перечисленные test IDs.

## Небольшая техническая граница

Для безопасности реализация обязана сохранить несколько внутренних правил:

- каждая попытка получает собственный внутренний идентификатор, не равный номеру задачи;
- каждый снимок и анализ привязаны к полному GitHub node key, head SHA и версии замечаний;
- неизменившийся снимок не создаёт новый анализ;
- технический анализ и перевод не имеют пишущих прав;
- перевод хранится отдельно от технического артефакта и не может изменить его решение;
- исходная версия PR запоминается и сравнивается перед работой и публикацией;
- одновременно нельзя запустить две попытки одного PR;
- записи состояния выполняются атомарно и защищены lease с fencing token;
- scope, VERIFY и приёмка привязаны к точному candidate tree digest;
- SSE сообщает только об изменении, а источником истины остаётся серверный snapshot;
- публикует host-код после ворот, а не пишущий агент;
- обычные `t<TASK>.pipeline` и их архивы review-функциональность не трогает.
