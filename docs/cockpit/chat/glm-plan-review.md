# GLM: ревью плана и исправленные контракты

Проверено 01.10.2026 отдельным критиком и автором доработки по текущему дереву Cockpit
и первичным исходникам OpenCode. Объект ревью — [план TDD](glm-integration-tdd-plan.md).
Интеграция не реализована, бинарь, модельные запросы и реальные MCP не запускались.
Приоритет P1 означает пробел допуска, P2 — существенную неоднозначность для исполнителя.

## Замечания критика

## Проверенные основания в Cockpit

[Контракт адаптера](../../../server/src/lib/executors/index.ts) содержит в `sessionBinding`
только `authProfileId` и `securityProfile`. [Чат](../../../server/src/modules/chat/index.ts)
сохраняет sessionId в обработчике `err.stopped`; обычная error-ветка не инвалидирует binding.
Существующая страховка `emptyRun` применяется к другому исходу. Поэтому слова «подключить
готовый механизм сброса после crash» давали исполнителю несуществующий API.

[Загрузчик](../../../server/src/lib/executors/index.ts) допускает адаптер в `getExecutors()`
по наличию `run`. Production `run` нельзя добавлять для удобства интеграционного теста:
тестовый resolver позволяет проверить чат, сохранив установочную карточку.

В [реестре моделей](../../../server/src/lib/modelsRegistry.ts) `resolveModelEfforts()`
отдаёт общий массив `executor.efforts()` раньше `model.efforts`. Исключение в `modelEfforts()`
сохраняет общий массив. Самое прямое решение для GLM — не объявлять оба метода и возвращать
per-model массивы из каталога. Custom-метаданные не отменяют проверку фактического runtime.

[ACP-клиент](../../../server/src/lib/acp/client.ts) не сообщает вызывающему момент записи
request в stdin. План выбирает консервативную границу перед вызовом `request('session/prompt')`.
[Retry helper](../../../server/src/lib/chat/retryContract.ts) анализирует возвращённый
`out.emptyRun`, а не произвольный `err.retryState`. Для ошибки после попытки prompt нужен
публичный code/message, а отсутствие автоматического повтора проверяется счётчиком запросов.

[Автоклассификатор](../../../server/src/lib/chat/autoApprove.ts) не устанавливает файловую
границу. `onPermission` общего чата учитывает `requiresExplicitUser`, поэтому именно адаптер
обязан отличить внешний путь. Тот же мост поддерживает `signal`, `canRemember` и
`acceptsComment`; их явные значения предотвращают обещание неподдержанного канала ответа.

Отсутствие `scopedWorkspace` закрывает соответствующий триаж, а штатный арбитр Factory
требует режим `plan`. Фактический обход Factory ревью не подтвердило. В план добавлены
регрессии отказа и preflight входа `run`, а не утверждение об обнаруженной уязвимости.

## Проверенные основания в upstream

Три уточнения — сохранение variant, подавление ошибки MCP и накопительная стоимость —
подтверждены чтением точного тега и внесены в [исследование](glm-integration-research.md).
Они меняют необходимые проверки; совместимость живого runtime из исходников не следует.

[Документация plugins](https://opencode.ai/docs/plugins/) описывает автоматическую загрузку
локальных plugins и установку их зависимостей при запуске. Поэтому итоговый server config
сам по себе не доказывает отсутствие ранее исполненного проектного кода. S04 проверяет
отдельные источники и фактические marker-эффекты, включая metadata-вызовы.

## Дополнительная доработка исполнения

- Разделены fake ACP, настоящий runtime с локальными fake model/MCP и live Z.ai.
  Отдельный runtime runner обязателен; отсутствие бинаря или изоляции сети не становится skip/GREEN.
- Снят цикл S01 → ещё не существующий installer/profile: spike использует временный
  проверенный артефакт, а production launcher повторяет контракт после S03/S04.
- Metadata-запуски получают отдельные cwd/home; проверяются listener, дочерние процессы,
  случайное наследование секретов и отсутствие побочных модельных запросов.
- Уточнены источники SSH/DB-policy, загрузка hook внутри поставляемого runtime и границы
  кооперативного запрета. Защита от произвольного same-uid кода не обещается.
- Для инструкций требуется marker в реальном запросе fake model, для иконки — браузер
  с настоящими стилями. Helper-тест и DOM-тест не заменяют эти доказательства.
- Нативный `question` отложен целиком, чтобы у исполнителя не было неопределённой развилки
  внутри первой поставки. Вопросы текстом и ожидание permission остаются.
- Повторное чтение критиком уточнило реальные поля provider DTO, очистку наследуемого env
  и внедрение fake endpoint в общий launcher. Отдельный упрощённый launcher не доказывает
  применение production profile; выдуманных capabilities для question/images в UI не добавляется.

Обычный API и OpenCode остаются допущениями автора плана. Ревью их не превращает в явно
подтверждённые пользователем требования. Непройденный обязательный gate оставляет интеграцию
незавершённой; все флажки S00–S14 пока открыты.
