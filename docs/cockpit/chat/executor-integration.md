# Модульное подключение нового ИИ

Реестр сканирует файлы `.ts` и `.js` в `server/src/lib/executors/`; отдельной регистрации Kimi в Fastify и Vue
не требуется. Адаптер экспортирует базовый контракт `id/name/vendor/color/bin/probe/auth/
seedModels/run`, а при наличии API аккаунта добавляет:

```js
{
  async usage() {
    return {
      state: 'ok',
      bars: [{ key: 'month', group: 'subscription', label: 'Месяц', pct: 24 }],
      resources: [{
        key: 'balance',
        label: 'Баланс Kimi',
        summary: '12 CNY',
        controls: [
          { id: 'top-up', kind: 'link', label: 'Пополнить', href: 'https://…' },
          {
            id: 'auto-top-up',
            kind: 'toggle',
            label: 'автопополнение',
            value: false,
            action: 'configure-auto-top-up',
            field: 'enabled',
            confirm: { on: { text: '…', label: 'Включить' }, off: { text: '…', label: 'Выключить' } },
          },
        ],
      }],
    };
  },
  usageActions: {
    'configure-auto-top-up': async ({ payload, requestId, config, deps }) => {
      // Адаптер валидирует payload и вызывает только API своего провайдера.
    },
  },
}
```

Ядро нормализует ресурсы, отбрасывает не-HTTPS ссылки и неизвестные controls. Внешний клиент
не может передать произвольный метод: выполняются только ключи из `usageActions` конкретного
адаптера. `requestId` обязателен на границе UI для идемпотентных денежных/расходуемых операций.

**Порядок полос и границы вёдер задаёт адаптер, а не сервис.** У одного аккаунта лимитов
несколько, и полосы одного ведра («сессия» и «неделя» одной модели) обязаны идти подряд.
Необязательное поле `group` называет ведро; `providerUsageView` ставит тонкую линию там, где
`group` сменился, — про вендора всплывашка при этом не знает ничего. Полоса без `group` линии
НЕ порождает: черта утверждает «дальше другое ведро», а исполнитель, который вёдра не назвал,
такого не сообщал. Сравнение идёт с последним НАЗВАННЫМ ведром, поэтому неназванная полоса не рвёт группу
и не начинает свою.

Как это выглядит у каждого исполнителя:

| исполнитель | источник вёдер | порядок | что называет `group` |
|---|---|---|---|
| Codex | объект `rateLimitsByLimitId` | СВОЙ (сервис тасует ключи) | `limitId` ведра |
| Claude | массив `limits[]` | сервиса, стабилен | `subscription` либо `scoped:<модель>` |
| Kimi | массив `summary` + `limits[]` | сервиса, стабилен | `subscription` либо `named:<имя>` |

**У Claude в `limits[]` есть СВОЁ поле `group`, и кокпит его намеренно не берёт.** Оно
означает тип ОКНА (`session` против `weekly`), а разделитель во всплывашке означает другую
КВОТУ. По версии сервиса `weekly_all` и `weekly_scoped` попали бы в один блок, и при нескольких
модельных квотах (`seven_day_opus`, `seven_day_sonnet` и прочие) было бы не видно, где кончается
одна и начинается другая. Поэтому кокпит группирует по квоте: общие лимиты подписки против
каждой модельной. Незнакомый `kind` при этом всё равно доезжает — своим именем, без allowlist.

Сортировать порядок обязан сам адаптер, если сервис его не гарантирует. У Codex
`rateLimitsByLimitId` — ОБЪЕКТ, и OpenAI отдаёт ключи в разном порядке на каждый ответ
(замер: шесть запросов подряд дали три разных порядка), поэтому минутное обновление шапки
перетасовывало полосы прямо под курсором. `parseCodexRateLimits` ставит первой общую квоту
аккаунта (ведро без собственного `limitName` — в неё упираются раньше всего), остальные
сортирует по ВИДИМОЙ подписи: по внутреннему id `base_model_inference` встал бы впереди
`codex`, хотя человек читает «gpt-reserve» и «Неделя (7д)». У Claude `limits` — массив, его
порядок стабилен, и сортировать там нечего.

Имена вёдер целиком принадлежат сервису: `limitName` вроде `gpt-reserve` (отдельная недельная
квота на инференс базовой модели, `limitId: base_model_inference`) или `GPT-5.3-Codex-Spark`
приходят по сети и в бинаре CLI не встречаются вовсе — поэтому новое ведро появляется в шапке
без релиза кокпита и без ветки по его имени в коде. Схема app-server это и закрепляет:
`rateLimitsByLimitId` объявлен открытой картой строковых ключей, никакого перечисления.

**Слоты окна внутри ведра перечислять списком тоже нельзя.** Сегодня схема знает ровно
`primary` и `secondary`, но `['primary', 'secondary']` в коде — снимок сегодняшней схемы, и
третий слот выпал бы молча, как выпадало бы новое ведро при allowlist по id. Окном считается
любое поле ведра с числовым `usedPercent`; `credits` и `individualLimit` под это не подходят —
у первого процента нет вовсе, у второго он называется `remainingPercent`. Порядок внутри ведра —
по длительности окна (сессия перед неделей), а не по имени слота.

**Имя лимита приклеивается к подписи окна, а не проигрывает ей.** У Kimi узнаваемое окно
проверялось первым, поэтому два именованных недельных лимита рисовались двумя одинаковыми
строками «Неделя (7д)». Теперь как у Codex: «Неделя · k2-reserve». У известных окон
длительность в скобках дублирует само слово и уходит, у вычисленного «Окно (3д)» она и есть
весь смысл подписи и остаётся.

**Контроль трат — отдельный ресурс, а не полоса лимита.** `individualLimit` (персональный
денежный потолок) и `spendControlReached` (упёрлись ли в него) приходили в ответе с самого
начала и не показывались нигде, поэтому исчерпанный потолок выглядел как «всё молча встало».
Ресурс `spend-control` появляется, ТОЛЬКО когда сервису есть что сказать: `null`/`false` — это
молчание, и пустая строка в шапке была бы шумом. Суммы остаются строками как пришли: это деньги,
`Number` на них молча теряет точность. Причину сервис называет кодом (`rateLimitReachedType`),
кокпит переводит известные и показывает незнакомый как есть — выдумывать за сервис перевод хуже,
чем показать его слово. `planType` не показывается: тариф и так виден по составу вёдер.

У Claude тот же сигнал зовётся `extra_usage.spend_limit_reached` и живёт не отдельным ресурсом,
а прямо в карточке доплаты: она И ЕСТЬ его контроль трат. Выбранный потолок делает её красной и
добавляет строку «сверх лимитов подписки работа не пойдёт» — тон важнее включённости, потому что
доплата формально включена, а работа уже встала. Выводить это из `used >= limit` нельзя: у
выключенной доплаты и у режима «без потолка» чисел может не быть вовсе.

Что у Claude приходит и НЕ читается: `severity` каждого лимита (сервис сам оценивает близость к
границе, а кокпит держит свой порог 85%), `is_active` (какой лимит сейчас связывает) и
верхнеуровневые вёдра `five_hour`/`seven_day`/`nimbus_quill` и прочие — они читаются только как
fallback при пустом `limits[]`, который остаётся каноническим источником панели.

**Ведро, которого раньше не было, помечается «новое».** Открытость карты вёдер означает, что
новое ведро появится САМО, но заметить его человеку было нечем — `gpt-reserve` обнаружился
случайно. Время первого появления каждого ведра лежит в `server/.state/provider-usage-seen.json`
(`lib/providerUsageSeen.ts`): состояние серверное, потому что вёдра общие для всех окон.
Метка — бухгалтерия кокпита, а не факт адаптера: адаптер называет ведро полем `group`, а помнит
ли его человек, знает только сервер.

Три инварианта, каждый чем-то оплачен:

- **первое наблюдение исполнителя — базовая линия**: все вёдра записываются как «было всегда»,
  иначе первый же показ объявит новыми сразу все. Та же грабля, что с меткой «новая» у задач
  B24, где пустой набор нельзя путать с «ничего не открывали»;
- **метка гаснет сама через две недели, подтверждения человеком нет**: всплывашка раскрывается
  наведением, и случайный проезд мышью снимал бы метку, которую никто не прочитал, — ровно тот
  отказ, против которого она заведена. Цена честная: не открывал шапку две недели — метку
  пропустил;
- **считается только по удачному чтению**: при отказе полосы приходят из прошлого ответа
  (`mergeProviderUsage`), и базовая линия по ним записала бы вёдра, которых сервис прямо сейчас
  не подтверждал. Битый файл тоже даёт базовую линию заново: потерять метку дешевле, чем
  объявить новым весь список.

Вытесняются из памяти только вёдра, отсутствующие в текущем ответе: выбрось запись
присутствующего — и оно вернётся с новым временем, то есть притворится новым.

**Знак исполнителя — часть подключения, а не украшение.** Иконку рисует
`web/src/shared/ProviderIcon.vue` по `provider.id`; **нет своей ветки — молча включается
фоллбэк «кружок с первой буквой имени»**. В этом и ловушка: пропажа выглядит «почти
нормально», поэтому отсутствие знака нужно проверять отдельно. Правила:
монохром через `currentColor` (цвет задаёт место: топбар и настройки берут нейтральный,
список чатов — фирменный `provider.color` самого исполнителя, см. выше),
`aria-hidden`, свой `viewBox`. Официальный знак **допустимо упростить** — заливка рядом со
штриховым claude читается кляксой, поэтому у claude в комментарии написано «упрощённая»,
а голова ламы обведена линией. Соседей уравнивают КАДРОМ, а не размером: `viewBox` у знаков
разный (`0 0 24 24`, `-2 -2 35 36`, `2.3 -0.4 19.4 19.4`), сходятся они по оптической массе.
Проверять замером на трёх реальных размерах — 15 (`AppShell`), 19 (`ChatList`),
20 (`SettingsView`), — а не на одном крупном: детали пропадают именно на 15.
Регрессия — `tests/web/provider-icon.component.test.js`.
- **Недоставленные ответы**: ход, принятый по `turnId`, ВСЕГДА кладёт итог в
  `chats/pending/<turnId>.json` — его HTTP-запрос давно получил подтверждение приёма
  ([доставка хода](turn-delivery.md)). Синхронный запуск без `turnId` пишет туда только при
  `request.socket.destroyed` (F5/закрытие вкладки). Живым окнам уходит SSE `chat-orphan`.
  Фронт забирает GET /api/chat/pending при `_load()`, по `chat-orphan`, `chat-done` принятого
  хода и на каждом `hello`, раскладывает по чатам (dedup по `pid` в сообщении) и подтверждает
  DELETE'ом только после устойчивой записи истории с ответом. Ошибки тоже доезжают
  (role: error, с лентой шагов). Навигация внутри SPA ответы не теряет — стор глобальный.

**Свежесть лимитов держит фоновый тик сервера, а не наведение и не открытая всплывашка.**
Цифры читались один раз, на `mouseenter` по ряду иконок, и дальше стояли; потом их перечитывала
открытая всплывашка (тик раз в 30 с, пока открыта), но первое наведение после минуты тишины всё
равно запускало живой поход к вендору, и секунды показывался прошлый снимок. Теперь сервер сам
перечитывает лимиты раз в период (`usageTickMs` модуля providers) и рассылает снимок всем окнам
событием SSE `providers-usage`; стор кладёт его через `applyUsage` и сдвигает свой минутный
троттл, поэтому наведение читает готовое. Тик молчит, пока ни одно окно не держит `/api/events`
(`sse.clientCount()`; слушатели процесса вроде пульта в счёт не идут — они подписаны всегда), и
не перечитывает снимок моложе половины периода: его только что принёс запрос окна. Открытая
всплывашка по-прежнему перечитывает сама (`open` — принудительно, дальше тик раз в 30 с, `close`
гасит): это страховка на оборванный поток, и к вендору такое чтение не ходит, потому что
серверный кэш (`createUsageReadCache`: `read()` окнам, `refresh()` тику) остаётся единственным
читателем usage. Запрос один на всех исполнителей (`GET /api/providers/usage`), отдельного
чтения на иконку нет.

**Период чтения лимитов — СВОЙ и длиннее реестра, а на «стучитесь реже» кокпит замолкает.**
Фон стучится, пока открыт кокпит, а не пока водят мышью, и минутный шаг (общий `CACHE_MS`
реестра) круглосуточно упёрся в отказ живого аккаунта: «Anthropic временно ограничил запрос
проверки лимитов». Поэтому у лимитов свой `USAGE_CACHE_MS` = 5 мин, и это ОДНА величина с
периодом тика и TTL кэша: разойдись они — между тиками к вендору ходило бы чтение окна. Окна
лимитов измеряются часами и неделями, пятиминутный шаг не теряет ничего: сессия в 5ч сдвигается
за это время на 1,7%. Отказ по частоте (`rate_limited`) — единственная беда, на которую ответ
молчание: сеть, протухший вход и отсутствие API лечатся повтором или человеком, а повтор в
прежнем темпе держит аккаунт в отказе сам. Пауза персональная (отказ у одного аккаунта ничего не
говорит про соседний) и считается в СВОИХ тиках: `USAGE_BACKOFF_TICKS` = 3 и дальше вдвое до
потолка `USAGE_BACKOFF_MAX_TICKS` = 12, то есть 15 → 30 → 60 минут при пятиминутном шаге.
Хранится сама пауза, а не число отказов: на потолке она перестаёт расти без отдельного счётчика.
Названный вендором `retryAt` (Retry-After) берётся, когда он длиннее — заголовка может не быть
вовсе, а просьба «через 30 секунд» вернула бы прежний темп. Внутри паузы тики идут, но отдают
прошлый снимок как есть: он уже несёт и слова вендора, и последние полосы. Удачное чтение
снимает паузу целиком, прочие беды её не трогают.

**Кнопка «проверить сейчас» во всплывашке обходит TTL кэша, но не пределы вендора.**
Фон ходит раз в пять минут, а человеку иногда нужна цифра этой минуты: `POST
/api/providers/usage/refresh` зовёт `refresh()` кэша и рассылает итог всем окнам тем же
`providers-usage` — проверку попросило одно окно, а полосы общие. Три границы: снимок моложе
`USAGE_FORCE_MIN_AGE_MS` = 15 с отдаётся как есть (дробь кликов не превращается в очередь походов);
пауза после отказа соблюдается самим чтением, и кнопка на неё не влияет; ход один на все
всплывашки (`usageRefreshing` стора), кнопки соседей показывают тот же спиннер. Срок паузы сервер
кладёт в `retryAt` снимка (`withPauseUntil`), и всплывашка по нему гасит кнопку и пишет рядом с
отказом «Следующая проверка сегодня 03:45» (`usagePauseOf`, формат `resetAt`): клик, который молча
вернул бы прошлые цифры, хуже погасшей кнопки с временем. Snapshot с `retryAt` в прошлом кнопку не
гасит — пауза снята, следующее чтение честное.

**Всплывашка топбара ПОКАЗЫВАЕТ, а меняют в плашке настроек.** Ручка ресурса объявляет
`scope`: по умолчанию её крутят только в «Настройках → Исполнители» — деньги аккаунта не меняют
мимоходом, из шапки, наведением мыши. Состояния ручек всплывашка не отражает вовсе: на «включено
или нет» уже ответила сводка ресурса, и строки «доплата выключена», «потолок: 20 USD» повторяли
её второй раз. Заметка ресурса остаётся там ТОЛЬКО у беды (`tone: 'bad'`): «месячный потолок
выбран — сверх лимитов подписки работа не пойдёт» терять нельзя, а спокойная «причина отказа:
out_of_credits» рядом со сводкой «выключено» — та же мысль другими словами; в плашке настроек
заметка остаётся всегда, там её читают, когда доплата не включается. `scope: 'live'` — операция над рантаймом (например, использовать заработанный сброс лимита у Codex): она отвечает на «что делать сейчас» и остаётся
кнопкой там, где видно состояние. Ссылки и кнопки в текст не переносятся: это действия, а не
свойства ресурса. Оба места рисует один `ProviderUsageResources`, режим задаёт `readonly`;
редактируемый блок «Ресурсы исполнителя» живёт в его карточке настроек.

**Шапка всплывашки — имя исполнителя.** Строка «Claude (Anthropic) · доступен · CLI хоста
(claude login) · 2.1.258 (Claude Code)» повторяла плашку настроек и занимала две строки из шести;
вендор, способ авторизации и версия остались в настройках, а во всплывашке имя делит строку с
точкой обновления. Из выброшенного вернулось одно: слово «недоступен» рядом с именем, когда
исполнитель недоступен. «Доступен» не пишется — это норма, а вот пропажу этого факта вместе со
строкой подробностей человек читал бы как «лимиты почему-то не пришли». Переход в
«Настройки → Исполнители» — шестерёнка в этой же строке, справа от точки обновления: полосой во
всю ширину внизу он забирал седьмую строку всплывашки ради одного перехода. У всплывашки версии
кокпита подвал-полоса (`.ptip-go`) остался — там переход единственное действие, и сжимать его
не ради чего.

**Подпись полосы называет и отсчёт, и календарный момент сброса.** «Сброс через 4д»
отвечает на «скоро ли», но не на «во сколько ждать окно», а планируют работу по второму:
`resetIn` даёт отсчёт, `resetAt` — «сегодня 07:19», «завтра 03:00», «15 сен 03:00», и вторая
половина уходит к правому краю строки, тише цветом. «Сегодня» и «завтра» считаются по местной
полуночи, а не по суткам вперёд: сброс через 20 часов приходится то на завтра, то на
послезавтра. Месяц и часы форматируются СВОИМ списком и `padStart`, а не через `Intl`:
сокращения ICU («сент.») скачут в длине, а урезанная сборка молча подменяет локаль чужой —
в строке фиксированной ширины это заметно сразу. Полоса без даты сброса показывает свою заметку и никакой даты не выдумывает.

**Ширина всплывашки ЗАДАНА, а не ограничена сверху.** С `max-width` она дышала между
`min-width` поверхности (260) и потолком: содержимое меняется на каждом тике («4ч 59м» → «4ч»,
проценты, новое ведро), и всплывашка ездила прямо под курсором, а переход на соседнюю иконку
менял её ширину вместе с составом полос. Теперь `width: min(320px, calc(100vw - 20px))` —
одна ширина у всех исполнителей и на любом тике; на узком экране замер даёт 310 при вьюпорте
330, строки при этом не переносятся.

**Сбой у вендора называет сам адаптер полем `statusPage`.** «Не удалось получить лимиты» без
адреса отправляло человека гадать по журналам, у кого поломка. Адрес официальной страницы
состояния объявляет адаптер (`claude` → status.claude.com, `codex` → status.openai.com, `kimi` →
status.moonshot.cn: у kimi.com своей страницы нет, сбои публикует Moonshot AI), реестр отдаёт его
полем `statusPage`, и Vue не хранит ни одного вендорского домена — подпись ссылки это хост из
URL. Подсказка показывается ТОЛЬКО у беды на стороне сервиса (`unavailable`, `blocked`,
`rate_limited`) и стоит СВЕРХУ, рядом с самим сообщением: своя беда чужой страницей не лечится —
при `auth_required` надо логиниться, при `unsupported` обновлять CLI. Локальный исполнитель поля
не объявляет: у демона на этой же машине внешней страницы состояния нет, и выдумывать её фронт
не вправе.

**Страницу состояния кокпит ЧИТАЕТ, а не только показывает ссылкой.** Ссылка отвечала «сходи
посмотри сам», а вопрос у человека один: это у меня или у них. Сервер разбирает сводку Atlassian
Statuspage (`<statusPage>/api/v2/summary.json`, `lib/providerStatus.ts`) и кладёт разобранное в
`usage.vendorStatus`: индикатор, слова сервиса, до трёх НЕ operational компонентов и заголовок
свежего инцидента. Знание форматное, а не вендорское — домена в ядре по-прежнему нет ни одного,
адрес объявляет адаптер. Инварианты: страница читается ТОЛЬКО у беды на стороне сервиса (иначе это был бы внешний запрос на каждый фоновый тик) и кэшируется на минуту по адресу; незнакомая форма
и недоступная страница дают `unknown` — придумывать за неё «у них всё хорошо» нельзя, подсказка
возвращается к одной ссылке; контейнер группы (`group: true`) в список компонентов не идёт, иначе
одна беда называется дважды; чужие тексты обрезаются (120/60 символов) и лишаются переводов строк —
это данные, а не разметка. Сеть до страницы состояния такая же нестабильная, как и до самого
вендора, поэтому чтение идёт через общий `withRetry`: две попытки с паузой, дольше держать ответ о
лимитах диагностика не вправе. Отдельная подпись «показываем последние успешно полученные
значения» при этом убрана: над полосами уже стоит «не удалось получить лимиты, повторим проверку
автоматически», и вторая строка о том же занимала место, ничего не добавляя.
