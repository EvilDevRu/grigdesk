# «Агент повис» на длинном ходе = лимит ленты глушил не хранение, а трансляцию

`createStepSink` (`lib/chat/streamSteps.ts`) выходил из `emit` целиком, как только
накапливал `MAX_CHAT_STEPS` (400): дальше не вызывался `onStep`, значит не уходил ни
SSE `chat-step`, ни копия в `activeRuns`. Ход на 1500 шагов (обычное дело для Codex на
ultra: reasoning + tool + res на каждый вызов) выбирал лимит за час и **дальше работал
для окна беззвучно** — вечное «думает…» без единого нового шага, и не отличить от
настоящего зависания. F5 не помогал: серверная копия хранила ПЕРВЫЕ 400 шагов, то есть
восстанавливала картину часовой давности.

Усугубляет Codex: `onProgress` у него вызывается только на `turn.completed`
(`executors/codex.js`), поэтому счётчик «думает… · N ток.» за ход не тикает ни разу —
других признаков жизни у окна не остаётся. У Claude счётчик живой, там немота ленты
менее заметна.

Теперь лимит ограничивает только **хранение**, и оно скользящее (последние 400) —
и в sink, и в `activeRuns`, и в сторе окна. Трансляция безусловна. Правило на будущее:
буфер и поток — разные вещи, переполнение буфера не имеет права затыкать поток.

Как проверять такое, не гадая: `GET /api/chat/active` показывает `at` последнего шага
(если он застыл, а `~/.codex/sessions/<...>.jsonl` растёт — виноват кокпит, не агент),
а `curl -sN /api/events` покажет, идут ли `chat-step` по этому `chatKey` вообще.
