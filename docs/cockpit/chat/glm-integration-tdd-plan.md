# План TDD: GLM как исполнитель Cockpit

Статус: план, реализация не начата. Доработан после двух независимых ревью 01.10.2026.
Рассчитан на исполнителя, которому нужны маленькие задачи, точные проверки и минимум
самостоятельных архитектурных решений. Доказанные исходные факты и ссылки вынесены в
[исследование интеграции](glm-integration-research.md), исправленные пробелы — в
[результаты первого ревью](glm-plan-review.md) и
[повторная проверка границ допуска](glm-plan-trust-gates.md).
Ревью не закрывает ни одного этапа реализации.

## 1. Результат и принятые решения

Пользователь выбирает «GLM (Z.ai)» в обычном чате Cockpit. Агент отвечает потоком, читает
и правит проект, запускает команды с действующей политикой разрешений, вызывает рабочие
MCP, помнит разговор между ходами и останавливается общей кнопкой. История и ответы после
перезагрузки окна проходят через существующие механизмы Cockpit.

Основной вариант доступа — обычный API Z.ai. Это допущение плана, а не подтверждённый выбор
пользователя. Вариант Coding Plan задаётся явно и использует другое подключение. Локальные GLM,
OpenRouter, BigModel и произвольные совместимые endpoint в первую поставку не входят.
Два режима проверяются offline, но производственный допуск выдаётся каждому отдельно после
его live smoke S14. Проверка `api` не разрешает запуск `coding-plan`, и наоборот.

OpenCode — также решение автора плана, которое должен подтвердить contract spike S01.
Не выдавать его за отдельное требование пользователя. Предлагаемая архитектура:

```text
Общий интерфейс чата и /api/events
  → существующий modules/chat
  → executors/glm.ts
  → lib/glm: запуск, каталог, права, нормализация событий
  → существующий lib/acp/client.ts
  → отдельный OpenCode заданной версии, команда acp
  → выбранное подключение Z.ai
```

OpenCode предоставляет агентный цикл и инструменты. Собственный HTTP-клиент GLM, SSE-парсер
модельного API и второй движок выполнения shell в этом плане не разрабатываются.
Доступ остаётся прямым к Z.ai; OpenCode — локальный runtime, без обязательного OpenCode Zen.
Основание выбора — [ACP OpenCode](https://opencode.ai/docs/acp/) и
[поддержка Z.AI](https://opencode.ai/docs/providers/#zai).

Первая поставка — доверенные интерактивные чаты на host. Не объявлять `scopedWorkspace`
или `untrustedInput`, не подключать GLM к автоматическому триажу и Factory. Отдельная
песочница, live steering, фоновые субагенты, картинки, динамические native settings,
платёжные действия и прогноз подписки — последующие задачи. Обычный чат с инструментами,
MCP, сохранением памяти и stop входит в этот план целиком.

## 2. Правила выполнения для модели

1. Полностью прочитай `CLAUDE.md`, существующий `CLAUDE.local.md` и ближайшие `AGENTS.md`.
   Перед областью открой её README. Не читай реальные чаты, ключи или runtime-сессии.
2. Работай по одному пункту TDD. Сначала тест поведения, затем RED, минимальный GREEN,
   затем небольшой рефакторинг и повтор тех же проверок.
3. Ошибка импорта нового файла — только начальная стадия. Создай заглушку контракта и получи
   падение содержательного assertion, прежде чем писать реализацию поведения.
4. Один подпункт RED ниже — один короткий цикл. Не пиши сразу весь runtime по списку тестов.
5. Подменяй внешние границы: процесс, сеть, часы, пути. Не подменяй функцию, поведение которой
   проверяешь. Тесты с `source.includes(...)` не доказывают работоспособность интеграции.
6. Не меняй ветку, не делай commit/push, не откатывай чужой diff. Перед правкой общего файла
   перечитай его: рабочее дерево может меняться параллельно.
7. После каждого этапа запиши пройденные тесты и следующий шаг. Флажок `[x]` означает,
   что критерий этапа доказан, а не что создан файл.
8. На провале обязательной совместимости останови зависимые этапы и зафиксируй наблюдение.
   Не обходи проверку, не расширяй права и не переходи молча на другой runtime или аккаунт.
9. Default export остаётся без `run()` до конца S14. S09–S14 используют тестовую композицию
   адаптера с `run` через зависимости стенда. Пропущенный runtime/live-тест не считается GREEN.

Шаблон отчёта этапа:

```text
Этап: Sxx
RED: имя теста и наблюдавшееся неверное поведение
GREEN: точная команда, exit code, число проверок
Изменённые файлы:
Проверенные ограничения:
Доказательство допуска: вид стенда, версия/хеш runtime, путь к очищенному отчёту
Следующий этап:
```

его кэш и реестр не смешиваются с соседними тестами и живыми исполнителями.

## 5. Конфигурация и контракт первой поставки

### Доступ и хранение

| Настройка службы | Значение и правило |
| --- | --- |
| `COCKPIT_GLM_API_MODE` | `api` по умолчанию; явно `coding-plan` для подписки |
| `ZAI_API_KEY` | Ключ только обычного API |
| `ZAI_CODING_API_KEY` | Ключ только явно выбранного Coding Plan |
| `COCKPIT_GLM_RUNTIME_HOME` | Абсолютный приватный каталог; по умолчанию `path.join(config.stateDir, 'cockpit-glm')` |
| `COCKPIT_GLM_BIN` | Абсолютный путь к установленному и проверенному OpenCode |

Ключ выбранного режима обязателен. Не использовать ключ другого режима как fallback.
Имена upstream providers получить из проверенного runtime в S01 и закрепить в `contract.ts`;
это идентификаторы подключений, список model IDs там не хранить.
В том же файле `releasedAccessModes` изначально пуст. S14 добавляет только режим с доказанными
runtime/live gates; это часть поставленного кода, а не переключатель в env или prefs.
В production `auth.available` для недопущенного режима — `false` с причиной, а preflight
`run` отклоняет его до spawn даже при наличии ключа. DI-стенд проверяет оба кандидатных
режима без изменения production-списка. Отсутствующий ключ отличается от отсутствия допуска.
Изолированный installation probe/metadata discovery разрешён для setup-only карточки,
но не отправляет model prompt и не выдаёт недопущенному режиму `available: true`.
В server config достаточно добавить `glmRuntimeHome` и `glmBin`; доступ читает helper
из окружения службы. Не создавать форму API-ключа в публичных prefs.

Ключ передавать процессу через его environment и ссылку `{env:...}` в приватной конфигурации.
Не включать его в argv, ошибки, историю, публичный каталог или журнал запуска.
Пути, XDG и конфигурация дочернего процесса строятся заново. Каталог состояния сессии
разделяется по серверному `chatKey`, преобразованному в hash, а не по сырой строке из HTTP.
Каталоги — `0700`, файлы с конфигурацией — `0600`.
Для `probe`/catalog/refresh выделить отдельные пустые cwd и home, без проектных MCP,
инструкций и plugins. Все вызовы OpenCode проходят один launcher с явным назначением
`metadata` или `turn`; карточка не запускает runtime в `config.rootDir` или cwd чата.

`auth()` сообщает «ключ задан в окружении службы», а не «ключ проверен Z.ai».
Проверка карточки и моделей не отправляет model prompt. Ошибки ключа/квоты/сети выявляются
обычным запуском и не превращаются в ложную успешную авторизацию.

### Адаптер

После завершения S14 производственный адаптер объявляет:

- `id: 'glm'`, `name: 'GLM (Z.ai)'`, `vendor: 'Z.ai'`, `order: 5`;
- `bin`, `probe`, `auth`, `install`, `catalogLive: true`, `catalog`, `catalogCacheKey`, `seedModels`;
- `retryContract: RETRY_CONTRACT.PRE_PROMPT_ONLY`, `compaction: { kind: 'summary' }`;
- `sessionBinding` и `workToolsTransport: 'mcp'`;
- `workdir: { switch: 'reseed', roots: 'single' }` только после проверки S10;
- `modes()` с `default` («Спрашивать») и `auto` («Авто»);
- `settings` и `directSshPolicy` только с доказанным enforcement из S07;
- `run`, `mcpStatus`; per-model усилия — только подтверждённые каталогом/runtime.

`default` и `auto` используют агентный режим работы с кодом и нативные permission requests.
В `auto` решение принимает существующий классификатор Cockpit; нативный режим «разрешить всё»
не включается. Название `plan` у OpenCode не считать доказательством read-only.
В первой поставке нет режима без подтверждений или заявленной изоляции ОС.

`seedModels()` возвращает `[]`: свежая установка получает список от runtime, а при временном
сбое остаётся последняя сохранённая версия каталога. Общий `efforts()` не объявлять:
его массив имеет приоритет над `model.efforts` в registry. `catalog()` возвращает `efforts`
у каждой модели отдельно; неизвестные усилия — `[]`. `modelEfforts()` для этого не нужен.
Не объявлять пока `session`, `inTurnInput`, `nativeSettings`, `untrustedInput`, `scopedWorkspace`.
Неизвестные usage/context/cost остаются неизвестными, а не нулевыми.

Preflight `run` требует непустой серверный `chatKey`, `onSessionCreated`, явную модель
выбранного подключения и поддержанный permission mode. Вход с `workspaceAccess`, без
контракта интерактивного чата или с режимом `plan`/обхода разрешений отклоняется до spawn.
На границе `run` значения `undefined` и `''` означают `default`: общий `allowedMode()`
именно так передаёт отсутствие выбора. Явные неизвестные значения при прямом вызове
отклоняются. Через chat route неизвестный mode уже превращён в `''`; здесь проверить
безопасный default, а не требовать восстановить потерянное исходное значение.
Отсутствие `scopedWorkspace` закрывает триаж; отсутствие режима `plan` закрывает штатный
арбитр Factory. Эти отрицательные сценарии проверяются отдельно, а не выводятся из названия GLM.

### Сессия и повтор

```text
preflight → spawn → initialize → new/resume → durable binding
  → set mode/model/effort → verify selection → prompt → updates → result → cleanup
```

`onSessionCreated` нужно дождаться до первого prompt. Ошибка сохранения binding запрещает
отправку текста. Модель и усилие устанавливаются заново после resume; session ID браузера
не заменяет серверный sidecar. Смена ключа, режима API или политики меняет fingerprint.
Отсутствие effort во входе означает снятие прежнего override: после `high` нельзя просто
пропустить setter. Передать подтверждённое S01 значение сброса (`default`, если оно
поддерживается) и сверить текущее значение. Для модели без effort option проверить отсутствие
прежнего variant. Не менять выбранную модель, чтобы исправить ошибку усилия.

`AcpClient.request()` не выдаёт подтверждения записи в stdin. Поэтому перед самым вызовом
`request('session/prompt', ...)` консервативно поставить `promptAttempted = true`.
Как только запись могла начаться, исход при обрыве считается неопределённым.
Отсутствие ответа JSON-RPC не доказывает, что агент не начал действие. Автоповтор после этой
границы запрещён. `session/load` может повторно публиковать историю; в нормальном пути
использовать подтверждённый `session/resume`, а не угадывать их эквивалентность.

Общий чат сохраняет binding после stop и обычной ошибки. Готового capability для
«сбросить сессию после аварии» сейчас нет. Поэтому безопасный resume после cancel, hard kill
и обрыва после эффекта — обязательный gate S11. Если он не пройден, оставить setup-only;
quarantine/новый контракт инвалидирования потребует отдельного пересмотра плана.

## 6. Порядок TDD

Каждый этап зависит от предыдущего, кроме чистых parsers S05/S08: их можно готовить после S01.
В S12 проверяется композиция в изолированном чате; производственный реестр допускает GLM
только в конце S14. Исследовательский S01 не считается GREEN всей интеграции.
Исследовательский launcher S01 не становится доказательством production-профиля:
после S04 все относящиеся runtime-сценарии повторяются через общий production launcher с DI.

Три вида доказательств нельзя подменять друг другом:

| Стенд | Что доказывает | Где выполняется |
| --- | --- | --- |
| Fake ACP + настоящий код Cockpit | Порядок callbacks, ошибки, CAS, поток, общий UI | Обычные `tests/server` и `tests/web`, без OpenCode/сети |
| Настоящий закреплённый OpenCode + локальные fake model/MCP | Применение профиля, инструменты, права, состояние после отмены/аварии | Отдельный обязательный runner `tests/glm-runtime/run-contracts.sh` |
| Настоящий OpenCode + выбранный доступ Z.ai | Реальная совместимость модели и аккаунта | Ограниченный ручной smoke S14 |

Runner второго вида проверяет артефакт и завершается ненулевым кодом, если его нет или
контракт нарушен. Он не скачивает `latest` и не подменяет отсутствие runtime зелёным skip.
Runner создаётся в S01 и принимает `--stage Sxx`: выполняет все runtime-контракты,
обязательные к указанному этапу. Состав этапов задан явно, не определяется наличием файлов.
Нет обязательного файла/фикстуры — ошибка, а не пропуск. Без `--stage` проверяется S14 целиком.
Обычный `tests/run-all.sh` не устанавливает runtime и не обращается к Z.ai. В итоговом отчёте
результат отдельного runner обязателен; зелёный общий набор его не заменяет.

  | --- | --- | --- |
  | Ошибка доступа, конфигурации, binding, model/effort до prompt | Бросить безопасный error с кодом причины; `retryState: pre_prompt` только диагностика | Нет |

  | Обрыв после попытки prompt | Бросить error с `code: glm_ambiguous_outcome`, `retryState: ambiguous_outcome`, sessionId/steps; сообщение «Связь оборвалась после отправки. Действие могло выполниться; автоматического повтора не было.» | Нет |

  | Принятый пустой terminal result | Вернуть `emptyRun: true, retryState: post_prompt`, sessionId/steps | Нет; общий чат инвалидирует пустую сессию |
  | Нормальный terminal result | Вернуть reply/sessionId/steps и только подтверждённые метрики | Нет |

- **Готово:** JSON-RPC/process errors дают корректный отказ и cleanup. Не подключать `run`

  Наличие общего разрешения на реализацию не забывать и повторно его не спрашивать.
- Сервер из агентного чата не перезапускать. После серверных изменений назвать человеку
  необходимый ручной рестарт. До live проверки статус — «offline готово, live не проверено».
- Только после обязательных runtime/live gates добавить `run()` в default export.
  Перед этим обновить `releasedAccessModes` только доказанными режимами и добавить RED/GREEN
  на production preflight: недопущенный режим с ключом не запускает процесс; допущенный
  попадает в свой provider/endpoint. Сам test adapter и наличие ключа не являются допуском.
  Assertion setup-only из S02 осознанно заменить проверкой обнаружения исполнителя новым
  процессом загрузчика; никаких тестовых env-флагов для включения production `run` не оставлять.
  Повторить изменённые адресные тесты и typecheck, зафиксировать полный прогон финального diff.
- **Готово:** все обязательные пункты раздела 8 подтверждены. Если остался исходный чужой отказ
  общего набора, в отчёте остаются его имя и код выхода; наличие проверенного baseline не делает
  весь набор зелёным. Пропущенный обязательный GLM gate запрещает производственный `run()`.

## 7. Команды проверок

Команды выполняются из корня репозитория. Запускать только существующие к этому этапу файлы.
Один файл, например S05:

```bash
bash tests/run-node-tests-safe.sh --test tests/server/glm-catalog.test.js
```

Несколько связанных файлов:

```bash
NODE_TEST_MAX_RSS_MB=4096 bash tests/run-node-tests-safe.sh --test --test-concurrency=2 \
  tests/server/glm-runtime.test.js \
  tests/server/glm-session.test.js \
  tests/server/glm-stop.test.js
```

Основная регрессия после S12:

```bash
NODE_TEST_MAX_RSS_MB=4096 bash tests/run-node-tests-safe.sh --test --test-concurrency=2 \
  tests/server/models-registry.test.js \
  tests/server/chat-provider-binding-capability.test.js \
  tests/server/chat-provider-routing.test.js \
  tests/server/deepseek-acp-client.test.js \
  tests/server/deepseek-project-mcp.test.js \
  tests/server/ssh-executor-contract.test.js \
  tests/server/db-executor-contract.test.js

NODE_TEST_MAX_RSS_MB=4096 bash tests/run-node-tests-safe.sh --test --test-concurrency=2 \
  tests/web/provider-icon.component.test.js \
  tests/web/glm-provider.component.test.js \
  tests/web/chat-model-availability.component.test.js \
  tests/web/chat-model-ref.test.js

npm --prefix server run typecheck
npm --prefix server run typecheck:tests
```

Первый отдельный контракт S01 и финальный допуск S14:

```bash
bash tests/glm-runtime/run-contracts.sh --stage S01 --bin /tmp/glm-contract/runtime/opencode

bash tests/glm-runtime/run-contracts.sh --stage S14 --bin /tmp/glm-contract/runtime/opencode
```

Путь — пример приватно подготовленного артефакта S01/S03; runner принимает абсолютный `--bin`,
проверяет manifest, готовит изолированный стенд и вызывает Node-тесты только через
`tests/run-node-tests-safe.sh` с лимитом памяти 4096 MB и concurrency 2. Логи/exit code
сохраняются в `.state/artifacts/`. Если OS-граница сети требует подготовки машины,
закончить независимые тесты, затем запросить именно этот ручной шаг; не объявлять стенд
изолированным по одним env-переменным. Новые runtime-тесты включить в соответствующий tsconfig.
К S01 добавляется `../tests/glm-runtime/**/*.mts` в `server/tsconfig.tests.json`; runtime-тесты
не должны выпадать из typecheck до финального этапа. Минимальный состав runner:

| Этап `--stage` | Добавляемый обязательный сценарий |
| --- | --- |
| S01 | `protocol.test.mts`: metadata, точные каналы, fake-model/tool lifecycle |
| S04 | `profile.test.mts`: повтор S01 через production launcher, все источники и секреты |
| S06 | `instructions.test.mts`: реальные запросы fake model с правилами/импортами |
| S07 | `permissions.test.mts`: exact identity, pre-effect deny/allow, SSH/БД |
| S09 | `turn.test.mts`: selection, ошибки, граница повтора и внутренние retries |
| S10 | `session.test.mts`: память, reset/compaction и смена профиля |
| S11 | `stop.test.mts`: cancel/crash/hard kill и счётчик эффектов после resume |
| S12 | `mcp.test.mts`: readiness, provenance, collision и смена inventory/scope |
| S14 | Все перечисленные offline-сценарии для обоих кандидатных access modes |

Промежуточный `--stage` выполняет накопленный набор, а не одну новую спеку. После изменения
runtime/profile/hook/MCP повторять накопленный набор достигнутого этапа; на S14 обязателен весь.
S02/S03/S05/S08/S13 не добавляют runtime-файл в эту таблицу и выполняют накопленный набор
предыдущей строки; неизвестный stage отклоняется. Новые tests добавляются в runner в своём этапе.
Live smoke не входит в offline runner и не появляется автоматически от выбора `--stage S14`.

Читаемость: `node web/scripts/check-code-readability.mjs --files <изменённые файлы кода>`.
Не передавать весь чужой diff. Все комментарии и интерфейсные сообщения — по-русски.
Общий прогон после адресных проверок — `bash tests/run-all.sh`. Долгий прогон отсоединять,
сохраняя exit code и лог в `.state/artifacts/`. Для этого набора использовать
`setsid --wait bash -c 'bash tests/run-all.sh'` без `&`, удерживая вызов инструмента:
`nohup ... &` наследует игнорирование SIGINT и даёт ложный отказ signal-теста.
Не запускать вторую копию поверх существующей.
После зелёных тестов и при изменениях web — `npm --prefix web run build`; помнить, что он
пишет в используемый `web/dist`. Сборка документации не требует этой команды.

Сторож всего набора может обнаружить исходные отказы общего дерева. Записать точные тесты,
exit code и ограничения; не обозначать весь набор GREEN, если прошли только адресные проверки.

## 8. Приёмка

| Проверяемое поведение | Где доказать |
| --- | --- |
| Setup-only сохраняется до приёмки, затем исполнитель обнаруживается без ручной регистрации | S02, S12, S14 |
| Ключ и режим не перепутаны, чужой провайдер не вызывается | S02, S04, S14 |
| Каждый производственный access mode имеет свой допуск; ключ не открывает непроверенный режим | S02, S09, S14 |
| Probe/catalog изолированы от проектных plugins/MCP и не отправляют prompt | S01, S02, S04, S05 |
| Версия и install integrity закреплены | S01, S03 |
| Project config не меняет endpoint/политику и не запускает посторонний plugin | S04 |
| Новая модель обнаруживается без правки списка в коде | S05 |
| Effort различается в registry по моделям, применяется и сбрасывается после resume | S05, S09, S10 |
| Инструкции проекта и их импорты доставлены | S06 |
| Разрешение/отказ/abort и SSH/БД gate действуют до эффекта | S07, S14 |
| Exact tool identity и MCP provenance не подменяются title/kind или коллизией runtime key | S01, S07, S12 |
| Текст, tool result и поздние шаги доходят до общей ленты | S08, S12 |
| Resume сохраняет память и не смешивает чаты | S10 |
| Stop/crash после эффекта и следующий resume не повторяют действие | S11 |
| Обрыв после попытки prompt даёт понятный неопределённый исход без retry | S09, S12 |
| Обязательный MCP готов до prompt и работает через server-owned scope | S01, S12 |
| Накопительная стоимость сессии не выдаётся за расход хода | S08 |
| F5/разрыв HTTP не теряет ответ и не дублирует его | S12, S14 |
| Смена исполнителя/папки и compaction соблюдают прежние контракты | S10, S13 |
| UI показывает реальные capabilities и отдельный знак | S13 |
| Factory/триаж и неподдержанный запуск отклоняются до spawn | S09, S12 |
| Действующий GLM ответил через настоящий runtime в каждом режиме `releasedAccessModes` | S14 |

Карточка, один mock-ответ или зелёный parser-test по отдельности не закрывают интеграцию.

## 9. Что передать следующему исполнителю

```text
Реализуй docs/cockpit/chat/glm-integration-tdd-plan.md по порядку.
```

не удалять. Для отката не использовать общий reset рабочего дерева.
