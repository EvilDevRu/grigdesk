# MCP у GLM: только cockpit-work, готовность до prompt и потеря

DSH не спрашивает approval для MCP-инструментов, поэтому проектные MCP-серверы из `.mcp.json`
в процесс GLM не подключаются вовсе: каждый даёт предупреждение в журнале хода, запуск
продолжается, а их инструментов нет в запросе модели (и поздних — тоже). Процесс получает
только служебный `cockpit-work` чата.

- Имя сервера — 2–32 символа без `__` и без `_` на краях (иначе имя сервера не читается из
  `mcp__<сервер>__<инструмент>`). `cockpit-work` в `.mcp.json` проекта зарезервирован.
- Имя инструмента — формула `dsh-mcp-client`: при нормализации до `[A-Za-z0-9_-]` или длине
  больше 64 — первые 51 символ, `_` и `sha256("<сервер>\0<инструмент>")[:12]`.
- `cockpit-work` монтируется с `failOnStartupError: true`: адрес web выдаётся только после
  `initialize` и `tools/list`, а сломанный `initialize` завершает процесс до prompt —
  `glm_mcp_not_ready`, модельных запросов нет.
- Переподключение выключено (`reconnect.enabled: false`). Иначе `dsh-mcp-client` молча
  перезапустил бы упавший сервер и выполнил вызов в новом экземпляре. Без него вызов после
  потери получает «Not connected», ход GLM останавливается с `glm_mcp_not_ready`, эффекта нет.
- Инструмент `cockpit-work`, объявленный после старта (`tools/list_changed`), DSH регистрирует,
  но hook политики его отклоняет: в инвентаре запуска его нет.
- Resume применяет текущий набор: инструменты прошлого запуска в запросе не появляются.

Статус MCP карточки GLM называет только число проектных серверов папки Кокпита, без имён,
команд и окружения, и прямо говорит, что они не подключаются.
