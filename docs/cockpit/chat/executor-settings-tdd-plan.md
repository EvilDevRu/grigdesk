## 1. Результат и границы первой реализации

В раскрытой карточке исполнителя появляется блок нативных настроек. Его поля, типы,
варианты и ограничения приходят из схемы установленного CLI. Обновление схемы добавляет
и снимает поля без изменения Vue и без добавления ключей в ручной реестр Cockpit.

Принятые для этого плана продуктовые решения:

1. Новые значения — **переопределения для чатов Cockpit**, применяемые при следующем
   безопасном открытии сессии. Подпись области в форме: «Для чатов Cockpit».
   Глобальные конфиги пользователя, конвейер `engine` и служебные задачи не меняются.
   Расширение на эти области — отдельная задача, поскольку у них другие права и запуск.
2. Источники обнаружения подключаются для Claude, Codex, Kimi и DeepSeek. Запись
   подтверждается для общего конфигурационного слоя/namespace данного транспорта,
   а не отдельным ручным allowlist ключей. Новый типизированный leaf в проверенном
   канале становится редактируемым после общей валидации и проверки ownership.
   Нетипизированное поле или новый неподтверждённый канал видны с объяснением запрета.
3. Существующие `settings[]`, запрет SSH, `fastMode`, выбор модели/effort, ресурсы и MCP
   сохраняют свои контракты. Если нативное поле уже управляется существующим контролом,
   второй независимый редактор не появляется: показывается его владелец/объяснение.
4. Изменение настройки не прерывает активный ход. Общая форма подтверждает сохранение
   для следующего запуска; успешная запись prefs не означает применение в конкретном чате.
   Факты передачи и подтверждения CLI проверяются отдельно на границе запуска.
5. Схема — источник состава полей. Значения, прочитанные из конфига, не заменяют схему:
   по одному текущему значению нельзя узнать допустимые варианты или неизвестные defaults.

Допустим код, знающий методы протокола, форматы схем и служебные границы адаптера.
Недопустимы списки всех нативных настроек, enum и defaults, вручную перенесённые из CLI.
Количество полей из анализа нельзя использовать как производственную константу.

- [оглавление тестов](../testing/README.md),

  [кэш document Vue](../testing/vue-document-cache.md).

Для каждого сценария внутри этапа выполняй цикл:

1. Напиши **один** тест наблюдаемого поведения.
2. Запусти его и сохрани причину RED. Ошибка импорта, синтаксиса или окружения не считается
   нужным RED: при необходимости создай минимальный экспорт-заглушку и дойди до assert.
3. Добавь минимальную реализацию, получи GREEN.
4. Убери дублирование, если оно появилось, и повтори затронутый тест после рефакторинга.
5. После всех сценариев этапа прогони указанные соседние регрессии и отметь этап.

Не пиши весь набор будущих тестов и всю реализацию одним большим изменением.
Не ослабляй существующий тест ради прохождения нового кода. В тесте отказа все остальные
предусловия должны быть правильными: например, проверка read-only поля обязана передавать
актуальную ревизию, иначе тест может пройти из-за совершенно другого отказа.

Во время работы веди локальный журнал в `.state/artifacts/executor-settings-tdd/`:
этап, тест, ожидаемое падение, результат GREEN, остаток работы. При передаче следующей
сессии укажи первый незакрытый этап и конкретные проверки; не полагайся на фонового агента.

Не начинай с двух полных универсальных нормализаторов. Первый проход этапов 1–5 делает
один boolean у synthetic provider: wire → минимальная нормализация → проверка → каталог →
запись. Затем доведи его через fake CLI (7) и форму (8–10). Это проверяет архитектурные
границы до расширения типов. Только после этого вернись к остальным сценариям 1–5,
подключи реальные источники (6) и заверши 7–10. В журнале различай «минимальный проход»
и «этап завершён»; один boolean не закрывает весь этап.

## 3. Зафиксированный контракт

### API

Существующий `POST /api/providers/:id/settings` не переименовывать и не расширять
приёмом произвольных нативных ключей. Для нового блока добавить:

| Маршрут | Назначение |
| --- | --- |
| `GET /api/providers/:id/settings/catalog` | Ленивое получение каталога и сохранённых overrides |
| Тот же GET с `?refresh=1` | Принудительное обновление источника |
| `POST /api/providers/:id/settings/overrides` | Одна операция `set` или `unset` над override |

В `GET /api/providers` добавить только capability `settingsCatalog: boolean`.
Получение реестра не вызывает медленное обнаружение нативных настроек.
Все новые маршруты находятся под существующей авторизацией `/api`.

POST принимает `fieldId`, `operation`, `schemaRevision`, `revision` и `value` только
для `set`. Схему, RPC-метод, команду, путь файла и произвольный cwd клиент не передаёт.
`fieldId` сервер разрешает в путь по своему каталогу. Для `unset` не использовать
`value: null`: null может быть допустимым самостоятельным значением.

`revision` — строковое представление ревизии хранения, при отсутствии контейнера `"0"`.
`schemaRevision` — отдельный отпечаток каталога; для `set` он обязателен и не равен null.
`unset` разрешает `schemaRevision: null`: операция удаляет существующий override по его
сохранённому id, проверяет ревизию хранения и не требует работающего CLI. Отсутствующий
override при актуальной ревизии — no-op. При наличии схемы сброс также не записывает
её default в prefs. Поле `schemaRevision` в запросе не опускается.

Общая карточка показывает каталог базового контекста адаптера: профиль и режим выбраны
сервером из существующей конфигурации запуска. Это не effective-конфиг каждого чата.
Подпись: «Базовые значения исполнителя; настройки папки чата могут их уточнить».
При запуске сервис получает настоящий cwd и заново проверяет совместимость overrides.

Проверка `set` выполняет обновление источника даже внутри обычного TTL чтения. Структуру
из неизменившегося бинаря можно переиспользовать, но политики, состав доступных полей и
readiness источника сверяются заново. Затем сравнивается `schemaRevision`; stale-результат
для записи непригоден. Долгое чтение CLI происходит до короткой транзакции prefs.
В транзакции повторно проверяются ревизия хранения и поколение каталога; если каталог
успел измениться — 409, без записи. Это не обещает атомарность с внешним CLI:
на границе запуска проверка выполняется ещё раз.

### Общие типы

Создать `shared/providerSettingsContracts.ts`, не дублируя `ProviderEntry` из
`shared/providersContracts.ts`. В новом файле определить JSON-значение, каталог,
узел формы, запрос изменения, ответ и runtime-декодеры.

Обязательные сведения каталога:

| Поле | Семантика |
| --- | --- |
| `protocolVersion` | Версия нашего wire-контракта, сначала `1` |
| `providerId` | Исполнитель |
| `state` | `ready`, `partial`, `stale` или `unavailable` |
| `scope` | Область записи `cockpit-chats`, с русской подписью |
| `source` | Вид источника, версия CLI, время проверки; без секретов и runtime id |
| `schemaRevision` | Отпечаток структуры, ограничений, контекста, доступности и владельцев; null, если безопасного каталога ещё нет |
| `revision` | Строковая ревизия хранения overrides, сравниваемая перед записью |
| `fields` | Нормализованные узлы формы |
| `inactiveOverrides` | Сохранённые, но больше не применимые overrides с причиной |

`state` относится к каталогу, а полнота задаётся отдельно для каждого источника/namespace
в `source.coverage`: `complete` или `partial`. Снятие поля доказывает только успешный
ответ с `complete` для его области. Смешанный каталог не теряет эту информацию.

Узел формы содержит `id`, `path: string[]`, подпись, описание, вид, ограничения,
children/items при необходимости, доступность записи, причину запрета и владельца.
Виды: `boolean`, `string`, `number`, `integer`, `enum`, `object`, `array`, `unknown`.
Путь содержит и namespace, если он есть у источника. Не разделять путь по точке:
ключ `a.b` и вложенность `a → b` различаются. Идентификатор можно получать стабильным
кодированием массива сегментов; пользовательская подпись не участвует в идентичности.

Default, override и значение источника представляются раздельно. Для каждого нужен
явный признак `known/unset/unknown/redacted`. Только `known` содержит `value`.
У `redacted` допустим признак наличия значения, но не само значение.
Не заменять unknown на `false`, `0`, пустую строку или schema default.

Enum сохраняет исходный JSON-тип значения. Строка `"1"`, число `1` и boolean `true`
не становятся одним пунктом. Неизвестный тип узла декодируется как read-only
`unknown`, чтобы новая версия сервера не ломала всю карточку старого клиента.

В первой версии object — группа, операции над ней целиком запрещены; редактируются
типизированные листья. Массив примитивов — один атомарный override, без overrides его
индексов. Это исключает неоднозначный порядок наложения родительского и дочернего пути.
Запрет записи самой группы не закрывает её редактируемые листья; политика managed/secret
для ветки, напротив, распространяется на всех потомков.

Ответ сохранения подтверждает только запись и необходимость следующего запуска.
В первой версии он имеет форму `{ ok: true, changed, catalog }`: `changed` означает
фактическое изменение storage, а не применение. Ошибка — `{ error, message }`, где
`error` — стабильный код, `message` — безопасное русское пояснение.
Новый журнал применения в форме и API истории чатов в этот план не входят. Факты
«передано»/«подтверждено» относятся к конкретной сессии и ревизии, проверяются адаптером
и тестами; их нельзя переносить из одного чата на весь исполнитель.

### Хранение

Нативные overrides хранить отдельно от плоских локальных полей, внутри:

```text
providerSettings[providerId].nativeSettings = {
  format: 1,
  revision: <монотонный номер>,
  overrides: {
    <fieldId>: { path: <массив сегментов>, value: <JSON-значение> }
  }
}
```

`nativeSettings` — зарезервированный контейнер Cockpit, он никогда не передаётся
в CLI как нативный ключ. Не сохранять весь каталог, новые секреты или развёрнутые defaults.
Неактивность вычислять при сверке со свежей схемой, сохраняя исходный выбор для человека.
GET ничего не переписывает в prefs. `unset` удаляет только соответствующий override.

Ревизия принадлежит всему набору native overrides одного исполнителя. После удаления
последнего поля оставить контейнер с новой ревизией и пустым `overrides`; не возвращать
ревизию в `0`, иначе старая вкладка сможет записать поверх нового состояния.
Неизвестный `format` и структурно повреждённый контейнер не заменять пустым: чтение даёт
безопасную ошибку состояния, запись — `settings_storage_invalid` без изменения файла.

Общий `/api/settings/prefs` уже защищает `providerSettings`; новая запись должна
оставаться под этой защитой. Старый `/providers/:id/settings` не должен принимать
`nativeSettings` как ещё одну ручку.

Для обоих writers использовать одну синхронную операцию в `PrefsStore`:
`updateProviderSettings(mutator)`. Она читает строгий актуальный снимок, вызывает чистый
mutator над копией всего `providerSettings` и записывает результат атомарным write.
Между чтением и записью нет `await`; для нового API mutator проверяет CAS и no-op.
Старый маршрут сначала асинхронно проверяет декларацию/подтверждение, затем адресно
меняет один локальный ключ этой же операцией. Он больше не записывает снимок, который
прочёл до `await`. В одном процессе сервера это общая граница для всех provider ids;
многопроцессная запись prefs не входит в этот план.

**Публичная проекция:** из GET и успешного POST `/api/settings/prefs` исключить только
вложенный `nativeSettings` у каждого исполнителя, сохранив прежние локальные поля.
`PrefsStore.read()` для внутренних потребителей не урезать. Каталог — единственный
публичный путь новых значений; его серверная проекция проверяет все slots и не отдаёт
raw storage. У `inactiveOverrides` всегда только id, безопасный путь/подпись и причина,
без исходного value. Если поле стало secret/unknown, прежнее значение остаётся приватно
до явного unset, но в HTTP и журнал не попадает. Не вызывать discovery из общего prefs API.

### Граница запуска

Добавить отдельное внутреннее поле запуска `nativeSettings` с **уже проверенным**
планом применения и его fingerprint. План строится на сервере для фактического cwd
чата. Сырой сохранённый контейнер не считается таким планом.

Существующие потребители `providerSettings` включают триаж, арбитров, генерацию
commit message и другие служебные задачи. Они не должны автоматически получить
новый override из-за общего чтения prefs. Новое поле передаёт только путь чата.
`runUntrusted` не принимает нативные overrides. Рабочие корни, hooks, sandbox,
служебные MCP и формат протокола остаются под контролем соответствующего адаптера.

Снимок выбора берётся при фактическом начале нового хода после ожидания очереди.
Сохранение во время уже открытого хода и доставка уточнения через in-turn/steer не
меняют его настройки. Если prefs обновились во время подготовки, текущий старт
использует уже выбранный снимок, следующий — новый. Непосредственно перед открытием
повторно проверить актуальную политику для выбранного снимка.

В `restartOn` передавать отдельную строку `nativeSettingsFingerprint`, а не весь объект
плана. Сырой контейнер предварительно исключён из старого `providerSettings`.
Fingerprint вычисляется из применяемых значений, семантики слоя и контекста; ревизия
storage, timestamps и неприменимые поля в него не входят. После снятия последнего
override пустой fingerprint должен отличаться от прежнего непустого и вызвать reset.

### Минимальный внутренний контракт адаптера

Имена ниже зафиксированы для `server/src/lib/executorSettings/types.ts`. Это server-only
типы: ни сырой snapshot, ни подготовленный payload не включаются в wire-каталог.

| Метод capability `nativeSettings` | Вход | Результат |
| --- | --- | --- |
| `discover(context, options)` | `NativeSettingsContext`, `{ signal, refresh }` | `Promise<NativeSettingsSnapshot>` |
| `prepare(context, snapshot, overrides, options)` | Тот же контекст, проверенный snapshot, принятые overrides, `{ signal }` | `Promise<PreparedNativeSettings>` |
| `verify(plan, readback)` | Подготовленный план и нормализованное чтение из конкретного runtime | `NativeSettingsEvidence` |

- `NativeSettingsContext`: `providerId`, `binaryIdentity`, `profileFingerprint`,
  `transport`, `mode`, `cwdRealpath`. Все значения задаёт сервер, не браузер.
- `NativeSettingsSnapshot`: контекст, идентификатор поколения, версия источника;
  список областей `{ path, format, dialect, schema, coverage, writeChannel }`,
  приватные прочитанные значения и политика ownership. `format` — JSON Schema или
  Schemastery; сырой `schema` начинается как `unknown` и проходит декодер формата.
- `writeChannel`: идентификатор слоя/namespace, область действия, состояние
  `verified | unsupported | unverified`, причина и совместимость с transport/profile/
  версией. `verified` означает доказанные формат, приоритет, изоляцию и reset общего
  слоя. Он не хранит allowlist всех ключей. Новая версия/канал не наследуют статус
  автоматически, если совместимость протокола не подтверждена.
- `PreparedNativeSettings`: `providerId`, `contextFingerprint`, `schemaRevision`,
  `storageRevision`, `fingerprint`, список принятых `{ fieldId, path, value, channelId }`
  и приватный типизированный JSON payload для адаптера. Это неизменяемый снимок;
  `prepare` не меняет работающую сессию или глобальный конфиг.
- `readback`: список сведений о принятых полях с основанием
  `accepted | effective | applied | unavailable`; значения остаются внутри сервера.
  `NativeSettingsEvidence` содержит field id, fingerprint и результат
  `sent | confirmed | overridden | rejected | unknown` с безопасным кодом причины.
  `confirmed` допустим только по достоверному `applied`; наличие в effective-конфиге
  доказывает чтение конфигурации, но не поведение модели. Отсутствие applied даёт
  `sent/unknown` и не закрывает само по себе доказанный канал передачи.

Нормализация, валидация и публичная проекция остаются в общем сервисе. Адаптер знает
формат источника, владение и способ записи своего payload. Синтетический адаптер обязан
пройти эти методы через настоящий общий сервис; прямой вызов fixture-helper не считается.

### Этап 1. Wire-контракт и независимые состояния значений

**Тест:** `tests/server/provider-settings-contract.test.js`.

RED → GREEN, по одному сценарию:

1. Декодер различает `known(false)`, `known(0)`, `known("")`, `known(null)` и `unset`.
2. Неизвестный вид поля сохраняется как read-only unknown; известные соседи доступны.
3. В `set` обязательно собственное поле `value`; в `unset` его быть не должно.
4. В запросе отсутствующая ревизия, лишние команды/пути и некорректная операция отклоняются.
5. Путь с точкой внутри сегмента не совпадает с двухсегментным путём.
6. Redacted-узел не может содержать скрытое `value` под другим полем wire-ответа.
7. `schemaRevision: null` допустим только для `unset`; ревизия хранения нужна всегда.

Реализовать типы и декодеры, затем добавить **типизированное** необязательное
`nativeSettings` capability в `ExecutorAdapter`. Не заменять его на `unknown`/`any`.
Общий контракт адаптера разделяет обнаружение, подготовку к запуску и проверку результата.
В этих типах не должно быть имён Claude/Codex/Kimi/DeepSeek.

Готово, когда синтетический пятый исполнитель проходит тот же декодер.

### Этап 2. Нормализаторы схем

**Тесты:** `tests/server/provider-settings-json-schema.test.js`,
`tests/server/provider-settings-schemastery.test.js`.

Начать с boolean, затем string/number/integer, enum, object, array и nullable.
Не пытаться реализовать весь стандарт JSON Schema за один цикл.

Подэтапы, каждый с собственным GREEN: **2a** scalar/enum; **2b** локальные refs;
**2c** object и наследование ограничений; **2d** массив примитивов; **2e** безопасный
fallback сложных веток. Затем повторить те же наблюдаемые сценарии для Schemastery.

Минимальная матрица JSON Schema первого прохода:

| Категория | Поддержка |
| --- | --- |
| Метаданные | `title`, `description`, `default`, `examples`, `$id`, `$schema`, `$comment` не являются ограничениями значения; `readOnly`/`writeOnly` учитываются как политика |
| Ссылки | Локальные `$ref`, `definitions`/`$defs`; циклы и внешние ссылки закрывают затронутую ветку |
| Скаляры | `type`, `enum`, `const`, minimum/maximum и exclusive-границы, `multipleOf`, min/maxLength |
| Контейнеры | `properties`, `required`, типизированный `additionalProperties`, однородный `items`, min/maxItems; проверка предков сохраняется |
| Объединения | Nullable scalar и enum из однотипных const; прочие `anyOf`/`oneOf`/`allOf` read-only |
| Неподдержанное | `if/then/else`, dependent-условия, tuple/`prefixItems`, `patternProperties`, pattern/format с семантикой проверки, прочие неизвестные validation keywords — read-only |

Диалект объявляет источник. Не переносить OpenAPI `nullable` и различающиеся формы
exclusive-границ между диалектами без явного преобразования и теста. Без типа, но с
непустым enum/const, допустим точный редактор этих констант; из текущего value тип не выводить.
Новые annotations игнорируются лишь в явно описанном источником metadata-контейнере;
неизвестный top-level keyword нельзя объявить annotation по догадке. Числовой UI-step
и ограничение `multipleOf` не отождествлять автоматически.

Обязательные RED-сценарии:

1. Добавленный только в fixture ключ появляется в результате без изменения парсера.
2. Enum берётся из схемы и сохраняет типы; minimum `0` и default `false` не теряются.
3. `$ref` и Schemastery `uid/refs` раскрываются без потери ограничений/описаний.
4. Объект `{}` и отсутствие type/enum/const дают unknown, а не угаданный по value редактор.
5. Циклическая ссылка, неизвестный обязательный constraint и неоднозначный union
   переводят затронутую ветку в read-only; остальные ветки сохраняются.
6. Неподдержанный `patternProperties`, tuple или условная схема не теряют ограничения
   молча. Nullable union и enum из однотипных констант обрабатываются явно.
7. Секретный потомок удаляется и из value родителя, default, user/base и массива.
8. Внешний `$ref` не запускает произвольный сетевой запрос из ядра/браузера.

Для словарей поддержать редактирование уже обнаруженных ключей только по объявленному
`additionalProperties`-типу. Произвольное создание ключей не включать в первый проход.
Readonly дочернего поля должно запрещать обход через замену всего родительского объекта.
Ограничить глубину, число узлов и размер схемы; пределы общие, проверяемые тестами.
Разделить известные описательные ключи (`title`, `description`, примеры) и ограничения.
Неизвестный ключ валидации закрывает запись затронутой ветки; неподдержанное ограничение
родителя закрывает запись и его листьев. Проверять не только лист, но и результат
наложения относительно поддержанных ограничений предков. Если для проверки нужен
неизвестный native base, запись недоступна с объяснением, а не разрешена по догадке.

Готово, когда обе fixture-схемы дают одинаковый wire-тип, а неполнота видна в каталоге.

### Этап 3. Валидация, владельцы и безопасное наложение

**Тест:** `tests/server/provider-settings-validation.test.js`.

Сначала тестировать чистую функцию проверки операции, без Fastify и CLI:

1. `false` принимается для boolean, `"false"`, `0` и `{}` отклоняются без coercion.
2. Проверяются enum, целочисленность, конечность, min/max/step, длины и поддержанные
   строковые/контейнерные ограничения. Неподдержанный constraint закрывает запись.
3. Unknown, read-only, secret, managed и чужой field id не изменяют сохранённый объект.
4. Запрещённые служебные ветки нельзя заменить через их предка или элемент массива.
5. Ключи `__proto__`, `prototype`, `constructor` не меняют прототипы объектов.
6. Наложение не мутирует native base и соседние overrides; массивы заменяются целиком.
7. `unset` убирает override: при новом default возвращается новое значение источника,
   а не default, скопированный в prefs при первом сохранении.
8. Запись объекта-группы целиком и отдельного индекса атомарного массива отклоняются;
   допустимые листовые overrides не перекрываются по пути.
9. Лист, сам по себе допустимый, отклоняется при нарушении ограничения родителя.
   Неизвестное родительское условие делает зависимые листья read-only.

Владение защищёнными ветками объявляет адаптер рядом со сборкой запуска. В него входят
существующие controls и служебные параметры, а не список всех разрешённых настроек.
Схема задаёт наличие поля, политика — допустимость его изменения в данном транспорте.
Узлы без надёжного описания секрета/области не раскрывают произвольный сырой объект.

Готово, когда тесты отказов отдельно проверяют код причины и отсутствие мутации.

### Этап 4. Каталог, кэш и эволюция схемы

**Тест:** `tests/server/provider-settings-catalog.test.js`.

Внедрить зависимости discovery, clock и binary identity. В unit-тестах не использовать
реальное ожидание TTL или установленный CLI.

Сценарии RED:

1. Два одновременных чтения одного контекста вызывают discovery один раз.
2. Разные cwd/профили/режимы запуска не получают общий effective snapshot.
3. Новая версия/замена бинаря и изменение состава plugins инвалидируют структуру.
4. Изменение ограничений/rollout при прежней версии CLI обнаруживается после TTL/refresh.
5. Старый запрос, завершившийся после инвалидации, не записывает устаревший результат поверх нового.
6. Первая ошибка даёт unavailable; ошибка после успеха — stale с последним безопасным каталогом.
7. Успешная схема без старого поля делает override неактивным; ошибка discovery не означает удаление.
8. Изменённый тип/enum делает несовместимый override неактивным, не подбирая замену.
9. Отсутствие поля в **неполной** схеме не доказывает удаление: причина «поддержка не подтверждена».
10. Поле, ставшее secret/unknown, не раскрывает прежний override ни в одной ветке ответа;
    inactive projection не содержит исходных значений даже после отказа discovery.

Fingerprint не должен меняться только из-за порядка ключей объекта или времени опроса.
Изменение порядка/содержимого enum, доступа или значимой схемы должно учитываться.
Отсутствующие defaults и метаданные сохранять как неизвестные, не додумывая их.

Готово, когда последовательность v1 → v2 → ошибка → v3 воспроизводится одним тестом
через реальный сервис каталога и сохраняет все пользовательские overrides.

### Этап 5. Хранилище overrides и новые HTTP-маршруты

**Тесты:** `tests/server/provider-settings-overrides.test.js`,
`tests/server/providers-native-settings-route.test.js`.

Сначала repository/service, затем Fastify `inject`:

1. `set` изменяет только указанный override; соседний provider и локальный SSH сохраняются.
2. Запись того же значения — no-op; ревизия и fingerprint применения не меняются.
3. Две записи с одинаковой старой ревизией не затирают друг друга: первая успешна,
   вторая получает conflict. Чтение актуальных prefs выполняется внутри сериализованной записи.
4. Новая схема между GET и POST отклоняет устаревшее редактирование.
5. Повреждённый prefs-файл не заменяется defaults; используется строгий путь записи `PrefsStore`.
6. Неактивный override можно удалить. При недоступном CLI допустим `unset` с null вместо
   отпечатка схемы и актуальной ревизией хранения; `set` запрещён. Повторное удаление
   отсутствующего override с актуальной ревизией — no-op, с устаревшей — conflict.
7. Общий `/api/settings/prefs` и старый `/providers/:id/settings` не обходят новый валидатор.
8. `GET /api/providers` отдаёт capability без вызова discovery; GET каталога вызывает его лениво.
9. Отсутствующий adapter/method, timeout и исключение одного источника не ломают остальных.
10. Авторизация новых маршрутов проверяется через существующую auth-границу приложения;
    один `inject` изолированного providers-модуля этого не доказывает.
11. Старый POST задержан на async-декларации; новый POST успел записать override;
    после завершения старого обе правки сохранены. Повторить с разными provider ids.
12. GET и POST общего prefs API не отдают `nativeSettings`, сохраняют старые локальные
    настройки и не запускают discovery. Значение sentinel не просачивается через эти ответы.
13. После `set → unset последнего поля` ревизия растёт; запрос исходной вкладки получает 409.
14. Неизвестный format/повреждённый контейнер не обнуляется; файл и соседние настройки сохранены.
15. Новая политика внутри ещё не истёкшего TTL обнаруживается на `set`; запись отклонена.
    Изменение поколения каталога во время подготовки также даёт conflict.

Коды нового API: malformed/unknown field для `set` — 400; unknown provider — 404;
read-only/managed — 403; invalid value — 422; revision conflict — 409;
недоступный или stale discovery для `set` — 503; повреждённый файл/контейнер — 500
с `prefs_corrupted`/`settings_storage_invalid`. GET каталога возвращает его состояние в теле,
если сам маршрут и provider существуют. При ошибке записи не возвращать `ok: true`.

Старый маршрут сохраняет свои коды и прежнюю форму ответа. После подтверждённой
новой записи вернуть `{ ok: true, changed, catalog }` из уже проверенного snapshot
и записанных prefs. Не запускать второй RPC после commit: его отказ не должен выдавать
неуспех операции, которая на самом деле сохранена. Добавить тест такого отказа.
Не передавать наружу stdout/stderr или полный ответ CLI как текст ошибки.

Регрессии: `provider-settings.test.js`, `providers-settings-route.test.js`,
`projects-settings-guard.test.js`. Готово, когда новый маршрут обслуживает synthetic
provider без ветки по его id и не меняет старый контракт.

- DeepSeek: не зашивать 14 namespaces. Читать профиль, соответствующий будущему запуску,

- Kimi: использовать request schema POST для записи. Одного появления ключа в GET мало.

- Claude: `get_settings` не перечисляет отсутствующие настройки. Внешнюю схему кэшировать

Каждый reader принимает AbortSignal, ограничивает объём stdout/ответа и освобождает
свои временные файлы, процесс и соединение в `finally`. Timeout завершает принадлежащий
reader процесс, а не только Promise. RED: fake CLI завис на initialize → каталог
unavailable/stale → дочерний процесс завершён → следующий refresh создаёт ровно один
новый. Работающий runtime чата и чужие процессы этим cleanup не затрагиваются.

Готово для чтения, когда все четыре адаптера отдают общий контракт либо точное
partial/unavailable. Это ещё не завершение записи и применения.

### Этап 7. Передача в реальный запуск

**Тесты:** `tests/server/provider-settings-launch.test.js` и сценарии в четырёх
адаптерных тестах предыдущего этапа. **Регрессии:**

**7c** Codex; **7d** Kimi; **7e** Claude; **7f** очередь, in-turn и resume.
После каждого подпункта должен быть GREEN своего файла и запись в журнале.
Проверять транспорты, реально выбранные чатовым адаптером. Наличие вспомогательного
ACP-модуля само по себе не требует добавить ему нативную запись в этой задаче.

Перед включением write-channel выполнить probe в собственном временном профиле:

1. Для аргументов/overlay: исходное чтение → отдельный процесс с override → чтение
   принятой конфигурации → следующий процесс без override → исходное наследование.
   Не изобретать setter для слоя, который существует только на старте процесса.
2. Для файлового setter: сначала создать отдельный слой запуска; доказать семантику
   адресного изменения, чтение результата и reset. Проверить обычного соседа и секретный
   sentinel в приватном временном конфиге: оба сохраняются после set и unset.
   Из redacted GET нельзя собирать полный документ для replace. Если CLI требует replace,
   нужен полный приватный base и проверенное слияние; placeholder не является секретом.
3. Для возобновляемого разговора повторить открытие с тем же id: новое значение и reset
   не должны застревать в параметрах сохранённой сессии. Если CLI не позволяет проверить
   applied без модели, подтверждать только передачу и принятие слоя (`sent/unknown`).

Модель не вызывать, реальные настройки пользователя не менять. Зафиксировать точную
wire-форму, приоритет и границы доказанного канала. Если формат/изоляция не подтверждены,
оставить `unverified`; доказанное отсутствие пути означает `unsupported`, это разные причины.
Не выводить поддержку из одного успешного setter без проверки будущего запуска и reset.

Направление реализации по адаптерам:

| Адаптер | Куда интегрировать | Что доказать |
| --- | --- | --- |
| Claude | `claudeProviderSettingsArgs`, `_claudeStream.ts`, разовый и persistent запуск | Generic JSON через `--settings`; служебные hooks и старый fastMode не потеряны; чтение `get_settings` не приравнивает все effective к applied |
| Codex | Аргументы app-server и конфигурация thread в `codex.ts` | Process-level настройки доходят до процесса; thread-level до thread; нельзя считать `config/read` процесса доказательством override только этой thread |
| Kimi | `hostWebHome.ts`, runtime и server client | `config.toml` временного home — собственный файл, а не symlink на пользовательский; POST пишет в него; contained не наследует host config |
| DeepSeek | `prepareDeepSeekLaunch`, построение файлов профиля и web client | Нативный setter работает с отдельным документом/слоем запуска; shared per-chat home не хранит остатки снятого override |

Для Kimi и DSH особенно важно **сначала изолировать назначение записи**, затем
вызывать setter. Нативный API может сохранять на диск. Копия исходной конфигурации,
если нужна runtime, остаётся приватной, не логируется и не становится fixture.
Нельзя вызывать setter на обычном home пользователя «для проверки».

Для Codex использовать передачу argv без shell. Если нужен TOML, выбрать проверенный
serializer и тестировать строки, кавычки, backslash, Unicode, массивы и вложенность;
JSON.stringify не является ни TOML serializer, ни shell escaping.
Параметры, для которых нельзя подтвердить передачу текущим transport, read-only.

Порядок RED-сценариев общего запуска:

1. Без native overrides запуск имеет прежние аргументы и не делает дополнительный discovery.
2. Новый синтетический ключ из схемы проходит API → storage → chat → фактический вход fake CLI.
   Assert проверяет вход CLI, а не вызов промежуточного setter/helper.
3. Повторная валидация использует cwd запуска. Если активный в базовом каталоге override
   несовместим именно с этим cwd, до prompt вернуть через существующий `channel.refuse`
   код 409, `native_settings_incompatible`, field ids и безопасные причины. Глобальная
   активность не меняется. Проверить два cwd: отказ виден одному чату, второй запускается.
   Подтверждённо неактивные в базовом каталоге поля исключаются из плана как раньше.
4. При unavailable/stale discovery с активными overrides новый запуск получает 503;
   он не стартует с молча потерянными настройками. Уже работающий ход не затрагивается.
5. Смена значения во время busy-хода не вызывает interrupt/close. Следующий ход использует
   новую сессию, если этого требует адаптер, сохраняя существующий механизм resume.
6. Обновление каталога без изменения применяемого набора не переоткрывает сессию.
7. После `unset` новое открытие наследует native base; старое значение не остаётся в файле
   временного профиля, args или состоянии ранее открытой сессии.
8. Служебный `run` без нового внутреннего поля и `runUntrusted` не получают эти overrides,
   даже когда исходный `providerSettings` содержит сохранённый контейнер.
9. Переопределение не меняет work roots, служебные hooks/MCP, sandbox и output format.
10. CLI отверг/перекрыл значение — статус rejected/overridden/unknown, а не «применено».
11. v2 добавила leaf в проверенный channel — он дошёл до fake CLI без изменения адаптера;
    leaf нового неподтверждённого channel виден, но `set` получает запрет с причиной.
12. Изменение prefs при ожидании очереди попало в новый ход; изменение во время подготовки
    не меняет уже взятый снимок. Уточнение in-turn не вызывает новую подготовку или restart.
13. Возобновление того же разговора с новым значением и после reset подтверждено отдельно
    от запуска новой сессии. Не учитывать случайный id/путь в fingerprint.

При сборке параметров чата извлечь сохранённый `nativeSettings` из плоского набора
локальных настроек, проверить его общим сервисом и передать отдельный подготовленный
план. У persistent adapters добавить scalar `nativeSettingsFingerprint` в `restartOn`
и передать его верхним полем spec. `nativeSettings.fingerprint` здесь не работает:
существующий `fingerprintOf` не разрешает dot-path.
Не вычислять fingerprint из времени discovery или случайных временных путей.

Готово, когда цепочка проверена для каждого включённого write-capability и отдельно
подтверждён reset. Положительный ответ `POST overrides` без этой проверки недостаточен.

RED-сценарии store:

1. Открытие карточки вызывает одну загрузку; повторное открытие свежего каталога — ни одной.
2. Смена provider до ответа не записывает результат в другую карточку.
3. Refresh инвалидирует старый незавершённый запрос, но сохраняет черновик до разрешения конфликта.
4. Записи сериализуются **по provider**, поскольку ревизия общая его полям. Изменения

   Другой provider не блокируется; черновики независимы, busy снимается при ошибке.
5. Conflict/validation error сохраняет введённый черновик и показывает ошибку.
6. Успех использует серверный ответ и новую ревизию; клиент не выдумывает effective value.
7. GET, начатый до успешного save, не затирает его поздним ответом. На 409 очередь этого
   provider останавливается, перечитывает каталог и сохраняет drafts; автоматического
   повторного set поверх чужой правки нет. Пользователь видит конфликт и повторяет выбор.

1. Синтетическая схема рисует boolean, number с min=0, typed enum, строки, группы и списки.
2. Переключение fixture v1 → v2 добавляет незнакомое поле без изменения компонента.
3. Неизвестный вид и нетипизированная ветка видны с причиной запрета, остальные поля работают.
4. Reset отправляет `unset`; выбор null отправляет `set` с null. Они различаются в UI.
5. В форме различаются наследование, сохранённое значение и отсутствие подтверждения применения.
6. Read-only/managed/secret не имеют активного пути записи; заменой родителя запрет не обходится.
7. При stale виден последний каталог и причина, при unavailable есть повторная проверка.
8. Неактивный override виден с причиной и действием удаления.
9. Все editable controls имеют label, клавиатурную навигацию и сообщения об ошибке.

Для вложенных объектов использовать раскрываемые группы. Массив примитивов редактируется
как список; сложный массив/union, для которого редактора ещё нет, виден read-only.

Не показывать технические ревизии, RPC-методы и дамп схемы обычному пользователю.

node web/scripts/check-code-readability.mjs --files <только изменённые файлы этой задачи>

Для длительного полного прогона и сборки подготовить отдельный script в
`.state/artifacts/executor-settings-tdd/`, который последовательно выполняет
`bash tests/run-all.sh` и, только при успехе, `npm --prefix web run build`, сохраняет
exit code. Ограничить engine через `TEST_JOBS=2`; перед запуском Bash вернуть
SIGINT/SIGQUIT в стандартное состояние. Фоновый `nohup … &` наследует SIG_IGN:
нужна обёртка, сбрасывающая сигналы до exec, либо `setsid --wait` без фонового `&`.
Основание — [проверка сигналов при отсоединённом запуске](../testing/background-sigint.md).
Читать log до результата.
Не запускать второй полный прогон поверх уже идущего и не убивать держателя lock.

Сервер из агентского хода не перезапускать. После завершения реализации сообщить,
что серверной части нужен ручной перезапуск; это не повод оставить код или тесты незавершёнными.

В сдаче дать матрицу по реально используемым transport/profile/namespace:

| Итог | Условие | Можно завершить соответствующую часть |
| --- | --- | --- |
| Поддержано и проверено | Generic channel, изоляция, передача, reset и нужный resume доказаны | Да; отсутствие applied-readback отмечено как sent/unknown |
| Доказанно не поддержано | Текущий протокол/схема не даёт надёжного способа; есть воспроизводимое основание | Да, как read-only с причиной; полнота внешней схемы может остаться partial |
| Проверка не завершена | Timeout, отсутствующий CLI, невыясненный формат или непроверенный setter | Нет; указать оставшийся probe, без объявления реализации полностью готовой |

Один timeout нельзя переименовать в «не поддержано». Нельзя принять и всё read-only
без исследования: каждый обнаруженный пригодный generic channel должен быть подключён.
Зелёные synthetic-тесты не заменяют эту матрицу.

## 7. Условия завершения

План завершён, когда проверены одновременно:

- появление/снятие полей вслед за достоверной схемой, без редактирования списка ключей;
- работа общих контролов и строгая серверная проверка их значений;
- адресное сохранение и reset без изменения настроек пользователя вне Cockpit;
- достижение поддерживаемых параметров реального транспорта чата;
- корректная жизнь активного хода и применение на следующем безопасном открытии;
- честное отображение ограничений схемы и неизвестного факта применения;
- сохранность прежних настроек, авторизации, ресурсов, MCP и служебных запусков.

Отметка `partial`, доказанный `unsupported` и отсутствие достоверного applied-readback
сами по себе допустимы. Непроверенный путь записи, подменённый обещанием «CLI, наверное,
применит», допустимым результатом не является. В матрице не остаётся `unverified`;
для каждого доступного канала подтверждены передача конфигурации и reset.
