# Спрос ВИСИТ, пока не ответишь (без короткого UI-таймаута)

- Было: 4 минуты на ответ, дальше сервер отвечал агенту deny («не ответил — действуй сам»).
  Человек отошёл — агент уезжал дальше по собственному разумению, а выбор пропадал с экрана.
  Теперь ожидание живёт до ответа (потолок `PERM_WAIT_MS` = сутки), снимается только
  «стопом» или концом хода (`dropPending` — иначе чип «ждёт ответа» висел бы вечно).
- Ждать должны ВСЕ три звена, иначе выигрыша нет:
  1. кокпит — держит HTTP-запрос от permission-mcp (см. [всплывашку разрешений](permission-prompt.md));
  2. **CLI** — `MCP_TOOL_TIMEOUT` в окружении запуска + `timeout` у самого сервера в `--mcp-config`
     (per-server override, «hard wall-clock limit per call»). Без них CLI обрывает вызов
     инструмента своим дефолтом, и агент идёт дальше, пока вопрос ещё висит на экране;
  3. **ход агента** — `execFile` не имеет `timeout`: долгие задачи могут выполняться часами.
     Автоматического лимита длительности у хода нет; прерывание через `ac.abort()` выполняет
     только явная кнопка «стоп».
- `GET /api/chat/waiting` — что висит прямо сейчас. Нужен потому, что SSE доставляет событие
  один раз: после F5 (и во втором окне) всплывашку иначе некому показать. Фронт зовёт его при
  загрузке стора и на каждое `hello` (переподключение SSE) и **синхронизирует список целиком** —
  после рестарта сервера запросы умирают вместе с процессами агентов, и старые записи стали бы фантомами.
  Вместе с ожиданием едет шапка чата — `chatTitle` и `taskId`. Окну она не нужна (у него
  свой стор), а **внешнему потребителю взять её неоткуда**: телеграм-пульт показывал
  безымянное «чат, вопрос агента», и вопрос вроде «что именно выпиливаем?» оставался без
  ответа. Читается точечно `ChatHistoryStore.peek(chatKey)` с кэшем 30 секунд: `readOne`
  для этого не годится — он поднимает с диска всю историю, а этот путь зовёт каждое окно
  на каждый `hello`.
- Во фронте висящие спросы — карта `chat.pending` (pid → `{kind: 'perm'|'question', chatKey, …}`),
  а не два одиночных поля: агенты работают в нескольких чатах, и новый спрос не должен затирать
  чужой. Компонент берёт свой через `permFor(chatKey)` / `questionFor(chatKey)`.
