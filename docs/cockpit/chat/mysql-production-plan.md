# TDD-план: чаты на MySQL и подготовка к продакшну

## Описание для человека

Мы переделываем хранение и загрузку чатов, чтобы ими можно было надёжно пользоваться
каждый день. При открытии сразу появятся список разговоров и последние сообщения.
Старая переписка будет загружаться небольшими порциями в фоне и при прокрутке вверх.
Позиция чтения сохранится, а длинная история не будет постепенно занимать всю память
браузера. Ответы агента продолжат появляться по мере написания.

Переписку будет сохранять сервер в MySQL. Закрытое окно или временный разрыв связи
не должны терять уже принятый вопрос и сохранённый ответ. Повтор отправки не должен
запускать агента второй раз. Сохраняются архив, поиск по старой переписке, вложения,
уточнения работающему агенту, выбор модели и папки, вопросы и разрешения.

Переход выполняется один раз вручную: остановить запись, сделать резервную копию,
перенести историю, проверить её и запустить новую версию. В этой версии уже удалены
старое файловое хранилище, прежние API и ветки совместимости чата. Отдельный архив
инструмента переноса проверяется заранее. Резервная копия истории и файлы вложений
при этом не уничтожаются.

Готовность к продакшну проверяется тестами с настоящим MySQL, измерением скорости
на большой искусственной истории, проверками обрывов и восстановлением из backup.
Это план для нынешней установки с одним владельцем и одним сервером; создание
многопользовательского сервиса не входит в эту работу.

Ниже — задания для менее сильной модели. Каждое изменение начинается с теста,
который показывает конкретную проблему; затем вносится минимальное исправление
и выполняется проверка. Рабочую миграцию и перезапуск проводит человек.

## Условия задачи

Уточнения заказчика:

- Продукт ещё не используется другими людьми. Допустима разовая **ручная миграция
  с остановкой**, без одновременной работы старого и нового хранилищ.
- Нужен результат, пригодный для продакшна, включая восстановление после сбоев,
  проверку производительности и эксплуатацию.
- Legacy нужно удалить целиком из действующего чата. Перенос JSON в одну колонку
  MySQL и сохранение прежнего клиентского протокола задачу не решают.

## Как выполнять этот план

1. Полностью прочитать корневые `AGENTS.md`, `CLAUDE.md`, существующий `CLAUDE.local.md`
   и оглавления затрагиваемых областей. Не читать рабочую переписку ради разработки.
2. Выполнять карточки раздела 8 по указанным зависимостям. Одна карточка — один
   небольшой TDD-цикл; внутри неё добавлять сценарии по одному, не писать весь
   набор тестов и всю подсистему одновременно.
3. Существующие пути ниже проверены по рабочему дереву на дату исследования.
   **Предлагаемые** пути, таблицы, команды и API ещё требуется создать.
4. Перед удалением файла выполнить `rg` по его имени и экспортам, перенести
   действующих потребителей, затем удалить файл. Нельзя оставлять пустую обёртку
   над прежним протоколом ради зелёных тестов.
5. В дереве уже есть незакоммиченные изменения чатов и их ускорения. Они принадлежат
   человеку; не откатывать их и не восстанавливать файлы из HEAD поверх них.
6. После карточки записать в журнал исполнения: файлы, проверенный RED, команды
   GREEN, результат REFACTOR и ограничения. Галочка означает пройденный выходной
   критерий, а не наличие кода. Пока работа не выполнена, отметки остаются пустыми.
7. Сервер Cockpit из собственного чата не останавливать и не перезапускать.
   Рабочую остановку, перенос и запуск выполняет человек по подготовленной инструкции.
   Изолированные тестовые процессы исполнитель запускает и завершает сам.

### Обязательный цикл RED → GREEN → REFACTOR

1. **Подготовка:** прочитать контракт карточки и названные файлы, запустить соседние
   уже существующие проверки. Исходный посторонний отказ записать отдельно.
2. **RED:** добавить один поведенческий тест и запустить его до реализации.
   В отчёте указать ожидаемое и фактическое значение. Ошибка импорта, отсутствие
   БД, синтаксическая ошибка или падение чужого теста не считаются нужным RED.
   Для нового модуля допустим минимальный типизированный каркас, чтобы тест дошёл
   до assertion; логика до первого RED не реализуется.
   Если поведение уже реализовано предыдущей карточкой и новый regression-тест
   сразу зелёный, записать это честно и выбрать ещё отсутствующий сценарий.
   Не ломать рабочий код ради искусственного RED. Если вся карточка уже покрыта
   реализацией, закрыть её как проверку существующего поведения с командами и
   доказательствами, явно отметив отсутствие нового RED/изменения кода.
3. **GREEN:** внести минимальное изменение из карточки. Повторить тот же тест;
   затем добавить следующий граничный сценарий отдельным циклом.
4. **REFACTOR:** убрать дубли и уточнить имена только в затронутой области.
   Повторить группу карточки и её зависимости. Не менять ожидания ради зелёного
   результата, не подменять реальную SQL-границу Map-реализацией.
5. **Выход:** сохранить команды и exit codes, обновить журнал. Порог производительности
   и проверка миграции не подменяются unit-тестом, наличие текста функции — её поведением.

Формат записи журнала исполнения, который следует добавить при начале реализации:

| Карточка | RED: команда и осмысленный отказ | GREEN: команда/код | REFACTOR и регрессии | Файлы/ограничения |
| --- | --- | --- | --- | --- |
| — | Пока не выполнялось | — | — | — |

Шаблон задания следующему исполнителю:

> Выполни только карточку `<ID>` из этого плана. Прочитай её зависимости и нужные
> контракты. Сначала получи указанный RED, затем GREEN, затем REFACTOR. Не меняй
> соседние подсистемы, не оставляй старый runtime-путь и не запускай рабочую миграцию.
> Запиши результаты и следующий незавершённый ID. Если проверка доказывает дефект
> контракта, опиши контрпример; не придумывай молча новый протокол.

Инвентаризация, исследовательские замеры и ручное переключение помечены **GATE**:
это подготовка или приёмка, для них не требуется искусственно падающий unit-тест.

## 2. Зафиксированные архитектурные решения

### 2.1. Границы первой production-версии

- MySQL **8.4 LTS**, InnoDB, `utf8mb4`. Это выбранная база совместимости плана;
  точную установленную версию и патч проверить на этапе инфраструктуры.
- Один host-native процесс Cockpit и один исполнитель очереди каждого чата.
  Два экземпляра сервера с одной БД одновременно не поддерживаются этой версией.
  Production-запуск — один настроенный systemd unit с контролем дерева процессов.
  Dev/тесты используют отдельную БД. Автоматического переноса владения между
  серверами при потере соединения с MySQL нет.
- Авторизация остаётся существующей: один владелец Cockpit, общий guard на `/api`.
  Многопользовательский SaaS, tenant-изоляция и распределённые исполнители сюда не входят.
- MySQL хранит переписку, настройки чатов, durable-состояния ходов, уточнения,
  привязки сессий, индексы и журнал изменений. Файлы вложений остаются файлами;
  в MySQL хранятся их идентичность, размер, хеш и связи с сообщениями.
- Данные и session-файлы самих CLI-исполнителей сохраняют своего владельца.
  Они не становятся второй копией истории Cockpit.
- Никакого постоянного `storage=json|mysql`, dual write, автоматического импорта
  при старте и возврата к JSON при ошибке БД. Недоступная БД означает явный `503`.
- Список, история, шаги и тяжёлое содержимое — разные ограниченные запросы.
  Поток ответов агента — существующий общий SSE. Не заводить отдельный EventSource
  на чат и не передавать весь архив одним длинным SSE/NDJSON-ответом.

### 2.2. Кто чем владеет

| Данные | Владелец и способ изменения |
| --- | --- |
| Сообщения и окончательные ответы | Сервер, транзакционные команды |
| Порядок сообщений, revision, generation | Сервер; клиент не назначает значения |

| Ещё не подтверждённая отправка | Небольшой outbox в IndexedDB; неизменяемая команда с `turnId` |

`modelRef = { provider, model }` — единственная форма выбранной модели.
Старые строки `model`, dual-write поля и эвристики выбора исполнителя удалить.
Существующую проверку актуального каталога и реальных возможностей адаптера сохранить.

## 3. Модель данных и гарантии записи

### 3.1. Схема

Для идентификаторов использовать регистрозависимые ASCII-колонки, например
`VARCHAR(80) CHARACTER SET ascii COLLATE ascii_bin`. Проверить длины всех существующих
типов идентификаторов до DDL; более длинные внутренние ключи хранить отдельно.
Счётчики — `BIGINT UNSIGNED`; наружу передавать десятичными строками, без потери
точности JavaScript. Время — UTC `DATETIME(3)`, наружу согласованный ISO-формат.
Неизвестные исторические timestamps остаются `NULL`, время миграции их не заменяет.

Минимальная схема, которую нужно оформить миграциями:

| `chat_search_documents` | PK(source_id, revision), неизменяемый lowercase-текст этой версии, text_bytes; одновременно возможны опубликованная и строящаяся версии |
| `chat_search_grams` | Postings по source_id/revision из раздела 4.2; весь индекс производный и восстанавливаемый |
| `chat_search_jobs` | source_id PK, wanted_revision, chat_id/generation, state, checkpoint, attempts; одна коалесцируемая работа на источник |

`chat_messages` — единая запись ответа, включая завершённый блок внутри хода.
Не создавать вторую полную таблицу текстов `assistant_messages` с последующим
перекладыванием в историю. `chat_in_turn` содержит receipt доставки, а не ещё одну
копию пользовательской реплики. Отдельной таблицы «pending для записи браузером» нет.

JSON допустим для ограниченных метаданных конкретной сущности. Массивы всей переписки,
всех шагов, всех ходов или всех чатов в одной JSON-колонке запрещены.
Тяжёлый текст сообщения не выбирается в запросах карточек и bootstrap.

Индексы обязательны как минимум для:

- активного списка: `(archived, deleted_at, activity_at DESC, id DESC)`;
- архива: `(archived, deleted_at, archived_at DESC, id DESC)`;
- истории: `(chat_id, generation, seq)`; страниц шагов: `(run_id, seq)`;
- состояния незавершённых ходов и переходов, а не сканирования всех сообщений при старте;
- связей вложений, удаления старых поколений и очистки журнала по небольшим партиям.

Названия, типы FK и collation должны совпадать. Удаление большого чата не выполнять
одним огромным каскадом в пользовательском запросе: сначала tombstone, затем
повторяемая фоновая уборка ограниченными транзакциями.

### 3.2. Последовательности и транзакции

1. `seq` сообщения назначается один раз под `SELECT ... FOR UPDATE` строки чата.
   Он задаёт порядок и не меняется при дописывании ответа. `created_at` для этого не годится.
   `next_message_seq` не сбрасывается при очистке: seq монотонен всю жизнь чата.
   Реплики и in-turn блоки одного запуска получают также общий runSequence под
   блокировкой строки run; использовать его для чередования уточнений и ответов.
2. `revision` сущности растёт при изменении; `generation` чата растёт при очистке.
   Поздний ответ страницы или события старого поколения отбрасывается.
3. Идемпотентность проверяется **до CAS**, чтобы повтор уже принятой команды после
   потерянного ответа вернул сохранённый результат. Тот же id с другим request_hash
   возвращает `409 idempotency_conflict`.
   Для новых команд установить пределы: пользовательский текст 64 KiB, draft
   64 KiB, UI-context 32 KiB, весь JSON admission 256 KiB; вложения передавать
   отдельным upload. Проверять лимиты до записи outbox и ещё раз на сервере.
   Исключение из порядка: сначала auth, проверка формата и совпадение databaseEpoch;
   команда старой БД не может стать новой записью из-за отсутствующего receipt.
4. Приём сообщения одной транзакцией сохраняет user-реплику, команду хода,
   карточку и событие изменения. Только после COMMIT вернуть `202` и разрешить запуск.
5. Финал одной транзакцией сохраняет/завершает assistant-реплику, outcome хода,
   usage/session/seed-состояние, карточку и события. Только после COMMIT показывать
   durable-завершение. Закрытый браузер никак не влияет на сохранение.
6. Все ветки — ошибка, stop, отказ команды после приёма, compact, фоновая активность,
   уточнение и переход папки — используют тот же принцип устойчивого результата.
7. Процесс исполнителя не запускается внутри SQL-транзакции. Нельзя держать
   соединение/row lock, пока модель думает, человек отвечает или идёт HTTP-запрос.
8. При deadlock повторяется короткая транзакция с тем же id, максимум три раза
   с jitter. Внешнее действие и запуск модели внутри этого повтора запрещены.
9. Ошибка/обрыв COMMIT имеет неопределённый результат: сверить receipt по тому же id.
   Не делать вторую отправку с новым id и не обещать, что первая точно не принята.

Блокировки InnoDB должны применяться внутри явных транзакций; `SKIP LOCKED` не
подходит для чтения пользовательской истории. Основание:
[MySQL: locking reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html).

Гарантия — идемпотентный приём и сохранённый результат. «Ровно одно внешнее действие
при любом падении» не обещается: после неизвестного исхода запуска его нельзя
автоматически повторять.

До реализации определить и тестировать единый механический контракт:

- `databaseEpoch` входит в каждую изменяющую команду и её persisted outbox.
  Несовпадение возвращает `409 database_epoch_changed` до любых записей/запусков.
- Request hash — SHA-256 канонического JSON валидированной команды: рекурсивно
  отсортированные ключи объектов, порядок массивов сохранён, без undefined и NaN,
  UTF-8. Исключается только сам requestHash; текст, epoch, версии, модель и workspace
  входят. Никакого trim/нормализации текста и подстановки новых настроек при retry.
- Для duplicate выполняющийся запрос ждёт исход первой транзакции в пределах
  общего дедлайна. После её COMMIT получает тот же результат с duplicate=true;
  по таймауту — retryable 503, клиент сверяет тот же id. Unique constraint обязателен:
  проверка «сначала SELECT, потом INSERT» без него недостаточна.
- `admission_seq` берётся из `chats.next_admission_seq` под lock. Все доменные
  транзакции берут locks в одном порядке: owner FOR SHARE → chat FOR UPDATE → run
  → дочерние сущности/receipts → sync singleton. Под первым lock сверить state/epoch,
  удерживать его до COMMIT; смена owner берёт FOR UPDATE той же строки. Отдельный
  давний SELECT epoch не защищает поздний callback. Долгие внешние операции
  за пределами транзакции; разные чаты совместно держат shared owner lock.
- Новое сообщение: source_key строится из типа и turnId/messageId/assistantMessageId.
  Hash role/text не является идентичностью. Вся команда, включая отказ после её
  durable-приёма, имеет один устойчивый результат; до приёма CAS-отказ — отдельный исход.
- После удаления чата id и hash принятого хода остаются в `chat_turn_tombstones`.
  Повтор не воссоздаёт чат и не запускает модель. Сначала перенос tombstones,
  затем пакетная очистка текстов и журналов; тест проверяет перезапуск между партиями.

### 3.3. Состояния и восстановление

- Ход: `accepted → running → completed | failed | stopped | interrupted`.
  `accepted` означает очередь после durable-приёма; пустая очередь не равна running.
- При старте найти незаконченные ходы индексом. Ходы предыдущего владельца
  завершить как `interrupted` с объяснением. Модель сама повторно не запускается;
  явное «Продолжить» создаёт новую команду.
- Сохранять идемпотентные id ходов весь срок жизни чата. После удаления чата
  допустим компактный tombstone без текста: старый outbox не должен запустить ход заново.
  Не наследовать прежнее удаление turnId через неделю.
- Runtime состоит из одного supervisor и его server/CLI-процессов. Предлагаемый
  `bin/chat-runtime-guard` удерживает OS flock отдельного `chat-runtime.lock`
  (не `orch.lock`), передаёт сигналы координатору shutdown и не отпускает lock до
  завершения дерева. В production он запускается только в одном настроенном unit;
  существующий `KillMode=mixed` проверяется тестом остановки/аварии guard.
  Обычный lock родительского PID без контроля потомков недостаточен.
- `GET_LOCK` на отдельном соединении — дополнительный gate БД. Его потеря переводит
  чат в `recovery_required`, запрещает приём/запуски и начинает остановку своего
  дерева. Свободный DB-lock сам по себе **не разрешает** новому процессу takeover:
  сначала supervisor/оператор подтверждает завершение прежнего cgroup/guard.
  При SIGSTOP, orphan CLI или неопределённости новый owner не назначается.
- Новый owner_epoch выдаётся после этого барьера; SQL-писатели старого epoch
  отвергаются атомарно. Это защита записей, а не способ остановить внешний инструмент.
  Выполненные внешние действия и уже отправленные запросы не откатываются.
  После неоднозначного аварийного исхода требуется ручное восстановление;
  авто-retry ходов запрещён. Во всех entrypoints prod DB запрещён обход guard;
  fake runtime в тестах работает только с выделенной тестовой БД.
- Имя advisory lock привязать к БД установки. Он принадлежит соединению и
  не освобождается COMMIT; соединение не возвращается в пул
  ([MySQL: GET_LOCK](https://dev.mysql.com/doc/refman/8.4/en/locking-functions.html)).
- Во время отказа БД не подтверждать новые команды. Для работающего хода буфер
  записи ограничен; при исчерпании лимита приостановить/остановить исполнитель
  и показать ошибку сохранения. Не писать аварийный JSON и не расти в памяти бесконечно.
- Текст незавершённого блока сохранять контрольными порциями: не реже раза в секунду
  при изменениях или после 64 KiB новых данных; перед complete/stop — обязательный flush.
  После аварийного завершения незаписанный хвост может отсутствовать, блок остаётся
  явно незавершённым. Уже подтверждённые сообщения теряться не должны.
- Шаги сохранять ограниченными пачками, например 50 шагов или 250 мс; финал ждёт flush.
  Сохранение новых шагов не перечитывает старые. Окно живых шагов ограничено отдельно
  от долговременной истории; вытеснение из памяти не удаляет записи из MySQL.

Для команд использовать schema validation с `additionalProperties: false`.

### 4.1. Курсоры сообщений

Первый запрос latest (без cursor/around) фиксирует `upperSeq` текущего поколения.
Generation, upperSeq, descriptors, их тексты и snapshotCursor читаются **одной
короткой read-only REPEATABLE READ транзакцией на одном соединении**. Между её
SELECT нельзя коммитить или брать другую connection из pool. Транзакция заканчивается
до отправки HTTP и не живёт между страницами. Это согласованный снимок одного
ответа; механизм описан в [MySQL: consistent reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html).
Если clear/редактирование произошли во время чтения, ответ целиком отражает прежний
снимок; новое generation/revision из синхронизации затем его вытесняет.
На странице — элементы в хронологическом порядке, счётчик оставшихся записей не нужен:

```json
{
  "chatId": "synthetic-chat",
  "generation": "1",
  "items": [{"id": "message-9000", "seq": "9000", "revision": "1", "role": "assistant", "text": "Ответ", "complete": true}],
  "olderCursor": "opaque-token",
  "newerCursor": null,
  "hasMoreOlder": true,
  "upperSeq": "9000",
  "snapshotCursor": "12000"
}
```

Форма курсора: версия, тип, chatId/runId, generation, upperSeq, beforeSeq/afterSeq,
фильтры, databaseEpoch и направление. Кодировать base64url, строго валидировать длину и поля; курсор не даёт прав
на чужую сущность и не подставляется в SQL. Для списка — полный составной ключ
сортировки и фильтр archived. Для поиска — также отпечаток запроса.

Запрос предыдущей страницы имеет следующую форму; значения передаются параметрами:

```sql
SELECT id, seq, revision, role, kind, run_id, text_bytes, complete
FROM chat_messages
WHERE chat_id = ? AND generation = ?
  AND seq <= ? AND seq < ?
ORDER BY seq DESC
LIMIT ?;
```

На первой странице условие `seq < beforeSeq` отсутствует. Выбрать `limit + 1`,
определить `hasMoreOlder`, вернуть выбранное в обратном порядке. Тексты получить
только для выбранных id и только в пределах бюджета ответа. Курсор строить по
**фактически возвращённой** границе. Не использовать OFFSET и не вычислять
`COUNT(*)` всей истории на каждом листании.

Размеры по умолчанию: 40 сообщений, максимум 100, максимум 512 KiB несжатого JSON.
Текст до 16 KiB допустим inline; более крупное сообщение получает preview,
`contentComplete: false`, `textBytes`, revision и ссылку на порционную загрузку.
Если страница упирается в байтовый бюджет, завершить её раньше. Даже единственное
очень большое сообщение должно дать маленький descriptor и продвижение курсора.
Полный текст хранится без молчаливого обрезания. Порция content — до 64 KiB по
корректным границам UTF-8; изменение revision требует начать чтение этого текста заново.
Preview и порции выбирать ограниченной SQL-проекцией, а не читать LONGTEXT целиком
в Node и затем делать slice. Сначала text_bytes/descriptors, затем один пакетный
запрос нужных небольших текстов; не создавать N+1 на каждую реплику.

Страницы шагов: 50 записей, максимум 100 и 256 KiB. Большой результат инструмента
получает descriptor по такому же правилу; полный исходный UTF-8 payload сохраняется
в `chat_step_content` и читается через отдельный step/content маршрут. Признаки
формата и bytes/revision находятся в descriptor; JSON не парсится целиком ради
preview. Исторические steps не входят в bootstrap,
карточки, сообщения и обычное live-событие.

Новые сообщения с `seq > upperSeq` приходят отдельным live-хвостом.
Дописанный старый блок обновляется по id/revision; его не обнаружить условием
`seq > lastSeq`, поэтому журнал изменений обязателен.

`upperSeq` ограничивает **конкретный проход назад**, а не все будущие чтения чата.
Latest всегда захватывает новую верхнюю границу. Для движения вперёд первый cursor
содержит afterSeq и текущую generation; сервер фиксирует свежий upperSeq и выбирает
`afterSeq < seq <= upperSeq ORDER BY seq ASC LIMIT limit+1`. Последующие forward
страницы держат эту границу, до её достижения. Из around возвращаются оба cursor.

Кеш хранит ограниченные загруженные интервалы [minSeq, maxSeq], их края и явные
разрывы. Между оставшимися страницами после LRU нет утверждения «всё загружено».
Возврат к низу получает свежий latest; движение в разрыв использует forward/older.
SSE может сообщить о seq=10000, но не заменяет вытесненные HTTP-страницы 9001–9999.
Нельзя удерживать все id выгруженных сообщений: достаточно краёв оставшихся окон.

`snapshotCursor` страницы — лишь нижняя граница актуальности её сущностей.
Он **никогда не присваивается глобальному appliedCursor**: между ними могут быть
изменения других чатов. AppliedCursor двигает только непрерывно применённый changes.

### 4.2. Курсоры списка и поиск

Карточка содержит title, preview до 240 символов, draftPreview, archived,
modelRef, activityAt/archivedAt, unread/waiting и состояние запуска. Список имеет
стабильный дополнительный ключ `id`; одинаковое время не создаёт пропуски.
Детерминированный ORDER BY с уникальным дополнительным полем необходим при LIMIT:
[MySQL: LIMIT optimization](https://dev.mysql.com/doc/refman/8.4/en/limit-optimization.html).

Сортировка активных: activity_at DESC, id DESC; архива: archived_at DESC, id DESC.
Требующие вмешательства показываются из отдельной лёгкой проекции состояния.
Черновик и каждый токен ответа не переставляют карточку: activity_at меняется
при принятой реплике и завершённом блоке/ходе.

Ключ сортировки списка изменяемый. Не обещать снимок всего списка между HTTP-запросами:
до первой страницы сохранить syncCursor; все изменения карточек после него получать
через changes, включая ранее не загруженные id. Переместившаяся вверх карточка приходит
как upsert, удалённая/архивированная — как изменение членства. Дедупликация по id.
При истёкшем syncCursor сбросить курсоры списка и загрузить первую страницу заново.
Тест обязан переместить ещё не загруженный чат через границу страницы и не потерять его.

Поиск не ограничивается кешем страниц. Сохранить нынешний смысл поиска подстроки
без учёта регистра в заголовках и тексте сообщений, включая кириллицу, короткие
запросы и архив. Нельзя просто заменить его на `FULLTEXT` и считать поведение прежним:
токенизация, пробелы и stopwords имеют отдельные правила
([MySQL: ngram parser](https://dev.mysql.com/doc/refman/8.4/en/fulltext-search-ngram.html)).

Для сохранения подстрок ниже задан **кандидат** производного индекса. До основного
переноса он обязан пройти ранний GATE G1 на настоящем MySQL. Его производительность
и размер пока не подтверждены; нельзя считать таблицы грамм принятым решением
только потому, что они перечислены в схеме. Слабая модель сначала воспроизводит
измерение и сохраняет результат, а не строит весь поиск на недоказанном допущении.

1. `chat_search_sources` хранит уникальную связь с исходной сущностью и указатель
   publishedRevision. `chat_search_documents` имеет PK(sourceId, revision) и
   **неизменяемый lowercase-текст именно этой версии**, textBytes. Снимок source
   копируется атомарно с проверкой wantedRevision/generation; чтение исходного
   изменяемого LONGTEXT партиями без фиксации версии запрещено. Worker далее читает
   свой неизменяемый снимок порциями. Новая версия не заменяет текст опубликованной.
2. `chat_search_grams`: уникальные последовательности из 1, 2 и 3 Unicode-символов
   документа; поиск по `(gram_length, gram, source_id, revision)`, обратный индекс
   `(source_id, revision)`. У каждой версии собственный staging-набор.
   Двоичное сравнение после общего lowercase; пробелы/знаки не выбрасывать.
3. Для запроса брать граммы длины `min(3, длина запроса)`, получать кандидатов
   пересечением и проверять фактическое вхождение подстроки. Индекс кандидатов
   сам по себе не доказывает совпадение.
4. Выдавать уникальные chatId с найденным messageId и коротким сниппетом;
   постраничная выборка не читает полные тексты всех чатов в память Node.
   Курсор включает ключ последней карточки и отпечаток запроса.
5. Индексировать заголовки, user и **завершённые** assistant-блоки. Checkpoint/дельта
   незавершённого блока задания не создают. Одна строка jobs на sourceId с последней
   wantedRevision; в момент завершения source и задание пишутся одной транзакцией.
   Так растущий ответ не переиндексируется целиком каждую секунду.
6. Worker читает неизменяемую revision, создаёт staging партиями до 1000 postings
   и 256 KiB, затем атомарно переключает publishedRevision лишь если source ещё
   актуален; проверка и переключение указателя защищены теми же chat/source locks.
   Старые задания/поколения не публикуются. Query соединяет source, document и grams
   по одной publishedRevision: текст, проверка подстроки и postings переключаются
   вместе. Удалённые/очищенные источники сразу исключаются по текущему generation/
   tombstone, даже если index cleanup отстаёт. Старые документы/postings убираются
   партиями. Незавершённый live-текст пока не входит в поиск; отставание завершённых
   данных обозначается indexing/pending. После импорта индекс должен догнаться полностью.
7. G1 проверяет точные подстроки, короткие частые/редкие/отсутствующие запросы,
   время rebuild, память и размер **всех** таблиц/индексов. Если кандидат не проходит,
   не начинать зависящие от него DDL/worker/search карточки: зафиксировать контрпример
   и пересмотреть именно этот раздел. Изменение семантики поиска или ослабление
   порогов нельзя маскировать зелёным тестом. Остальные независимые карточки доступны.

## 5. Живой поток и восстановление связи

### 5.1. Durable-события и курсор

Существующий `/api/events` остаётся единственным SSE-соединением вкладки.
Добавить события `chat-change` и `chat-live` в серверную шину и `EVENT_NAMES`.
Остальные подсистемы Cockpit используют шину как прежде.

- `chat-change` сообщает durable-изменение, cursor, entityId, revision и generation.
  Payload небольшой: карточка/receipt/descriptor, без истории и больших текстов.
- `chat-live` содержит временный текстовый фрагмент или прогресс с runId,
  messageId и точной базой фрагмента. Он может повторяться/теряться; завершённая история
  восстанавливается из MySQL.
- Произвольный SSE-пакет не считается ACK сохранения. В интерфейсе различать
  неподтверждённый живой хвост и сохранённый блок.

Для текстовой дельты обязательны databaseEpoch/generation, messageId, runId,
baseRevision, baseTextBytes, streamEpoch, deltaSeq, fromByte, toByte и text.
Один event содержит не более 8 KiB текста, границы соответствуют UTF-8. Клиент
добавляет фрагмент только к точной базе, ожидаемым deltaSeq и fromByte.
Повтор игнорируется, старый streamEpoch не применяется. При gap/base mismatch
склейка прекращается, хвост помечается «синхронизация»; читается текущий durable
checkpoint и принимаются только совместимые с ним фрагменты. Пропавший ещё не
сохранённый текст восстановится следующим checkpoint/финалом, выдумывать его нельзя.

После COMMIT checkpoint сервер начинает новый streamEpoch с новой baseRevision;
descriptor checkpoint содержит их и сохранённую длину. Опередивший descriptor
live-пакет допускается лишь в ограниченный буфер, а не в видимый текст.
На complete незавершённый хвост заменяется каноническим содержимым той же revision.

`chat-change` с descriptor загруженного сообщения вызывает coalesced hydration
через by-id (до 40 id за запрос, один запрос на чат в полёте). После ответа снова
проверить revision/generation; незагруженную старую страницу лишь инвалидировать.
Не превращать reconnect со 100 изменениями в 100 одновременных fetch.

**Не использовать один AUTO_INCREMENT как доказательство порядка COMMIT.**
Транзакция с меньшим id может завершиться позднее, и catch-up пропустит её.
Для этой одиночной установки выбрать простой алгоритм:

1. В конце каждой короткой изменяющей транзакции, после блокировок сущностей,
   заблокировать singleton `chat_sync_state` через FOR UPDATE.
2. Выделить следующие seq, вставить `chat_changes`, обновить committed_seq.
3. Немедленно COMMIT. После взятия sync-lock не читать/блокировать другие сущности
   и не вызывать внешние сервисы. Все писатели соблюдают этот порядок.
4. Пока транзакция держит lock, следующая не выдаёт более высокий видимый cursor.
   Ограничить размер пакета; проверить contention нагрузочным тестом.
5. Один publisher читает только committed changes и рассылает их по порядку.
   Сбой после COMMIT до broadcast безопасен: changes уже доступны catch-up.

`chat_changes` одновременно служит transactional outbox для шины и журналом
восстановления. Доставка как минимум один раз; клиент применяет сущность только
при более новой revision и допустимом generation. Own-origin не даёт права
пропустить серверное подтверждение. Cursor двигается лишь после применения
непрерывной последовательности изменений; обнаруженный разрыв запускает catch-up.

### 5.2. Первая загрузка и reconnect без гонки

1. Подписаться на общую SSE-шину, буферизовать относящиеся к чатам события.
2. Получить bootstrap с committed syncCursor и databaseEpoch.
3. Запустить параллельно первую страницу карточек и последнюю страницу выбранного
   чата. Выбор из URL/настроек устройства проверять точечным GET, он может быть архивным.
4. Показать полученную страницу сразу. Не ждать старую историю и каталоги чужих чатов.
5. Выполнить catch-up от bootstrap cursor. Первый ответ фиксирует `until` текущего
   прохода; последующие страницы используют его, чтобы постоянный поток не делал
   восстановление бесконечным. Затем разобрать буфер с дедупликацией.
6. Ответ страницы не вправе откатить уже полученную новую revision. Для незагруженного
   сообщения достаточно инвалидировать соответствующую страницу; не тянуть весь чат.
7. После reconnect догнать changes, сверить незаконченные отправки по turnId,
   активные ходы и вопросы. Повтор всей истории не делать.

Гонка незагруженной строки требует отдельного механизма. До отправки HTTP записать
in-flight scope (чат/поколение/окно либо фильтр списка) и его dirtyCursor. Каждое
применённое change, способное затронуть этот scope, повышает dirtyCursor, даже если
строки ещё нет в кеше. Ответ с snapshotCursor < dirtyCursor или старым generation
не сливать: инвалидировать и повторно прочитать это окно. Новый согласованный
ответ должен покрывать dirtyCursor; очистка сразу отменяет старые запросы.
Для scope, границы которого пока неизвестны, консервативно учитывать все изменения
его чата/списка. Хранить watermark только для ограниченного числа кешированных/
in-flight окон, а не историю revisions всех когда-либо увиденных id. Changes для
незагруженного scope без запросов не требуют загрузки: будущий fresh snapshot их учтёт.
List/by-id/read-ответы также содержат cursor своего согласованного снимка. Проверить:
строки в кеше нет → change rev2 применён → запоздал page rev1; rev1 не появляется.

Клиентский буфер во время catch-up также ограничен: максимум 1000 descriptors
или 1 MiB. При переполнении отбросить буфер и догнать БД от последнего **применённого**
cursor; нельзя продвинуть его до последнего лишь полученного SSE. Страница changes
ограничена 100 записями и 256 KiB, cursor строится по реально выданным событиям.

Хранить changes 7 дней как начальную настройку. После истечения —
`410 sync_cursor_expired`: сбросить **только серверные кеши** и курсоры, повторить
маленький bootstrap, карточки и страницу открытого чата. Outbox и локальный
неотправленный черновик сохраняются. Не выдавать пустую успешную страницу изменений.

Cursor хранить в памяти рядом с кешем. На F5, когда кеш отсутствует, брать новый
bootstrap; нельзя подставить старый cursor к пустому состоянию и пропустить историю.
После восстановления БД из backup сменить databaseEpoch, чтобы все клиенты
сбросили несовместимые курсоры. Epoch неизменно хранится в outbox, поэтому сравнение
работает и после F5. Команды прежнего epoch автоматически не переотправляются:
сначала read-only сверка turnId/hash; неизвестный исход переводится в recovery_required
и показывается человеку. Явная новая отправка возможна как новая команда после
этого объяснения. Подменять epoch старой команды при загрузке запрещено.

### 5.3. Ограничение нагрузки

- Склеивать текстовые дельты одного блока за 30–50 мс; не перерисовывать каждую
  букву. Статусы, вопросы и permissions не ждать за большой очередью текста.
- Ограничить буфер медленного SSE-клиента: исходно 1 MiB или 5 секунд без drain.
  При превышении закрыть только это соединение; reconnect восстановит durable-данные
  и текущие вопросы. Не накапливать бесконечные `res.write`.
- Не открывать дополнительные потоки при выборе другого чата. Проверить две вкладки
  по HTTP/1.1: отправка, стоп и вопрос должны отвечать при работающих агентах.
- Потеря эфемерного token/progress-события не препятствует получению финала.
  Нельзя забыть обновить внутреннего подписчика Telegram при замене chat-событий.

## 6. Поведение браузера

### 6.1. Страницы и фоновая подгрузка

Начальные значения лимитов сделать именованными константами, проверяемыми тестами:

| Параметр | Начальное значение |
| --- | --- |
| Первая страница карточек | 50, максимум 100 |
| Первая страница сообщений | Последние 40, максимум 100 |
| Упреждающая загрузка | Одна предыдущая страница после первого рендера; максимум две впереди чтения |
| Параллельные фоновые запросы истории | Один на вкладку |
| Кеш сообщений открытого чата | До 5 страниц и 8 MiB текста, с сохранением видимого окна |
| Кеш неактивных чатов | LRU: до 3 чатов и общий лимит 16 MiB |
| DOM ленты | Видимая область + overscan; ориентир до 120 строк |
| Живой текстовый хвост | Ограниченный буфер отдельно от исторических страниц |

Подгрузка не означает «после открытия скачать весь архив в фоне». Первый рендер
зависит только от маленькой страницы. Затем фоновый запрос подготавливает ближайшую
историю, а приближение к верхнему краю запускает следующую. Список чатов также
имеет нижний sentinel и постраничную выдачу.

- `IntersectionObserver` наблюдает верхний sentinel контейнера ленты с запасом
  примерно одного экрана. Один cursor не загружается двумя запросами одновременно.
- `AbortController` и request generation отменяют/отсекают ответы прежнего sid,
  поиска и поколения истории. Поздний ответ чата A не появляется в чате B.
- При скрытой вкладке, offline, `saveData` или активной отправке упреждающий fetch
  приостанавливается. Явное чтение пользователя имеет приоритет.
- Ошибка старой страницы не скрывает уже показанные сообщения. Над лентой остаётся
  компактное «Не удалось загрузить историю — повторить».
- `hasMoreOlder=false` прекращает запросы. Пустая история — конечное состояние,
  а не бесконечный skeleton.
- При вытеснении страницы хранить границы для повторного чтения в обе стороны.
  Live-хвост и незавершённая отправка не теряются при LRU-очистке.

### 6.2. Прокрутка и рендер

Перед prepend запомнить id первой видимой строки и её offset относительно viewport.
После добавления страницы восстановить тот же id/offset. Корректировать изменение
высоты через ResizeObserver, включая картинки, Markdown и раскрытие steps.
Одного `scrollTop += newScrollHeight - oldScrollHeight` для этого недостаточно.

Виртуализировать строки переменной высоты: стабильный messageId/stepId вместо индекса
массива, измеряемые высоты, верхний/нижний spacer, overscan. Старые группы хронологии
строить только по загруженному окну. Если страница разрезает ход, group/run metadata
должны позволять показать продолжение без загрузки всех сообщений запуска.

Сохранить правило [автопрокрутки](auto-scroll.md): новые ответы ведут вниз только
когда человек уже внизу; своя отправка возвращает к хвосту. При чтении старого
показывать кнопку «Новые сообщения», не менять scrollTop. Prepend не должен
срабатывать как «новый ответ» в существующем watch длины массива.

Шаги старого хода загружать при раскрытии, следующими страницами — при прокрутке
самого блока. Большие ответы явно раскрывать порциями; preview не выдавать за
полный текст. Не парсить Markdown выгруженных страниц и не пересчитывать прошлые
ответы от счётчика токенов. При необходимости тяжёлый разбор переносится в worker,
но его необходимость подтверждается профилем, а не заменяет ограничение объёма.

### 6.3. Outbox, черновики, несколько окон

- Перед отправкой записать в IndexedDB неизменяемую команду: turnId, chatId,
  databaseEpoch, generation, текст, attachment ids, выбранные параметры, workspaceKey,
  UI-context и request hash. После F5 повторяется эта команда, а не заново
  собранный запрос из изменившихся селектов.
  Если локальную запись не удалось завершить, сохранить текст в композере и
  показать ошибку подготовки отправки; не начинать POST с ложной гарантией outbox.
- На 202 отметить приём, показать серверную user-реплику; затем удалить outbox
  после устойчивого завершения локальной транзакции. Повтор после сбоя удаления
  безопасен благодаря turnId. При неизвестном исходе сначала запросить статус.
- Retry: 1/2/4/8/15 секунд с jitter, ограниченное число автоматических попыток;
  явный 4xx не повторять вслепую. «Не доставлено» сохраняет текст и действие повтора.
- Черновик сохранять отдельно с debounce 400 мс и собственной revision.
  При конфликте другого окна локальный несохранённый текст не затирать: показать
  конфликт и предложить выбор. Очистка черновика при send условная по revision:
  поздний save не возвращает отправленный текст и не стирает новый набор.
- Непрочитанность определяется отдельным notificationSeq, а не неизменяемым seq
  сообщения. Новый завершённый видимый assistant-блок/ошибка увеличивает его
  в той же транзакции; содержательное завершённое дополнение того же messageId
  также создаёт новое уведомление. Checkpoint/токены и повтор того же финала — нет.
  При показе завершённого содержимого окно подтверждает максимум действительно
  увиденных notificationSeq; user-реплика и открытие старой страницы из поиска
  не продвигают этот watermark. Прочитанный partial → уход → complete того же id
  должен снова дать unread. Очистка чата атомарно снимает старую непрочитанность.
- Локальная ошибка сети не становится общей assistant/error-репликой. Общие
  ошибки исполнения записывает сервер, транспортные ошибки принадлежат вкладке.

## 7. Сохранить действующие продуктовые контракты

Перед изменением прочитать связанные документы из [оглавления чатов](README.md).
Следующие сценарии являются требованиями, а не совместимостью со старым хранилищем:

- Архив открывается без восстановления; новая отправка атомарно возвращает чат
  из архива. Недоступная модель не удаляет переписку и выбор модели.
- Повтор turnId не запускает второй ход; очередь одного чата сохраняет порядок
  принятия. Приём во время остановки сервера отклоняется явно.
- In-turn сохраняет состояния принятия/передачи/неопределённого исхода. Непереданный
  текст виден человеку, но не становится инструкцией следующей модели.
- История для следующего запуска читается сервером. Нельзя передать исполнителю
  только последние 40 сообщений, потому что столько загрузил UI. Если адаптеру
  нужна текстовая проекция, читать её страницами до его явного бюджета контекста;
  существующие resume/seed/compaction правила сохраняются.
- Вопросы и разрешения после reconnect видны снова; ответ другого окна снимает
  карточку. Они привязаны к точным chatId/runId и текущему владельцу запуска.
- Binding и память не меняются из PATCH. Смена папки использует существующий журнал
  preparing/ready/resetting/done, CAS и блокировку с очередью; они переносятся в БД.
- Очистка видимой истории и сброс памяти исполнителя — разные операции.
  `/clear` увеличивает generation и очищает ленту; `/reset` сбрасывает session/seed.
  Если slash-команда требует оба эффекта, оркестрировать их явно и идемпотентно.
  Во время активного/принятого хода и перехода возвращать busy, не оставлять гонку.
- Compact, генерация названия, фоновый ход живой сессии, stop, отказ и сбой CLI
  должны получать устойчивый результат даже при закрытом окне.
- UI-context остаётся недоверенными данными. Ни workspace, ни MCP, ни permissions,
  ни session identity из текста страницы не выводятся.
- Сохранить загрузку/выдачу вложений с авторизацией, лимитами и проверкой принадлежности.
  Не удалять файлы, на которые ещё есть ссылки; сироты убираются с grace period.

Отдельный production-блокер уже описан в
[ошибке stdin при запуске Claude](claude-startup-pipe-error.md): EPIPE не должен
ронять сервер. Перед объявлением готовности воспроизвести его изолированным fake CLI,
исправить жизненный цикл ошибки и проверить сохранение итога/освобождение очереди.

## 8. Карточки выполнения по TDD

Все карточки пока **не выполнены**. Порядок ниже является рекомендуемым; зависимости
обязательны. Обозначения `UNIT`, `MYSQL`, `BROWSER` и `PERF` раскрыты в §10.3 в точные
команды. Указанные новые test-файлы и модули — задания на создание, не существующие

Каждая карточка считается закрытой только после её собственных проверок и ближайших
затронутых регрессий. Переходить к dependent-карточке при красной зависимости нельзя.
Отсутствие MySQL, браузера или systemd-стенда означает «не проверено», а не GREEN.

**REFACTOR/выход:** fault-тесты зелёные; инструкция содержит точные backup/restore/
rebuild команды, права, пороги и реакции. Само восстановление и RPO/RTO проверяет G3,
наличие текста инструкции не является доказательством recoverability.

### Приёмка и ручное переключение

#### G3 — GATE: чистый кандидат, реальные отказы и скорость

**После:** T01–T41, G1, G2; журнал содержит все выполненные циклы.

- Выполнить §10.2 и точные команды §10.3 на кандидате **после удаления** Legacy.
- Пройти production-browser и §10.1 на фиксированной синтетике; записать
  cold/warm p50/p95, bytes, EXPLAIN, RSS/heap, DOM, event-loop и худшие результаты.
- Проверить самостоятельный архив G2, restore backup+attachments в отдельную БД,
  смену epoch, старый persisted outbox после F5, измерить RPO/RTO §11.
- Зафиксировать checksum/версию единственного готового release artifact и схему,
  добавить человеческую инструкцию G4. Не менять код во время рабочего переноса.
- Подготовить безопасный способ экспорта браузерных черновиков/неподтверждённых
  отправок **до закрытия** каждого старого окна; включить его в cutover checklist.

**Выход:** результаты, а не обещания. Любой провал бюджета/матрицы — незакрытый
блокер; рабочую остановку не начинать. Readability/types/offline/MySQL/browser
проверены раздельно. Новая рабочая сборка — только после зелёных проверок.

#### G4 — GATE: ручной перенос и окончательная приёмка человеком

**После:** G3. Исполнитель готовит команды с конкретными путями/версиями и результатами
репетиции. Рабочий сервер из текущего агентского чата не останавливает.

1. Человек прекращает новые действия во всех браузерах/устройствах и пульте.
   **До закрытия окон**: дождаться подтверждённого сохранения доступных изменений,
   экспортировать локальные черновики, снимки и неподтверждённые отправки.
   Неизвестную отправку сверить по id; не превращать её автоматически в новый ход.
   Записать, какие устройства проверены; недоступное устройство — открытый пункт.
2. Завершить или явно остановить активные ходы, закрыть окна/пульт и остановить

   сохранить прежнюю сборку/конфигурацию. Импортировать только замороженный backup.
3. Применить схему проверенного нового релиза в пустую выделенную БД. Архивом G2

4. Сверить manifest: каждый чат, порядок/count/hash сообщений и steps, полные тексты,

5. Запустить **тот же** чистый release artifact из G3 с новой конфигурацией.

   там есть пользовательские данные и вложения. Никакой Legacy-код сейчас не дописывается.
6. Обновить PWA/web. Проверить старую вкладку: запрещённые запросы не дают ложного
   успеха и не восстанавливают её snapshot поверх БД. Новые окна показывают импорт.
7. Smoke: список/архив, глубокая история/поиск, вложение, отправка/уточнение,

   Автотест Telegram остаётся на fake Bot API; реальные действия пульта — вручную.
8. Сделать первый согласованный MySQL+attachments backup и выполнить restore

**Откат:** до первой новой записи можно вернуть прежнюю сборку и frozen backup.
После новых записей откат на старые файлы теряет данные: остановить запись, сохранить
текущую БД/вложения и восстановить новый стек либо выполнить отдельно проверенный
обратный экспорт. Автоматического JSON-fallback не существует.

## 10. Проверки и измеримые критерии приёмки

### 10.1. Наборы и условия измерений

Использовать одинаковый стенд до/после: production web, настоящий API, MySQL 8.4
на локальном SSD; зафиксировать CPU/RAM/версии и конкурентную нагрузку. Для UI отдельно
профиль сети 100 мс RTT / 10 Mbit/s и CPU slowdown ×4, если браузер это поддерживает.
Сделать не менее 30 измерений загрузки, отдельно cold/warm, p50/p95 и размер ответа.
Числа ниже — **цели**, не утверждение о выполненных измерениях.

| Сценарий | Условие готовности |
| --- | --- |
| Bootstrap и первые 50 карточек | API p95 ≤ 150 мс на стенде; нет messages/steps, совокупно ≤ 128 KiB JSON |
| Последние 40 сообщений | API p95 ≤ 200 мс; тело ≤ 512 KiB; не зависит линейно от всего размера чата |
| Глубокая страница 100 000-сообщенийного чата | p95 ≤ 200 мс и не более 2× первой страницы, подтверждённый index range scan |
| Холодное открытие выбранного чата | Видимый полезный хвост ≤ 1,5 с p95 в указанном сетевом профиле |
| Переключение на кешированный чат | ≤ 100 мс p95 до видимого содержимого |
| Приём обычной небольшой команды | ≤ 200 мс p95 до durable 202 при 10 параллельных чатах; время модели не входит |
| Доставка сохранённого блока | До видимости ≤ 250 мс p95 без учёта генерации модели |
| Набор и live-обновление | p95 обработчик + рендер < 50 мс; повторное обновление не обходит всю историю |
| Фоновый prepend | Якорь сохраняется в пределах 2 px после стабилизации layout; нет прыжка к хвосту |
| 20 минут листания и потока | Кеши остаются в заданных лимитах; DOM ограничен; память выходит на плато |
| Поиск в большой истории | Первый результат/страница ≤ 500 мс p95 после готовности индекса; незагруженные сообщения находятся |
| Медленный SSE-клиент | Буфер ограничен, остальные окна/stop/permission не блокируются |
| Увеличение числа сообщений в 10 раз | Размер первой выдачи, работа ввода и объём сохранения не увеличиваются в 10 раз |

На больших ответах отдельно измерять загрузку content и разбор Markdown.
Не улучшать метрики уменьшением набора, выключением durable flush, пропуском steps
или исключением медленных прогонов из отчёта. Провал бюджета — открытый блокер,
который разбирается по SQL, сети и профилю браузера.

### 10.2. Обязательная матрица отказов

| Сбой/гонка | Что проверить |
| --- | --- |
| Обрыв POST до/после COMMIT и потерянный 202 | Один turnId, одна user-реплика, не больше одного запуска |
| Падение после COMMIT до SSE | Финал виден через catch-up без помощи старого окна |
| Падение во время финализации | Есть завершённая транзакция либо честный interrupted, нет ложного complete |
| БД недоступна/диск заполнен/pool exhausted | Нет ACK до сохранения, ограниченная память, понятный 503/ошибка |
| Deadlock и неопределённый COMMIT | Повтор транзакции безопасен, внешний эффект не повторяется |
| Два окна редактируют/читают/отправляют | CAS, монотонный read state, draft не затирается, финал не дублируется |
| Queue + in-turn + stop + workdir/reset | Порядок и запреты busy сохраняются, нет обхода binding/seed |
| F5/сон вкладки/retention/restore БД | Catch-up или ограниченный bootstrap; outbox не теряется |
| Очистка/удаление при запросах страниц | Старое generation не воскресает; tombstone не создаёт новый чат |
| Очень большой текст/steps/вложения | Лимиты всех ответов и памяти, полное содержимое доступно по явному действию |
| XSS/SQL injection/поддельные поля | Markdown проходит существующую безопасную обработку; параметры SQL; запрет server-owned PATCH и чужих вложений |
| Неверный CLI/PATH/EPIPE/ранний exit | Сервер жив, очередь завершена, ошибка хода сохранена |
| Второй сервер и потеря runtime-lock | Нет двух исполнений, старые callback не пишут поверх нового владельца |
| Старый PWA/frontend | Не может записать полный snapshot или незаметно включить старый send |

### 10.3. Команды и организация тестов

**Новый SQL-стенд создаётся в T02.** `tests/run-chat-mysql.sh` получает отдельные
`COCKPIT_CHAT_TEST_MYSQL_*`, создаёт уникальную БД с безопасным тестовым prefix,
проверяет ownership созданной БД и удаляет только её. Не принимать production DSN.
Отсутствие MySQL, неверная версия/схема или невозможность очистки — ошибка прогона,
а не skip. Runtime user отдельно от пользователя DDL. Тесты каждого suite изолированы;
данные и fault injection одной проверки не протекают в другую.

`tests/mysql/helpers/chatMysqlFixture.js` поднимает настоящий Fastify/chatService/
repositories и реальные соединения. Для внешнего исполнения извлечь управляемый fake
из существующего `tests/server/helpers/chat-turns.js` (`controlledExecutor`), а не
вызывать Claude/Codex/других агентов. DB-конкурентность проверяют разные соединения,
падения — отдельные процессы, а не перестановка результатов Map. В T03–T06 можно
подготовить тестовую owner-строку без запуска процессов; T07 отдельно доказывает
production-barrier. Границу транзакции/COMMIT допускается остановить тестовым barrier,
которого нет в production-конфигурации.

Добавить `tests/mysql/**/*` в `server/tsconfig.tests.json`. Новые product-модули —
TypeScript по правилам проекта; расширение теста само по себе не доказывает типизацию.
Существующие DB-зависимые `chat-turn-accept`, `chat-turn-delivery-store`,
`chat-in-turn-*`, `chat-workdir-transition`, `chat-session-binding`,
`chat-shutdown-drain`, `chat-delivery-failure*`, `chat-concurrent-sends` перенести
в SQL-набор вместе с полезными assertions. Чистые contract/projector/adapter/UI-тесты
оставить offline. **Не сохранять старый файловый backend ради offline run-all.**

Общий `tests/run-all.sh` остаётся offline. SQL и настоящий браузер — самостоятельные
обязательные release gates. UI unit может мокать API; такой тест не доказывает durable
запись. Новый `chatStoreFixture.js` передаёт зависимости или собирает реальный TS-store,
не развивает regexp-подмену логики старого `tests/web/helpers/chat-store.js`.

Команды карточек — сокращения **в тексте плана**, не уже установленные shell aliases:

| Сокращение | Точная форма команды после создания стенда |
| --- | --- |
| `UNIT <file>` | `NODE_TEST_MAX_RSS_MB=4096 bash tests/run-node-tests-safe.sh --test --test-concurrency=2 <file>` |
| `MYSQL <file>` | `NODE_TEST_MAX_RSS_MB=4096 bash tests/run-chat-mysql.sh <file>` |
| `BROWSER <scenario>` | `NODE_TEST_MAX_RSS_MB=4096 bash tests/run-chat-browser.sh --scenario <scenario>` |
| `PERF` | `NODE_TEST_MAX_RSS_MB=4096 bash tests/run-chat-browser.sh --performance --repeats 30` |

Контракт нового `run-chat-mysql.sh`: без аргументов — все `tests/mysql/*.test.js`;
с путями — только указанные; `--test-name-pattern=...` перед путём фильтрует Node-тесты.
Внутри всегда используется `run-node-tests-safe.sh --test --test-concurrency=2`,
внешние flags корректно передаются массивом, exit code не скрывается. Ограничение
test concurrency не мешает одному тесту открыть несколько соединений для гонки.
Подготовку БД/cleanup и весь сценарий ограничить дедлайнами.

Пример одного TDD-цикла после создания файла:

```bash
NODE_TEST_MAX_RSS_MB=4096 bash tests/run-chat-mysql.sh --test-name-pattern=lost-ack tests/mysql/chat-admission.test.js
NODE_TEST_MAX_RSS_MB=4096 bash tests/run-chat-mysql.sh tests/mysql/chat-admission.test.js
```

Первую команду запустить до GREEN и сохранить ожидаемый assertion failure,
вторую — после GREEN/REFACTOR. Ошибка «нет БД/модуля» не является нужным отказом.
Назвать соответствующий тест с `lost-ack` в заголовке. Для других карточек аналогично
использовать их файл и имя сценария. Не гонять весь run-all после каждого assertion.

**Браузерный стенд создаётся перед первым RED в T28.** Новый `tests/run-chat-browser.sh`
строит production-mode fixture в `.state/artifacts/chat-mysql/`, использует существующий
Playwright, запускает изолированный API/реальную тестовую БД через общий harness T02.
Рабочий `web/dist` и production port не трогает. Сценарии `outbox`,
`history-scroll`, `lazy-content`, `search` — явный выбор; неизвестное имя — ошибка.
Выбранные реальные store/components проходят тот же код, что продукт; внешние
executor/Bot API — fake. До T37 допускается отдельная fixture-страница реальных
модулей, G3 дополнительно проверяет полный собранный UI без подмен business logic.

Функциональные браузерные сценарии идут через сторож памяти и имеют assertions.
Для `--performance` использовать измерители существующего
`web/scripts/check-chat-performance.mjs`, но перенести его с ChatHistoryStore/stubs
на новый store и реальный SQL API в T37. Сохранять версии, hashes, размеры набора
и JSON-отчёт. Production-сборка стенда, наличие Chrome и готовность API —
предварительные условия; их отсутствие не выдаётся за RED поведения.

Перед G3 выполнить:

```bash
node web/scripts/check-code-readability.mjs --changed
npm --prefix server run typecheck
npm --prefix web run typecheck
bash tests/run-chat-mysql.sh
bash tests/run-all.sh
bash tests/run-chat-browser.sh --all
bash tests/run-chat-browser.sh --performance --repeats 30
npm --prefix web run build
```

`--all` — все перечисленные browser-сценарии; реализовать в runner, не трактовать
как неизвестный pass. Полный build продукта выполняется после зелёных тестов.
Долгий общий прогон запускать отсоединённо с логом и exit-code файлом в
`.state/artifacts/chat-mysql/`, чтобы он пережил остановку агента; затем проверить
exit code и отчёт. Не запускать второй run-all поверх чужого. Не считать запуск
команды без прочтения результата выполненной проверкой.

## 11. Эксплуатация после переключения

- Метрики: latency/error каждого chat endpoint; pool wait/in-use; transaction
  retries; event-loop lag; lag publisher/search; размер SSE-очередей; число
  accepted/running/interrupted; возраст старейшего незавершённого хода;
  время старта и восстановления. SQL-логи не содержат тексты и секреты.
- Readiness: БД доступна, схема совпала, runtime принадлежит этому серверу.
  Liveness не зависит от доступности внешней модели. Отказ БД не выглядит пустым чатом.
- Алерты: durable-write errors, затянувшееся восстановление/очередь, исчерпание пула,
  отставание changes/search, рост диска и неуспешный backup.
- Backup: согласованный MySQL-backup + файлы вложений + manifest хешей;
  конфигурация/ключи хранятся отдельно безопасным способом. Для начала ежедневный
  полный backup, binlog для восстановления до момента, хранение не менее 14 дней.
- Цели эксплуатации: RPO ≤ 15 минут, RTO ≤ 60 минут на зафиксированном стенде;
  достижимость доказать восстановлением. Сроки хранения и размер диска документировать.
- Retention changes и уборка сирот/старых поколений — маленькими партиями;
  сообщения действующих чатов автоматически по возрасту не удалять.
- Rebuild поиска и очистка служебных данных не блокируют горячие запросы и
  прерываются/продолжаются по checkpoint. Права на DDL не нужны обычному runtime.
- При backup/restore и смене databaseEpoch документировать поведение открытых
  вкладок и незавершённых отправок, не обещать безопасный replay неизвестных действий.

## 12. Когда работа действительно закончена

- [ ] Чаты и все их durable-журналы работают только через MySQL.
- [ ] История сохраняется при полностью закрытом браузере.
- [ ] Приём/финал имеют проверенные транзакционные и идемпотентные гарантии.
- [ ] Список, архив, история, поиск, steps и большие тексты имеют ограниченную выдачу.
- [ ] Первая страница показывается быстро; ближайшая история подгружается в фоне.
- [ ] Бесконечная прокрутка сохраняет позицию, не накапливает DOM и память без границ.
- [ ] Общий SSE восстанавливается без полной загрузки истории и без потери изменений.
- [ ] Telegram и остальные потребители переведены на единственный новый контракт.
- [ ] Legacy-матрица закрыта кодом и проверками, временный мигратор убран из продукта.
- [ ] Ручной импорт проверен counts/hash/семантическим экспортом, backup восстановлен.
- [ ] Закрыты EPIPE и другие воспроизведённые блокеры завершения хода.
- [ ] Пройдены offline-тесты, реальный MySQL, production-браузер и бюджеты скорости.
- [ ] Есть актуальные документы, метрики, инструкция запуска/восстановления и итоговый отчёт.

Замена файлов SQL-запросами, красивые skeleton или один успешный ручной send
сами по себе не означают завершения этого плана.
