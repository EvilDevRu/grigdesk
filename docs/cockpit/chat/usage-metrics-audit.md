# Аудит токенов и остатков лимитов

Проверка 17.10.2026: трассировка текущих адаптеров и UI, сопоставление с протоколами
исполнителей, воспроизведение на искусственных событиях. Расчёты приложения при аудите
не менялись. Частные переписки и состояние аккаунтов для проверки не использовались;
конкретный расход изображённого на скриншоте хода этим аудитом не установлен.

## Что означают числа

- Число рядом с секундомером — **выход текущего хода**: текст, рассуждения и вызовы
  инструментов в пределах того, что учитывает адаптер. Это не сумма входа и выхода,
  не размер контекста и не расход всей подписки. Подсказка находится в `ChatThinking.vue`.
- Проценты справа — **остаток квоты аккаунта**: `100 − bars[].pct`.
  `providerUsageSummary.ts` не переводит токены хода в процент подписки.
  Полосы во всплывашке исполнителя используют расход: при сравнении этих поверхностей
  нужно учитывать направление шкалы.
- Кольцо — последний размер контекста относительно практического порога:
  минимум поддерживаемого автосжатия и 80% окна модели. Поэтому его процент может
  отличаться от процента полного окна в консоли при одинаковом количестве токенов.

Условный остаток «94%» в строке означает 6% расхода соответствующего окна аккаунта.
Соседство с токенами одного чата не превращает аккаунтную квоту в квоту этого чата.

## Источники по исполнителям

| Исполнитель | Выход хода | Квота или баланс |
| --- | --- | --- |
| Claude | Во время работы: сумма `estimated_tokens_delta` из `system/thinking_tokens` плюс длина текста и JSON аргументов / 3. В конце оценку заменяет `result.usage.output_tokens` | `oauth/usage`, `limits[].percent`; запасной формат — поля `utilization` |
| Codex | Прирост `tokenUsage.total.outputTokens` относительно начала хода; рассуждения отдельно не прибавляются | `account/rateLimits/read`, окна с `usedPercent` |
| Kimi | Обработчик берёт `session.usage_updated.usage.output_tokens` напрямую; фактические метрики шагов установленного CLI пропускает, см. ниже | `/api/v1/oauth/usage` через отдельный процесс server; парсер ожидает `summary` и `limits` с `used/limit` |
| DeepSeek | Web-транспорт DSH суммирует `outputTokens` по обращениям; незаконченные обращения оценивает по символам | Денежный остаток `/user/balance` |
| GLM | Тот же счётчик web-транспорта DSH, что у DeepSeek | Обычный API: денежный баланс; Coding Plan: `limits[].percentage` кабинета Z.ai |

Tripo — специализированный адаптер, а не исполнитель обычного чата: его денежный
ресурс не участвует в счётчике вывода разговора.

Общий модуль `server/src/modules/providers/index.ts` читает квоты через `ex.usage()`.
Штатный TTL и период фонового опроса — пять минут; после ограничений частоты есть
дополнительная пауза. UI получает результат через `providers-usage`.
Токены текущего хода идут отдельным путём `onProgress → chat-progress`.

## Подтверждённые пробелы

### Живые квоты не подключены к общему снимку

Codex сообщает `account/rateLimits/updated`, но `consumeAppNotification` в `codex.ts`
его не обрабатывает. Адаптер использует только отдельное чтение по таймеру.
Официальный контракт подтверждает наличие обоих каналов:
[Codex App Server](https://learn.chatgpt.com/docs/app-server).

У Claude сборщик не обрабатывает `rate_limit_event`. Терминальная строка CLI также
получает `rate_limits` с долей расхода и временем сброса, но её JSON — отдельный
контракт, его нельзя объявлять уже присутствующим в stdout Cockpit:
[Claude status line](https://code.claude.com/docs/en/statusline).

Следствие: одинаковый аккаунт в консоли и Cockpit может показывать разные остатки
между опросами. Само это расхождение не доказывает ошибку вычитания процентов.

### Округление превращает ненулевой остаток в ноль

`parseClaudeUsagePayload`, `parseCodexRateLimits` и `parseKimiUsageBars` округляют
долю расхода до целого **до** передачи в UI. Воспроизведение для каждого адаптера:

```text
Исходный расход 99,6% → bars[].pct = 100 → остаток в чате «0%».
Прямой вызов remainingUsagePercent(99.6) → «<1%».
```

Таким образом, UI уже умеет сохранять малый остаток, но адаптеры теряют информацию
раньше. Случай подтверждён синтетическими ответами; частота дробных значений у
конкретного аккаунта этим не измерялась.

### Claude: оценка, неиспользованный поток и повторные события

`_claudeStream.ts` намеренно не складывает `assistant.message.usage.output_tokens`:
прежние проверки обнаружили в этих сообщениях снимок начала ответа. Вместо него
работает оценка по символам и дельтам размышлений. «≈» в UI честно обозначает эту
оценку; её точность для конкретного длинного хода неизвестна без сравнения с итогом.

Стандартные аргументы запуска не включают `--include-partial-messages`, а сборщик
не читает `stream_event`. Синтетический `message_delta` с `output_tokens: 120`
оставляет счётчик нулевым. CLI поддерживает включение частичных событий:
[программный запуск Claude](https://code.claude.com/docs/en/headless).
Суммирование точного usage по обращениям потребует проверки полного потока установленной
версии, границ сообщений и повторов; простая замена одного поля этого не обеспечивает.

Дополнительно воспроизведён дефект повторного учёта: `isReplay` исключён из
`madeProgress`, но не из накопления токенов. Повтор assistant-блока с явной отметкой
`isReplay: true` снова увеличивает `contentChars`. Это условный сценарий парсера;
его наличие в показанном пользователем ходе не установлено.

### Kimi: метрики приходят в событиях, которые адаптер пропускает

Схема и встроенный клиент CLI 0.33.0 подтверждают:

- `turn.step.completed.usage` содержит `inputOther`, `output`, `inputCacheRead`,
  `inputCacheCreation`; штатный клиент прибавляет выход каждого шага к своей сумме;
- `agent.status.updated` содержит `contextTokens` и `maxContextTokens`;
- клиент формирует из этих данных собственное событие `sessionUsageUpdated`.

В `server/src/lib/kimi/serverTurn.ts` ветка `turn.step.completed` только завершает
текст и возвращается, `agent.status.updated` не разбирается. Есть другая ветка
`session.usage_updated`, которая напрямую принимает `output_tokens`, без вычитания
базы сессии. Её наличие не заменяет обработку метрик фактического потока.

Воспроизведение через искусственный REST/WS-сервер: шаг с `output: 42` и статус
контекста `12345 / 262144` завершают ход успешно, но `onProgress` не вызывается ни разу.
Текущая тестовая фикстура с `event.session.usage_updated` этот пропуск не обнаруживает.

Итог server-хода также не возвращает измеренный контекст. Старое описание команд
`/status` и `/usage` относится к ACP-пути, тогда как адаптер запускает `transport: 'server'`.

Нельзя автоматически переносить новую сетевую документацию на установленную версию:
актуальная [документация Kimi Server API](https://www.kimi.com/code/docs/en/kimi-code-cli/reference/server-api.html)
описывает аккаунтные квоты как `quota.usages` / `usedRatio`, тогда как проверенный бинарь
ещё содержит `summary/limits`. Несовместимость с новым ответом — граница обновления,
а не доказанный отказ квот установленного CLI.

### DeepSeek и GLM: живой контекст не сохраняется в итоге

`deepseek/serverTurn.ts` передаёт в прогресс сумму
`inputTokens + cacheReadTokens + cacheWriteTokens` последнего обращения.
Расход вывода суммируется отдельно по обращениям; прежняя ошибка «последний запрос
вместо всего хода» в этом месте уже исправлена.

Однако `deepseek/webRuntime.ts` возвращает `contextTokens/contextWindow: undefined`
и `contextMetric: unavailable`; `glm/runtime.ts` тоже выставляет `unavailable`.
Сборщик server-хода не сохраняет последний размер в результате. Это разрыв между
живым замером и итоговыми данными для сохранения истории, а не неверная сумма выхода.

### GLM: отсутствие процента становится полным остатком

`glm/usage.ts`, функция `quotaBar`: `money(limit.percentage) ?? 0` превращает
отсутствующий или некорректный процент в нулевой расход. Синтетическое окно
`TOKENS_LIMIT` без `percentage` проходит как успешный ответ и показывает остаток
«100%». Отсутствие замера здесь не отделено от реально свободной квоты.

## Границы проверки

Аудит подтверждает поведение исходников и воспроизводимые случаи на искусственных
данных. Он не сравнивает одновременно открытый реальный чат с консолью и не даёт
точную погрешность числа на скриншоте. Утверждать, что весь отображённый расход
ошибочен, на этих данных нельзя.

Для численного сравнения нужны одинаковые границы: основной агент или все агенты,
запрос или ход или сессия, вход или выход, время замера и одно окно квоты.
Пересчёт всех исполнителей одной формулой эти различия скроет.
