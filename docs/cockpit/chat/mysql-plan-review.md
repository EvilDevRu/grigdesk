# Ревью плана перевода чатов на MySQL

Дата: 02.10.2026. Проверен [план реализации](mysql-production-plan.md), затем
доработанная версия независимо прочитана тем же критиком ещё раз.
Это проверка документа по исходникам и контрактам. Реализация, TDD-прогоны,
измерения MySQL и рабочая миграция в рамках этого ревью не выполнялись.

## Что исправлено

| Приоритет | Проблема исходного плана | Решение и проверка в плане |
| --- | --- | --- |
| P0 | После restore и F5 старый outbox мог повторить неизвестное внешнее действие | Epoch сохраняется в неизменяемой команде; сервер отвергает mismatch до записи; read-only сверка и явное recovery. T08, T28, G3 |
| P0 | Потеря GET_LOCK не останавливает старый живой CLI | Lifetime guard, один unit/cgroup, отказ takeover при неопределённости; SQL fencing защищает только записи. T07, T20 |
| P1 | «Реализация, затем тесты» вместо исполнимого TDD | 41 карточка с зависимостями, файлами, RED/GREEN/REFACTOR и командами; пять отдельных gates. Разделы 8 и 10.3 |
| P1 | Вытесненный live-хвост недоступен через старый upperSeq | Fresh latest, forward/around и явные ограниченные интервалы/пробелы. T24, T30 |
| P1 | Descriptor и текст страницы могли принадлежать разным снимкам | Короткая consistent-read транзакция; page snapshotCursor не продвигает глобальный appliedCursor. T23, T27 |
| P1 | Live-дельты могли склеиться с неверным основанием | Base revision/bytes, streamEpoch/sequence/offsets, gap recovery и пакетная hydration. T26, T27 |
| P1 | Завершение уже показанного partial не создавало unread | Отдельная notification sequence; чтение видимого завершённого содержимого. T12, T29 |
| P1 | Для тяжёлого tool payload не было полного устойчивого источника | Отдельный content, bounded chunks и проверка полного hash после restart. T13, T32 |
| P1 | Скорость/размер gram-индекса предполагались без проверки; checkpoint вызывал бы повторную индексацию | Ранний реальный G1, coalesced jobs только завершённых блоков, ограниченные staging batches. T33 |
| P1 | Удаление импортера зависело от переноса, а перенос — от удаления | Самостоятельный архив G2 → удаление T40 → проверка релиза G3 → ручной перенос G4 |
| P2 | Hash, duplicate wait, admission sequence и tombstones оставляли выбор исполнителю | Канонический hash, UNIQUE, дедлайн повторов, единый порядок locks, tombstones без каскадного удаления. T01, T04, T06, T08 |
| P2 | Закрытие старых окон предшествовало спасению локальных данных | Экспорт/подтверждение черновиков и неизвестных отправок на всех устройствах до закрытия. G3, G4 |

## Что добавило повторное ревью

- **P1: версии поискового текста.** Старые postings нельзя соединять с новым
  lowercase-текстом. Теперь documents имеют ключ sourceId/revision и неизменяемый
  текст; единый published pointer переключает текст и postings. T33 проверяет
  запрос во время переиндексации.
- **P1: первая загрузка ещё отсутствующей строки.** Одной проверки revision кеша
  недостаточно, когда строки там ещё нет. Bounded dirtyCursor in-flight scope
  запрещает принять старую страницу после уже применённого события. Этот случай
  стал отдельным RED в T27.
- **P2: существующее поведение.** Если новая regression-проверка сразу зелёная,
  исполнитель это фиксирует; искусственно ломать код ради RED запрещено.
- **P2: ложные поисковые кандидаты.** G1 явно включает длинные запросы, повторные
  граммы и пример `abcd` / `abcXbcd`, проверяющий точную фильтрацию после индекса.

Критик признал прежние P0 закрытыми на уровне контракта и не обнаружил других
P0/P1 при условии двух последних исправлений; оба включены в план. Зависимости
карточек и последовательность удаления Legacy больше не образуют цикла.

## Что ещё предстоит доказать реализацией

Начальные бюджеты скорости, пригодность поискового индекса, работа guard на реальном
systemd-стенде, восстановление БД и RPO/RTO остаются проверяемыми gates. Они не
объявлены достигнутыми. Все карточки плана пока не выполнены.

План начинается с описания результата для человека. Далее слабая модель получает
одну карточку за раз; журнал должен хранить реальные команды, осмысленный RED,
GREEN и регрессии. Наличие тестового файла или успешный запуск моков не закрывают
MySQL/browser-проверки и не дают основания запускать рабочую миграцию.
