# Ограничения повторного использования сохранённых шагов

Проверено по коду 01.10.2026 при критическом разборе
[плана устранения фризов](../web/chat-freeze-fix-plan.md). Ниже — ограничения исходного
кода до реализации протокола ссылок на шаги. Появившаяся реализация описана в
[контракте](history-step-reuse.md), состояние её проверок — в
[промежуточном отчёте](../web/chat-freeze-fix-results.md).

## Старый PUT не отклоняет неизвестное поле

`server/src/modules/chat/index.ts`, обработчик `PUT /api/chat/store/chat`, читает
только `chat`, `archived`, `origin`. Неизвестный `reuseSteps` не мешает записи.
В `mergeMessages` (`server/src/lib/chat/mergeChat.ts`) совпадающее начало без
серверного хвоста возвращает присланную историю, включая отсутствие `steps`.
Поэтому capability, прочитанный раньше, не защищает сокращённый PUT при откате
сервера. Нужен отдельный маршрут: неизвестный `/api/*` получает JSON 404 в
`server/src/plugins/static.ts`. Полный fallback должен брать полную копию снимка.

## Успешный ACK не подтверждает точную форму истории

`ChatHistoryStore.saveOne` в `server/src/lib/chat/historyStore.ts` вызывает
`protectCanonicalMessages` после `mergeChat`. Защита может добавить сообщение
или перекрыть его поля, в том числе steps, без изменения `restored`/`dropped`;
`stale` отражает только сравнение входной revision с базой. Нулевые флаги не
доказывают ни совпадение позиций, ни сохранение присланного массива шагов.

Подтверждения для refs нужно строить по итоговой сохранённой истории под тем же
lock. Их отсутствие означает отсутствие доказанной базы для оптимизации.
Общая revision также изменяется серверными `syncMessages` и `patchExecution`:
длительный сценарий должен проверять частоту конфликтов и восстановление refs.

## Отпечаток и снимок отправки имеют разные ограничения

В `web/src/stores/chat.js` `fingerprintOf` заменяет непустой массив steps его
длиной. Он не обнаруживает замену тела шага или массива той же длины. Инвалидация
кэша refs сама по себе не преодолеет early return в `_persist`/`_putChat`.
Dirty-проверке нужен отдельный дешёвый признак изменения исторических массивов.

`slimOf` сохраняет ссылку на `s.messages`, а `_putChat` считает отпечаток
подтверждения после await. `applyAssistantFinal` в `web/src/stores/chatInTurn.ts`
использует `Object.assign` для уже существующей реплики. Поэтому поверхностная
копия снимка может получить изменения, которых не было в отправленном JSON.
Отпечаток и подтверждения обязаны относиться к данным на момент отправки.

## Кэш проекции не должен удерживать старые объекты сообщений

`turnRows` в `web/src/views/chat/chatTimeline.ts` возвращает строки с `row.message`.
`_applyRemoteChat` может принять новый массив сообщений с прежними полями хронологии,
но другими вложениями, статусом доставки или метриками. Кэшировать можно разбиение
шагов; ссылки на сообщения и индексы нужно обновлять по текущей истории.

## Журнал API не измеряет сериализацию запроса

В `web/src/shared/apiClient.ts` `request` вызывает `JSON.stringify(body)` до
начала измерения попытки, используемого `api.slow`. Для проверки фризов нужен
замер вокруг самого вызова/сериализации и обработки события. Разбор запроса,
серверное слияние и полная сверка истории в стенде должны выполняться вне
главного потока страницы, иначе измеряется лишняя работа тестового приёмника.
