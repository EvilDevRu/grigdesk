# Снятие адаптера: каталог моделей, память и история

Сверено по исходникам 30.09.2026. Удаление файла исполнителя затрагивает три разных
границы: runtime-каталог, память выбранного ИИ и устойчивую историю Cockpit. Ниже
описаны текущее поведение и найденные ограничения; исправление снятия адаптера ещё
не реализовано.

## Сохранённый каталог не означает наличие исполнителя

`lib/executors/index.ts` собирает адаптеры из файлов и кэширует Map до конца процесса.
Удалённый файл перестаёт участвовать только в новом процессе. При этом
`lib/modelsRegistry.ts`, `getModelsRegistry()`, сейчас обходит все ключи сохранённого
каталога, даже когда соответствующего id уже нет в `getExecutors()`.

`ChatHistoryStore` получает именно этот runtime-реестр. Поэтому сохранённый список
снятого исполнителя может оставить старую пару `modelRef` в состоянии `resolved`.
Тест только с заранее очищенным объектом registry этого не обнаружит: нужен временный
файл каталога, настоящий путь его чтения и сохранённый schema-2 чат.

Отсутствие адаптера отличается от неудачного probe/auth. Модели временно недоступного
исполнителя сохраняют выбор — см. [контракт доступности](unavailable-executor-model-selection.md).
Данные каталога на диске и runtime-представление также имеют разные задачи: снятие
исполнителя само по себе не требует уничтожать сохранённые списки и метаданные.

## Перевыбор модели должен сбросить память прежнего ИИ

`ChatSession.vue`, `onModelChange()`, сейчас узнаёт прежнего provider только из
`current.value.provider`. Если адаптера нет в реестре, условие reset пропускается.
`stores/chat.js`, `setModel()`, меняет пару модели, но само не очищает `sessionId`.
В результате прежний идентификатор может попасть в запуск другого исполнителя.

Общий `resetContext()` уже умеет сначала подтвердить сброс сохранённого чата через
`POST /api/chat/session/reset`, а затем очистить локальную память. Он сохраняет
сообщения; при ошибке отмечает неудавшийся сброс. Проверка выбора модели снятого
исполнителя должна охватывать порядок вызовов, задержанный ответ и отказ, а не только
новый текст селекта. Старую пару можно восстановить из сохранённого `modelRef`.

Это не универсальная очистка sidecar снятых исполнителей: `resetWorkspaceMemory()`
инвалидирует binding лишь при объявленной capability `sessionBinding`. Если сам
адаптер отсутствует, очистку его осиротевшего sidecar нужно рассматривать отдельно.

## Вход исполнителя и запись истории — разные операции

В `modules/chat/index.ts`, `runChatTurn()`, до запуска исполнителя читаются pending,
а `history.syncMessages()` сохраняет проекцию `inTurnHistory` под lock файла чата.
Так уточнения, промежуточные ответы и итог предыдущего запуска попадают в историю
при закрытых окнах. Ошибка записи не позволяет запустить следующий executor.

Результат этой записи сейчас используется ещё и как `runArgs.chatHistory` для
stateless-исполнителя. Удаление такого входа не отменяет эффект сохранения:
`await history.syncMessages(...)` должен остаться перед запуском.

FLOW-15 и FLOW-17 в `tests/server/chat-in-turn-history.test.js` проверяют состав
истории и запрет запуска после ошибки записи. Пока успешную проекцию они наблюдают
через `options.chatHistory`. При снятии этого входа проверку следует перенести на
raw JSON временного chat-файла в момент входа следующего executor: чтение через store
или API способно само достроить проекцию и скрыть ошибку порядка.

Прежняя проблема без такого барьера сохранена как
[исторический разбор](queued-turn-history-gap.md). Действующий пользовательский
контракт описан в [уточнениях внутри хода](in-turn-messages.md).
