# MCP DeepSeek: изоляция стенда и границы проверки плана

Проверено по дереву 2026-10-01 при независимом ревью
[плана TDD](deepseek-mcp-tdd-plan.md). Это снимок предпосылок до реализации:
описанные ниже изменения включены в план. Реализация и результаты проверок
фиксируются в нём; итоговый контракт — [безопасный список MCP](deepseek-mcp-status.md).

## Подмена адаптеров не изолирует весь providers-модуль

В [providers-модуле](../../../server/src/modules/providers/index.ts)
`opts.getProviderAdapters` выбирается как `adaptersOf`. Общий реестр использует эту
зависимость, но MCP GET и `checkUpdates` вызывают настоящий `getProviderAdapters`.
Проверка обновлений запускается безусловным таймером через 30 секунд: медленный
route-тест может обратиться к живым CLI и сети даже без явного вызова этой функции.

Каталог моделей вызывается напрямую в трёх местах: `buildRegistry`, refresh общего
реестра и обновление CLI. Подмена только `buildRegistry` оставит refresh вне fixture.

В плане нужны `adaptersOf` в MCP GET и `checkUpdates`, а также единая зависимость
`modelsOf` во всех трёх вызовах каталога. По умолчанию они сохраняют настоящие
реализации. Обычный запуск, TTL и правила обновления не меняются.

Изоляцию MCP нужно доказать отдельным синтетическим id: в настоящем реестре его нет,
поэтому обход fixture сразу даст 404. Подмена настоящего DeepSeek сама по себе обход
не выявляет. Вызов `checkUpdates` можно проверить через существующий маршрут ручной
проверки версий, без тридцатисекундного ожидания. Обновление CLI стенд не запускает.

## Warnings не дают точного диагноза

[Reader проектных MCP](../../../server/src/lib/deepseek/projectMcp.ts)
складывает в один массив ошибки чтения, JSON, неподдерживаемых записей и команд.
`warnings.length > 0` не доказывает, что файл прочитан и виновата отдельная запись.
Публичные сообщения должны быть фиксированными и не приписывать конкретную причину.
Для проверки ошибки чтения подходит `.mcp.json` в виде каталога; запрет чтения через
`chmod 000` зависит от привилегий процесса и потому недостаточен.

Helper должен возвращать ошибку через поле `error` и перехватывать также ошибки
построения карточек: общий MCP-маршрут публикует message неперехваченного исключения.
В [SettingsView](../../../web/src/views/SettingsView.vue) ветка ошибки скрывает `note`,
поэтому само сообщение ошибки должно называть папку кокпита.

Публичное имя сервера сохраняется. Запрет вывода команд, args, env и warnings
не означает скрытие секрета, который владелец сам поместил в имя. Имя выводится
обычной текстовой интерполяцией, без интерпретации HTML.

## DOM-стенд не проверяет геометрию

[Компилятор component-тестов](../../../tests/web/helpers/compile-vue.js)
собирает Node-модуль с `file:`-импортами и не обрабатывает `<style>` SFC.
[Helper страницы настроек](../../../tests/web/helpers/settings-view.js)
по умолчанию заменяет нативную панель пустой заглушкой. Такой прогон проверяет
текст и взаимодействие, но не CSS, overflow или соседство настоящих панелей.

Визуальная проверка требует отдельного браузерного entry с Vue-плагином Vite,
настоящими CSS, UI и нативной панелью. API, stores и SSE получают синтетические данные;
стенд не обращается к рабочему Cockpit. Общая галерея проверки UI тоже не заменяет
монтирование настоящей SettingsView.

## Что исправлено в плане

- Разрешены точечные изменения границ зависимостей и добавлены тесты их использования.
- Заданы полная форма ошибки, нейтральные тексты и проверки I/O-отказов.
- Разведены DOM-проверка и браузерная проверка с настоящими стилями.
- Сохранено существующее объединение слоёв, включая отсутствие tombstone для выключенной записи.
- Убрана несуществующая просьба пользователя отменить общий прогон: при реализации
  действует требование `CLAUDE.md` запускать `tests/run-all.sh` после адресных проверок.

Завершение ревью плана не закрывает пункты реализации и не доказывает работоспособность
ещё не написанного helper. Результаты исполнения фиксируются отдельно в самом плане.
