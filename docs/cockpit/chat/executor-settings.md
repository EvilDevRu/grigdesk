# Свои настройки исполнителя объявляет сам executor

Здесь `executor` означает адаптер Cockpit. Декларации `settings[]` содержат вручную
выбранные локальные ручки Cockpit. Отдельная capability `nativeSettings` обнаруживает
схему CLI для динамического блока «Дополнительные настройки»:
[форма, API, область действия и проверенные транспорты](executor-native-settings.md).
Полнота каталога зависит от источника и видна в карточке; значения конфига сами по
себе не являются схемой.

- **Свои настройки исполнителя объявляет сам executor** — поле `settings`:
  `[{ id, kind, label, hint?, value, disabled?, note?, confirm? }]`. Схема приходит от исполнителя,
  выбор человека лежит в prefs (`providerSettings`), склейка — `lib/providerSettings.ts`;
  сохранение — `POST /api/providers/:id/settings` (`{ settingId, value }`). Ядро про смысл
  ключа не знает: принимает ТОЛЬКО объявленный id и приводит значение к типу `kind`, поэтому
  чужой ключ в prefs не попадёт. Фронт рисует по `kind` (`stores/providers.saveSetting`,
  оптимистично с откатом).

- Нативный блок загружается только для открытой карточки через отдельный GET
  `settings/catalog`. POST `settings/overrides` записывает один `set/unset` с ревизиями;
  контейнер `nativeSettings` зарезервирован и закрыт старому writer. Сохранённый выбор
  действует в объявленной каталогом области: у DeepSeek общие поля — в чатах и
  новых узлах конвейера, у остальных провайдеров — в чатах. «Сбросить»
  удаляет override; busy-ход продолжает работу со своим снимком. Успешная запись
  не означает применения настройки моделью.

- Настройки находятся в раскрываемой панели исполнителя и занимают высоту по
  содержимому. Фиксированные 220 px больше не нужны: одновременно открыт один
  исполнитель. Своего tabindex у тела нет, клавиатура проходит по самим ручкам.
  Раскладка описана в [контракте гармошки](../web/executor-settings-accordion.md).
