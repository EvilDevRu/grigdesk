# Кольцо контекста, prompt cache и сжатие

Продуктовый контракт измерения, свежести и шкалы кольца: `docs/cockpit/guide/chat-context.md`.

- **Кольцо показывает запас рабочего контекста, а не цену хода.** Размер контекста и
  переиспользование prompt cache связаны только наблюдаемым поведением конкретного запроса:
  большой контекст может почти целиком читаться из кэша, а маленький — переписаться после
  изменения префикса. Поэтому у кольца нет тарифной отсечки, а формулировка «ход уже
  подорожал» по одному `contextTokens` запрещена. Историческое наблюдение около 250k и его
  ограничения записаны в [граблях](live-context-usage.md).
- **Кэш показывается отдельным фактическим блоком** из `contextCache`: доля чтения и
  сообщённые `readTokens`/`writeTokens`/`uncachedTokens` относятся только к последнему
  model request. `unavailable` означает, что исполнитель не отдал телеметрию;
  `not-applicable` — что для него эта метрика не имеет такого смысла. Предупреждать о
  перезаписи можно только по реально пришедшему `writeTokens`, не по размеру контекста и
  не по id provider-а.
- **Собственный автокомпакт CLI привязан к доле окна модели.** Замер по сессиям, где компакт
  реально сработал: окно 200k → сжатие на ~166k, окно 1M → ~959–999k. Отдельная настройка
  кокпита позволяет раньше ограничить рабочий контекст ради управляемого размера и задержки;
  это не тарифная граница и не обещание cache miss.
- **Настройка «Запуски → Сжимать контекст чата при N токенах»** (prefs `chatAutoCompactWindow`,
  дефолт 200 000) кладёт порог туда, где он нужен. Claude получает его переменной
  `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, Codex — config override
  `model_auto_compact_token_limit=N` в thread config каждого `thread/start`/`thread/resume`.
  Читается перед каждым ходом — правка действует сразу, без рестарта. `0` — не вмешиваться,
  у CLI остаётся собственный порог.
- **У ЭТАПОВ конвейера порог свой** — соседняя настройка и отдельный ключ prefs
  (`stageAutoCompactWindow`): границы рабочего контекста те же, а цена сжатия разная. В чате
  оно рвёт нить разговора с человеком, на этапе — просто ужимает рабочий контекст между вызовами
  инструментов, и трогать его можно смелее. Путь тоже другой: не переменная процесса CLI,
  а `FACTORY_STAGE_AUTO_COMPACT` в запуск движка, дальше `RUNNER_AUTO_COMPACT_WINDOW`
  раннеру — см. `docs/engine/ENGINE.md`. Применяется к новым ЗАХОДАМ, идущий этап
  доработает как есть.
- **Собственный автокомпакт CLI виден в ленте шагом note** с причиной и размером до сжатия.
  На `compact_boundary` старый замер инвалидируется: `contextMetric: unavailable`, без
  процента и предупреждающей дуги. Ближайшее основное обращение возвращает измерение.
  `compactedAt` остаётся признаком ручного сжатия, а не штатного автокомпакта.
- **Снимок передаётся целиком**: `contextTokens`, `contextWindow`, `contextMetric`,
  `contextIsEstimate`. Он проходит `onProgress`, SSE, `/api/chat/active`, остановку
  и восстановление страницы. В браузере это runtime `liveContextUsage`; событие только
  с расходом вывода не стирает снимок, измеренный ноль не заменяется прошлым числом.
  Сохранённая цифра во время следующего хода подписана «прошлый ход, ждём замер».
- **Источники всех четырёх исполнителей проверяются отдельно.** Codex публикует
  `thread/tokenUsage/updated` сразу; Claude не берёт cumulative `result.usage` и
  замеры субагентов; DeepSeek сообщает ACP `usage_update.used` во время хода;
  Kimi измеряет локальными `/status` и `/usage` после хода.
  `unavailable`, `legacy-unavailable` и неподтверждённое окно не дают точного процента.
- **Дуга, цвет и процент используют одну границу**:
  `min(применимое автосжатие, 80% окна)`; жёлтая зона начинается на 80% этой шкалы.
  Ноль настройки означает «не вмешиваться». Поддержку настройки объявляет адаптер
  через `autoCompactEnv` или `chatAutoCompact: true`, каталог отдаёт
  `capabilities.chatAutoCompact`. Claude и Codex применяют настройку; Kimi и DeepSeek
  её не применяют, поэтому их шкала — 80% окна, без обещания автоматического сжатия.
  Полный чат и Telegram-пульт следуют одному правилу. Окно модели остаётся
  справочной строкой; цена и prompt cache в шкалу не входят.
  Сторож — `tests/web/chat-task-tooltip.component.test.js`.
- **SVG кольца не должен наследовать text clipping кнопки.** `UiIconButton` оборачивает slot
  во внутренний label с `overflow: hidden`, полезным для текста, но режущим составную SVG-иконку.
  Контекстный skin задаёт label точную коробку 22×22 px и `overflow: visible`; менять только
  размер самого `<svg>` недостаточно.
- **Клик по кольцу — СЖАТИЕ** (с подтверждением), **Alt+клик — сброс памяти агента**, он же
  `/reset`. Раньше клик делал только второе, причём молча: переписка на экране остаётся (история
  кокпита к сессии CLI не привязана), поэтому «ничего не произошло» — и сброс легко было принять
  за сжатие. Теперь у каждого действия свой вопрос, а результат виден плашкой `role: 'note'`.
  Для Kimi локального `sessionId = null` недостаточно: стор сначала вызывает
  `POST /api/chat/session/reset`, сервер вращает sidecar в пустую generation, и до подтверждения
  reset отправка заморожена. Ошибка reset сохраняет прежнюю session и требует явного повтора.
- **Как устроено сжатие** — `POST /api/chat/compact` и `/api/tasks/:id/compact`, тот же
  `runChat` и та же очередь чата (сжатие — полноценный ход агента, а два CLI на одну сессию
  не живут). План берётся у исполнителя, поле `compaction`:
  - `{ kind: 'native', message: '/compact' }` — CLI понимает слэш-команду и в режиме
    `-p --resume`: в сессии появляются `compact_boundary`/
    `isCompactSummary`, id разговора не меняется. **Грабля:** stdout такого хода ПУСТОЙ (вывод
    команды локальный, в поток не идёт), поэтому текст для ленты подставляет сервер, а повтор
    «пустого хода» для сжатия отключён — иначе второй прогон сжал бы уже сжатое.
  - `{ kind: 'summary' }` (codex и любой новый исполнитель по умолчанию) — родного компакта нет,
    сервер заказывает рабочую выжимку текстом (`SUMMARY_PROMPT`: задача, решения и их причины,
    файлы с путями, что сделано и что осталось). Клиент кладёт её в `pendingSeed`, обнуляет
    `sessionId`, и выжимка уезжает первым блоком СЛЕДУЮЩЕГО сообщения. `pendingSeed` живёт в
    файле истории — иначе F5 превратил бы сжатие в потерю памяти; при провале отправки семя
    возвращается в ожидание. **Сервер при этом гасит живую сессию и отдаёт `sessionId: null`:**
    пустой id следующего хода пул живых сессий считает «окно ещё не знает id» и поднял бы
    прежний thread с полным контекстом под выжимку — сжатия бы не было (грабли 14.09.2026).
    Итог сжатия, доехавший через `pending`, клиент применяет тем же `applyCompactResult`, а
    восстановленный из `pending` вопрос показывает без блока выжимки.
- **Пока сжатие идёт, чат заморожен, кроме поля ввода** (`frozen` в `ChatSession.vue`): селекты
  задачи/модели/режима, слайдер усилия, «На конвейер» и отправка выключены — ход уже в полёте,
  менять ему модель или задачу поздно, а второй ход на ту же сессию её убьёт. Текстовое поле,
  вложения и диктовка живые: следующее сообщение готовится, пока агент пересказывает разговор.
  Признак работы один — кольцо крутится (у сжатия нет ленты шагов), поэтому на это время дуга
  становится коротким бегунком: полное кольцо при вращении выглядело бы неподвижным.
- **Идёт ли сжатие — знает сервер, а не окно.** Флаг `compact` лежит в `activeRuns`, уезжает
  в `GET /api/chat/active` и в SSE `chat-turn-start`, а окна ставят по нему `compacting`. Раньше
  признак жил ТОЛЬКО в затеявшем окне: на компьютере кольцо крутилось, а планшет, открытый на том
  же чате, не показывал ничего — ни кольца, ни «думает…». Догнать состояние было нечем: у родного
  компакта stdout пуст всегда, значит ни `chat-progress`, ни `chat-step` по нему не идёт, и
  одноразовый `chat-turn-start`, пропущенный в офлайне, был единственным шансом. Отсюда же сверка
  `_loadActive()` — при загрузке и на каждое `hello` (переподключение SSE, рестарт сервера):
  сверяемся ПОЛНОСТЬЮ, как со спросами, иначе после рестарта кольцо крутилось бы вечно. Не трогаем
  только то, по чему из этого окна висит свой незакрытый запрос (`compactInflight`) — его разморозит
  собственный ответ. «Думает…» во время сжатия не показываем нигде: индикатор один — кольцо.
- **Сжатие останавливается кнопкой «стоп»**, как обычный ход (это тот же процесс CLI в `activeRuns`).
  Оборванный ход возвращается обычным ответом с `stopped: true`, и `compact()` обязан его отличать:
  для Claude/Codex контекст остался прежним, а общий путь обнулил бы счётчик и написал
  «контекст сжат». Kimi после `session/cancel` сохраняет ACP binding/session id, а следующий
  явный ход делает `session/resume`. Binding сбрасывается только как страховка, если resumed
  prompt завершился пустым post-prompt ходом; автоматического повтора такого хода нет.
- **Точный размер после сжатия не знает никто:** ход сжатия читал ещё старую переписку, поэтому
  его `contextTokens` — это размер ДО. Сервер отдаёт 0, кольцо гаснет, а настоящую цифру измерит
  следующий обычный ход — так и написано в подсказке кольца. В плашке остаётся только размер ДО
  («было N токенов»): это единственное честно известное число.

Источник до переноса: docs/cockpit/chat-agents.md § Кольцо контекста, prompt cache и сжатие

При [переносе в другую папку](workdir-transition-preconditions.md) применяется отдельная
серверная операция: принудительный summary выполняется в прежнем cwd даже у Kimi с native
compact. Seed записывается до reset и хранится в workdirState. Новый клиент с
workdirProtocol не приклеивает pendingSeed к сообщению: сервер резервирует выжимку перед
первым обычным ходом, сохраняет её при ошибке/stop и восстанавливает после падения.
