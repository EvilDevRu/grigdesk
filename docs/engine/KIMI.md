# Kimi в Factory: spike batch-режима и статус внедрения

Исходный spike снят на `kimi` 0.31.1; отдельные повторные проверки ниже явно помечены
версией 0.33.0. Это provenance наблюдаемого протокола, а не пин конкретной машины.
Generic-контракт: [ADDING-RUNNER.md](ADDING-RUNNER.md).

Статус: **допущен к боевым цепочкам**. Раннер `engine/lib/runners/kimi.sh` реализован по TDD,
offline suite зелёный, а протоколы субагентов, effort и resume подтверждены отдельными
проверками. Оговорки раздела «Не доказано» остаются в силе: они описывают границы наблюдения,
а не запрет для конкретного профиля.

**Номер версии CLI сам по себе не является допуском и не является гейтом**: совместимость
держат terminal CAS и fail-closed `classify` (незнакомый отказ остаётся `unknown` и не
перезапускает стадию), а версия пишется в metadata запуска как диагностика.

## Методика spike

Ручные прогоны `kimi -p <prompt> --output-format stream-json` в изолированном каталоге
(`/tmp/kimi-runner-spike`, после spike удаляется), минимальные безобидные промпты.
Обезличенные результаты — `tests/engine/fixtures/classifiers/kimi-*` (PROVENANCE=runtime-spike).

## Формат событий stream-json (доказано)

Поток NDJSON в stdout, одна строка = одно событие. Наблюдаемые формы:

| Форма | Пример | Семантика |
|---|---|---|
| `{"role":"assistant","content":"..."}` | финальный текст | model activity |
| `{"role":"assistant","tool_calls":[{"type":"function","id":"tool_…","function":{"name":"Write","arguments":"…"}}]}` | вызов инструмента | tool activity |
| `{"role":"tool","tool_call_id":"tool_…","content":"…"}` | результат инструмента | tool activity |
| `{"role":"meta","type":"session.resume_hint","session_id":"…","command":"kimi -r …"}` | всегда последняя строка | мета, не активность |

stderr пуст при успехе; при ошибках запуска — одна строка `error: failed to run prompt: …`.
stdout содержит **только валидный NDJSON этого диалекта**: журнал разбирают
`classify` и GrigDesk, поэтому произвольный вывод обёртки в него недопустим. Единственное
исключение — нормализованные события моста телеметрии (см. следующий раздел): они той же
формы (`role` = assistant/tool) и помечены полями `agent`/`bridge`.

## Субагенты в stream-json НЕ видны

Делегировав работу инструментом `Agent`, CLI перестаёт писать в stdout вообще: в потоке
нет ни самого вызова `Agent`, ни единого события субагентов. В проверочном прогоне
в `events.jsonl` вызовов `Agent` не было, тогда как главный wire содержал делегирования, а вся работа
субагентов лежала в соседних `agents/agent-N/wire.jsonl` и в журнал этапа не попала.

Две беды, обе наблюдались:

- **`events.jsonl` замирает на десятки минут при здоровом ходе.** GrigDesk считает молчание
  по свежести журнала (`readRunSilence`) и звал человека к работающему агенту. Хартбитов,
  как у Claude, у kimi нет — падать было не на что.
- **`fanout_count` не имел источника** и возвращал ноль всегда, то есть телеметрия
  делегирований у kimi отсутствовала как класс.

Поэтому раннер пропускает поток CLI через мост `lib/runners/kimi-wire.py`:

- мост — **единственный писатель журнала** (труба `CLI | python3 kimi-wire.py --merge`).
  Второй параллельный писатель в тот же fd недопустим: строки CLI доходят до 32 КБ, это
  много больше PIPE_BUF, и атомарность append не гарантируется ни для одной из сторон;
- поток CLI переливается **байт-в-байт**, события субагентов вливаются между строками;
  сканер wire-файлов работает отдельным потоком, иначе события ждали бы очередной строки
  от CLI — то есть молчали бы ровно всё время делегирования;
- из `main` мостится **только** делегирование (`Agent`) и его итог: остальную свою работу
  главный агент печатает сам, и дублировать её в журнале нельзя. Из `agent-*` мостится всё
  осмысленное — этих событий в журнале нет вовсе;
- **исход хода берётся у CLI** (`PIPESTATUS[0]`): сбой моста не имеет права стать отказом
  стадии. Без `python3` мост тихо пропускается — телеметрия субагентов не стоит отказа хода.

Инвариант classify при этом не смягчается, а усиливается: подмешанное событие субагента —
это доказанная model/tool activity, поэтому `_runner_kimi_no_model_activity` на нём
возвращает «работа была», и `provider_unavailable` не переключит стадию, часть которой уже
выполнили субагенты.

`fanout_count` читает тот же per-run home и считает вызовы `Agent` во ВСЕХ агентах хода
(субагент вправе делегировать дальше — цифра отвечает на «сколько ходов было порождено»).
Счёт — разбором JSON, а не грепом: `llm.tools_snapshot` несёт ОПИСАНИЕ инструмента `Agent`,
поэтому `grep '"name": "Agent"'` дал бы ненулевой fanout на ходе без единого делегирования.

Формы событий `wire.jsonl` (конверт `{"type":"context.append_loop_event","time":<ms>,"event":{…}}`):

| `event.type` | Поля | Что с ним делает мост |
|---|---|---|
| `content.part` | `part.type` ∈ `think`/`text`, текст в поле с именем типа | из `agent-*` → `assistant` с `thinking`/`content` |
| `tool.call` | `toolCallId`, `name`, `args` | `assistant` + `tool_calls`; из `main` — только `name == "Agent"` |
| `tool.result` | `toolCallId`, `result.output` | `tool` + `content`; из `main` — только для запомненных делегирований |
| `llm.request`, `usage.record`, `llm.tools_snapshot`, `step.begin/end` | — | игнорируются |

Содержимое режется до 2000 символов: журнал — телеметрия, а не хранилище выводов
инструментов (один `Read` субагента доходит до сотен килобайт).

Capability `fanout` раннер по-прежнему НЕ заявляет, и это не противоречие: делегирование
у kimi решает модель внутри одного хода, а capability отвечает на другой вопрос — умеет ли
раннер исполнять параллельные ветви, которыми управляет движок. Второе spike не доказывал.

Промпт передаётся **только аргументом** `kimi -p "<prompt>"`: форма `-p -` stdin не читает
(доказано прогоном — модель получила пустое сообщение, rc=0). Практический предел —
ARG_MAX (~2 МБ на argv+env); конвейерные промпты на порядки меньше, отдельной защиты
не делаем.

## Permissions в headless (ключевой результат)

**Batch-режим по умолчанию выполняет всё без вопросов.** Доказано: без единого флага
`kimi -p` выполнил и `Write` (создание файла), и `Bash` (shell-команда) — rc=0, без
запросов и без зависаний. Флаги `-y/--yolo` и `--auto` описывают поведение
интерактивных режимов; в batch дефолт уже permissive. Промежуточного режима
«правки да, деструктивные нет» у `-p` нет.

Следствие: permission-политика раннера = «всё разрешено», деструктивные команды
ограничены только моделью. Это принятая политика раннера (голый запуск, как из терминала).
Зависания в ожидании ответа не происходит —
headless-пригодность подтверждена.

## Exit codes и сигнатуры

| Случай | rc | Сигнатура | Статус |
|---|---|---|---|
| Успех (включая tool calls) | 0 | events: assistant/tool + resume_hint | доказано |
| Нет логина (`KIMI_CODE_HOME` без credentials) | 1 | stderr: `No model configured. Run \`kimi\` and use /login to sign in…` | доказано, fixture `kimi-no-login` |
| Несуществующая модель (`-m`) | 1 | stderr: `config.invalid: Model "…" is not configured in config.toml` | доказано, fixture `kimi-bad-model` |
| SIGTERM во время хода | 143 | events может быть пустым, если TERM до первого события | доказано, fixture `kimi-interrupted` |
| Исчерпана квота биллингового цикла | 1 | stderr: `provider.auth_error: 403 You've reached your usage limit for this billing cycle…` | доказано живым инцидентом, fixture `kimi-usage-limit` |
| Weekly/subscription limit подписки | — | **не снято** (живьём не воспроизводится по команде) | НЕ доказано |
| 5h rate window / голый 429 | — | не снято | НЕ доказано |
| 401/403 от API (протухший токен) | — | не снято (нужен протухший credential) | НЕ доказано |
| 413 / context overflow | — | не снято | НЕ доказано |
| Обрыв транспорта на обновлении OAuth-токена | 1 | stderr: `OAuth request to https://auth.kimi.com/api/oauth/token failed: fetch failed: …` | доказано 10 живыми инцидентами, fixture `kimi-oauth-transport` |
| Прочий network error | — | не снято: CLI игнорирует `HTTP(S)_PROXY` (прогон с битым прокси ответил rc=0) | НЕ доказано |

**Ограничение classify v1:** остальные сигнатуры лимитов и 401/403 от API не доказаны,
поэтому классификатор их НЕ содержит — они уходят в `unknown`, стадия не переключается,
run встаёт в STALLED до человека. Это fail-closed и осознанно: при новом живом инциденте
снять stderr/events (PROVENANCE=runtime), добавить fixture и сигнатуру.

Три доказанные сигнатуры. Первые две — только при доказанном отсутствии model/tool
activity (пустой events.jsonl), по инварианту ADDING-RUNNER.md:

- `No model configured … /login` (незалогиненный CLI) → `provider_unavailable`;
- `provider.auth_error: 403 … usage limit … billing cycle` (кончилась квота) → `limited`,
  то есть провайдер уходит под предохранитель на cooldown, а не считается сломанным.
  Требуются ОБЕ части текста: голый `provider.auth_error: 403` тем же кодом отвечает
  и на отозванный токен, который ожиданием не лечится. Ограничение видно и в самом
  классификаторе: `limited` он ставит только до первого действия модели — лимит,
  догнавший ход в середине, остаётся `unknown`, иначе следующий заход переиграл бы
  уже сделанную работу.

Третья сигнатура устроена иначе, и это не послабление инварианта, а его обратная
сторона:

- `OAuth request to https://auth.kimi.com/api/oauth/token failed` **вместе с** обрывом
  соединения (`fetch failed`, `socket disconnected`, `ECONNRESET`, `ETIMEDOUT`,
  `EAI_AGAIN`) → `transient`. Требуются ОБЕ части: один `OAuth request … failed`
  покрывает и отозванный токен (`401 invalid_grant`), а он ожиданием не лечится;
  один обрыв соединения печатает и провайдер модели, а это другой отказ с другой ценой.

Проверки «модель не работала» у него НЕТ намеренно. У `provider_unavailable` и `limited`
она защищает от переключения исполнителя поверх частично сделанной работы; `transient`
исполнителя не переключает вовсе, поэтому защищать нечего. А главное — в этом отказе
модель как раз работала: guard исключил бы ровно тот случай, ради которого класс заведён.

Замер 10 инцидентов (CLI 0.33.0): семь случились ПОСЛЕ реальной работы, от 7,7 до
58,9 минут, 169 минут суммарно. В самом долгом ходе wire-журнал насчитал 59 обращений
к модели — CLI пометил ошибку `"retryable": false`, завершил ход целиком, и вся эта
работа пропала вместе с ним.

**Класс `transient` эту потерю НЕ отменяет.** Он меняет только видимость: раньше в
`meta.env` стояло `RESULT_CLASS=unknown`, и отличить моргнувшую сеть от настоящей поломки
можно было только грепом по `wire.jsonl` внутри per-run home. Повторить сам запрос токена
GrigDesk не может — он живёт внутри CLI.

## Прерывание (доказано)

TERM по обёртке (`timeout`) → процесс умирает чисто, rc=143, остаточных процессов нет.
CLI не создаёт собственную сессию: дерево остаётся в setsid-сессии launcher'а, штатный
quiesce достаточен, `runner_kimi_interrupt` = `return 0`. Внимание: на хосте живут
долгоживущие `kimi acp` процессы чат-рантайма GrigDesk — убивать по имени процесса
нельзя, только по сессии/PGID (launcher так и делает).

## Статусный канал (доказано по примитивам)

env наследуется: агент через `Bash` видит `FACTORY_*` переменные родителя
(fixture: `printenv FACTORY_PROBE` → значение дошло). Shell выполняется без вопросов.
Значит `bash $FACTORY_HOME/lib/stage-result.sh done` достижим для агента в
request-транспорте (`status_request`); end-to-end коммит результата проверяется
integration-тестами с fake-раннером, не живым CLI.

## Startup inventory (зафиксирован)

`KIMI_CODE_HOME` (по умолчанию `~/.kimi-code/`): `config.toml` (default_model,
`[providers."managed:kimi-code"]` oauth, 4 модели), `credentials`, `oauth/`, `sessions/`,
`session_index.jsonl`, `logs/`, `telemetry/`, `workspaces.json`, `bin/` (CLI + `kimi.bak`
после self-update). При пустом `KIMI_CODE_HOME` CLI создаёт `config.toml`, `logs/`,
`updates/`, `device_id`, `migrations-effort.json`. Раннер запускает CLI с per-run
`KIMI_CODE_HOME` (`$run_dir/kimi-home`, см. «Effort через per-run home»): symlink
`credentials`/`oauth` + копия `config.toml`, остальное CLI пересоздаёт на запуск.
Skills без `--skills-dir`
подхватываются auto-discovery из user и project каталогов (по `--help`) — раннер
наследует это поведение, как запуск из терминала (принятый риск).

## Каталог и совместимость CLI

Версия CLI **не является допуском**. `probe` требует доступный `kimi` и успешный
`kimi --version`, а наблюдаемую версию сохраняет в metadata конкретного provider run
для диагностики. Обновление между узлами маршрута допустимо: immutable-контракт
попытки закрепляет маршрут и входы, но не исполняемый CLI.

Граница безопасности здесь не semver, а протокол движка:

- успех этапа принимается только через run-scoped CAS `stage-result`;
- известная отказная сигнатура применяется лишь при доказанном отсутствии
  assistant/tool activity;
- новая или изменившаяся форма отказа классифицируется `unknown`, поэтому не вызывает
  автоматический failover и повторное выполнение стадии;
- версия остаётся в `meta.env`, то есть расследование не теряет фактический runtime.

Это гарантирует корректность оркестрации, а не одинаковое качество модели или побочные
особенности CLI во всех релизах. `kimi upgrade` может менять их; если изменение не ломает
доказанный протокол, Factory его специально не блокирует.

Модели (из `config.toml`, `kimi provider list`: `managed:kimi-code`, source=oauth,
default `kimi-code/k3`): `kimi-code/k3`, `kimi-code/k3-256k`, `kimi-code/kimi-for-coding`,
`kimi-code/kimi-for-coding-highspeed`. Каталог раннера — pinned models.tsv с этими id.
Границы совместимости runtime в этих строках — `*/*`: список моделей закреплён
адаптером, но semver CLI его не выключает.

Effort: argv-флага и env-переменной у `-p` нет (по `--help`), но `[thinking].effort`
из config.toml применяется — см. «Effort через per-run home» ниже.

## Effort через per-run home

Spike (тот же протокол, что основной; каталог `/tmp/kimi-effort-spike`, удалён после):

- `KIMI_CODE_HOME=<per-run>` с symlink `credentials`/`oauth` на дефолтный home и копией
  config.toml: `kimi -p … --output-format stream-json` → rc=0, события `assistant` +
  terminal `session.resume_hint`, stderr пуст. Per-run home рабочий, credentials
  symlink-ами достаточно.
- Валидные значения `[thinking].effort` (`low`, `max`) переживают запуск — config.toml
  не переписывается.
- **Невалидное значение CLI не отвергает**: `effort = "bogus"` → rc=0, модель отвечает,
  а config.toml молча переписывается в `effort = "high"` (след — `migrations-effort.json`).
  Поэтому набор `low|high|max` пиннутого CLI валидирует сам раннер, fail-closed rc 4 до
  вызова модели (иначе мусорный пин незаметно деградирует в high).
- Effort в событиях stream-json не наблюдается: доказательство применения — принятие
  валидных значений и сохранность конфига, а не поле в потоке.

Реализация: `runner_kimi_run` собирает `$run_dir/kimi-home` (копия config.toml с
переписанной секцией `[thinking]` — блоки моделей с их `default_effort` не трогаются;
`credentials`/`oauth` symlink) и запускает CLI с `KIMI_CODE_HOME` на него. Пустой
effort → конфиг копируется без правки (наследуется дефолтный home). Пины —
`MODEL_<СТАДИЯ>_KIMI_EFFORT` / `MODEL_DEFAULT_KIMI_EFFORT` в runners.env, как у
других провайдеров.

## Принятые риски (наследуют риски редакции 2 плана)

- Голый запуск: env/ФС/сеть хост-пользователя без OS-границы; деструктивные команды
  не ограничены ничем, кроме модели.
- Egress не фильтруется (CLI к тому же игнорирует proxy env).
- Общий credential file с чат-рантаймом GrigDesk; гонки OAuth refresh — наблюдать в live.
- Auto-discovery skills/config из home и project каталогов — как у запуска из терминала.
- CLI может обновиться между узлами одной route-attempt; фактическая версия каждого
  provider run записывается, а незнакомый отказ остаётся `unknown` без автоповтора.
