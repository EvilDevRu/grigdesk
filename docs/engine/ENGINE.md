# Устройство Factory Engine

Документ для изменений в `engine/`. Контракт проекта описан в
[PROFILE-CONTRACT.md](PROFILE-CONTRACT.md), создание нового профиля — в
[NEW-PROJECT.md](NEW-PROJECT.md), multi-AI cutover — в [MULTI-AI.md](MULTI-AI.md).

## Инварианты

1. Движок не содержит имён контейнеров, БД, репозиториев и команд конкретного проекта.
2. Каждый локально установленный профиль имеет валидный `profiles/<name>/runners.env`;
   `/profiles/` не отслеживается Git, implicit provider отсутствует.
3. Агент не пишет pipeline напрямую. Terminal result идёт через run-scoped `stage-result`,
   typed failure metadata — через тот же capability, разрешённый progress — через
   `stage-progress`.
4. Любой повтор/switch получает новый `run_id`, больший `epoch` и новую capability.
5. Автоматический failover выполняется только для классифицированных provider failures.
6. Config/state writers используют `flock`, CAS/revision и atomic rename.
7. Offline tests не запускают Cockpit и не выполняют model call.
8. Опубликованный route v2 bundle проверяется engine независимо от server-а; изменение
   `current` не меняет уже закреплённую ревизию.
9. Model/provider/effort отсутствуют в route schema и остаются только в `runners.env`.
10. Guard, locks, capabilities и состояние v2 лежат в `FACTORY_CONTROL_ROOT`, который
    не пересекается с provider-writable `STATE_DIR`.
11. Delivery выводится из закреплённой топологии: нет канонического `ship` — нет delivery
    spec, actions, targets и stage-scoped delivery-команд.

## Запуск этапа

```text
factory
  → validate profile + canonical runner config
  → require RUN_PROTOCOL=2
  → resolve route chain
  → resolve family policy against local catalog
  → require fresh coverage
  → begin run_id/epoch/capability
  → launch provider adapter
  → classify outcome
      success/status result → commit
      switchable provider failure → next candidate
      task/policy/unknown-side-effect failure → stop
```

`core.sh` provider-agnostic: в нём нет прямого запуска Claude/Codex и нет выбора модели.
Project write roots и `STATE_DIR` передаются обоим adapter-ам явно; Codex получает их через
повторяемый `--add-dir`, сохраняя `workspace-write`, а не переходя в `danger-full-access`.

**Адрес стенда в контексте.** `services.frontendUrl`/`apiUrl` собирает `factory-context`
из порта песочницы и хоста `PROFILE_SERVICE_HOST` (умолчание — `127.0.0.1`). Имя вынесено
в профиль не для красоты: приложение вправе отличать локальный запуск от production по
`window.location.hostname`, и тогда петлевой адрес открывает другой режим работы. В одном
прогоне браузерная приёмка получила петлевой IP вместо ожидаемого hostname. Фронтенд
переключился в production-режим, запросил сессию у production endpoint, получил 401 и
попал в цикл редиректов на маршрут, отсутствующий в sandbox-сборке. За десятки навигаций
URL разросся, страница осталась пустой, а Playwright перестал отвечать: `evaluate` ждал
execution context, уничтожаемый каждой навигацией. Узел дошёл до лимита с зависшими
вызовами MCP и без проверенных сценариев. Мораль движковая: health-check по HTTP
(«порт отвечает 200») ничего не доказывает про то, что агент увидит в браузере.

**Лимит времени этапа.** Секунды даёт `_stage_timeout` по классу узла из бандла
(`policy.timeoutClass`), с переопределением профилем; порядок разрешения и таблица
дефолтов описаны в [PROFILE-CONTRACT.md](PROFILE-CONTRACT.md).
Тем же числом `run_agent` приписывает в конец промпта регламент времени: агент иначе
не знает срока и планирует проверки вслепую. Без регламента он может потратить весь остаток
на необязательную регрессию, не успеть отчитаться и потерять вместе с этапом готовый код.
Промпт нигде не хешируется, поэтому приписка безопасна; менять её нужно вместе с тестом
`unit/stage-time-budget.sh`, который сверяет
названные агенту минуты с фактическим `timeout`. Сам `timeout` вызывается с `-k 30`:
провайдер, переживший TERM, иначе остался бы висеть с занятым слотом.

**Бюджет раундов — в том же блоке и намеренно мягкий.** Раунд — это одно обращение к модели
внутри захода. Модель снова получает накопленный диалог, поэтому сырой вход захода из N
раундов составляет примерно `N × конечный контекст / 2`, то есть растёт **квадратично**.
Фактический счёт может быть ниже благодаря prompt cache и определяется только сообщёнными
provider-ом cache read/write/uncached, а не размером контекста сам по себе. Но объём всё равно
влияет на задержку и цену cache miss. В выборке прогонов входной объём превышал уникальный
на десятки раз. Раздувает его при этом не работа, а поиск: короткие `grep`/`ls` тратят раунд
почти без нового контекста, а чтения увеличивают вход всех последующих раундов.
Число берёт `_stage_round_budget` (`FACTORY_STAGE_ROUND_BUDGET`, умолчание 150).

Предел объявлен агенту **порогом сведения, а не остановкой**, и это не смягчение
формулировки: молча брошенный заход движок считает «результата нет» и списывает попытку из
бюджета этапа (`tries_left` в `route-runtime.sh` — это `1 + retry_no_result +
provider_attempts`). Останавливаться по счётчику раундов значило бы отдавать попытку за
дисциплину, то есть отнимать ровно ту автономию, ради которой всё и делается. Поэтому текст
блока велит свести сделанное в черновик и закрыть узел через `stage-result` тем, что готово,
а остаток назвать в отчёте. Жёсткий вариант потребовал бы собственного счётчика попыток и
делается отдельно.

**Три правила счёта в том же блоке — они переводят «квадратично» в решение у инструмента.**
Само по себе знание про раунды агенту ничего не даёт: считать надо в момент, когда он
собирается что-то прочитать или записать.

- **Чтение добавляет во вход `размер × число раундов ПОСЛЕ него`, а не только свой размер.**
  Файл на пять тысяч токенов, открытый в начале захода из нескольких десятков раундов,
  добавит более ста тысяч сырых входных токенов: он поедет в каждом следующем запросе.
  Какая часть будет прочитана из кэша, заранее неизвестно. Отсюда требование открывать нужный
  кусок, а не файл целиком, и не перечитывать то, что уже в диалоге.
- **Служебные файлы самого движка читать нечего.** В замерах этап открывал собственный
  `logs/runs/**/wire.jsonl`: небольшой файл, повторённый в дюжине следующих раундов, уже добавляет десятки тысяч токенов. Этап также заново вычитывал
  только что написанный им же тестовый файл. Это не код проекта и к задаче отношения не имеет,
  поэтому запрет назван в блоке прямо: `logs/runs/**`, домашние каталоги раннера, состояние
  движка.
- **Запись в артефакт добавляет `размер × раунды ВСЕХ следующих этапов` во вход.** Это самое
  дорогое и самое незаметное: `plan.md` на пять тысяч токенов при более чем сотне дальнейших
  раундов добавляет сотни тысяч сырых входных токенов и при промахах кэша — заметную долю
  стоимости всего прогона, причём последствия несёт не тот, кто писал. Поэтому блок требует
  складывать в артефакт решения, адреса (файл и символ) и проверки, а не пересказ кода и не
  цитаты исходников: кому понадобится текст, откроет его по адресу.

Правила универсальные и живут в движке ровно потому, что не зависят ни от проекта, ни от
исполнителя: `run_agent` собирает промпт до выбора раннера. Профильные промпты поверх этого
говорят частности — что именно записать на конкретном этапе.

**Автосжатие контекста этапа: вход движка и выход раннеру — РАЗНЫЕ переменные.** Порог
приезжает в `FACTORY_STAGE_AUTO_COMPACT` (кокпит передаёт его явным `--setenv`, всегда,
включая `0`), а при пустом значении движок спрашивает профиль — ключ `AUTO_COMPACT_WINDOW`
в его `runners.env`. Разрешённое число уезжает раннерам под **другим** именем,
`RUNNER_AUTO_COMPACT_WINDOW`, и раннер переводит его на диалект своего CLI
(`CLAUDE_CODE_AUTO_COMPACT_WINDOW` у claude, `-c model_auto_compact_token_limit=N` у codex).

Разделение имён не косметика: bash закрепляет временное присвоение перед вызовом функции,
если функция сама пишет в ту же переменную, — порог, заданный одному этапу, протёк бы
«настройкой» во все следующие заходы демона. Зачем порог вообще нужен: собственный
автокомпакт CLI считается от доли ОКНА модели и на окне в миллион токенов срабатывает
около 959k. Явная более ранняя граница удерживает рабочий контекст, задержку и риск overflow
в выбранных человеком пределах; это не тарифный порог и не предсказание cache miss. Замер
показал, что без такой границы этап доходил до 506k. `0` — не вмешиваться.

**Карта задачи из разведки — служебный блок, а не правка промптов.** SCOUT уже находит, где
что лежит, но его артефакт `<STATE_DIR>/t<TASK>.recon.md` читал только он сам: каждый
следующий этап выяснял то же самое поиском заново. Донести карту может **только движок** —
маршрут прибивается хешем при старте попытки, а промпты этапов принадлежат схеме и правятся
по профилям, так что вклейка в них разъехалась бы на первой же формулировке. Способ тот же,
что у черновика хода: `_stage_task_map_block` достаёт из `recon.md` раздел `## Карта задачи`
и `run_agent` приписывает его **первым** служебным блоком (порядок: карта → граница scope →
карточка решения → регламент времени → контекст повтора → черновик → указание человека
последним).

Три решения внутри, каждое оплачено:

- **резервный заголовок `## Область изменения`.** Это раздел, который `recon.md` содержал и
  ДО введения карты, с тем же списком файлов. Поэтому блок заработал без единой правки в
  профилях и без единой публикации каталога — новый формат карты доезжает постепенно, по мере
  публикаций, а польза есть с первого же прогона;
- **потолок 16 КБ (≈5k токенов) и режется КОНЕЦ**, в отличие от черновика, где ценен хвост.
  Окупаемость прямая: карта в K токенов на заходе из N раундов стоит `K × N`, сэкономленный
  раунд возвращает средний контекст C — порог примерно `K × N / C`, то есть 6–8 раундов из
  полутора сотен, которые заход тратит на поиск;
- **правило поведения живёт в блоке, а не в тридцати шаблонах агентов.** Блок сам говорит
  читателю: названные файлы открывать напрямую, не подметая дерево `ls -R`/`find`, а
  найденное дописывать обратно в `## Карта задачи`. Одно место — одна формулировка, и она
  гарантированно доезжает; дублировать её внутрь самой карты нельзя, за неё платил бы каждый
  раунд каждого этапа.

Разбор — `python3` по той же причине, что у черновика: обрезка байтами может попасть внутрь
многобайтного символа и отравить весь промпт до model call. Тесты — `unit/stage-time-budget.sh`.

**Scope задачи — замкнутый служебный блок.** `_stage_scope_block` доезжает до каждого
агентского узла из `run_agent`, поэтому действует и для попытки, которая уже закрепила старый
route hash: новый каталог для этого не нужен. Источники требований ограничены самой задачей,
её явными исключениями и прямыми решениями человека. План, разведка, отчёт и finding могут
только связать требование с кодом и доказательством; самостоятельно расширить задачу они не
могут. Изменение, тест или блокирующий finding без ссылки на критерий остаётся неблокирующим
`outside scope / follow-up` и не вызывает rewind.

К границе относятся и команды: явный запрет команды и точная безопасная замена из задачи
сильнее общего профильного prompt. Проверочный узел не имеет права запускать запрещённую
команду «для полноты»; без названной замены он фиксирует непроверенное и останавливается у
человека. Это правило живёт в служебном блоке, поэтому доезжает до уже закреплённых попыток:
иначе старый `SYNTAX` продолжал выполнять разрушительную сборку даже после исправления
профиля и публикации нового каталога.

**Отказ политики прав виден числом, а не только в потоке.** Правила выше — регламент, и
на живом прогоне он был нарушен: нужный запуск «был заблокирован политикой», агент в тот
же ход написал «проверю через прямой запуск скриптов», и результат подменённой проверки
уехал дальше как требуемое доказательство. Опасен здесь не потраченный вызов, а подмена,
поэтому нужен машинный признак.

Необязательный метод раннера `denial_count` читает отказы из завершившегося хода
(`permission_denials` события `result` у claude), `multi-runner` проверяет число и пишет
его в реестр как `DENIALS_<STAGE>` — той же дорогой, что и `FANOUT_<STAGE>`. Кокпит
показывает его чипом в модалке узла, то есть человеку на воротах.

Ноль пишется только как ФАКТ. У оборванного хода (таймаут, KILL, падение) события
`result` не будет вовсе, а отказы в нём могли быть: метод отвечает ненулевым кодом,
движок ключ не пишет, чип не рисуется. Записанный в таком случае ноль утверждал бы, что
запретов не случилось, — ровно то, чего проверить нельзя. Раннер без метода не пишет
ничего. Тесты — `unit/claude-denial-count.sh`, `tests/server/factory-stage-denials.test.js`.

**Дефект, существующий на базовой ревизии, замечанием задачи не является** — ни
блокирующим, ни отложенным. Инструмент проверки почти всегда шире задачи: линтер идёт по
всему файлу, прогон — по всему spec-файлу, сборка — по всему проекту. Отложенная находка
это хвост САМОЙ работы, который поедет к человеку на ворота; чужой давний дефект туда не
относится и делает хвост нечитаемым, поэтому ему место в комментарии узла отдельным
списком «было до задачи». Отделять велено арифметикой, а не суждением: прогнать ту же
проверку на базовой ревизии и вычесть совпавшее либо ограничить охват инструмента диффом;
не смог разделить — сказать это в отчёте и не подавать неразделённое блокирующим.

Цена ошибки несимметрична, отсюда жёсткость правила. Чужой дефект, поданный блокирующим,
разворачивает маршрут к автору; автор справедливо его не чинит; набор id не меняется — и
маршрут встаёт на топтании до человека, детерминированно. Пропущенный чужой дефект не
стоит ничего: он лежал в репозитории и до задачи. Сама вычитающая проверка принадлежит
профилю: движок про git не знает ничего и базовую ревизию подсказать не может, её кладёт
в typed context узла профиль (`PROFILE-CONTRACT.md`, раздел про проверяющий command-узел).

Для пары «автор → проверяющий» блок задаёт дополнительную монотонность. На первом проходе
проверяющий обязан собрать полный набор связанных с критериями замечаний. После возврата
`evidence.findings.open` образует замкнутый блокирующий набор: та же проблема сохраняет id,
а новый id переводит commit в human-resumable `no-progress`, не выполняя ещё один rewind.
Тот же `owner + ids` после одного ремонта также сразу даёт `no-progress`: изменение summary
не покупает ещё один автоматический проход. Это консервативно и для настоящей регрессии после
исправления: ledger не умеет доказать её причинность, поэтому расширение сначала видит человек.
Пропущенная ранее идея остаётся follow-up.

**Самостоятельное решение предъявляется карточкой.** `_stage_decision_card_block` идёт сразу
за границей scope и говорит обратное ей по знаку: граница запрещает расширять задачу, карточка
разрешает решить неназванное — но не молча. Порядок именно такой; обратный читался бы как
разрешение решать что угодно, лишь бы записать.

Правило появилось из замера живых остановок «спорное — человеку»: одна стоила 14 часов
простоя стенда и слота ради одного `goto`, вторая — 31 минуты, в которые человек работал
курьером между тем же ИИ и полем причины. Знания он не добавил ни разу: разбор в обоих
случаях делала модель. Разбуженный посреди маршрута человек приносит задержку и ложную
запись в журнале, будто решение обдумано; приходит он к готовой работе, и предъявлять надо
там.

Цена права решать самому названа прямо: конвейер, который сам обновляет эталон, так же тихо
примет регресс. Защита ровно одна — карточка вместе с доказательством. Пять пунктов в
фиксированном порядке (что сделал, почему, чем доказал, чем грозит ошибка, подробности), и
**первые четыре обязаны читаться без открытия репозитория**: путь, имя поля или хеш в них —
дефект карточки, а не подробность.

Адрес карточки — `artifacts.report`, и это не новый артефакт. `report.md` уже является
накопительным отчётом приёмки: ворота `gate_accept` показывают именно его (`NODE_DOC`), и
узлы маршрута уже дописывают туда свои сводки — так же поступает досье аудита. Свой файл
потребовал бы ключа в `artifacts` движка, записи в `STAGE_DOCS` сервера и в `NODE_DOC`
фронта — трёх мест, которые расходятся молча (см. `docs/cockpit/factory-graph.md`).

Блок собирает движок, поэтому правило доезжает до попыток, закрепивших старый route hash,
и не требует ни публикации каталога, ни правки шаблонов агентов. Цена — 1001 байт служебной
обвязки в каждом заходе; она внесена в явный бюджет `unit/stage-time-budget.sh`.

**Открытые находки доезжают до автора служебным блоком, а не через `requiredContext`.**
`_stage_open_findings_block` собирает `evidence.findings.open` (id, `sourceNode`, summary)
и `run_agent` приписывает его после черновика хода, но ПЕРЕД словом человека: указание
человека сильнее машинных находок. Источник — контекст, уже построенный для узла
(`_route_v2_open_findings_from_context`), а не повторное чтение журнала: диспетчер держит
task lock, и `attempt_stage_state_findings_v2` в этой точке встал бы на нём. Показываются
только `open`: `closed` — история, `deferred` адресованы человеку на воротах.

Почему это инвариант движка, а не поле схемы: `render_node` вклеивает в промпт ровно те
секции, что перечислены в `prompt.requiredContext`, поэтому узел без `evidence` замечаний
своего критика не видел вовсе. Профили объявляли `evidence` вразнобой — замер 22.08.2026
по всем локальным профилям: узел плана слеп везде, узлы автора тестов и реализации —
через один, причём один профиль чинил свой узел точечно, не заведя общего правила. Цикл
«критик отклонил → автор не увидел причину → те же дефекты → `no-progress`» стоил двух
кругов по 25 минут на живом прогоне. Валидатором маршрута это чинить нельзя:
`validate_machine` работает и на ЧТЕНИИ бандла, поэтому новое требование сделало бы
невалидными все уже опубликованные каталоги посреди идущих прогонов. Блок вместо этого
действует и для попыток, закрепивших старый route hash, — как `_stage_scope_block`.

**Находка, пережившая ремонт, помечена, и под списком стоит диагноз движка.** Числа
`openedSequence` и `lastSeenSequence` приезжали в контекст с самого начала, но именно как
два числа: агент видел их и всё равно шёл на третий круг прежним подходом. Теперь
`lastSeenSequence > openedSequence` даёт метку «ПЕРЕЖИЛА РЕМОНТ» в строке находки, а под
списком — прямой текст: прошлый подход не сработал, уточнением формулировки это не
обходится (движок сравнивает id, а не текст), выбери одно из двух — почини иначе и назови
чем, либо объяви, что закрыть нельзя, и назови причину. Второе объявлено законным исходом
захода: молчаливый третий круг стоит дороже и всё равно кончается остановкой.

Диагноз появляется ТОЛЬКО по факту. Без признаков топтания и при нечитаемых номерах
заходов блока нет вовсе: постоянный текст про топтание в каждом заходе обесценился бы к
третьему разу — ровно как обесценились числа. Ложный диагноз здесь дороже отсутствующего:
он велит сменить подход там, где прежний ещё не пробовали.

Пустой список, повреждённый JSON и отсутствующая секция дают отсутствие блока, а не отказ:
находки усиливают промпт, но не являются условием исполнения узла. Сторож —
`tests/engine/unit/stage-open-findings.sh`.

**У служебной обвязки промпта есть явный бюджет — 14600 байт** (замер 26.08.2026: 14322;
прогон идёт под `LC_ALL=C`, и русская буква стоит двух). Блоки движка вклеиваются в КАЖДЫЙ заход каждого узла и платятся токенами на
каждом обращении к модели, а расти умеют только в одну сторону: каждое правило выглядит
полезным по отдельности. Прежний потолок 20000 стерёг обрезку черновика и разрастание
регламента поймал случайно, одним общим числом. Превысил — либо ужимай текст, либо
поднимай границу в `tests/engine/unit/stage-time-budget.sh` вместе с причиной.

**Исключение — первый проход по новому артефакту.** Ремонт замкнутого набора сам создаёт
файлы: закрыть «сценарий не покрыт» нельзя, не написав тест. Замечание по такому файлу — не
рост охвата, а первая встреча с новым кодом, и человека для него звать незачем. Различие
выводится из журнала, а не из слов агента: у finding есть необязательный `anchor` (путь
артефакта), у вердикта — необязательный `reviewed` (что проверяющий фактически просмотрел
на этом проходе). Новый id, чей `anchor` не входит в объединение `reviewed` прошлых вердиктов
серии, расширением не считается и уходит обычным автоматическим возвратом, списываясь из
общего бюджета попытки. Отсев работает только при непустом `reviewed`: без объявленного
охвата «не видел раньше» неотличимо от «не потрудился посмотреть», и один якорь отменял бы
весь сторож. Вердикты без обоих полей ведут себя ровно как прежде.

**Второе исключение — документ самого ремонтируемого узла.** Отсев по `reviewed` рассчитан
на дугу, где ремонт СОЗДАЁТ файлы. На дуге планирования ремонт файлов не создаёт: он
переписывает свой документ (`t<TASK>.<узел>.md`), а замечания указывают на давно
существующий код — поэтому там отсев не срабатывал НИКОГДА, и допуск на расширение у
плановой дуги был ровно нулевой. Замер по журналам всех попыток: `skeptic → plan` —
самая частая дуга типизированных остановок (10 из 31), и ни у одной находки на ней якорь
не указывал на созданный ремонтом файл. Замечание по документу, который ремонт только что
переписал, — первый проход по новому тексту по построению. Документ ЧУЖОГО узла
послабления не получает.

**Третье — один допуск на дугу.** Прежнее правило звало человека на первом же новом
блокирующем id. Цена измерена: 13 остановок из 31 — «набор расширен новыми id», медиана
ожидания человека 15 минут, сумма 59.7 часа, максимум 13.9 часа простоя стенда и слота.
При этом ремонт в таких сериях работал: в разобранном живом случае автор закрыл два
замечания из трёх, а остановило маршрут одно новое. Поэтому первое расширение проходит,
второе останавливает. Допуск не бесплатный: он списывается из общего бюджета возвратов
попытки и hard-лимита дуги, поэтому серия «каждый круг приношу новый сценарий нарушения
того же контракта» по-прежнему конечна — она стоит на один круг дольше. Считается допуск
по СЫРЫМ наборам id, без якорных послаблений: послабления отвечают на вопрос «эта находка
законна», а допуск — на вопрос «сколько раз проверяющий уже выходил за замкнутый набор».

**Отложенные находки доезжают до узлов.** Раньше `deferred` считались адресованными
человеку на воротах и в промпт не шли вовсе, из-за чего проверяющий, не зная о собственной
прошлой отложенной находке, находил её СНОВА следующим кругом (замер: 8 попыток из 29
переоткрывают тот же id на том же узле, одна — трижды). Теперь они едут отдельным списком
и с обратным смыслом: автору «не чини», проверяющему «не открывай заново». Открытые
находки идут раньше отложенных — обратный порядок читался бы как список работы. Автор на повторе закрывает набор, не выращивая
требования или матрицу тестов. Так scope-контракт не даёт обходить guard последовательностью
новых формулировок одной проверки.

**Контекст повтора.** Ретрай узла — не чистый лист: `route_v2_dispatch_next` считает заход
(`ROUTE_V2_NODE_RETRY`) и причину (`no-result` или `failed`), а `run_agent` приписывает их
в промпт вместе с требованием сначала осмотреть следы предыдущего захода. Без этого повторный
BUILD может заново переписать уже готовый код. Бюджеты попыток при этом не меняются:
считается только то, что и раньше, — сумма `noResult` + `providerFailure` и отдельно
`productFailure`.

**Автоматический rewind конечен и наблюдает прогресс.** Опубликованный route задаёт цель и
reset-набор. Для legacy failed без metadata сохраняется старый предохранитель: два одинаковых
`node → rewind-target`, третий даёт `kind=rewind-limit`/`stop=rewind-limit`. Typed failed получает
широкий hard ceiling шесть, но обычно останавливается раньше. Сторож сравнивает снимки
`owner + sorted finding ids` и атомарно пишет `kind=no-progress`/`stop=no-progress` в четырёх
случаях: повторный набор получил новый id относительно первого verdict автономной дуги;
тот же набор пережил один ремонт; цикл `A→B→A→B→A`; **непустое пересечение** последних
`limit+1` наборов — замечание, которое пережило каждый ремонт. Первая проверка замыкает scope
у первого critic verdict и не позволяет выдавать рост задачи за прогресс; расширение остаётся
в ledger, но требует человека. Последняя проверка ловит то, чего не видят проверки точных
наборов: пока прежние сопутствующие findings закрываются, цикл может ходить вокруг одной
неснятой причины. Прогрессом для проверки ядра считается только сужение, затрагивающее
само ядро; ядро — пересечение окна, поэтому по построению пережило каждый ремонт, и отброшенный
хвост сопутствующих findings подозрение не снимает. Прежнее правило «любое строгое сужение —
прогресс» разоружало сторож: ревью могло закрыть сопутствующее замечание при живом ядре,
после чего цикл начинался заново. Все проверки находятся внутри locked append; `goto` кладёт
`human-rewind`, сбрасывает историю автономной дуги и передаёт причину следующему агенту. Решения
ворот в автоматический бюджет не входят.

**Кто принял решение — необязательное поле `actor` события.** Курсор возвращает не только
человек: сам рантайм двигает его после исчерпанного бюджета повторов, а кокпит — решением
арбитра типизированной остановки. Пока исполнитель не назывался, все три случая лежали в
журнале неотличимо, то есть машинное решение утверждало «это обдумал человек». Теперь
`factory goto --actor <id>` пишет поле в событие, и оно появляется ТОЛЬКО когда решал не
человек: умолчание `human` не пишется вовсе, поэтому обычный `goto` и все уже записанные
события остаются байт в байт прежними. Валидатор принимает `actor` только у `human-rewind`
и только не равным `human`: у прочих видов событий исполнителя нет — их вырабатывает сам
доверенный рантайм.

Рубежом безопасности поле не является и не может им быть: кокпит работает от того же
пользователя и мог бы назваться человеком. Это запись аудита, на которой стоит весь план
автономности — предъявленное решение обязано отличаться от принятого.

**Суммарный бюджет возвратов на попытку.** Per-arc лимиты считают дугу `node → rewind-target`
и не видят чередования дуг в один и тот же узел: в наблюдавшемся цикле build получил шесть
возвратов от review и один от lint, не исчерпав ни одной дуги. Поэтому `route_v2_dispatch_next` передаёт девятым
аргументом `attempt_stage_state_commit_v2` общий потолок автоматических возвратов В ОДИН target
за попытку (`target_rewind_budget`, сейчас 10). Считаются все `kind=commit` с `action.rewind`,
кроме `outcome=rejected` (решение человека на воротах), по всему журналу попытки. Порядок
проверок при коммите: scope/no-progress → лимит дуги → бюджет, и каждая причина называет себя
отдельно (`kind=rewind-limit`, reason про суммарный бюджет). **Человеческий `goto` бюджет не
обнуляет** — иначе предохранитель снимался бы тем же действием, которым человек продолжает
прогон; после исчерпания `goto` даёт шаг, а не восстановленную автономию. Ноль отключает
проверку, поэтому старые вызовы функции не меняют поведения.

**Findings — производная журнала.** Typed verdict сохраняется в immutable commit event. API
`attempt_stage_state_findings_v2` сначала проверяет весь hash-chain, затем строит
`open/closed/deferred`: повторный failed обновляет полный набор findings source-узла, а `done`
того же узла закрывает его открытые пункты. Отдельного изменяемого ledger-файла нет.
`factory-context` публикует эту проекцию в `evidence.findings`, поэтому автор получает точный
незакрытый долг, а reviewer переиспользует стабильные id вместо полного забывания предыдущего
круга.

**Вес замечания: `blocking` и `deferred`.** У finding есть необязательное поле `severity`;
отсутствие читается как `blocking`, поэтому события, записанные до его появления, остаются
валидными без миграции. Возврат работы автору, сторож топтания и бюджет дуги считают ТОЛЬКО
блокирующие замечания. `deferred` — находка вне цели задачи: она не открывает цикл ремонта, не
маскирует топтание сменой сопутствующего хвоста и живёт в проекции отдельной секцией до ворот
приёмки, где движок выкладывает её человеку в `t<task>.deferred.md`.

Отсюда два следствия в контракте исходов. Во-первых, `done` теперь может нести вердикт — но
только из отложенных находок: блокирующее замечание при `done` отвергается как противоречие.
Во-вторых, `failed`, в котором не осталось ни одного блокирующего замечания, выпрямляется в
`done` с тем же хвостом (`stage-result.sh` для агентских узлов, `_route_v2_command_result` для
доверенных команд): разворачивать сборку по замечаниям, чинить которые никто не просил, не за
что, а прежде такой вердикт неизбежно упирался в `no-progress`. Владелец (`failureOwner`)
выбирает ветку возврата и поэтому участвует в запросе перехода только у `failed`.

Это ровно тот рычаг автономии, которого не хватало проверяющим узлам: раньше единственным
способом сообщить о настоящем дефекте был отказ, то есть возврат, поэтому находка вне цели
задачи либо разворачивала маршрут, либо терялась в комментарии. Граница проходит по цели
задачи: блокирует то, что ломает саму цель или является регрессией ранее работавшего;
требование, недоказуемое на текущем стенде, блокирующим быть не может.

**Черновик хода.** Этап атомарен: пока агент не вызвал `stage-result`, для конвейера ничего
не произошло, и убитый по таймауту заход уносит с собой всё, что успел понять. Поэтому
`run_agent` даёт агенту файл `$STATE_DIR/t<TASK>.<этап>.checkpoint.md` (`_stage_checkpoint_path`)
и в регламенте времени просит дописывать туда строку после каждого осмысленного куска.
Канал именно файловый, а не `stage-progress`: тот проверяет ключи по фиксированному
маршрутному списку (ROUTE/SIZE/PLANS/…) и произвольный текст не примет by design — расширять
его под заметки значит ломать смысл нетерминального API. Права на `STATE_DIR` у агента и так
есть, лишней поверхности не появилось. Следующий заход получает UTF-8-безопасный хвост
черновика объёмом до 6000 байт
отдельным блоком, и отдаётся он **по наличию непустого файла, а не по номеру захода**: после
убитого оркестратора resume входит в узел заново с попыткой №1. Блок
прямо говорит, что это заметки, а не доказательство: сверять с `git status`/`git diff`.

Заголовок и вступление блока зависят от того, есть ли в файле подпись (ниже): без неё это
«## Черновик незакрытого захода» — обломки оборванной работы; с ней «## Заметки предыдущих
заходов», и вступление прямо говорит, что перед агентом сделанная работа, которую не приняли
дальше по маршруту. Случаи разные, и заход, принявший второе за первое, начнёт переделывать
готовое.

**Терминальный коммит черновик не стирает, а ПОДПИСЫВАЕТ.** При успешном закрытии узла
(`done`/`skipped`, плюс после успешной проверки bootstrap-записи SCOUT) `route-runtime`
дописывает в конец строку «ЗАХОД ЗАКРЫТ: исход `<outcome>`, <дата UTC>» и оставляет файл
на месте. Стирание выглядело логичным («узел закрыт — заметки чужие»), но ровно оно и стоило
дороже всего: узел, отклонённый следующим за ним критиком, возвращается сюда тем же маршрутом
и с **той же** попыткой, и второй заход получал побайтово тот же промпт без единой строки о
том, что первый уже сделал. В наблюдаемом цикле оба захода заняли десятки раундов, а их начальные чтения совпали почти по порядку —
второй заход заново выводил разведку первого. Новая эпоха узла ретраем не считается (`ACTIVE_EPOCH_<STAGE>=2` — это штатный цикл
`узел → критик → узел`), поэтому блок повтора здесь не срабатывает и подменить черновик
не может.

Подпись — не украшение: она отделяет «здесь всё сделано и закрыто» от «здесь остановились
на середине». На `failed` и `exhausted` черновик остаётся **без** подписи: узел не закрыт,
маршрут передан человеку, и файл тут единственная запись остатка работы. Если TESTS
отчитается «детали и остаток — t<TASK>.tests.checkpoint.md», а движок сразу сотрёт файл,
у остановленного маршрута останется одно предложение комментария вместо разбора.

Границей владения служит **попытка, а не узел**: чужие заметки — это заметки брошенного
прогона, а не собственного предыдущего захода. Поэтому черновики всей задачи стираются один
раз, при создании новой попытки (`_stage_checkpoint_clear_task` в `bin/factory`, рядом с
`v2_shared_lease_bind`). Внутри попытки — от первого захода до `goto` человека — файл живёт
и накапливается.

**Указание человека при возврате на узел.** Свободный человеческий текст должен переживать
отдельный процесс `resume`, поэтому mutable-комментарий ворот не может быть его источником:
reset-проекция закономерно очищает решение до нового захода. И `goto` обычного узла, и
`rejected` на воротах теперь кладут указание в immutable журнал попытки. В первом случае
это причина события `human-rewind`, во втором — bounded `reason` commit-события
`rejected`; при rewind он адресован узлу из `action.rewind`, а при stop остаётся
неизменяемым аудитом причины остановки. Для допустимого rejected→next адресат так же
берётся из `action.next`. `attempt_stage_state_human_note_v2`
читает последнее адресованное указание, `route_v2_dispatch_next` берёт его **один раз на вход в узел**
(журнал за время узла не меняется, а каждое чтение — обход всех событий под локом)
и отдаёт `run_agent` в `FACTORY_STAGE_HUMAN_NOTE`, а тот приписывает блок
**последним** — черновик выше зовёт «продолжай с этого места», а человек мог вернуть узел
ровно затем, чтобы с этого места свернуть; блок прямо объявляет, что при расхождении прав
человек. Указание живёт до первого коммита узла: повторы внутри захода его видят, а
следующий приход сюда (петля маршрута, возврат через полгода) — уже нет, иначе агент
получит чужой приказ и будет уверен, что человек велел это ему. Блок движковый, не
маршрутный, поэтому публикация каталога профиля не нужна.

Exact retry решения ворот включает и комментарий: после crash между ledger CAS и
UI-проекцией дословный повтор идемпотентен, но новый текст получает конфликт 75. Иначе
кокпит показал бы новый комментарий, которого нет в журнале и который агент никогда не
увидит. Непустой комментарий при rewind/next разрешён только с целью `executor=agent`:
автоматический command не читает промпт и не может честно считаться получателем.

На практике указание пропадало молча в двух местах.

**Возврат на узел, где курсор уже стоит.** `prepare-human-rewind` считал такой заход
пустым — двигать нечего — и не клал события, а `factory goto` всё равно печатал «курсор
возвращён» и отвечал успехом. Кокпит показывал успех, человек шёл дальше, указания не было
нигде. Но возврат несёт ДВЕ вещи, курсор и указание, и вторая от положения курсора не
зависит: «перейти сюда» на текущем узле — основной путь, именно так к этапу и прикладывают
решение. Теперь гасится только настоящий повтор — тот же узел, состояние `ready` и **ровно
то же** указание, ещё не отработанное коммитом (как в `prepare-pause`); новый текст всегда
ложится событием.

**Коммит восстановления.** Подъём после обрыва снимает активную инструментацию, а
диагностический узел (`diagnose`, `hyposkeptic`, `proof`) стоял именно на ней, поэтому
`route_v2_recover_instrumentation` закрывает его `failed` и маршрут уводит на `instrument`
за новой разметкой. Узел при этом никто не исполнял, а указание снимал первый же коммит —
и получалась петля: человек прикладывает решение, жмёт «продолжить», подъём закрывает узел
за отсутствующую разметку, и обратно узел входит уже без решения. Такой коммит теперь
помечен константой `RECOVERY_COMMIT_REASON` (кроме неё `reason` у commit разрешён только
для человеческого `rejected`), `attempt_stage_state_commit_v2` берёт
метку восьмым аргументом, а `human_rewind_note` такой коммит пропускает — указание доживает
до настоящего захода.

**Форма причины и названный отказ.** Причина (`--reason` у `goto`, `abandon`, `recover`;
она же у `pause`) — 1..20000 символов, переводы строк РАЗРЕШЕНЫ, прочие управляющие
символы (в том числе `\r` и табы) — нет: она ложится в доверенный журнал и едет
в промпт агента как есть, абзацами и разметкой. Правило живёт ровно в одном месте,
`_attempt_state_reason` (`lib/attempt-state.sh`), и **отказ обязан называть нарушенную
границу**: сколько символов пришло против допустимых, либо позицию управляющего символа.
Молчащий код 2 неотличим от отказа ledger — человек ищет причину в состоянии попытки,
а не в своём тексте (та же болезнь была у вердикта этапа, см. `stage-result` ниже).
`bin/factory` зовёт проверку **сразу после загрузки библиотеки**: до локов, до профиля
и до единой строки в журнале, чтобы лишние символы стоили ноль. Кокпит показывает
человеку именно этот текст движка (`routeMessage` в `server/src/lib/factory-route-cli.js`),
второй копии границ на стороне сервера нет и заводить её не нужно.

**Почему 20000 и почему многострочно.** Первая редакция границы была «ОДНА строка до 500
символов, разбор — в файл, в причину — ссылка». На живом прогоне это оказалось ложной
экономией: агент файл по ссылке НЕ читает, если в промпте нет прямого приказа его открыть, а
человек, возвращая узел, пишет именно разбор — с перечнем файлов, запретами и числами. Текст
молча резался (движок схлопывал `\n` в пробел, кокпит рубил по 500), и агент получал огрызок
первого абзаца, по которому достраивал остальное сам. Потолок поднят до 20000 символов:
`MAX_ARG_STRLEN` ядра — 128 КБ на аргумент и на переменную окружения, а 20000 кириллических
символов в UTF-8 — это 40 КБ, троекратный запас до жёсткой границы. Переводы строк разрешены,
потому что указание человека — это структурированный текст, а не ярлык; остальные управляющие
символы по-прежнему отклоняются поимённо (`\r` из редактора ронял `goto` уже после набора).
Переполнение — **явный отказ, а не обрезка**: молчаливо укороченный приказ хуже отвергнутого.
Реестр `t<TASK>.pipeline` построчный и парсится awk, поэтому туда кладётся выжимка на 300
символов (`_gate_comment_digest` в `bin/factory`) — источник истины остаётся в журнале.

Из-за этого пришлось поправить идемпотентность коммита. Она существует ради одного случая:
событие легло в журнал, процесс умер до того, как увидел успех, и повтор не должен положить
второе. Ключ — `lastCommit` (узел + исход), а он переживал `human-rewind`, и переигранный
узел с **прежним** исходом события не клал: курсор не двигался, диспетчер видел тот же узел
готовым и гонял по нему агента до потолка шагов. Человек жмёт «перейти сюда» как раз на
только что закрытом узле, так что путь основной. `prepare-commit` теперь пропускает
идемпотентность, если по узлу есть непогашенный `human-rewind`; после нового коммита узла
возврат перестаёт быть свежим, и настоящий переигрыш умершего процесса гасится как прежде.
Маршрутный `rewind` (отказ ворот) сюда не относится и не менялся: там `lastCommit` указывает
на сами ворота.

**Сигналы демону.** TERM/INT обрабатывает route launcher: сначала снимает собственный
trap, затем через trusted runner identity останавливает exact process group активного
узла и только после доказанной quiescence восстанавливает instrumentation. Если identity
или cleanup нельзя доказать, попытка получает `STALLED_HUMAN=1`, а baseline и shared lease
не освобождаются молча.

**Trusted identity раннера.** Публичная идентичность живого запуска — файл
`${FACTORY_CONTROL_ROOT}/runner-processes/t<TASK>.active` (SCHEMA=1, ровно 11 строк:
TASK/STAGE/RUN_ID/EPOCH/RUNNER/PID/PGID/SESSION/STARTTIME/STATE). Публикация требует
доказанной setsid-изоляции (`PID==PGID==SESSION`) и сверки с живым `/proc` по четырём
полям (pgid, session, starttime, state); каталог 700, файл 600, symlink запрещены.
`factory <task> runner switch` читает ТОЛЬКО этот файл — provider-writable `meta.env`
сохраняет PID/PGID/STARTTIME лишь как диагностику и перенаправить сигнал не может.

Гашение — всегда СЕССИЯ раннера целиком (TERM → CONT → grace → KILL по каждой
группе процессов сессии) с re-check идентичности. Порядок TERM → CONT, а не
наоборот: остановленному на барьере раннеру сигнал ставится в очередь и
доставляется в момент разморозки, иначе между CONT и TERM он успевает вызвать
provider CLI мимо барьера. На интервал fork → publish
сигналы TERM/INT откладываются и переигрываются после барьера. Граница именно
сессия, а не группа лидера: GNU `timeout` вокруг provider CLI делает себе
`setpgid`, поэтому дерево агента живёт в другой группе той же сессии — пока
проверка смотрела на группу лидера, «группа пуста» ложно доказывало тишину, и
launcher мог снять identity под живым агентом: claude, MCP и docker переживали TERM.
Собственная сессия под сигнал не попадает никогда.
Порядок проверок в `_runner_runtime_present` менять нельзя: сначала дешёвый
`kill -0` по группе лидера и только на пустой группе — скан сессии по `/proc`
(один форк awk, ~30 мс). Скан впереди `kill -0` стоил ~0,25 с на КАЖДЫЙ опрос, и
хвост этапа с циклами ожидания уезжал за секунды — так падал
`core-multi-runner` на границе human-stall. Цикл ожидания по той же причине
сначала спрашивает уже известные группы и платит за скан, лишь когда они
опустели. Коды: 73 — identity mismatch/чужой lock,
76 — не изолирован или живая чужая запись, 78 — повреждённое/небезопасное состояние.

**Скан сессии не имеет права молчать.** Файлы `/proc/<pid>/stat` открываются
внутри awk через `getline`, а не передаются ему в argv: процесс, исчезнувший
между globом и открытием, для awk (и gawk, и mawk) — «критическая ошибка», после
которой он обрывает обработку целиком и не печатает НИЧЕГО. Одного такого
процесса на живой машине хватало, чтобы скан объявил непустую сессию пустой, —
то есть ровно то ложное доказательство тишины, ради которого скан и написан.
При `getline` исчезнувший pid просто пропускается.

**Чтение и снятие identity.** Запись читается по ОДНОМУ открытому дескриптору:
доверие (владелец, права 600, ровно одна жёсткая ссылка) проверяется через
`stat -L /proc/self/fd/N`, содержимое берётся оттуда же. Через путь получалась
TOCTOU: `stat` подтверждал один inode, а `mapfile` читал другой, который
конкурентный publish уже подменил. Исчезновение записи — штатная часть протокола,
а не подмена: отсутствие файла и `nlink == 0` дают 3 («активной identity нет»),
78 остаётся за действительно недоверенным состоянием. Снятие идемпотентно —
уборщиков двое, launcher (раннер умер) и оператор (`runner switch` погасил того
же раннера), они регулярно встречаются на одной записи, и проигравший гонку
обязан отвечать успехом. Пока это считалось ошибкой, CLI отчитывался о провале
состоявшегося переключения, а launcher ловил `group_rc` и подменял результат
этапа на 76 (`core-multi-runner` краснел под нагрузкой 5 прогонов из 24).

## Lifecycle, provider lineage и runtime usage

### Authority и иерархия

Для каждой immutable route-attempt движок ведёт host-owned lifecycle под
`${FACTORY_CONTROL_ROOT}/protocol-v2/tasks/t<TASK>/attempts/<ATTEMPT_ID>/lifecycle/`.
Provider-writable `events.jsonl`, run-каталог и `meta.env` не являются authority причин,
spans, связей или usage. Каноническая вложенность одинакова для engine, server и export:

```text
Task
  RouteAttempt
    OrchestratorSession
    NodeVisit
      NodeExecution
        Dispatch
          RunnerRun
      GateWait
      HumanIntervention
    SandboxSpan
    BootstrapSpan
    CleanupSpan
```

Новый `NodeVisit` создаётся на каждый вход cursor в узел. Его `visitReason` — ровно одно
из `initial`, `forward_transition`, `route_rewind`, `gate_rejected`, `human_rewind`,
`recovery`. Product retry остаётся в том же visit, но создаёт новый `NodeExecution` с
`executionReason`: `initial`, `no_result`, `product_failure` или `manual_resume`. Один
execution может иметь несколько dispatch/run; реально стартовавший provider process
получает `runReason`: `primary`, `provider_failover`, `model_fallback` или
`manual_switch`. Пропущенный dispatcher candidate — событие dispatch, но не `RunnerRun`.

Started/finished одной сущности используют один `spanId`; длительность того же процесса и
boot считается monotonic clock, допустимое восстановление помечается `wall`/`derived`.
Причины и исходы — closed enums из
[`lifecycle-event.schema.json`](../../schemas/analytics/lifecycle-event.schema.json).
Свободный prompt, комментарий или reason в ledger не копируется: при необходимости событие
содержит bounded code и SHA-256 исходного evidence. Provider result не подменяет trusted
`NodeExecution.productOutcome`.

Stage ledger остаётся authority перехода cursor. Lifecycle ссылается на exact
`stageEventHash` и stable `transitionId`; writable start/resume вызывает
`runtime_lifecycle_reconcile_routing_v2`, который после полной проверки stage chain
добавляет пропущенный `routing_transition_reconciled` с исходным временем и
`clock.fidelity=derived`. Process span из такого перехода не выдумывается.

### Сегментированный lifecycle-журнал

`manifest.json` выбирает ровно одну generation: последовательность immutable sealed
segments и один `segments/active-<generation>.ndjson`. `tail.json` — проверяемая быстрая
проекция, не отдельный источник истины; `quarantine/` хранит content-addressed torn bytes,
`usage/` — immutable usage documents. Каталоги принадлежат host user и имеют mode 0700,
файлы состояния — 0600; symlink, лишняя hardlink, non-canonical path и mixed writer
отвергаются fail-closed.

Каждая canonical NDJSON-запись проходит общую schema и hash chain
`sequence → previousEventHash → eventHash`. `eventId` даёт идемпотентный append только при
тех же canonical bytes; та же identity с другим payload — конфликт. Initial publication и
rotation соблюдают полный durability barrier:

```text
fsync(segment) → fsync(segments directory) → fsync(manifest temp)
→ rename manifest → fsync(lifecycle directory)
```

Manifest не выбирает generation до durable directory entry сегмента. Reader никогда не
чинит состояние: torn active tail возвращает 74. Следующий exclusive writable append
сохраняет повреждённые bytes в `quarantine/`, публикует новую generation и первым событием
фиксирует `lifecycle_tail_recovered`; полностью подтверждённые события не теряются и не
дублируются.

Стабильная shell API ledger-а:

```text
attempt_lifecycle_init_v2 TASK ATTEMPT_ID
attempt_lifecycle_append_v2 TASK ATTEMPT_ID EVENT_DRAFT_JSON
attempt_lifecycle_read_v2 TASK ATTEMPT_ID
attempt_lifecycle_validate_v2 TASK ATTEMPT_ID
attempt_lifecycle_canonical_v2 INPUT_JSON
attempt_lifecycle_event_hash_v2 EVENT_JSON
```

Первые четыре операции — production storage API; последние две — conformance helpers.
Draft уже содержит весь common envelope и exact per-kind `details`, кроме writer-owned
`sequence`, `previousEventHash`, `eventHash`; успешный append печатает принятый hash.
Host-модули не собирают envelope вручную: они задают context через
`runtime_lifecycle_set_context_v2`/`runtime_lifecycle_set_route_v2` и вызывают typed
begin/finish helpers из `runtime-analytics.sh`. Восстановление crash gaps имеет отдельные
идемпотентные границы `runtime_lifecycle_previous_open_session_v2`,
`runtime_lifecycle_reconcile_routing_v2` и `runtime_lifecycle_reconcile_usage_v2`.

**Попытка старше самого ledger-а не получает историю задним числом.** Первым событием
журнала обязан идти `route_selected`: до него схема запрещает любое событие со scoped
route identity. Поэтому `resume`, `goto` и `abandon` попытки, у которой в журнале нет
ни одного события, открывали бы сессию заведомо невалидной и падали кодом 78
детерминированно, то есть человек терял и продолжение прогона, и снос стенда.
`v2_lifecycle_begin_session` в режиме `resume` такую попытку распознаёт
(`v2_lifecycle_ledger_empty`: `rc=0` и ноль строк — пусто, ошибка чтения остаётся
ошибкой) и просто не открывает сессию: все typed-события стоят за
`runtime_lifecycle_enabled_v2`, поэтому невыставленный context означает «не пишем
ничего», а не «половина журнала». Придумывать `route_selected` с несуществующим
временем выбора запрещено — выдуманная аналитика хуже отсутствующей.

### Provider lineage и launch barrier

Native resume имеет отдельную CAS authority под
`${FACTORY_CONTROL_ROOT}/protocol-v2/provider-lineage/schema-1/<PROVIDER>/<SCOPE_SHA256>.json`.
Raw provider scope никогда не становится частью пути. Canonical record проходит состояния:

```text
advanced → reserved_before_start → started → advanced
                              ↘ cancelled_before_start
                                      started → blocked_after_start
```

`cancelled_before_start` разрешён только с доказательствами `neverReleased` и quiescence.
После `started` predecessor checkpoint считается потреблённым: ни сбой child, ни повтор
команды не разрешает использовать его ещё раз. Полный eligible child checkpoint переводит
lineage в следующую `advanced` generation; иначе запись становится
`blocked_after_start` и требует явного разрешения причины.

CAS API принимает strict request JSON из
[`provider-lineage.schema.json`](../../schemas/analytics/provider-lineage.schema.json):

```text
provider_lineage_initialize_advanced_v1 REQUEST_JSON
provider_lineage_reserve_v1 REQUEST_JSON
provider_lineage_mark_started_v1 REQUEST_JSON
provider_lineage_advance_v1 REQUEST_JSON
provider_lineage_cancel_v1 REQUEST_JSON
provider_lineage_block_v1 REQUEST_JSON
provider_lineage_read_v1 PROVIDER THREAD_ID
provider_lineage_validate_v1 PROVIDER THREAD_ID
provider_lineage_scope_canonical_v1 PROVIDER THREAD_ID
provider_lineage_scope_hash_v1 PROVIDER THREAD_ID
provider_lineage_record_path_v1 PROVIDER THREAD_ID
```

`runner-launcher.sh` не запускает provider до trusted commit. Для native resume порядок
неизменен: проверить exact predecessor usage/checkpoint и CAS-записать
`reserved_before_start` → fork child в новой setsid-сессии, остановленной `SIGSTOP` до
adapter-а → проверить/publish PID, PGID, session и starttime → append+fsync
`runner_started` → CAS `started` → `SIGCONT`. Fresh invocation проходит тот же identity и
lifecycle barrier без reservation. Любая ошибка до `SIGCONT` quiesce-ит ещё остановленную
сессию; после durable `runner_started` она дополнительно получает `runner_abandoned`.
`runner_finished` допустим только после доказанной quiescence всей process session.

`factory ... resume` возобновляет route orchestration и сам по себе не означает provider
resume. Adapter вправе объявить capability `native_resume_v1` только если его `run`
fail-closed соблюдает `FACTORY_PROVIDER_SESSION_MODE=fresh|resume` и при `resume` передаёт
CLI exact `FACTORY_PROVIDER_RESUME_SCOPE`. Generation и immutable parent citation приходят
в `FACTORY_PROVIDER_LINEAGE_GENERATION` и `FACTORY_PROVIDER_PARENT_USAGE_REF`; adapter их
не меняет и не пишет lineage store. Текущие Codex/Claude adapters capability не объявляют
и всегда фиксируются как `fresh`; resume-ветка становится достижимой только вместе с
отдельно проверенным invocation contract конкретного CLI.

### Retained-FD usage и diagnostic meta mirror

До fork launcher через retained run dirfd создаёт новый `events.jsonl` с
`O_CREAT|O_EXCL|O_NOFOLLOW`, mode 0600 и `nlink=1`, затем до конца run удерживает исходные
read/write descriptors. После quiescence host fsync-ит retained write fd, bounded-читает
тот же inode через retained read fd, считает SHA-256 и повторно сверяет fstat обоих fd и
lstat имени. Finalizer никогда не reopen-ит provider-writable path. Подмена имени,
symlink/FIFO, mutation, oversize или identity mismatch дают named conflict и не позволяют
прочитать новый target как расход старого запуска.

Внутренний launcher-only bridge `runtime-usage.mjs` имеет точные операции:

```text
prepare CONTEXT_JSON                         # retained events fds 7/8 и run dirfd 9
invalidate PREPARED_JSON DIAGNOSTIC_CODE
publish CONTEXT_JSON PREPARED_JSON           # run dirfd 9
reconcile-plan CONTROL_ROOT TASK ATTEMPT LIFECYCLE_NDJSON [RUN_ID]
meta CONTEXT_JSON initial                    # run dirfd 9
meta CONTEXT_JSON final [PREPARED_JSON|-] [RESULT_CLASS]  # run dirfd 9
```

Нормализованный документ публикуется по адресу
`lifecycle/usage/<RUN_ID>.json` настоящей операцией publish-if-absent: одинаковые
канонические байты идемпотентны, разные байты/хеш — конфликт неизменяемости, перезапись
запрещена. Порядок коммита:
`runner_scope_bound` → долговечный `runner_finished` → неизменяемый usage-документ →
`runner_usage_recorded` (либо закрывающий разрыв после падения `runner_usage_reconciled`) →
продвижение lineage → диагностическое зеркало. Документ сохраняет точную идентичность
всей цепочки, запрошенную/разрешённую модель, отпечаток источника, полноту/происхождение,
scope сессии провайдера, неизменяемый `parentUsageRef`, пригодность checkpoint/resume и
отдельные usage-сегменты.

`meta.env` публикуется последним целиком через retained dirfd: unique 0600 temp, fsync,
rename и directory fsync. Symlink/FIFO target не открывается и не изменяется. Его
`USAGE_SCHEMA=2`, token/cost-поля и process identity — только удобная diagnostic projection
для старых readers; authority usage — immutable document плюс lifecycle link. Отсутствие
usage означает missing, не ноль. Cache read, 5-minute write, 1-hour write и write с
неизвестным TTL не сливаются в одно тарифицируемое число.

## Бандлы маршрутов v2

Server публикует route и catalog как content-addressed каталоги
`revisions/<sha256(manifest)>`. Engine не доверяет HTTP-ответу или имени каталога:
`factory-route` повторно проверяет типы файлов, отсутствие symlink/лишних каталогов,
manifest/hash/size, строгую schema, достижимость, переходы, owner↔status и все prompt-ссылки.

Catalog содержит точные route hashes и bootstrap Scout. Рендерер принимает только JSON
context, проверяет обязательные корневые секции, отклоняет secret-shaped поля и добавляет
их как ограниченные hash-секции данных. Условия prompt-блоков поддерживают только
`context.path == JSON scalar`; произвольных выражений и shell нет. Golden-тест фиксирует
точный детерминированный core рендера. Run-specific команды `stage-result` и
`stage-progress` по-прежнему добавляет `multi-runner.sh` последним блоком непосредственно
перед запуском provider-а.

У каждого исполняемого узла `id` точно равен `runKey.toLowerCase()`, а `timeoutClass`
принадлежит известному движку набору. Наличие канонического `ship` включает
`delivery.mode=publish`; его отсутствие включает `disabled` и запрещает delivery-capability
в остальных узлах. Поэтому маршрут анализа может завершиться через собственный tail без
пустых targets или фиктивного SHIP.

`current.json` читается только при создании новой попытки. После pin все команды получают
явный `catalogHash`; route hash выбирается только из этого каталога. Единственный launcher
исполняет только опубликованные route bundles: legacy prompt hooks и fallback на профильные
массивы этапов удалены.

Trusted-журнал попыток отделён от отображаемой runtime-проекции `state/tNN.pipeline`:

```text
${FACTORY_CONTROL_ROOT}/protocol-v2/tasks/t<TASK>/
  protocol.json
  active-attempt.json
  attempts/a_<id>/
    attempt.json
    pins.json
    route-pin.<sha256>.json
    terminal.<sha256>.json
```

`attempt_state_begin_v2` один раз закрепляет catalog и bootstrap Scout,
`attempt_state_select_route_v2` один раз выбирает route только из этого catalog.
`resume` всегда перечитывает и проверяет закреплённые bundle, а не новый `current`.
Успешный `finish` разрешён только после route pin; `abandon` допустим и в bootstrap.
Recovery создаёт новую attempt с новым catalog pin и явной ссылкой на abandoned attempt.
Оператору обе операции доступны как `factory TASK abandon|recover --attempt …
--reason …` (recover дополнительно требует `--route` и сразу пинит его — попытка без
route pin была бы тупиком для resume); обе берут lock оркестратора задачи, поэтому
под живым foreground-прогоном получают отказ, а не режут попытку под ним.
Про форму `--reason` и то, почему отказ по ней называет границу, — «Форма причины
и названный отказ» выше.
Хранилище опубликованных бандлов по умолчанию — `~/.factory/routes`; сервер публикует
туда же через `COCKPIT_ROUTES_DIR`.

Ретраи исполняет доверенный рантайм по контракту бандла. Попытки без результата
повторяются в пределах суммы бюджетов `retry.noResult` и
`retry.providerFailure.attempts`: no-result и провайдерский сбой на этой границе
неразличимы, потому что multi-runner уже исчерпал failover-цепочку ВНУТРИ
`run_agent` (обязательный coverage из `runners.env` — это и есть runner-failover).
Committed `failed` повторяется только в пределах `productFailure`. Исчерпание
бюджета — синтетический исход `exhausted`, его вырабатывает рантайм, агент
сообщить его не может. Перед таким коммитом host закрывает оставшийся без результата
run-state как `failed`: exact run id/epoch сохраняются для fencing, но этап больше не
остаётся ложным `running` на доске. Остановка `stop=human` с таким исходом не требует
разбора: раннер результата не зафиксировал (лежал провайдер или окружение), а бюджет
повторов локален заходу в узел — новый диспетчер заводит его заново. Поэтому `resume`
из такой остановки сам возвращает курсор на узел доверенным `human-rewind`
(«продолжение после исчерпанного бюджета повторов»), не требуя отдельного `goto`:
нажатие «продолжить» и есть решение человека переиграть узел, и журнал фиксирует его
тем же событием, что и возврат кнопкой. Остановки `rewind-limit`/`no-progress` и исход
`failed` так не обнуляются — они по-прежнему ждут явного `goto` с новой гипотезой. Agent-узел с `parallel/N` допустим только при
`filesystem=state-only`: native-capable runner получает требование поднять N независимых
read-only ветвей, а `degrade=allow-single` разрешает runner-у без native fanout выполнить
их последовательно в одном запуске. `degrade=forbid` в таком случае останавливает попытку
fail-closed до запуска. `executor=command` исполняет только allowlisted hook профиля,
единожды и с `fanout=single`; shell из route bundle не исполняется. Пока не реализована
только стратегия повторов `same-runner`, она также отклоняется
`_route_v2_node_caps_guard` до запуска.
После runner-а и `state-only` guard диспетчер вызывает необязательный evidence hook профиля
с точным `runId`. Его отказ коммитится как продуктовый `failed`: это позволяет машине
остановить недоказанный coverage у человека без бессмысленного no-result retry.
Доверенный результат hook хранится под control-каталогом конкретной immutable attempt;
provider-writable файлы в `STATE_DIR` остаются только отображаемыми копиями. Так поздний узел
не может незаметно переписать уже принятую матрицу линзы, а новая попытка той же задачи не
подхватывает evidence предыдущей.
Active pointer меняется под kernel `flock` и compare-and-swap. `factory` принимает resume
только с exact immutable attempt; исторический реестр без такого pin остаётся read-only.
`FACTORY_CONTROL_ROOT` создаёт trusted host; provider adapters не получают его как
`--add-dir` или writable state root.

### Что заморожено, а что живое

В попытку замораживается только опубликованный bundle. Live-компоненты применяются по своим
границам и не становятся частью pin автоматически:

| Слой | Где лежит | Когда перечитывается |
|---|---|---|
| Движок | `engine/bin`, `engine/lib` | при каждом запуске процесса |
| Профиль | `profiles/<имя>/profile.sh` | перед каждым этапом (`_reload_profile`) |
| Runner policy | `profiles/<имя>/runners.env` | при каждом routing decision; во время активного прогона не менять |
| Server / web | `server/`, `web/` | после сборки и человеческого рестарта процесса |
| Исходник схемы | `profiles/<имя>/routes/` | сам по себе ни на что не влияет; нужен publish CAS |
| Схема (маршрут) | `~/.factory/routes/<профиль>/` | **никогда** — берётся по пину попытки |
| Состояние задачи | `state/tNN.*`, `protocol-v2/tasks/tNN/` | своё на задачу, кодом не управляется |

Публикацию делает `publish.mjs` профиля (или сервер). Она валидирует исходник, считает
sha256 всего бандла и кладёт его в `catalog/revisions/<хеш>/`. Хеш не назначается версией —
он ВЫЧИСЛЯЕТСЯ из содержимого: одинаковый исходник даёт тот же каталог и не плодит ревизию,
любая правка даёт другой каталог, а старый остаётся нетронутым. Ревизии не дублируют друг
друга по задачам и занимают только объём уникальных бандлов.

У публикации два независимых эффекта, и путать их не надо:

1. **новая ревизия** — это защита УЖЕ ИДУЩИХ попыток: их каталог никто не переписывает;
2. **сдвиг `current.json`** — это раскатка: с него новые попытки начнут брать новое.

Попытка не копирует схему себе, она записывает две ссылки: `pins.json` (`catalogHash`) и
`route-pin.<sha256>.json` (`routeId` + `routeHash` + `selectedAt`). Имя pin-файла — sha256
его собственного содержимого, поэтому подмена видна без обращения к чему-либо внешнему;
рядом лежат `pins.sha256` и `attempt.sha256` тем же приёмом. Дальше каждый узел читает
промпт из хранилища по этому пину, а каждый переход сверяется с `catalogHash` попытки и
отказывает при расхождении. Подменить схему под работающим прогоном нельзя даже намеренно.

Практические следствия, за которые уже платили временем:

- **правка схемы не догоняет запущенное.** Ни `resume`, ни `goto` каталог не перечитывают;
  `current.json` открывается только в режимах `check` и `start`. Хочешь новые промпты —
  нужна новая попытка, старой они не достанутся никогда;
- **`goto` дешевле, но остаётся на старой схеме.** Он двигает курсор ВНУТРИ попытки:
  сбрасывает целевой узел и весь хвост маршрута после него, сохраняя результаты пройденного
  начала. Годится, когда надо переиграть узел, а не проверить новую схему;
- **`recover` берёт текущий каталог, но начинает с чистого bootstrap.** Новая попытка пинит
  `current` в момент создания (`_attempt_state_create_locked` читает его сам) и наследует
  только ВХОДНЫЕ контракты предшественницы — ticket, delivery, scope, diagnosis. Результаты
  работы (`bootstrap.json`) намеренно не переносятся, поэтому цепочка идёт заново со SCOUT.
  Требует, чтобы предыдущая попытка была `abandoned`.
  Заодно `recover` **вычищает диск под новую попытку**: выходы этапов из namespace задачи
  (`<state>/t<TASK>.*`, кроме движковых `active/env/instrumentation/lock/orch.log/pipeline/
  pipeline.lock/route`) уезжают в `attempts/<предшественница>/state-artifacts/`
  (`attempt_state_quarantine_artifacts_v2`), а реестр переинициализируется в `pending`
  по узлам ЗАКРЕПЛЁННОГО маршрута новой попытки. Без этого «чистый bootstrap» врёт:
  CLI отказывается перезаписывать файл, который в этой сессии не читал, поэтому SCOUT может
  принять чужой `t<TASK>.recon.md` за свой и закрыть этап `done`, а PLAN — обойти отказ
  склейкой и приклеил к свежему плану хвост прошлой попытки с разделами
  SKEPTIC/TRANSLATOR/TCRITIC, а сам PLAN до этого прочитал в реестре `TESTS=done`
  от отменённой попытки и пошёл искать несуществующие тесты;
- **workspace mode закреплён в попытке.** В `isolated` профиль создаёт отдельные worktree и
  task-стенд своим `up.sh`; engine проверяет непересечение source/worktree. В `shared`
  source и workspace обязаны быть одним canonical primary checkout, а stand — заранее
  существующим внешним ресурсом. Engine не вызывает `up.sh`/`down.sh`, не создаёт и не
  удаляет worktree/container/volume и держит durable lease всех объявленных
  `profile/workspace/stand/gpu` ресурсов до completion или успешного `abandon`.

## Файловые политики

`state-only` контролируется exact before/after guard: HEAD, worktree,
index, tracked/untracked content, symlink targets и объявленные sensitive ignored-файлы.
Расхождение приводит к human stall; общего autorevert нет.

`transactional-write` предназначен для временной инструментации: host заранее фиксирует file
scope, проверяет отсутствие изменений вне него, сохраняет ожидаемый checkpoint и при cleanup
восстанавливает только transaction-owned файлы. Несовпавший CAS оставляет чужую правку
нетронутой и останавливает попытку.

Instrumentation contract выводится только из закреплённой машины, не из route id. Наличие
транзакционного узла `instrument` задаёт режим `explicit`: `start` обязан получить хотя бы
один `--instrumentation-file`, и тот же immutable scope используется до `proof`. Прочий
исторический `transactional-write` получает режим `derived` и строит scope из уже сделанного
diff перед короткой транзакцией; маршрут без таких узлов имеет режим `disabled` и явный scope
не принимает. `factory check --route …` печатает этот режим как `instrumentation=…`, чтобы
Cockpit мог fail-closed сверить свой опубликованный каталог с движком. Переименование маршрута
не меняет ни один из этих режимов.

**Одна транзакция на пару instrument→proof — и запрет возврата внутрь неё.** `instrument`
открывает транзакцию и намеренно не закрывает (`_route_v2_transaction_after` пропускает cleanup
ровно для него), `proof` работает внутри и закрывает за собой. Отсюда следствие, которое стоило
трёх сожжённых заходов подряд: после первого прохода `proof` активной транзакции нет, а
`_route_v2_transaction_before` для `proof` при её отсутствии отдаёт 78 — открыть свою значило бы
мерить дерево без инструментации. Возврат курсора на любой узел МЕЖДУ `instrument` и `proof`
(chairman, скептик, консилиум) `instrument` не переигрывает: `goto` режет `chain[index:]`, а он
левее. Маршрут после такого возврата исполним быть не может в принципе — и узнавал об этом
человек через 10-12 минут работы промежуточных узлов вхолостую, по молчаливому коду 78.

Поэтому отказ перенесён на момент решения: `_route_v2_goto_transaction_guard` проверяет зону
при `goto` и отказывает кодом 75 сразу, называя оба выхода — переиграть от `instrument` (ценой
всего хвоста за ним) либо вернуть за `proof`. Fail-closed у самого `proof` при этом сохранён:
гард закрывает штатный путь, а не подменяет проверку. Возврат на сам `instrument` разрешён — он
открывает транзакцию заново.

Guard не заменяет host sandbox. Рабочий запуск `state-only` запрещён, пока выбранный
runner физически сохраняет source roots writable.

Для Claude trust boundary держат флаги запуска, а не список разрешённых версий CLI:
runner принимает только owner-only `0400` settings из `CONTROL_DIR`, а сам control tree
помещает в tool-level `Read/Edit/Write/NotebookEdit` deny. CLI запускается с пустым
`--setting-sources`, `--strict-mcp-config` без MCP config и `--disable-slash-commands`;
`--bare` не используется, поэтому штатная OAuth/keychain авторизация сохраняется.
`--safe-mode` снят намеренно: агентам конвейера нужна память проекта (CLAUDE.md с
@-импортами знаний) из worktree — hooks, плагины, skills и произвольные MCP при этом
остаются закрытыми перечисленными флагами. `runner_claude_probe` требует от CLI лишь
разборчивый номер версии: он уходит в телеметрию запуска.

**Соблюдает ли флаги живой бинарь, проверяет smoke, а не allowlist.** Прежде границу
сторожил перечень аудированных версий в probe, и он оказался дорогим ритуалом: дописывать
его приходилось руками на каждое обновление, до правки regex весь конвейер стоял
`runner_preflight_unavailable`, а доказывал он только то, что кто-то однажды прогнал
эксперимент вручную. Эксперимент теперь автоматизирован —
`tools/claude-contract-smoke.mjs` поднимает временную фикстуру с hooks
(`SessionStart`/`UserPromptSubmit`), `.mcp.json`, `CLAUDE.md` и приватным `--settings`,
делает три коротких хода установленным CLI и проверяет шесть инвариантов: без изолирующих
флагов маркеры обязаны появиться (иначе проверка недействительна), `--strict-mcp-config`
глушит MCP и не трогает hooks, а полный набор раннера закрывает hooks и MCP, оставляет
память проекта и сохраняет действие переданного `--settings`. Вердикты — `CONTRACT_OK`,
`CONTRACT_BROKEN`, `INVALID_FIXTURE` (коды возврата 0/1/2). Гонять после обновления CLI и
периодически; в offline suite он не входит, потому что ходит в реальную модель.
Юнит-тест `tests/engine/unit/claude-runner-sandbox.sh` подменяет claude фейком и по
устройству отвечает на другой вопрос — какие флаги мы ПЕРЕДАЁМ.

**Native OS sandbox временно снят — и вот почему.** Обязательный блок
`"sandbox":{"enabled":true,"failIfUnavailable":true,"allowUnsandboxedCommands":false,…}`
в engine-owned settings на Linux означает bwrap, то есть user namespace, где отображены
только uid/gid запускающего. Следствий два, и оба смертельны для рантайм-этапов:
дополнительные группы теряются, поэтому `/var/run/docker.sock` (`root:docker 0660`) виден
агенту как `nobody:nogroup` и недоступен; сеть уходит в свой namespace, поэтому порт стенда
на хостовом localhost отвечает «в соединении отказано». Рантайм-этапы ходят в стенд ровно
этими двумя каналами. В одном прогоне это выглядело как провал REPRO с пустым результатом: агент
прочитал код и записал гипотезу, но не снял ни одного объективного сигнала, а
`allowUnsandboxedCommands:false` закрывал и escape-hatch (`dangerouslyDisableSandbox`).
Читающие узлы (SCOUT) при этом проходили, поэтому регрессия и не была видна сразу.

Обратно границу можно вернуть только вместе с каналом до стенда:
- прокси перед `docker.sock` от своего uid + `allowAllUnixSockets` (per-path
  `allowUnixSockets` в этом CLI — macOS-only, seccomp не фильтрует по пути), заодно сузив
  API до контейнеров своей задачи; доступ к порту стенда снаружи придётся заменить на
  `docker exec … curl` изнутри контейнера, либо разбирать `allowedDomains`-прокси;
- либо sandbox по классу узла из бандла маршрута: жёсткий для `state-only`, снятый для
  рантайм-классов.

Пока этого нет, раннер не заявляет capability `sandbox`. Валидатор settings при этом
сохранён наполовину: блока `sandbox` может не быть вовсе, но если он объявлен — обязан быть
прежней аудированной формой (hard-fail при недоступности, без `excludedCommands` и
`allowRead`). Имитация границы хуже её честного отсутствия. Тест
`tests/engine/unit/route-agent-permissions.sh` падает при возврате блока — это напоминание
вернуть канал вместе с ним.

**Составную команду CLI решает по самой слабой части, и это стоило 1240 отказов.**
Замер по журналам всех прогонов 26.08.2026: отказ политики Bash встречается хотя бы раз в
89% заходов, 88% отказов — составные команды. Первые по частоте блокирующие куски: `echo`
(1178) и `cd` (357), то есть ровно то, что само по себе ничего не делает. Из-за этого
отказывали и `git status --short && cd … && git status` целиком (хотя все части нужного
типа разрешены), и **собственный `stage-result.sh` движка — 33 раза**: агент дописывал в
хвост `; echo "EXIT=$?"`. Цена измерена честно и оказалась меньше страшной: все 33 захода
завершились `ok`, агент повторял команду без хвоста. Платили вызовами и токенами, не
узлами.

Опасен не потраченный вызов, а ПОДМЕНА проверки. В живом прогоне агент на отказ ответил
«видимо, скрипт заблокирован политикой, проверю через прямой запуск Python-скриптов» — и
результат другой проверки уехал дальше как требуемое доказательство. Правило «нет
названной замены — фиксируй проверку как не выполненную» в служебном блоке уже стоит, и
этот прогон его нарушил, поэтому у отказа появился машинный признак — `DENIALS_<STAGE>`
(см. «Отказ политики прав виден числом, а не только в потоке» выше).

Поэтому базовый набор получил правки с разной границей:

- **`cd` — всем узлам**: записать он не может ничего;
- **`echo`/`printf` — тоже всем узлам, включая проверяющие.** Сначала их не выдавали
  `state-only`: `echo x > file` префиксным правилом не выражается. Замер показал цену
  запрета: из 1302 отказов прав `echo`/`printf` участвует примерно в 610, и
  перенаправление содержат лишь 12% из них — остальное метки-разделители и хвост
  `; echo "exit=$?"`, валящие составную команду целиком;
- **питон проекта — всем узлам.** В allowlist стоял только системный `python3`, а
  питон-проект живёт в venv: `<repo>/.venv/bin/python` не совпадал ни с одним правилом
  (замер: 33 таких отказа, 28 из них на проверяющем узле). Каталог ищется по факту его
  существования в `PROFILE_AGENT_DIRS`, а форма `-c` закрывается так же, как у `python3`.

**Рубеж не исчез, а переехал туда, где видно команду целиком** — PreToolUse-хук
`lib/stage-write-guard.sh`, который ставится ТОЛЬКО на `state-only` узлы и получает
каталог состояния аргументом. Он отказывает по цели перенаправления: разрешены `/dev/null`,
дублирование дескриптора, каталог состояния (там лежат отчёт и черновик хода) и временный
каталог, всё остальное — отказ до исполнения. Хук строже прежнего правила, потому что
ловит запись ЛЮБОЙ командой: замер по 3265 живым командам проверяющих узлов дал 8
срабатываний на ранее прошедших командах, и 7 из них — настоящие
`git show HEAD:… > <worktree>/файл`, то есть оплаченный инцидент из
`../cockpit/gotchas.md`. Молчание хука означает «решает обычный список прав»; любой сбой
разбора превращается в отказ — сломанный сторож обязан быть громким, иначе он молча
вернул бы дыру, ради которой написан.

Границу хук закрывает не всю и не притворяется, что всю: `awk '{print > "f"}'` пишет файл
изнутри кавычек, и его по-прежнему ловит только посмертный `_guard_readonly`. Хук лишь
возвращает узлу команды, которые и так ничего не пишут.

**Однострочник остаётся запрещён, но опыт разрешён** — `lib/stage-probe.sh`. Он выполняет
тот же код (`--lang python|node|php|sh`) в одноразовом каталоге вне рабочего дерева, берёт
питон из venv проекта и снимает дешёвый отпечаток деревьев до и после запуска: дифф рабочей
копии, дифф индекса и список неотслеживаемых путей (замер — 7–9 мс на репозиторий).
Расхождение делает результат опыта недействительным ЦЕЛИКОМ, вместе с выводом, и говорит
об этом словами. Это тот же посмертный сторож, только посмертие занимает секунды вместо
сорока минут работы этапа. Чего отпечаток не ловит, названо прямо: изменение содержимого
уже существующего неотслеживаемого файла — его поймает полный сторож узла, просто позже.

Зачем это понадобилось: в живом прогоне проверяющий узел пять раз подряд пробовал выяснить
форму импорта общего модуля (`python -c "import ..."`), все пять раз получил отказ прав,
эскалировал неразрешённый вопрос БЛОКИРУЮЩИМ замечанием и остановил маршрут у человека.
Человек ответил за три минуты — и ошибся в посылке, потому что отвечал по комментарию в
коде. Проверить было дешевле, чем спросить. Отсюда же правило служебного блока промпта:
**«не смог проверить» не является блокирующим замечанием** — это свойство захода, а не
работы автора, и место такой находке в отложенных.

Границы под тестами `tests/engine/unit/route-agent-permissions.sh` и
`tests/engine/unit/stage-probe-guard.sh`.

Restricted Codex для shared stand не наследует writable control root и не включает network
proxy. Exact `PROFILE_AGENT_CONTROL_DIR` проверяется как canonical owner-only directory mode
`0700`, не пересекающийся с writable `--add-dir`, и добавляется в permission profile только
как `read`. В проверенной shared-конфигурации внутри control dir находятся две FIFO `0600`
и regular lock `0400`: Codex 0.145 на Linux умеет открывать FIFO на запись и брать `flock`
через такой read-only bind. Командный sandbox поэтому работает с `network.enabled=false`;
localhost/TCP, AF_UNIX и Docker socket в agent transport отсутствуют.

**Обёртки команд в deny-листе.** Разрешения раннера сверяются по ПРЕФИКСУ строки, поэтому
любой запускатель отмывает запрет: `timeout git commit …` не совпадает с `Bash(git commit:*)`
и проходит как `Bash(timeout:*)`. На проверочных этапах `_agent_settings` поэтому запрещает
сами обёртки (`timeout`, `env`, `xargs`, `nohup`, `setsid`, `stdbuf`, `nice`, `sudo`,
`sh -c`, `bash -c`) рядом с встроенными интерпретаторами. Это существеннее, чем кажется:
раньше файл этапа ложился поверх личных настроек человека, где `Bash(timeout:*)` мог быть
разрешён «для себя». Claude route runner теперь полностью отключает эти setting sources;
engine-owned deny остаётся самостоятельной политикой. Добавляя обёртку в этот список,
проверяй, не пользуется ли ею сам профиль: запрет действует и на его скрипты.

В `isolated` инструментационная транзакция требует отдельный linked worktree,
эксклюзивно арендованный trusted host-ом. В `shared` primary checkout допустим только при
точно проверенном durable lease всех workspace/stand ресурсов. Lease остаётся занят до
полного cleanup; после восстановления scope профиль обязан синхронизировать существующий
stand и подтвердить health. Ошибка cleanup или post-restore оставляет попытку и lease в
human stall — автоматического освобождения поверх изменённого checkout нет.

**Что попадает в снимок.** Чувствительный список транзакции — это `scope.list`, и только он:
записи по нему нужны cleanup-у, чтобы доказать побайтовое восстановление инструментации.
Правки исходников ловятся не через него — записи `TRACKED_WORKTREE`, `TRACKED_INDEX` и
`UNTRACKED` `workspace_guard` строит прямо из состояния git.

Раньше сюда добавлялись ВСЕ игнорируемые git файлы каждого корня — `node_modules`, `vendor`
и прочий рантайм целиком, в крупном проекте десятки тысяч путей. Это стоило дорого и не
защищало: см. «Почему игнорируемые файлы сняты с наблюдения» ниже. Побочный эффект отмены —
снимок из 72 778 путей превратился в десятки, а он берётся ЧЕТЫРЕЖДЫ за транзакцию (baseline,
checkpoint и дважды в cleanup). Оптимизация, ради которой сбор записей переписывали на один
процесс python (`_workspace_guard_batch_records`, 19 минут → 2 секунды), стала запасом
прочности, а не необходимостью — но выбрасывать её не нужно.

Формат записи при этом обязан оставаться байт-в-байт прежним: снимки сравниваются `cmp`, и
baseline, снятый прошлой версией движка, должен сойтись с checkpoint новой — иначе перезапуск
демона посреди открытой транзакции выдаст ложное нарушение readonly и убьёт живой прогон.
Поэтому sha256, base64 и восьмеричный режим считаются так же, как их считали `sha256sum`,
`base64 -w0` и `stat -c '%a'`, а ветка «ни файл, ни symlink» по-прежнему зовёт
`stat -c '%F:%s:%Y'`: его текст переводится локалью и в python не воспроизводится. Меняя эту
функцию, сверяйся с прежней реализацией на фикстуре со всеми видами записей, а не только
тестом «снимок поймал правку». Нечитаемый файл даёт пустое поле хеша, а не провал снимка:
контейнеры стенда пишут в рабочее дерево от своего пользователя, и прежний конвейер
`sha256sum | awk` вёл себя ровно так же (код возврата брался у `awk`).

**Почему игнорируемые файлы сняты с наблюдения.** Замысел был такой: следить за всем, что
git игнорирует, — иначе агент спрячет правку в `.env`, `vendor` или `node_modules`. На деле
это не защищало и стоило прогонов.

Не защищало, потому что сторож сравнивает ДВЕ ТОЧКИ — `begin` и `checkpoint`. Всё, что
изменили и вернули между ними, для него не существует: чтобы обойти надзор, достаточно
откатить `.env` перед завершением этапа. Ловилась только небрежность, не намерение.

Стоило, потому что стенд поднят всю транзакцию — узел вроде `TRACE` ради живого прогона и
существует, — а его мусор сторожу неотличим от правки: файл был другой, значит кто-то менял.
В одном прогоне приёмка встала на 177 runtime-дампах и трассах Playwright, без единого
исходника. Список исключений `PROFILE_VOLATILE_PATHS` эту дыру не закрывал, а лишь
регистрировал прошлые попадания: в нём оказывалось ровно то, на чём уже умер прогон, тогда
как следующая мина всегда лежала взведённой — `node_modules/.vite` (128 файлов), `.vite-temp`,
`.vue-global-types`, и внести их было нельзя, `node_modules` в списке запрещали намеренно.
Перечислением инструменты не догнать.

Замер на одном профиле показал, что именно охранялось. Игнорируемые runtime-каталоги
имели `nlink=1`: это копии песочницы, они исчезают вместе с ней и в диф не попадают.
Исключением оказался каталог зависимостей с несколькими hardlink-ссылками, потому что
профиль клонировал его через `cp -al`: запись в одной песочнице меняла файлы основного
репозитория и соседних рабочих деревьев. Это дефект провижна, а не предмет надзора,
и лечится он полной копией — требование «самодостаточное рабочее дерево, без общих inode»
теперь записано в PROFILE-CONTRACT.

Итог: игнорируемые файлы в чувствительное множество не попадают, `PROFILE_VOLATILE_PATHS`
и `volatile.list` отменены целиком. Половина сторожа, которая несёт нагрузку, не тронута —
доказать, что инструментация снята и в диф не уехало лишнего, он по-прежнему обязан.

По той же линии игнорируемые файлы сняты и с проверки маркера
(`_instrumentation_tx_marker_absent_in_roots`, её зовут и `begin`, и финал `cleanup`):
она смотрит только tracked-содержимое и untracked-файлы вне gitignore. Требование «маркера
нет ни в одном игнорируемом файле» невыполнимо в принципе, потому что вывод самой
трассировки приложение пишет ВНУТРЬ дерева — например, в runtime-лог приложения. В одном
прогоне три строки такого лога дали `baseline_not_restored` при побайтово восстановленном исходнике, а
следующий `begin` отказывал 78 по тому же логу: узел нельзя было ни закрыть, ни переиграть.
Маркер, оставленный в ИСХОДНИКЕ, по-прежнему запирает транзакцию — именно он уехал бы в диф.
Попутно ушёл обход `vendor`/`node_modules` — минуты на каждый `begin` и `cleanup`.

**У `stalled` нет автоматического восстановления, и это намеренно.** Checkpoint или cleanup,
увидевший чужое изменение, пишет durable `STATE=stalled` с `REASON` (`out_of_scope_change`,
`unsafe_scope_object`, `snapshot_failed`, `cleanup_snapshot_failed`, `concurrent_change`,
`cleanup_resume_conflict`, `restore_failed`, `baseline_not_restored`) и
возвращает 75; диспетчер валится fail-closed, демон уходит, узел остаётся незакрытым.
Разбирать такое обязан человек: движок не знает, чья это правка. Чтобы разбор не начинался
с base64 в снимках, `_route_v2_log_transaction_stall` пишет в журнал причину и сводку
`workspace_guard_diff_paths` — тип записи и каталог с числом файлов, без содержимого.
Причину журналу отдаёт КАЖДЫЙ путь, где транзакция встала, включая снятие инструментации
упавшего узла (`route_v2_cleanup_active_instrumentation`): раньше там логировал только
`_route_v2_transaction_after`, и раньше при таком отказе в журнале оставалась единственная строка «код 75» —
`REASON` пришлось доставать из `state.env` руками, не зная даже, что дело в транзакции,
а не в раннере.
`resume` вставшую транзакцию не подхватывает: `route_v2_cleanup_active_instrumentation`
знает только `active`, `cleaning` и `completed`, на `stalled` возвращает 75 — демон
поднимется и тут же умрёт, пока человек не разберёт.

**Как расшить вставшую транзакцию** (`<TX>` — `~/.factory/control/transactions/t<TASK>/<txid>`):

1. Убедиться, что демон мёртв: `systemctl --user is-active factory-t<TASK>.service`.
2. Прочитать `<TX>/state.env` — `REASON` называет вид расхождения, а
   `workspace_guard_diff_paths <TX>/baseline.tsv <TX>/checkpoint-1.tsv 12` показывает, где.
3. Сверить файлы scope с бэкапами: `<TX>/files.tsv` даёт пары «путь → `backups/<хеш>.data»
   (пути в base64). Совпали побайтово — инструментация уже снята, восстанавливать нечего;
   разошлись — вернуть файл из бэкапа, это и есть ручной cleanup.
4. Убрать транзакцию из-под ног: `mv <TX> <TX-родитель>/.stalled-<метка>` и удалить
   `active.env`. Именно `mv`, а не `rm`: бэкапы и снимки — единственная улика.
   **Каталог обязан перестать совпадать с txid.** Идентификатор — `v2-<attempt>-s<sequence>`
   от курсора ленты, а провалившийся узел в ленту ничего не записал, поэтому повтор возьмёт
   ТОТ ЖЕ txid, а `instrumentation_tx_begin` при существующем каталоге отдаёт 73.
5. Проверить, что маркер этапа не остался в ИСХОДНИКАХ:
   `git -C <root> grep -F FACTORY-TRACE:t<TASK>` плюс тот же `grep` по
   `git ls-files --others --exclude-standard`. Остался — `begin` откажет снова, уже с кодом 78.
   Игнорируемые файлы чистить не нужно и проверять их бесполезно: в них лежит вывод самой
   трассировки, надзор его не видит.
6. Поднять демона обычным `resume`; узел пойдёт заново с чистого baseline.

Менять состав снимка под уже вставшей транзакцией бесполезно и вредно: её `baseline.tsv`
снят прежним кодом, и новый checkpoint разойдётся с ним на ОТСУТСТВИИ записей, которых
теперь не пишут. Поэтому шаг 4 — вынести транзакцию, а не чинить её на месте.

## Canonical config

Parser принимает только allowlisted keys и безопасные значения. Обязательны:

```text
RUNNERS_SCHEMA=1
CONFIG_REVISION=<integer>
PROJECT_RUNNER_PRIMARY=<provider>
```

`profile_config_write`:

1. берёт lock;
2. проверяет schema и expected revision;
3. строит новый документ;
4. пишет temp в том же каталоге;
5. делает atomic rename.

Код 72 означает stale revision, 78 — неподдерживаемую schema/config.

Routing не имеет запасного provider-а вне canonical policy.

## Model policy

Приоритет модели:

```text
stage/provider policy → DEFAULT/provider policy → provider default family
```

Поля:

```text
FAMILY
FAMILY_FAILOVER
VERSION
VARIANT
EFFORT
EXACT
```

`family + version=latest` разрешается только по локальному trusted catalog. Codex adapter
читает `models_cache.json`; сеть на пути разрешения модели не нужна.

EFFORT применяется адаптером провайдера: claude — флаг `--effort`, codex —
`-c model_reasoning_effort=...`, kimi — через per-run `KIMI_CODE_HOME` с переписанной
секцией `[thinking]` config.toml (argv-флага у CLI нет; допустимы только `low|high|max`,
невалидное значение отвергается fail-closed до вызова модели — см. docs/engine/KIMI.md).

Exact id допустим, если он подтверждён каталогом/coverage. Молчаливого downgrade нет.

## Ошибки и failover

Adapter возвращает нормализованную категорию, а не текст, который core пытается угадать.

Switchable:

- `unavailable_preflight`/`route_unavailable` до model call;
- доказанный `limited` после начала model call;
- `provider_unavailable` для 401/403, если event stream доказывает отсутствие model/tool activity;
- CAS-подтверждённый manual switch.

Non-switchable:

- task/stage result `failed`;
- test/build/sandbox failure;
- permission/safety/policy denied;
- malformed/stale status;
- operator cancellation;
- `context_overflow`/HTTP 413;
- обычный HTTP 429 без доказанного subscription/weekly limit;
- outcome unknown после возможного side effect;
- auth/transport error после фактической активности модели.

Breaker scoped по provider/auth profile. Он не является глобальным переключателем всей фабрики.
Срока «навсегда» у него нет (точное время сброса даёт опциональный `limit_until` раннера, иначе
cooldown), а явный выбор человека — назначение на задачу/этап и кнопка переключения — заходит
в исполнителя даже под закрытым предохранителем. Правила целиком —
[MULTI-AI.md](MULTI-AI.md), «Предохранитель».

Новый провайдер добавляется по [ADDING-RUNNER.md](ADDING-RUNNER.md): контракт адаптера,
fail-closed classify, TDD-порядок с критикой тестов, live-допуск.

## Status protocol

Транспорт статуса двухпутевой: fd 7 с capability-токеном — быстрый путь, deferred
`status_request` (файл-запрос в `control-requests/`, применяет runner-launcher вне
песочницы) — обязательный резерв. Оба заявляют и Codex, и Claude: начиная с
CLI 2.1.220 Claude не наследует fd 7 в тул-шелл агента, из-за чего Scout не может
отчитаться; `stage-result.sh` сам выбирает доступный путь.

`run_state_begin` атомарно:

- увеличивает epoch;
- создаёт active run record;
- сохраняет hash capability;
- выставляет stage `running`.

Capability передаётся adapter-у через FD, а не argv/env/prompt.

Статус `running` появляется РАНЬШЕ этого момента: маршрутный рантайм помечает узел на входе
(`_route_v2_mark_node_running`), до рендера промпта, открытия транзакции и снимка рабочих
деревьев, и пишет в журнал строку «узел N: подготовка к исполнению». Пометка трогает
только колонку статуса; владение запуском по-прежнему выдаёт исключительно `run_state_begin`
со своим epoch и capability, поэтому вторая запись `running` — не конкурент, а уточнение.
Без пометки доска показывает прошлый узел всю подготовку, и человек читает это как
«конвейер встал». Явная projection-запись восстановила эту семантику после перехода
на route dispatcher.

`stage-result` проверяет:

- активный task/stage;
- точный `run_id`;
- точный `epoch`;
- capability hash;
- состояние `active`;
- точную схему typed verdict: owner из закрытого набора и непустой список findings
  с каноническими стабильными id. Legacy `failed` без verdict остаётся допустимым только
  для совместимости со старыми маршрутами.

Повторный или поздний terminal result возвращает конфликт и не меняет новый run.

**Отказ обязан называть нарушенное правило.** Валидатор вердикта (`lib/run-state.sh`)
печатает в stderr, какое поле не прошло и по какому допуску (лимиты и мотив — в
PROFILE-CONTRACT, «Status protocol v2»), а не просто выходит с кодом 2. Молчащий отказ
неотличим для агента от «команда не работает»: он начинает угадывать форму пробными
вызовами, и один из них закрывает узел. Текст самого замечания в stderr не печатается —
то же сообщение уходит в журнал маршрута при trusted-проверке. То же требование к prompt:
лимиты названы прямо в блоке завершения этапа (`lib/multi-runner.sh`), чтобы агент узнавал
о них до вызова, а не по отказу.

`stage-progress` выполняет те же проверки и дополнительно применяет allowlist ключей/значений.
Он никогда не завершает текущий stage.

`pipeline-set.sh` не входит в agent permissions и не владеет инициализацией, topology,
lifecycle, provenance, route status или route comments. Эти записи проходят только через
host/control writer либо run-scoped capability API. Immutable attempt ledger остаётся
источником истины даже при повреждении отображаемой проекции.

## Pipeline storage

Canonical task file:

```text
${STATE_DIR}/t<TASK>.pipeline
```

Архив:

```text
${STATE_DIR}/archive/t<TASK>.pipeline
```

Все multi-key updates выполняются под task lock. Readers должны читать последний canonical
key; writers не должны использовать ad-hoc `sed` вне storage API.

Основной route не архивирует реестр. `bin/factory` сначала завершает `SHIP`, затем `RETRO`,
проверяет оба terminal status и только после этого переносит карточку в archive. Ошибка
хвоста оставляет active registry для безопасного resume.

### Урок RETRO лежит в двух местах, и второе — рабочая копия

`artifacts.lessons` — прежний адрес в архиве состояния (`archive/t<TASK>.lessons-proposed.md`):
он переживает снос рабочей копии и остаётся страховкой. `artifacts.lessonsRepo` — тот же текст
внутри ПЕРВОГО repository попытки, в каталоге `LESSONS_DIR` профиля (умолчание `docs/lessons`).

Второй адрес не дубль ради надёжности. Архив фабрики лежит вне репозитория: он не попадает
ни в `git status`, ни в diff, ни в PR — поэтому предложения RETRO там просто копились и никто
их не открывал (30 файлов за три недели по четырём профилям). В рабочей копии урок попадает
человеку на глаза тем же путём, что и код.

Из этого следуют два ограничения, которые нельзя молча ослабить:

- узлу `retro` нужен `filesystem: workspace-write` и секция `workspace` в `requiredContext` —
  иначе писать в рабочую копию физически некуда;
- `delivery` узлу `retro` **не выдаётся**: схема маршрута разрешает delivery-capability
  единственному каноническому узлу `ship` (`machine: delivery-capability разрешена только
  каноническому узлу ship`). Право публиковать наружу принадлежит одному узлу после приёмки,
  и ослаблять это ради уроков нельзя.

Поэтому у маршрута с публикацией хвост идёт **`retro` → `ship`**, а не наоборот: ретро пишет
файл, `ship` забирает его отдельным вторым коммитом, и урок приезжает человеку в том же PR,
что и работа. Инвариант цел, а урок перестаёт зависеть от того, вспомнит ли кто-то заглянуть
в архив.

Два условия этого порядка обязательны:

- **любой исход `retro` ведёт в `ship`** (`done`, `skipped`, `failed`, `exhausted`). Ретро не
  имеет права задержать публикацию уже принятой человеком работы: неудачный разбор процесса —
  не повод не отдать сделанное;
- **`ship` знает про файл поимённо.** Промпт публикации запрещает массовое добавление
  worktree и отбрасывает runtime-артефакты, поэтому файл урока в нём назван прямым
  исключением — иначе он был бы принят за мусор и не уехал.

Цена решения названа честно: `retro` больше не видит `artifacts.ship`, то есть уроки о самой
публикации (конфликт слияния, `gh pr edit` без body, файл, доживший до коммита) из ретро
уходят. Их продолжает фиксировать сам `ship` в своём отчёте — там они и остаются.

## Учёт времени попытки

`factory TASK work-time --attempt a_<32hex>` — read-only сводка: `work_time_s` (работа узлов
без ворот), `gate_wait_s` (ожидание решений человека на воротах), `last_event_at` (эпоха
последнего события журнала). Источник — тот же hash-chained журнал попытки, отдельного
таймера нет: интервал узла = промежуток между предыдущим событием и его коммитом, а ворота
классифицируются по `executor` из закреплённого `describe-route`, а не по имени узла. Проекция
в реестр (`WORK_TIME_S`, `GATE_WAIT_S`, `WORK_TIMER_SINCE`) — витрина: она пишется после
коммита и на входе в ворота, её падение маршрут не останавливает, а sealed-попытку CLI читает
уже из реестра. По `WORK_TIMER_SINCE` доска дотикивает интервал текущего узла в браузере.

Что это НЕ измеряет: коммит восстановления (`recovery`) интервала не получает и обрывает его,
но подъём песочницы после `init` попадает в первый узел, а простой между обрывом прогона и
`resume` — в тот узел, который отработает следующим. Человеческий `goto` от этого прикрыт
(`human-rewind` — событие журнала, оно обрывает интервал), голый `resume` — нет. Значение
годится для сравнения узлов между собой и для «сколько попытка вообще идёт», но не для
биллинга: цифра включает всё, что происходило между двумя записями в журнал.

## Coverage gate

`factory-check --host-preflight` проверяет CLI/catalog/capabilities без prompt и model call.
Artifacts привязаны к config revision и по умолчанию действуют 6 часов
(`FACTORY_HOST_PREFLIGHT_TTL`, не более суток). Этого хватает на рабочую сессию и длинный
этап, но проверка всё равно регулярно подтверждает состояние CLI/auth/catalog.

`RUNNERS_COVERAGE=required` означает fail-closed:

- нет artifact;
- artifact истёк;
- revision не совпадает;
- provider/model/capability unavailable.

Ни одно из этих состояний не лечится скрытым выбором другого provider-а.

**Host preflight не применяется к `gate --commit-only`.** Решение человека на воротах
агентов не запускает — это CAS в журнале попытки и проекция в реестр, поэтому готовность
раннеров к нему отношения не имеет. Пока preflight стоял и на этом пути, обновление любого
CLI могло проявить недоступность провайдера, `profile_runner_host_preflight` возвращал
**1** — и ворота нельзя было ни
принять, ни отклонить. `start` и `resume` preflight проходят по-прежнему: там
действительно бегут агенты, и недоступный раннер обязан их остановить. Практическое
следствие для человека: решение ворот запишется всегда, но продолжить маршрут, пока
раннер недоступен, не выйдет — сначала чинится CLI.

Непройденный preflight возвращает typed-маркер
`FACTORY_ERROR=runner_preflight_unavailable RUNNERS=<id,…>` в stderr и журнал этапов.
Артефакт `<state>/coverage/<профиль>/host.env` хранит те же идентификаторы в
`UNAVAILABLE_RUNNERS`. **Голый код 1 не является диагнозом preflight:** shell-движок
может вернуть его и по другой причине; Cockpit типизирует отказ только по маркеру.

## Debug

Эффективный уровень:

```text
task → profile → global → off
```

Task-level debug ограничивается TTL. Typed events пишут routing/classification/breaker/status
решения, но не prompt, credentials, capability и полный model response.

Debug setting хранится отдельно от runner config, поэтому его включение не инвалидирует
policy revision/coverage.

## Историческое состояние

Legacy registry можно читать или отдельно архивировать, но единый `factory` никогда не
исполняет и не возобновляет его. Resume требует exact immutable attempt из trusted control
root; одного старого `RUN_PROTOCOL=2` недостаточно (legacy launcher тоже писал этот маркер).
Автоматического мигратора, compatibility wrapper или пути назад в удалённый legacy-цикл нет.

## Как проверять изменения

Сначала targeted test, затем полный suite:

```bash
rg -l -0 '^#!/usr/bin/env bash' engine/bin engine/lib profiles | xargs -0 bash -n
python3 -m py_compile engine/lib/dashboard.py
engine/bin/factory-check --quick
tests/run-all.sh
```

Тесты располагаются только в корневом `tests/`, документация — только в корневом `docs/`.
Новые `engine/tests` и `engine/docs` не создавать.

Offline-набор движка идёт параллельно: `tests/engine/run-offline.sh` запускает сам себя
по одному файлу на процесс (`xargs -P`, по умолчанию `nproc`, переопределяется
`TEST_JOBS=1` для последовательного разбора). Изоляция та же, что и была: у каждого файла
свой `TEST_ROOT`/`STATE_DIR` и `env -i`, вывод файла печатается одним блоком под общим
`flock`, поэтому порядок файлов в выводе плавает, а строки не перемешиваются. Отсюда
требование к новым тестам: не полагаться на порядок между файлами и не считать процессы,
группы и содержимое `/proc` за пределами своего поддерева — соседний файл в это же время
делает то же самое. Общее время набора теперь равно самому долгому файлу, а не сумме.

Host preflight запускается отдельно и явно:

```bash
RUN_HOST_PREFLIGHT=1 engine/bin/factory-check --host-preflight
```

Он допускается после offline suite, но до Cockpit/рабочего запуска. Реальный model call не является
частью автоматического test suite.

## Когда изменение вступает в силу

- `profile.sh` перечитывается перед этапом;
- `runners.env` читается при каждом routing decision;
- task override читается из pipeline;
- server/web код требует обычного рестарта соответствующего процесса;
- уже запущенная provider attempt не меняет модель посередине; switch создаёт новую attempt;
- промпты и схема v2 требуют публикации И новой попытки: примороженный бандл не меняется
  ни от `resume`, ни от `goto` — см. [Что заморожено, а что живое](#что-заморожено-а-что-живое).

Отсюда типичная ошибка при разборе прогона: правку внесли, задачу перезапустили `resume`,
поведение не изменилось — и правку начинают считать неработающей. Сначала ответь, какой это
слой. Движок и профиль подхватятся на следующем же этапе; схема — только следующей попыткой.

**Но не весь `profile.sh`: контракт попытки закреплён и сверяется побайтово.** При старте
попытка получает `artifacts/profile-contract.tsv` (пути репозиториев, контейнер, ветка,
хост-требования) и `artifacts/project-context.json` (`profile_project_context` — стек и
guardrails), режим 0400. Каждый `start`, `resume` и решение ворот пересчитывают их заново
и сравнивают `cmp`-ом с закреплённым: разошлось — код 75 и никакого прогона. Операции
«перезакрепить» нет и не будет, иначе привязка попытки к профилю ничего не значит.
Поэтому правка `profile_project_context` (или путей, контейнера, закреплённых веток) при
живой попытке запирает её насмерть: `resume` будет молча умирать, пока текст не вернут байт в байт
или попытку не закроют `abandon`. В одном случае одна строка guardrails была заменена
на две, последовали четыре попытки продолжить прогон, а в журнале осталось лишь
«repo/project contract попытки изменился или повреждён (код 75)». Теперь строка
называет разошедшееся поле (`attempt_state_contract_drift_v2`): «project-context:
guardrails» вместо загадки. Меняешь контракт профиля — сначала убедись, что активных
попыток нет.

**Но `bin/factory` при живом прогоне не править вообще.** Демон — это и есть исполняемый
`bin/factory`, а bash читает скрипт лениво, по сохранённому смещению в файле. Правка сдвигает
всё, что ниже: демон дочитывает следующую команду уже с чужого места и умирает синтаксической
ошибкой в строке, которой в исходнике нет. Момент случайный — от «сразу» до «через час», когда
управление дойдёт до непрочитанного куска. В одном случае демону дописали 51 строку под ногами, и он
упал с `exit 2` вместо штатного fail-closed `75`, оборвав разбор на полпути; `bash -n` при этом
был чист, потому что на диске файл корректен. Правишь движок — сначала дождись конца прогона
или сними его `abandon`. Библиотеки в `lib/` этой ловушке не подвержены: они `source`-ятся
целиком до начала работы.

Ловушку заряжает ПЕРЕЗАПИСЬ файла на месте (`sed -i`, `>`, дописывание в конец) — она меняет
байты под тем же inode, который открыт у демона. Замена целиком (запись во временный файл и
`mv`, так пишут большинство редакторов и агентских инструментов) оставляет живому демону его
собственную копию: inode остаётся открытым, помеченным `(deleted)`, и прогон дочитывает
неизменённый файл. Проверяется одной командой, и делать это надо ДО паники, а не после:
`ls -l /proc/$(awk -F= '$1=="ORCH_PID"{print $2}' "$STATE_DIR/t<TASK>.pipeline")/fd/255` —
bash держит скрипт на fd 255. Ссылка с `(deleted)` и inode, не совпадающий с текущим файлом
(`stat -c %i bin/factory`), означают, что прогон в безопасности. Совпадающий inode — правка
уже под ногами демона, и лучше снять прогон самому, чем ждать случайного `exit 2`.
На гарантию способа записи не полагайся: правило «не править при живом прогоне» остаётся.
