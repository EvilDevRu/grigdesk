# Чаты во встроенном интерфейсе APK

Полное приложение Android хранит интерфейс в `assets/ui` внутри APK. Обновление сервера
не заменяет эти файлы: приложение обновляется отдельной сборкой и установкой.
Рабочий `web/dist` также не является источником интерфейса уже установленного приложения.

Актуальный общий интерфейс получает карточки порциями до 40 через
`GET /api/chat/store/list?page=1&archived=0&limit=40`. Только явный выбор открывает
последние 40 сообщений через `GET /api/chat/store/chat/:id?window=1`; старые сообщения
приходят по cursor при прокрутке вверх. Архив и поиск не загружаются заранее.
При восстановлении SSE `POST /api/chat/store/changes` сверяет только известные версии
и верхнюю порцию текущего списка. Частичное сохранение использует отдельный window URI. Отказ первого списка оставляет
`loaded=false`, показывает причину и повтор. Контракты — [лёгкая история](../chat/lazy-history.md)
и [восстановление загрузки](../chat/store-loading-recovery.md).

Старый встроенный интерфейс может продолжать читать весь `GET /api/chat/store` даже
с обновлённого сервера. В прежнем варианте отказ этого запроса подтверждал пустой список
без ошибки, после чего мог появиться автоматически созданный «Новый чат».
Это объясняет возможное расхождение между приложением и свежим окном компьютера;
оно само по себе не доказывает удаление серверной истории.

Есть и промежуточный клиент: `GET /api/chat/store/list` без `page=1` получает сразу
все активные и архивные карточки, а адресный `GET /api/chat/store/chat/:id` без `window=1`
читает всю историю выбранного разговора. Истории остальных разговоров при этом могут
оставаться незагруженными. Поэтому наличие list/detail само по себе ещё не подтверждает
порционную загрузку. На очень длинной истории полный detail создаёт нагрузку после
окончания сети: принятие сообщений, служебные обходы и построение всей ленты выполняются
в WebView. Сверяют отдельно размер ответа, число принятых сообщений и блокировки клиента;
время `JSON.parse` не описывает всю последующую работу интерфейса.

Начальная порция до 40 сообщений не ограничивает размер уже открытой ленты навсегда:
старые порции добавляются по запросу, а сообщения активного хода могут материализоваться
из realtime-снимка. При проверке разделяют первый ответ истории, добавления живого хода
и явную загрузку старых сообщений. Число строк DOM после этих действий само по себе
не доказывает полного GET истории.

При диагностике проверяют интерфейс, извлечённый из самого APK: запрос списка, видимую
причину отказа, ручной повтор, текст открытой ленты и сверку после нового `hello`.
Проверки одних исходников или запроса detail недостаточно: запрос может завершиться
ошибкой, а форма ввода уже отображаться. Для изоляции используют синтетическую историю.
Совпадение `versionName` и `versionCode` не подтверждает одинаковые файлы UI: сверяют
встроенный JS-ресурс и фактические параметры запросов. При диагностике рабочей истории
собирают числовые метрики без текста переписки; зависший замер не считают завершённым
CPU-профилем.

Штатная сборка описана в [инструкции Android](android-build.md). До установки сверяют
подпись и совместимость версии; debug-кандидат не является опубликованным обновлением.
Сначала обновляют сервер, затем приложение. Браузерная проверка встроенного UI и JVM-тесты
трубы не подтверждают версию установленного APK, связь конкретного телефона, Keystore
или биометрию: эти проверки требуют устройства.
