# Локальное окружение GrigDesk на Android

Ограничения окружения сверены по исходникам проекта и документации платформ.
Нативный сервер дополнительно проверен в пробном APK на физическом Android 16 ARM64.

## Что уже есть в проекте

Обычный APK содержит интерфейс и подключается к выбранной машине напрямую или через посредника:
[архитектура приложения](client-app.md).
Вариант `probe` содержит также нативный сервер и его окружение.
Сервер работает непосредственно на хосте; Docker не является обязательной оболочкой
для его запуска: [контракт сервера](../server/host-native-runtime.md).

## Заставка локального запуска

При холодном открытии `probe` показывает по центру окно 3:2 c разметкой, рельефом,
фирменной надписью и анимацией desktop-заставки. WebView заставки читает встроенные
ресурсы и перевод «Запуск сервера…» без сетевых запросов. Заставка скрывает промежуточные состояния трубы,
пока подключение, вход и кадр рабочей области не готовы. Каталог исполнителей загружается
отдельно, после входа.

При отказе запуска, несовместимости или после 120 секунд открывается обычное окно
с текущим состоянием. Штатные повторы связи продолжаются. Поворот сохраняет срок,
а при возврате из фона с восстановлением локальной связи действует новый срок. Заставка
закрывается после готового кадра без плашки восстановления. Сохранившаяся фоновая связь
позволяет показать окно сразу. Если выбрана удалённая машина, приложение открывает её
без ожидания местного сервера. Нативная блокировка приложения
отображается поверх заставки. Обычный `:client` без встроенного сервера этот слой не создаёт.

На Android 16 ARM64 проверены оба сценария. При завершении процесса сервера до готовности
заставка закрылась, и обычное окно показало состояние «нет связи». Возврат на передний план запустил
сервер повторно. При задержке готовности приложение показало то же состояние после истечения
срока и автоматически открыло рабочую область, когда сервер продолжил запуск.

Кнопка «Подключиться сейчас» для профиля «Это устройство» запрашивает запуск службы
и сразу начинает проверку связи. Служба запускает новый процесс, если прежний завершился.
Автоматические повторы продолжают проверять готовность уже запущенного сервера.

В [server/package.json](../../../server/package.json) сервер запускается через Node.js,
а [grigdesk-ctl](../server/grigdesk-cli.md) поддерживает запуск без systemd. Наличие Node.js
на другой платформе само по себе не подтверждает переносимость исполнителей,
их песочниц, инструментов проектов и интеграций с хостом.

## Почему FEX и Wine не дают Docker

FEXCore исполняет инструкции x86/x86-64 и может собираться для Android AArch64.
Это не собственное ядро Linux. [FAQ upstream FEX](https://wiki.fex-emu.com/index.php/FAQ)
не обещает поддержку Android как Linux-окружения, но не описывает возможности всех
сторонних оболочек. DroidDeck поставляет Linux rootfs и адаптированный PRoot и использует
FEX для x86-программ: [проверенные детали упаковки](android-linux-packaging.md).
[Proton](https://github.com/ValveSoftware/Proton) использует Wine для запуска Windows-игр
на Linux. Слои совместимости не предоставляют гипервизор для Docker Desktop.

Docker опирается на функции ядра, включая namespaces и cgroups:
[устройство изоляции Docker](https://docs.docker.com/engine/security/).
Rootless Docker также требует user namespaces и настройки отображения UID/GID:
[его требования](https://docs.docker.com/engine/security/rootless/).
Windows-версия Docker Desktop использует отдельный backend виртуализации, например WSL 2
или Hyper-V: [требования Docker Desktop](https://docs.docker.com/desktop/setup/install/windows-install/).
Следовательно, одного запуска Windows-программы через Wine недостаточно для локальных контейнеров.

## Linux-окружения на Android

- [Termux](https://termux.dev/en/) работает без root и предоставляет Node.js, Git, Bash
  и Python. Это подтверждает доступность базовых инструментов, но не совместимость всего GrigDesk.
- [PRoot-Distro](https://github.com/termux/proot-distro#limitations) даёт Linux userland
  без собственного ядра и без настоящих root-прав. Его поддержка OCI-образов не означает
  запуск Docker Engine: namespaces, cgroups и полноценный init он не предоставляет.
- [QEMU в режиме system emulation](https://www.qemu.org/docs/master/system/introduction.html)
  запускает гостевую ОС с собственным ядром. Его TCG выполняет программную эмуляцию;
  аппаратное ускорение требует отдельного доступного механизма виртуализации.
- В Android есть Linux Terminal с Debian в VM:
  [документация Android 16](https://source.android.com/docs/whatsnew/android-16-release#virtualization).
  Доступность зависит от устройства и прошивки:
  [документация для поддерживаемых устройств](https://developer.android.com/about/versions/15/release-notes).

Из требований Docker следует, что локальный Engine нужно оценивать в полноценной Linux-VM
либо на Android-хосте с нужными правами и функциями ядра. Одного root недостаточно для
гарантии совместимости. Docker внутри конкретной Android-VM здесь не проверялся.

## Как окно подключается к серверу

При первом открытии пробный APK выбирает профиль «Это устройство» и запускает
сервер через foreground-сервис. Оболочка показывает состояние подключения и
повторяет проверку готовности, пока сервер распаковывает окружение и запускается.
После bind сервер публикует ключ окна в приватном каталоге приложения. Нативная
труба обменивает ключ на сессию владельца через `/api/auth/window-session`.
WebView использует встроенный интерфейс и cookie трубы. Ключ и cookie серверной
сессии остаются в нативном процессе. После перезапуска сервера труба использует
новый ключ. Сохранённый выбор машины применяется при следующих запусках.

На физическом Android 16 ARM64 после установки и после принудительной
остановки приложения окно само вошло в локальную сессию. Загрузились доска
и показания CPU и памяти с локального сервера.

## Что ограничивает автономное приложение

В пробном APK Bionic Node 24.21.0 подтвердил запуск дочернего процесса,
Unix-сокет и `fsync` внутри приложения. Обычный JS bundle ответил HTTP 200 после
первого запуска и повторно после принудительной остановки приложения.
[Блокировка папки данных на Android](../server/data-home.md#ранний-старт-и-блокировка)
использует атомарное переименование каталога. Отдельная проба SEA завершилась
SIGSEGV. Для команд фабрика запускает собственный супервизор, который принимает
осиротевших потомков и подтверждает завершение по `wait4(ECHILD)`. Перед
сигналом дочерняя связь проверяется по pidfd. Чтение `/proc/1` для этого
больше не требуется.

На физическом ARM64 в контексте самого приложения прошёл маршрут до ворот
и продолжение той же попытки. Команда выполнилась один раз. На этом же
устройстве проверены отмена, завершение осиротевшего потомка и сохранение
соседнего процесса. Штатный запуск пробного APK поднимает foreground-сервис.
Он передаёт движку физические пути внутри приложения и выставляет в PATH
имена нативных Bash, Git и flock из комплекта. Git собран с Android-вариантом
чтения имени пользователя. Это устранило падение дочернего процесса при
создании worktree на планшете. Bionic Python с полной stdlib прошёл пробу
`forkpty` внутри приложения. Qwen-маршрут и приёмка x86_64 остаются открытыми.

Для локального сервера отдельно проверяются запуск дочерних процессов, доступ к проектам,
совместимость бинарных зависимостей и механизмов изоляции исполнителей. ARM64-сборки
инструментов позволяют обойтись без перевода x86-инструкций там, где такие сборки доступны.

Длительная работа требует учёта Android lifecycle. Foreground service показывает уведомление
и имеет ограничения запуска и времени работы в зависимости от типа:
[документация Android](https://developer.android.com/develop/background-work/services/fgs).
Наличие такого сервиса не является гарантией непрерывной работы сервера и всех его процессов.

В Android 17 ограничения памяти приложений относятся ко всем target SDK. Устройство с
большим объёмом RAM также требует проверки лимитов конкретной прошивки:
[поведение Android 17](https://developer.android.com/about/versions/17/behavior-changes-all#app-memory-limits).
