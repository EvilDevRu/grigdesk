# Движок и профили одиночного ELF

Раскладка I/D/R описана в [обзоре сервера](server-binary.md). Закрепление движка
за попыткой и продолжение после обновления — в [контракте кэша](server-binary-cache.md).

`factoryRuntimePaths` выбирает Go-фабрику. Запуск из исходников использует
`bin/factory` из корня checkout. Её собирает `grigdesk-ctl build factory`.
В серверном комплекте бинарник находится в `R/engine/bin/factory`.
Явное переопределение для отдельной установки требует абсолютных путей и
`GRIGDESK_ENGINE_MODE=external`.

Профили payload читаются из физического `realpath(D)/profiles` или явного
`FACTORY_PROFILES_DIR`. Путь с symlink-компонентом, `..` или завершающим `/` отклоняется
`factory_profiles_not_physical` с подсказкой физического пути: движок сверяет `canonical_file`
и запрещает такие компоненты. Профиль не переносится, ссылка `R/profiles` не создаётся.

Схемы lifecycle и provider lineage в серверном комплекте находятся в
`FACTORY_HOME/../schemas`. Перенесённая копия R без checkout прошла настоящий
`factory check` на минимальном профиле с capability route-v2 в физическом D/profiles;
тот же профиль через ссылку на D движок отверг кодом 78.

Штатная серверная сборка для Linux x64 и Apple Silicon компилирует фабрику
из `utilities/factory/` с Go 1.27.4. Для подготовленного бинарника сборщик принимает
`--factory-candidate <путь-к-бинарнику>`. Сбой сборки фабрики останавливает сборку
сервера до публикации. Изолированный релизный рецепт переносит только физический
каталог Go 1.27.4 из окружения сборщика. Для Apple Silicon действует отдельный
нативный допуск.

Под `engine/` в комплекте лежат `engine/bin/factory` и
`engine/lib/delivery_contract.py`. `server/factory-engine.json`
фиксирует протокол, формат, OS/ABI, права и SHA256 обоих файлов. Пакет с descriptor
проверяется до запуска. Старый пин без Go descriptor даёт
`factory_runtime_engine_retired`. Остановленную попытку можно перепривязать
к текущему Go-комплекту через карточку. Это сохраняет её идентификатор,
закреплённый маршрут, курсор и журнал.

Статический каталог этапа GLM, API-допуск и запрет переключения исполнителя по сигнатурам —
[отдельный контракт GLM Factory](../chat/glm-factory-stage.md). Hooks/status MCP используют
[собранные helpers из R](server-binary-factory-helpers.md). Граница bounded initialize
DeepSeek ACP описана [отдельно](../pipeline/deepseek-acp-startup.md); проверка chat/web
не заменяет приёмку этого транспорта на конкретном ELF.

## Нативная приёмка Go-фабрики

`bash tools/check-factory-native.sh linux/amd64 <путь-отчёта>` использует
`bin/factory` или явно заданный абсолютный `FACTORY_NATIVE_BINARY`.
В отдельной установке он проверяет профиль, запуск, открытие той же попытки
на воротах после перезапуска сервера, продолжение, чтение истории и остановку.
Отчёт фиксирует SHA256 ELF, исходы HTTP, завершение процесса и число эффектов.
Собранный Linux amd64 сервер прошёл отдельный smoke после распаковки.

На Linux amd64 штатный установщик приложения дважды успешно установил подписанный
тестовым ключом комплект в режиме `local`. Сервер из установленного комплекта
прошёл тот же сценарий с одним результатом. AppImage этого комплекта открыл окно
на изолированном X11 в режиме `--appimage-extract-and-run`. В браузере GrigDesk
карточка после переоткрытия оставалась на тех же воротах. Штатная кнопка
«Принять» завершила попытку с одним результатом. В тестовом интерфейсе
SVG-узел открылся через вспомогательную кнопку для прежней версии браузера.

В отдельной установке Linux amd64 в режиме `server` штатный установщик
подготовил подписанное тестовым ключом обновление с Bash на Go. Команда
`grigdesk-ctl server resume-update --restart` дождалась остановки старого
сервера и запуска нового. Попытка на воротах сохранила идентификатор, хеш
маршрута и пин старого поколения. После штатной перепривязки она продолжилась
на Go и завершилась с одним результатом. Новая задача сразу получила пин
Go-поколения и тоже завершилась с одним результатом.

В режиме `local` штатный установщик подготовил подписанное обновление на
Linux amd64 с настоящим AppImage. После закрытия окна worker дождался
остановки прежнего сервера и запустил новые сервер и окно. Оба подтвердили
версию, обновление завершилось. Попытка на воротах сохранила данные, прежний
пин и хеш маршрута. После перепривязки она завершилась на Go с одним
эффектом. Новая задача сразу запустилась на Go и дала один эффект.

Арбитр сверяет начало целевого визита командой `lifecycle-read` текущей
Go-фабрики. Она проверяет сохранённый формат журнала и точную identity попытки.

Приёмка полных комплектов Linux arm64 и macOS arm64 остаётся открытой.
Для среды без доступной пробы команда возвращает 77.

## Нативная фабрика Windows из исходников

Windows x64 и ARM64 используют `bin/factory.exe` из рабочего дерева.
Скрипты `npm start` и `npm run dev` собирают его через нативный Go 1.27.4.
Сервер запускает фабрику напрямую. Дескриптор сборки принимает PE32+
соответствующей архитектуры и имя `engine/bin/factory.exe`.

```powershell
npm --prefix server run build:factory
.\bin\factory.exe capabilities --format json
go test -run '^TestWindows|^TestProcessLockWindows' ./utilities/factory/internal/host ./utilities/factory/internal/state ./utilities/internal/processidentity
```

Профильным хукам нужен Bash для Windows из Git for Windows либо физический
абсолютный путь к `bash.exe` в `FACTORY_WINDOWS_BASH`. Дочерний процесс
исполнителя добавляется в Job Object до первого исполнения. Остановка
оркестратора проходит через закрытое событие с номером задачи, PID и
временем рождения процесса. Статусный результат в Windows передаётся
штатной очередью, которую проверяет хост фабрики.

Защищённое состояние требует локального тома с поддержкой DACL, например
NTFS. Для чтения сервер делегирует проверку прав открытому handle фабрики.
Запись закрепляет содержимое до смены имени под блокировкой. Открытие
отклоняет reparse points и проверяет владельца, права и число ссылок.

Нативный CI на Windows x64 и ARM64 подтвердил сборку, остановку оркестратора,
блокировки и повторное открытие защищённого состояния. Командный маршрут
из заранее опубликованного каталога дошёл до ручных ворот и возобновился
в новом процессе с тем же курсором. Серверный читатель подтвердил журнал
попытки, команда в маршруте выполнилась ровно один раз. WSL2 в этом
сценарии не требуется.

Для владельцев серверных блокировок каталогов фабрика на Windows читает
время создания процесса из Win32 handle. Ошибка проверки оставляет
состояние владельца неизвестным. Уборка требует подтверждённого
завершения владельца или несовпадения времени создания.

Приватные файлы сервера публикуются через фабрику. Она закрепляет DACL
и синхронизирует содержимое перед атомарным переименованием. Сервер из
исходников ответил HTTP 200 на `/api/auth/state` на обеих архитектурах.
Отдельный нативный прогон подтвердил публикацию
черновика из редактора, повторную выдачу квитанции и освобождение замка
после остановки владеющего процесса. Приёмка установщика Windows
остаётся открытой. Профили с Linux-песочницей, Linux-браузером и
транзакционной инструментацией используют возможности своей платформы.
