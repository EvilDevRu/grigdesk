# Лёгкий установщик и проверка дистрибутива

Новая поставка Linux x64 (glibc ≥ 2.28) состоит из POSIX shell `grigdesk-install`
размером до 64 KiB, отдельного `grigdesk-maintenance.gz`, трёх архивов компонентов,
индекса v3 и installer proof v1. URL API `/api/releases/v1/` сохраняется.
Helper v3 собран Go, архивы компонентов загружаются отдельно.
[Исторический хвост ELF](installer-archive-tail.md) читается только для прежних выпусков.

## Начало установки и доверие

`sh ./grigdesk-install` спрашивает режим local/remote/server, папку программы и данных,
показывает версию и байты загрузки, затем просит согласие. До согласия сеть не используется.
Ответы читаются из `/dev/tty`; автоматизация требует `--yes --mode …`.
Сохранён и вызов `install local|remote|server`; смешение его с `--mode` отвергается.

Корень первоначального доверия — скрипт, полученный по официальному HTTPS.
В нём закреплены точная версия, размер/SHA индекса, gzip и распакованного helper.
Mutable latest после начала установки не читается. Helper проверяет Ed25519-подпись
индекса до архивов и изменений программы. Detached proof скрипта проверяют ctl и publisher.
JSON metadata не исполняется как shell. Redirects запрещены; curl делает до трёх попыток.

Во всех режимах загружается control. `remote` добавляет desktop, `server` добавляет server,
`local` добавляет оба компонента.
Системные Node/npm и исходники не нужны. Обязательны curl, gzip и coreutils.
GUI/FUSE нужны для запуска окна: без `--launch` их отсутствие даёт предупреждение;
с `--launch` — ранний отказ. Server с `--launch` запрещён. Пакеты системы автоматически
не устанавливаются. Пути принимаются шестью прежними флагами и должны быть абсолютными.
Программа и данные раздельны; пробелы допустимы, служебные символы unit/desktop отвергаются.

Для официального Linux x64 stable ZIP достаточно распаковать комплект и выполнить
`sh ./grigdesk-install --source-dir "$PWD"`. Подготовленные системные зависимости
позволяют начать установку с отключённой сетью и без sudo. В корне ZIP — установщик,
его `.sha256` и `.sig`, `grigdesk-maintenance.gz`, `release.json`,
`desktop.tar.gz`, `server.tar.gz` и `control.tar.gz`. Индекс формата 3 требует
компонент control во всех режимах.

Shell кандидата macOS 15+ для Apple Silicon принимает обязательный
`--source-dir /абсолютный/путь`. Индекс, helper и нужные компоненты берутся из этого
каталога. Shell проверяет CPU/ОС и хеши с помощью системного `shasum`. Maintenance
проверяет Ed25519, платформу и отдельное физическое размещение программы и данных.
В пути D действует серверный алфавит без пробелов. В I, bin и LaunchAgents пробелы допустимы.

## Повтор и сохранность

Проверенные архивы сохраняются в приватном cache `grigdesk/install/<manifestDigest>`
папки XDG_CACHE_HOME. Перед повтором size/SHA проверяются заново; порча уходит в quarantine,
незавершённый `.part` удаляет только его владелец. HTTP Range не используется.

Sibling install lock сериализует оба входа установки. Чужая или неполная папка root
не удаляется; после сбоя сохраняются файлы для восстановления. `current.json` публикуется
после launchers, descriptor и unit. Служба регистрируется без enable/start.
Повтор завершённого выпуска проверяет опись. Другой выпуск готовит штатное обновление
компонентов, сохраняя прежний maintenance: автоматической миграции старого helper нет.
Данные и активные процессы не меняются.

Свежая установка macOS закрепляет файлы и пути приватным intent, проверяет
staging, публикует proof и переносит каталог одной операцией без замены.
После прерывания повтор с тем же комплектом и путями проверяет уже записанные
файлы и дописывает свои. `current.json` появляется после обязательных launcher,
descriptor и LaunchAgent данного режима. Конфликт существующего файла останавливает
установку. Нативные прогоны восстановления выполняются отдельно.

## Локальная сборка и официальный кандидат

Команда `grigdesk-ctl dist build` без цели выбирает нативный рецепт.
Пункт «Дистрибутив → Linux x64» явно выбирает `--target linux-x64 --channel dev`
и выполняет полный релизный рецепт.
Она фиксирует tracked dirty/staged и неигнорируемые untracked, затем создаёт независимые
server/web/build/verify копии. Рабочие node_modules, bin и web/dist не меняются.
Node/npm берутся из закреплённого SHA архива. HOME/XDG/cache и окружение стадий изолированы.
Каждый scope получает короткий приватный TMPDIR в `/tmp/gd-dist-*` (0700).
В Unix-сокет Linux помещается 107 байт пути и завершающий ноль. Вложенный путь
до сокета Kimi занимает 104 байта под этим префиксом. Scratch удаляется после завершения
процессов. Рабочие копии, журналы и receipts сохраняются в artifacts. Linux-кандидат после
проверки переносится в `dists/dist-build-*/release-artifacts/` папки данных. На Apple Silicon
кандидат сохраняется в папке прогона. Кэш pinned Node (`deepseek-node-cache`)
находится рядом с деревом тестовых результатов (`deepseek-tests`), вне области их уборки.
Уборка большого dependency cache под общим барьером не должна блокировать запуск runtime.
Системную подготовку одноразовой Ubuntu 24.04 выполняет владелец через
`bash tools/ci/provision-ubuntu.sh --disposable-environment`; doctor ничего не устанавливает.
Для локальной сборки AppImage он проверяет curl, unzip и 7z. Подготовка Electron
и инструментов AppImage использует те же закреплённые архивы, что CI.

Общий `tools/releaseRecipe.json` исполняется `tools/releasePipeline.mts` локально и в Actions.
Успех обязательных стадий определяется exit code. Ошибка не разрешает bundle;
отмена 130/143 и timeout 124 не становятся skipped после exit 0 ребёнка.
Журналы и receipts сохраняются в artifacts, recipeDigest покрывает код runner,
подготовки окружения и provisioning. Receipt фиксирует фактическое окружение.

«Дистрибутив → Linux x64» и прямой нативный `dist build` показывают процент
успешно завершённых стадий, текущую стадию, последнюю строку её вывода и папку журналов.
100% появляется после записи `verified`. Полный вывод стадий сохраняется в `pipeline-*.log`
и `bundle.log`. При `TERM=dumb` шкала печатается при смене стадии вместе с обычным выводом.
Запуск через pipe и Actions сохраняют потоковый вывод команд.

Локальный кандидат подписывается временным ключом только в копиях исходников.
Сборка сначала сверяет отпечаток API исходного снимка. После подстановки временного ключа
она пересчитывает отпечаток в каждой копии, сохраняя номер API и исходный снимок.
Приватная запись `artifacts/distribution-runs/<UUID>/run.json` закрепляет ключ, sourceDigest,
recipeDigest и точные байты файлов. `verified` записывается после автоматической установки
всех режимов и бинарных проб; GUI-приёмка остаётся отдельной.

- `dist check --local-run <UUID>` и `dist install --local-run <UUID> --mode …` доверяют своей записи.
- `dist check --from <каталог>` и `dist install --from <каталог> --mode …` доверяют только
  pinned ключу продукта. Commit берётся из release-checks.json Actions или `--commit`.
- `dist doctor` запускают отдельно из корня исходников по необходимости. Поле `ok` показывает,
  выполнены ли обязательные условия, а `checks` содержит результаты отдельных проб.
  На Apple Silicon сборка сама проверяет хост перед созданием снимка и выполняет проверку
  `--require-native-ready` в релизном рецепте с подготовленным окружением.

Меню проверки и установки сначала выбирает источник. Для установки пользователь явно
задаёт корни и подтверждает тестовый профиль; рабочие launchers не подставляются молча.
Official check не пересобирает и не переподписывает скачанные файлы.
Publisher отвергает local-build.json независимо от заданного ключа.

## Публикация и граница приёмки

Stable .deb несёт те же восемь файлов в `/usr/lib/grigdesk`. Его launcher
при первом открытии обычным пользователем вызывает `install local --launch --source-dir /usr/lib/grigdesk`.
Последующие открытия используют launcher из профиля пользователя. Удаление системного
.deb сохраняет программу и данные в пользовательских каталогах. Dev и локальный dist
по умолчанию пакуют лёгкий сетевой .deb. APT нужен для установки системной оболочки,
а штатный updater использует официальный канал после возвращения сети.
Проверка publisher проходит до SSH; immutable версия сравнивается побайтно при повторе.
Индекс переключается последним. После успеха остаются текущая и предыдущая лёгкие версии
каждого канала; исторические полные комплекты без helper.gz исключены из retention.
До SCP требуется свободное место не меньше двух размеров выпуска; staging старше семи дней убираются.

Promote скачивает точный artifact id успешного release-workflow и повторно проверяет
commit/version/channel/digest. Для стабильной публикации дополнительно сверяются
общий proof и байты Linux x64 до доступа к SSH. Сборка и новая подпись отсутствуют.
Полномочия подписанта
доступны только build, SSH — только publish после verify.
[Контракт workflow](release-workflow-validation.md).

Автоматические проверки со stub-компиляторами не подтверждают настоящий SEA/AppImage.
Реальный полный кандидат, Actions, чистая VM, настоящее окно и публикация учитываются
отдельно. Публикацию приложения и синхронизацию сайта поручает владелец после приёмки.
