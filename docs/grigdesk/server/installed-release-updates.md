# Обычная установка и подписанный выпуск

Официальный вход `tools/bundle.mts` использует `executeInstalledBundle`. Выход
`release-artifacts/` содержит shell `grigdesk-install`, отдельный `grigdesk-maintenance.gz`,
его суммы/подпись, `desktop.tar.gz`,
`server.tar.gz`, `control.tar.gz`, `release-acceptance.json` и индекс выбранного канала. Исторический
локальный сборщик portable-комплекта сохранён без публикации; официальный выпуск
не создаёт переносимый комплект и не собирает исходники при установке.

Серверный архив включает отдельные `bin/grigdesk-server`, `bin/tracker`, `bin/pipeline`,
`bin/routes`, `bin/voice`,
`bin/grigdesk-relay` и `bin/deepseek`. Утилиты tracker, pipeline, routes, voice и relay собираются Go.
По пути `control/bin/grigdesk-ctl` собирается отдельный Go CLI, а стабильный Go helper
поступает через `grigdesk-maintenance.gz`. Исходники речевых моделей в архив не входят.
Подписанная опись закрепляет размер, SHA256 и права каждого файла.

## Номер и доверие

`VERSION` остаётся базовым X.Y.Z. CI до сборщиков проверяет ref: release требует
main либо `vX.Y.Z` с совпадающим VERSION/commit; dev требует ветку dev и даёт X.Y.Z-dev.N.
Build identity один для server manifest, payload VERSION, help, web и desktop main.
Inputs workflow включают channel, publish=false, ручной test_mode=full/skip и notes — JSON с ru/en.
`GRIGDESK_RELEASE_NOTES_JSON` поступает в подписанный payload; пустое описание — null.

Индексы разделены: `/api/releases/v1/release.json` и `/api/releases/v1/dev.json` —
единственная версия API каналов (прежний переносной `channel.json` удалён до первого
выпуска). Payload содержит identity, notes, API, платформу и три компонента формата v3.
Опись включает пути, размеры, SHA256 и права. Ed25519 подписывает domain separator,
LF, canonical JSON payload и завершающий LF. Общие проверяющие находятся в `shared/node` и `utilities/internal/installation`;
пустой pinned key запрещает доверие.

Сеть ограничена HTTPS, запретом redirects, пятью секундами на источник и 1 MiB документа.
Cache/single-flight относятся к выбранному каналу. Проверенный локальный cache доступен
новому процессу CLI; ошибка сохраняется отдельно от последнего результата и времени.
Publisher проверяет подписи/архивы до SSH, извлекает help из проверенного ELF, сохраняет
immutable версии и переносит выбранный индекс последним. Другой канал не изменяется.

Внутренний формат кандидата Apple Silicon задаёт `darwin`, `arm64`, минимум macOS 15.0
и отдельные пути компонентов `/releases/darwin-arm64/<версия>/`. Оконный tar включает
`GrigDesk.app.zip` и `GrigDesk.app.tree.json`. Подписанный объём распакованного дерева
входит в проверку свободного места. Внешняя опись и внутреннее дерево сверяются до
распаковки. Развёрнутый `grigdesk.app` проверяется ещё раз по размеру, режиму и SHA
файлов, целям внутренних ссылок, архитектуре Mach-O, bundle ID и подписи кода.
Publisher сайта принимает Linux x64. Нативная приёмка кандидата macOS проходит отдельно.

Новый [лёгкий установщик](lightweight-installer.md) скачивает helper и только выбранные
компоненты. Архивы больше не встроены в ELF. Проверка кандидата — `dist check --from`
или `--local-run`; прежний tail-reader сохранён для исторических файлов.

## Указатель v2 и переход на Go

В новом корне `current.json` формата 2 фиксирует роли desktop/server, путь control
и версию первого Go-поколения в поле `floor`. Установщик готовит приватный соседний
каталог и записывает intent до атомарного появления корня. `current` становится
доступен после регистрации launchers и службы. Служба после чистой установки
не запускается автоматически.

Для зарегистрированного прежнего helper нужен отдельный допуск `--migrate-to-go`.
В автоматизации он используется вместе с `--yes --expected-current-sha <sha256>`.
SHA относится к исходным байтам всего `current.json`, включая обе роли.
Go helper служит границей перехода. Старые канонические пути уходят в quarantine,
а переключение продолжает сохранённую цель. Для применения после переключения
нужны нативные доказательства запуска.

## Linux x64 с локальным источником

CI собирает `grigdesk-X.Y.Z-linux-x64-offline.zip` и `grigdesk_X.Y.Z_amd64.deb`
из стабильного подписанного комплекта. Оба содержат установщик, его detached proof,
helper, индекс и три архива компонентов. Из ZIP запустите установщик с
`--source-dir "$PWD"`. Ярлык из .deb впервые указывает на `/usr/lib/grigdesk`,
затем вызывает пользовательский launcher. Источник пакета сохраняет stable receipt
и установленный ключ. Можно подготовить обновление из следующего ZIP или
вернуться к штатному обновлению через подписанный канал сайта после подключения.
Установку с отключённой сетью, новое поколение и сохранность данных владелец
принимает в чистой VM. [Правила установки](lightweight-installer.md).

Остальная часть документа описывает протокол прежних зарегистрированных выпусков v2.

## Установка

Server-компонент включает `bin/pipeline` с подписанными size/SHA256 и режимом 0555.
Установленный `grigdesk-ctl pipeline` через maintenance ctl заново читает проверенные receipt/current,
выбирает `bin/pipeline` из `current.server` и заменяет процесс через execve.
Аргументы, stdin/stdio, сигналы и код выхода получает выбранный CLI. Папки данных и env-file
принадлежат receipt этой установки; явные GRIGDESK_URL/GRIGDESK_TOKEN сохраняют приоритет.
Следующий вызов после смены current выбирает новое поколение. Remote без server, отсутствующий
ELF, ссылка или небезопасный executable дают отказ 1 без source/PATH/другого поколения.


`install local|remote|server` принимает `--root`, `--data-home`, `--user-data`,
`--bin-dir`, `--applications-dir`, `--unit-dir`. Значения — абсолютные пути.
Default root — пользовательская папка программы, данные и Electron userData — отдельно.
Серверному режиму не нужны GUI, репозиторий или системный Node/npm.
Исторический сетевой .deb ставит `/usr/bin/grigdesk` и подписанный
shell-скрипт. Первое открытие инициирует пользовательскую установку в `~/.local`,
а дальнейшие обновления выполняет приложение.

Приватный installation.json связывает uid, физический root, installationId, канал и режим.
Один current.json содержит ссылки на неизменяемые компоненты generations/version.
Launchers вызывают удержанный update/maintenance и читают current при каждом запуске.
Повтор installer над своей регистрацией готовит update через тот же manager; такой же
установленный manifest проверяется без повторной замены. Чужая регистрация/ярлык/unit — отказ.
При переходе с прежнего descriptor требуется закрыть старый сервер; descriptor сохраняется
в программе как резерв. Данные и старую portable-папку установщик не удаляет.

Local создаёт descriptor v5 с идентификатором установки. Каталог команд определяется по current. Remote не создаёт descriptor, серверный компонент или unit.
Local/server получают user-unit с каноническим ExecStart, WorkingDirectory=I,
EnvironmentFile из D, KillMode=mixed и бюджетом слива 60 секунд. Регистрация не делает
самовольный enable/start; без user-systemd ctl использует manual launcher с PID/starttime lease.
I определяется из физического бинарника и проверенного receipt до загрузки server config;
ресурсы payload R и installationBin текущего поколения остаются отдельными путями.

## Подготовка и применение

Go maintenance хранит журнал под блокировкой установки. Job фиксирует requestId,
подписанный envelope/digest, scope, previous/target и исход. Desktop читает статус,
готовит handoff, подтверждает запуск и восстанавливает запись через закрытый JSON IPC.
При восстановлении helper проверяет инкарнацию нового владельца окна и сбрасывает
старое подтверждение worker перед новой попыткой.
На Linux helper связывает окно с AppImage своего поколения. Если процесс Electron
убрал `APPIMAGE` из начального окружения, helper проверяет FUSE-монтирование и
удержанный дескриптор AppImage. Путь, inode и версия должны совпасть с установкой.
Перед принятием handoff процесс обновления оставляет из унаследованных
дескрипторов только стандартные потоки. Служебная труба старого AppImage
тогда освобождает FUSE при выходе окна, а новое окно получает дескриптор
своего образа.
После подтверждённой остановки updater ждёт выхода оставшихся процессов
прежнего поколения. При гонке с закрытием FUSE он повторяет проверку процессов.
Указатель меняется после полного обхода без прежних владельцев.

Офлайн receipt v2 закрепляет исходный вид выпуска и SHA нормализованного публичного
ключа. Скачанный кандидат сохраняет maintenance от установленного поколения A.
Установщик B проверяет A и копирует свои архивы в отдельные временные файлы под
installation lock. Повтор продолжает тот же job. Сетевые проверить, сменить канал
и продолжить скачивание доступны установкам с источником channel.
У Apple Silicon при применении и откате записывается точная инкарнация запускаемого
окна. Дочерний maintenance ждёт permit после устойчивой записи, а CLI отката ждёт ACK
своей новой попытки. Нативные сценарии выхода, запуска и отката проверяются отдельно.
Потоковое скачивание проверяет размер/SHA; ustar-распаковка принимает только подписанные
ordinary files. Links, лишние записи, traversal и превышение объёма запрещены.
Пробы работают в отдельной HOME/D, до ready current и процессы остаются прежними.
Проба подтверждает identity: версию, releaseId desktop либо packageId server и валидный
JSON на stdout. У server метаданные `runtime` содержат объект Node ABI.
Строка `go` проверяется у `grigdesk-ctl` из control.
На Linux проба подписанного type-2 AppImage распаковывает его штатным
`--appimage-extract` в собственную временную папку и запускает оттуда
`AppRun`. Проверка identity получает stdout приложения отдельно от вывода
распаковщика. Для этой стадии FUSE не нужен.
Шум запуска в stderr (например, ERROR dbus/bus.cc у Electron пробы
без DBUS-адреса) подмену не доказывает и провалом не считается: фактический вывод
сохраняется в update/<job>/probe-<компонент>.log до любого отказа, включая отказ запуска.

InstalledApplication подключает автономный сервис к main до соединения с машиной.
Optional appUpdates и снимок передаются существующим shell long-poll, без нового SSE.
Local готовит пару, remote — desktop; scope и выпуск закрепляются за job. При смене
local/remote режима apply требует вернуться к подходящему профилю, цель не подменяется.

Apply требует отдельного intent и подтверждения последствий. Явная кнопка применения
показывает свежие числа ходов, очереди и задач; закрытие окна с готовым заданием
считает применение подтверждённым самим выходом и идёт без повторного диалога.
При активной работе exit-controller передаёт управление updater до обычного Stop
конвейеров и supervisor.stop; его 90-секундный deadline на время применения снимается.
Если обычный supervisor.stop уже начался, даже поздний ready не разрешает update:
его SIGKILL не подтверждает штатный drain. В portable Linux при отказе updater выход
продолжает Stop конвейеров и сервера со своим сроком, без повторной попытки применения.
На macOS местная установленная пара удерживает выход и показывает предупреждение,
если владение, допуск или renderer нельзя подтвердить. Закрытие окна и Cmd+Q
проходят тот же строгий допуск. Для дочернего сервера окно ждёт подтверждения выхода
обоих процессов, launcher и worker. Отдельно запущенный сервер той же установки
продолжает работать. Свёрнутое окно разворачивается для повторного решения.
Сигналы завершения, сбои подготовки и обычный запуск окна применение не запускают:
quit.stopping/exiting запрещают его и при закрытии последней заставки после ошибки старта.
Закрытый сервис не применяет сохранённый снимок. Кнопка применения и повторные события
выхода ждут один handoff, включая его отказ, даже когда снимок уже перешёл из ready в stopping.
Shared worker заново проверяет receipt, SHA/права, ресурсы, владельца, API и current-CAS.
После durable ACK он останавливает pipeline штатным Stop с бюджетом 20 секунд, затем
сливает сервер. Server shutdown записывает bound proof только после шагов и close Fastify;
forced exit, неизвестная активность и timeout не разрешают switch.
Если на macOS запрос остановки сервера или выхода старого окна уже отправлен,
а подтверждение потеряно, задание сохраняет intent в `manual_recovery_required`.
После запроса остановки worker оставляет допуск у сервера до его выхода
или проверки живого экземпляра штатным наблюдателем. Оператор может явно
запустить откат того же задания.

Main ждёт drain, сохраняет настройки/cookies и хвост stdout/stderr до своего exit.
Worker ждёт исчезновения старого процесса и одной записью заменяет current пары.
Worker и новые процессы запускаются в отдельных transient user-unit; без user manager —
в отдельных сессиях с собственными stdio. Завершение worker не завершает новое приложение.

Успех пары требует живого desktop ACK с nonce/build identity и серверного runtime-identity
с нужными version/packageId. Один новый диск или --version probe не означает completed.
Остановленный отдельный сервер остаётся остановленным: applied_not_started. Первый явный
start подтверждает runtime. Обычный запуск окна не применяет ready; пользовательское
закрытие применяет готовое задание только подходящего профиля до начала обычной остановки.

## Владение и восстановление

Shared installedServer проверяет точный unit, ExecStart/WorkingDirectory/installationId,
uid/PID/starttime и boot instance. Manual требует lease канонического launcher.
Чужой owner не получает stop/start. Зарегистрированная служба active/inactive имеет
приоритет над child supervisor; второй сервер не создаётся. Локальный сервер может быть
не запущен или поднят откуда угодно с любой папкой данных: осмотр определяет stopped
по отказу порта (ECONNREFUSED) ещё до чтения CLI-токена; живой порт без читаемого
токена установки даёт release_server_token_unreadable вместо сырого ENOENT.

При ожидании завершения `ENOENT` и `ESRCH` от чтения `/proc` означают, что процесс
уже завершился: он может исчезнуть между открытием `stat` и чтением его содержимого.
Worker продолжает подтверждённое обновление после выхода старого desktop.
`EPERM`, `EACCES` и другие ошибки доступа сохраняют отказ; PID с другим временем старта
или executable не считается прежним процессом и не получает сигнал.

Remote-сервер не получает update/stop/restart от updater окна. Offline desktop допускается
только при сохранении полного прежнего client API range; иначе ready требует связи с тем
же доверенным профилем. Настройки selected/pin/cookies остаются в прежнем userData.

Resume использует сохранённый envelope, а recovery сравнивает previous/target и возвращает
целое предыдущее поколение через того же владельца. Перед повторным запуском проверяется
подписанная опись retained generation. Ошибка rollback даёт manual_recovery_required.
Applied_not_started по умолчанию ждёт явного start; если новое поколение не запускается
на реальных данных, `resume-update --rollback` возвращает previous по явному согласию.
Успешное обновление удаляет свой staging (архивы, распаковки, пробы) и логи задания,
прореживая generations до current и previous; journal, данные и настройки сохраняются.
Старый portable recovery не подтверждает диск как runtime и не запускается
на registered-установке.

После подтверждённой смерти владельца installation lock общий механизм убирает его
и повторяет захват в том же вызове, включая `waitMs: 0`. Это действует при confirm,
apply и recover; живой или неизвестный владелец остаётся препятствием. Ручное удаление
блокировки для первого resume не требуется. [Контракт блокировки](../overview/directory-lock-recovery.md).

`GET /api/system/runtime-identity` закрыт общим auth guard. Update-drain требует CLI-токен
и bound intent/job/digest. Legacy package-update запрещён на registered-паре и направляет
server-only в CLI, чтобы старый клиент не обновил половину комплекта.

## Граница приёмки

Локальная сборка на Apple Silicon подготавливает нативный Node по
`server/build/node-runtime-darwin-arm64.json` и запускает группы `mac-prepare`,
`mac-check` и `mac-build` в отдельном снимке. Install и check сверяют
платформу по подписанному индексу. UUID локального запуска задаёт собственный ключ
и digest. При неизвестном состоянии дочерних процессов временный каталог
сборки сохраняется с путём в журнале.

Исходный и Android-клиенты сохраняют API 0.1; Android updater сюда не входит.
Ключ доверия и доступы CI/сайта задаёт владелец. Реальные Actions ELF/AppImage, публикация,
процессные fault-матрицы и браузерная приёмка обязательны перед пользовательским выпуском;
синтетические компоненты и зелёные прежние тесты их не заменяют.
