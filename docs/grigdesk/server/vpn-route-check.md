# Ворота VPN проверяют маршрут, а не конкретный клиент

По умолчанию ворота **отключены**: сервер стартует без проверки туннеля, и запуск на любой
машине не зависит от VPN. Включаются только явно — переменной `GRIGDESK_REQUIRE_VPN=1`
или разделом «Система → Запуск → Ворота VPN». Имя конкретного клиента в поставку не
зашито: включённые ворота смотрят фактический маршрут до пробы и автоматически принимают
интерфейс только тогда, когда ядро отмечает его как TUN.

## Управление из интерфейса

Раздел «Система → Запуск → Ворота VPN» (`web/src/views/settings/VpnGatePanel.vue`)
читает и пишет машинный `.env` через `GET`/`PUT /api/system/vpn-gate`
(`server/src/lib/vpnGate.ts`, запись — общий писатель `lib/envFile.ts`):

- переключатель «Требовать VPN при запуске» пишет явный `GRIGDESK_REQUIRE_VPN=1|0`;
- «Интерфейс VPN» и «Адрес пробы» пишут `GRIGDESK_VPN_IFACE` / `GRIGDESK_VPN_PROBE`,
  пустое значение удаляет ключ из файла (автоопределение и проба по умолчанию).

Поля ворот входят в общий черновик настроек. «Применить» сохраняет их одним PUT,
«ОК» сохраняет и закрывает окно; отмена отбрасывает неприменённый ввод. Отдельной
кнопки сохранения в панели нет. Ошибка записи сохраняет черновик для повтора.

Ворота исполняются **до** старта сервера (`ExecStartPre` юнита и окно-владелец), поэтому
запись не применяется к живому процессу. Вид настроек отдаёт и сохранённую конфигурацию,
и ту, с которой текущий процесс уже работает (`active`); при расхождении интерфейс
показывает предупреждение и признак `restartRequired` — новая конфигурация действует
после перезапуска сервера (кнопка «Перезапустить» в том же разделе).

Ручные переопределения в `.env` папки данных остаются для нестандартной схемы:

```dotenv
GRIGDESK_VPN_IFACE=wg0        # например, интерфейс без tun_flags
GRIGDESK_VPN_PROBE=1.1.1.1   # если стандартная проба не подходит
GRIGDESK_REQUIRE_VPN=0        # явное отключение (то же, что умолчание)
```

При включённых воротах и отсутствии подходящего маршрута `ExecStartPre` возвращает
ненулевой код, systemd не запускает сервер и повторяет через `RestartSec`. Когда VPN
появится, GrigDesk поднимется сам.

Проверяется **маршрут**, а не наличие интерфейса:

```
ip route get <probe-address>   →   ... dev <vpn-interface> ...
```

VPN-клиент может создать интерфейс РАНЬШЕ, чем расставит правила маршрутизации; в этом окне
интерфейс уже есть, а трафик ещё идёт напрямую — стартовать там означает ровно ту утечку,
ради которой ворота ставятся. Две тонкости, на которых легко ошибиться:

- у tun-устройств `operstate` = `unknown`, а не `up` (норма ядра). Требование строгого `up`
  не откроет ворота никогда;
- policy routing может зависеть **от владельца сокета** — проверка обязана идти от того же
  пользователя, что и сервер. Для `systemd --user` это выполняется само.

Чего ворота НЕ гарантируют: маршрут есть ≠ пакеты доходят. Если туннель поднят, а сервер на той
стороне мёртв, GrigDesk стартует без интернета. Это безопасное направление отказа — трафик уходит
в туннель и там умирает, наружу мимо VPN не течёт.

Ворота проверяются только перед стартом и не гасят уже работающий сервер при исчезновении
туннеля. Если машине нужен строгий runtime-binding, он добавляется локальным systemd drop-in с
`BindsTo=` к её device-юниту: в общий unit имя интерфейса не переносится. Такой режим обрывает
веб-интерфейс и открытые чаты-агенты при каждом коротком моргании туннеля.

`GRIGDESK_VPN_IFACE` читается и в рантайме: `server/src/lib/mobile/vpn.ts` проверяет маршрут
до посредника мобильной связи — глобальное отключение стартовых ворот не открывает публичный
dial релея. Новое значение интерфейса доходит и туда тоже только после перезапуска.
