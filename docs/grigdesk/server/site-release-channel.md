# Подписанные каналы выпуска с сайта

Единственный формат — подписанные v1-индексы каналов `/api/releases/v1/release.json`
и `/api/releases/v1/dev.json`. Формат, доверие, раскладка и текущие ограничения —
в [контракте обычной установки](installed-release-updates.md). Отдельного
`channel.json` переносимого комплекта больше не существует: стабильных выпусков
с ним не было, читатель и публикатор удалены; локальный сборщик прежнего комплекта
описан в [истории portable](portable-bundle.md).

## Ключ подписи

Публичный ключ SPKI PEM — константа `RELEASE_SIGNING_PUBLIC_KEY`. Пустой ключ даёт
`release_signing_key_missing` до скачивания, чужая подпись — `release_signature_invalid`.
`node tools/release-keygen.mts <абсолютный каталог>` создаёт приватный PKCS8 PEM
с правами 0600 и публичный SPKI PEM 0644. Повторная запись приватного ключа запрещена.
Приватный ключ в репозиторий не включается.

## Сборка и публикация

Workflow выпуска запускается только вручную через `workflow_dispatch`; отправка
коммитов и тегов не запускает сборку и публикацию. Первый шаг записывает
пути тестов и кеша из `$RUNNER_TEMP` в `$GITHUB_ENV` для следующих шагов; контекст
`runner` в `jobs.build.env` недоступен. Проверка конфигурации и диагностика писем
GitHub описаны в [валидации workflow](release-workflow-validation.md).

`node tools/release-publish.mts <абсолютный каталог выпуска>` публикует только
`release-artifacts/` обычной установки: подпись payload, архивы, описи и отдельная
подпись installer проверяются до любых SSH-команд (см. контракт установки).
`--dry-run` проверяет выпуск и печатает план без изменения файлов.

Настройки основного сайта: `RELEASE_SITE_HOST`, `USER`, `KEY`, `DIR`, `PUBLIC_ORIGIN`
с общим префиксом `RELEASE_SITE_`; необязательный `PORT` по умолчанию 22.
`KEY` для скрипта — путь к SSH-ключу. Зеркала используют наборы
`RELEASE_SITE_MIRROR_`, `RELEASE_SITE_MIRROR2_`, `RELEASE_SITE_MIRROR3_`.
На сайте заранее нужны `<DIR>/api/releases/v1/` и `<DIR>/releases/`.
SSH использует BatchMode и запоминает новый ключ хоста; изменившийся ключ отвергается.

Статическая раздача `/api/releases/v1/` нужна на каноническом origin, который читает
клиент, даже если `PUBLIC_ORIGIN` архивов принадлежит отдельному хосту. Переадресация
не заменяет эту раздачу: читатель канала запрещает redirects. Общая заглушка сайта
не должна перехватывать маршруты индекса, `/releases/` и публикуемой справки `/help/`.
Для nginx это отдельные `location ^~` с корнем каталога публикации и `try_files`;
до первого выпуска отсутствие индекса даёт 404, после публикации — подписанный JSON.

Одна удалённая транзакция берёт `.grigdesk-release-publish.lock`, проверяет состав,
выставляет immutable каталоги `releases/<version>/` и `help/<version>/`, затем
latest.html/latest.js и последним индекс канала. Повтор допускается с теми же суммами
и обоими языковыми корпусами; старые версии не перезаписываются.
Публикатор требует `help.json` (ru) и `help.en.json` (en) в серверном payload и сайте,
сверяет их байты, locale, version и commit с подписанным выпуском.
На основном сайте и зеркалах публикуется весь reader с обеими редакциями.
Повторная публикация сравнивает обе редакции до замены индекса канала.
SSH disconnect освобождает lock через
trap; SIGKILL может оставить каталог — владелец проверяет отсутствие publisher
и удаляет пустой lock вручную. GitHub сериализует ручные запуски общей concurrency group.

Основной хост обязателен, отказ зеркала даёт предупреждение. Коды: 2 — нет настроек,
3 — локальная проверка выпуска, 4 — отказ публикации основного сайта.
Оба канала содержат один origin артефактов: зеркало резервирует метаданные,
скачивание остаётся на основном origin. Рядом с installer публикуется собранный
deb-бутстрап `grigdesk_<version>_amd64.deb` (необязательный файл того же выпуска).

## Проверка

Чтение канала допускает только HTTPS, запрещает redirects, ограничено пятью секундами
на источник и 1 MiB тела. Успех кешируется на пять минут; после общего отказа —
пауза 30 секунд. Параллельные запросы разделяют одну операцию. Подпись конверта
проверяется тем же общим verifier до передачи данных менеджеру обновления.

Реальная сборка комплекта и открытие окна — ручная приёмка владельца.
Допуск GLM `api` также выполняет владелец отдельно; CI не имеет платного ключа и
не продлевает допуск. Сборщик сохраняет отказ `deepseek_glm_unadmitted` без допуска.

Workflow принимает необязательный notes в виде JSON с ru/en; сборщик получает его
через GRIGDESK_RELEASE_NOTES_JSON и включает в подписанный payload до публикации индекса.
Actions artifact содержит release-acceptance.json с явной границей runtimeAcceptance;
успешная упаковка не объявляет выполненной приёмку реальных процессов.

Владелец выбирает full/skip вручную в плане выпуска; версия не меняет выбор.
В skip причина видна в подписанном описании, а точная запись решения — в acceptance
артефактов Actions. Сборка с подписью, проверка скачанных пакетов и публикация разделены
границами jobs. Публикация использует artifact-id успешной сборки и запускается только
после обязательной проверки пакетов; повтор публикации не требует пересборки.
