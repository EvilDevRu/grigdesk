# Сборка служебных программ сервера

Здесь сохранён контракт helpers прежнего каталога R и перехода с исходников.
Их размещение в payload описано в [обзоре одиночного ELF](server-binary.md).

Каталог `server/build/helpers.json` задаёт id, исходный вход, вид запуска и exports
собственных служебных программ. `server/scripts/sea/helpers.mts` собирает их в ESM:
npm-зависимости остаются внешними, предупреждение esbuild останавливает сборку.
Сгенерированный вход передаётся через stdin с постоянным sourcefile и разрешением импортов
от корня исходников. Случайный workDir не попадает в комментарии или байты бандла:
[детерминированный вход](sea-helper-staging-comments.md).
Вид `library` сохраняет exports без вызова CLI; `script` сохраняет побочный запуск
скрипта, у которого нет guard по исходному URL.

Упакованный helper получает контекст `helper` через подмену `runtimeBuildContext.ts`.
Его физический URL определяет корень комплекта, вложенный Node и соседние helper-ы.
Контекст не выбирается переменной окружения. AST-плагин сохраняет прежние URL ресурсов
каждого исходного модуля после объединения файлов. Исключение — supervisor установки:
его self-fork использует фактический URL собственного ESM-файла.

Для входа `main` генератор сначала ставит маркер, затем импортирует модуль и вызывает
`main` один раз. Исходный guard `isDirectRun` учитывает маркер. Проверка URL исходника
без явного входа ненадёжна после преобразования: программа может успешно завершиться,
не выполнив работу.

`tests/server/sea/helpers.test.mts` проверяет перенос комплекта, чтение ресурса,
вложенный запуск, публикацию GLB, self-fork supervisor и результат ingest с модельной
заглушкой. `mcp.test.mts` в той же папке проверяет настоящий stdio-протокол собранных
permission/work MCP с локальными broker-ами, scope и отказом чужому nonce.

`server/build/compatibility.json` перечисляет прежние пути data-home, legacyBrand
и двух JS-мостов движка. Генератор создаёт в staging относительные import/re-export
на собранные helper-ы. Исходные bash-файлы движка при этом не меняются.
`bin/grigdesk-ctl` в комплекте выбирает вложенный Node и собранный CLI; при отсутствии
Node или готового b24 отказывает. Source-команды разработки сохраняют прежний вход.
Публикатор маршрутов остаётся внешним скриптом профиля; сервер выбирает для него
`nodeExecutable()`, сохраняя validate/publish, cwd, аргументы и ограничения времени.
Схему и хранилище маршрутов скрипт получает из library-helper-а `routes-publish-kit`: путь к его
файлу сервер передаёт в `GRIGDESK_ROUTES_KIT` (`helperModule` в `runtimePaths.ts`; вход `main`
или `script` так не отдаётся — его импорт запустил бы CLI).
