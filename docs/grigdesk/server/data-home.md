# Единая папка данных GrigDesk

GrigDesk хранит настройки и рабочие данные вне дерева кода. По умолчанию это
`~/.grigdesk`; непустая переменная окружения `GRIGDESK_HOME` выбирает другую папку.
Общее правило реализовано в `shared/runtime/dataHome.ts` и `deploy/lib/runtime-env.sh`.

Путь должен быть абсолютным, состоять из латинских букв, цифр и символов
`. _ + - / @ , = :`, не быть `/` и не содержать сегментов `.` или `..`.
Конечные `/` удаляются. Умолчание также проверяется: если домашний каталог содержит
пробелы или другие символы, задайте подходящую `GRIGDESK_HOME`, например
`/home/user/grigdesk-data`. Папка не должна совпадать с домашним каталогом,
лежать внутри кода или содержать его.

Папка считается явной, только если заданное нормализованное значение отличается от
`<домашний каталог>/.grigdesk`. Поэтому переданное сервером детям умолчание остаётся
неявным. Сервер создаёт папку и `state/` с правами 0700, приводит существующие права
к 0700 и передаёт детям канонический путь через `GRIGDESK_HOME`.

## Содержимое папок

Пути относительны папки данных. Умолчания вычисляет `server/src/config.ts`,
индивидуальные переменные `GRIGDESK_*_DIR` и `*_PATH` важнее их. Папки создаются
по мере надобности: отсутствующая папка означает, что функция на этой машине
ещё не использовалась. Рабочая папка агентов `artifacts/` описана
[отдельным разделом](#папка-артефактов) ниже. Краткая пользовательская версия
раскладки — в статье руководства [Данные и резервные копии](../guide/ru/data-and-backups.md);
она компилируется в справку релиза и доступна агенту через `grigdesk_help`.

### chats/ — история разговоров

Каждый чат — отдельный файл `chats/YYYY-MM/<id>.json`, где `YYYY-MM` — месяц
**создания** чата; при правках файл не переезжает. **Чтобы найти чат по ID**,
ищите файл `<id>.json` в папках месяцев; если месяц создания неизвестен —
просмотрите все папки `YYYY-MM/`. ID чата виден в адресе интерфейса и в
UI-контексте (`chatId`). Чтение переписки допускается только с явного
разрешения человека.

Остальное содержимое каталога:

| Путь | Назначение |
| --- | --- |
| `meta.json` | Дефолты новых чатов (модель, усилие, режим, рабочая папка) и недавние папки |
| `deleted.json` | Памятка удалений `{schema, deleted:[{id, at}]}`: последние 90 дней, не больше 2000 записей |
| `attachments/` | Загруженные вложения; в видимом списке папок хода каталог скрыт |
| `pending/` | Не забранные окнами итоги ходов, файл на чат |
| `turns/` | Журнал принятых по turnId ходов: файл на ход, хранение 7 дней |
| `in-turn/` | Durable-журнал уточнений внутри активного хода, файл на пару (чат, сообщение) |
| `in-turn-assistant/` | Ответы ассистента для проекции уточнений и прошлых запусков |
| `.bindings/` | Server-owned привязки сессий исполнителей (sessionId); клиент назначить их не может |
| `.web-heads.json` | Кэш каталога: шапки чатов и тексты поиска |
| `.migration-backups/` | Резервные копии одноразовых миграций |

Устройство хранилища, слияние и доставка — [хранилище истории](../chat/history-storage.md),
[доставка хода](../chat/turn-delivery.md) и [границы модулей уточнений](../chat/in-turn-module-boundaries.md).
Исходники: `server/src/lib/chat/historyStore.ts`, `turnLedger.ts`, `inTurnLedger.ts`,
`catalogCache.ts`, привязки — `modules/chat/index.ts`.

### state/ — состояние сервера

Настройки, креды и служебные хранилища (папка 0700, приватные файлы 0600);
пути определены в `server/src/config.ts`:

- `prefs.json` — общие настройки из UI; `models.json` — реестр моделей исполнителей;
  `usage-forecast.json` — ряды прогноза лимитов.
- `auth-sessions.json` — сессии входа; `cli-token` — токен локальных CLI-команд;
  `grigdesk-update.json` — состояние применения обновлений.
- Ключи исполнителей и каналов: `claude-auth.json`, `telegram-account-creds.json`,
  `github-creds.json`, `tracker-credentials.json`.
- `ssh/` — SSH-профили, известные хосты и журнал команд; `db/` — профили БД и журнал запросов.
- `tracker-settings.json` и `tracker-data/<id>/` — настройки и данные трекеров.
- `tickets/`, `sandboxes/`, `factory-task-sources.json`, `arbiter-cards.json`,
  `arbiter-conversations/`, `task-favorites.json`, `task-shelf.json`, `task-seen.json` —
  задачи Б24, стенды и конвейер.
- `provider-installs/`, `provider-usage-seen.json`, `external-cli-factory.json`,
  `npm-global/` — установка и использование внешних CLI исполнителей.
- `plugin-installs.json` и `plugins/<id>/` — состояние установок и рабочие данные
  пользовательских плагинов.
- `driver-installs.json`, `db-engine-installs.json` — состояние установок драйверов и движков БД.
- `media/`, `media-venv/`, `hf/`, `speech-install/` — речь: задания, Python, модели, установка.
- `showcase/`, `showcase-auth/`, `showcase-browser/` — «Презентации»: ролики, снимок
  входа тестовой учётки, браузер записи.
- `mobile-apk/` — APK и описание выпуска; `web-log/` — дневной журнал окна (NDJSON).
- `grigdesk-server.log` и его `.gz`-части — журнал сервера ([ротация](log-rotation.md));
  `server.lock` — владелец папки данных.
- `ui-releases/` — прежние UI-версии; новым сервером не используются.

В папке могут оставаться файлы прежних версий продукта — это история, а не текущая
раскладка; текущий код их не пишет.

### factory/ — конвейер

Состояние движка и доверенные каталоги: `state/` (включая homes исполнителей
`grigdesk-deepseek`, `grigdesk-glm`, `grigdesk-kimi-contained`), `control/`, `config/`,
`routes/` (опубликованные маршруты) и `routes.authoring/` (черновики), `analysis/` —
триаж задач. Переопределения путей перечислены в разделе «Что остаётся снаружи»;
устройство — [конвейер](../pipeline/README.md).

### qwen-runtime/ — homes сессий Qwen Code

Каждая связка чата и рабочей области получает свой home: `qwen-runtime/<hash>/`,
в host-режиме — `qwen-runtime/host-builtin-v1/<hash>/`. Hash — sha256 связки
(chatKey, рабочая папка, отпечаток конфигурации, дополнительные папки). Внутри —
`session.json` с привязанным sessionId исполнителя и `.qwen/` — runtime-каталог
Qwen Code (память, проекты). Чужой sessionId не принимается: home выбирается
точным совпадением сохранённой сессии (`server/src/lib/qwen/session.ts`, `host.ts`).

### runtimes/ — кэши поставок

`runtimes/server/` — приватный кэш автономного сервера, `runtimes/deepseek/` —
кэш распакованных поставок DeepSeek (`packages/` — проверенные поколения,
`releases/` — резервные ELF). Корневая папка `deepseekRuntime/` — прежнее место
кэша: текущий код использует только `runtimes/deepseek`.

### profiles/ — проектные профили фабрики

Проектные профили бинарной поставки; запуск из исходников держит профили
в `<код>/profiles`, явная `FACTORY_PROFILES_DIR` важнее обоих умолчаний.

### plugins/ — установленные пользовательские плагины

`plugins/<id>/plugin.json` (плюс `server.js` и собственная документация
`docs/README.md`). Рабочие данные плагина живут отдельно в `state/plugins/<id>`
и сохраняются при обновлении.

### drivers/ и db-engines/

`drivers/` — внешние драйверы трекеров (реестр, папка на драйвер,
`server/src/lib/trackers/runtime.ts`); источники перечислены в `driver-sources.json`
корне папки данных. `db-engines/` — внешние движки баз данных, активируются
при следующем старте сервера. Состояние установок — `state/driver-installs.json`
и `state/db-engine-installs.json`.

### telegram/ и github/ — архивы входящих

Архивы входящих сообщений: NDJSON по месяцам плюс индекс, настройки и привязки
аккаунтов. Токены и секреты лежат отдельно в `state/` (`telegram-account-creds.json`,
`github-creds.json`). Устройство — [входящие](../inbox/README.md).

### mobile/ — доступ телефона

TLS-ключи мобильного входа, `devices.json` — реестр устройств, `phone-access.json` —
настройка доступа, `relays.json`, `relay-deployments.json`, `relays/` и `operations/` —
состояние посредников и операций. Устройство — [приложение на телефоне](../mobile/README.md).

### 3d/ — библиотека 3D

Файлы раздела «3D» (плагин studio3d): модели и сцены в папках проектов. Библиотека
отделена от чатов и проектных деревьев; плагин открывает её только после включения.

### browser/ и provider-cli-leases/

`browser/relay.sock` — приватный сокет браузерного relay: один data home задаёт один
listener независимо от поколения движка; длинный путь получает короткий hashed путь
в `/tmp` (`server/src/lib/browser/factoryBrowserRuntime.ts`). `provider-cli-leases/` —
leases копий внешних CLI исполнителей: живые сессии держат копию, lease защищает
её от удаления во время работы (`server/src/lib/providerInstall/service.ts`).

## Что остаётся снаружи

- Фабрика — внутри папки данных: `factory/state`, `factory/control`, `factory/config`,
  `factory/routes` и `factory/analysis`; homes исполнителей — внутри `factory/state`.
  Умолчания сервера указывают туда же, явные `FACTORY_STATE_DIR`, `FACTORY_CONTROL_ROOT`,
  `FACTORY_CONFIG_ROOT`, `GRIGDESK_ROUTES_DIR` и `GRIGDESK_ANALYSIS_DIR` важнее. Прежний
  корень `~/.factory` после переноса не существует. Собственные фоллбэки движка при
  запуске без окружения всё ещё помнят старый путь: сервер всегда передаёт пути явно,
  отказ от старого пути в самом движке — отдельное изменение. Запуск из исходников
  по-прежнему держит проектные профили в `<код>/profiles`, а бинарный комплект пишет
  новые профили в `<папка данных>/profiles`: его корень `R` доступен только для чтения.
  Явная `FACTORY_PROFILES_DIR` важнее обоих умолчаний.
- Установленное окно `<код>/bin/grigdesk-app`, его `runtime.json` в
  `~/.local/share/grigdesk/desktop`, каталог данных окна `~/.config/GrigDesk`: это клиентская
  программа.
- Разработка: Android SDK, Gradle, загрузки, ключи подписи APK и состояние DevLink. Неиспользуемые каталоги прежней конфигурации не удаляются.
- Сборки и ресурсы кода: `node_modules`, `web/dist`, legacy generation DeepSeek,
  `third_party`, `bin/grigdesk-relay`, `desktop/release`.
  Обновлятель получает отдельный `--work-root <код>/.state` для временной копии git.
- Homes внешних исполнителей: `~/.claude`, `~/.codex`, `~/.kimi-code`.

Распакованная автономная поставка DeepSeek — данные в `runtimes/deepseek`,
в отличие от legacy generation в дереве кода. Явный абсолютный `--cache-dir`
выбирает другой приватный кэш; относительный путь отвергается без fallback.
Внутри `packages/<packageId>/` лежат проверенные поколения. Они не удаляются
автоматически при ошибке или появлении нового выпуска.

У [сервера одним ELF](server-binary.md#раскладка-i-d-и-r) различаются физическая
установка I, папка данных D и поколение R внутри `D/runtimes/server/packages/<packageId>`.
Guard сверяет D с I; штатный R внутри D не считается исходным деревом. R содержит только
проверенные ресурсы, а изменяемые профили и история остаются вне него. Владение поколениями,
продолжение попыток и ручная уборка описаны в [контракте кэша](server-binary-cache.md).

## Папка артефактов

`artifacts/` — рабочая папка агентов и инструментов вне дерева кода; явная
`GRIGDESK_ARTIFACTS_DIR` важнее (`artifactsPath` в `shared/runtime/dataHome.ts`, `config.artifactsDir`).
Сервер создаёт её с правами 0700 и добавляет к каждому ходу чата как дополнительную папку с
правом записи; в видимом списке папок хода она скрыта, как каталог вложений. Kimi её не получает:
его изоляция не пускает каталоги папки данных. Картинки из неё показываются в чате, документы
открываются. Скрипты проверок и тесты берут базу через `artifactsPath`; сторож памяти передаёт
тестам настоящую `GRIGDESK_ARTIFACTS_DIR`, хотя `GRIGDESK_HOME` у них временная. Прежняя
`<код>/.state/artifacts` в выдаче картинок допускается ради старых сообщений.
Обычные ходы на Linux используют [отдельные папки запусков](../chat/artifact-runs.md).
Связи с чатами и срок хранения лежат в `state/chat-artifact-runs/`.

## Настройки и окно

Все читатели выбирают `GRIGDESK_ENV_FILE`, иначе `<папка данных>/.env`:
сервер, окно, CLI, запускалки, установщик речи и Vite при разработке. Юнит получает
выбранный путь в `EnvironmentFile`. Сборка Vite этот файл ради порта не читает.

`GRIGDESK_HOME` и `GRIGDESK_ENV_FILE` внутри файла запрещены, даже с пустым значением:
файл не может выбирать собственное место. Сервер отказывает с кодом 78,
CLI и bash — с кодом 1, окно сообщает ошибку описания установки.
Присутствующая переменная окружения, даже пустая, важнее значения файла.
Сервер читает файл до конфигурации; импорт `config.ts` сам данных не читает и не пишет.
`NODE_OPTIONS` и `NODE_EXTRA_CA_CERTS` для самого процесса требуют загрузки окружения
до запуска Node: через окно, юнит или `grigdesk-ctl`.
В одиночном ELF раннюю `.env` читает launcher перед стартом собственного Node worker;
`NODE_EXTRA_CA_CERTS` действует с его запуска, а `NODE_OPTIONS` удаляется.

Изменения делает [общий писатель](env-file-writer.md), в том числе через совместимую
ссылку из дерева кода. Ключи исполнителей, сохранённые окном, применяются сразу;
ручная правка машинных настроек требует перезапуска.

Перенос 16.10 добавлял отсутствующие переходные ключи путей для старой сборки окна.
Команда brandMove удаляет их, если значения совпадают с новыми умолчаниями.
Новое окно читает source descriptor версии 1 (`root`, `node`) либо 2
(`root`, `node`, `home`), готовый SEA — через версию 3 (`kind: sea`, `root`, `home`),
а одиночный ELF — через [версию 4](server-binary-desktop.md)
(`kind: binary`, `binary`, `home`, `cliPaths`). В версиях 2/3/4 `home` важнее окружения окна.
Версия 4 не хранит packageId/R: они получаются заново при каждом старте.
Сервер не раздаёт UI: встроенный пакет
приложения обслуживает локальная труба, прежние `state/ui-releases` не используются.
Установщик source-сервера
сначала пишет версию 1, заменяет AppImage, затем при явной папке пишет версию 2.

Перенос 16.10 завершён, инструмент `moveDataHome` удалён.

## Ранний старт и блокировка

Первый синхронный импорт приложения проверяет путь и старую раскладку, затем создаёт
папку, канонизирует путь, читает `.env` и берёт блокировку. При неявной папке
оставшиеся данные в коде, неверная совместимая ссылка либо незавершённый журнал
переноса дают код 78 с командами переноса или возврата. Вторая копия репозитория
(git worktree, где `.git` — файл) без своей явной `GRIGDESK_HOME` не стартует: иначе стенд
при закрытом окне поднялся бы на настоящих данных. Журнал старой сборки окна в
`<код>/server/.state` (`grigdesk-server.log*`) старой раскладкой не считается. Проверка
размещения пути действует и при явной папке.

`server/scripts/dataHomeCheck.mts` проверяет те же условия без создания файлов
и запуска сервера: код 0 — можно продолжать, 78 — отказ с причиной. Пишущие
запускалки вызывают его до действий. Юнит содержит `RestartPreventExitStatus=78`.
До переноса после обновления кода сервер не перезапускать и окно не закрывать.

`state/server.lock` создаётся атомарно с правами 0600 и содержит `pid`, `starttime`,
`root`, `startedAt`. На Linux время старта читается из `/proc`. Если оно недоступно,
живой PID удерживает lock. В коде Darwin start token и состояние выдаёт проверенный
нативный helper, а неопределённость сохраняет lock. Этот путь ждёт проверки на macOS.
Второй сервер ждёт до
`GRIGDESK_LOCK_WAIT_MS` (по умолчанию 15 секунд), затем выходит с кодом 78.
Мёртвая или повреждённая блокировка переименовывается в уникальное имя, сверяется и
заменяется новой. При выходе сервер снимает только собственную блокировку;
после SIGKILL её разбирает следующий старт. `restart.sh` ждёт выхода PID до 45 секунд,
а не только освобождения порта.

## Команды и тесты

До переноса старые CLI-токен и `.env` читает только CLI `grigdesk-ctl`: пока в папке данных
нет токена или файла настроек, а на старом месте — настоящий каталог или файл. Пустая папка,
созданная раньше времени, это чтение не отрезает. `b24` старую раскладку не читает
([команда b24](../b24/binary-cli.md)): с явными `GRIGDESK_URL` и `GRIGDESK_TOKEN` папка данных
ему не нужна, без токена он отказывает до HTTP-запроса и называет ожидаемый путь.

Сторож памяти создаёт временную `GRIGDESK_HOME`, проверяет её и удаляет после прогона.
Он же снимает `GRIGDESK_ENV_FILE`, `GRIGDESK_UI_RELEASES_DIR` и `GRIGDESK_LOG`, которые сервер
передаёт агентам из `.env`. Фикстуры сервера задают собственные HOME и GRIGDESK_HOME внутри
`os.tmpdir()`; песочницы CLI и ярлыка наследуют окружение, но заменяют HOME, XDG и
GRIGDESK_HOME. Проверки systemd используют
заглушки. Ядро переноса при `NODE_TEST_CONTEXT` дополнительно запрещает реальные
пути. Сканер миграции кода исключает корневые каталоги данных до обхода; сторож
`data-home-paths` проверяет построение путей только в исходниках.

## Ограничения

- Старые тексты чатов и комментарии Б24 сохраняют абсолютные пути вложений. После
  переноса они указывают на прежнее место; превью по имени файла работают.
- Рабочую папку чата внутри прежних `plugins/` или `3d/` нужно выбрать заново; рабочая
  папка Kimi в режиме contained внутри папки данных отклоняется.
- Файлы `.env` внутри рабочей папки Kimi contained не маскируются (маскируются только
  каталоги): копия со своей явной `GRIGDESK_HOME` и настоящим `<копия>/.env` видна агенту.
- Перенесённые `bin/pip` и `activate` venv содержат прежние пути и после уборки ссылок
  не работают; вызов через `bin/python` работает, включая `bin/python -m pip`.
- Собственные файлы плагинов (запускалки, конфигурации в `state/plugins/<id>`) перенос не
  переписывает. Абсолютный путь к прежнему `<код>/plugins/<id>` ломается сразу: ссылки
  совместимости для `plugins/` нет. После переноса такие места находит
  `rg -l '<код>/plugins/' <папка>/state/plugins <папка>/plugins`.
- Записи процессов заданий (`identity.cmdline`, `process.cmdline`), рабочие файлы завершённых
  заданий и `task.mediaHfDir` старых заданий речи сохраняют прежние пути. Это история:
  на работу и на `--drop-links` она не влияет.
- Перенос и работа на реальных данных требуют действий владельца. Тесты проверяют
  временные фикстуры; они не означают, что данные установленной копии уже перенесены.
