# Окружение и проверка серверного комплекта

При packaged boot окружение дочерних процессов строится общим
`shared/node/packagedEnvironment.ts`. Каталог собственного Node стоит последним в PATH;
установленный Node пользователя сохраняет приоритет. Внутренние helpers GrigDesk
запускаются явным путём к вложенному Node и от PATH не зависят.

`PYTHONDONTWRITEBYTECODE=1` запрещает Python писать `__pycache__` в R, в том числе при
вызове `engine/bin/factory-route`. Глобальный npm использует `D/state/npm-global`,
если пользователь не выбрал абсолютный `npm_config_prefix` вне R. Приоритет Node
не направляет обычный `npm -g` в `R/runtime/node`. Те же правила применяются к окну,
ручному запуску и службе; source-режим сохраняет своё окружение.

Обычный запуск окна/CLI вызывает `--check-startup`: проверяются canonical contentId
manifest, платформа/ABI, наличие всех файлов, размеры, биты исполнения, внутренние
ссылки, хеш SEA и собственного Node. Хеши библиотечных файлов при этом не читаются.
`--check-runtime` сверяет все хеши потоково; он используется при явном `use-server`,
сборке и приёмке комплекта. Обе проверки не запускают сервер и не обращаются к D.

Изменённый или удалённый файл manifest запрещает полную проверку. Добавленный файл
даёт запись в `warnings`, сохраняя `ok=true`; сторонний `__pycache__` игнорируется.
Права записи группы не определяют целостность: сравниваются биты исполнения.
Manifest проверяет согласованность самого себя, внешнего якоря доверия у него пока нет.

Тест `sea/writable.test.mts` использует отдельную копию архива с доступным на запись R.
Из настоящего терминала он вызывает factory-route и npm, проверяет окружение и отсутствие
pyc, повторяет boot и полную проверку. Остальные namespace-сценарии сохраняют read-only R.
Точные границы изоляции описаны в [приёмке комплекта](sea-isolation.md).
