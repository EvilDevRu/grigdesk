# Ротация и чтение журналов

Общий уровень диагностики управляет подробностью сервера, фабрики и журнала окна.
Обязательные журналы действий модулей и история разговоров имеют собственные
контракты; описанная здесь ротация не удаляет их.

## Вывод сервера

Приложение и `deploy/restart.sh` собирают stdout/stderr серверного процесса через
`shared/node/rotatingLog.ts`. Трубы имеют backpressure; gzip выполняется потоком.
Сервер и его потомки не держат файловый дескриптор уже закрытой части журнала.

Путь — `GRIGDESK_LOG` либо `<папка данных>/state/grigdesk-server.log`.
Активный файл ограничен 10 МиБ, закрытые части получают имена
`grigdesk-server.log.<16-значный номер>.gz`. Номер возрастает и сохраняет порядок
между запусками. По умолчанию остаётся до десяти архивов; бюджет активного файла
и архивов — 100 МиБ. При запуске и ротации сначала удаляются самые старые части,
в том числе архивы старше 14 суток. Во время сжатия требуется дополнительное
место для закрытой raw-части и временного gzip.

Новые файлы имеют 0600, новый каталог — 0700. При запуске прежний `.1`
импортируется в архив. После аварии `.raw` остаётся доступным для чтения,
незавершённый `.gz.tmp` пересоздаётся из него при следующем запуске. Старый gzip
и новые записи не перезаписывают друг друга.

В desktop один потребитель на путь обслуживает все поколения собственного
сервера. Выход приложения даёт трубам до пяти секунд на хвост после выхода
сервера и дожидается записи принятых байтов. При отказе журнала
вывод переключается в stderr приложения, чтобы не заблокировать трубы сервера.
Ручной launcher `run-logged-server` передаёт SIGTERM/SIGINT своему ребёнку,
дожидается закрытия труб и сохраняет исходный код выхода.

Служба systemd продолжает писать в journald: ротация и срок хранения задаются
политикой ОС. Прямой запуск команды сервера с внешним `>> file` также оставляет
управление этим файлом запускающей стороне; для штатной файловой ротации
используется приложение или `deploy/restart.sh`.

Чтение на машине сервера:

```bash
tail -F <папка данных>/state/grigdesk-server.log
zcat <папка данных>/state/grigdesk-server.log.*.gz | less
journalctl --user -u grigdesk-server --since '2 hours ago'
```

Последовательные серверные части — байтовые отрезки потока: полная строка может
проходить через границу частей. Для полного разбора соединяйте архивы по имени
и активный файл после них.

## Журнал окна

Каталог — `GRIGDESK_WEB_LOG_DIR` либо `<папка данных>/state/web-log`.
Активный файл UTC-дня — `YYYY-MM-DD.ndjson`. После заполнения 20 МиБ он сжимается
в `YYYY-MM-DD.ndjson.<номер>.gz`, запись продолжается в активный файл этого дня.
Строки NDJSON не разрезаются. Одна допустимая запись может превышать заданный
в тесте размер части; production-лимит 20 МиБ значительно больше предела записи.

Суточного отказа после первых 20 МиБ больше нет. Остаются текущий и 13 предыдущих
UTC-дней, до 128 архивных частей и 280 МиБ суммарно. При заполнении бюджета
удаляются самые старые файлы, поэтому сохранённый период может быть короче
14 дней. Уборка выполняется при запуске, записи и по суточному таймеру.

Скачивание дня через прежний API и CLI автоматически раскрывает gzip и соединяет
части в хронологическом порядке. Прежние дневные файлы читаются без миграции.
Открытое скачивание фиксирует inode и размеры всех частей: последующая запись,
ротация или удаление по лимиту не меняет его содержимое. Два прохода CLI для
дедупликации используют один снимок.

```bash
node server/scripts/web-log.mjs --day YYYY-MM-DD --json
node server/scripts/web-log.mjs --since 2h --level warn --dump
```

Подробный контракт — [журнал окна](../web/window-log-contract.md), действия
человека — [руководство](../guide/web-log.md).

## Проверки и применение

`tests/server/log-rotation.test.mts` проверяет сохранность байтов, пределы,
права, запрет симлинков, восстановление после аварии, импорт `.1`, обе трубы,
IPC и код ручного запуска. `web-log-store`, `web-log-reader`, `web-log-api`
проверяют продолжение записи, UTC-очистку, дедупликацию и стабильность скачивания.

После обновления кода сервера требуется ручной перезапуск. Изменение desktop
применяется после сборки и установки нового окна и его ручного перезапуска.
Работающее приложение и сервер агент не перезапускает.
