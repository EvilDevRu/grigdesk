# Порт владельца процесса на Darwin

На Darwin код получения идентичности процесса использует небольшой Mach-O helper.
Он сравнивает PID, UID, start token, PPID и PGID по `PROC_PIDTBSDINFO`, получает SID
и путь исполняемого файла. Start token сохраняет секунды и микросекунды как
числовую строку. Ошибка доступа или неполный ответ остаются неизвестным состоянием.
Порты directory lock, серверных leases и maintenance используют одну форму владельца.

Server launcher и maintenance вкладывают helper и ожидаемый SHA-256 в собственные
SEA-ресурсы. Перед пробой ресурс проверяется и пишется в приватный временный
каталог. После пробы каталог удаляется. Серверный worker получает собственную
копию из проверенного дерева payload. Исходные сборщики принимают путь и SHA
через `GRIGDESK_BUILD_PROCESS_HELPER` и `GRIGDESK_BUILD_PROCESS_HELPER_SHA256`
после проверки приватного физического каталога, владельца, режима и байтов.

`tools/darwinBuildTools.mts` готовит `process-identity` и `setsid` для ARM64 с
deployment target macOS 15.0. В режиме permit `setsid` создаёт сессию и ждёт
байт с разрешением до запуска команды. Его используют нативный сторож,
локальный `dist build`, сборка Actions и транзакции запуска конвейера.
Приёмка на Apple Silicon ещё открыта.

Сборочные процессы Darwin запускаются через проверенную копию `setsid`.
Родитель снимает полный снимок своей UID до запуска, ждёт подтверждённую сессию
и только затем разрешает wrapper запустить команду. Таймаут и отмена сохраняют
коды 124, 130 или 143. Непосредственный выход ребёнка начинает ограниченную
проверку очистки даже при открытых потоках вывода.

Перед сигналом helper сверяет UID, PID, start token, SID и PGID участника.
Неатрибутированные записи остаются без сигнала. Очистка подтверждается двумя
согласованными снимками. При неизвестном владельце серверный сборщик сохраняет
временные файлы, а релизный runner блокирует следующую стадию. В квитанции Darwin
записываются SHA подготовленных инструментов. Нативная проверка этого пути открыта.

## Закрепление runtime короткого решения

Gate, Goto, Abandon и ответ на вопрос разведки получают выбранную поставку через
одноразовый FD 3. Сначала выполняется read-only допуск под lock оркестратора.
Writer становится отдельной сессией после освобождения lock чтения попытки.
Он перепроверяет SHA попытки, физические пути и выбранный Node. Прямой CLI
проверяет pending migration по физическому control, task и attempt.

Сначала сохраняется реестр, затем marker его инициализации. До первого ref
writer закрепляет intent и runtime на диске. GC удерживает эту поставку до
завершения записи authority и индекса. Resume и runtime-rebind возвращают
`factory_runtime_pin_migration_pending` до операций над стендом и закреплением.
Publish, reclaim и release на Darwin сериализует один sibling flock. Канонический
lock публикуется после синхронизации owner и каталога. Старое имя при reclaim
уходит в tombstone с проверкой inode и без замены существующего каталога.

## Запуск конвейера

Выбранный runtime передаёт серверному worker проверенные копии обоих helper
и их SHA. Перед запуском конвейера сервер проверяет абсолютные пути зависимостей
Homebrew и передаёт отдельный PATH дочерней фабрике. Удержанные дескрипторы
вывода и каталога run передаются через [брокер движка](../../engine/ENGINE.md#retained-fd-usage-и-diagnostic-meta-mirror).

Серверные операции над каталогом маршрутов и другие блокировки через общий
kernel lock на Apple Silicon находят `flock` по физическому пути формулы
Homebrew. Процессу LaunchAgent достаточно системного PATH. Общие и
исключительные блокировки сохраняются до закрытия дескриптора у владельца.

Сервер до запуска записывает `launch-processes/t<ID>.<UUID>.json` в доверенный
control root. В записи `reserved` указаны boot UUID и точный владелец.
Wrapper `setsid` ждёт permit через отдельный FD. Сервер сверяет его PID, PPID и
сессию, синхронизирует запись `registered` и повторно проверяет идентичность
перед выдачей permit. При доказанном отказе до permit сервер ждёт выход wrapper,
проверяет точную запись и синхронизирует удаление. Если последняя синхронизация
сорвалась, повтор старта под тем же task lock сперва завершает эту очистку.

При первом запуске встроенного движка на Darwin сервер закрепляет физические
каталоги state, control и их подкаталоги для launch и runner records в
`D/state/darwin-factory-ownership.json`. Последующие запуски сверяют device, inode
и время создания. Пропажа или замена закреплённого каталога блокирует detached
запуск. Чтение launch records работает до появления `.pipeline`. После
рестарта очередь сохраняет состояние bootstrap для такой записи.
Новый запуск проверяет её до preflight, а повтор после отказа до permit
досинхронизирует доказанный откат под lock задачи и проверяет артефакты.
Запись `registered` текущей загрузки сохраняют до подтверждения завершения
связанных сессий. Нативные сценарии permit, FD и замены каталогов ждут Mac.

## Владение задачами при обновлении

Установленный worker читает отдельный CLI-маршрут
`GET /api/tasks?updateOwnership=1`. Ответ версии 1 содержит отдельные статусы
оркестратора, раннера и финализации. Сервер сверяет два обхода каталогов,
поколение допусков и проверенные файлы запуска. Живой лидер сессии или точный
участник ранее подтверждённого снимка привязывает SID к запуску. Неизвестное
владение, ошибка чтения или незакрытая финализация без проверяемого исхода
блокируют дальнейшие действия.

Worker обновления на macOS удерживает допуск от осмотра задач до запроса
выключения. Допуск связан с установкой, серверным instance, intent обновления
и проверенным PID worker. Фоновая операция арбитра удерживает свою ссылку до
записи исхода. Повтор уже принятого requestId получает прежний ACK.
Перед fork launcher сохраняет pending intent. Подтверждённый runner
публикует scope с boot UUID, launch UUID и хешем точной active identity до
SIGCONT. При известном осиротевшем runner native helper принимает удержанные
FD записи и engine lock, проверяет поколение перед каждым сигналом и
подтверждает два пустых census. Неизвестное владение сохраняет записи.
Связь Stop с полной финализацией стенда, обычным quit и CLI Stop ещё открыта.

## Восстановление транзакции при Stop

После выхода оркестратора сервер может продолжить Stop через `stop-cleanup`
того же закреплённого движка. Команда проверяет попытку под lock оркестратора и
подтверждает отсутствие активной привязки runner. Сервер принимает результат
после повторного чтения статуса той же попытки.

Перед выдачей permit launcher закрепляет запись поколения с точными task,
attempt, TX, run и epoch. Обычный postamble, Stop и допуск следующего исполнителя
используют один ключ контрольной точки этого поколения. Номер, снимок рабочего
дерева и описание индекса закрепляются до выбора нового состояния TX.
Контрольная точка до первого permit остаётся нулевой. В этом случае Stop
сверяет baseline и завершает ту же транзакцию без восстановления файлов.
Нативная проверка сбоев записи и восстановления остаётся открытой.
