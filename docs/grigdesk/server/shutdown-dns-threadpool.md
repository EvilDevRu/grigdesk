# DNS может удерживать выход Node после process.exit

## Воспроизведённый механизм

Отмена `fetch` не означает завершение системного `getaddrinfo`. В изолированном
опыте на Node 24.21.0 два HTTPS-запроса к синтетическим именам завершились
`TimeoutError` через 250–280 мс, но `_getActiveRequests()` сохранил два
`GetAddrInfoReqWrap`. Использовался TCP DNS: `use-vc timeout:2 attempts:2`.
Тестовый DNS принял соединения и запросы, но намеренно не отвечал.

Через 0,7 секунды фикстура вызвала `process.exit(1)` и выполнила JS-событие `exit`.
Через шесть секунд процесс всё ещё существовал и держал свой UDS listener.
Нативный стек показал две связанные цепочки:

```text
Главный поток:
node::DefaultProcessExitHandlerInternal
  → uv__threadpool_cleanup → uv_thread_join → pthread_join → futex

Два libuv-worker:
uv__getaddrinfo_work → getaddrinfo → send_vc → read(fd, ..., 2)
```

После выдачи DNS-ответов тот же процесс завершился за 7 мс без повторного сигнала.
Контрольный процесс без DNS-запросов завершился после того же вызова `process.exit`.
Изолировались user, mount и network namespaces; настройки и сеть хоста не менялись.

Это соответствует исходникам Node: его
[обработчик выхода](https://github.com/nodejs/node/blob/v24.21.0/src/api/environment.cc#L1072)
вызывает `uv_library_shutdown` до выхода ОС, а
[очистка пула libuv](https://github.com/nodejs/node/blob/v24.21.0/deps/uv/src/threadpool.c#L152)
ожидает все рабочие потоки. Таймер в том же JS-процессе не может добить процесс,
уже заблокированный в этом нативном ожидании.

## Связь с прежней остановкой GrigDesk

Координатор `server/src/lib/shutdown.ts` даёт общий бюджет шагам слива и
`fastify.close()`. По превышении он пишет сообщение о принудительном выходе
и вызывает `process.exit`. Эта запись не доказывает фактического завершения.
При описанном DNS-ожидании сервер может продолжать удерживать сокет браузера;
следующий запуск получает `browser_socket_busy`.

Отдельный подтверждённый источник долгого закрытия —
[текущий обход Telegram-вотчера](../telegram/watcher.md#остановка-вотчера).
Его прежний `stop` ждал весь обход, а отдельные сетевые вызовы сериализованы. Лимит
каждого вызова не ограничивает сумму ожиданий всего обхода.

Launcher в `server/src/binary/worker.ts` при получении сигнала или разрыве
внешнего IPC ставит собственный срок и может завершить только своего worker
через SIGKILL. Этот таймер принадлежит launcher. Если сам launcher исчез,
worker-bootstrap видит потерю IPC и запрашивает SIGTERM, но независимого
от worker процесса-сторожа после этого уже нет.

## Границы диагноза

Воспроизведение доказывает механизм с молчащим TCP DNS, включая сохранение
listener после `process.exit`. Оно не устанавливает причину потери DNS-ответа
на конкретной машине: resolver, VPN и транспорт требуют отдельного наблюдения.
Настройки `timeout` resolver и AbortSignal сами по себе не доказывают,
что уже начатый блокирующий TCP read будет отменён.

Без нативного стека исходного процесса нельзя объявлять доказанным, что именно
этот механизм удерживал его выход. Без логов начала и окончания каждого шага
также нельзя по одному общему таймауту назвать зависший drain или onClose-хук.

Увеличение бюджета остановки не устраняет этот класс отказов. Реализованные
[независимые сторожа](shutdown-watchdogs.md) ограничивают фактический выход,
включая исчезновение launcher. Telegram использует общий
[изолированный транспорт](isolated-statistics-fetch.md); вотчер и account poller
отменяют текущую сеть. Это устраняет воспроизведённые механизмы, но не устанавливает
инициатора DNS или зависший шаг прежнего инцидента. Прочие сетевые обращения сервера
автоматически не подменяются.
