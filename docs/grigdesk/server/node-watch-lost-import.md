# `node --watch` теряет импорт, на котором упал, и не поднимается после исправления

`npm run dev` сервера запускает `server/src/app.ts` через голый `node --watch`; так же
был устроен стенд задачи у конвейера, пока на этом не встала выкладка. Если при перезапуске
импортируемый модуль не разбирается — чаще всего в нём маркеры конфликта слияния, —
процесс пишет `Failed running … Waiting for file changes before restarting...` и остаётся
жить, но порт не слушает.

Дальше ловушка: исправление **этого же** файла сервер уже не будит. Модуль, на котором
упал разбор, в набор слежения не попал; следятся только файлы, загруженные до ошибки.
Сервер поднимется лишь от правки другого загруженного файла — например, входного `app.ts`.
Снаружи процесс жив, его юнит `active`, а API отказывает в соединении часами.

Проверено на Node 22.22.1 опытом из двух файлов. После конфликта в импорте не помогли ни
обычная запись исправленного файла, ни запись через rename, как делает git. Помогло только
`touch` входного файла. С `--watch-path=<папка>` вместо голого `--watch` сервер поднялся сам,
как только файл исправили: Node следит за всей папкой, а не за графом модулей.

Что из этого следует:

- слияние или rebase в рабочей папке, из которой работает `--watch`-сервер, может оставить
  сервер мёртвым после успешного разрешения конфликтов;
- проверка «процесс жив» здесь не годится — готовность определяет только ответ порта;
- `--watch-path` выключает слежение за графом импорта целиком, поэтому перечислять надо
  всё, что грузит сервер: `server/src`, `shared`, `server/scripts` и
  `server/deepseek-host-contract.json` (отдельный файл тоже принимается). Путь не должен
  содержать то, что сервер пишет сам: запись внутри него снова будит перезапуск, и он идёт
  по кругу;
- кто ждёт готовности такого сервера, перезапускает процесс, если тот жив дольше
  бюджета старта, а порт молчит: живой процесс сам по себе не доказывает готовность.
