# Режим GLM при установке согласованной пары

Допуск GLM привязан к режиму `api` или `coding-plan`. Подтверждённый `coding-plan`
не подтверждает `api`: один ELF может иметь действующий допуск только одного режима.
Если проверять такую установку по умолчанию host-контракта `api`, повторная сборка
сервера остановится, хотя фактический режим службы остаётся совместимым.

`grigdesk-ctl build server`, `build all` и `build deepseek` используют общий
`server/scripts/ctlBuild.mts glm-mode <env-файл>`. Экспортированный
`GRIGDESK_GLM_API_MODE` имеет приоритет над одноимённой настройкой из `.env` папки
данных. Отсутствующее или неизвестное значение даёт прежнее умолчание `api`.
Файл разбирается через `parseEnv`, не исполняется как shell; другие значения из
него не загружаются в окружение сборки и не выводятся.

Оба установщика получают `--glm-mode api|coding-plan`. При ручной установке
сервера этот флаг тоже нужно передать, если потребитель использует режим,
отличающийся от host-контракта. Без флага серверный установщик использует режим host-контракта.
Неизвестный аргумент режима отклоняется до файловых эффектов.

Установщик сервера по-прежнему читает host-контракт из payload кандидата сервера.
Переопределяется только режим проверки admission: capabilities, profile/policy
revisions, полный verify, SHA, lock и атомарная публикация остаются обязательными.
Допуск не копируется между режимами и не выдаётся без живого smoke.
Работающие процессы эта проверка и установка не перезапускают.

Проверки: `tests/server/ctl-build.test.js` проверяет передачу режима из окружения
и `.env` в обе установки; `tests/server/server-binary-install.test.js` проверяет
успех с единственным допуском `coding-plan`, отказ по default `api`, несовместимые
ревизии кандидата и сохранение сервера при отказе.
