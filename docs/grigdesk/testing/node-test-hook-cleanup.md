# Очистка общей фикстуры должна регистрироваться вне before

В `node:test` вызов импортированного `after()` внутри исполняемого `before()` привязывает
очистку к текущему hook. Проверено на копии SEA-файла: `before` успешно копировал файл,
затем зарегистрированный там `after` удалял каталог ещё до первого теста. Запуск файла
падал с ENOENT, хотя сама сборка была исправна.

Для общей копии регистрируйте файловый `after` на верхнем уровне. В `before` можно
сохранить функцию очистки, которую этот `after` вызовет после всех тестов. Так устроены
`tests/relay/sea/{commands,network,process}.test.js`: одна копия с пробелами в пути на файл
тестов, удаление после завершения всех его случаев.

Отдельные процессы и сокеты принадлежат конкретному тесту и очищаются через его `t.after`.
Время жизни общей копии и время жизни отдельного процесса должны соответствовать разным
контекстам регистрации hooks.

Внутри отдельного теста hooks также исполняются в порядке регистрации. У HTTP-фикстуры
сначала закрой Fastify и дождись его фоновых записей, затем удаляй временный каталог.
Удаление перед `app.close()` даёт `ENOTEMPTY`, когда подготовка истории успевает заново
создать файл в удаляемой папке. В `chat-permission-comment.test.js` эти действия объединены
в один последовательный `t.after`.

У Telegram-пульта отправка ответа предшествует удалению durable marker. Фикстура
`telegram-pult-assistant.test.js` сначала останавливает пульт, завершает удержанный
ответ поддельной модели и дожидается всех `assistant.background`, включая задачи,
добавленные во время завершения. Затем ждёт `store.queue` и удаляет каталог.
Один `actions.stop()` снимает таймеры и подписку, но не ожидает фоновые записи;
появление сообщения в fake Bot API также не доказывает их завершение.

Когда два сервера разделяют каталог истории, их fixtures принадлежат дочернему
`t.test`, а удаление каталога — родительскому тесту. Дочерние hooks успевают закрыть
оба сервера и стартовую сверку до родительского удаления.
Фикстура установки CLI сначала вызывает `ProviderInstallService.dispose()`: completion
операции не заменяет ожидания очереди durable-записей и остановки output-таймера.

После завершения собственного CLI нужно дождаться события `exit` его ChildProcess,
зарегистрировав ожидание до отправки сигнала. Проверка `/proc/<pid>` сразу после
доказанной смерти может ещё увидеть zombie, пока родитель не обработал выход.
В `provider-install-leases.test.js` отдельно ожидаются holder и записанный child;
исходные проверки отсутствия обоих процессов и снятия lease сохраняются.
