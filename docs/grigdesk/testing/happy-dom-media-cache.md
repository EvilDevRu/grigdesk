# Happy DOM: кэш стиля после изменения viewport и указателя

В установленной версии Happy DOM изменение `happyDOM.setWindowSize()` обновляет
`matchMedia`, но само по себе не сбрасывает ранее вычисленный `getComputedStyle`.
Изменение `happyDOM.settings.navigator.maxTouchPoints` также меняет результат
`pointer: coarse/fine` без гарантированного сброса этого кэша.

Поэтому responsive-тест может читать стиль предыдущего размера окна, хотя media-query
уже возвращает новое значение. Это даёт ложный отказ после правильного изменения CSS
или ложный успех проверки, которая должна была заметить смену представления.

## Как проверять каскад

Сохранить настоящий CSS компонента в строку и после каждого изменения окружения,
перед чтением `getComputedStyle`, повторно присвоить его уже подключённому `style.textContent`.
Мутация DOM сбрасывает кэш стилей. Не подменять `getComputedStyle` или результат media-query:
проверка должна продолжать читать настоящий CSS.

Ограниченная проверка существующего `.graph-stop` в `FactoryGraph.vue` дала такой результат:

| Действие | `max-width: 720px` | Вычисленные колонки |
| --- | --- | --- |
| Окно 500 px, CSS подключён | true | `1fr auto` |
| Окно изменено на 1164 px | false | прежние `1fr auto` |
| Тот же CSS повторно записан в style | false | `auto minmax(0, 1fr) auto` |

Механизм виден в исходниках Happy DOM: `CSSStyleDeclarationComputedStyle` возвращает
сохранённое вычисление, `BrowserPage.setViewport` меняет размеры и отправляет resize,
а мутации `Node` сбрасывают `computedStyle`. Это контракт тестового окружения, а не
свидетельство аналогичного поведения Chromium или Android WebView.

Проверка каскада в Happy DOM не заменяет измерение геометрии, проверку экранной клавиатуры
или доступности на реальном устройстве. Node-проверки по-прежнему запускаются только
через сторож памяти проекта.
