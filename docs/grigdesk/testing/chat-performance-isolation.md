# HTTP-приёмник не должен останавливать управление браузером

Проверено 29.10.2026. `check-chat-performance.mjs` раньше исполнял HTTP-приёмник,
`ChatHistoryStore` и управление Playwright в одном Node event loop. Синхронный
JSON большого файла останавливал и обработку ответов автоматизации. Поэтому
длительность `locator.press` могла превышать 100 мс при пустом браузерном журнале
`longtask`. Такой замер сам по себе не локализует фриз в браузере.

Приёмник теперь живёт в отдельном `worker_threads`-потоке того же driver.
RPC передаёт reset, включение параллельной записи, чтение синтетической истории,
patch и завершённый сетевой журнал. Команды выполняются последовательно; reset
ждёт незавершённых HTTP-запросов. Поколения browser context остаются проверкой
до доступа к данным. Ошибка или выход worker отклоняют ожидающие RPC;
`finally` завершает принадлежащий driver поток.

`press` продолжает учитывать транспорт и проверки Playwright. Задержки серверного
HTTP, длительность браузерных задач и ввод следует читать раздельно. Увеличение
`ackMs` также включает намеренную паузу фикстуры 420 мс. Для CPU-локализации есть
отдельный режим профилирования; его тайминги не сравниваются с обычной серией.

Ввод использует `page.keyboard.press` после однократного `textarea.focus`.
Раньше каждый `locator.press` снова искал поле в большом DOM; CPU-профиль
показал около двух секунд в selector query за серию из десяти событий.
Проверяется точный прирост значения поля на число отправленных нажатий:
потеря фокуса или символов не может дать ложное ускорение. Порог ввода остаётся
50 мс. Метаданные отчёта называют способ ввода, изоляцию и хэши исходников сервера.

После изоляции возможны отказы порога ввода, даже при корректном протоколе.
Они остаются ошибками отчёта; разделение потоков не отменяет порог 50 мс и
не разрешает объявлять незавершённый либо красный прогон зелёным.
