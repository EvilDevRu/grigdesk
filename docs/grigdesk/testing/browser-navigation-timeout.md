# Таймаут навигации браузерной фикстуры

В `tests/web/provider-install.browser.test.js` ожидание элементов ограничено вызовом
`page.setDefaultTimeout(2000)`, а навигации — `page.setDefaultNavigationTimeout(30000)`.
Первое открытие страницы явно использует `timeout: 30000` и `waitUntil: 'domcontentloaded'`,
а `second.reload()` наследует тридцать секунд и ждёт `load`. Проверки прежнего id операции,
единственного POST и общей блокировки выполняются после загрузки страницы.

Без отдельного navigation timeout вызов `setDefaultTimeout(2000)` также задавал две секунды
для `reload()`. Это приводило к отказу до проверок восстановления операции.

Фикстура `client-browser.mjs` обслуживает исходное приложение через Vite. Перезагрузка
повторно запрашивает больше тысячи модулей, включая Monaco и Markdown. Истечение срока
ожидания `load` само по себе не доказывает сбой восстановления серверной операции:
страница может продолжить загрузку и показать прежний job с общей блокировкой.

При таком отказе отдельно замеряют событие загрузки и проверяют прежний id операции,
отсутствие повторного POST и блокировку соседнего действия. Диагностический опыт с
задержкой сети 30 мс воспроизводит двухсекундный timeout, после которого эти проверки
проходят. Опыт не меняет исходники или API продукта. Ожидание навигации в тесте должно
допускать загрузку приложения; требования к восстановлению проверяются по состоянию UI.

Общая i18n-фикстура оставляет элементам бюджет 10 секунд, а первой навигации даёт
60 секунд: на двух CPU холодный Vite обслуживает полный граф приложения. Долгое ожидание
`load` не сокращает проверки готовности конкретных controls после перехода.

`clientBrowser` задаёт бюджет навигации 60 секунд и контекстам, и одиночным страницам.
Проверки редактора этапа и песочниц сохраняют короткое ожидание controls отдельно от
холодной навигации. Фикстура tracker settings считает корни web/shared от import.meta.url,
поскольку `npm --prefix web test` выполняет тесты с cwd пакета web.

Проверки touch-площадок учитывают общий `::after`: текстовое действие UiPaneHeader
может иметь видимую высоту 32 px и область касания 44 px. В телефонной шапке проверяются
также колокольчик оповещений и перенесённые в меню «Разделы» системные действия.

Матрица установки исполнителей проверяет install из настроек, update — из настроек и
топбара. Неустановленный и недоступный CLI отсутствует в топбаре по общему
`isTopbarProvider`; отдельная проверка сохраняет это условие. Девять холодных сценариев
имеют общий бюджет 300 секунд, ожидания отдельных controls не увеличиваются.

На телефоне QR-диалог открывается поверх «Разделов». Проверка адресует
`data-role="phone-connect"`: после Escape этот диалог исчезает, а родительское меню
остаётся открытым и принимает возвращённый фокус. Общий `.ui-dialog` обозначает оба слоя.

При смене viewport видимые настройки могут появиться до переноса соседей через Teleport.
Общий waitForShellActions активирует страницу и ждёт три кнопки в телефонном
`.topbar-actions` либо пять на desktop. Общий parking-host содержит также контекст экрана,
сводки и другие системные действия, поэтому его полное число кнопок здесь не фиксируется.
Закрытие настроек подтверждается исчезновением диалога до следующей ширины.

В смешанной i18n-фикстуре client-browser импортируется динамически после prepareI18nWindow.
Транзитивный импорт Vue до установки happy-dom навсегда сохраняет null document в runtime-dom;
последующая замена globalThis.document не чинит уже загруженный singleton.

Escape в проверке настроек отправляется после появления [data-role="settings-modal"].
Общий dialog с тем же доступным именем сначала принадлежит SettingsModalLoading:
каркас намеренно недоступен для закрытия до загрузки модуля. Его появление ещё не
подтверждает готовность настоящей формы и обработчика закрытия.
