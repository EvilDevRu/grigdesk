# Фикстуры чата после перехода на постраничный каталог

Холодный store читает `/api/chat/store/list?page=1&archived=0&limit=40`, а затем
адресное окно `/api/chat/store/chat/:id?window=1`. Фикстура с прежним полным store
или `listProtocol: 1` не проверяет загрузку после F5. Используй общие `protocolPage`,
`protocolWindow` либо `loadApi`, сохраняя метаданные выбранной модели в ответе каталога.
HTTP-стенд выбирает ответ сначала по полному `pathname + search`: ключи page/window
не должны теряться при выборе прежнего ответа только по pathname.
Последующие `window=1&before=…` также проходят настоящий `protocolWindow` с cursor;
ответ прежнего полного detail не является страницей истории. Сценарии сохранения DOM
без проверки пагинации держат сообщения в одном окне, чтобы prepend старой страницы
не менял защищаемую позицию прокрутки во время измерения.
Это относится и к восстановлению карточек SSH/DB: устаревший list останавливает `_load`
раньше чтения `/api/chat/waiting?include=ssh,db`.

Если сценарий пишет историю после F5, транспорт должен передать `window` в настоящий
`ChatHistoryStore.saveOne` и вернуть подтверждённые prefix/base hashes, границы и cursor.
Одного прежнего ACK с revision недостаточно: store справедливо откажет с ошибкой
«Сервер не подтвердил базу окна».

Сверка уже загруженного непостраничного окна использует POST `/api/chat/store/changes`:
ответ содержит лёгкие шапки, `listProtocol` и `gone`. Двойник GET не удерживает этот запрос.
Одновременные `_resyncStore()` объединяются; проверяй число сетевых запросов и принятые
данные, а не идентичность Promise, которые оборачивает Pinia.

`ChatsView` монтирует detail лишь для id из `openedChatIds`. В проверках загрузки и
мобильного pane задавай явное открытие отдельно от сохранённого `activeId`. Двойникам
`ChatList` нужны методы поиска и объект страницы; проверки геометрии и сна используют
общий `chatListPagingStub`, а настоящая пагинация проверяется настоящим store.
Браузерные loading-фикстуры также помечают синтетический разговор открытым: иначе
переход в ready снимает каркас, но намеренно не монтирует ожидаемый тестом композер.

У `ChatSession` ссылка на статью ошибки использует собственный Pinia store. В изолированных
проверках доставки и продолжения она остаётся границей `compileChatSession`, как остальные
непроверяемые product children. Это позволяет проверять настоящую ленту и кнопки без
случайного запуска чужих stores.
Сценарий, который проверяет сам переход в справку, явно включает `realHelp: true` и
передаёт свой подготовленный Pinia, как `chat-session-loading.component.test.js`.

`clientBrowser` выбирает `ru-RU` по умолчанию, сохраняя явно заданную locale контекста
или страницы. Это фиксирует язык синтетических сценариев независимо от языка runner.
SSE-фикстура отправляет `: ping` каждые 15 секунд и снимает таймер при закрытии ответа;
холодная загрузка Vite не превращает бездействующий поток в ложное восстановление связи.

Общий clientBrowser отвечает также metadata выбранного внешнего трекера: BoardStore
сверяет источник через `/api/trackers` до чтения dashboard. Собственная ветка получает
personalStateVersion=1 и независимые favorites/seen; пустой `{}` не является готовым снимком.

При ручной проверке одного HTTP-стенда страницы открываются последовательно и закрываются
после сценария. Каждая держит SSE и long poll оболочки; несколько одновременных вкладок
одного origin могут занять соединения браузера и задержать остальные ответы фикстуры.

Общий clientBrowser вычисляет list через protocolPage по полному URL, включая q,
archived и cursor. Обёртка i18nBrowser передаёт chatStore и не перекрывает list
статическим ответом protocolRoutes: иначе поиск получает прежний каталог вместо
отфильтрованной страницы. Карточки внешних панелей объявляют настоящий модульный
маршрут через общий pluginCard; web-файл без маршрута не делает пункт навигации доступным.

При сужении App до телефона индикатор ресурсов получает context phone-status-metrics
во второй полосе шапки. После resize тест ждёт именно этот context: прежняя
кнопка ещё может быть видимой до обработки matchMedia. Фикстура проверяет сохранённый
снимок в том же диалоге, а не требует прежнего desktop context topbar-metrics.

На телефоне topbar-actions содержит подключение, колокольчик и настройки. Кнопки
подключения телефона, справки и сетевых данных доступны через «Разделы»; тест
открывает этот диалог перед проверкой перенесённых controls и закрывает перед
кликом основных действий. Desktop сохраняет все пять действий в верхней полосе.
