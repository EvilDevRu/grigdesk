# Smoke GLM и меняющийся допуск выпуска

Обычный адаптер проверяет admission выбранного ELF, а не постоянный запрет на запуск
тестового candidate. `deepseek/compatibility/glm.json` уже содержит api admission;
совпадение с рассчитанной compatibility разрешает запуск Harness. `glm_auth_failed`
после этого относится к авторизации, а не доказывает пропущенную проверку допуска.

`glm-live-binary.test.js` проверяет SHA ELF до и после smoke, затем запускает обычный
адаптер без DI admission с синтетическим ключом, loopback endpoint и egress guard.
Допущенный выпуск выполняет настоящий протокол локально. Несовместимая identity проверяется
отдельно: `glm_runtime_not_admitted` должен возникнуть до spawn и до нового запроса модели.
Серверная политика разрешает `api` и `coding-plan`; этот loopback-сценарий проверяет
`api`. Внешняя сеть и реальные ключи ему не нужны. Отдельные отрицательные ожидания
Coding Plan в том же файле устарели: [границы фикстур режимов](glm-smoke-mode-fixtures.md).

Такой тест сохраняет отрицательную границу допуска и не принимает ошибку авторизации
за ожидаемый результат. Временный DI-допуск smoke не изменяет metadata или байты выпуска.

Минутный signal production-хода создаётся после повторной подготовки candidate и
сравнения admission. Уборка и полный verify могут занять этот бюджет ещё до запроса
модели; тогда тест ошибочно сообщал «Ход GLM остановлен». Проверка неизменности ELF
и admission сохраняется, но не расходует срок следующего самостоятельного хода.

Детерминированная модель выбирает последнюю содержательную user-реплику, пропуская
`Current runtime context` и `<system-reminder>`. Harness может добавить напоминание
о навыках после задания дочернему агенту; это не новый запрос модели. Без фильтра
фейк отвечал общим «готово» вместо чтения marker.txt, и smoke честно не находил
дочерний Read. Настоящие делегирование, инструмент и связь parent по-прежнему обязательны.
