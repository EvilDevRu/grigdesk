# Вложенный node_modules останавливает проверку снимка Harness

## Одна причина нескольких отказов

`safeVendorPath()` в `deepseek/scripts/deepseekVendorManifest.ts` запрещает
`node_modules` в любом сегменте пути. `verifyDeepSeekSnapshot()` обходит весь
`upstream/` и требует точного соответствия manifest: состав, SHA-256 и режим каждого
файла. Это намеренный контракт неизменяемого source cache, а не проверка исправности npm.

28.10.2026 два отказа расширенного прогона и остановка общего прогона имели одну причину:

| Место | Как доходит до отказа |
| --- | --- |
| `tests/deepseek/vendor.test.mts` | прямо проверяет исходный vendor |
| `tests/deepseek/buildInputs.test.mts` | копирует пакет и запускает builder, который проверяет копию vendor |
| `tests/run-all.sh` | на preflight строит legacy fixture, builder проверяет тот же vendor |

Ошибка во всех случаях:

```text
Небезопасный путь снимка: native/system/packages/entry/node_modules
```

В исходном cache найден один лишний каталог. В нём лежит
`@deepseek-ai/node-addon-system-linux-x64` — символическая ссылка на соседний выбранный
пакет `native/system/packages/linux-x64`. Ссылка рабочая, но ни её, ни `node_modules`
в manifest нет. Git не показывает этот мусор, поскольку весь `upstream/` игнорируется.
В standalone-тесте фильтр копирования исключает только корневой `node_modules`, поэтому
эта вложенная запись переносится в проверяемую копию и обнаруживается builder-ом.

## Подтверждение без правки общего дерева

В артефактах создана отдельная копия vendor без каталогов `node_modules`.
Штатный `verifyDeepSeekSnapshot()` успешно проверил в ней все 2540 файлов и два патча.
Иных отличий от manifest проверка не обнаружила. Исходный cache и найденная ссылка
при аудите не менялись. Кто создал ссылку, по этим данным не установлено.

В upstream найден `native/system/test/link-platform.mjs`. Он создаёт этот точный вид
записи: `entry/node_modules/@deepseek-ai/node-addon-system-<platform>-<arch>` с абсолютной
целью соседнего platform-пакета. Запуск настоящего скрипта в отдельной копии vendor
воспроизвёл загрязнение; verifier отверг его. После удаления только сгенерированного
каталога копия снова прошла проверку. Это устанавливает способ появления ссылки,
но не устанавливает, кто запускал скрипт в исходном cache.

Для восстановления исходный source cache должен снова точно соответствовать manifest.
Лишние зависимости нужно сохранять за его пределами, а сборочные ссылки создавать
только в staging generation — так уже устроен штатный `linkWorkspace()` builder-а.
Ослабление verifier-а или молчаливое пропускание лишних файлов не исправляет контракт.

## Восстановление и повторная проверка

После аудита лишний каталог сохранён в артефактах вместе с исходной символической
ссылкой. Из source cache удалены только эта ссылка и два опустевших каталога;
целевой native-пакет не менялся. Штатный verifier исходного vendor после восстановления
проверил все 2540 файлов и два патча. Защита manifest не ослаблялась.

Штатный `buildRuntime.mts` создаёт workspace dependencies и запускает native builder
только внутри staging generation; `test/link-platform.mjs` он не вызывает. Регрессия
`buildInputs.test.mts` теперь проверяет полную неизменность vendor после успешной сборки
и после отказа из-за изменения входов. `vendor.test.mts` воспроизводит опасный helper
только в копии и проверяет, что исходный cache остался целым.

Повтор ручного запуска upstream helper непосредственно в source cache снова нарушит
manifest. Native/ABI-эксперименты нужно выполнять в отдельной копии или staging;
автоматически удалять неизвестные файлы или пропускать их в verifier-е нельзя.

Повтор `tests/deepseek/buildInputs.test.mts` и `tests/deepseek/vendor.test.mts` через
сторож памяти завершился успешно: 16 проверок, без отказов и пропусков. Общий
`tests/run-all.sh` после этого прошёл подготовку legacy fixture, на которой раньше
останавливался, проверку типов DeepSeek, все 162 основных теста пакета и 11 тестов SEA.
Эти результаты подтверждают устранение конкретного повреждения source cache;
зелёного результата всего проекта они не подтверждают. Общий прогон обнаружил
отдельные отказы layout, документации, движка и серверных сценариев, затем был прерван
до итоговой сводки и следующих пакетов. Проверки типов сервера и серверных тестов
до прерывания прошли.

Дополнительные регрессии прошли отдельной сборочной проверкой (13 тестов) и в составе
пакета (всего 163 основных теста и 11 тестов SEA). Запрет лишнего `node_modules` сохранён;
проверка воспроизведения helper-а использует только одноразовую копию снимка.

Эти отказы относятся к подготовке сборки и тестов. Они не объясняют HTTP `1113`
от Z.ai на прямом запросе или запросе отдельного официального клиента.
