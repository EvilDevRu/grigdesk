# Песочница единой команды

`tests/cli/helpers/sandbox.mts` создаёт отдельные HOME/XDG/GRIGDESK_HOME внутри `os.tmpdir()` и копию `bin/grigdesk-ctl`,
`deploy/lib/runtime-env.sh`, `cli/`, общих модулей папки данных (`shared/runtime/dataHome.ts`),
настроек (`shared/runtime/runtimeSettings.ts`), готовности и описания окна, а также VERSION.
Свой порт сначала
резервируется через `listen(0)`, затем освобождается; `.env` песочницы содержит только этот
порт и лежит в её папке данных. Тестовый CLI-токен и compose-файл также принадлежат песочнице.

До первого запуска выполняется `bash -c 'command -v systemctl journalctl docker xdg-open
notify-send'` с будущим окружением ребёнка. Каждый путь должен находиться в каталоге заглушек;
любой другой путь прекращает тест до команд. Переданный в тест overrides не должен менять
PATH так, чтобы системные команды снова стали доступны. Старый Node проверяется заглушкой
в том же каталоге, остальные команды сохраняют защиту.

Заглушки пишут argv в calls.log и читают ответы из отдельных файлов:

- unit задаёт свойства show и необязательный ответ после start/stop/restart;
- journal задаёт последние строки VPN-ворот либо поток журнала;
- docker задаёт список compose-контейнеров и строку inspect;
- fail задаёт код и stderr управляющих команд/журналов, чтение show/ps/inspect сохраняется;
- hold удерживает systemctl на файловом барьере до разрешения либо до 10 секунд;
- installWindow создаёт скрипт, который пишет argv, путь ключа и наличие постороннего секрета;
- installRuntime кладёт `runtime.json` установленного окна в XDG_DATA_HOME песочницы (по
  умолчанию — исправный, текст можно задать): так проверяется переходный режим `open`;
- lock создаёт настоящую ссылку SingletonLock в отдельном профиле окна.

`requests()` возвращает пути HTTP-запросов к фикстуре по порядку: проверка «сервер не
запрашивался» опирается на него, а не на отсутствие ошибок.

Окружение удаляет значения порта, токена, ключа, проекта и профиля рабочего процесса;
HOME/XDG/GRIGDESK_HOME и cgroup указывают в песочницу. Внешнее окружение не загружается из `.env` ребёнка.
Заглушки desktop/mobile/release и готового `bin/b24` записывают переданные аргументы и
возвращают тестовый код.

Ветки `b24` проверяет `tests/cli/entry.test.mts`. Без `bin/b24` команда запускает исходник
`b24/src/main.ts` — в песочнице это минимальный вход, который оставляет маркер и печатает argv, —
и передаёт argv без потерь, включая пустой аргумент. Готовый файл исполняется без Node:
заглушка `node` в PATH не вызывается. Отказ готового файла с кодом 22 исходник не запускает.

HTTP-фикстура отвечает схемой auth/state и данными mobile/status только при тестовом
CLI-токене. Другие режимы дают 404 или удерживают соединение. Серверы и сокеты закрываются
в after; зависший CLI имеет предел 20 секунд. Барьеры проверяются опросом раз в 25 мс
с диагностикой calls.log; фиксированной паузой событие не подменяется.

Снятие файлового барьера идемпотентно: after может вызваться после общей уборки каталога.
Это предотвращает отказ hook при успешном основном assertion.

Проверки запускаются через сторож памяти:

```bash
NODE_TEST_MAX_RSS_MB=4096 bash tests/run-node-tests-safe.sh --test --test-concurrency=2 \
  tests/cli/*.test.mts tests/server/launch-script.test.js tests/desktop/client-runtime.test.js
```

Настоящие start/stop/restart, Docker-действия, AppImage и ярлык эти тесты не запускают.

## Терминальные сценарии

`helpers/pty.mts` и `pty.py` запускают точные argv через Python stdlib pty/termios.
stdin/stdout независимо подключаются к псевдотерминалу; отдельный JSON-канал передаёт
клавиши, resize, сигналы, вывод и снимки termios до/после. Снимок снимается до cleanup,
поэтому уборка фикстуры не маскирует повреждение терминала. Есть срок выполнения и уборка
только собственных процессов.

`menuFixture.mts` добавляет маркеры исходников и общие каталоги переводов в прежнюю песочницу.
`buildFixture.mts` использует существующую build-фикстуру со стабами npm/установщиков.
Ни одна терминальная проверка не собирает и не устанавливает продукт на машине владельца.
Сценарии сигналов запускаются на переднем плане через сторож памяти: фоновый Bash может
унаследовать игнорирование SIGINT и исказить результат.

Живой status — отдельная проверка только на чтение. Недоступные systemd/Docker в окружении
дают ограничение сверки реального формата, а не основание ослаблять разбор данных.
