# MCP-серверы: «отвалился» = не поднялся на этой сессии, переподключать нечего

Спрос «сделать кнопку переподключения, а то playwright отваливается» упирается в устройство
запуска: MCP-серверы — **дочерние процессы CLI**, и живут они ровно столько же, сколько его
сессия. При живой сессии это «поднялись один раз при открытии и держатся до её конца»,
при выключенной (prefs `chatLiveSessions: false`) — «стартуют заново на каждый ход».
В обоих случаях отдельного «соединения», которое чинится кнопкой, не существует: сессию
целиком переоткрывают смена модели, сброс памяти, простой или рестарт сервера.
«Отвалился» на практике означает «не поднялся», и лечится причиной отказа, а не
повторным коннектом.

Слоёв MCP два, и они лежат в разных местах:

Server-owned `grigdesk-work` — отдельный третий случай: nonce-authenticated UDS отдаёт child-
процессу exact descriptors (`supervised_ssh`, `supervised_db`) и диспатчит вызовы обратно
в server scope. Список нельзя хардкодить в MCP child или provider adapter: иначе новый tool
объявится только части исполнителей. Plugin toggle descriptor не меняет; живой gate проверяет
broker на каждом вызове.

| слой | где определён | что о нём знает GrigDesk |
|---|---|---|
| файловый | `mcpServers` в `~/.claude.json`, `.mcp.json` проекта, `--mcp-config` | всё: команда запуска, аргументы, env |
| аккаунтный (коннекторы claude.ai) | на стороне аккаунта | только имя (в `claudeAiMcpEverConnected`) — определения на диске НЕТ |

Отсюда правила панели (`mcpStatus` у claude, `parseClaudeMcpList`):

- **`claude mcp list` — единственный источник живости, но НЕ полный список**, причём
  текстовый: машинного формата у команды нет. Разбор идёт по маркеру статуса (« - » + иконка
  либо `Connected`/`Failed`/`Needs …`), а НЕ по последнему « - » в строке: в команде запуска
  дефисов полно (`docker run -i --rm --env-file …`), и половина команды уезжала бы в статус;
- **exit code у неё 0, даже когда сервер не поднялся.** Отказ виден только в тексте, поэтому
  вызов идёт с `anyExit: true`, а решение принимается по разобранным строкам;
- **коннекторы claude.ai она печатает НЕ всегда.** Два замера подряд на одной машине: в
  первом из трёх коннекторов не было ни одного (только файловые bitrix и playwright), во
  втором появился один. Поэтому секция «claude.ai» строится не из вывода команды, а из имён
  в `claudeAiMcpEverConnected` (`~/.claude.json`), а совпавшие по имени схлопываются — иначе
  панель то показывала бы коннекторы, то нет, и в один из заходов дублировала бы их;
- **живость аккаунтного коннектора локально не проверить ничем**, поэтому у него своё
  состояние `remote` («включён на claude.ai», серая точка). Жёлтое «состояние неизвестно»
  над тремя рабочими коннекторами — ложная тревога, а зелёное «подключён» — выдумка;
- **`needs auth` в выводе `mcp list` не отражается вовсе** — этот признак живёт отдельно,
  в `~/.claude/mcp-needs-auth-cache.json`. Мало того, коннектор, которому нужна авторизация,
  команда печатает как **`✔ Connected`** (замер: `claude.ai Google Drive` при живой записи в
  кэше). Соединение и правда есть, инструментов у агента всё равно нет — поэтому кэш
  перебивает статус, а вместе со статусом подменяется и текст: «Нужна авторизация» с
  пояснением «Connected» под ней — противоречие на экране. Провал этим не подменяется
  никогда: упавший процесс входом не лечится;
- **область видимости выводится вычитанием**: имя есть в файлах — «Свои»/«Проект», нет нигде —
  значит аккаунтный коннектор. Спросить об этом CLI напрямую нечем;
- опрос занимает около 4 с (живой health-check каждого сервера), поэтому эндпоинт отдельный
  и ленивый — см. [чат с агентами](README.md).

**На конвейере файловых MCP нет вообще:** раннер движка запускает claude со
`--strict-mcp-config` (`engine/lib/runners/claude.sh`), то есть ничего из `~/.claude.json`
и `.mcp.json` не грузится. Панель в настройках описывает ЧАТ, а не этапы конвейера — не
переносить её выводы на прогоны.

**Процесс с большим потреблением ресурсов не обязательно принадлежит GrigDesk.** Каждому
живому `claude -p` должен соответствовать идущий ход из `GET /api/chat/active`; долгий ход легко
принять за осиротевший процесс. Процессы браузера и каталоги `playwright_chromiumdev_profile-*`
могут принадлежать стороннему контейнерному сервису, а не playwright-mcp GrigDesk. Прежде чем
чинить «утечку», сверь PID с активными ходами и
`/proc/<pid>/cgroup` с владельцем — иначе чинишь чужое.
