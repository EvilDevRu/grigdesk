# Подготовка и кэш каталога чатов

`ChatHistoryStore.prepareWeb()` разделяет между вызывающими один запуск миграции схемы,
построения шапок и импорта старой истории. Миграция проецирует прочитанные файлы сразу:
отдельного полного `scan()` для восстановления рабочих папок при старте нет. Короткая
служебная отметка выбирает только чаты с `seedClaim` или незавершённой фазой перехода;
полную запись затем читает `workdirTransitions.recover(id)`.

Модуль не ждёт подготовки при регистрации. Маршруты истории, рабочих папок, сессий и
подготовка нового хода ждут общий promise каталога и восстановления. Запросы разрешений,
системные маршруты и `/api/events` продолжают
обслуживаться. Перебор файлов передаёт управление через `node:timers/promises.setImmediate`
не реже чем через 50 файлов или после 8 мс порции. Тёплый перебор текстов поиска также
разбит на порции. Один синхронный разбор отдельного очень большого файла не дробится.

## Персистные шапки

`chats/.web-heads.json` — производный кэш с режимом `0600`, публикуемый через tmp+rename.
Он содержит id, относительный путь, inode, size, mtimeMs, ctimeMs, SHA-256 исходных байтов,
две короткие проекции (web и mobile), отметку восстановления и признак проверки миграции.
Сообщения, steps и тела вложений в него не попадают. Неизменная сверка ничего не записывает.

Заголовок связывает кэш с физической папкой, форматом кэша и отпечатком версии мигратора,
схемы чатов, поверхности и значимых для миграции полей реестра моделей (id, aliases,
modelRefAliases, family, tier, extra). Изменение runtime-усилий или подписей само по себе
не сбрасывает шапки. Проверяются целостность сериализованных записей,
структура и допустимые пути. Ошибка или несовпадение означает перестроение из файлов чатов;
неудачная запись кэша не делает историю недоступной.

При старте каждый существующий файл проверяется по stat. Только совпадающая запись с
проверенной миграцией позволяет пропустить чтение и разбор. Внешняя правка, замеченная
после подготовки, обновляет шапку. Если байты уже соответствуют текущей нормализации,
шапка остаётся пригодной для следующего процесса. Иначе следующий процесс проверит миграцию
заново. Смена реестра моделей сохраняет прежнюю семантику
миграции и резервных копий. При изменении алгоритма миграции или проекции нужно менять версию
`catalog` в его отпечатке.

## Поиск

Поиск сначала разделяет общую сверку stat с list/delta. Для выбранной группы сохраняются
только исходные тексты реплик, lowercase и поля заголовка, нужные для совпадения названия.
Это кэш текстов, а не полных чатов и не результатов конкретного запроса. Иной запрос тоже
не перечитывает неизменённые файлы. Исходный текст нужен прежнему фрагменту вокруг первого
совпадения; черновик и steps в область поиска не добавляются.

Кэш поиска живёт только в памяти процесса. Изменение inode, размера, mtime или ctime
сбрасывает запись; удаление и повреждение файла освобождают её. Объём зависит от суммарного
текста просмотренных поиском групп, без тяжёлых steps и вложений.

## Проверка

`tests/server/chat-list-benchmark.test.mjs` создаёт отдельный синтетический каталог:
1000 чатов, 34 тысячи сообщений и около 250 МБ JSON. Он проверяет один разбор каждого файла
при старте, первый список после повторного создания сервера с кэшем менее чем за секунду
и нулевое число чтений файлов чатов при повторном поиске.

Во время холодной подготовки тест опрашивает дешёвый `/api/system` на том же Fastify/event
loop и требует задержку менее 50 мс. В замер включено опоздание таймера запроса, чтобы
блокировка до входа в HTTP hook не скрылась. Пробы ОС, сети и внешних исполнителей в эту
ручку не входят; это проверка отзывчивости event loop под нагрузкой каталога.

API-тесты дополнительно проверяют повреждённый и чужой кэш, права файла, изменение stat,
смену реестра, выбор незавершённых переходов и инвалидацию поиска при правке, архивировании
и удалении. Прежняя полная выдача проверяется отдельно в `chat-store-compat.test.js`.
