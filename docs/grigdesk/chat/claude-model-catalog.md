# Список моделей Claude — ИЗ БИНАРЯ УСТАНОВЛЕННОГО CLI

- **Список моделей Claude — ИЗ БИНАРЯ УСТАНОВЛЕННОГО CLI** (`executors/_claude-catalog.js`):
  бинарь сканируется потоком по regex `claude-(opus|sonnet|haiku|fable)-N(-M)?(\[1m\])?`, tier —
  из семейства и версии. Почему так: захардкоженная подпись версии протухает молча. В историческом
  инциденте реестр показывал «Opus 4.8», а установленный CLI резолвил `opus` в другую версию; бинарь
  знает локально поддерживаемые id и не требует ключей или сети.
  Скан ~0.3 с на 230 МБ, поэтому каталог пересобирается только при смене версии CLI,
  `CATALOG_SCHEMA`, executor-owned ключа окружения и по `?refresh=1`. Для Claude в ключ
  входит хотя бы `CLAUDE_CODE_DISABLE_1M_CONTEXT`: изменение флага после обычного рестарта
  обязано обновить каталог даже при прежней версии бинаря.
  **Свойства модели тот же скан берёт из РЕЕСТРА внутри бинаря, а не выводит из имени.**
  Рядом с каждым id лежит запись вида
  `{id:"claude-fable-5",family:"fable",display_name:"Fable 5",context:{window:1e6,native_1m:!0},`
  `max_output_tokens:{default:64000,upper:128000},capabilities:["effort","xhigh_effort",…]}` —
  оттуда приезжают окно контекста, подпись, потолок вывода и возможности. Прежнее правило
  выводило окно из ИМЕНИ («есть суффикс `[1m]` — миллион, иначе 200k») и потому занижало его
  **всему текущему поколению**: у Fable 5, Opus 5/4.8/4.7 и Sonnet 5 миллион ВСТРОЕННЫЙ
  (`native_1m`), без всякого суффикса. У Fable на 165 172 токенах реальная заполненность
  окна поэтому **17%**, но процент кольца зависит от ближайшего события: со стандартным
  автосжатием 200k это **83% до сжатия**, а не 17% — см. [грабли](live-context-usage.md).
  Правило резолва повторяет сам CLI: миллион даёт суффикс `[1m]` ЛИБО `native_1m`, а
  `CLAUDE_CODE_DISABLE_1M_CONTEXT` отменяет оба пути; `context.window` — для остальных.
  Bool-диалект совпадает с CLI: выключатель включают только `1|true|yes|on`, а строки
  `0|false|no|off` означают false и не должны случайно спрятать миллион.
  При включённом запрете варианты `[1m]` из селекта уходят совсем: показывать пункт с
  названием «(1M)» и окном 200k нельзя. Их старые exact id остаются в
  `modelRefAliases` базовой 200k-модели, поэтому сохранённый versioned чат не ломается и
  не запускает недоступный режим.
  Чего GrigDesk не видит: CLI дополнительно срезает окно до 200k, когда у аккаунта заблокированы
  кредиты на 1M (`longContext1mCreditsBlocked`) — этот флаг наружу не отдаётся.
  **Бандл чужого CLI — не контракт, поэтому разбор ограничен ОДНОЙ записью и проверяется
  ПО КАЖДОЙ модели.** Парсер сначала находит точную границу объекта реестра с учётом
  вложенных скобок, строк и escape-последовательностей (4096 символов — только fail-closed
  потолок ОДНОГО объекта), а уже внутри неё ищет `context`, `max_output_tokens` и
  `capabilities`. Слепой фиксированный хвост после id запрещён: если у текущей записи
  исчезнет поле, regex иначе одолжит его у следующей модели и выдаст чужое окно за
  проверенное. Оборванный до потолка объект не парсится вовсе.
  Окно меньше 1000 токенов бракуется — смени бандл запись числа на `1_000_000`, и простой
  regex поймал бы «1». Здоровье не бывает глобальным «распарсилась хотя бы одна»: неполная
  запись помечает непроверенной именно свою модель, не скрывая деградацию за соседними.
  Поля независимы: `contextUnverified`, `nameUnverified`, `maxOutputUnverified` и
  `effortUnverified` показывают, какой кусок не прочитан, а `metadataUnverified` — общий
  машинный признак деградации записи.
  `mergeCatalogModel` при этом сохраняет последние проверенные метаданные этой модели
  (`context`, `name`, `maxOutput`, `capabilities`, `effortGates`), но НЕ снимает признаки
  деградации. `contextUnverified` означает: обновление CLI не имеет права ни заменить
  известный миллион заглушкой 200k, ни выдать старый снимок за свежепроверенный; подсказка
  кольца явно пишет «окно модели N (не подтверждено)». Исключение — явно включённый
  disable-1M: его эффективный cap 200k известен без registry и сильнее старого сохранённого
  миллиона, хотя остальные поля записи всё ещё могут быть непроверенными.
  `effortUnverified` отделён от окна:
  если возможности/гейты конкретной записи не прочитались, ladder блокируется fail-closed
  и слайдер не предлагает потенциально неподдерживаемый `xhigh`, даже когда last-known
  capabilities сохранены в файле. У новой модели без прошлого снимка остаются
  консервативные заглушки с теми же явными признаками. Сторож —
  `tests/server/claude-catalog.test.js`, там же тест по НАСТОЯЩЕМУ установленному CLI:
  он падает в тот день, когда обновление ломает разбор, и пропускается, если CLI не стоит.
