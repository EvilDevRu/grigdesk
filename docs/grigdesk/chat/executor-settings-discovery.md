# Обнаружение настроек установленных исполнителей

Исходное исследование 30 сентября 2026 года. Ниже сохранены наблюдения до реализации;
автоматическое обнаружение, новая форма и адресные overrides теперь реализованы.
Актуальные API, проверки set/reset/resume и ограничения описаны в
[нативных настройках чатов](executor-native-settings.md).

Проверенные версии: Claude Code 2.1.285, Codex CLI 0.159.2, Kimi Code 0.33.0,
DeepSeek Harness 0.1.5-rc.2. Номера и количества ниже описывают этот замер,
а не константы для будущего кода.

## Что сейчас показывает GrigDesk

Карточка получает `settings` из нашего адаптера в `server/src/lib/executors/`.
Сейчас это вручную объявленные поля:

| Адаптер | Поля блока «Настройки исполнителя» |
| --- | --- |
| Claude | `blockDirectSsh`, `fastMode` |
| Codex | `blockDirectSsh` |
| Kimi | `blockDirectSsh`; пояснение зависит от режима запуска |
| DeepSeek | `blockDirectSsh` |

`blockDirectSsh` принадлежит GrigDesk: нативный каталог CLI не обязан его знать.
Модели, effort, режимы прав, MCP, лимиты и ресурсы обслуживаются другими контрактами;
их отсутствие именно в `settings[]` не означает отсутствия во всём интерфейсе.

Цепочка сейчас: `executor.settings` → `resolveProviderSettings` →
`GET /api/providers` → `views/settings/pages/ProviderPage.vue`. Адаптеры
`features/settings/resources/providers.ts` сохраняют общий черновик по «Применить» через
`POST /api/providers/:id/settings` и кладут значение в `prefs.providerSettings`.
Этот маршрут не вызывает универсальный нативный setter исполнителя.

Наблюдаемые ограничения:

- `providerSettings.ts` проверяет объявленный id и `kind: info`, приводит boolean/number
  и обрабатывает подтверждение. Проверок схемы, enum, границ числа и серверного запрета
  для `disabled` нет. `!!value` превращает строку `"false"` в `true`.
- Обычная форма умеет toggle, text, number, range и подпись для остальных видов.
  Enum, массивы, вложенные значения и явный unset доступны отдельно через нативный каталог.
  Числовая форма обычных параметров сохраняет законный `min: 0`.
- Для Claude `claudeProviderSettingsArgs` собирает `fastMode` и служебные hooks.
  Для Codex `codexAppServerConfig` задаёт несколько фиксированных параметров, включая
  `model_reasoning_summary: detailed`. Простое добавление поля в `settings[]` не
  подключит его к запуску. В частности, нативная настройка summary сейчас будет
  перекрыта значением GrigDesk.
- Сохранённые значения подставляются поверх декларации без повторной проверки типа.
  При изменении схемы это может вернуть устаревшее значение в новую форму.

Опорные файлы: `server/src/lib/providerSettings.ts`,
`server/src/modules/providers/index.ts`, `server/src/lib/executors/{claude,codex,kimi,deepseek}.ts`,
`web/src/views/settings/pages/ProviderPage.vue`,
`web/src/features/settings/resources/providers.ts`, `web/src/stores/providers.ts`.

## Codex: каталог флагов, схема протокола и конфигурация

У установленного бинаря проверены две команды без запуска модельного хода:

```sh
codex features list
codex app-server generate-json-schema --experimental --out <artifact-dir>
```

Первая вернула 152 записи: 47 stable, 3 experimental, 58 under development,
4 deprecated и 40 removed. Это каталог жизненного цикла флагов: все 152 записи
нельзя превращать в одинаковые доступные переключатели. Имена и исчезновение
функций можно обнаруживать без списка в GrigDesk.

Сгенерированная схема этой версии подтверждает следующие RPC:

- `experimentalFeature/list`: имя, стадия, текущее и стандартное включение,
  подпись и описание; есть пагинация. Подпись и описание могут отсутствовать.
- `config/read`: `config`, `origins`, опциональные `layers`; параметр `cwd` влияет
  на проектные слои.
- `configRequirements/read`: ограничения допустимых значений и обязательные политики.
- `config/value/write`, `config/batchWrite`: адресная запись, `expectedVersion` для
  защиты от устаревшего редактора. `batchWrite.reloadUserConfig` не обещает горячего
  применения всех параметров: схема отдельно исключает часть настроек сессии.

В `ConfigReadResponse.definitions.Config` описаны 26 верхних полей, среди них
`web_search`, `model_verbosity`, `model_reasoning_summary`, `service_tier`.
Например, `WebSearchMode` этой версии перечисляет `disabled/cached/indexed/live`,
`Verbosity` — `low/medium/high`. Их enum надо брать из схемы.

Но `Config` допускает `additionalProperties: true`. Экспорт схемы **протокола**
не является полным экспортом схемы **config.toml**; по одному `config/read` нельзя
обнаружить все отсутствующие в файле необязательные ключи и их типы.
Официальная полная JSON Schema config.toml опубликована отдельно. Её latest-версию
нельзя без проверки считать соответствующей установленному CLI.

RPC в этом замере проверены по сгенерированной схеме и официальному описанию.
Первая проба живого app-server не завершила инициализацию. Последующая изолированная
проба той же версии подтвердила `config/read`, все страницы features, передачу
конфигурационного слоя, reset и `thread/resume`; модельный ход не запускался.
Итоговая матрица приведена в документе реализации.

Источники: [App Server](https://learn.chatgpt.com/docs/app-server),
[config.toml](https://learn.chatgpt.com/docs/config-file/config-reference),
[опубликованная JSON Schema](https://learn.chatgpt.com/docs/config-schema.json).

## Claude: чтение значений есть, полного каталога в ответе нет

В отдельном процессе с пустым каталогом конфигурации, без пользовательского сообщения
и без модельного хода проверен stream-json control protocol:

1. `control_request` с `request.subtype: initialize`.
2. `control_request` с `request.subtype: get_settings`.

`get_settings` ответил `effective`, `sources`, `applied`. В замере `effective`
содержал только переданный флаг `disableAllHooks`; `sources` называл `flagSettings`.
`applied` содержал `model`, `effort`, `advisor`, `ultracode`,
`ultracodeRequested`, `ultracodeAvailable`.

`initialize` также отдаёт модели, доступные output styles, состояние fast mode
и причину его недоступности. Это полезные данные доступности, но не JSON Schema
всех настроек. Наличие `get_settings` подтверждено именно для проверенной версии;
на стабильность этого control subtype без проверки версии полагаться нельзя.

Официальная документация направляет на JSON Schema в SchemaStore и прямо
предупреждает, что она может отставать от CLI. `--settings <file-or-json>` позволяет
передавать пользовательские настройки на запуск; у managed и global-config ключей
другие правила. `--help` описывает флаги запуска и отдельные enum, но не весь
каталог ключей settings.json.

Практический источник — опубликованная схема плюс нативное чтение значений и
доступности. Совпадение внешней схемы с установленной версией нужно отмечать явно.
Без актуальной полной схемы нельзя обещать автоматическое обнаружение любого
нового, ещё нигде не заданного параметра.

Источник: [настройки Claude Code](https://code.claude.com/docs/en/settings).

## Kimi: живая OpenAPI, но часть типов не описана

На отдельном `kimi web` с пустым home, собственным bearer token и без сессий
получены `/openapi.json` и `GET /api/v1/config`. OpenAPI сообщает версию 0.33.0.
Для редактирования есть `POST /api/v1/config`, для уведомлений —
`event.config.changed`.

В схеме POST 19 верхних свойств. В частности, она описывает telemetry,
объединение skills, дополнительные каталоги skills, режимы запуска и experimental.
Шесть свойств имеют схему `{}`: `secondary_model`, `thinking`, `permission`,
`services`, `loop_control`, `background`. Внутри `providers/models` и `hooks`
тоже есть нетипизированные места. Из `{}` нельзя вывести enum, границы числа
или правильный вложенный редактор.

Живой GET на пустом home показал и поля за пределами перечисленных свойств POST,
например `subagent`, `identity`, `cron`, `token_counting`, `image`, `mcp`.
Наличие в GET не доказывает возможность записи через POST. Полноту нужно оценивать
по фактической схеме записи и результату чтения, не по одному ответу конфигурации.

Документация также объявляет интерфейс экспериментальным. Окончательным источником
для конкретной установки является её OpenAPI, с честным отображением пробелов.

Источник: [Kimi Server API](https://moonshotai.github.io/kimi-code/en/reference/server-api.html).

## DeepSeek: готовые описания зарегистрированных настроек

На отдельном штатном web-профиле установленного DSH, с пустым home и без создания
сессии, проверен RPC `settings/describe`. Получены `writable`, `hasDocument`
и 14 namespaces. Каждый namespace отдаёт:

- `ns`, `schema`, `value`, опциональные `base` и `user`;
- `revision`, `applies: live|restart`, `secrets` без значений секретов.

Это схема Schemastery (`uid` и `refs`), а не JSON Schema; нужен отдельный
преобразователь формата. В ответе обнаружены, например:

- `agent-loop.maxParallelToolCalls`: число, шаг 1, минимум 1, default 10;
- `shell`: таймауты, размер вывода и spill, время остановки;
- `llm-deepseek`: thinking, reasoningEffort, maxTokens, контекст, retryPolicy,
  параметры изображений и сетевых таймаутов;
- `subagent-model-selection`: включение и разрешённые модели.

Есть и настройки собственного интерфейса DSH — тема, размер шрифта, вид переписки.
Они не меняют внешний вид GrigDesk; область действия должна быть видна человеку.

Код установленного `@deepseek-ai/dsh-api-settings-controller` подтверждает операции
`settings/update`, `settings/replace`, `settings/mutate`. Последняя принимает
`set/unset` по пути и `expectedRevision`. Запись сначала проверяется и сохраняется,
ответ содержит повторно прочитанное описание с удалёнными секретами.
В исходном исследовании запись не выполнялась. При реализации отдельная проба
с собственным документом подтвердила set/unset и сохранность соседей; затем
проверены запуск с изолированным слоем и reset/resume того же session id.

Каталог принадлежит загруженному профилю и его плагинам. 14 namespaces штатного
web-профиля нельзя зашивать как обязательный набор каждого запуска GrigDesk.
Кроме того, текущий GrigDesk создаёт отдельный DSH home на чат: изменение настроек
одного такого процесса само по себе не задаёт default всем будущим чатам.

Опорные пакеты установленного CLI: `@deepseek-ai/dsh-api-settings-controller`,
`@deepseek-ai/dsh-settings`, `@deepseek-ai/schemastery`.

## Предлагаемый контракт

У каждого адаптера нужен источник описаний, чтение и применение изменений.
Ядро и Vue работают с единой нормализованной формой. Список ключей и вариантов
поступает из источника; код знает форматы протоколов, типы контролов и границы запуска.

Минимальные сведения каталога:

- идентификатор/отпечаток схемы, версия CLI, источник, время проверки и состояние
  `ready/partial/stale/unavailable`;
- область действия: override GrigDesk, нативные настройки пользователя, проекта,
  профиля или конкретной сессии;
- поля с адресом как массивом сегментов, типом/схемой, вариантами, ограничениями,
  default, явным override и effective value;
- источник effective value, запрет записи с причиной, признак секрета и момент
  применения: сразу, следующий ход или переоткрытие сессии.

Default, явный `false`, `null` и отсутствие override различаются.
«Вернуть по умолчанию» удаляет override, а не копирует сегодняшний default в prefs.
Русские подписи известных ключей могут дополнять каталог; отсутствие перевода
не должно скрывать новый ключ или подменять его варианты.

Нормализатор разворачивает `$ref`, enum, массивы и объекты JSON Schema,
а также `uid/refs` Schemastery. Общая форма рисует boolean, enum, number, text,
списки и вложенные группы. Неполная схема остаётся явно неполной: допустим просмотр,
а универсальный JSON-редактор — только при наличии проверяемого нативного пути записи.
Угадывать схему по одному текущему значению нельзя.

## Чтение, сохранение и применение

Обнаружение лучше вынести в ленивый метод/маршрут карточки исполнителя. Сейчас
`GET /api/providers` нужен также топбару и спискам моделей: запуск всех CLI ради
каждого чтения этого реестра увеличит задержки и свяжет отказы независимых карточек.

Кэш структуры привязывается к бинарю, его версии, транспортным возможностям
и отпечатку схемы; для профилей/плагинов учитывается их состав. Значения и ограничения
кэшируются с учётом workspace и области. Одной версии CLI недостаточно: rollout,
политики и набор плагинов могут измениться без обновления бинаря. События изменения
плюс ограниченный TTL обновляют значения; обновление CLI пересобирает структуру.

Для записи нужны следующие инварианты:

1. Сервер повторно сверяет путь, тип, enum, ограничения и право записи с актуальной
   схемой. Старая форма передаёт ревизию; несовместимое изменение требует перечитывания.
2. Локальные политики GrigDesk, включая SSH, остаются в prefs. Нативное изменение
   проходит через setter адаптера в выбранной области. Произвольные RPC, команды
   или пути файлов из браузера не принимаются.
3. Для override только запусков GrigDesk адаптер передаёт динамический документ
   через поддерживаемый конфигурационный слой CLI. Такой режим можно объявлять
   только после проверки его приоритета и поддержки соответствующим транспортом.
4. Поля, которыми уже управляет GrigDesk, получают владельца и объяснение: выбор
   модели/effort, рабочие корни, служебные hooks, формат потока, sandbox. Новое поле
   не должно молча перекрывать обязательные параметры или существующий контроль.
5. После записи читается результат: сохранённый выбор и применённое значение могут
   различаться из-за managed policy, аргументов запуска или живой сессии. Изменение
   глобального файла не считается доказательством применения к уже работающему агенту.

У Codex и Claude механизм persistent session уже учитывает `providerSettings`
при решении о переоткрытии; нативным записям вне prefs потребуется свой сигнал
об изменении. У Kimi host home конфигурация может быть ссылкой на пользовательский
home, а у DSH область привязана к чату. Эти различия обязан учитывать адаптер.

Секреты фильтруются на сервере до попадания в ответ и журнал. В DSH есть структурный
признак `secrets`, у Kimi read-projection скрывает ключи провайдеров. Копировать
сырой конфиг остальных CLI в браузер как универсальный fallback нельзя.

## Добавление и удаление настроек

- Новый поддерживаемый тип поля автоматически появляется после перечитывания схемы.
- `removed` и подтверждённо исчезнувшие пути больше не передаются в CLI. Их старые
  overrides сохраняются отдельно как неактивные, с возможностью удалить их вручную.
- Недоступность источника не считается удалением полей: последний успешный каталог
  остаётся видимым как устаревший, запись до проверки ограничивается.
- Изменившийся тип или набор enum требует повторной проверки сохранённого override.
  Молча приводить несовместимое значение или выбирать другой вариант нельзя.

Автоматическое появление и снятие настроек достижимо в пределах достоверной схемы.
Полное покрытие всех будущих настроек Claude и нетипизированных областей Kimi
без улучшения их источников обещать нельзя. Это ограничение метаданных исполнителей.

## Последовательность реализации и проверки

1. Добавить отдельное чтение каталога и effective values с указанием полноты,
   сохранив нынешние локальные ручки GrigDesk. Проверить источники на реальном профиле.
2. Сделать нормализатор и общую форму; DeepSeek даёт наиболее полный образец,
   Codex — отдельный каталог флагов и схему RPC, Kimi — OpenAPI с пробелами,
   Claude — значения/доступность и внешнюю схему.
3. Подключить адресные setter-ы и сброс override с ревизиями, затем связать их
   с запуском и жизнью уже открытых сессий. Область записи показывать до сохранения.

Для реализации нужны проверки появления/исчезновения поля без изменения Vue,
смены enum и типа, отличия `false` от unset, отказа по ревизии, недоступного discovery,
редактирования вложенных ключей, удаления секретов и чтения фактически применённого
значения. Отдельно проверить, что настройка достигает нового запуска и не нарушает
служебные параметры транспорта. Сам анализ не требовал сборки или запуска тестов продукта.
