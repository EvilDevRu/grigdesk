# Поставка и защищённый запуск Qwen Code 1.0 Preview.2

[Официальный релиз](https://github.com/QwenLM/qwen-code/releases/tag/v1.0.0-preview.2)
публикует нативные архивы. Для Linux x64 кнопка «Установить» в карточке Qwen
загружает архив, проверяет его размер и SHA-256, извлекает `qwen` и проверяет ELF.
Сервер публикует готовый файл атомарно в `runtimes/qwen-code/1.0.0-preview.2` папки
данных GrigDesk. Сохранённые ключи и настройки подключения используются дальше.
Версия появляется в карточке после установки. Штатные чаты и фабрика читают этот путь.

Для CI и ручной подготовки `tools/install-qwen-preview.sh <каталог> [архив]`
проверяет закреплённый SHA-256 Linux-архива для x64 или ARM64 и публикует один ELF
`qwen`. Повтор с тем же архивом возвращает путь к существующей копии. Файл с другим
содержимым и символическая ссылка на месте установки дают отказ. Каталог следует
выбирать отдельно для версии. Команда подготавливает файл для проверки и не меняет
действующую привязку GrigDesk.

На Linux x64 проверены распаковка настоящего архива, повтор установки, отказ для
другой контрольной суммы и запуск бинарника в `bwrap` с пустым home без внешней сети.
Архив ARM64 закреплён по данным релиза; запуск ARM64 не проверен.

## Изменения протокола

- Бинарник сообщает `1.0.0-preview.2` и принимает `--acp --permission-mode default`.
  Прежний `--auth-type` отклоняется ещё до `initialize`.
- `initialize` возвращает успешный ACP-ответ без `_meta` обязательного guard 0.x.
  В новом запуске защита обеспечивается управляемыми правилами и проверкой GrigDesk.
- Модели из `providers` получают идентификаторы `<provider>/<model>`. В Preview.2
  `session/new` перечисляет только текущую модель. GrigDesk публикует полный список
  из источника настроек после проверки старта CLI и назначает выбранную модель до
  запуска ACP. Перед запросом GrigDesk сверяет текущий идентификатор в `configOptions`.
- Читаемый из `--config-dir` файл `managed-settings.json` с правилом `ask` для `*`
  передал запрос Bash по `session/request_permission` даже в `bypass_permissions`.
  Ответ `reject_once` предотвратил запись контрольного файла и в основном ходе,
  и при вызове Bash из одобренного foreground-субагента. Покрытие иных инструментов
  и фоновых сессий требует отдельной проверки перед переключением.
- Запуск с `--permission-mode plan` и `general.plan.enabled: true` создал обычную
  ACP-сессию. В списке режимов не было `plan`, а `session/set_mode` вернул отказ.
  Запись и shell в режиме «План» закрывает GrigDesk. Native-утверждение плана пока не перенесено.
- `--sdk` в официальном Linux-бинарнике завершается сообщением о неподдерживаемом
  режиме. Переход на него не заменяет недостающий ACP-контракт.

## Запуск через GrigDesk

Карточка указывает отдельную управляемую поставку. При запуске сервер сравнивает SHA-256
раскрытого Linux x64 ELF и передаёт этот inode в bwrap через открытый дескриптор.
Профиль CLI примонтирован read-only. В нём закреплены `managed-settings.json` с правилом
`ask` для `*`, настройки провайдера, белый список инструментов и запрет hooks.
Доступны только разрешённые MCP. Опции управления старым guard не передаются.

Ключи моделей не передаются в окружение CLI. Preview.2 не разрешил переменную в поле
`apiKey` при запуске настоящего ACP, поэтому на каждый процесс сервер открывает короткоживущий
loopback-шлюз. Одноразовый токен действует только для выданного каталога и операций
вывода модели. Шлюз подставляет закреплённый ключ в запрос к настроенному адресу и отказывает
при редиректе. Цена перехода — дополнительное локальное HTTP-соединение на запрос.

Обычный чат загружает [общие навыки](qwen-skills.md) из read-only каталога. Путь
из описания навыка разрешается до обращения к ресурсу, а выходящие ссылки закрыты.

Чат и каталог проверены через реальный бинарник и синтетический OpenAI-compatible API.
Доказаны запрос на выдачу разрешения, прекращение действия после отказа, продолжение той же
сессии и запрос к штатному рабочему MCP. Обёртка фабрики записала `last.md` через этот же
исполнитель. Уточнение принимается стандартным `session/prompt` в активной сессии и
выполняется следующим запросом после первого ответа. Лента разделяет ответы, а завершение
подтверждает receipt уточнения. Режим «Хост» передаёт нативному процессу файловый
доступ пользователя в отдельной области systemd. Проверены запрет SSH, подтверждение
инструментов, продолжение в одном процессе и закрытие этой области.
[Контракт инструментов и режима «Хост»](qwen-native-tools.md#режим-хост).

## Квоты

GrigDesk задаёт `QWEN_EXPOSE_TOKEN_USAGE=1`, чтобы Preview.2 публиковал реальные токены
хода в стандартном `usage`. В `session/prompt` с синтетическим сервисом ответ `_meta.quota`
содержал токены сессии и разбивку по модели. Остатка подписки и времени сброса в нём
не было. В Preview.2 сообщение с ожидаемым сбросом подписки Qwen обрабатывает
HTTP 402 `insufficient_quota`, когда шлюз возвращает соответствующее время.
В API-режиме GrigDesk синтетический HTTP 402 с `quota.reset_at` стал ошибкой хода,
а карточка квот сохранила состояние `unsupported`. Авторизованный аккаунт Qwen
отдельно не проверен. Управляющий интерфейс QwenCloud Token Plan описан
в [исследовании источников квот](qwen-token-plan-usage.md).

Во всплывашке Qwen в верхней панели видна неактивная полоса «Квота подписки»
без процента и времени сброса. После измеренного хода под ней появляются входные
и выходные токены из итоговых ACP-ответов, включая выполненные в этом ходе уточнения.
Сервер держит последний замер в памяти до перезапуска или следующего измеренного хода.
Счётчики обновляются через общий SSE сразу по завершении хода, независимо от автоматического
опроса квот. Ответ без измеренного расхода сохраняет предыдущий замер.
