# Проверка GLM с явно выбранным бинарником

`server/scripts/glmLiveSmoke.mts` проверяет чат GLM через временный Fastify и настоящий
ELF DeepSeek Harness. Для живого запуска обязательны режим `api` или `coding-plan`,
`--confirm-live`, абсолютные `--binary` и `--cache-dir`. Оба режима могут обращаться
к внешней модели. Настройки службы не подменяют выбранный ELF или cache-dir;
инструмент использует async descriptor и metadata выбранного выпуска.

## Ручной запуск

Из корня репозитория, заменив пути на свои:

```bash
node server/scripts/glmLiveSmoke.mts --mode api --confirm-live \
  --binary /absolute/path/to/deepseek \
  --cache-dir /absolute/path/to/smoke-cache
```

Для Coding Plan укажи `--mode coding-plan`. Модель по умолчанию — `glm-5.3-flash`;
`--model glm-5.3` явно выбирает другую модель. Модель не входит в compatibility-хэш,
но успех на одной модели не подтверждает поведение остальных. Этот сценарий проверяет
чат; отдельный [этап Factory](glm-factory-stage.md) им не проверяется.

Ключ читается из `GRIGDESK_ENV_FILE`, если он задан, иначе из `.env` папки данных,
определяемой `GRIGDESK_HOME` и общим значением по умолчанию. Значения файла перекрывают
унаследованное окружение. Режим `api` использует только `ZAI_API_KEY`, `coding-plan` —
только `ZAI_CODING_API_KEY`; ключ другого режима не подставляется. Ключ через argv
не передаётся и в отчёт не выводится. Явный `--mode` задаёт режим проверяемого адаптера
поверх `GRIGDESK_GLM_API_MODE` из окружения.

Неверный режим, отсутствие обязательных аргументов или относительные пути дают код `2`
до чтения env-файла и создания рабочих каталогов. После принятия аргументов CLI создаёт
каталог отчётов и временную папку, читает env-файл и проверяет runtime. Поэтому ошибка
ELF или допуска не означает отсутствия файловых эффектов.

Для проверки выбирай отдельный cache. CLI требует абсолютный путь, но не проверяет,
отличается ли он от cache рабочей службы. Временные чат, проект и home находятся
в рабочей папке smoke; CLI удаляет эту папку в `finally`. Переданный cache сохраняется.

## Временный и выпускной допуск

Smoke рассчитывает временный DI-допуск для выбранного режима по входам выбранного ELF.
Проверки host contract, profile/policy и наличия plugin сохраняются. Обычный production
adapter продолжает проверять admission из metadata выпуска; DI-допуск smoke его не меняет.

Без `--admit` выпускной список не записывается. С `--admit` и только после `report.ok: true`
CLI заменяет все записи выбранного режима одной проверенной записью в
`deepseek/compatibility/glm.json` рабочей копии, где расположен скрипт. Остальные режимы
и ревизии сохраняются. Уже собранный ELF не изменяется: нужна следующая сборка,
которая включит список в metadata, и установка этого выпуска.
Запуски с `--admit` для одной рабочей копии выполняются последовательно: запись файла
не защищена блокировкой. Подробности — [допуск бинарной поставки](glm-binary-admission.md).

## Сценарий и результат

Сценарий запрашивает ответ; чтение, правку и команду над маркерным файлом; рассуждение
и результат инструмента; resume; foreground-критика с дочерним чтением; запрещённую
SSH-команду; остановку во время approval; повтор принятого хода по `turnId`.
Последняя проверка моделирует повторную отправку через API, браузерный F5 не выполняется.

Потолок — восемь вызовов `/api/chat`, включая повтор `turnId`. Это не лимит запросов
к модели или стоимости: инструменты, субагент и повторы транспортных ошибок могут
потребовать дополнительные запросы. Маршрут разрешает до десяти повторов запроса.
Если первый ход не дал полноценного ответа, дальнейшие ходы smoke не выполняются.
Неуспешная проверка более позднего шага сама по себе сценарий не прерывает.

Отчёт содержит `kind` (`loopback` для локального model endpoint, иначе `live`), `mode`,
`compatibility`, `packageId`, `sha256` выбранного ELF, `model`, `turns`, `ok`, `steps[]`
и `modelErrors[]`. Поле `model` — строка JSON с парой провайдер/модель.
`ok` означает успех всех проверок `steps[]`.
`modelErrors[]` содержит [HTTP-статус и полный очищенный текст модельного отказа](glm-smoke-http-errors.md);
сетевому исключению соответствует `httpStatus: null`. Краткие `steps[].detail` очищаются
и ограничиваются 400 символами.

CLI сохраняет JSON с правами `0600` в
`<artifacts>/glm/G12/live-smoke-<mode>-<timestamp>.json`, печатает `OK <путь>` или
`FAIL <путь>` и возвращает соответственно `0` или `1`. Папку артефактов определяет
`GRIGDESK_ARTIFACTS_DIR`, иначе используется `artifacts/` папки данных.
Ошибки подготовки могут завершить запуск до появления отчёта. При `--admit` запись
допуска идёт после отчёта: строка `OK` ещё не подтверждает успешную запись;
нужны сообщение `ADMIT <режим> <compatibility>` и итоговый код `0`.

## Граница offline-проверки

Основной loopback-сценарий `tests/server/glm-live-binary.test.js` вызывает
`runGlmLiveSmoke` напрямую: синтетический ключ, локальная модель, fetch guard и настоящий
ELF. Ветка `main`, читающая env-файл и записывающая admission по `--admit`, в нём
не вызывается. Проверяются протокол, явный ELF/cache, неизменность байтов и допуска
выпуска. Такой результат не выдаёт живого допуска.

Production admission не предполагается пустым: допущенный `api` ELF работает без
DI-подмены admission, несовместимая identity отклоняется до запуска Harness.
См. [фикстуру допуска выбранного выпуска](../testing/glm-release-admission-fixture.md).
У model fixture отдельные callId, путь для approval извлекается до добавленной
подсказки GrigDesk.

В тестовом файле остаются отрицательные ожидания прежнего запрета Coding Plan;
полный файл нельзя считать подтверждением актуального CLI и обоих режимов.
Проверенное расхождение и границы безопасного запуска описаны в
[документе о фикстурах режимов smoke](../testing/glm-smoke-mode-fixtures.md).
