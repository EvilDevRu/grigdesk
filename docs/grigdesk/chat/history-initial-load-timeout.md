# «На телефоне нет чатов» = вся история одним GET не укладывается в таймаут

Симптом до [восстановления загрузки](store-loading-recovery.md): окно на медленном пути
(телефон через сеть и TLS-трубу, слабый канал) после входа показывало пустой раздел «Чаты».
Ошибки не было; компьютер с тем же сервером видел все чаты. В журнале сервера у такого окна
`GET /api/chat/store` оставался без `request completed`, повтор приходил ровно через 30,7 с
после первого.

Причина: `_load()` в `web/src/stores/chat.ts` берёт всю историю одним
`GET /api/chat/store` — активные и архивные чаты вместе с лентами сообщений. Ответ
не сжимается и растёт с историей без верхней границы: на долгоживущей установке он
достигает сотен мегабайт, и даже loopback отдаёт его за секунды. Раньше этот GET шёл
под общим сроком клиента `web/src/shared/apiClient.ts` — 30 с и один повтор через 700 мс.
Второй таймаут попадал в `catch` с `j = null`, и стор без снимка помечался `loaded` пустым.

Теперь отказ виден: «Чаты» показывают причину и «Повторить», стор повторяет загрузку сам
и до успеха ничего не пишет на сервер. Срок этого GET считается по молчанию канала, а не
по общей длительности. Объём при этом прежний: медленное окно качает всю историю целиком,
а затем разбирает её в памяти.

Сверка по `hello` после переподключения тоже читает полный `GET /api/chat/store`.
Каждый разрыв SSE снова гонит всю историю.

Данные на сервере это не портит: полный `PUT /api/chat/store` сохраняет чаты,
отсутствующие в теле ([хранилище истории](history-storage.md)).

Смежное: запись истории уже точечная по той же причине — объём запроса не должен зависеть
от числа накопленных чатов ([лимит тела PUT](history-request-size-limit.md)). Чтение
первой загрузки этому правилу пока не следует.
