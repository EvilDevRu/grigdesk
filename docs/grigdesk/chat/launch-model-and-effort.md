# Что реально ушло в запуск (проверка модели и эффорта)

- `actualModel` — модель из потока (`system/init.model`, точнее — `message.model` ходов). CLI резолвит
  алиасы сам: на 2.1.85 `opus` → `claude-opus-4-6`. Показывается строкой под панелью управления
  («факт: …») и подписью у ответа агента; расхождение с выбранной подсвечивается.
- Уровень эффорта проверяется по каталогу модели ПЕРЕД запуском: `--effort xhigh` для claude — не
  «игнор», а падение CLI с ошибкой валидации (`It must be one of: low, medium, high, max`). Замены
  нет: окно отправляет уровень, только если он есть в списке модели, иначе пустой (умолчание
  исполнителя); сервер (`resolveRequestedEffort`) на чужой уровень отвечает 400 `unsupported_effort`.
- **Команды и навыки**: ввод «/» в композере открывает меню CLI-команд, ввод «$» —
  меню нативных навыков Codex (фильтр по мере набора,
  ↑/↓ + Enter/Tab, Esc, клик). Меню двух секций: «GrigDesk» (клиентские, на сервер не ходят:
  `/clear` — история+контекст, `/reset` — только контекст, `/new` — новый чат, `/compact` —
  сжатие) и секция исполнителя выбранной модели (цветной бейдж, имя из реестра).
  Список исполнителя — поле `commands?(config)` его адаптера (`server/src/lib/executors/*.js`),
  едет в `/api/providers` (общий 60-секундный кэш; источники cwd-независимы). Состав по
  исполнителям: kimi — статические ACP-команды + скан пользовательских скиллов
  (`<kimiHome>/skills/*/SKILL.md` в host-режиме, `<kimiRuntimeHome>/skills` в contained;
  ACP исполняет их как `/<имя>`, хотя `/help` их не перечисляет); claude — built-ins + скан
  `$CLAUDE_CONFIG_DIR/commands/*.md`; codex — информационный список TUI-команд плюс
  `skills/list` его app-server для включённых user/admin/system-навыков. Repo-навыки
  намеренно исключены из глобального `/api/providers`: его 60-секундный кэш не знает cwd
  конкретного task-chat и иначе показывал бы недоступную команду чужого worktree.
  Дедупликация по имени: команда GrigDesk глушит провайдерскую, built-in исполнителя — его скилл.
  Пункты `run: 'none'` (у codex это все TUI-команды: app-server `turn/start` не является TUI
  и такие команды не исполняет)
  показаны серым с hint и не выбираются ни клавиатурой, ни кликом.
  `$skill` уходит обычным model prompt без `slashCommand`: Codex сам раскрывает явное
  упоминание в содержимое `SKILL.md` (синтаксис `$skill-name` — контракт самого CLI).
  Поэтому навык, в отличие от служебной `/`-команды, **уносит приложенные файлы**:
  «разбери вот этот скриншот» — обычный его сценарий, а у служебного хода вложений не
  бывает вовсе. Фильтр меню регистронезависим: имя навыка приходит от Codex как есть,
  и заглавные в нём законны. Канонический user-scope — `$HOME/.agents/skills`;
  устаревший совместимый — `$CODEX_HOME/skills`. Чтение read-only и в 60-секундный
  кэш реестра укладывается (замер живого `skills/list`: около 0,4 с на подъём
  app-server), поэтому отдельного ленивого эндпоинта ему не заводили.
  **Грабля:** класс выделения строки меню — `on`, не `sel` (`.sel::after` в этом же файле рисует шеврон селектов).
- **Провайдерская `/`-команда — служебный ход `slashCommand`**: `runCommand` шлёт
  `chat.send(sid, cmd, [], { slashCommand: cmd })`, без `requestTitle` и без provisional-заголовка.
  Сервер валидирует поле строго по списку `commands()` исполнителя (текст хода = сама команда,
  иначе 400 `unknown_slash_command` — полем нельзя обойти титул-хук/повторы для обычного текста).
  Для такого хода: титул-хук НЕ приклеивается (kimi матчит ACP-команды побуквенно — склейка
  превращала `/status` в «Unknown ACP command»), автоповтор пустого хода отключён и kimi-ветка
  emptyRun НЕ инвалидирует session binding (молчание локальной команды — штатно); пустой вывод
  подменяется плашкой `role: 'note'` («✓ Команда … выполнена локально — вывода нет.»).
  **Грабли, закрытые этим признаком:** claude `/clear` в `-p --resume` молча
  начинает НОВУЮ сессию с пустым stdout → emptyRun → автоповтор → ложный диагноз «нет сети»
  (поэтому `/clear` в списке claude нет вовсе); пустой ответ kimi без признака слёг бы
  в `kimi_empty_response` со сбросом сессии.
- **Автоназвание нового чата — общий хук GrigDesk**: первый ход безымянного чата отправляется с
  `requestTitle`; `modules/chat` добавляет provider-neutral служебную инструкцию в тот же запрос.
  Агент возвращает маркер `GRIGDESK_CHAT_TITLE` с осмысленным названием ровно из трёх слов,
  сервер валидирует его и вырезает из ответа/живой ленты, а клиент применяет как метаданные чата.
  Отдельного модельного вызова нет. Пока основной ход не завершён, `web/src/shared/chatTitle.ts` показывает
  мгновенный локальный вариант; ответ агента заменяет только его — ручное название и заголовок
  задачи всегда сильнее. Тот же заголовок едет через `chats/pending` после F5/закрытия окна.
