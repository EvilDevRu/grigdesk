# Политика инструментов GLM и разрешения

В web-чате профиля `grigdesk-glm-profile-v3` с политикой `grigdesk-glm-policy-v3`
каждый вызов проходит [native gate](glm-native-gate.md), включая
окончательный guard перед эффектом. Chat policy дополнительно разрешает только foreground
`subagent` и `subagent_fork` без смены модели и прав ребёнка.

Ниже описан прежний контракт hook, который сохраняется у Factory и ACP-каталога.
В этой ветке каждый вызов проходит server-owned PreToolUse hook с matcher `*`
(`server/scripts/glmToolPolicyHook.mts`, таймаут 30 с). Hook решает чистой локальной функцией
по точному имени и аргументам, без сети; политику запуска (инвентарь `grigdesk-work` и флаги
SSH/БД чата) он читает из файла `glm-policy.json` каталога запуска (0600).

## Что пропускается

- Инструменты профиля по точному имени: `read`, `read_image`, `write`, `edit`, `glob`, `grep`, `bash`,
  `skill`, `job_list`, `job_output`, `job_kill`, `todo_write`, `ask_user_question`.
  `read_image` — просмотр изображения с типом действия `read`; поддержку image input
  выбранной модели проверяет сам Harness: [контракт изображений](glm-image-input.md).
  `skill` — нативный загрузчик инструкций навыка: чтение `SKILL.md` в контекст без файловых
  и сетевых эффектов, тип действия `read`. `job_*` — фоновые задачи самого процесса: запуск
  идёт через `bash`, `job_list`/`job_output` читают состояние и вывод (тип `read`),
  `job_kill` останавливает свою задачу (тип `execute`). Делегирующие, субагентные, workflow,
  goal, plan, `present`, `web_search`, `web_fetch` и любое неизвестное имя —
  отказ.
- `bash` — через общую политику прямых команд: SSH при запрете — отказ; удалённый клиент БД
  при `blockDirectDb` — отказ, клиент с непроверяемым хостом — отказ при `strictUnknownDbClient`.
- MCP — только инструменты служебного `grigdesk-work` этого запуска, по имени формулы DSH;
  проектные MCP в процесс не подключаются, а их имена и поздние инструменты отклоняются.
- Файловую границу (запись только в рабочей папке, отказ через symlink) держит песочница DSH.

## Fail-closed внутри hook

Неразбираемый stdin, неизвестное событие, повреждённая политика запуска, исключение и
непойманный отказ промиса — exit 2. Тот же hook зарегистрирован на `UserPromptSubmit`: при
испорченной политике он блокирует сам prompt, ход завершается `glm_turn_blocked` без единого
модельного запроса.

## Сверка хода

Hook исполняется в песочнице и пишет только stderr: строку `GLM-POLICY {…}` с `tool_use_id`,
точным именем, sha256 канонического JSON аргументов (ключи отсортированы рекурсивно), типом и
решением; аргументы в stderr не попадают. DSH публикует её в событии `hook/result`.
На `UserPromptSubmit` hook пишет маркер `hooks-alive`; номер хода несёт событие.

Ход GLM на каждом шаге проверяет: `tool/call` без маркера этого хода и результат инструмента
без дескриптора по его `callId` — немедленный cancel и `glm_policy_hook_missing`.

## Approval

В `workspace-write` DSH спрашивает approval только при эскалации песочницы
(`sandbox_permissions`). Тип действия берётся из точного `toolName`, аргументы — из `tool/call`
этого хода и сверяются с хэшем дескриптора hook. Нет вызова, нет дескриптора, другие аргументы,
неразбираемые аргументы или чужая сессия — отказ без вопроса человеку. Разрешение только
разовое (`canRemember: false`), комментарий к отказу не доставляется, внешний путь и MCP требуют
человека и в режиме «Авто». Ответ после стопа превращается в отказ. `grigdesk-work` одобряется без
человека только по точному имени из инвентаря запуска; автоодобрения по префиксу нет.

## Остаточный риск

Канал hooks DSH fail-open: блокирует только exit 2. Если процесс hook убит до ответа, вызов
пропускается. Если `hooks.json` не загрузился, DSH молча работает без hooks: тогда ход
останавливается по отсутствию маркера на первом `tool/call`, но вызов, уже начатый DSH, может
успеть выполниться до cancel. Быстрый локальный hook, маркер хода и сверка дескрипторов эти
случаи сужают, но не исключают.
