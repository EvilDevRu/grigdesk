# Картинки GLM: чтение вложений и поддержка модели

## Действующий контракт

Общий чат передаёт GLM текст с путями загруженных вложений. Адаптер не посылает байты
изображений в web-RPC: `session/prompt` содержит только текстовый блок. Ввод в активный
ход объявлен только для текста, без `inTurnInput.images`.

Политика `grigdesk-glm-policy-v3` разрешает штатный инструмент Harness `read_image`
в `GLM_NATIVE_TOOLS` с типом действия `read`. Разрешение действует и в native gate чата,
и в hook Factory/ACP; лишнего ручного подтверждения из-за типа `other` нет.
GrigDesk не определяет поддержку изображений за модель: `assertImageCapableRoute`
внутри `read_image` проверяет, объявлен ли `image` во входах выбранного маршрута.

В каталоге pi-ai закреплённой generation из моделей `zai` изображения принимает
`glm-5.3-flash` (`input: ['text', 'image']`). У `glm-4.7`, `glm-5-turbo`, `glm-5.2`,
`glm-5.2-highspeed`, `glm-5.3` и `glm-5.3-highspeed` объявлен только текст.
Для них Harness возвращает понятный отказ `model does not declare image input`,
который агент может сообщить человеку. Разрешённый инструмент не добавляет модели зрение.

Общий блок `[Вложения]` предлагает подходящий инструмент чтения изображений:
`Read` или `read_image`, доступный в окружении. Файл остаётся на диске в
`<chatsDir>/attachments/`; модель открывает переданный путь через `read_image`,
а не получает байты в исходном `session/prompt`.

## Чтение и запись

Режим `workspace-write` в Harness ограничивает запись, а не чтение файлов за пределами
проекта. `SandboxedFileSystem` наследует чтение от `LocalFileSystem` без дополнительного
фильтра; проверка рабочей области применяется к `writeText` и `editText`.

Linux-песочница shell через bubblewrap монтирует корень только для чтения и возвращает
рабочую папку на запись. Его приватный `/tmp` может скрывать временные файлы хоста;
это отдельное свойство shell-песочницы, а не общий запрет чтения вне проекта.

Адаптер публикует отдельные заметки: вложения переданы путями и доступны только на чтение,
а просмотр изображений зависит от image input модели; дополнительные каталоги доступны
только на чтение, GLM пишет только в рабочей папке. Заметка о вложениях не подменяет
доступность файла границей записи и не обещает просмотр текстовой модели.

## Ревизия и допуск

Ревизия v3 входит в `glmCompatibilityIdentity` и требования
`server/deepseek-host-contract.json`. Прежний допуск v2 не подходит: после ручного
перезапуска сервера GLM закрыт до повторной живой проверки
`server/scripts/glmLiveSmoke.mts` и новой записи admission владельцем.
Проверка `assertGlmGenerationAdmission` и прежние записи допуска не ослабляются;
ревизия Factory и поведение этапов сохраняются.

Общий binary probe тоже сверяет ревизию с host-контрактом. Поэтому прежний общий
ELF DSH с v2 отвергается как `deepseek_binary_incompatible` ещё до проверки допуска
GLM; для восстановления исполнителей нужна совместимая поставка с v3 и новым допуском.
[Проверка пары при установке сервера](../server/server-executor-install-guard.md)
сохраняет этот отказ и не заменяет работающие процессы.

Проверено по `server/src/lib/glm/contract.ts`, `server/src/lib/glm/policy.ts`,
`server/src/lib/deepseek/serverClient.ts` и закреплённым исходникам Harness:
`packages/fs/fs-sandbox/src/index.ts`, `packages/sandbox/sandbox-local/src/profiles.ts`,
`packages/fs/tool-fs/src/read-image.ts`.
