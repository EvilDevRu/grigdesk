# Штатные инструменты Qwen и серверный допуск

`qwen/policy.ts` допускает известные инструменты внешнего CLI по точному имени.
Общий отказ `Tool invocation denied by host policy` больше не применяется ко всему
веб-поиску и служебным возможностям только из-за отсутствия их в списке.

## Набор

- `web_search`, `web_fetch` — поиск и получение страниц штатным backend CLI.
- `todo_write` — список дел в приватном runtime home разговора.
- `save_memory`, `manage_memory`, `search_memory` — штатные операции памяти.
- `ask_user_question`, `enter_plan_mode`, `exit_plan_mode` — вопросы и планирование.
- `agent` и прежнее имя `task`, управление задачами и командами агентов, их сообщения.
- `skill`, `lsp`, `notebook_edit` — навыки, языковой сервер и правка блокнотов.
- Изображения и инструменты семейства `omni_*`, перечисленные в политике,
  — штатная обработка медиа.
- `cron_create`, `cron_list`, `cron_delete`, `loop_wakeup`, операции целей,
  `workflow`, операции артефактов и источников — native состояние и сценарии CLI.

Список не является разрешением любого будущего имени. Неизвестный инструмент,
чужие session/prompt/cwd и вызов после отмены по-прежнему отклоняются. Прямые MCP
выдаются сервером для конкретного хода; `tool_search` и `tool_call` не включаются.

Managed settings включают opt-in `tools.todoWrite.enabled`, `tools.workflowsEnabled`,
`tools.lspEnabled` и `experimental.agentTeam`. Обычный субагент по умолчанию работает
в foreground (`agents.defaultBackground: false`), чтобы завершиться до закрытия ACP.
Omni включается при наличии исполняемых `ffmpeg` и `ffprobe` в PATH песочницы.
Read-only системные `/etc/alternatives` и `/etc/ld.so.cache` обеспечивают доступ
к библиотекам этих утилит; секретные настройки хоста не монтируются.

## Вопросы и план

`qwen/permissions.ts:qwenPermissionResponse` переводит `session/request_permission`
в общую карточку GrigDesk. Вопрос определяется native metadata
`qwenInteractionKind: user_question` и `qwenQuestions`, а не текстом заголовка.
Мультивыбор и собственный текст возвращаются в ACP как `answers` с числовыми
индексами вопросов. Неполный ответ, отмена и позднее решение не становятся разрешением.
В Factory пользовательский вопрос не открывается.

`exit_plan_mode` показывает текст плана и предлагаемые CLI способы продолжения.
Выбирается только предложенный `optionId`; отказ не превращается в согласие.
Runtime принимает native `current_mode_update` и `qwen/notify/session/mode-update`
только своей сессии. Поэтому guard использует текущий режим: после утверждения
плана можно писать файлы в том же ходе, а после входа в план запись и shell закрыты.
Выбор режима следующего сообщения остаётся настройкой разговора.

## Файлы, окружение и граница поддержки

Допуск сохраняет рабочие корни bwrap, маски `.env`/`.qwen`, проверку прямого SSH и набор
передаваемых credentials. `notebook_edit` проверяет `notebook_path`, `lsp` —
`filePath`; действуют физические рабочие и read-only корни.
Вызовы LSP с `item.uri` также проходят проверку физического пути.
Обработка медиа и workflow не допускаются в режиме плана, поскольку могут создавать
файлы без стандартного `write_file`. Native permission и проверки самого CLI
применяются дополнительно к серверному допуску.

Политика не устанавливает LSP, навыки, модели обработки медиа и поисковый backend.
Их доступность определяет установленный CLI и его подготовленная конфигурация.
Поиск может потребовать отдельного поддерживаемого маршрута и credentials;
ключ обычного запроса модели сам по себе не гарантирует поиск.
Штатный `web_fetch` в local-режиме CLI может обращаться также к localhost и частным
адресам; допуск не создаёт отдельной изоляции сети.

ACP-процесс песочницы по-прежнему создаётся на один ход и завершается вместе со своими
потомками после ответа или остановки. Разрешение native расписаний, целей и фоновых
задач не превращает GrigDesk в постоянный worker этих функций; исполнение после
закрытия процесса и отдельное долговечное расписание этой интеграцией не предоставляются.
Сохранённое состояние доступно следующему запуску в рамках возможностей самого CLI.
В режиме «Хост» процесс живёт между ходами (см. ниже).

У проверенных CLI 0.27.2 и 0.27.3 есть отдельное ограничение субагентов: `AgentCore`
сбрасывает invocation context перед своим циклом. Required attached guard не получает
родительскую session/prompt identity и возвращает `Tool invocation guard failed`
до обращения к серверному guard. Допуск `agent` позволяет запустить субагента,
но его инструменты в этих версиях остаются недоступны. Это относится также к
дочерним исполнениям workflow, использующим тот же цикл. Защита не отключается
и identity чужой сессии не приравнивается к родительской; нужна совместимая
реализация передачи контекста во внешнем CLI.

Отказ повторно воспроизведён на настоящем CLI 0.27.3 с локальным синтетическим API:
до `AgentCore.runReasoningLoop` родительский invocation context существует и совпадает
с сессией Config, внутри цикла он отсутствует. `createManagedExternalToolGuard`
в attached-режиме выбрасывает ошибку до reverse RPC. Обновление с 0.27.2 до 0.27.3
само по себе этот отказ не устраняет.

В отдельной экспериментальной копии 0.27.3 проверена передача только
`version/sessionId/promptId` через собственный AsyncLocalStorage для guard.
Обычный invocation context субагента остаётся пустым: намеренная изоляция workflow
и channel-полномочий не снимается. Attached guard использует эти данные лишь при
отсутствии обычного контекста и совпадении сессии Config; сервер продолжает проверять
активный prompt, отмену, инструмент и рабочие корни. Такой прототип восстанавливает
чтение, запись и разрешённый shell обычного foreground-субагента, сохраняя запрет
прямого SSH, записи за пределы рабочего корня и через выходящий симлинк.
Это доказательство направления исправления внешнего CLI, а не внедрённый патч
GrigDesk или установленного пакета. Фоновые/resume-сценарии этим опытом не проверены.

## Режим «Хост»

Выключенный по умолчанию режим включается вручную настройкой
`providerSettings.qwen.allowHostAccess` (строгое `=== true`) с подтверждением
`confirm.on`; сервер требует `confirmed === true`. Режим даёт доступ к Docker,
процессам и файлам с правами пользователя сервера без автоматического sudo.
Выбранные режимы подтверждения и запрет прямого SSH сохраняются. Host не является
новой изоляцией: это доверенный запуск без bwrap, и предупреждения о песочнице
к нему не применяются.

Запуск идёт штатным launcher выбранной копии CLI с её reader lease. Пользовательские
HOME/PATH и native QWEN_HOME доступны; runtime output изолирован в отдельный
QWEN_RUNTIME_DIR. Исходные настройки не переписываются: системный слой копируется
во временный overlay, ключи маршрутов заменяются проверенным снимком моделей,
автообновление CLI и telemetry выключаются. Настройки LSP/MCP/hooks/skills/media
читает сам CLI; отсутствующая зависимость даёт видимую причину, а не установку
или расширение прав. Модель выбирается только `session/set_config_option`;
при отсутствии массива configOptions Host отказывает до prompt, persist-default
fallback `session/set_model` в Host не используется.

Guard остаётся обязательным: `QWEN_CODE_PRIVATE_EXTERNAL_TOOL_GUARD=required-v1`
и private-parent nonce, без attached-provider маркера. Не-shell инструменты
выполняет builtin-путь CLI; `run_shell_command` и `monitor` проходят reverse guard
по identity сессии (`qwen/policy.ts`, ветка `hostAccess`): своя сессия в живом
канале, непустой callId, объект arguments, абсолютный invocationCwd при наличии,
строка command. Plan запрещает shell; прямой SSH оценивается текущей настройкой
`blockDirectSsh`, unknown verdict не разрешается; ошибка/EOF/отмена дают deny.
Родительский promptId ребёнка не подделывается. Дополнительного списка разрешённых
не-shell имён GrigDesk в Host нет.

Host требует включённого общего «Держать агента чата живым между ходами»,
работающего user systemd и отдельного unit приложения (`.service` либо
`app-grigdesk-*.scope`; обычная terminal/session scope не подходит). Процессы
принадлежат уникальному transient user scope с `KillMode=control-group` и
`BindsTo`+`After` к app unit: остановка приложения завершает весь native scope,
автозапуска после перезагрузки ОС нет. Нет manager или своего app unit — видимый
`qwen_host_scope_unavailable` до prompt, без fallback в песочницу. Разовый запуск
Host без живой сессии отклоняется (`host_persistent_required`). Закрытие
подтверждается inactive/not-found и пустой собственной cgroup; при отказе запись
и слот удерживаются до подтверждённого повторного закрытия, чужие PID/unit не
затрагиваются. Живые процессы не вытесняются молча: при заполненных слотах
(порог общего `maxSessions`) новый Host получает видимый отказ с предложением
закрыть ненужный живой процесс.

Процесс живёт между сообщениями: фон, расписания и субагенты публикуются в ленте
через общий владелец фоновых ходов, «Стоп» прерывает ход, а закрытие живого
процесса, сброс памяти и выход GrigDesk завершают его. Heartbeat active-work
(v1, interval 5000 мс, категории agent/notification/shell/session/workflow/tool)
согласовывается в initialize и обязателен в ответе Host; старый seq, чужие сессии
и повреждённые снимки не очищают задачи. Replay окна `session/load` подавляется:
native воспроизводит историю до запуска cron-планировщика, а настоящий cron не несёт
`backgroundTurn` (эту метку ставит только background_notification-цикл), поэтому после
автономного старта cron/loop его обычные кадры окна откладываются по принадлежности,
а не отбрасываются как история. Наблюдённый жизненный цикл session hold решает судьбу
очереди: held→released внутри окна подтверждает завершённый цикл и публикует его ровно
один раз с полным текстом после хода; незавершённый цикл ждёт свежего session hold
(подтверждение ≤11 с, иначе очередь отбрасывается как история). Принадлежность снимается
при `session/prompt`, поэтому текст cron не вклеивается в ответ пользователя,
а исторический replay не создаёт новый фон. Включение/выключение настройки применяется
к следующему ходу: старый host handle закрывается до запуска песочницы;
немедленное прекращение уже начатой работы — закрытие живого процесса в списке.
Смена профиля отделяет native-память (отдельный namespace `host-builtin-v1`,
sessionId между профилями не переносится); переписка GrigDesk сохраняется.

Две особенности отказов: при отказе handshake ресурс, переданный владельцу
(`onOwnedProcess`), живёт до явного закрытия живого процесса — слот удержан и
виден в списке, повторный send даёт явную ошибку «незавершённая подготовка
требует подтверждённого закрытия»; закрытие хода в окне открытия показывает
человеку общую stopped-причину остановки, исходная причина остаётся в журнале.

## Проверки

`qwen-tool-policy.test.js` проверяет весь добавленный набор, неизвестные имена,
identity, отмену, файловые корни, SSH и перевод вопросов/плана.
`qwen-native-tools.test.js` проверяет настоящий CLI с локальной синтетической моделью:
сохранение списка дел, текст ответа на вопрос, утверждение плана и субагента.
Для субагента проверяется именно закрытый отказ при утрате invocation context,
а не успешное выполнение инструментов. Дополнительно проверяются настоящий
`web_fetch` с локальной страницей и изменение ячейки `.ipynb`.
Платный поиск, внешние API обработки медиа и браузерная приёмка выполняются отдельно;
допуск имени инструмента не считается проверкой этих сервисов.

Host проверяется без платных вызовов: `qwen-tool-policy.test.js` — ветка Host guard
(shell/monitor, чужая сессия, plan, SSH, неизвестное имя); `qwen-live.test.js` —
один процесс на два хода, обязательный guard ACK, фон и cron после ответа,
Stop/EOF/heartbeat, replay, настоящий cron в окне load без искусственной metadata
и cron, завершившийся (held→released) в окне load или во время foreground, fingerprint;
`qwen-host-lifecycle.test.js` — отказ handshake и повтор close, force-close во
время initialize на двойниках systemd-run/systemctl (один scope, отсутствие
позднего prompt, пустой lease, argv без sudo); `qwen-host.test.js` — неизменность
исходных settings, отсутствие attached-маркера и `session/set_model`, очистка
overlay; UI-тест `qwen-provider.component.test.js` — ручное подтверждение, Apply,
отказ и повтор на английском. Native-приёмка с живым user scope (процессы и сокеты
хоста, субагент, LSP/медиа/поиск, MCP scopes, подтверждения, картинка второго
send, close detached shell и lease) требует работающего user systemd приложения
и выполняется владельцем на хосте; в окружении исполнителя без user bus эти
проверки дают видимый отказ и не считаются зелёными.
