# «Связь теряется при отправках в несколько чатов» = POST держал соединение весь ход

Симптомы при нескольких одновременных ходах: интерфейс «теряет связь», из топбара исчезают
CPU/RAM, после F5 остаётся реплика человека без работающего агента и без ошибки.
Исправлено протоколом приёма хода — [доставка хода](turn-delivery.md). Ниже — механизм,
чтобы не вернуть его обратно.

## Причина

- **Каждый ход занимал HTTP-соединение до конца работы агента**, включая ожидание очереди
  чата: `send` ждал `POST /api/chat`, а сервер отвечал только по итогу `runChatTurn`. Прямые
  слушатели HTTP/1.1 (Fastify без `http2`), у Chrome —
  шесть соединений на хост, одно из них держит общий SSE вкладки. Пять ходов забирали всё:
  метрики, `stop`, ответы на разрешения и запись истории стояли в очереди браузера, хотя
  сервер отвечал за миллисекунды.
- **Запись истории не подтверждала запуск.** Реплика сохранялась PUT-ом до POST; если POST
  не дошёл (очередь браузера, F5, обрыв), в истории оставалась голая реплика. Флаг
  `modelRequestStarted` ставился до fetch, а не по ответу сервера, id отправки не было,
  поэтому ни отличить «не дошло» от «идёт», ни безопасно повторить было нельзя.
- **Фоновые запросы усиливали затор**: опрос метрик запускался каждые 3 с, не дожидаясь
  прежнего (GET — две попытки по 30 с), любая ошибка стирала метрики (`data = null`),
  поздняя ошибка старого запроса перетирала свежий ответ. `_persist` повторно слал тот же
  снимок чата, пока первый PUT ждал ответа.
- **Переподключение SSE не подбирало pending**: `hello` сверял спросы, ходы и историю, но
  не `chats/pending`; ответ, записанный во время разрыва, появлялся только после F5.
  Подбор pending подтверждал запись DELETE до устойчивой записи истории и удалял записи
  чатов, которых в окне не было, — ответ мог пропасть насовсем.

## Как проверено

- Журнал окна за 26.09.2026: 585 медленных `GET /api/system` с медианой 28,6 с при
  тривиальном обработчике — ожидание соединения, а не работа сервера; 67 `TypeError` на
  `POST /api/chat`. Причину каждого исторического обрыва журнал не устанавливает: в нём нет
  стадии приёма и id отправки.
- Chrome против настоящего модуля чата со stub-исполнителем, один SSE и десять отправок:
  старый режим — 5 запусков из 10, метрики и `stop` упираются в таймаут; приём по `turnId` —
  все 10 приняты за 13–18 мс, метрики 10 мс, `stop` 3 мс, после reload сервер знает все ходы.
- Поведенческие тесты перечислены в [доставке хода](turn-delivery.md#проверки); до
  исправления они падали на тех же местах (долгий приём, дубли PUT, накопление опросов,
  отсутствие состояния доставки, pending без `hello`).

## Что осталось синхронным

- **Сжатие контекста** — по-прежнему POST на весь ход: одно на чат, по явной кнопке,
  переводить его на приём по `turnId` нужно вместе с раскладкой итогов «сжатие прервано».
- **Telegram-пульт** ходит без `turnId` через inject внутри процесса: соединений браузера
  он не занимает.
