# Живые проверки Coding Plan

## Успешная проверка с новым ключом 28.10.2026

После замены ключа три прямых запроса к Coding Plan endpoint — `glm-5.3`,
`glm-5.3-flash`, `glm-4.7`, `ping`, `max_tokens: 16` — вернули HTTP 200 без ошибки Z.ai.
Ключ прочитан из актуального `.env` поверх унаследованного окружения; значения ключей
не выводились. Проверка проведена после 14:20 UTC, вне опубликованного пикового окна.

Затем `glmLiveSmoke.mts --mode coding-plan --confirm-live --binary <ELF>
--cache-dir <отдельный cache>` запущен в отдельной копии серверных исходников.
Только в этой копии временно расширены политика режимов и ограничение entrypoint smoke.
Использован выбранный рабочий ELF без замены; homes и cache проверки отдельные.

Отчёт: `kind: live`, `mode: coding-plan`, `model: zai/glm-5.3`, `ok: true`,
`turns: 8`, `modelErrors: []`. Успешны все восемь проверок: ответ, маркерные
чтение/правка/команда, рассуждение и результат инструмента, resume, foreground-критик
с дочерней лентой, запрет SSH, остановка во время approval и повтор `turnId` после F5.

Контрольный расчёт `api` по `glm.inputs` выбранного ELF воспроизвёл существующий admission.
Та же `glmCompatibilityIdentity` дала для `coding-plan`:
`cec077352a4f30466bcbc531ed4010539e8b675d3b9ce852a5b01f8290081522`.
Адрес режима входит в хеш, поэтому отпечаток отличается от `api`.

Только после полного успеха в основном дереве разрешены `api` и `coding-plan`,
а в `deepseek/compatibility/glm.json` добавлена точная запись Coding Plan. Старые ELF
с единственным admission `api` не получают новый допуск от правки серверного файла:
нужна упаковка выпуска с новым списком и его установка. Способ выбора ключей, окно
доступа и `usage.ts` не менялись. Тип прежнего ключа остаётся не установлен;
успех нового ключа сам по себе не доказывает, что прежний был Standard.

## Первая неуспешная проверка 28.10.2026

28.10.2026 `glmLiveSmoke.mts` проверен в режиме `coding-plan` на актуальном ELF,
с отдельным cache и ключом `ZAI_CODING_API_KEY` из `.env` папки данных.
В основном дереве `GLM_ALLOWED_MODES` и `deepseek/compatibility/glm.json` не менялись:
временный допуск и снятие ограничения smoke на `api` существовали только
в отдельной копии серверных исходников для проверки кандидата.

Совместимость рассчитана той же `glmCompatibilityIdentity`, которую использует smoke,
по `glm.inputs` выбранного ELF. Контрольный расчёт для `api` воспроизвёл существующую
запись допуска. Для `coding-plan` получен другой отпечаток: адрес режима входит в хеш,
а маршрут использует встроенный endpoint `zai` библиотеки pi-ai без `baseURL` в overlay.

Отчёт имеет `kind: live`, `mode: coding-plan`, `ok: false`, `turns: 8`.
Первый ответ и шаг остановки завершились кодом `glm_quota_exhausted`; модель — `glm-5.3`.
Ответ, инструменты, resume и foreground-критик не прошли проверку. Успешен только
локальный шаг повторного `turnId`, который сам по себе не подтверждает доступ к модели.
Повторного smoke в этой попытке не было.

Smoke сохранил публичный код ошибки, а не исходное HTTP-тело Z.ai. Этот результат
не подтверждает ограничение подписки официальными клиентами и не доказывает его отсутствие.
Он также не давал основания открывать режим: после этой попытки политика разрешала
только `api`, admission Coding Plan отсутствовал. Для открытия требовалась отдельная успешная
живая проверка после устранения причины отказа; ключи и usage для этого не меняются.

## Прямые запросы 28.10.2026

В 10:45:13–10:45:15 UTC выполнено по одному запросу для трёх моделей с тем же источником
`ZAI_CODING_API_KEY`: `.env` папки данных поверх унаследованного окружения. Проверка
валидности ключа и чтение квот не повторялись. Повторов запросов не было.

Адрес: `POST https://api.z.ai/api/coding/paas/v4/chat/completions`.
Тело каждого запроса, где `<модель>` заменено на значение из таблицы:

```json
{"model":"<модель>","messages":[{"role":"user","content":"ping"}],"max_tokens":16}
```

| Модель | HTTP-статус | Код Z.ai |
| --- | --- | --- |
| `glm-5.3` | `429` | `1113` |
| `glm-5.3-flash` | `429` | `1113` |
| `glm-4.7` | `429` | `1113` |

Полное тело ответа совпало побайтно для всех трёх моделей:

```json
{"error":{"code":"1113","message":"Insufficient balance or no resource package. Please recharge."}}
```

Для каждого ответа отдельно сохранены статус, время запроса и полный текст тела без
усечения; секреты маскируются до записи. Проверка сохранённых артефактов на наличие
прочитанных ключей прошла.

Текст `Insufficient balance` согласуется с классификацией `QUOTA`, но не восстанавливает
утраченное тело ответа предыдущего smoke. Ответ провайдера не устанавливает причину
отказа активной подписки и не подтверждает влияние пиковых часов или запрет сторонних
клиентов. Ошибка повторилась на всех трёх запрошенных моделях.

После отказа этих прямых запросов проверка была остановлена: новый smoke тогда не запускался,
его скрипт не дорабатывался. `GLM_ALLOWED_MODES` оставался `['api']`, admission Coding Plan отсутствовал.
Доработка отчёта smoke и новый живой прогон требовались перед открытием режима.

Последующая [сверка типов ключей и кодов Z.ai](glm-key-types.md) установила, что прямые
запросы в 10:45 UTC выполнены вне опубликованного пика 06:00–10:00 UTC. Standard-ключ
может давать `1113` при действующей подписке даже на Coding Plan endpoint; тип текущего
ключа не установлен. Отображение `Pro` в usage не различает эти варианты биллинга.

В 11:15 UTC [дополнительная диагностика](glm-entitlement-diagnostics.md) подтвердила
успешно оплаченный активный Pro без блокировки, но OpenAI Coding и Anthropic Coding
снова вернули `1113`. Сохранены полные ответы, диагностические заголовки и Anthropic
`request_id`; тип ключа через доступные метаданные кабинета не установлен. Это были
два прямых запроса без повторов, а не новый live smoke; допуск не менялся.

Последующая [проверка официальным Claude Code](glm-entitlement-diagnostics.md#проверка-официальным-клиентом)
также получила `1113`. После этого доработан только
[сбор HTTP-ошибок smoke](glm-smoke-http-errors.md): статус, полный очищенный текст
и остановка после неуспешного первого ответа. Новый живой smoke Coding Plan
тогда ещё не запускался; успешного admission не было. Результат с новым ключом приведён выше.
