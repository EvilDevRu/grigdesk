# Codex: запись файлов через shell называется в строке Bash

Модели Codex на Ultrafast пишут код не через `apply_patch`, а shell-командой внутри
`/bin/bash -lc`: `cat > P <<'EOF' … EOF`, `cat >> P`, `… | tee P`, `sed -i … P`, `> P.ext`.
Для app-server это обычный `commandExecution` без диффа — item `FileChange` не приходит.
Нормализатор показывал такую строку серым `Bash` с началом команды в заголовке, и человек
читал ход как «агент ничего не писал», хотя на диске появились файлы.

Проверено сверкой сырого журнала `~/.codex/sessions/…/rollout-*.jsonl` с сохранённой
лентой чата «Parser GEO» (Codex 0.172.0, `gpt-6.2-sol`, ultrafast): транспорт ничего не
теряет — все 357 `CommandExecution`, 42 `FileChange` (111 файлов), 463 `DynamicToolCall`
и 61 `AgentMessage` из журнала присутствуют в ленте с совпадающими наборорами файлов.
`apply_patch` в 0.172 идёт внутри JS-обёртки `custom_tool_call name=exec`
(`tools.apply_patch(...)`); сама обёртка в ленту не попадает — диффы доходят отдельными
`FileChange`. Проблема была только в подаче shell-записи.

## Контракт

`shellWriteFiles(command)` в `server/src/lib/executors/_codexSteps.ts` возвращает
уникальные пути в порядке появления. Читаются четыре формы:

- `cat > P <<TAG` / `cat >> P <<TAG` — путь между `cat` и heredoc-меткой;
- `tee P` и `| tee P` — первый аргумент после `tee`, флаги `-a`/`-p` пропускаются;
- `sed -i … P` — последний аргумент;
- голый `> P.ext` / `>> P.ext` — только с расширением исходника или документа из
  `SHELL_WRITE_EXTENSIONS`; `/dev/null` и `>` без расширения записью не считаются.

Invariant: путь берётся только из текста команды. Тело heredoc не разбирается и в ленту
не попадает — это имя записанного, а не дифф; дифф у shell-записи появляется только
через отдельный `FileChange`, которого у неё нет. Кавычки внутри `-lc` экранированы
(`\"`, `\'`) и раскрываются до разбора.

Шаг `Bash` получает поле `files: string[]` (тот же ключ, что у `Edit`), а заголовок —
`→ N файл: a.ts, journal.md` с базовыми именами и пределом `SHELL_WRITE_TITLE_LIMIT`
(300); без записи заголовок остаётся первой строкой команды. Полная команда по-прежнему
режется `cutMiddle` до `STEP_TEXT_LIMIT` (1200) — это отдельно от заголовка.

Окно (`web/src/views/chat/StepList.vue`, `kindOf(row)`): `Bash` с непустым `files`
получает класс и иконку правки `write`, имя инструмента остаётся `Bash`; в раскрытии
над командой перечислены полные пути (`.body.files`). `Bash` без `files` и `Edit` свой
вид не меняют.

## Стоимость

Разбор — четыре `matchAll` по строке ≤1200 символов на каждый `commandExecution`; на
чат с 1412 такой командой это микросекунды. Пишущие команды — 6–56% от `Bash`, к шагу
добавляются десятки байт. На скорость Codex не влияет: всё происходит после прихода
события. Хранение не растёт: в окно `MAX_CHAT_STEPS` шаги укладываются без изменений.

## Проверки

`tests/server/codex-app-server-contract.test.js` — «Codex: запись файлов через shell
называется в свёрнутой строке Bash»: шесть пишущих форм из реальной ленты, чтение без
`files`, `/dev/null`. `tests/web/step-list.test.js` — знак правки, полные пути в
раскрытии, неизменность обычного `Bash` и `Edit`. После серверных правок нужен ручной
перезапуск. Живая проверка Ultrafast-ходом в окне не проводилась — регрессия доказывает
контракт нормализатора и компонента, а не поведение конкретной модели.
