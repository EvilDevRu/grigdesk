# Qwen Code: границы подключения и внешние источники

Сведения авторизации upstream уточнены 2026-11-12; реализация и локальный контракт CLI 0.27.2 —
2026-11-12. Автоматические проверки используют синтетический API на loopback;
они не подтверждают доступ аккаунта к оплаченной модели.

## Две точки подключения

Чат обнаруживает адаптеры в `server/src/lib/executors/` через `getProviderAdapters`.
Наличие метода `run` и универсального типа открывает чатовый runtime.
Карточка setup-only без `run` сама по себе не предоставляет поддержку чатов.

Конвейер отдельно обнаруживает shell-модули в `engine/lib/runners/`.
Каталог сервера `runnersCatalog.ts` не выводит поддержку Factory из наличия чатового
адаптера. Новый исполнитель требует обе точки подключения и проверки общего запуска.
Подробнее — [границы выбора раннера](../pipeline/runner-selection-boundaries.md).

В `factoryRouteCli.ts` запуск через systemd передаёт ключи отдельным `EnvironmentFile`,
а fallback без systemd наследует окружение процесса. Проверка запуска из терминала
не доказывает, что доступ доедет до transient service.

## Что сообщает upstream

Официальное описание различает headless CLI, ACP по stdio и отдельный daemon.
Совместимость одного транспорта не доказывает совместимость другого.
[Способы интеграции Qwen Code](https://qwenlm.github.io/qwen-code-docs/en/developers/rest-api-integration/).

Headless-документация описывает структурированный вывод и возобновление по конкретной
сессии. Конкретные события, отмена, permissions и учёт расхода требуют проверки выбранной
версии и транспорта.
[Headless Mode](https://qwenlm.github.io/qwen-code-docs/en/users/features/headless/).

Бесплатный Qwen OAuth прекращён с 2026-04-15. Актуальная документация также описывает
OAuth с подпиской Plus/Pro; этот способ наша интеграция не реализует. GrigDesk использует
API-ключи и конфигурацию провайдера; доступность конкретного аккаунта нельзя выводить
из наличия ключа или старого OAuth-файла.
[Authentication](https://qwenlm.github.io/qwen-code-docs/en/users/configuration/auth/).

Каталог `modelProviders` задаёт настроенные модели и их параметры. Эти записи сами по
себе не подтверждают успешную авторизацию и доступ аккаунта к выбранной модели.
[Model Providers](https://qwenlm.github.io/qwen-code-docs/en/users/configuration/model-providers/).

В дереве также есть Qwen3-TTS для озвучки презентаций. Это отдельная интеграция,
не runtime универсального coding-исполнителя.

## Контракт адаптера

Адаптер `executors/qwen.ts` использует штатные npm-установку, обновление, probe и окно
credentials. `DASHSCOPE_API_KEY` и безопасные `envKey` из `modelProviders` объявляются
адаптером. Inline `apiKey` не переносится в runtime или публичный каталог.
Принятое продуктовое решение — [правило подключения Qwen](qwen-integration-policy.md).

Штатная установка 0.27.2 использует проверенный профиль `audio-capture`, включая
native-исходники и prebuild. Заголовки выбранного Node готовятся до preview;
offline start не загружает их через node-gyp. Подробности и границы проверки —
[установка Qwen](qwen-install-hooks.md).

Settings читаются JSONC-парсером с проверкой ошибок. Источник discovery фиксирован
`config.rootDir`: system defaults, пользовательский Qwen home, проектный `.qwen`, system
settings. Содержимое файлов и состояние ключей входят в хеш инвалидации. Native
`availableModels` подтверждает полные id, включая authType; одинаковые bare id разных
провайдеров не сливаются. Неизвестные контекст и ступени рассуждения не выдумываются.
`availableModels[]._meta.contextLimit` задаёт рабочее окно native CLI; при отсутствии
этого поля используется явный `generationConfig.contextWindowSize`. Это metadata CLI,
а не результат проверки максимального запроса к API модели.

Выходную модальность CLI 0.27.2 не объявляет: зонд на синтетическом loopback API
показал `description: null` у provider-моделей, а `_meta.modalities` описывает только
вход (например, `image`/`video` у `qwen3.7-plus`); видео-, TTS- и embedding-id
подтверждаются как обычные чатовые маршруты с общим окном 200k. Поэтому чат-пригодность
объявляют данные каталога, а не подтверждение CLI —
[пригодность и свежесть](model-catalog-usability.md).

Для каждой подтверждённой модели metadata-сессия отдельно выбирает её через
`session/set_config_option` (`configId=model`) и читает `reasoning_effort` из `configOptions`.
Ступени и группировка принадлежат этой модели: они не наследуются от соседней записи.
Подтверждением служит `_meta['qwenCode/reasoning']`; общий fallback CLI без этого признака
не публикуется как поддержка конкретной модели. В частности, наличие общей шкалы у
неизвестной CLI модели или Wan не создаёт доступных усилий.
`default` сохраняется, в том числе как включение thinking у toggle-only модели.
Старый CLI без `configOptions` не получает выдуманных усилий. Ревизия ключа кэша
перечитывает прежний каталог без изменения identity пользовательской сессии.

Ход снова получает настройки выбранной модели, проверяет допустимость уровня и вызывает
`session/set_config_option` с `configId=reasoning_effort` до prompt. Требуется ACK с
подтверждённым текущим значением; `default` может разрешиться в конкретную ступень.
Без явного выбора используется native default. Отказ или устаревший уровень не превращается
в оплаченный запрос с молча проигнорированным усилием.

Граница metadata важна для сторонних моделей через QwenCloud: документация сервиса
описывает GLM-5.3 как thinking-only, а общий fallback CLI всё равно содержит `none`.
Без model-specific контракта адаптер не обещает эти ступени.
[QwenCloud Thinking](https://docs.qwencloud.com/developer-guides/text-generation/thinking).

При отсутствии `modelProviders` во всех слоях `qwen/discovery.ts` получает OpenAI-compatible
`GET <baseUrl>/models` выбранного сервиса. `GRIGDESK_QWEN_SERVICE` объявлен как choice
общего окна доступа; отсутствие выбора означает `dashscope-intl`. Адреса сервисов заданы,
модели — нет. Ключ `DASHSCOPE_API_KEY` передаётся только выбранному адресу, redirect запрещён.
Используется ограниченный `isolatedFetch`, без prompt и платного вызова генерации.

Ответ превращается в `modelProviders` в памяти, без записи исходного Qwen home.
В settings CLI попадают только id, имя и заданные нами baseUrl/envKey; признаки
каталога (`createdAt`, `nonChat` с причиной) живут в снимке и в settings CLI не
копируются. Явно нетекстовая выходная модальность помечает модель нечат-моделью,
а не выбрасывает: запись остаётся в реестре, но выбор моделей её не показывает.
CLI подтверждает native ids в той же обязательной песочнице.
Пустой или неверный ответ, HTTP-отказ и отсутствие ключа не заменяются фиксированным списком.
Ошибка discovery попадает в подпись доступа карточки. Native ACP-отказ сохраняет прежний
общий контракт исключения каталога, но дополнительно сохраняет безопасное пояснение
для того же fingerprint доступа. Несовместимый CLI, отсутствие bwrap и пустой native-каталог
не оставляют ложную готовность. В карточку попадают собственные сообщения с действием,
без stderr и секретов; успешный каталог снимает отказ. Состояние ограничено 16 доступами.

Каталог не объявляет общее `family=default`: ACP не сообщает, что модели заменяют
друг друга. Иначе общий краткий список оставил бы одну случайную запись и скрыл остальные,
включая новые Qwen. Регрессия проверяет Qwen4 вместе с несколькими поколениями и GLM.
У QwenCloud Individual/Team Plan используется вариант `qwencloud-token`; Alibaba Coding Plan
обращается к другому сервису и не заменяет его. Подсказки выбора явно различают подписки.

Кэш успешного автоматического снимка для ходов ограничен минутой и 16 источниками;
перечитывание каталога всегда обновляет API. Ключ, выбранный сервис, CLI и исходные settings
входят в identity. Поздний ответ прежнего доступа отвергается. Изменение только списка
моделей не меняет identity сессии. Чат и отдельный процесс конвейера используют один resolver.
Существующий явный `modelProviders`, в том числе пустой, имеет приоритет; повреждённый JSON
не разрешает автоматический fallback. Переустановка CLI не создаёт и не удаляет этот источник.

ACP-процесс создаётся для каждого хода. Сессия привязана к чату, физическому cwd и
отпечатку доступа; callback сохранения sessionId завершается до prompt. Replay загрузки
не публикуется новым ответом. Отмена завершает собственную process group и снимает reader
lease после выхода процесса. У bwrap явный доступ к текущему внешнему CLI context.

Подтверждённая модель сессии передаётся в общий `onRunMetadata` с источником `session`
до prompt и сохраняется в `actualModel` результата. Источники — `currentValue` опции
`model` в ACK `session/set_config_option`, собственное уведомление
`qwen/notify/session/model-update` и активные `config_option_update`. Нужен id своей
сессии; replay загрузки не публикуется. Отправленный model id, список доступных моделей
и пустой ACK `session/set_model` без названной модели подтверждением не считаются.
Поэтому отметка «запр.» исчезает только после факта от CLI. Проверки:
`tests/server/qwen-run-model.test.js` и native-сценарий clean-install в
`tests/server/qwen-cli-contract.test.js` с локальным синтетическим API.

`session/prompt` ожидает весь ход и получает отдельный аварийный предел 24 часа,
совпадающий с общим ACP-клиентом. Запросы подготовки и metadata сохраняют 30 секунд,
handshake — 15 секунд. Размышление и ожидание человека не обрываются коротким таймером;
сигнал отмены и ошибки CLI по-прежнему завершают ожидание сразу.
[Срок ожидания Qwen](qwen-prompt-lifetime.md).

Дельты текста и размышления собираются в законченные блоки до передачи в общий sink.
Старая токеновая лента отображается через объявленную адаптером capability без изменения
истории. [Границы блоков Qwen](qwen-stream-blocks.md).

Терминальные ACP-события инструмента переводятся в общий результат `res` с тем же id:
`completed` даёт `ok: true`, `failed` — `ok: false`. Дополнительное поле `error` сохраняет
обратный признак ошибки. Живая и сохранённая лента получают одинаковые шаги; отметка
успеха определяется полем `ok`, а не отсутствием ошибки или наличием текста результата.

Запуск требует Linux, bwrap и ACP v1 с private-parent capability и обязательным ACK
`qwen-code/external-tool-guard-ready=required-v1`. Совместимость другого транспорта
не используется как fallback. Песочница предоставляет выбранные writable рабочие корни и
отдельный home сессии; исходные settings не монтируются. Дополнительные корни также
передаются в CLI, guard использует тот же набор путей. В каждом корне `.qwen` и `.env`
перекрываются приватными пустыми данными. Для символической ссылки пустая цель
монтируется внутри новой файловой системы, без монтирования исходного секрета и без
замены ссылки на хосте. Ссылка на предка рабочей/служебной папки запрещается;
отсутствующая цель внутри writable рабочей папки не создаётся за человека.
Stderr сохраняется с момента spawn: ранний выход bwrap и гонка attachChild с `/proc`
показывают очищенную причину запуска после reaping child и снятия reader.
Корень песочницы и родительские каталоги
под `/tmp` доступны только на чтение; CLI получает отдельный writable `TMPDIR`.
Временные точки монтирования удаляются по
своему inode; чужие файлы не удаляются. Guard проверяет связь session/prompt/cwd,
известный инструмент, физический путь и запрет прямого SSH перед исполнением.

Адаптер объявляет этот рубеж как `directSshPolicy.enforcement=command-hook` из общего
контракта исполнителей. Публичный API сохраняет способ проверки и её пояснение.
Проверка выполняется сервером через final guard ACP, включая режим yolo; пользовательские
native hooks не становятся источником разрешений.

Managed settings отключают ToolSearch/ToolCall: разрешённые MCP объявляются сразу
прямыми инструментами и проходят final guard под собственными именами. Это не включает
MCP из пользовательских или проектных настроек. Ошибка native ACP сохраняет строковую
причину из `error.data.details`, например HTTP 401, после маскировки значений ключей.

Штатные web, todo, memory, agent/team, skill, LSP, notebook, media, cron/goal и workflow
инструменты допускаются по точным именам. Вопросы передают ответы через ACP в общую
карточку GrigDesk; утверждение плана и native-события режима обновляют режим guard
внутри текущего хода. [Набор и границы поддержки](qwen-native-tools.md).

Вложения пока получают явный отказ до prompt. Адаптер поддерживает несколько рабочих
корней и native `auto`; смена набора корней требует переноса памяти.
[Рабочие корни и режимы Qwen](qwen-workspace-permissions.md).
`mcpStatus` не заявляет подключение серверов, выданных будущему ходу.
Usage capability возвращает `unsupported` с пояснением, что получение квот пока не
реализовано в GrigDesk. Это не результат проверки возможности API Qwen и не нулевая квота.

С настоящим CLI 0.27.2 и локальным синтетическим API проверены каталог и его обновление,
read/write/shell, шаги, отмена, resume в новом процессе, разрешённый MCP и запрет прямого
SSH, записи в соседнюю папку и через выходящий симлинк. Пользовательский settings
в приватном runtime home допускает атомарную запись выбора модели; системный снимок
при этом остаётся read-only и имеет приоритет.

Карточка, каталог и ACP-reader также проверены тестовым CLI; конвейер — настоящим
launcher и host-status MCP в обоих файловых режимах, с проверкой эффектов и отмены.
Установка через карточку, браузерная приёмка и оплаченный smoke остаются отдельными
проверками на стенде. Настоящий ключ предоставляет человек через окно доступа.

## Режим «Хост»

Рубеж песочницы объявляется как `qwen-bwrap-private-guard-v1`. Отдельный вручную
включаемый режим «Хост» (`providerSettings.qwen.allowHostAccess`, строгое `=== true`,
подтверждение `confirm.on`, сервер требует `confirmed === true`) объявляет
`qwen-host-builtin-guard-v1` и запускает выбранную копию CLI без bwrap, с обязательным
builtin guard `required-v1` и private-parent nonce, но без attached-provider маркера.
Factory и недоверенные/model-only ходы Host не получают; разовый запуск Host без живой
сессии отклоняется (`host_persistent_required`). Sandbox fallback при отказе Host запрещён.

Host требует работающего user systemd и отдельного unit приложения; процесс принадлежит
уникальному transient user scope (`KillMode=control-group`, `BindsTo`+`After` к app unit).
Нет manager/unit — видимый `qwen_host_scope_unavailable` до prompt. Native-память Host
живёт в отдельном namespace `host-builtin-v1`; sessionId между профилями не переносится,
переписка GrigDesk сохраняется. Живой процесс, фон, keepAlive и слоты —
[живая сессия исполнителя](persistent-executor-session.md); набор инструментов и guard —
[штатные инструменты Qwen](qwen-native-tools.md#режим-хост).

## Окружение native-проверки

`tests/server/qwen-cli-contract.test.js` требует заранее подготовленный настоящий
CLI: абсолютный путь к `cli-entry.js` передаётся через `GRIGDESK_QWEN_BIN`.
Обёртка проверки с аргументом `--qwen-cli` устанавливает эту переменную перед
запуском профильного сторожа памяти. Нужен также работающий Linux bwrap.

Проверяющий процесс должен явно доставить путь CLI в тестовое окружение после его
очистки. Один список тестовых файлов этого не делает. Без пути все три native-теста
падают в подготовке с сообщением «передайте настоящий CLI через --qwen-cli», ещё до
вызова адаптера. Это отказ окружения проверки; он не доказывает дефект интеграции
и не заменяет проверку с настоящим CLI. Автоматического выбора CLI, загрузки пакета,
подмены тестовым CLI или тихого пропуска native-проверки нет.
