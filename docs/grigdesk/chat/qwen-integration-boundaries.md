# Qwen Code: границы подключения и внешние источники

Сведения upstream проверены 2026-10-18; реализация и локальный контракт CLI 0.27.2 —
2026-11-12. Автоматические проверки используют синтетический API на loopback;
они не подтверждают доступ аккаунта к оплаченной модели.

## Две точки подключения

Чат обнаруживает адаптеры в `server/src/lib/executors/` через `getProviderAdapters`.
Наличие метода `run` и универсального типа открывает чатовый runtime.
Карточка setup-only без `run` сама по себе не предоставляет поддержку чатов.

Конвейер отдельно обнаруживает shell-модули в `engine/lib/runners/`.
Каталог сервера `runnersCatalog.ts` не выводит поддержку Factory из наличия чатового
адаптера. Новый исполнитель требует обе точки подключения и проверки общего запуска.
Подробнее — [границы выбора раннера](../pipeline/runner-selection-boundaries.md).

В `factoryRouteCli.ts` запуск через systemd передаёт ключи отдельным `EnvironmentFile`,
а fallback без systemd наследует окружение процесса. Проверка запуска из терминала
не доказывает, что доступ доедет до transient service.

## Что сообщает upstream

Официальное описание различает headless CLI, ACP по stdio и отдельный daemon.
Совместимость одного транспорта не доказывает совместимость другого.
[Способы интеграции Qwen Code](https://qwenlm.github.io/qwen-code-docs/en/developers/rest-api-integration/).

Headless-документация описывает структурированный вывод и возобновление по конкретной
сессии. Конкретные события, отмена, permissions и учёт расхода требуют проверки выбранной
версии и транспорта.
[Headless Mode](https://qwenlm.github.io/qwen-code-docs/en/users/features/headless/).

Документация авторизации помечает прежний Qwen OAuth как прекращённый с 2026-04-15.
Она описывает доступ через API-ключи и конфигурацию провайдера; доступность конкретного
аккаунта нельзя выводить из наличия ключа или старого OAuth-файла.
[Authentication](https://qwenlm.github.io/qwen-code-docs/en/users/configuration/auth/).

Каталог `modelProviders` задаёт настроенные модели и их параметры. Эти записи сами по
себе не подтверждают успешную авторизацию и доступ аккаунта к выбранной модели.
[Model Providers](https://qwenlm.github.io/qwen-code-docs/en/users/configuration/model-providers/).

В дереве также есть Qwen3-TTS для озвучки презентаций. Это отдельная интеграция,
не runtime универсального coding-исполнителя.

## Контракт адаптера

Адаптер `executors/qwen.ts` использует штатные npm-установку, обновление, probe и окно
credentials. `DASHSCOPE_API_KEY` и безопасные `envKey` из `modelProviders` объявляются
адаптером. Inline `apiKey` не переносится в runtime или публичный каталог.
Принятое продуктовое решение — [правило подключения Qwen](qwen-integration-policy.md).

Штатная установка 0.27.2 использует проверенный профиль `audio-capture`, включая
native-исходники и prebuild. Заголовки выбранного Node готовятся до preview;
offline start не загружает их через node-gyp. Подробности и границы проверки —
[установка Qwen](qwen-install-hooks.md).

Settings читаются JSONC-парсером с проверкой ошибок. Источник discovery фиксирован
`config.rootDir`: system defaults, пользовательский Qwen home, проектный `.qwen`, system
settings. Содержимое файлов и состояние ключей входят в хеш инвалидации. Native
`availableModels` подтверждает полные id, включая authType; одинаковые bare id разных
провайдеров не сливаются. Неизвестные контекст и ступени рассуждения не выдумываются.

ACP-процесс создаётся для каждого хода. Сессия привязана к чату, физическому cwd и
отпечатку доступа; callback сохранения sessionId завершается до prompt. Replay загрузки
не публикуется новым ответом. Отмена завершает собственную process group и снимает reader
lease после выхода процесса. У bwrap явный доступ к текущему внешнему CLI context.

Терминальные ACP-события инструмента переводятся в общий результат `res` с тем же id:
`completed` даёт `ok: true`, `failed` — `ok: false`. Дополнительное поле `error` сохраняет
обратный признак ошибки. Живая и сохранённая лента получают одинаковые шаги; отметка
успеха определяется полем `ok`, а не отсутствием ошибки или наличием текста результата.

Запуск требует Linux, bwrap и ACP v1 с private-parent capability и обязательным ACK
`qwen-code/external-tool-guard-ready=required-v1`. Совместимость другого транспорта
не используется как fallback. Песочница предоставляет одну writable рабочую папку и
отдельный home сессии; исходные settings не монтируются. Проектные `.qwen` и `.env`
перекрываются приватными пустыми данными. Корень песочницы и родительские каталоги
под `/tmp` доступны только на чтение; CLI получает отдельный writable `TMPDIR`.
Временные точки монтирования удаляются по
своему inode; чужие файлы не удаляются. Guard проверяет связь session/prompt/cwd,
известный инструмент, физический путь и запрет прямого SSH перед исполнением.

Адаптер объявляет этот рубеж как `directSshPolicy.enforcement=command-hook` из общего
контракта исполнителей. Публичный API сохраняет способ проверки и её пояснение.
Проверка выполняется сервером через final guard ACP, включая режим yolo; пользовательские
native hooks не становятся источником разрешений.

Managed settings отключают ToolSearch/ToolCall: разрешённые MCP объявляются сразу
прямыми инструментами и проходят final guard под собственными именами. Это не включает
MCP из пользовательских или проектных настроек. Ошибка native ACP сохраняет строковую
причину из `error.data.details`, например HTTP 401, после маскировки значений ключей.

Вложения пока получают явный отказ до prompt. Дополнительные writable папки не
поддерживаются. `mcpStatus` не заявляет подключение серверов, выданных будущему ходу.
Отсутствие usage capability означает «не сообщает», а не нулевую квоту.

С настоящим CLI 0.27.2 и локальным синтетическим API проверены каталог и его обновление,
read/write/shell, шаги, отмена, resume в новом процессе, разрешённый MCP и запрет прямого
SSH, записи в соседнюю папку и через выходящий симлинк. Пользовательский settings
в приватном runtime home допускает атомарную запись выбора модели; системный снимок
при этом остаётся read-only и имеет приоритет.

Карточка, каталог и ACP-reader также проверены тестовым CLI; конвейер — настоящим
launcher и host-status MCP в обоих файловых режимах, с проверкой эффектов и отмены.
Установка через карточку, браузерная приёмка и оплаченный smoke остаются отдельными
проверками на стенде. Настоящий ключ предоставляет человек через окно доступа.

## Окружение native-проверки

`tests/server/qwen-cli-contract.test.js` требует заранее подготовленный настоящий
CLI: абсолютный путь к `cli-entry.js` передаётся через `GRIGDESK_QWEN_BIN`.
Обёртка проверки с аргументом `--qwen-cli` устанавливает эту переменную перед
запуском профильного сторожа памяти. Нужен также работающий Linux bwrap.

Проверяющий процесс должен явно доставить путь CLI в тестовое окружение после его
очистки. Один список тестовых файлов этого не делает. Без пути все три native-теста
падают в подготовке с сообщением «передайте настоящий CLI через --qwen-cli», ещё до
вызова адаптера. Это отказ окружения проверки; он не доказывает дефект интеграции
и не заменяет проверку с настоящим CLI. Автоматического выбора CLI, загрузки пакета,
подмены тестовым CLI или тихого пропуска native-проверки нет.
