# Сетевой сбой DeepSeek и отказ остановки

Новое правило: окончательная ошибка модели и исход остановки runtime сохраняются раздельно.
Раньше исключение `server.stop()` во внешнем `finally` заменяло готовый результат хода,
теряя `TRANSPORT` и сведения для восстановления.

## Допуск к продолжению

После принятого `turn/start` и окончательного `turn/end` с переходной ошибкой сборщик
возвращает `deliveryFailure`, `turnFailure` и `turnRecovery` только после успешного stop.
Работает существующее [автопродолжение](auto-continue.md): та же сессия, `turnId` и `runId`,
один итог и сохранённые шаги. Следующий запуск получает только просьбу продолжить и
сверить сделанное; исходный запрос, вложения и действия инструментов не переотправляются.

Owner бинарника подтверждает закрытие процесса, код **0 либо 130**, исчезновение своей
группы и отсутствие эскалации. Неизвестный код, выход сигналом, code 75, ошибка запуска,
оставшаяся группа или эскалация SIGKILL означают отказ. Отсутствие группы само по себе
не доказывает сохранность разговора. Общий бюджет ожидания и идемпотентный stop прежние.

Если сигнал уже отправлен через тот же `ChildProcess`, stop не посылает второй TERM:
launcher мог снять обработчики, завершая штатный выход. Это только запрет лишнего сигнала;
код 0/130, закрытие stdio и исчезновение группы по-прежнему проверяются полностью.

При отказе остановки остаётся исключение `deepseek_binary_cleanup`. Оно сохраняет:

- первичный `turnFailure` и признак работы, если окончательный результат был получен;
- `turnRecovery.canContinue: false`, запрещающий повтор даже при передаче ошибки в петлю;
- отдельный `stopFailure` и `stopDetails`: exit/code/signal, ошибку запуска, эскалацию
  и подтверждение отсутствия группы (`null` — подтверждения нет);
- сессию, принятые шаги и `retryState`; после prompt — только `post_prompt`;
- исходное исключение через `cause`, включая неизвестный исход и пользовательский стоп.

Сообщение человеку содержит обе причины. Сохраняются каталоги диагностики запуска
DeepSeek и GLM: их владельцы по-прежнему получают отказ cleanup. GLM использует общий
сборщик; собственная классификация входа, лимита и политики не заменяется сетевой.
Та же передача причин действует при ошибке web startup и у владельцев ACP settings,
каталога и ACP-хода: нештатный stop не подменяет первичную ошибку запуска или запроса.
У прерванного хода `stopped` остаётся внутри `cause` ошибки cleanup: внешний отказ
нельзя выдавать за штатный «Стоп» и скрывать его диагностику. При успешной остановке
обычный результат `stopped` сохраняется.
Без окончательного `turn/end` разрешение продолжать не возникает даже после штатного stop.
Стоп, новое сообщение, выключатель, паузы и бюджеты автоматики остаются прежними.

## Проверка и границы

`tests/server/deepseek-transport-cleanup.test.js` использует локальные HTTP/WebSocket,
настоящие сборщик, owner и петлю. Синтетический дочерний критик жив при окончательном
`TRANSPORT`; stop 0/130 допускает одно продолжение, code 75 и эскалация сохраняют обе
причины и запрещают его. Отдельно проверяются неизвестный исход, выход сигналом,
ошибка запуска, неостановленная группа, стоп и окончательные виды ошибок.
Ядро одного хода и приоритет человека проверяют `chat-auto-continue.test.js` и
`auto-continue.test.js`; совместимость GLM — его runtime/stop/startup проверки.

Критик фикстуры завершается **до** намеренно зависшего disposer. Это не доказывает вину
настоящего критика Harness. Внутренние повторы запроса модели не исполняются: подаётся
их окончательный исход. Платный API и отключение сети машины для проверки не нужны.

Причина реального зависания disposal и причина сети ниже `TRANSPORT` не установлены.
При code 75 автоматического продолжения по-прежнему не будет: человек получит исходную
ошибку и отдельную причину отказа cleanup. Исправленный ниже DNS-путь после завершённого
disposal теперь возвращает штатный код, сохраняя этот запрет для настоящих отказов.

Дополнительный опыт на неизменённом production ELF Harness **0.1.5-rc.2** использовал
настоящие web-профиль, инструмент делегирования `task` и loopback API. Родитель получал
окончательный `TRANSPORT` после пяти внутренних повторов. Критик оставался либо в
висящем модельном запросе, либо в восьмисекундной паузе повтора. Проверены continuable
и one-shot варианты фоновой работы; для имени `task` менялся только тестовый preset.

Все четыре варианта завершились кодом 0 без эскалации: stop занял 80–101 мс.
Наблюдение `Fiber._unload` не обнаружило незавершённых fibers: корневой disposal
занял 42–47 мс, `subagents.continuations()` — 1–4 мс. Поэтому удерживающий выход
disposer этим опытом **не установлен**, а зависание из инцидента **не воспроизведено**.
Данные не доказывают, что другой runtime или другое состояние сессии завершится так же.
Предварительный `session/cancel` как исправление этого неизвестного не добавлен.

Дополнительные опыты проверили зависание критика после HTTP-заголовков, первого текста
и первого фрагмента размышлений SSE. Во всех пяти вариантах continuable/one-shot stop
завершился кодом 0 за 82–104 мс; корневой disposal занял 41–58 мс. С включённой штатной
генерацией заголовка её модельный запрос тоже оставался незавершённым: stop подтвердился
кодом 0, исчезновением группы и отсутствием эскалации. Эта проверка также не воспроизвела
исходный отказ и не устанавливает его причину. Телеметрия отключается самим окружением
GrigDesk; её отключение в фикстуре соответствует рабочему адаптеру.

Сквозной локальный опыт через ядро чата и два запуска ELF подтвердил одно продолжение,
прежние sessionId/turnId/runId, один итог и сохранённый шаг `task`. Второй запуск получил
только `AUTO_CONTINUE_PROMPT`, без вложений; делегирование не повторилось. Такой же опыт
с исходным сборщиком до правки тоже проходит: это подтверждение штатного сценария,
а не регрессия, воспроизводящая прежнее зависание.

Строгая остановка применяется и к GLM как потребителю общего owner: внешний SIGKILL
теперь означает отказ cleanup и сохранение launchDir, даже когда группа исчезла.
Это изменение допуска остановки, необходимое для подтверждения штатного кода 0/130.

`tests/server/deepseek-startup-cleanup.test.js` проверяет на ELF первичные причины
`boot-kill` и `abort-startup`, а также отказ initialize у ACP settings, каталога и
ACP-хода при вторичной ошибке cleanup. Доказанные ниже механизмы не устанавливают
конкретную причину исходного инцидента.

## Изолированные DNS и MCP

Дополнительная проверка на том же payload worker использовала отдельные user, mount и
network namespaces, собственный DNS и только созданные фикстурой адреса. Сеть машины и
настоящий API не использовались. Родитель исчерпывал пять внутренних повторов и получал
окончательный `TRANSPORT`; настоящий фоновый `task` критика оставался активным.

Молчащий DNS удерживал `GetAddrInfoReqWrap` после отмены запроса критика. Все
`Fiber._unload` завершались за 56–74 мс, затем worker вызывал `process.exit(0)`, но
не завершался. Системная трасса показала SIGKILL worker от внутреннего launcher через
четыре секунды и итоговый код 75. Ответ DNS через 1,2 секунды после отмены освобождал
выход: тот же сценарий завершался кодом 0. Значит, этот воспроизведённый путь к cleanup
удерживает нативное DNS-ожидание после disposal, а не незавершённый Fiber.
`stopDetails.escalated` относится к эскалации внешнего owner своей группы; внутренний
SIGKILL launcher может дать code 75 при `escalated: false` и исчезнувшей группе.

TCP в состоянии SYN-SENT и TLS после ClientHello без ответа завершились кодом 0,
без эскалации, за 81–83 мс. Эти сетевые фазы сами по себе отказ не воспроизвели.

Отдельная stdio MCP-фикстура предоставляла настоящий инструмент работающему критику.
При быстром выходе MCP-сервера незавершённый вызов не мешал stop: код 0 за 124 мс.
Сервер с медленным выходом после EOF удерживал `mcp-client.connection`; его
`Fiber._unload` не завершился до вызова `process.exit(75)` трёхсекундным таймером host.
В этом варианте SDK ожидает закрытие stdio две секунды, затем TERM ещё две секунды;
этот путь превышает бюджет host. Отказ повторился в наблюдательном прогоне.

Оба опыта воспроизводят механизмы отказа, совместимые с исходным сообщением cleanup,
но не устанавливают, какой из них произошёл в реальном разговоре. Повторный cancel,
увеличение бюджетов и трактовка code 75 как успеха не добавлены.

## Подтверждение завершённой уборки

DNS-путь исправлен в host и launcher: после успешного disposal worker подтверждает по
IPC код 0/130. Через 100 мс launcher при необходимости завершает удерживаемый DNS
worker и возвращает подтверждённый код. Протокол и его границы описаны в
[жизненном цикле бинарника](deepseek-binary-lifecycle.md). Сроки 3/4 с и серверный owner
не ослаблены. Медленный MCP не заканчивает disposal и не отправляет подтверждение:
он по-прежнему даёт 75, отдельную причину cleanup и запрет продолжения.

Постоянная регрессия `deepseek-dns-cleanup.test.js` запускает настоящий ELF и ядро чата
в `unshare -rmn`. Молчащий DNS удерживает запрос критика к hostname модели; родитель
получает TRANSPORT после пяти повторов. На прежнем ELF это 75 и отказ; на исправленном
— 0, исчезновение worker и managed shell, одно продолжение с прежними sessionId/runId,
одним turnId, итогом и шагом task. Адаптер получает только `AUTO_CONTINUE_PROMPT`.
Отдельно проверены медленный MCP (75, ни одного продолжения) и «Стоп» (штатный выход,
ни одного продолжения). Тест требует явно выбранный подготовленный тестовый ELF;
без него или user namespaces пропуск сообщает причину. API и сеть машины не нужны.

`tests/deepseek/worker.test.mts` проверяет порядок IPC после dispose, отказ при ошибке,
зависании и отсутствии IPC, подтверждённые 0/130 после добивания, повреждённое сообщение,
переполнение вывода и сохранение реального кода 75. Настоящий timeout зависшего disposer
и остальные исходы web/GLM остаются в полной матрице `deepseek-binary-stop.test.js`.
