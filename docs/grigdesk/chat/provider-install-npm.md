# Приоритет npm при установке и обновлении CLI

Карточка `/api/providers` и `ProviderInstallService` используют общий
`providerInstall/commands.ts`. Resolver ищет исполняемый файл npm в абсолютных каталогах
PATH сервера и передаёт его путь адаптеру через `installation(config, { npm })`.
Пустые и относительные каталоги, каталог с именем npm и файл без права запуска не подходят.
Собственный npm packaged runtime исключён, пользовательский npm далее в PATH допускается.
Перед стартом доступность проверяется заново; кэш карточки не закрепляет старую команду.

## Явная операция и её окружение

Карточка остаётся лёгкой: npm-probes, startup-файлы и выбор каталога выполняются только
в явной операции `prepare`/`start`. Операция закрепляет одну пару внешних Node и npm.
`providerInstall/npmEnvironment.ts` строит копию окружения: снимает защитный
`npm_config_prefix=D/state/npm-global`, сохраняет пользовательские registry/proxy/CA/cache/
userconfig и оставляет одну каноническую форму ключа prefix. Внутренний, относительный
или пустой prefix из окружения — отказ `npm_prefix_invalid`, а не «навязанный».
Каталог выбранного Node ставится первым только в PATH установщика: npm — скрипт с `env node`.

`npm prefix -g` выполняется тем же внешним npm из безопасного cwd вне проекта.
Происхождение значения не выводится: политика применяется к самому effective prefix.
Внешний writable prefix используется как есть. Новый lifecycle
(`external-cli-lifecycle.md`) не подменяет недоступный пользовательский prefix
запасным `HOME/.local`: это отказ `npm_prefix_unwritable`, требующий нового preview.
Для прежних действий ниже сохранено описание fallback-а. Относительный, пустой или
внутренний (D/I/R) prefix — `npm_prefix_invalid`. Проверяются сам prefix, `bin`,
`lib/node_modules`, существующая цель пакета и ближайшие родители отсутствующих
каталогов; realpath ссылки посреди пути не обходит запрет внутренних папок.
Prefix внутри `<NVM_DIR>/versions/node/<версия>` допустим с предупреждением
`npm_prefix_nvm_scoped`; nvm default не меняется. Предупреждение справочное: GrigDesk
вызывает копию по абсолютному пути, а управляемый блок PATH держит её каталог при смене
версии nvm. Окно, всплывашка и строка итога его не показывают и не считают поводом
для внимания; код остаётся в job для диагностики.

Установка, определение установленного bin и сетевые повторы используют один
закреплённый контекст: явный `--prefix <P>` в argv и `runtime.env` вместо `ports.env`.
Обычный пакет ставится как `<имя>@latest`; локальный путь или `file:`-спецификация —
как есть, поэтому офлайн-стенд проверяет настоящую npm-границу без production-переключателя.
Отсутствие внешнего npm даёт `npm_missing`, отсутствие внешнего Node — `npm_runtime_missing`.
После установки новая копия проверяется адаптером и отдельным внешним запуском:
[JavaScript использует выбранный Node, нативный Linux ELF запускается напрямую](provider-install-native-bin.md).

| Исполнитель | Официальный npm-пакет | Если пользовательского npm нет |
| --- | --- | --- |
| Kimi | `@moonshot-ai/kimi-code` | Прежний официальный `install.sh` для установки и host-обновления |
| Claude | `@anthropic-ai/claude-code` | Прежний native installer, обновление через настроенный bin |
| Codex | `@openai/codex` | Прежний `codex update`; первая установка требует npm и выдаёт `npm_missing` |
| DeepSeek, GLM | Не используются для установки runtime из карточки | Управляемая поставка сохраняет отдельные установку и обновление |
| Tripo | CLI не устанавливается | API-провайдер с настройкой ключа |

Отсутствие npm выбирает прежний способ до запуска. Ошибка уже выбранной npm-команды
не переключает установку на другой installer; сетевые повторы работают в прежнем бюджете.
Вход в аккаунт остаётся отдельным действием. Contained Kimi по-прежнему запрещает update,
DeepSeek/GLM по-прежнему запрещают установку и update через общую карточку.
Native installers сохраняют admission и не превращаются в npm-операцию насильно.

Проверки: `tests/server/providers-install-npm.test.js` использует реальные декларации трёх
адаптеров, fake probe и собственные временные Node/npm. Проверяются карточка и job,
обе операции, прежние команды без npm, явный `--prefix`, гонка «npm исчез/появился»
между карточкой и стартом и отказы до активации. Настоящие пакеты на машину тесты не ставят.
Офлайн-границу с настоящим npm проверяет `providers-install-external-shell.test.js`.
