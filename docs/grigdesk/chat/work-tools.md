# Рабочие инструменты GrigDesk

`supervised_ssh` доставляется Claude через MCP, Codex как app-server dynamic tool,
Kimi и DeepSeek через ACP/MCP; descriptor и dispatcher едины. Агент видит все живые
SSH-сессии с допуском человека независимо от проекта задачи, проекта свободного чата
или обычной рабочей папки. Список содержит `sessionId`, `projectId`, `label` и `role`.
Команда выбирает сессию по `sessionId`; прежняя пара метка/роль допустима только при
единственном совпадении. Неоднозначный выбор возвращает `ambiguous_session`.

Любой `exec`, независимо от permission mode/auto/remember, создаёт `origin:'ssh'` в общей
`pendingPerms`; чат доставки задаёт сервер, ответ идёт только через
`/api/ssh/approvals/:pid`. Broker проверяет допуск до подтверждения и после него, не
подменяя выбранный ID другой сессией. Human shell отделён от exec-channel агента,
SFTP в tool отсутствует. Lifecycle и DTO описаны в [ssh.md](../plugins/ssh.md).

`supervised_db` сохраняет проектный scope: у задачи он строится из trusted attempt ledger,
а у свободного чата — из явно выбранного проекта (`workdir.kind: 'project'`). Сервер
проверяет действующую регистрацию. Недоверенная/legacy-задача не получает fallback к
проекту чата; обычный путь, выбор GrigDesk и удалённая регистрация не дают DB scope.
UI-context, текст сообщений, поля запроса хода и аргументы model tool не выбирают его.
Смена проекта входит в `workToolScopeKey`. Рубеж DB описан в
[дополнительных контрактах](../reference/runtime-contracts.md).
Прежний третий tool, `knowledge_search`, снят вместе с базой знаний — его устройство сохранено
в [истории базы](../overview/knowledge-base-history.md).

#### Что рисует всплывашка разрешения (контракт `input`)

`ChatPermission.vue` показывает не сырой запрос, а РАЗОБРАННЫЙ: `description` (что просят),
`details`/`plan` (шапка запроса), `command`, `file_path`, `diff` (две колонки, тем же
`web/src/shared/diff.ts`, что и лента) и `choices` — специфические кнопки варианта. JSON остался
последним фоллбэком для незнакомой формы. Раньше фоллбэк был единственным путём: Kimi
приезжал объектом ACP, и человек читал `{"toolCall":{"toolCallId":…}}` вместо «правлю такой-то
файл» — решение принималось вслепую.

Собирает это сам адаптер (`permissionPresentation` в `lib/kimi/runtime.ts`), и там два
неочевидных места:

- **ACP-запрос разрешения не несёт ни `kind`, ни аргументов вызова** — только `title` и
  текстовые блоки. Тип действия и команду runtime помнит по `toolCallId` из notification
  `tool_call`/`tool_call_update`; без этого классификатор «Авто» спрашивал бы про каждое
  чтение файла (проверено тестом «тип и команда читаются из восстановленного input»).
- **Правку Kimi отдаёт структурными блоками** `{type:'diff', path, oldText, newText}`, а не
  текстом. В permission-запросе обычно один блок, но lifecycle одного tool call может нести
  несколько; normalizer сохраняет каждый файл отдельно. Пока читались только текстовые блоки,
  дифф во всплывашку и ленту не попадал вовсе.

Обратный ход — три поля ответа, и каждое чем-то оплачено:

| поле | что делает | почему не «политика GrigDesk» |
|---|---|---|
| `choice` | нажатая кнопка из `choices` едет обратно своим `optionId` | у плана ACP различает «доработать» и «отклонить и выйти»; общего allow/deny для них мало |
| `remember` | «разрешать до конца сессии» → ACP-вариант `allow_always` | галка жила только в памяти вкладки: агент спрашивал снова из каждого окна и после F5 |
| `comment` | пояснение к отказу | ACP-outcome текста не несёт → `commentDelivered: false`, фронт досылает сообщением |

`grigdesk_help` читает встроенное руководство через тот же реестр и server-owned сервис,
включая режимы только чтения. Он принимает только index/search/read, возвращает версию
и revision, не даёт файловых прав и не меняет scope SSH/БД/browser.
[Контракт справки](help-tool.md) описывает порции чтения и подсказку обычного хода.
