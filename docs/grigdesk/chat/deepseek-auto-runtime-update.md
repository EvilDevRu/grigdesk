# Авторежим DeepSeek и обновление установленной поставки

Проверено сравнением native журнала, исходного host gate и распакованного payload
установленного ELF. Если в режиме `auto` обычный `bash` получает причину
«Действие требует разрешения пользователя», проверьте именно исполняемый payload.
Старый `toolPermissionPolicy.mjs` разрешал автоматически только `write` и `edit`,
поэтому любая shell-команда попадала в завершающий `ask`, включая чтение файлов
и работу внутри workspace. Наличие capability `toolPermissions: true` само по себе
не доказывает наличие исправления этой ветки.

В исправленной policy доверенный `bash` в `auto` возвращает `native`: команду исполняет
штатная workspace-write песочница. Явное `sandbox_permissions: danger-full-access`
по-прежнему проходит отдельное native подтверждение; `default` спрашивает, а
`read-only` не запускает shell. Поведенческая проверка —
`tests/server/deepseek-tool-permission-parity.test.js`: реальный ELF, эффект записи,
число запросов и отказ записи вне разрешённой папки.

Правка `deepseek/src/host/` не обновляет уже установленный ELF. Нужны сборка,
проверки и [установка candidate](../server/deepseek-binary-install.md).
В папке исходников весь цикл закрывает `grigdesk-ctl build deepseek`: зависимости,
подготовка среды, сборка, `verify`, проверка и живой smoke допуска GLM по выбору,
установка штатным установщиком и чистка кэша ([контракт цели](../server/ctl-build.md)).
Работающий процесс завершает ход на прежнем
payload; новый процесс получает новую поставку. Перезапуск сервера для совместимой
замены ELF не требуется. Допуск GLM сверяется по фактическим входам новой
поставки для режима потребителя; успешные offline-тесты DeepSeek его не заменяют.

Если live smoke обычного GLM API получает HTTP 429 с кодом `1113`
(`Insufficient balance or no resource package`), первый ход завершается неуспехом
и остальные ходы сценария не выполняются. Проверка новой поставки 28.10.2026
воспроизвела этот отказ после успешных offline-проверок авторежима. Повторная
проверка 29.10.2026 кандидата `grigdesk-ctl build deepseek` (композиция
`grigdesk-host-web-acp-v4:ccd84258…`, identity `53cdf3b3…`) упёрлась в тот же
429/1113 на первом ответе. Такой результат
не даёт нового admission и не позволяет штатную установку. Он относится к ключу
и маршруту обычного API; исчерпание подписки Coding Plan из него не следует.
Ключи двух режимов не взаимозаменяемы — [контракт доступа GLM](glm-access-contract.md).

У двух внешне похожих вопросов другая причина:

- Linux bubblewrap создаёт приватный `/tmp` для каждого shell-процесса. Созданная там
  папка не сохраняется для следующей команды. Для зависимых шагов нужен один вызов
  либо каталог внутри workspace.
- Папка артефактов вне workspace не становится writable от подсказки в сообщении.
  В текущем профиле её запись требует явного расширения доступа. Полученное разовое
  разрешение не расширяет standing policy для следующих команд.

Эти ограничения backend описаны в [контракте штатной песочницы](deepseek-native-sandbox.md).
