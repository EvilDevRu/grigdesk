# Фоновый запуск живого процесса

`ChatLiveSessions` присваивает каждой entry поколение `sessionToken`, каждому фоновому
циклу — `backgroundId`. Реестр `ChatBackgroundRuns` хранит записи по паре этих id,
создаёт отдельный `runId` и снимок параметров процесса. Поздний exit старой entry
не закрывает новое поколение того же чата. Закрытие каждой entry сообщается ровно один раз.

Обычный фон открывают события главного агента `assistant`, `result` или `user` без replay
и начало запроса модели `system/init`, пришедшие вне заказанного хода. Прочие служебные и
вложенные события сами фон не открывают: буфер до 20 событий вливается в коллектор при
старте и очищается перед следующим stdin. Отложенные команды уточнений сохраняют
собственный путь транспорта.

Пробуждение настоящего CLI (замер 6.10.2026, haiku) начинается служебными
`system/background_tasks_changed`, `system/task_updated`, `system/task_notification`, и лишь
через ~0,1 с — `system/init`. Сообщение человека, записанное в stdin в этот промежуток, CLI
ставит в свою очередь (`command_lifecycle queued`) и начинает (`started`) только после
`result` проснувшегося хода. Поэтому, когда CLI сообщает lifecycle, заказанный ход владеет
потоком только с `started` своей главной команды (или её replay). Всё, что пришло до этого,
относится к проснувшемуся ходу и открывает фон; `started` закрывает незакрытый фон. Старый
CLI без lifecycle отдаёт поток ходу сразу.

Запись проходит `running` → `publishing` → удалена. При публикации итог сначала пишется
в pending с `runId`, `source: 'background'`, `unsolicited: true`, затем идут `chat-orphan`
и `chat-done`. Сбой записи журналируется; orphan не изображает доставку, done закрывает
индикатор. Смерть процесса закрывает running без выдуманного ответа; publishing ждёт
своей записи.

Очередь модуля ждёт конца всех running и publishing циклов чата. Только после этого ход
становится running в ledger и объявляет `chat-turn-start`. Пул ждёт работающий фон до
сравнения параметров и отправки; ожидание прерывается abort заказанного хода. Транспорт
ждёт естественного result, exit или interrupt фона перед stdin. Пул и транспорт не ждут
записи pending: этим барьером владеет реестр. Фоновое завершение не берёт lock очереди.
При сливе сервер отказывает ожидающим ходам, будит очередь и ограниченно ждёт публикации.

Фон, возникший рядом с управляемым запуском, хранится скрытым. Управляемый старт скрывает
живой фон; после своего done модуль объявляет оставшийся цикл с тем же `runId`,
`restored: true`, временем, шагами и метриками. На сливе восстановление не объявляется.
Спросы работающего фона не снимаются finally предыдущего управляемого хода.

`POST /api/chat/stop` прерывает фон его поколения и снимает спросы. Штатное завершение
сохраняет процесс, даёт `stopped: true` и при пустом result текст «⏹ Ход остановлен.».
Страховка через 10 секунд закрывает не ответивший процесс; следующий ход восстанавливает
разговор по сохранённому sessionId. Индикатор снимается done реестра.

Фон занимает процесс: простой, вытеснение и массовое гашение свободных его пропускают.
Новый процесс чата поднимается только после того, как закрылся прежний: второй CLI на тот
же sessionId падает сразу. Список процессов показывает busy/running и обновляется при старте
и конце фона. Перенос
папки, сброс памяти, удаление чата и гашение одной сессии без force получают `409 chat_busy`.
Telegram-пульт игнорирует события с `source: 'background'`, но учитывает фон при ожидании
свободного companion-чата через `/active`.

Принятые ограничения: папка вложений по-прежнему входит в fingerprint параметров процесса;
её изменение может переоткрыть процесс после конца фона. Сжатие выжимкой закрывает процесс
вместе с фоном, и фон получает done без ответа. Предупреждение перед рестартом считает
фон ходом. «Стоп» пульта, чей запрос ждёт фон, остановит этот фон.
