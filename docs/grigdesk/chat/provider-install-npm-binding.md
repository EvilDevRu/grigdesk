# Подключение установленной npm-копии CLI

Для npm-команды адаптер объявляет `npmBinding`: идентификатор пакета, имя исполняемого файла,
поле config и имя переменной bin в `.env`. Общий сервис не ветвится по имени исполнителя.
Claude, Codex и host Kimi используют этот контракт для первой установки и обновления.

Сервис не спрашивает prefix повторно: установленный bin — это `<P>/bin/<имя>` выбранного
и закреплённого в операции каталога. Файл проверяется на исполняемость, затем новая копия
проверяется адаптером через временную копию config и отдельным внешним запуском:
[JavaScript — выбранным Node, Linux ELF — напрямую](provider-install-native-bin.md).
Только после этих проверок путь сохраняется общим `updateEnvFile`, применяется
к config и окружению сервера. Это подключает новую копию сразу и сохраняет выбор после
перезапуска. Порядок PATH, исходная копия и её файлы не меняются, `node_modules` вручную
не перемещается.

Отказ установки, отсутствие npm-бинарника, нераспознанная или устаревшая версия,
неудачный запуск внешним Node и отказ сохранения `.env` оставляют прежний bin.
Код ноль у npm сам по себе не даёт успеха. Отсутствующий `envPath` также запрещает
объявить успешное подключение. Причины `npm_binary_missing`, `npm_binding_failed`,
`npm_runtime_missing` и `npm_bin_conflict` переводятся на RU/EN.

## Перенос прежней ссылки

Если выбранный каталог — `HOME/.local`, npm создаёт bin ровно там, где может остаться старая
ссылка на D-копию пакета. Такая ссылка доказывается пакетом: realpath ведёт в
`<D>/state/npm-global/lib/node_modules/<packageId>`, а `package.json` подтверждает имя пакета.
Одного пути с подстрокой `.grigdesk` или имени файла недостаточно. Чужой файл, ссылка на другой
пакет или другой current bin дают `npm_bin_conflict` до запуска npm.

Для доказанной ссылки сервис пишет приватный журнал миграции в состояние установки: job id,
цель, соседнее резервное имя, исходные байты и identity ссылки, ожидаемый packageId и фаза.
Сначала устойчивый intent, затем rename в свободное соседнее имя, проверка identity и снова
устойчивая фаза. После успешной установки и `.env` резервная копия удаляется, старая D-копия
остаётся. При отказе до commit старый путь возвращается только если имя свободно или занято
доказанной заменой этой операции; неизвестный объект не удаляется, а блокирует новые установки
кодом `migration_recovery_required`. После commit старая ссылка не возвращается. При следующем
обращении восстановление читает фактический `.env`: новая привязка уже записана — резерв
удаляется, старая — ссылка возвращается, неоднозначный случай блокирует установки.
Собственный подтверждённый worker до этого останавливается по прежнему контракту.

Повтор после `needs_setup` идёт через обычное обновление: он может повторить npm-команду,
но не делает второй backup, не дублирует блок PATH и не требует устаревшей версии.

`tests/server/providers-install-npm.test.js` проверяет три декларации, запись выбора
в `.env` и окружение, а также отказы до активации. `provider-install-legacy-bin.test.js`
проверяет классификацию ссылки, backup/recovery, неизвестный объект, отказ npm до commit
и восстановление после перезапуска. `providers-install-external-shell.test.js` повторяет
EEXIST настоящим npm на локальном пакете. Пакеты и CLI владельца тесты не меняют.
