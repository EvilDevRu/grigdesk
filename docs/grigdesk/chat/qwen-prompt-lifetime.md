# Qwen: срок ожидания полного хода

`session/prompt` возвращает результат после всего хода, включая размышление,
инструменты и ожидание разрешения человека. Это отличается от коротких запросов
подготовки сессии. Общий 30-секундный предел транспорта раньше обрывал исправный
ход сообщением `ACP timeout: session/prompt`; поступление chunks не продлевало таймер.

В `qwen/runtime.ts` обёртка `request` передаёт необязательный отдельный timeout.
Только `session/prompt` получает 24 часа — такой же аварийный предел, как у общего
ACP-клиента. Запросы создания/загрузки сессии, модели, усилия и режима сохраняют
30 секунд из `openQwenTransport`; `initialize` отдельно ограничен 15 секундами.
Каталог также сохраняет короткие сроки запросов metadata.

Сигнал вызывающей стороны продолжает прерывать любой ожидаемый запрос. Поэтому
кнопка остановки и внешний срок этапа конвейера не ждут суточного предела.
EOF и ошибки CLI завершают ход сразу; автоматического повторного prompt нет.
В `finally` выпускается накопленный текстовый хвост, закрывается собственная
группа процесса и снимается reader lease. Позднее разрешение после отмены
не допускает исполнение инструмента.

При отмене активного prompt runtime ждёт его native-завершения не больше секунды
перед закрытием процесса. Это даёт CLI дописать доступную память, включая исходный
запрос первого хода. Guard и канал уточнений уже закрыты; зависший CLI не продлевает
остановку сверх этого срока. Ранняя отмена подготовки не ждёт завершения prompt.

Отмена сигналом на любой стадии, включая подготовку сессии, передаётся адаптером
с `stopped: true`. Native `stopReason: cancelled` имеет тот же исход без обязательного
AbortSignal. Сохраняются известная сессия и шаги вместе с выпущенным текстовым хвостом.
Чат показывает «⏹ Ход остановлен.», а следующий запрос может загрузить ту же сессию.
Другой `stopReason`, ошибка RPC или EOF без отмены остаются ошибками. Отмена после
создания сессии не отправляет новый prompt.

## Продолжение после сообщения с вложением

Общий чат добавляет `attachmentsDir` в `extraDirs` только для сообщения с вложением.
Если включать этот каталог в binding памяти Qwen, следующий текстовый ход ищет другой
home и завершается «Qwen: чужая или неверная identity сессии» ещё до `session/load`.
Остановка делает этот сценарий заметным, но чередование обычных сообщений с картинками
имело ту же причину.

Runtime сравнивает физические пути и исключает server-owned каталог вложений из
дополнительных рабочих корней, mounts и guard. Картинки по-прежнему передаются байтами
ACP. Настоящие корни проекта, cwd, чат и fingerprint доступа остаются в binding.

`qwen/session.ts:resolveQwenSessionHome` сначала проверяет маркер `session.json` в
home постоянной рабочей области. Для уже созданной сессии допускается также прежняя
формула с каталогом вложений. Выбирается только home с точным совпадением sessionId;
перебора чужих папок, сброса памяти и автоматического повторного prompt нет.
Старый home используется на месте, чтобы native-память оставалась доступной после
обновления. Другая рабочая область, чат или доступ не получают эту память.

`qwen-prompt-timeout.test.js` продвигает часы на 90 секунд после начала prompt:
проверяются успешное размышление, ожидание человека, исходная ошибка CLI и отмена.
`qwen-runtime.test.js` проверяет признак остановки, сохранение шагов и сессии,
возобновление после стопа, native cancelled и отсутствие prompt после ранней отмены.
`qwen-session.test.js` проверяет текст → картинка → текст с остановкой и без неё,
символическую ссылку на папку вложений, отсутствие её mount, восстановление старого
binding и отказ чужим чату, рабочим корням, доступу и sessionId до запуска CLI.
Отложенный ACK отмены успевает записать память, а отсутствие ACK ограничено сроком.
`qwen-cli-contract.test.js` проверяет настоящий CLI с локальным синтетическим API,
который отправляет размышление, ждёт реальную 31 секунду и завершает ответ.
Живая и возвращённая ленты совпадают. Оплаченный запрос к сервису для этой
проверки не требуется. Отдельные native-сценарии проверяют остановку первого хода,
доставку картинки и сохранение исходного текстового запроса при продолжении как
новой, так и прежней привязки home. Применение установленного исправления требует ручного
перезапуска сервера.
