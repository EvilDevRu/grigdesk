# Codex в чате: граница Git и отличие от конвейера

Адаптер `server/src/lib/executors/codex.ts` задаёт `workspace-write` и
`approvalPolicy: 'on-request'`, `approvalsReviewer: 'auto_review'` при открытии
или возобновлении обычного thread и повторяет их на каждом ходе. Это сохраняет
песочницу и направляет запросы расширения прав встроенному reviewer Codex.

## Почему Git требует отдельного разрешения

В стандартной политике Codex `workspace-write` каталог `.git` внутри разрешённого
рабочего корня защищён от записи. В worktree защита распространяется и на Git-каталог,
на который указывает файл `.git`. Поэтому доступ на запись в исходники не означает
доступ к индексу, объектам и ссылкам Git, необходимый для `git add` и `git commit`.

Это описано в [официальной документации OpenAI](https://learn.chatgpt.com/docs/agent-approvals-security#protected-paths-in-writable-roots).
При intentional `never` служебного чата агент не может запросить выполнение за
границей песочницы. В обычном чате такой запрос проверяет native reviewer; наличие
Auto-review не обещает одобрения. Проверять причину следует по effective настройкам
и событиям reviewer; пробный коммит в рабочем репозитории для диагностики не нужен.

Правило проекта «не коммитить без прямой просьбы» — отдельный уровень: явная просьба
даёт согласие на действие, но сама по себе не меняет файловые разрешения процесса.

## Чат и этап конвейера запускаются отдельно

Чат использует `codex app-server`, а этап конвейера — `codex exec` через
`engine/lib/runners/codex.sh`. У них разные параметры запуска и рабочие корни.
Движок явно передаёт `STATE_DIR` и `PROFILE_AGENT_DIRS` в `RUNNER_CODEX_ADD_DIRS`,
а раннер преобразует их в `--add-dir`. Недоступность каталога состояния из свободного
чата не объясняет отказ Git на этапе конвейера.

Серверные `supervised_ssh` и `supervised_db` не участвуют в локальных операциях Git.
Их состав не является причиной отказа commit/merge и не требует изменения для
исправления этих прав. Отдельный конфликт политики раннера и контракта `SHIP`
описан в [документе конвейера](../pipeline/codex-delivery-permissions.md).

## Почему недостаточно переключить один параметр

Адаптер принимает server requests `mcpServer/elicitation/request` и `item/tool/call`;
ручные запросы подтверждения команд и файловых изменений отклоняются с закрытием
собственного процесса. Поля sandbox и approvals принадлежат адаптеру,
поэтому форма нативных настроек их не редактирует. `/approvals` в чате также не
переключает политику — см. [контракт подтверждений Codex](codex-mcp-approvals.md).

Для ручных интерактивных разрешений нужна отдельная связь запросов app-server
с решением человека. Встроенный Auto-review её не использует. Конвейер выбирает
`--approve-for-me` только при route workspace-write и native workspace-write;
служебные и restricted режимы сохраняют свои границы.

У Codex уже есть [штатные подтверждения, Auto-review и правила команд](codex-native-approvals.md).
Снятие песочницы и собственный классификатор GrigDesk не являются обязательным решением.
