# Повторное использование сохранённых шагов

Способ проверки производительности описан в [методике замеров](../web/chat-performance-checks.md).
Клиент продолжает отправлять полный порядок сообщений и их метаданные, но может
не передавать повторно тела неизменённых, подтверждённых сервером `message.steps`.
Файлы истории и GET по-прежнему содержат полную переписку со всеми шагами.

## Возможность и отдельный маршрут

Новый сервер объявляет `historyStepReuseProtocol: 1` в `GET /api/chat/store`.
Без этого поля окно использует прежний полный `PUT /api/chat/store/chat`.
Сокращённый запрос отправляется исключительно в
`PUT /api/chat/store/chat/step-reuse`; прежний URI никогда не получает урезанную историю.
Это защищает от отката сервера после GET: прежний обработчик игнорировал неизвестные
поля и мог принять отсутствие steps как обычную полную запись.

Новый маршрут использует тот же обработчик сохранения, учёт активных записей,
`ChatHistoryStore.saveOne`, модель, workspace, CAS и уведомления. Публичного
исключения из общего auth guard для него нет.

Вместе с обычными `chat`, `archived`, `origin` запрос содержит:

```json
{
  "reuseSteps": {
    "protocol": 1,
    "baseRevision": 7,
    "refs": [
      {
        "messageIndex": 2,
        "sourceIndex": 2,
        "expectedKey": "assistant\u0000run-id\u0000message-id",
        "expectedLength": 150
      }
    ]
  }
}
```

`messageIndex` указывает сообщение в запросе, `sourceIndex` — сообщение последней
подтверждённой базы. Ключ вычисляет общий `shared/chat/chatMessageIdentity.ts`:
существующий приоритет устойчивых id, иначе роль и текст. Старый server-файл
идентичности остаётся фасадом с re-export. Позиции различают одинаковые legacy-ответы
с разными шагами; поиск первого совпадения текста не используется.

В позиции с ref поле `steps` должно отсутствовать. Даже `steps: null` запрещён.
Новые и неподтверждённые массивы передаются полностью. Без refs используется
прежний PUT, в том числе при очистке истории.

## Проверка базы и подтверждение

DTO и декодеры находятся в `shared/chat/chatHistoryStepReuse.ts`. Protocol строго равен 1;
revision — положительное safe integer, индексы и длина — неотрицательные safe integers.
Индексы назначения и источника уникальны; неизвестные поля DTO и неверные позиции
назначения отклоняются. Ссылки без сообщений не допускаются.

`server/src/lib/chat/historyStepReuse.ts` восстанавливает массивы под существующим
`withChatLock` до `mergeChat`. Проверяются оба ключа, позиция источника, наличие массива
и его длина. При совпавших refs изменение общей revision не мешает восстановлению:
серверные метрики и новые блоки не меняют сохранённые шаги. Несовпадение refs даёт 409
даже при одинаковой revision. CAS настроек независимо использует исходную revision
запроса; свежая head не выдаёт старым настройкам новое основание CAS.
Входные сообщения и база не мутируют: создаются новые оболочки сообщений.

Применение web pending и mobile reconcile назначает steps только сообщениям без уже
сохранённого массива. Существующие тела, в том числе пустые массивы, не заменяются
при повторе pending или присоединении метаданных финала. Web reconcile прикладывает
свежую head к событию `chat-store`; dirty-окно обновляет каталог без полного GET.

Неверная форма даёт 400 `bad_step_reuse`. Отсутствующая или изменившаяся база,
источник, ключ либо длина дают 409 `chat_steps_changed`. При отказе нет записи,
повышения revision и SSE; учёт активных сохранений освобождается.

После восстановления выполняется прежний pipeline, включая canonical protection
и атомарную запись. Успешный full или sparse ACK может содержать:

```text
stepReuseAck: {
  protocol: 1,
  revision: <итоговая revision>,
  confirmed: [{ messageIndex, sourceIndex, expectedKey, expectedLength }]
}
```

Подтверждение строится под lock по итоговой durable-истории, включая доказанный no-op.
Первая версия подтверждает только однозначное соответствие на том же индексе:
совпадают ключ и всё содержимое steps. Сначала сравниваются ссылки; сравнение JSON
разных массивов допускается только на сервере. Разные тела одинаковой длины не
подтверждаются. Canonical-замена или сдвиг позиции могут оставить `confirmed` пустым,
даже при `stale: false`, `restored: 0`, `dropped: 0`.

## Владение данными окна

Runtime helper `web/src/shared/chatHistoryStepReuse.ts` принадлежит экземпляру store
через WeakMap, не Pinia JSON. Для каждого чата он хранит один набор подтверждений:
revision, позицию, ключ, raw-ссылку массива, длину и версию его идентичности.
Удаление, очистка, reload, dispose и потеря capability сбрасывают основание refs.
Неприменённый GET и новая шапка сохраняют доказанные массивы; фактическую применимость
refs проверяет сервер. Архивирование сохраняет тот же чат и его шаги.

Первое подтверждение возможно по фактически принятой серверной истории. Browser
snapshot и GET, отклонённый из-за локальной dirty-правки, не подтверждают местные
данные и не поднимают их revision. Поколение чата защищает от позднего ACK после
более нового принятого GET либо удаления.

Перед `await api.put` `captureChatHistorySnapshot` отделяет массив сообщений, оболочки
сообщений и изменяемые вложенные метаданные: receipt, attachments и остальные JSON-поля.
Исторические steps разделяют raw-ссылки без обхода тел. Эта экономия требует
неизменяемого владения: завершение через `applyAssistantFinal` один раз копирует ленту
и её вложенные объекты; последующие исправления заменяют массив и изменённые объекты
по copy-on-write. Мутация исторического тела на месте недопустима, особенно во время PUT.

Помимо отпечатка без тел шагов dirty-проверка сравнивает ссылки, длины и версии массивов.
Замена массива той же длины ставит запись в очередь. ACK подтверждает именно снимок
отправки; изменения текста, receipt, steps, draft и новые сообщения за время сети
остаются dirty и уходят следующей склеенной записью.

Текущая активная лента и неподтверждённые массивы всегда передаются полностью.
Неявного подтверждения по нулевым флагам ответа нет; невалидный или отсутствующий
`stepReuseAck` оставляет клиента без новой базы refs.

## Fallback и границы ускорения

После named409 `chat_steps_changed` окно читает `GET /api/chat/store/head/:id` и один
раз повторяет sparse с новой `baseRevision`, прежними refs и исходной CAS revision.
Только повторный named409 подтверждает несовпадение refs и разрешает полный PUT того
же неизменяемого снимка. Отказ head, generic409, сеть, auth, лимит тела и 5xx сохраняют
обычный путь ошибки и retry, без полного PUT и преждевременного сброса основания.
404/405 нового URI разрешают один полный повтор и отключают capability до следующего GET.
Ошибка полного повтора завершает попытку; следующий штатный retry уже использует full.

Валидные `confirmed` принимаются и при `stale`, `restored` или `dropped`: подтверждение
построено по итоговой durable-истории и касается только перечисленных позиций.
Невалидный ACK сбрасывает основание. При stale CAS окно сверяет выбор модели, усилия
и режима по лёгкой head и повторяет запись, сохраняя доказанные refs.
Старая head без effort/mode требует полного GET для сверки настроек, сохраняя sparse PUT.
После обычного валидного ACK новый GET для подтверждения не нужен.
Сквозной тест с реальными `patchExecution`, canonical-проекцией и pending проверяет,
что после конфликта стабильная серия снова использует refs.

Протокол уменьшает повторную сериализацию шагов, но не сериализацию текста сообщений,
первого большого ответа, полного fallback или cold GET. Сравнение и запись на сервере
также имеют стоимость. Способ раздельного измерения этих затрат описан в
[методике замеров](../web/chat-performance-checks.md).

Основные проверки: `chat-step-reuse.test.js` в `tests/server` и `tests/web`,
`tests/server/chat-step-reuse-flow.test.js`, прежние проверки merge, CAS, workdir,
доставки и pending. Сквозной rollback-тест использует настоящий Fastify без нового
маршрута и проверяет 404 без записи, затем полный PUT со всеми телами.
