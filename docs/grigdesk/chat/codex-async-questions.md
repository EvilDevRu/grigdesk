# Асинхронные вопросы Codex

Проверено на Codex CLI 0.166.0. В обычном ходе `request_user_input_async`
не использует server request `item/tool/requestUserInput`. Он возвращает модели
`{"accepted":true}` и публикует `item/completed` с `item.type = "agentMessage"`,
`delivery = "async"` и массивом `questions`. Каждый вопрос содержит `title`
и необязательный массив строк `options`; текст сообщения уже содержит вопрос
и варианты в виде Markdown-списка.

Такая форма подтверждена журналом настоящего хода и схемой установленного CLI:
`v2/ItemCompletedNotification.json`, определения `AgentMessageDelivery`,
`AsyncUserInputQuestion` и ветка `agentMessage` в `ThreadItem`.
Это другой контракт, чем `ToolRequestUserInputParams` со стабильными ID,
`header`, `isBlocking` и ответом по JSON-RPC request ID.

## Карточка и ответ

Адаптер преобразует `questions` в общую structured-карточку через
`codexAsyncQuestionPresentation`. Поддерживаются один–три вопроса, варианты
и ограниченный свободный текст; без вариантов открывается текстовое поле.
Позиционные ключи различают одинаковые заголовки. Ответ проверяется по исходной
серверной форме, а `requiresExplicitUser` исключает автоматический выбор в `auto`.

Вопрос не блокирует независимую работу модели и канал обычных уточнений.
Ответ карточки поступает в тот же ход через штатный `turn/steer`, с проверкой
`expectedTurnId` и подсказкой продолжить исходную работу. Явный пропуск передаёт
отсутствие ответа и согласия; невалидный ответ не передаётся. Отказ доставки виден
предупреждением в ленте и не вызывает автоматического повтора.

Карточку создают только события с подтверждёнными thread/turn. Отдельный набор
waiter не смешивает item ID с native request ID. Повтор одного item в том же
ходе не создаёт вторую карточку; новое использование ID в следующем ходе допустимо.
Стоп, завершение хода, закрытие процесса и общий суточный deadline снимают ожидание.
Позднее решение не переносится в следующий ход.

Текст вопроса остаётся в переписке, но `delivery = "async"` исключает его
из итогового ответа и запасного commentary, даже при `phase = "final_answer"`.
Прежний обработчик читал только текст, поэтому вместо карточки появлялся список,
а вопрос мог ошибочно стать итогом хода. Режим `auto` причиной этой ошибки не был.

## Проверка

`tests/server/codex-async-questions.test.js` использует версионированную фикстуру
`tests/fixtures/codex-app-server/async-question-0.166.0.mjs` и настоящий
`openCodexSession`. Проверяются карточка, независимое продолжение, точная адресация
ответа, свободный текст, пропуск, повтор, чужие события, поздние решения,
закрытие процесса, отказ доставки и исключение вопроса из финала.

Прежние `tests/server/codex-questions.test.js` отдельно проверяют
`item/tool/requestUserInput`. Офлайн-проверка обоих каналов не заменяет
приёмку установленного сервера с реальной моделью и окном браузера.
