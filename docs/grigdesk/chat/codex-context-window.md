# Окно Codex 258 400 у модели «на 1M» = стандартное окно thread, большое включается конфигом

Симптом: кольцо контекста у модели Codex, которую объявляют миллионной, показывает
окно 258 400 и зовёт сжимать на ~207k. Выглядит как хардкод GrigDesk — его нет: GrigDesk
берёт `modelContextWindow` из `thread/tokenUsage/updated` (и `model_context_window` из
rollout) как есть, `model/list` app-server размер окна не отдаёт вовсе.

Окно выбирает сам Codex. В каталоге моделей (`~/.codex/models_cache.json`) у каждой
модели два поля: `context_window` — стандартное окно thread, `max_context_window` —
потолок, и `effective_context_window_percent` (95). Без настройки thread идёт со
стандартным окном: `272 000 × 95% = 258 400`. Большое окно — opt-in через config key
`model_context_window`; Codex сам режет значение до `max_context_window` модели и
применяет те же 95%.

Замер 03.10.2026, CLI 0.160.0, `codex exec -m <id> -c model_context_window=N`, окно из
`token_count` rollout:

| модель | N | окно в rollout |
|---|---|---|
| `gpt-6-astra` | не задан | 258 400 |
| `gpt-6-astra` | 1 000 000 | 828 400 (= 872 000 × 95%) |
| `gpt-6-astra` | 100 000 000 | 828 400 |
| `gpt-5.5` | 100 000 000 | 258 400 (у неё потолок 272 000) |

Следствия:

- «1M» у моделей этого поколения — это `max_context_window` 872 000 на вход, рабочее
  окно 828 400; ровно миллиона Codex не даёт.
- Завышенное `model_context_window` безопасно: модель с малым потолком остаётся на нём.
  Значит, правило «брать максимум» подхватывает новые модели без списка в GrigDesk.
- Пробные ходы короткие: работу бэкенда с реальным входом больше 272k и цену такого
  входа по подписке они не проверяли.
