# Где остаются пробелы в завершении реплик

Состояние проверено 14.10.2026 по текущим исходникам и изолированным проверкам.
Это описание оставшихся ограничений, а не сообщение об их исправлении.

## Завершение текста и завершение хода

`ChatInTurnReply.vue` показывает «Пишет…», когда `complete === false`, нет `abandoned`
и проекция считает запуск текущим. Надпись зависит от двух источников: завершения
конкретного блока и актуальности сведений о запуске в окне. Подробное правило —
[подпись реплики](in-turn-reply-label.md).

`settleRun()` закрывает черновики после возврата исполнителя. Эта страховка не определяет
границы отдельных ответов внутри продолжающегося хода.

## Неудачная сверка после восстановления связи

В `web/src/stores/chat.ts` обработчик `hello` запускает `_afterReconnect()`, который
вызывает `_loadActive()`. Если `GET /api/chat/active` отказывает, `_loadActive()` возвращается
без изменения состояния запуска и без сигнала для повторной попытки. Повтор прохода
предусмотрен при ещё одном `hello`, пришедшем во время прохода; отдельного повтора
из-за ошибки запроса нет.

Воспроизводимый случай: окно сохранило черновик и активный запуск, пропустило завершение,
после `hello` получило единственный временный отказ `/api/chat/active`. Даже после
восстановления API прежние `sending` и `complete: false` остаются. Второй явный проход
восстанавливает завершённый блок и снимает активность. Это общая для исполнителей
зависимость восстановления, а не особенность DeepSeek.

Один отказ чтения не доказывает обрыв ответа. Автоматически ставить `abandoned` или
`complete` по времени тишины нельзя: повторять можно чтение подтверждённого состояния.

## Два канала ответа DSH

DeepSeek и GLM используют `server/src/lib/deepseek/serverTurn.ts`. В закреплённых
исходниках DSH `AssistantStreamAttempt` публикует потоковые кадры `start/chunk/end`.
Перед `end` с исходом `committed` сохраняется `assistant/message` или `assistant/attempt`.
`start` содержит `attemptId`, `turn`, `step`; `end.outcome` — тип события и `seq`.
Это позволяет сопоставить живой блок с сохранённым результатом попытки.

Текущий адаптер GrigDesk:

- Для потокового текста использует `storageMessageId(attemptId + '-' + index)` и закрывает
  блок на `block-end`.
- Для `assistant/message` строит другой id из `turn/step`, всегда с индексом `0`.
  Обрабатывает текст лишь при `!reply`, то есть пока ни один ответ ещё не завершён.
- На `end` бросает оставшиеся черновики независимо от `outcome`; сохранённый полный
  ответ не восстанавливает пропущенный `block-end` исходного блока.
- `compactText()` складывает дельты, но при очередном текстовом `block-end` заменяет
  всю строку. Несколько текстовых блоков могут превратиться в один последний.
- Не учитывает `data.interrupted` в резервной обработке `assistant/message`: текст
  прерванного потока без собственного `block-end` может быть опубликован как полный.

Синтетическая подача событий через настоящий HTTP/WebSocket-адаптер воспроизводит эти
четыре ограничения: несовпадение идентичности, потерю второй сохранённой реплики,
потерю первого текстового блока и ложное завершение прерванного текста. Обычный поток
с `block-end` завершает исходный id; явно брошенная попытка остаётся брошенной.

Настоящий протокол первые три последовательности не даёт. Живые кадры и сохранённые
события идут одним упорядоченным сокетом `session/follow`. `assistant/message` пишется
внутри `settle()` до кадра `end` своей попытки, а обрыв сокета валит весь ход. Те же
сценарии живыми кадрами в форме upstream завершаются верно.

Достижим только четвёртый пункт — «Стоп» посреди текста. На отмену DSH сохраняет
`assistant/message` с `interrupted: true` и видимым префиксом без `block-end`. Адаптер
публикует этот обрывок полным блоком под id `<turn>-<step>-0`, а `end` следом бросает
живой блок с тем же текстом. Окно получает обрывок дважды: «готовым» и «Ответ оборван».

## Последние буквы ещё не означают конец протокола

DSH отдаёт `block-end` всех блоков ответа разом, только в конце ответа модели:

- DeepSeek — после маркера `[DONE]` (`packages/llm/llm-deepseek/src/translate.ts`);
- GLM — после конца потока в `@earendil-works/pi-ai`: провайдер `zai` идёт через
  `api/openai-completions.js`, где `finishBlock` всех блоков вызывается после цикла чтения.

Поэтому ответ «текст + вызов инструмента» держит текст открытым, пока модель пишет
аргументы инструмента, например содержимое длинного файла. Всё это время под готовым
текстом стоит «Пишет…», а строка хода активна. Сигнал конца текста в живом потоке есть:
первый кадр вызова — `block-start` с `blockType: 'tool-call'` (`agent.ts` публикует каждый
кадр через `live.push`). Адаптер GrigDesk на него сейчас не реагирует.

Чтобы различить задержку протокола, ошибку адаптера и устаревшее состояние окна,
нужна последовательность событий одной реплики через адаптер, журнал, SSE и проекцию.
Снимок с активной строкой хода не доказывает, что сервер уже закончил запуск.
