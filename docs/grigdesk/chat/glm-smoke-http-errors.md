# HTTP-ошибки в отчёте живой проверки GLM

`glmLiveSmoke.mts` сохраняет ошибки модельного HTTP-запроса в `modelErrors[]`:

```json
{
  "httpStatus": 429,
  "errorText": "{\"error\":{\"code\":\"1113\",\"message\":\"Insufficient balance or no resource package. Please recharge.\"}}"
}
```

Тело сохраняется целиком, без ограничения краткого `steps[].detail` в 400 символов
и runner-сообщений в 8192 символа. Из него удаляются известные секреты окружения,
адреса электронной почты, приватные пути и значения чувствительных JSON-полей.
Для сетевого исключения `httpStatus` равен `null`: HTTP-ответ в этом случае не выдумывается.

Наблюдатель `glmSmokeDiagnostics.mts` загружается отдельным временным плагином только
в процесс проверки. Он оборачивает исходный `fetch`, читает отказ через `Response.clone()`
и не меняет адрес, авторизацию или успешный SSE-поток. Для живого запуска наблюдаются
модельные запросы Z.ai; для offline — точный переданный loopback endpoint.
Переданный offline-сторож внешней сети загружается первым и сохраняет свой запрет.
Временный JSONL имеет права 0600; итоговый JSON повторно очищается секретами родителя.
Успешные ответы модели, prompt и заголовки запросов в диагностику не записываются.

Если первый ход не дал полноценного ответа модели, сценарий останавливается и отчёт
остаётся неуспешным. Оставшиеся шаги не расходуют квоту после уже установленного отказа.
При рабочем первом ответе сохраняется полный сценарий и потолок восемь ходов.
Это не ослабляет [условия допуска Coding Plan](glm-coding-plan-smoke.md).

Регрессии: `tests/server/glm-smoke-diagnostics.test.js` проверяет длинный HTTP-отказ,
маскирование ключа/почты/пути, неизменный исходный ответ, успешный SSE и отдельный сетевой
сбой. `tests/server/glm-live-binary.test.js` проверяет HTTP 429 / 1113 через настоящий ELF,
остановку после одного хода, полный зелёный сценарий на loopback и сохранение admission.
Они подтверждают диагностику и протокол, а не живую работоспособность подписки.
