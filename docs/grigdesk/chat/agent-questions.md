# Диалог: агент задаёт вопрос (AskUserQuestion)

- В headless-режиме сам инструмент отвечать некому: выполненный AskUserQuestion возвращает агенту
  пустое «User has answered your questions: .». Поэтому вопрос перехватывается на уровне
  permission-prompt-tool (он получает `tool_name: AskUserQuestion` с полным списком вариантов),
  а ОТВЕТ пользователя возвращается как `behavior: 'deny'` с текстом в `message` — единственный канал,
  по которому текст доезжает до агента дословно (проверено: агент читает его как результат
  инструмента и продолжает ход).
- Поток: SSE `chat-question {pid, chatKey, questions, at}` → `views/chat/ChatQuestion.vue` (варианты,
  мультивыбор, поле «свой ответ») → `POST /api/chat/permission/:pid {answers}` → сервер собирает текст
  («Ответ пользователя из GrigDesk: • Заголовок: Вариант»). Пропуск — пустые answers.
- Пока вопрос ждёт человека, [канал уточнений](in-turn-messages.md) этого запуска
  показывает `awaiting_answer` и не принимает текст композера как новый steer. После
  ответа канал открывается, если ход всё ещё активен. Это правило действует и для
  прямого моста Kimi/DeepSeek/Codex, и для MCP-вопроса Claude.
- **Возможности канала объявляет исполнитель, а не угадывает всплывашка.** У вопроса есть
  `multiSelect` и `allowFreeText`. Текущий серверный транспорт Kimi передаёт выбранные
  `option_ids` и свой текст через `question/respond`; DeepSeek передаёт ответы через
  `$events/result`. Прежний ACP-мост Kimi принимал только один `optionId`: его
  `question_degraded` и подсказка об ограничении остаются в legacy-коде, но не описывают
  текущий путь чата. Если конкретный канал не передаёт свой текст, ответ помечается
  `textDelivered: false` — тем же правилом, что и `commentDelivered` у отказа.
- Из-за этого AskUserQuestion попадает в `permission_denials` результата; в `claude.js` он исключён
  из списка «действия не были разрешены», иначе пустой ответ подменялся бы ложным предупреждением.
- `ExitPlanMode` остаётся обычным разрешением, но в всплывашке показывается как план
  (текст целиком, кнопки «Утвердить план» / «Доработать»).
- **Отказ — с пояснением**: «Отклонить»/«Доработать» открывает модалку с полем текста
  (`promptDialog` из `web/src/ui.ts`, поверхность — общий `UiDialogHost`; пустое — как раньше,
  Esc — отмена отказа).
  Пояснение едет в `POST /api/chat/permission/:pid` полем `comment`: у claude оно вкладывается
  в deny-message («Пользователь отправил план на доработку. Что изменить: …») — агент читает
  его прямо в ходе, как ответы на вопросы. **Доезжает ли текст — свойство КАНАЛА, а не
  вендора**: серверный Kimi передаёт feedback разрешения, прежний ACP-outcome Kimi текста
  не нёс. Для каждого транспорта это отдельное свойство. Поэтому ожидание помечается
  `acceptsComment` при создании, а ответ — `commentDelivered`. Если текст не доехал,
  фронт отправляет пояснение обычным сообщением в очередь чата. Запись плана в
  переписке дополняется строкой «**Пояснение:** …».
- **Всплывашка одна на всех, вендорных веток в ядре нет.** Ожидание помечается флагом
  `direct`: исполнитель ждёт ответа сам (серверный transport Kimi/DeepSeek, Codex MCP),
  без локального HTTP MCP-процесса, как у Claude. От флага зависит только ФОРМА ответа
  (`{allow, comment, remember, choice}` против MCP-JSON), поэтому новый прямой исполнитель
  ничего не добавляет ни в `modules/chat`, ни во фронт. Классификатор авто-режима — общий
  `autoDecision` (`lib/chat/autoApprove.ts`) по словарю ACP-действий `toolCall.kind`
  (`read`/`search`/`edit`/`execute`/`delete`); исполнитель обязан лишь назвать свой вызов
  одним из этих типов, а не заводить вторую политику рядом.
