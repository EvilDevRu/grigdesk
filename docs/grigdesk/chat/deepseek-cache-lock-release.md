# Ожидающий кэш переживает освобождение lock

При проверке занятого directory lock ожидающий процесс создаёт внутри `.reclaim`,
сверяет PID/starttime владельца и убирает claim, если тот жив. Владелец может
переименовать и удалить свой lock между последним `lstat` claim и его `rmdir`.
В этом случае `ENOENT` или `ENOTDIR` означает, что уборка уже выполнена владельцем:
ожидающий продолжает обычный захват. Остальные ошибки уборки сохраняют отказ.

Решение не позволяет снимать живой или недоступный lock. Проверки inode claim,
PID/starttime/token владельца, повторное чтение перед reclaim и ограниченное
ожидание остаются обязательными. Хэши готового поколения не связаны с этой гонкой
и проверяются независимо; `--verify` всегда выполняет полный контроль содержимого.

Регрессионный тест в `tests/deepseek/extract.test.mts` освобождает владельца ровно
между `lstat` и `rmdir` ожидающего. Следующий handle получает собственный token;
повторный release прежнего владельца не снимает новую запись.
