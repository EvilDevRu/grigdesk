# Установка CLI исполнителя в общем окне

Claude, Codex и Kimi объявляют установку в серверном адаптере через `installation(config)`.
При доступном внешнем npm установка и обновление всех трёх используют npm в пользовательском
каталоге с явным `--prefix`. Если npm не найден, сохраняются прежние команды:
native installer Claude, `npm i -g @openai/codex` для Codex и официальный `install.sh` Kimi;
обновление Claude/Codex вызывает настроенный бинарь, host Kimi повторяет installer.
Без npm первая установка Codex, как прежде, завершается `npm_missing`.
Подробности выбора — [приоритет npm](provider-install-npm.md).
Contained Kimi не предлагает обновление и сохраняет прежний runtime gate.
Повторная первая установка поверх установленного CLI запрещена.
Управляемая поставка DeepSeek/GLM этим механизмом не меняется.

## Подготовка, подтверждение и старт

Новый клиент сначала вызывает авторизованный
`POST /api/providers/:id/:operation/prepare` с пустым телом. Подготовка не запускает npm
и не пишет shell: она выбирает внешний runtime, каталог установки, цель bin и точный текст
будущих правок, затем возвращает `ProviderInstallPreparation` с непрозрачным token,
`expiresAt`, командой с выбранным prefix, `prefix`, `shellChanges[{file, action, block}]`,
`terminalSetup` и предупреждениями. ENV, argv и снимки целей остаются на сервере.
Token живёт 5 минут, привязан к серверу, авторизованной identity, исполнителю и операции;
на одну область хранится не больше восьми подготовок. GET `/api/providers` по-прежнему
не запускает shell- и npm-prefix probes.

Старт `POST /api/providers/:id/:operation/start` принимает ровно `{ preparationToken }`
или пустое `{}` для прежнего клиента. Любые другие имена полей отвергаются 400 до admission.
После допуска сервер заново проверяет установленность, identity внешних Node/npm, effective
prefix и снимки bin/rc. Изменение даёт 409 `preparation_changed` до первой записи; нужен новый
preview. Истёкший token — `preparation_expired`, чужой — `preparation_invalid`, повторный —
`preparation_consumed`. Занятость даёт `busy` и не тратит token. Прежний `{}` старт получает
исправленное npm-окружение, но не права менять shell rc или убирать legacy-ссылку: результат —
обычная установка с `terminal=needs_setup` либо `npm_bin_conflict` до npm.
Старый `POST /api/providers/:id/update` ждёт тот же сервис, возвращает прежний ответ
и не открывает нового обхода блокировки.

Одна операция занимает весь GrigDesk, включая другие вкладки. Сервер сохраняет running до
ответа 202, а окно можно закрыть без остановки процесса. `GET /api/providers/installations/current`
и событие общего SSE `provider-install` возвращают атомарный снимок с revision, активной
операцией и последними исходами. Первое чтение сохранённых итогов не пересобирает реестр;
один refresh нужен при завершении увиденной активной операции.

Скачивание и установка — одна честная фаза. Затем проверка версии, настройка терминала
и обновление списка моделей. Все фазы используют бегущую полосу без процентов. Вывод
объединён и ограничен 200 строками и 32 КиБ, публикуется пачками по 100 мс.

Успех требует нулевого кода команды и распознанной версии новой копии. До commit ошибки
сохраняют прежнюю привязку; после commit отказ настройки терминала сохраняет новую рабочую
привязку и даёт предупреждение, а не откат. Итоги: установлен, обновлён, уже последняя версия,
отказ или прервано. `migration` в job показывает смену пути копии при равной версии
(`outcome=current`). `terminal` показывает `ready`, `needs_setup` или `conflict` отдельно
от успеха CLI; у старых jobs поля нет, и это значит «не проверялось», а не «готово».
Сбой обновления моделей сохраняет успех с отдельным предупреждением.

Приватное состояние лежит в `provider-installs/state.json` папки данных; журнал миграции
bin-ссылки хранится там же и в публичный снимок не входит. Записи атомарны и синхронизируются
на диск. При следующем обращении после рестарта running становится interrupted, команда
не повторяется; прежняя привязка определяется фактическим `.env`. Чужой PID не завершается:
несовпавшая identity или повреждённое состояние блокируют новые старты. При остановке сервера
сервис прекращает admission и завершает только собственный worker.

Браузер подтверждает конкретный preview: в общем диалоге видны команда с выбранным каталогом,
каталог установки и одной строкой имена shell-файлов, куда допишется PATH. Текст управляемого
блока остаётся в DTO, но человеку не показывается: его устройство описано в
[настройке терминала](provider-install-shell-path.md). Отмена не отправляет
старт, token уходит только после согласия. Ответ другой машины отбрасывается по client scope.
После итога окно отдельно объясняет состояние терминала и показывает перенос копии.
Login-команда строится из абсолютного bin и `loginArgs`; Enter не отправляется.
Все собственные надписи есть на русском и английском.

Проверки: `providers-install-routes.test.js` (подготовка без эффектов, token, TTL, scope,
busy, revalidation, restart, деградация shell probe), `provider-install-contracts.test.js`
(стадии и строгие DTO), `providers-install-service.test.js` (commit/частичный исход),
`provider-install-legacy-bin.test.js` (миграция) и web-тесты окна/store. Настоящие пакеты
владельца и его rc в тестах не участвуют.
