# База знаний: как была устроена до переноса в docs/

История решения. Записи базы знаний о ней самой, сохранённые при переносе знаний в файлы `docs/`. Кода, о котором здесь речь, после снятия плагина в репозитории нет, а полный контракт плагина на момент снятия — `docs/grigdesk/guide/knowledge.md` — остался в истории git.

Базу сняли, потому что она держала знание о GrigDesk вне репозитория: свежий клон не получал ни записей, ни карт. Задачу «не грузить всё в контекст» решают оглавления со ссылками без `@`-импорта, а поиск — `rg` по `docs/`.

## Хранилище

По умолчанию SQLite-файл находится в
`~/.config/grigdesk/knowledge/knowledge.db`. Машинный override — только абсолютный путь
`GRIGDESK_KNOWLEDGE_DB_PATH` из корневого `.env`. Родительский каталог создаётся с режимом
0700, обычный файл — 0600; симлинк, каталог или иной не regular file отклоняются.
Файл создаётся лениво при первом разрешённом обращении и находится вне Git checkout.

Таблица `records` содержит UUID `id`, логические `project` и `repository`, `kind`, `title`,
полный `body`, серверное `updated_at` и целочисленную `revision`. Точные теги лежат в
`record_tags`, нормализованные title/tags/body — в FTS5. Используются
`journal_mode=DELETE`, `synchronous=FULL`, `foreign_keys=ON` и busy timeout. Изменение
записи, тегов и FTS-индекса выполняется одной `BEGIN IMMEDIATE` транзакцией.

При первой схеме один раз создаются три пробные записи размером 1–5 КБ. Marker в `meta`
не даёт удалённому sample воскреснуть при следующем открытии. Автоматического backup или
экспорта пока нет: этот один файл остаётся единственной копией и требует отдельной политики
резервирования.

## Поиск

И индекс, и запрос проходят один и тот же детерминированный конвейер: NFKC, нижний регистр,
`ё → е`, Unicode-разбиение на слова и русский Porter/RV stemmer. Поэтому запрос `деплой`
находит исходный текст со словом `деплоя`; латиница и числа сохраняются. Сырой ввод никогда
не попадает в SQLite `MATCH`, поэтому кавычки и операторы пользователя не становятся FTS-
синтаксисом.

Стеммер не является лемматизатором: он не связывает формы с беглой гласной (`сборка` и
`сборок`) и слова при смене части речи (`перезапустить` и `перезапуск`). Такие варианты
нужно указывать в тексте или тегах явно либо искать отдельными запросами.

Результаты ранжирует `bm25`: совпадение в title сильнее tags, а tags сильнее body;
одинаковый вес разрешается стабильным порядком. Краткий элемент содержит только
`{id,title,tags,fragment}`. Фрагмент вырезается из исходного body без HTML и служебных
стемов. Пустой запрос или отсутствие совпадений — успешный пустой результат `{items:[]}`;
отказ открытия — отдельная `knowledge_unavailable`, а не пустой список.

## HTTP, браузер и CAS

Общий auth guard закрывает все маршруты. `GET /api/knowledge` возвращает
`{items,facets:{projects,tags}}`, `GET /api/knowledge/search?q=...` — ранжированные краткие
`{items}`, `GET /api/knowledge/:id` — `{record}`. Human-only CRUD использует
`POST /api/knowledge`, `PUT /api/knowledge/:id` и `DELETE /api/knowledge/:id`.

PUT и DELETE обязаны передать `expectedRevision`. Успех возвращает authoritative revision;
stale-форма получает 409 `knowledge_conflict` и `currentRevision`. Браузер сохраняет
черновик, показывает ошибку и не повторяет мутацию. Неизвестная запись даёт `not_found`,
отказ хранилища — 503 `knowledge_unavailable` с безопасным reason без абсолютного пути.
Все ответы имеют `Cache-Control: no-store`.

Системный плагин `knowledge` включён по умолчанию. Его live gate проверяется на каждом HTTP-
и tool-вызове: выключение без рестарта даёт 404/tool `plugin_disabled`, но не закрывает и не
удаляет SQLite. Старый web-бандл игнорирует неизвестный page-only route, новый открывает
страницу `/knowledge`; записи при разнесённом rollout сохраняются.

## Инструмент чата

Server-owned `knowledge_search` имеет три действия: `search` с `query`, `repository`, `tags`, `limit`; `read` с `id`; `write` с полным `record`, а для изменения — также с `id` и свежей `revision`. Поля выбора проекта нет. Чат задачи навязывает trusted project из attempt ledger; UUID чужого проекта выглядит как `not_found`. Свободный чат может искать и читать глобально и изменять существующую запись в её проекте, но не создавать запись без trusted project. Delete исполнителю недоступен.

Search возвращает только краткую выдачу, read — полный record. Для write сервер задаёт происхождение; CAS защищает от перезаписи чужой правки. После сохранения точечно обновляются карты старой и новой темы, которые задаёт первый тег. Если карта не обновилась после сохранения, ответ явно содержит `maps_refresh_failed`, `committed: true`, id и новую revision.

Общий descriptor используется в Claude MCP, Codex MCP, Kimi ACP/MCP и Ollama toolbox. Nonce-authenticated UDS передаёт дочернему MCP список descriptors. Живой plugin gate проверяется broker-ом перед каждой операцией; изменение тумблера не требует менять descriptor. Абсолютные пути хранилища, ошибки SQLite и stack не проходят наружу.

Актуальные правила подтверждения write и межпроцессной синхронизации карт описаны в docs/grigdesk/guide/knowledge.md. Изменения серверного поведения вступают в силу после перезапуска GrigDesk.

## Офлайн CLI

Команда не использует сеть и не требует работающего Fastify:

```bash
knowledge search "очередь деплоя" --project <project> --repository <repo> --tag queue --limit 10
knowledge read <uuid>
knowledge write --project <project> --repository <repo> --kind факт --title "Заголовок" --body "Проверенный факт" --tag queue
knowledge write <uuid> --expected-revision <revision> --repository <repo> --kind факт --title "Заголовок" --body "Уточнённый факт" --tag queue
```

Код exit 0 означает найденную выдачу, прочитанную или записанную запись; код 1 — пустой поиск либо not_found; код 2 — конфликт ревизии, недоступность SQLite/runtime или ошибка карты. При ошибке карты после сохранения stderr явно содержит maps_refresh_failed, committed: true, id и новую revision. Код 64 означает ошибку аргументов. Delete, import и export в агентском CLI отсутствуют.

CLI разрешает собственный симлинк, находит корень по реальному файлу и читает корневой .env, поэтому работает из worktree внешней задачи. Существующую БД search/read открывают read-only; write подчиняется файловым правам процесса. Первый тег задаёт безопасную тему карты. Чужая ревизия не перезаписывается.

GrigDesk при старте добавляет bin своей установки в PATH дочерних агентов и передаёт этот PATH transient-прогонам конвейера. Launcher-ы также добавляют пользовательские каталоги CLI. Симлинк ~/.local/bin/knowledge, который создаёт установщик, остаётся удобством для обычного shell; агентский запуск от него не зависит. Изменение окружения уже работающего сервера требует его ручного перезапуска.

Источник: docs/grigdesk/guide/knowledge.md § Поиск и CLI
