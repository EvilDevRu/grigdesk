# Узлы маршрута обязаны ходить в общий runtime под ОДНИМ uid

Симптом: профильная проверка уже выполнила полезную работу, но падает при записи или выводе
итога с ошибкой доступа к детерминированному временному файлу:

```text
write-cache: /tmp/<cache-key>: Permission denied
```

При `fs.protected_regular = 2` перезапись файла чужого владельца в sticky-каталоге запрещена
даже root'у. Если одна команда запускается с явно заданным пользователем контейнера, а другая —
с пользователем по умолчанию, первая создавшая кэш становится его владельцем, а следующая получает
`Permission denied`. Полезная проверка может уже закончиться, но ненулевой код вывода всё равно
останавливает маршрут.

Лечение — один профильный helper запуска и единая настройка пользователя для **всех** обращений
к общему runtime. Разовую очистку конфликтующего кэша описывает локальный runbook профиля:
общий движок не должен знать ни расширение артефакта, ни команду конкретного стека. Та же ловушка
касается любых кэшей и логов, в которые по очереди пишут процессы с разными uid.
