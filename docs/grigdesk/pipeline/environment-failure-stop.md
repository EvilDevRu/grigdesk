# Отказ среды не повторяется: узел останавливается после первого failed/environment

Агент, сдавший вердикт `failed` с владельцем `environment`, заявил доказуемый факт:
этап блокирует среда, а не продукт. Тот же исполнитель в той же среде на повторе
даст тот же отказ, поэтому доверенный рантайм **не тратит `productFailure`-бюджет**
на такой вердикт и останавливает узел сразу. Решение уходит человеку штатной
остановкой `human` с исходом `failed`; продолжение идёт только через «перейти сюда»
(`route_v2_failed_stop_held` удерживает resume без goto).

## Почему это не «сбой исполнителя», а контракт

Стена, об которую сгорают заходы, — детерминированная. Замер по живым прогонам
(07.11.2026, задача SHIP, раннер codex): песочница codex в `workspace-write`
защищает `.git` от записи, а git-каталог linked worktree (`<main>/.git/worktrees/<имя>`,
где лежит `index.lock`) находится в основном checkout — вне рабочей области. Агент
пять заходов подряд честно отдавал `failed/environment` («git add: Read-only file
system»), каждый заход — полный контекст xhigh; ни один повтор ничего не вылечил.
Та же формулировка отказов — в t100000000007 и t100000000008 (04.11.2026),
t93037 и t100000000001 (28–31.10.2026).

Доставить этап при этом исполнитель **может** — успешные прогоны (t100000000009,
t9536, t100000000003) проходили ту же стену обходом: копия/клон репозитория в
записываемой области (`/tmp`), коммит и пуш оттуда. Поэтому движок сознательно не
запрещает «проблемные» пары «этап × исполнитель» до запуска: умеет ли агент
доставить в конкретной среде — решает он сам на живом этапе, а не булев факт в
каталоге раннеров. Прямая запись в gitdir linked worktree невозможна для codex
в `workspace-write` всегда; kimi (без файловой границы) и claude (native sandbox
снят) пишут git напрямую и на эту стену не нарываются.

## Что именно делает рантайм

`route-runtime.sh` в цикле повторов узла, перед тратой `productFailure`, читает
владельца вердикта (`run_state_verdict_owner`; legacy `failed` без typed verdict
даёт пустого владельца и живёт по прежним правилам). Для `environment`:

1. цикл прерывается: исход `failed`, вердикт сохраняется как есть, бюджет не
   списывается;
2. комментарий узла (`<RUN_KEY>_COMMENT`) перезаписывается по образцу отказа
   сторожа доказательств: машинная причина + ` · отчёт агента: <дословный отчёт>`;
3. журнал этапов получает строку с причиной;
4. суффикс строки остановки (`route_v2_stop_line_suffix`) печатает машинную часть
   причины для failed-остановок с комментарием «отказ среды: …» — отчёт агента в
   строку не едет, он остаётся в комментарии узла.

Текст машинной причины: «отказ среды: повтор с тем же исполнителем обречён — среду
этапа агент исправить не может; смени исполнителя узла или исправь среду, затем
вернись «перейти сюда»». Карточка остановки GrigDesk разбирает её правилом
`human — отказ среды…` (`server/src/lib/stall.ts`): заголовок «отказ среды
исполнителя», подсказка называет смену исполнителя (вкладка «Исполнители») и
возврат goto. Арбитру остановка не отдаётся — `stop=human`, вердикта у неё нет.

Границы правила: отказ сторожа доказательств (`evidence-rejected`) проверяется
раньше и сохраняет свой один повтор; повторы продуктовых `failed` с другими
владельцами (`build`, `tests`, `plan`, `human`) работают как прежде; исчерпание
no-result-бюджета не зависит от этого правила.
