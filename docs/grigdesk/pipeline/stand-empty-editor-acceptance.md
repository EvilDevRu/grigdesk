# Изолированный стенд пуст: приёмка редактора упирается в отсутствие данных

Стенд задачи собирает окружение с нуля (`stand-server.mjs` берёт список путей из
`isolatedEnv` в `tests/server/helpers/pluginBootFixture.js` того же worktree): свои
`FACTORY_STATE_DIR`, `FACTORY_PROFILES_DIR`, `GRIGDESK_ROUTES_DIR`, `GRIGDESK_PREFS_PATH`
и остальные каталоги внутри папки стенда. Профили владельца, его проекты и попытки туда
не попадают — это изоляция, а не поломка.

## Симптом

Браузерная приёмка редакторных функций (форма запуска, настройки исполнителя этапа,
настройки попытки) останавливается с честным «не проверить»:

- форма создания задачи: «Нет проектов с доступным конвейером»;
- `GET /api/projects` и `GET /api/tasks` отвечают пустыми списками;
- `launch-options` отвечает HTTP 400 `bad_profile`, «запрошенный профиль конвейера
  не установлен», `profiles:[]`.

Вход при этом работает, порты отвечают — препятствие не в транспорте и не в коде
задачи. Фикстурные проверки тех же сценариев остаются зелёными, но живое
доказательство они не заменяют.

## Что с этим делать

- Живая приёмка требует посева стенда: профиль в `profiles/` папки стенда, проект
  с этим профилем, опубликованный маршрут и попытка прогона. Посев делает профиль
  или человек в своей среде; указывать каталоги стенда на живые данные владельца
  нельзя — это ломает изоляцию и смешивает данные.
- Если посев не предусмотрен, приёмка честно останавливается, а решение принимает
  человек: принять работу по собранным доказательствам (фикстуры, статика, аудит)
  с открытой находкой о среде либо проверить вручную в отдельном окне.
- Находку о среде не закрывать повтором: без посева повтор даёт тот же отказ.

Связанное: [данные фабрики](factory-data.md),
[границы выбора исполнителя](runner-selection-boundaries.md).

## Повторяемый тестовый посев

Для проверки запуска есть явный помощник
`tests/server/helpers/pipelineStandSeed.mjs`. Его вызывают для уже выделенного root
изолированного стенда; основной каталог данных и профили владельца не передаются.

```bash
node tests/server/helpers/pipelineStandSeed.mjs \
  --root "$STAND_ROOT" --fe-port "$STAND_FE_PORT" --api-port "$STAND_API_PORT" \
  --systemd-runtime "$XDG_RUNTIME_DIR"
```

Помощник создаёт синтетический профиль `launch-retry-demo`, собственный Git-репозиторий,
опубликованный маршрут `retry-check` и фикстурную npm-копию Kimi внутри HOME стенда.
У маршрута отключена публикация, bootstrap пропускается, первый узел — ворота:
успешная подготовка не вызывает модель. Фикстурный CLI отвечает только на `--version`;
остальные команды завершаются отказом. Настоящие install/login и доступы поставщика
для этого сценария не требуются.

Повторный посев сохраняет hash каталога, исходный `.env` и существующие startup-файлы
Bash. Профиль без собственного маркера не перезаписывается. Порты передаются явно;
проект появляется в штатном списке из установленного профиля.

Базовое `isolatedEnv` объявляет `SHELL=/bin/bash`: без него descriptor не дойдёт до
инвентаризации копии и вернёт `shell_unsupported`. Для настоящей регистрации transient
юнита опция `--systemd-runtime` добавляет `XDG_RUNTIME_DIR` в собственный `.env` стенда.
Применение новой среды требует перезапуска только сервера стенда **до** начала сценария;
между отказом CLI и повтором процесс сервера должен оставаться тем же.

Состояние копии переключается тем же помощником:

```bash
node tests/server/helpers/pipelineStandSeed.mjs --root "$STAND_ROOT" --cli broken
node tests/server/helpers/pipelineStandSeed.mjs --root "$STAND_ROOT" --cli ready
```

`broken` отвязывает исполняемый bin от declared entry npm-пакета, сохраняя его точный
путь для диагностики. После 500 проверяются отсутствие реестра, control-каталога задачи
и резервации. `ready` восстанавливает ссылку: повтор той же тестовой задачи должен
передать запуск движку без рестарта сервера. Для проверки окна до trusted identity
можно временно создать `$STAND_ROOT/pipeline-fixture/hold-probe`: probe CLI ждёт удаления файла,
первый launch отвечает `started`, а следующий — 409 `run_exists`. Затем файл удаляют
и проверяют появление trusted attempt. Ворота тестового маршрута не принимают.

Перед новой пробой другим task id прежнюю фикстурную попытку закрывают штатным
`POST /api/tasks/:id/close`. Ожидание на воротах удерживает shared-аренду стенда и
репозитория; следующая задача иначе завершится кодом 73 до создания attempt. Такой
отказ уже переданного запуска сохраняет pending по действующему контракту и не является
повторным отказом подготовки CLI.
После появления attempt оркестратор ещё может работать: перед `close` ждут фактической
остановки на воротах (`daemonAlive=false`), иначе API вернёт 409 `running`.

Стенд и файловые права проверяющего — разные условия. Для Codex с `state-only`
запрет escalation остаётся в силе. При явном разрешении владельца профиль может
использовать парные `profile_agent_control_start` / `profile_agent_control_stop`, чтобы
добавить проверяющему точные каталоги в `RUNNER_CODEX_ADD_DIRS` перед запуском provider.
Помощник `--root "$STAND_ROOT" --write-roots` только читает маркер и возвращает bin
фикстурной копии и `pipeline-fixture`. Он проверяет владельца/mode маркера и canonical
пути без symlink; весь root, HOME, `.env` и ключи не выдаются на запись. Ограничение
hook по task и run key принадлежит локальному профилю; добавлять эти права всем узлам
или пытаться получить escalation из уже запущенного `state-only` агента не требуется.

После выдачи путей нужен новый запуск BROWSER: права существующего provider-процесса
не меняются. PID/starttime сервера проверяют по собственному `state/server.lock` стенда,
а не по `/proc` хоста: namespace проверяющего скрывает внешние процессы, но не marker
старта, записанный сервером.

Серверный журнал проверяют при включённом уровне диагностики «Ошибки» или выше.
При выключенной диагностике logger имеет уровень `silent`; отсутствие записи в этом
режиме не доказывает потерю причины в обработчике.

Проверки помощника: `tests/server/pipeline-stand-seed.test.js` — повторяемость,
реальная npm identity до/после ремонта, сохранение настроек и отказ перезаписи чужого профиля.
