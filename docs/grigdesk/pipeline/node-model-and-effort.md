# Модель и effort в окне этапа

Вкладка «Исполнители» сразу сохраняет связку исполнитель, модель и effort при выборе
строки или изменении поля. Отдельной кнопки «Применить» нет; окно остаётся открытым.
Выбор действует для следующего запуска этого узла текущей попытки конвейера.
Настройка не меняет профиль, соседние узлы, другие задачи и новые попытки конвейера.
Правило области и двух режимов закреплено в [решении о настройках этапа](stage-runner-settings-scope.md).

Работающий этап разделяет сохранение будущего и перезапуск:

- Автоматическое сохранение оставляет текущий процесс с его прежними параметрами.
- «Перезапустить с этими параметрами» после предупреждения останавливает точный текущий
  запуск и создаёт новый run с большей epoch, в том числе при изменении только effort.

У модели и effort есть независимое значение «Из профиля». Null хранит наследование,
поэтому последующее изменение политики влияет на следующий запуск. Пустой effort —
отдельный явный выбор отсутствия флага, разрешённый только metadata конкретной модели.
Неподходящий второй параметр не сбрасывается автоматически: редактор объясняет конфликт.
Новый исполнитель начинает с наследования собственных параметров.
Клик по исполнителю сначала читает его каталог и затем сохраняет целую связку.
С первого ожидания каталог и запись принадлежат захваченному узлу, а не открытию окна:
закрытие диалога и переход к другому узлу не отменяют сохранение. Повторное открытие
подхватывает выбранного исполнителя, параметры и ожидание без дублирования запроса.
Новый клик по исполнителю до отправки POST заменяет прежний выбор; после отправки
действия этого узла заблокированы до ответа. Отказ после закрытия окна показывается
общим диалогом с исходной задачей и этапом, а не теряется вместе с модалкой.
Несовместимая пара остаётся несохранённой до исправления второго поля. Отказ записи
показывает явный повтор сохранения; повтор discovery завершает ожидающий выбор.
Во время загрузки и после отказа discovery прежний каталог не используется: поля
и применение заблокированы до успешного повтора для выбранного исполнителя.
Подтверждённая локальная пара при этом остаётся видимой, включая значения, которых
уже нет в каталоге: такие пункты доступны только для просмотра.

Подтверждённые настройки видны в полях; работающий этап дополнительно показывает короткую
сводку следующего запуска под списком. Инструкции и общая плашка черновика не занимают
место над списком, ошибки и несовместимая пара показываются явно. Источник поля доступен
в подсказке к его подписи. История использует собственные model/effort из meta.env; явный
пустой EFFORT отображается как «Не задано», legacy без этого поля сохраняет fallback.
Перечитывание графа и единый SSE не заменяют черновик. Повторное открытие и обновление
страницы читают подтверждённое из API.
Смена run/epoch, состояния процесса или завершение применения перечитывают options,
не заменяя черновик. Поэтому следующее действие после перезапуска использует собственный
новый actual; обычное обновление токенов не запускает metadata discovery.
Legacy записи без epoch считаются старше новых запусков и не вытесняют их из
последних двадцати записей истории. Наблюдение за actual предпочитает запуск с epoch.

## API и authority

Ленивый `GET /api/tasks/:id/runner/options` принимает exact profile/attempt/node/stage.
Без provider сервер читает `show` сохранённого исполнителя из authority узла; это чтение
не требует доступности его каталога и coverage. Окно восстанавливает confirmed/draft,
затем обязательно запрашивает строгие options с явным provider. Только второй ответ
разрешает редактирование и применение; базовый исполнитель графа не подменяет сохранённый.
`POST /api/tasks/:id/runner/settings` принимает целую selection и mode `next|restart`,
expectedRevision, expectedRun `{id, epoch}` либо null, catalogRevision и requestId.
Общий строгий DTO находится в `shared/pipeline/stageRunnerSettings.ts`.
Options содержит selection, sources, effective, inherited, chain, models, actual и receipt.
Inherited — живая базовая пара выбранного исполнителя, actual — собственные параметры
точного текущего запуска. Эти данные не добавляются в общий graph loader.
Граф без CLI и discovery читает только подтверждённую selection точного узла из
`runner-settings/<node>.json`: собственная цепочка, модель и effort перекрывают политику
профиля уже до первого запуска. Identity, revision, права и обычный файл проверяются
перед проекцией. Факт уже состоявшегося запуска и его история сохраняют приоритет
в подписи узла; настройка следующего запуска отдельно видна в окне этапа.

Сервер проверяет capability `stage-runner-settings-v1` именно в закреплённом движке.
Старая или неподтверждённая поставка показывает недоступность редактора с повтором;
чтение истории и прежние команды остаются доступны. Подмены движком текущего сервера нет.
Мутация выполняется только через `factory TASK runner settings apply`, с отдельными
argv profile/attempt/node/stage и JSON payload. Оба API закрыты общим auth guard.

Authority — `runner-settings/<node>.json` внутри trusted attempt directory: каталог 0700,
owned regular-файл 0600 без symlink/hardlink. Commit использует pipeline lock, затем
task-directory lock, CAS identity/revision/run и durable replace с fsync. До commit ошибка
не меняет ни одного поля и не останавливает процесс. Повтор requestId с тем же payload
возвращает receipt; другой payload либо прежний запрос после новой записи конфликтуют.

Restart intent хранится атомарно с selection и замороженной парой запуска. Стабильный
черновик lifecycle-события сохраняется до его публикации, сигнал идёт только после неё.
Однократный consume предшествует новому запуску. Ошибка после accept сохраняет целую
selection и отдельный receipt с причиной: сохранение и успешный перезапуск различаются.
Остановка использует trusted process identity, никогда PID из диагностического meta.env.
Отказ resolver/coverage до launcher завершает receipt с причиной по итогу всей цепочки;
успешный резерв учитывается как успешный исход. Запоздалый отказ остановки меняет только
pending receipt и не понижает уже consumed/started. При таймауте с любой диагностикой
в stderr сервер проверяет receipt по типизированному признаку timedOut, а не тексту ошибки.

## Каталог и путь запуска

Необязательный callback раннера `model_options` возвращает schema 1 и per-model
`id`, `label`, `efforts`, `aliases`. Canonical id непрозрачен, включая JSON modelRef.
Метаданные читаются без model call и без записи models.json чата. Codex пересекает native
model/list с каталогом раннера; Claude использует возможности конкретной модели своего CLI;
Kimi — каталог и принимаемые раннером уровни; DeepSeek — пересечение Factory и native
metadata; GLM — Factory-каталог и допуск выбранного режима DSH.

Сервер и движок проверяют выбранную пару. Каталог и политика входят в revision; устаревший
снимок даёт конфликт без подбора замены. При 409 окно сохраняет черновик и перечитывает
options; при недоступности каталога есть явный повтор. Launcher снова проверяет доступность,
а admission сверяет снимок под тем же lock, что и создание run. Конфликт перечитывает всю
цепочку, максимум три раза. Резерв получает свою политику, не параметры основного.
Явный локальный primary сохраняет семантику назначения человеком: только он обходит
предохранитель, основанный на прошлом лимите. Отказ самого запуска по-прежнему может
перевести этап к разрешённому резерву; наследование primary сохраняет профильный допуск.

Проверки: prepared `stage-runner-settings` contract/integration, `stage-runner-restart`,
серверные `factory-stage-runner-settings`, `factory-stage-runner-models`, UI
`pipeline-runner-override`, `pipeline-stage-isolation` и проверки display/упаковки.
Браузерная приёмка выполняется отдельно на стенде задачи после BUILD.
