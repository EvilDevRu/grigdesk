# Маршрут встал «код 78» на узле, который отработал = вердикт command-узла не по контракту

Симптом: конвейер стоит, в `t<TASK>.pipeline` узел числится `running`, `ORCH_PID` пуст,
`STALLED_HUMAN=1`. Нажатие «продолжить» в UI не двигает ничего — в журнале появляется ещё одна
пара строк и всё:

```text
route: узел <имя_узла>: подготовка к исполнению
route: dispatcher остановлен fail-closed (код 78)
```

Причина: `executor=command` исполняется хостом, а его JSON-вердикт движок разбирает уже ПОСЛЕ
работы скрипта. Скрипт успел записать свои артефакты, но форма вердикта не по контракту
(`docs/engine/PROFILE-CONTRACT.md`, раздел про `executor=command`) — парсер
`_route_v2_command_result` отвечает кодом 78, узел не коммитится. Отказ детерминированный:
`resume` упирается в то же место, пока не исправлен скрипт профиля.

Чем отличить от «агент не отчитался»: `t<TASK>.route-v2.log` **пуст** (модель не звалась вовсе),
а артефакты узла на диске свежие, с временем последней попытки. Проверить форму вердикта
напрямую, не гоняя маршрут:

```bash
source engine/lib/route-runtime.sh; _route_v2_command_result /путь/к/result.json; echo $?
```

Реальный случай — маршрут с кворумом нескольких мнений: выпал один провайдер из трёх, кворум
собрался, агрегирующий command-узел посчитал ранги и записал сводки — но вернул `done` с
информационным `findings` про отсутствующего участника. Движок принимает `findings` только при
`failed`, поэтому недоступность **одного** исполнителя останавливала весь конвейер. Там же
пряталась вторая мина: при двух выпавших вердикт `failed` нёс два finding с одинаковым `id` —
движок отвергает и дубли тоже.

### Третья серия: ANSI из вывода инструмента в `summary` — вердикт отвергнут целиком

`_route_v2_command_result` запрещает в `comment` и в каждом `summary` любой символ с кодом < 32
и 127. Профильный `compact()` схлопывал вывод через `" ".join(value.split())` — а `split()` знает
только пробельные символы. Playwright рисует прогресс курсорными последовательностями
`ESC[1A ESC[2K`, они доезжали до finding целиком и валили ВЕСЬ вердикт: узел отработал, честно
собрал два замечания (`verify-unit-tests-failed`, `verify-browser-tests-failed`), а маршрут встал
кодом 78, будто скрипт сломан. Инструмент без cursor-последовательностей не проявлял проблему.

Теперь `compact()` вырезает ANSI-последовательности целиком (голое удаление `ESC` оставило бы
мусор `[1A[2K`) и заменяет остальные control-символы пробелом. Правило для любого профильного
скрипта: всё, что уходит в вердикт, обязано пройти такую чистку — вывод чужого инструмента
контролю не поддаётся.

### Причина отказа больше не теряется: отвергнутый вердикт сохраняется файлом

Раньше разбор этого отказа был археологией: вердикт лежал во временном `result_file`, который
`_route_v2_run_command_node` удаляет на каждой ветке `return 78`, stderr хука пуст (скрипт-то
отработал), а в журнал уходила одна строка «dispatcher остановлен fail-closed (код 78)».
Теперь перед удалением копия уезжает в `t<TASK>.command-verdict-rejected.json`, а в
`t<TASK>.route-v2.log` пишется, чем именно вердикт не понравился — форма JSON, `comment` не
декодировался, не прошла `run_state_verdict_validate` или не снялся workspace-снимок «после».
Файл перезаписывается следующим отказом той же задачи, смотреть его надо сразу.
