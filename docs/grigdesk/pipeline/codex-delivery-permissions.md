# Codex на SHIP: native Auto-review и границы сдачи

`engine/lib/runners/codex.sh` запускает этап через `codex exec`, отдельно от
чатового app-server. По умолчанию `RUNNER_CODEX_SANDBOX` равен `workspace-write`.
Параметр `stage` не определяет разрешения. При точном сочетании route policy
`workspace-write` и native sandbox `workspace-write` раннер передаёт
`--approve-for-me`, который выбирает workspace-write и native reviewer.
Конфликтующий `--sandbox` в этой ветке не передаётся. Сеть, model/effort,
автосжатие, stdin, output, timeout и дополнительные корни сохраняются.

Стандартная песочница Codex защищает `.git` от записи, включая Git-каталог по указателю
linked worktree. Защита мешает не только `git commit`, но и `git add`, записи объектов,
ссылок, индекса и служебных файлов при `fetch`/`merge`.
Источник — [официальная документация OpenAI](https://learn.chatgpt.com/docs/agent-approvals-security#protected-paths-in-writable-roots).

Движок при этом требует от канонического `SHIP` политику маршрута `workspace-write`,
класс `delivery` и контекст `delivery` (`engine/lib/route_model.py`). В образце профиля
`server/seed/pipeline-sample/profile/routes/prompts/ship.md` поручает агенту вызвать
`deliver.py`; скрипт делает `git add`, `git commit`, а при стратегии `merge` — локальный
`fetch` и `merge --ff-only`. Он выполняется как команда агента и наследует песочницу.
Разрешение действия в delivery-контексте само по себе не открывает файловую запись.

Запись Git требует запроса разрешения, который теперь может решить native reviewer.
Одобрение конкретного действия не гарантируется. Правка только чатового адаптера
не меняет этот отдельный запуск.
Подтверждение конкретного отказа живой попытки требует её ошибки и эффективной
конфигурации; сборка argv доказывает политику запуска, а не исход всех прогонов.

## Файловый отказ и запрос native Auto-review

Отказ `Read-only file system` при записи Git-индекса сам по себе не означает отказ
Auto-review. В разрешённом delivery-контексте с принятой приёмкой SHIP сначала
запрашивает `sandbox_permissions=require_escalated` для конкретных поимённых `git add`,
`git commit` и доверенного скрипта публикации. Без такого запроса включённый reviewer
может вообще не участвовать в решении. Повтор той же команды без изменения прав
не исправляет файловую границу.

Отключение всей песочницы, обход deny-правил, прямые запрещённые push/gh и изменение
целевой ветки этим не разрешаются. Restricted shared no-ship, `state-only` и `never`
сохраняют свои ограничения. При фактическом отказе/ошибке reviewer или недоступности
штатного запроса применяют разрешённый резервный сценарий; в отчёте сохраняют действие,
статус и точную причину. Отклонённое действие не повторяют под другой формой команды.

Живая проверка 12.11.2026 на CLI 0.167.1 подтвердила поимённый add и commit в linked
worktree, затем push и создание открытого PR через доверенный скрипт с адресными native
запросами. Первый заход того же SHIP остановился без единого запроса reviewer:
старый промпт сразу предписывал клон и передачу человеку. Это подтверждение конкретной
публикации, а не обещание одобрения всех команд или автоматического UI-вопроса.

Исправленный промпт опубликован для новых попыток. Существующая попытка сохраняет свой
bundle: её продолжают штатным возвратом только на SHIP с явным новым указанием, сохраняя
принятую приёмку. Публикация каталога и перепривязка engine runtime сами промпт не заменяют.

Живая статистика (28.10–07.11.2026): прямая запись в gitdir linked worktree не
удаётся codex ни в одном прогоне (`git add`: Read-only file system на `index.lock`
в основном checkout), при этом доставки codex доезжают — агент находит обход
(копия/клон репозитория в записываемой области, коммит и пуш оттуда). Когда агент
обход не находит, он честно сдаёт `failed/environment`. Такой вердикт повторами
не лечится: тот же исполнитель в той же среде даст тот же отказ, поэтому движок
не тратит на него `productFailure`-бюджет и останавливает узел сразу —
[контракт останова по отказу среды](environment-failure-stop.md). Запрещать
«этап × исполнитель» до запуска движок не вправе: доставляет ли агент в своей
среде, решает он сам на живом этапе.

## Дополнительные корни и намеренные запреты

`engine/lib/core.sh` передаёт `STATE_DIR` и `PROFILE_AGENT_DIRS` в
`RUNNER_CODEX_ADD_DIRS`; раннер выдаёт каждый существующий каталог через `--add-dir`.
Каталог состояния уже разрешается отдельно, но это не снимает защиту `.git`.
Серверные инструменты SSH/БД не участвуют в локальной сдаче.

При `RUNNER_CODEX_RESTRICT_SHARED_STAND=1` действует отдельная политика no-ship:
`.git` явно смонтирован как read-only, `approval_policy="never"`, а командный hook
запрещает `git worktree/commit/push`. Такой намеренный запрет нельзя смешивать с
дефектом прав разрешённого этапа сдачи или снимать общей настройкой всех этапов.

Проверяющие `state-only` явно получают `approval_policy="never"`, сохраняя прежние
roots и host guard: новой физической read-only песочницы исходников эта правка не
создаёт. `transactional-write`, неизвестная/отсутствующая route policy и другой
explicit sandbox сохраняют прежний запуск без нового Auto-review.

Протокольный отказ отдельного действия не становится provider failure по слову
denied. Разрешённая альтернатива может закончить этап обычным stage-result done;
семантический failed/human не переключает исполнителя. Терминальный sandbox_denied
остаётся остановкой у человека без failover. Код 0 без stage-result не означает done.

У CLI есть штатный `--approve-for-me` для автоматической проверки запросов разрешения
с сохранением песочницы. Его границы и отличие от подтверждений человеком описаны в
[контракте штатных разрешений Codex](../chat/codex-native-approvals.md).
Матрица argv и сохранность restricted-ветки проверяются offline. Живые Git/SHIP
операции и авторизация GitHub/B24 этими проверками не доказаны. Выбор исполнителя
настоящих профилей не меняется автоматически.

## Контракт доставки решает, чем заканчивается клон-обход

Временный клон завершает доставку целиком только там, где она заканчивается push на
origin: клон коммитит и пушит, защищённый локальный `.git` не нужен (живой случай другого
профиля: публикация 33 файлов двумя PR из свежих клонов target SHA). Там, где контракт —
локальная перемотка `dev` основного checkout без push/PR, клон внутри песочницы доставку
завершить не может: запись общего `.git` и рабочих файлов основного checkout недостижима
при любом обходе. Один и тот же обход в одном профиле закрывает узел, в другом — только
готовит публикацию.

## Стратегия клона закреплена в промпте узла публикации (07.11.2026)

Узел с локальной перемоткой `dev` упал `failed/environment`: агент обход не нашёл, бюджет
повторов движок не тратил (контракт останова по отказу среды). После этого стратегия
закреплена в промпте узла публикации профиля, а не оставлена самостоятельному поиску
агента:

- отказ записи `.git` запрещает повтор той же команды и немедленную сдачу: агент собирает
  commit во временном клоне — поимённый перенос по `status --porcelain`, те же правила
  сообщений и запреты, побайтная сверка перенесённых файлов, `diff --check`;
- `merge dev` в клоне не делается: его выполняет штатный скрипт перемотки в worktree после
  переноса commit;
- человек получает bundle и ровно три команды: `fetch` bundle в worktree, `merge --ff-only
  FETCH_HEAD`, штатный скрипт перемотки;
- вердикт — `failed` с владельцем `human` («доставка собрана в клоне, перемотка `dev`
  требует записи вне песочницы»); публикация частичным успехом не объявляется.

Прямая ветка (исполнитель без файловой песочницы) остаётся основной: ветка клона
включается фактом отказа записи `.git`, а не именем исполнителя, и ничего не меняет для
него. Проверка `factory-check --quick` профиля после правки промпта зелёная.
