# Конкретная ошибка провайдера доходит до карточки остановки

Остановка по исчерпанию повторов раньше получала только класс последнего запуска.
Если адаптер возвращал `unknown`, исходное сообщение оставалось в `events.jsonl`,
а человек видел «заходы без результата, последний — unknown» и общую подсказку
про таймаут. Такое случалось, в частности, при перегрузке модели.

## Распознавание и политика

Классификатор Codex не привязан к одному номеру CLI. `CLI_VERSION` сохраняется
в metadata; смысл отказа определяется по структурированным событиям `error`,
`turn.failed` и `usage_limit_reached`. Вывод команд и сообщения агента не являются
ошибками провайдера. Продолжение хода или новой сессии снимает прежний отказ.
Непроверенный источник, повреждённый поток и неизвестная сигнатура дают `unknown`.

Общий разбор — `server/src/lib/runnerFailure.ts`; движок вызывает его через
`engine/lib/codex-failure.mjs`. Чтение классификатора ограничено64MiB, без symlink/FIFO.
Перегрузка и обычный rate limit классифицируются как `transient`: они не разрешают
автоматическую смену провайдера и не включают breaker квоты. Прежние правила
`limited`, `denied`, `context_overflow`, кодов0/124 и auth до работы сохранены.
Неизвестные события не доказывают отсутствие работы для переключения после auth.

## Новые запуски

`runtime-usage.mjs prepare` извлекает сообщение из уже проверенного retained FD
вместе с нормализацией расхода. Финальный diagnostic mirror `meta.env` получает
`FAILURE_CODE`, `FAILURE_MESSAGE`, `FAILURE_DETAIL`. Они не меняют управляющий
`RESULT_CLASS`, immutable usage schema, вердикт этапа или политику повторов.
Таймаут, успешный запуск и ручное переключение не наследуют прежнюю ошибку.
У GLM этапа источник — последнее событие `wrapper_error` host-wrapper-а
(`inspectGlmFactoryFailure`); класс при этом остаётся `unknown`, см. [GLM.md](../../engine/GLM.md).
Карточка остановки читает этот mirror для Codex и GLM. Источник отказа объявлен
в общем `RUNNER_FAILURE_READERS` для всех пяти исполнителей:

| Исполнитель | Источник и признаки |
|---|---|
| Claude | `events.jsonl`: отказ `rate_limit_event`, synthetic-реплика CLI, ошибочный `result` или `error` |
| Codex | `events.jsonl`: `error`, `turn.failed`, `usage_limit_reached` |
| DeepSeek | `events.jsonl`: `wrapper_error`, общие коды DSH `AUTH`, `QUOTA`, `RATE_LIMIT`, `TRANSPORT` и другие |
| GLM | `events.jsonl`: `wrapper_error`, собственные `glm_*` причины и общие коды DSH |
| Kimi | `stderr.log`: последняя строка `error: failed to run prompt: …` |

У Claude обычная реплика модели и текст инструмента не становятся ошибкой по ключевым
словам. Отказ окна подписки означает квоту; общий HTTP 429 итоговой строки не отменяет
это более точное событие. Реальный ответ модели и разрешённое окно снимают прежний отказ.
У DeepSeek и GLM успешный `result` и новый старт также снимают старую ошибку wrapper-а.
Собственные сообщения GLM сохраняют различие исчерпанного окна и нехватки баланса/пакета.

Обёртки DeepSeek/GLM сохраняют `last.md`, затем проверяют `deliveryFailure`. Такой
результат runtime становится ошибкой процесса с исходными кодом, HTTP-статусом и сообщением модели,
а не успешным terminal `result`. Внешний сигнал остановки имеет приоритет. Собственного
повтора модельного запроса здесь нет. Старый запуск, где обёртка уже потеряла причину
и завершилась кодом 0, по этим данным диагностировать невозможно.

## Kimi и журнал попыток

Batch CLI Kimi печатает окончательную ошибку строкой `error: failed to run prompt: …`
в `stderr.log`, поэтому один разбор stdout её не видит. Сервер берёт последнюю такую
строку, распознаёт причину общим реестром с теми же правилами квоты Kimi, что и чат,
и показывает «Закончилась квота» для `reached your … usage limit`. Это работает и после
частично выполненного хода, чей управляющий класс остался `unknown`. Авторизация,
частота запросов, сеть и неверная конфигурация получают свои пояснения; неизвестная
причина сохраняет очищенный исходный текст. Один HTTP 429 не означает исчерпания квоты.

`runner.attempts[].failureDetail` использует общий источник для всех пяти исполнителей и
перекрывает общую подпись класса в журнале окна узла. Читаются только последние 20
видимых запусков, по 256 KiB хвоста соответствующего файла. Ссылки и изменившиеся
файлы отклоняются тем же файловым помощником, что и у карточки остановки. Успех,
таймаут, сигнальная остановка и ручное переключение не наследуют старую ошибку.
Диагностическое обогащение не меняет классы движка, предохранитель, повторы и
автоматическую смену исполнителя. Обёртки DSH отдельно исправляют ложный код 0
для полученного отказа модели; правила разрешённого failover остаются прежними.

## Неожиданная ошибка и отсутствие диагностики

Общий `readRunnerFailure` читает mirror, затем протокол исполнителя и запасной
`stderr.log` через один удерживаемый каталог. Если протокол не распознал отказ,
последняя содержательная строка stderr показывается как «Последнее сообщение
исполнителя: …». Заголовок ошибки имеет приоритет перед хвостом стека и версией Node;
ссылки на private журнал и кадры стека отбрасываются. Эта строка не считается
доказательством квоты или разрешением автоматического повтора.

Если доступные файлы пусты или не содержат причину, показывается «Процесс завершился
с кодом N; исполнитель не сообщил причину». Если файлы недоступны — «Процесс завершился
с кодом N; журнал диагностики недоступен». Уже доказанные классы `limited`, `denied`
и `context_overflow` сохраняют своё пояснение даже без файла причины.
Новый формат провайдера и новый исполнитель получают тот же запасной путь.
Обрезанная первая строка хвоста не выводится, включая файл без перевода строки.

Старый сервер может не прислать `failureDetail`. Клиент в этом случае заменяет
`unknown` и незнакомые классы явным отсутствием причины, добавляя код процесса,
когда тот доступен. Пустой результат остаётся идущим запуском. Исходный управляющий
`unknown` остаётся в DTO и не превращается в выдуманную известную причину.

## Передача причины движком

Диспетчер передаёт пояснение последнего запуска через `DISPATCH_RESULT_DETAIL`.
Маршрут использует его в комментарии и строке остановки, сохраняя число попыток.
При отсутствии пояснения работает прежнее отображение класса. Сообщение очищается
от управляющих символов и типичных секретов; исходная диагностика ограничена500
символами, поле для маршрутного комментария —220.

## Уже остановленные задачи

`runnerStall.ts` дополняет сводку и граф одним способом. Он работает только с
`exhausted` и точным `ACTIVE_RUN` соответствующего этапа: проверяет task, stage,
attempt, run, epoch, окончание процесса и время текущего визита. Для старого запуска
без `FAILURE_*` читает последние256KiB файла соответствующего раннера, отбрасывая обрезанную первую строку.
Ошибка другого запуска, старого визита, успешного хода или таймаута не подходит.

Чтение каталогов и файлов привязано к удерживаемым дескрипторам; ссылки, FIFO,
hardlink и меняющийся файл отклоняются. Недоступные доказательства оставляют прежнюю
карточку. Этот путь ничего не пишет и не пересматривает outcome/арбитраж.
Неизвестный класс сохраняет конкретный текст ошибки для человека.

Изменения движка подхватываются новым процессом. Для нового текста существующей
карточки нужен обычный перезапуск сервера GrigDesk; повтор задачи для этого не нужен.

## Регрессии

Проверяются обновляемая версия CLI, capacity после работы, неизвестный отказ,
текст внутри команды, восстановившийся поток, auth после работы/повреждения,
приоритет timeout, секреты и длина сообщения. Настоящий launcher с фиктивным Codex
проверяет публикацию `FAILURE_*`; маршрут — передачу текста при обычном бюджете
повторов; dispatcher — отсутствие смены модели и утечки причины в следующий запуск.
Серверные тесты сверяют сводку/граф старой остановки, совпадение идентичности,
временную границу, ссылки и большой журнал без мутаций состояния.
Отдельные проверки Kimi покрывают квоту в stderr, неизвестную причину, скрытие секретов,
исключение успешных и остановленных запусков и прежний `unknown` без изменения реестра.
Реальные формы Claude взяты из сохранённых engine fixtures. Контрактные события DSH
проверяют различие квоты, авторизации, частоты и сети; это не live-инцидент квоты DeepSeek.
Проверка сравнивает реестр источников диагностики с полным каталогом встроенных раннеров.
Матрица всех пяти исполнителей подтверждает текст в журнале попыток и исключение успеха,
таймаута и остановки. Компонентный тест проверяет карточку и журнал окна узла для каждого.
Проверки обёрток воспроизводят `deliveryFailure` без успешного result и без второго вызова.
Матрица запасного пути проверяет новый текст stderr, скрытие секретов, пустые и пропавшие
журналы, обрезанную строку и незнакомого исполнителя. Клиентская проверка отдельно
проходит ответ старого сервера без `failureDetail`.
Платные запросы к моделям и живая проверка после перезапуска сервера не проводились.
