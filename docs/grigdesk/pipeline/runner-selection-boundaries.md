# Почему в узле видны не все исполнители

Каталог чатов и каталог конвейера имеют разные границы. Наличие карточки в
«Настройки → Исполнители» не означает, что движок умеет запускать её в узле.

## Каталог конвейера

`GET /api/factory/runners` вызывает `listInstalledRunners` из
`server/src/lib/runnersCatalog.ts`. Функция читает имена `*.sh` из
`config.factoryRunnersDir` либо `<factoryHome>/lib/runners`, исключает служебные
`index`, `policy`, `catalog` и проверяет формат id. Проверки ключа, CLI и допуска
runtime здесь нет: «установлен» означает наличие модуля раннера.

В дереве движка есть `claude.sh`, `codex.sh`, `deepseek.sh`, `kimi.sh`, `glm.sh`.
Endpoint назначения проверяет каталог раннеров; отдельная регистрация карточки
исполнителя в чате сама по себе не создаёт поддержку конвейера.

## Состояние узла меняет список

`web/src/views/PipelineView.vue` разделяет два действия:

| Состояние | Источник вариантов | Действие |
| --- | --- | --- |
| Узел не выполняется либо прогон остановлен | Каталог раннеров плюс сохранённый primary | `runner/override`, следующий запуск |
| Есть живой оркестратор, статус `run` и `runner.actual` | Только `runner.chain` без actual | `runner/switch`, остановка текущего запуска |
| Попытка доступна только для чтения | Изменений нет | Просмотр |

Поэтому установленный DeepSeek или Kimi отсутствует среди кнопок живого
переключения, если его нет в текущей цепочке. Такой же запрет находится в
`server/src/modules/factory/index.ts`: цель вне `runner.chain` получает
`409 runner_not_allowed`. Это ограничение API и интерфейса. Движковая команда
`runner switch` проверяет только формат id; `runtime_switch_request` сохраняет
stage override, а `multi_runner_run` запускает новую цепочку с ручной целью.
Регистрация и доступность цели проверяются уже на пути её исполнения, поэтому
при расширении ручного выбора нельзя считать CLI предварительной проверкой каталога.

Загрузка каталога в `loadFactoryRunners` одноразовая на экземпляр страницы:
`factoryRunnersRequested` устанавливается до запроса и не снимается при ошибке.
После отказа повторное открытие узла не перечитывает список. При пустом каталоге
сохранённый primary всё ещё может остаться единственной карточкой.

`resolveRunnerState` в `server/src/lib/runnerState.ts` заполняет `runner.models`
только для текущей цепочки. У установленного раннера вне цепочки может отсутствовать
подпись модели; это само по себе не исключает его из карточек назначения.
Выбор конкретной модели и effort сейчас задаётся политикой профиля, а карточка
назначает исполнителя, не модель.

## Граница GLM

`engine/lib/runners/glm.sh` вызывает host-wrapper `glmRunner.mts` поверх того же
отдельного DeepSeek ELF. Этап поддерживает только Обычный API; каталог моделей
статичен. Node, ELF и кэш приходят из `GRIGDESK_DEEPSEEK_*`.

`server/src/lib/glm/runtime.ts` принимает `factory: true` только с проверенным
контекстом task/stage/run/epoch. Узел `state-only` получает `read-only`, узел
`workspace-write` — запись в рабочей папке; оба работают с `approval: never`.
Вопрос получает отказ без ожидания человека. Монтируется только host-owned
`factory-status` с точными `stage_progress` и `stage_result`; текст модели не
завершает этап. Fanout и native resume не объявлены. Сигнатуры GLM не переключают
исполнителя автоматически.

`routeLaunchEnv` передаёт режим GLM и пути хоста в обе ветки отвязанного запуска.
Transient-юнит получает `DEEPSEEK_API_KEY` и `ZAI_API_KEY` только через
`route-secrets.env` с режимом 0600. Ключ Coding Plan не передаётся, ключи в argv
не попадают. Проверка systemd-run исполняет команду с окружением, собранным с нуля.

## Проверки

- `tests/server/runners-catalog.test.js` — обнаружение модулей, включая DeepSeek.
- `tests/server/factory-runner-override.test.js` — назначение DeepSeek, границы
  активного и остановленного этапов, вызов canonical CLI.
- `tests/web/pipeline-runner-override.component.test.js` — разные действия в
  состояниях узла, сохранение модалки и отображение выбора.
- `tests/engine/integration/runtime-switch.sh` — CAS, однократное потребление
  switch, DeepSeek как цель и завершение собственного дерева процессов.
- `tests/server/binary/factory.test.mts` — настоящие упакованные этапы и status MCP,
  оба режима GLM, nvm-only Codex через dispatcher, EnvironmentFile и продолжение
  попытки через authenticated API нового ELF и возврат к обновлённому source.

Эти границы описывают код, а не состояние конкретного открытого пользователем
прогона. Отсутствие DeepSeek в остановленном узле требует проверки ответа каталога,
источника `factoryHome` и версии загруженного интерфейса.
