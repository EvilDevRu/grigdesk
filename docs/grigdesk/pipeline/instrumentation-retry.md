# Повтор транзакционного этапа после cleanup

Временный отказ провайдера оставляет узел без stage-result. Движок восстанавливает
исходники через cleanup инструментации и начинает повтор по бюджету узла. Позиция
stage-журнала при этом прежняя, а каталог завершённой транзакции сохраняется для аудита.

Когда ID вычислялся только из attempt и позиции журнала, повтор использовал тот же
каталог. `instrumentation_tx_begin` возвращал 73 до нового запуска агента, хотя cleanup
прошёл успешно и бюджет повторов ещё не исчерпан.

Общий `_route_v2_transaction_id` в `engine/lib/route-runtime.sh` выбирает свободный номер,
начиная с позиции журнала, и пропускает только каталоги `STATE=completed`. Его используют
и контекст в `engine/bin/factory`, и открытие транзакции. Ничего не переименовывается,
старые backups сохраняются; прежний формат ID и читатели восстановления не меняются.
Выбор происходит под блокировкой оркестратора задачи, а `begin` сохраняет собственную
проверку отсутствия каталога под transaction lock.

Активная транзакция остаётся общей для `instrument→proof`. Отсутствующий active pointer
при `active`, `cleaning`, `stalled`, повреждённое состояние и symlink блокируют запуск.
Они не считаются завершённой историей и не обходятся новым ID.

Регрессии: `tests/engine/unit/route-transaction-id.sh` и сценарий временного отказа
INSTRUMENT в `tests/engine/integration/route-dispatch.sh`. Интеграция проверяет повторный
вызов агента, восстановление baseline, отдельный ID и передачу успешной транзакции proof.
