# Составная ссылка на модель в lifecycle

GLM хранит modelRef строкой с JSON-парой `["маршрут","модель"]`. Это контракт каталога
и запуска раннера; исходное значение передаётся адаптеру без изменения.

Строгая схема lifecycle допускает в modelId только `^[A-Za-z0-9][A-Za-z0-9._:/+-]*$`.
Поэтому `runtime_lifecycle_model_id_v2` из `engine/lib/runtime-analytics.sh` переводит
JSON-массив ровно из двух строк в `маршрут/модель` перед записью `requestedModel` и
`resolvedModel` в событиях `dispatch_candidate_selected`, `dispatch_candidate_skipped`
и `runner_started`. Пробелы JSON не влияют на результат. Обычные идентификаторы,
пустые строки и неподдерживаемые формы остаются прежними; отсутствие resolvedModel
в событиях диспетчера сохраняется как JSON null.

Это представление телеметрии, а не новый формат вызова модели. Схема не расширяется,
запрещённые символы внутри компонентов не удаляются: невалидный результат по-прежнему
отклоняется писателем с кодом 78. Без преобразования JSON-пара давала
`lifecycle-schema-invalid: $: expected exactly one discriminated schema branch`
на выборе кандидата, ещё до запуска раннера, и расходовала бюджет повторов узла.

Регрессия — `tests/engine/contract/lifecycle-model-id.sh`: все три производственных
помощника собирают полное событие, затем настоящий `event-hash` проверяет схему.
Сырой modelRef отдельно возвращается в каждое из двух полей как отрицательный контроль.
Штатный запуск GLM и сохранение modelRef в argv проверяет `unit/glm-runner-launch.sh`.
