# Создание конвейера без автоматического старта

Тумблер «Автоматически стартовать конвейер при создании» («Настройки → Автоматизация →
Запуск», prefs `pipelineAutoStart`, по умолчанию включён) управляет только ручным
запуском из карточки задачи. Выключенный тумблер создаёт конвейер, но не запускает
ни одного узла: человек назначает исполнителей на узлах и стартует прогон вручную.
Автозапуски по правилам Telegram, массовый запуск, CLI и перезапуск стенда не
затрагиваются.

## Контракт

- Веб-карточка читает настройку свежим запросом `/api/settings/prefs` при запуске и
  при выключенной добавляет в тело `POST /api/tasks/:id/launch` поле `autoStart: false`.
  Отсутствие поля = старт сразу: сервер не подмешивает настройку сам, поэтому CLI
  (`tracker pipeline launch`) и автозапуски сохраняют прежнее
  поведение. Отказ чтения настройки не меняет запуска.
- Сервер передаёт движку `start --hold-start` (`routeStartArgs`). Движок выполняет
  всю штатную подготовку — попытка, pins, lifecycle, identity-проекция реестра,
  immutable контракты, ticket, подъём стенда — но пропускает bootstrap-разведку и
  основной диспетчер. Курсор не инициализируется.
- Маркер реестра `HELD_START` двухфазный: `pending` пишется сразу после полной
  identity-проекции (стенд ещё поднимается), `1` — только после полного
  `v2_sandbox_bootstrap_wait`. Выход раньше готовности стенда запрещён: EXIT-trap
  убивает незавершённый `up.sh` и оставляет частичную песочницу (тупик 75 на resume).
  Маркер снимает любой следующий заход движка (start `--init`, общая проекция
  resume/gate, recovery) — по образцу `STOPPED_SIGNAL`.
- Подтверждение создания не требует живого демона: `heldRegistryIdentity`
  (`lib/factoryRouteCli.ts`) сверяет те же ключи, что `startRegistryIdentity`, минус
  `ORCH_PID`, плюс маркер `HELD_START ∈ {pending, 1}`. Значение маркера в identity-строку
  не входит: переход pending→1 не сбрасывает счётчик подтверждений. После четырёх
  подтверждений выполняются `sealPipeline` и trusted ticket proof, ответ —
  `outcome: 'created'`. Мёртвый юнит с полной held-identity — штатный исход, без
  identity — отказ создания.
- Ручной старт — существующий `POST /api/tasks/:id/resume`. При `HELD_START=pending`
  сервер отвечает 409 `hold_pending`: resume упёрся бы в частичную песочницу. Resume
  сам выполняет разведку (если нет `artifacts/bootstrap.json`) и идемпотентно создаёт
  курсор; отсутствия курсора у никогда не стартовавшей попытки защиты не требуют
  (штатный путь recover-попыток).
- Поузловые назначения до старта — существующий `POST /api/tasks/:id/runner/override`
  и вкладка «Исполнители»: им достаточно реестра и закреплённой попытки, живой демон
  не нужен (активный этап по-прежнему отбивается). Назначение читается при запуске
  узла (`routing_resolve`) и вступает в силу с первым узлом после ручного старта.
  Task-level смена primary на попытке запрещена контрактом trusted ledger.
- Классификация: `detectStall` при `HELD_START=1` возвращает null (не обрыв и не
  остановка); `HELD_START=pending` живёт под живым демоном, а оборванный подъём
  стенда без маркера готовности остаётся `crashed`. Трекерный `pipeline wait`
  отвечает `stopped` на удержанную попытку, не доводя до timeout.
- Витрина: DTO списка и графа несут `held` и `holdPending`. Карточка показывает
  «ожидает старта» с главным действием «▶ запустить» (тот же resume, своё
  подтверждение) либо «создаётся» без кнопки старта. Ромб стенда у готовой
  удержанной попытки — `done`, не `fail`. Массовый «Плей» наследует гейт
  `canResume`: удержанные готовые попытки стартуют, поднимающиеся — пропускаются.

## Цена решения

Стенд создаётся ДО старта: resume не умеет provisioning (isolated absent → 73,
shared env отсутствует → 73), поэтому удержанная попытка держит слот и стенд, а в
shared-режиме — lease профиля, до ручного старта или abandon. Карточка предупреждает
об этом в подсказке действия.
