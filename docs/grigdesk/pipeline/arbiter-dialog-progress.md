# Арбитр учитывает ответы и продолжает диалог

`buildConversationPrompt` различает первый разбор (`start`) и продолжение
(`discuss`, `diagnose`). Первый ход объясняет остановку целиком. Продолжение коротко
подтверждает решение человека, объясняет его последствия и следующий шаг. Повтор
полного разбора, прежних фактов и отвеченных вопросов запрещён; новый вопрос нужен
только при невозможности продолжить без ответа. Диагностика сообщает новые выводы.

Первый абзац публичной реплики и `summary` содержат 2–4 простых предложения:
что случилось с задачей и что требуется от человека. Метрики, пути, идентификаторы,
эпохи и хеши относятся к «Подробностям» реплики или `technicalDetails`. Вопросы
и предложения описывают доступные человеку решения без внутреннего жаргона.

## Принятые ответы

При выборе варианта или собственного ответа операция `discuss` сохраняет
`answeredQuestion`: исходные `questionId`, необязательный `optionId`, текст вопроса
и окончательный ответ. Это снимок выбранного вопроса до снятия прежнего результата.
Человеческая реплика остаётся его представлением для истории. Свободное сообщение
не получает такую структуру и не считается разрешением применения.

Prompt получает `answeredQuestions: [{question, answer}]` за всю историю, независимо
от ограничения последних сообщений. Эти ответы не дублируются в `humanDecisions`,
а в `lastResult` остаются только неотвеченные вопросы. Старые документы schemaVersion 1 без этого поля
читаются без миграции: пара восстанавливается из человеческой реплики того же хода
и текста вопроса в сохранённых результатах. Многострочный ответ сохраняется целиком.

После строгой проверки итога сервер снимает точные повторы отвеченных вопросов:
сравнивает текст без различий регистра и пробелов. Сравнение только по `questionId`
недопустимо: модель может использовать прежний `q1` для другого вопроса. Смысловые
перефразирования регулирует prompt, сервер не классифицирует их отдельной моделью.

## Следующий шаг

Необязательное поле результата `nextStep` уточняет состояние диалога:

- `answer_questions` — есть вопросы, предложения могут отсутствовать;
- `choose_proposal` — вопросов нет, есть предложения для явного выбора;
- `continue_discussion` — оба списка пусты, `summary` объясняет дальнейший шаг.

Старый результат без `nextStep` остаётся допустимым с вопросами или предложениями.
Пустые оба списка требуют явного `continue_discussion`. Несогласованное значение
отклоняется строгим декодером. UI сохраняет свободное сообщение без вопросов;
для законченных уточнений убирает пустую колонку решения, если совместимость
не требует отдельного предупреждения. Применение отражает серверное состояние
`applying`, которое возникает только после отдельного действия человека.

Новый ход по-прежнему снимает старые активные предложения. Актуальное предложение
модель явно возвращает в новом итоге; автоматического восстановления после отказа
или согласия применить действие из обычной переписки нет.

## Граница модели

`parseArbiterModelResult` удаляет неизвестные поля вопроса, варианта и предложения.
Пропущенный `allowCustom` означает `true`; явно переданное другое значение не
исправляется. Пропущенные `recommended` и `explanation` сохраняют прежние правила
восполнения. Корневой итог, вложенный `action`, цели, известные поля, ограничения
длины и количества остаются строгими. Лишний исполняемый текст не сохраняется
и не исполняется. Хранилище и HTTP не получают этих послаблений.

Проверки: shared-декодер, парсер модели, runner, durable HTTP-сценарий двух ответов
и компонент UI. HTTP-сценарий использует подменённую модель и отдельное хранилище;
он не изменяет настоящую остановку и не доказывает качество ответа живой модели.
