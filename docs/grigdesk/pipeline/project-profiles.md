# Профили конвейера: устройство и параметры

Профиль — адаптер проекта к общему движку фабрики. Он задаёт репозитории, окружение,
проверки, права агентов, выбор исполнителей и доступные маршруты. Один профиль может
обслуживать несколько репозиториев; несколько профилей могут работать с одними исходниками.
Имя профиля не определяет стек, модель или режим работы: эти свойства объявляются явно.

Маршрут задаёт этапы, инструкции, возвраты и ворота человека. Попытка — конкретный запуск
задачи по закреплённой версии маршрута. Узел — отдельный агент, команда или ворота внутри
этой попытки. Выбор маршрута принадлежит человеку; триаж предлагает маршрут по политике
профиля. Проект в реестре GrigDesk может существовать и без исполняемого профиля фабрики.

Здесь перечислены общие параметры профиля. Проектные значения, команды и дополнительные
переменные принадлежат README самого локального профиля. Подробные ограничения протокола —
в [контракте профиля](../../engine/PROFILE-CONTRACT.md), порядок подключения — в
[инструкции нового проекта](../../engine/NEW-PROJECT.md).

## Файлы и хранение

Поставляемый [образец профиля](profile-sample.md) находится в
`server/seed/pipeline-sample/` и в исходниках, и в комплекте сервера. Его копируют вручную;
репозитории, команды, стенд, правила, исполнители и способ сдачи заполняют в одном project.json.
Скрипт configure проецирует его через canonical CLI, общие инструкции этапов не меняются.
На старте автоматической установки и изменения существующих профилей нет.

```text
profiles/<PROFILE>/
  profile.sh                    переменные и доверенные хуки проекта
  runners.env                   исполнители, резерв и модели
  graph.json                    возможности профиля
  dashboard.env                 параметры панели и постоянного стенда
  routes/
    definition.mjs              исходники маршрутов при управлении скриптом
    publish.mjs                 проверка и публикация этих исходников
    editor-capabilities.json    доступные редактору команды и секции контекста
    ...                         промпты и вспомогательные модули проекта
  up.sh / down.sh / status.sh    lifecycle изолированных песочниц, если они нужны
  ...                           обёртки тестов, проверки и интеграции проекта
```

Четыре корневых файла составляют профиль запуска. Содержимое каталога — локальная
конфигурация окружения, оно не поставляется вместе с движком. На конкретной установке
`profiles` может быть ссылкой на внешний каталог; наличие ссылки в Git не означает,
что Git хранит её содержимое.

| Настройка размещения | Значение и умолчание |
|---|---|
| `FACTORY_PROFILES_DIR` | Явный каталог профилей; сильнее умолчаний. Для движка нужен абсолютный физический путь без symlink-компонентов. |
| `config.profilesDir` | Разрешённый сервером каталог: при запуске из исходников без override — `<корень кода>/profiles`, в пакете — `profiles` в папке данных. Сервер передаёт его фабрике через `FACTORY_PROFILES_DIR`. |
| `GRIGDESK_ROUTES_DIR` / `config.routesDir` | Хранилище опубликованных неизменяемых каталогов и маршрутов; без override — `~/.factory/routes`. CLI получает его через `--routes-dir`. Это отдельное хранилище, не папка исходников `routes/` профиля. |
| `GRIGDESK_ROUTES_AUTHORING_DIR` | Хранилище черновиков редактора; без override — `<config.routesDir>.authoring`. Не заменяет каталог опубликованных маршрутов. |
| `GRIGDESK_FACTORY_PROFILE` | Явный профиль по умолчанию для сервера. Не создаёт профиль и не включает его возможности. |

Имя, принимаемое GrigDesk, соответствует `^[a-z0-9][a-z0-9_-]{0,40}$`: от 1 до 41 символа.
Форма запуска выбирает профиль в порядке: явный `profile` запроса → настройка сервера →
единственное совпадение репозиториев триажа → прежний профиль по умолчанию. Неоднозначное
совпадение не выбирается за человека. Архивные проекты исключаются из новых запусков;
форме нужен опубликованный каталог. Подробнее —
[выбор профиля по триажу](launch-profile-consistency.md).

## `profile.sh`: переменные

Это исполняемый доверенный Bash-файл. Он может содержать собственные переменные проекта,
но движок не придаёт им смысла без явного чтения в хуке. `source` не должен печатать
произвольные данные или запускать подготовку стенда: потребители читают профиль и при
триаже, просмотре формы или проверке конфигурации.

| Параметр | Формат, назначение и поведение без значения |
|---|---|
| `PROFILE_NAME` | Идентификатор профиля; должен совпадать с именем каталога. `factory` экспортирует выбранное имя перед загрузкой файла. |
| `PROFILE_CTX` | Текст о стеке, правилах и запретах для триажа. Без значения — пустой контекст. Контекст route-агента отдельно объявляет `profile_project_context`. |
| `PROFILE_AGENT_CWD` | Абсолютный базовый рабочий каталог для потребителей профиля, в том числе триажа. При исполнении route v2 launcher заменяет его workspace первого репозитория. |
| `PROFILE_AGENT_DIRS` | Строка дополнительных путей через пробел. При исполнении route v2 список формируется из закреплённых workspace; состояние и служебные каталоги добавляет движок. Пробелы внутри путей этот формат не экранирует. |
| `PROFILE_AGENT_ALLOW` | Bash-массив разрешений команд, например `"Bash(npm test:*)"`. Дополняет базовые разрешения движка; без массива проектных добавлений нет. Узкие права роли лучше выдавать через `profile_stage_agent_allow`. |
| `PROFILE_AGENT_DENY` | Bash-массив запретов инструментов и команд. Дополняет запреты движка; разрешение не отменяет запрет. Без массива остаются системные ограничения. |
| `PROFILE_SERVICE_HOST` | Голое имя хоста или адрес без схемы, порта и `/`; умолчание `127.0.0.1`. Из него и портов строятся `services.frontendUrl` и `services.apiUrl`. Если приложение ожидает `localhost`, это нужно указать явно. |
| `PROFILE_LOOP_MAX_ROUNDS` | Целое 1..300, потолок передач в маршруте с `loop`; отсутствующий ключ означает 20. Пустое значение, 0 и мусор отвергаются. На обычные маршруты не влияет; проверяется при start/resume/gate. |
| `PROFILE_TRIAGE_REPOS` | Строка `ключ:/абсолютный/source другой-ключ:/другой/source`, пары разделены пробельными символами. Задаёт репозитории триажа и паспорт проекта. Нет значения — триаж не получает репозитории. Это source, а не будущие worktree задачи. |
| `PROFILE_TRIAGE_MARKERS` | Свободный текст проектных маркеров риска для триажа: миграции, платные API и другие особенности. Нет значения — проектных маркеров нет. Это инструкция оценке, не shell-команда и не запрет движка. |
| `PROFILE_TRIAGE_ROUTES` | Строка пар `род:глубина=routeId`, например `feature:light=small feature:mid=small feature:full=feature`. Глубина — `light`, `mid` или `full`; цель должна существовать в каталоге. Без карты род работы сопоставляется с именем маршрута. |
| `PROFILE_TRIAGE_RULES` | Строка пар `ключ:относительный/файл`, где ключ объявлен в `PROFILE_TRIAGE_REPOS`. Файлы решений продукта читаются в снимке кода триажа. Абсолютные пути и `..` отбрасываются. Без значения файлов правил нет. |
| `PROFILE_AGENT_CONTROL_DIR` | Служебный результат `profile_agent_control_start`, а не постоянная настройка workspace. Абсолютный owner-only каталог канала управления, mode `0700`; restricted Codex получает его только для чтения. Без пары control-хуков не требуется. |

`PROFILE_TRIAGE_ROUTES` лучше задавать одним литералом в кавычках, допускающим переносы
строк. Редактор проверяет карту без исполнения shell и отвергает динамическое или
неоднозначное присваивание. Парсер триажа пропускает мусорные пары; при повторе одной
пары «род:глубина» побеждает первая. Политика глубины —
[отдельный контракт триажа](triage-routing-policy.md).

`PROFILE_VOLATILE_PATHS` — снятая переменная, движок её не читает. Для untracked-артефактов
проверок существует `profile_route_volatile_paths`; он не разрешает произвольную запись
проверяющему агенту.

## `profile.sh`: обязательные хуки

Хук — Bash-функция, которую вызывает движок или сервер. Если не оговорено иначе,
данные возвращаются через stdout, диагностика — через stderr, ненулевой код означает отказ.
`TASK` — номер задачи, `REPO` — имя репозитория из профиля, `RUN_KEY` — ключ роли узла,
например `BUILD`. Отсутствующий обязательный хук блокирует запуск.

В дополнительных сигнатурах `ROUTE` и `NODE` — ID маршрута и узла; `OUTCOME` —
заявленный исход, `RUN_ID` — идентификатор точного запуска, `RC` — код возврата процесса.
`CONTEXT_FILE` — файл доверенного typed context этого запуска, `SCOPE_FILE` — файл
точного списка путей инструментации. `CLASS` выбирает класс времени, `COMMAND_ID` —
разрешённую команду профиля. `RESULT` в предпроверке — сдаваемый `done` или `skipped`.
Эти значения передаёт вызывающая сторона; хук не должен угадывать их по старому реестру.

| Хук | Возвращаемые данные и смысл |
|---|---|
| `profile_workspace_mode` | Ровно `isolated` или `shared`. Режим объявляется явно, равенство путей не переключает его автоматически. |
| `profile_repositories TASK` | 1–16 строк `имя<TAB>source<TAB>workspace`. Имена уникальны; первый репозиторий — основной cwd. `source` существует; в `isolated` workspace отдельный, в `shared` точно равен source. |
| `profile_project_context` | JSON только с `stack: string[]` и `guardrails: string[]`: стек и обязательные правила route-агентов. Закрепляется в попытке, произвольные поля и секреты сюда не входят. |
| `profile_source_branch TASK REPO` | Ветка workspace указанного репозитория. В `shared` соответствует текущей ветке checkout; в `isolated` это общая для всех репозиториев ветка задачи. База, от которой её создаёт `up.sh`, задаётся отдельно самим профилем. |
| `profile_container TASK` | Непустое имя стенда/контейнера для контекста и аренды ресурса. Сам хук ничего не запускает. |
| `profile_stand_alive TASK` | Код 0, если существующий стенд готов; ненулевой — не готов. Проверка health без создания, запуска и удаления ресурсов. |

Разница режимов:

| Свойство | `isolated` | `shared` |
|---|---|---|
| Код задачи | Отдельные workspace/worktree | Существующие основные checkout |
| Подготовка | Профильный `up.sh TASK`, затем проверка стенда | Проверка уже существующего окружения |
| Владелец стенда | Задача | Внешний владелец |
| Снос | Только ресурсы соответствующей задачи | Чужой checkout и стенд не удаляются |
| Общие ресурсы | Задаёт lifecycle проекта | Защищаются долговечной арендой до завершения/abandon, включая ворота человека |

Зависимости изолированной задачи копируются без общих inode: `cp -a`, не `cp -al`.
Иначе тестовый кэш одного workspace может переписать зависимости соседних задач.

## Условные и дополнительные хуки

| Хук | Когда нужен; формат и поведение при отсутствии |
|---|---|
| `profile_service_ports TASK` | Обязателен в `shared`: одна строка `FE_PORT<TAB>API_PORT`, текущий launcher принимает порты 1000..65535. В `isolated` порты берутся из env песочницы. |
| `profile_exclusive_resources TASK` | Обязателен в `shared`: 1..32 строки стабильных ключей ресурсов. Включает точные `workspace:<путь>` и `stand:<имя>`; общий GPU — одинаковый `gpu:<имя>` у всех его пользователей. |
| `profile_instrumentation_restored TASK SCOPE_FILE` | Обязателен в `shared`: синхронизирует восстановленные файлы scope с внешним стендом и проверяет health. Не создаёт и не удаляет ресурсы; отказ удерживает аренду и остановку. |
| `profile_delivery_targets TASK` | Нужен GrigDesk для маршрута с `ship`: строки `имя-repo<TAB>целевая-ветка`, по одной на каждый репозиторий. Сервер передаёт их движку через `--delivery-target`; прямой CLI обязан передать targets сам. |
| `profile_delivery_actions TASK` | Необязательные дополнительные действия доставки, по одному на строку; сейчас словарь содержит `task-comment`. Без хука или при пустом выводе добавлений нет. Базовые разрешения publish-маршрута не отключает. |
| `profile_stand_start TASK` | Необязательный идемпотентный запуск процессов уже существующего стенда задачи. GrigDesk зовёт перед resume, если health не прошёл и стенд принадлежит задаче; затем повторяет health. Без хука автоматического восстановления процессов нет. |
| `profile_slots` | Необязательный источник занятости слотов для `factory slots --profile <PROFILE>`. Строка `RANGE <min> <max>`, затем `USED <k> <владелец> <причина>` для занятых; поля USED без пробелов, `ERROR <текст>` означает отказ. Нет хука — ответ `supported: false`. Сам хук слот не резервирует. |
| `profile_timeout_class CLASS` | Необязательные секунды для класса времени узла. Целое число заменяет дефолт класса; нет хука/числа — остаётся дефолт движка. |
| `profile_stage_agent_allow RUN_KEY` | Необязательные дополнительные разрешения роли, по одному на строку. Нет хука — только общие права. Команды доставки выдаются роли `SHIP`, а не всем агентам. |
| `profile_route_command TASK ROUTE NODE RUN_KEY COMMAND_ID CONTEXT_FILE` | Обязателен при наличии `executor=command`. Сопоставляет ID команды из закреплённого маршрута с доверенной реализацией; неизвестный ID отвергает. Возвращает строгий JSON-вердикт, не shell-строку. |
| `profile_route_node_evidence_check TASK ROUTE NODE RUN_KEY OUTCOME RUN_ID CONTEXT_FILE` | Необязательная доверенная проверка доказательств после runner и файлового сторожа. Код 0 принимает сдачу; отказ отклоняет её, последняя непустая строка — причина. Подробнее о повторе и точных снимках — в контракте профиля. |
| `profile_stage_result_check TASK RUN_KEY` | Необязательная предпроверка сдачи: печатает путь исполняемого файла либо ничего. `stage-result.sh` запускает файл с `TASK RUN_KEY RESULT` до `done/skipped`; ненулевой код отклоняет сдачу в текущем ходе агента. Не заменяет доверенную проверку после runner. |
| `profile_route_volatile_paths TASK` | Необязательные строки `имя-repo<TAB>относительный-путь` untracked-артефактов проверок. Нет хука — исключений нет. Tracked-файлы остаются под сторожем; абсолютные пути, `..`, `.git` и неизвестные repo запрещены. |
| `profile_agent_control_start TASK RUN_KEY` | Только в паре со `stop`: создаёт временный доверенный канал exact stage и экспортирует `PROFILE_AGENT_CONTROL_DIR`. Без пары канал не включается; половина пары — ошибка. |
| `profile_agent_control_stop TASK RUN_KEY RC` | Парный cleanup после любого результата runner; `RC` — его код возврата. Проверяет завершение брокера и освобождает канал. |

Классы времени: `planning`, `standard`, `review`, `delivery`, `check` — 1800 секунд;
`test`, `build` — 3600; `diagnostic`, `browser` — 5400. Неизвестный класс не принимается.

Хуки выбора runner/model в shell не входят в контракт. `profile_agent_cwd` в route v2
задаётся самим launcher; проект объявляет рабочие каталоги через `profile_repositories`.

### Результат подготовки workspace

В `isolated` профильный `up.sh TASK` записывает `STATE_DIR/t<TASK>.env`. В `shared`
такую проекцию пишет движок сам, не вызывая lifecycle профиля. Это результат подготовки,
а не файл для ручного редактирования настройки запущенной задачи.

| Поле env | Смысл |
|---|---|
| `TASK` | Номер задачи, которому принадлежат данные. |
| `WORKSPACE_MODE` | Объявленный режим `isolated` или `shared`. |
| `STAND_OWNERSHIP` | `task` для стенда задачи, `external` для внешнего стенда. Не даёт права сносить внешний ресурс. |
| `SB_K` | Индекс слота песочницы; для shared-проекции движок пишет 0. |
| `FE_PORT`, `API_PORT` | Порты frontend и API; должны совпадать с проверенным контрактом. |
| `SOURCE_BRANCH` | Ветка задачи/checkout первого репозитория; не имя базы, от которой создан worktree. |
| `REPO_COUNT` | Число репозиториев, 1..16. |
| `REPO_<N>_NAME` | Имя репозитория; индексы начинаются с 0. |
| `REPO_<N>_SOURCE` | Абсолютный source-путь этого репозитория. |
| `REPO_<N>_WT` | Абсолютный workspace-путь этого репозитория. |
| `REPO_<N>_BRANCH` | Закреплённая ветка этого workspace. |
| `PROTOCOL`, `CONTAINER`, `SERVICE_HOST` | Shared-проекция дополнительно хранит `route-v2`, имя стенда и хост сервиса. |

Прочие поля env принадлежат проекту. Старые `BE_WT`/`FE_WT` не заменяют generic
`REPO_<N>_*` в исполняемом контракте.

`FACTORY_BOOTSTRAP_WORKSPACE_ENV` — необязательный вход `up.sh` от движка для ранней
готовности isolated workspace. Если профиль использует его, он атомарно записывает
туда полный будущий env после готовности файлов и зависимостей. Окончательный env
должен совпасть побайтово; успешный `up.sh` и health стенда всё равно обязательны.
Отсутствие переменной означает обычную синхронную подготовку. Подробнее —
[ранняя готовность workspace](../../engine/PROFILE-CONTRACT.md#ранняя-готовность-isolated-workspace).

## `runners.env`: исполнители и резерв

Это плоский файл `KEY=VALUE`, не Bash: без `export`, кавычек и подстановок. Пустые строки
и строки, начинающиеся с `#`, разрешены; повтор ключа и неизвестные семейства ключей
отклоняются. Допустимые символы значений — `A–Z a–z 0–9 . _ , : / @ = + -`.
Изменения выполняются CLI `factory profile <PROFILE> runner/model ...`: запись атомарна,
а revision защищает от перезаписи чужой конфигурации.

| Параметр | Формат, умолчание и назначение |
|---|---|
| `RUNNERS_SCHEMA` | Обязательная версия формата, сейчас `1`. |
| `CONFIG_REVISION` | Обязательное неотрицательное целое; CLI увеличивает при записи и проверяет ожидаемую ревизию. Это не версия маршрута. |
| `RUNNERS_COVERAGE` | Для рабочего профиля требуется `required`: перед вызовом модели проверяется совместимость runner/model policy с хостом. |
| `PROJECT_RUNNER_PRIMARY` | Обязательный ID основного установленного исполнителя. Список узнаётся через `engine/bin/factory runners`, по имени проекта исполнитель не угадывается. |
| `PROJECT_RUNNER_FAILOVER` | Упорядоченный список резервных исполнителей через запятую. Отсутствие/пустая строка — автоматического резерва нет. |
| `STAGE_<RUN_KEY>_PRIMARY` | Основной исполнитель отдельной роли, например `STAGE_REVIEW_PRIMARY`. Без непустого значения используется проектная пара primary/failover. |
| `STAGE_<RUN_KEY>_FAILOVER` | Резерв этой роли, список через запятую. Применяется вместе с её primary; пустое значение не наследует проектный резерв. |
| `RUNNER_<PROVIDER>_AUTH_PROFILE` | Необязательная метка auth-профиля для fingerprint учётного контекста и breaker. Без неё используется `default`. Это не секрет, путь к credential-файлу или команда переключения аккаунта. |

В ключах `PROVIDER` — ID исполнителя в верхнем регистре с заменой `-` на `_`,
`RUN_KEY` — ключ роли узла из маршрута, а `DEFAULT` — политика всех неуточнённых ролей.

Приоритет цепочки исполнителей:

```text
task-stage → task → profile-stage → profile-project
```

Override задачи хранится в реестре задачи и не переписывает профиль. Это замена всей пары
primary/failover, а не добавка к проектному резерву. Выбранный вручную исполнитель не меняет
семейство и effort, заданные для него модельной политикой.

Резерв применяется по классификации отказа, а не по любому ненулевому результату.
Продуктовый `failed` сам по себе не является причиной смены поставщика. Точные условия —
[контракт мульти-ИИ](../../engine/MULTI-AI.md).

## `runners.env`: модели

Каждый следующий суффикс применим к обеим формам ключа:

```text
MODEL_DEFAULT_<PROVIDER>_<СУФФИКС>
MODEL_<RUN_KEY>_<PROVIDER>_<СУФФИКС>
```

Для каждого поля отдельно движок берёт непустое значение роли, затем `DEFAULT`.
Пустое значение роли не отключает унаследованное значение. Если не заданы ни `FAMILY`, ни
`EXACT`, runner может предоставить собственную default policy; для воспроизводимой
настройки профиль явно задаёт семейство и effort.

| Суффикс | Что означает и как разрешается |
|---|---|
| `FAMILY` | Семейство модели из каталога исполнителя. `latest` ищется только внутри него; автоматически выбирать соседнее семейство нельзя. |
| `VERSION` | Версия внутри семейства; пустое значение означает `latest`. Выбирается доступная совместимая стабильная модель. |
| `VARIANT` | Вариант модели; пустое значение означает `auto`, то есть каталоговый вариант `default`. Иное значение — точное имя варианта из каталога. |
| `EFFORT` | Уровень рассуждения, который поддерживает выбранный runner и модель. После разрешения полей при пустом значении используется `high`, если не применена собственная default policy runner. Единого допустимого списка для всех исполнителей нет. |
| `EXACT` | Точный model ID, сильнее поиска по `FAMILY`/`VERSION`/`VARIANT`. Требует доступности и совместимости с CLI; неизвестный ID не заменяется. Exact может осознанно закреплять deprecated/beta модель, если каталог допускает её использование. |
| `FAMILY_FAILOVER` | Необязательное резервное семейство того же исполнителя при лимите модели/семейства. Без значения такой подмены нет. Это отдельный механизм от резерва поставщиков; при лимите всего provider смена семейства не помогает. |

Маршрут не содержит `provider`, `model` и `effort`: только `runKey`, по которому выбирается
политика. Смена модели не требует публикации новой topology, но требует совместимого
metadata-only host preflight. Уже работающий процесс не меняет модель посреди хода.

Пример чтения и изменения политики:

```bash
engine/bin/factory profile <PROFILE> runner show
engine/bin/factory profile <PROFILE> runner set codex --failover claude
engine/bin/factory profile <PROFILE> runner set REVIEW claude --failover codex
engine/bin/factory profile <PROFILE> model set DEFAULT codex \
  family=<FAMILY> version=latest variant=auto effort=high
engine/bin/factory profile <PROFILE> model set REVIEW codex effort=<EFFORT>
RUN_HOST_PREFLIGHT=1 engine/bin/factory-check <PROFILE> --host-preflight
```

### Порог автосжатия: текущее ограничение

`FACTORY_STAGE_AUTO_COMPACT` — входная настройка запуска в токенах: неотрицательное
целое, `0` означает не вмешиваться. GrigDesk передаёт её явно, включая ноль; движок
передаёт разрешённое значение runner через служебную `RUNNER_AUTO_COMPACT_WINDOW`.

В `core.sh` есть резервное чтение `AUTO_COMPACT_WINDOW` из `runners.env`, но текущий
`profile_config_validate` этот ключ не допускает. Поэтому добавлять его в валидный
профиль сейчас нельзя: конфигурация будет отвергнута до модели. Рабочий вход — настройка
запуска `FACTORY_STAGE_AUTO_COMPACT`; резерв файла требует отдельной правки движка.

## `graph.json`: возможности и историческое представление

| Поле | Назначение |
|---|---|
| `capabilities` | Массив строк. `route-v2` явно включает route-протокол; без него `factory start` отказывает до lifecycle. На этапе подготовки оставляют `[]`, включают после публикации и проверок. |
| `launchable` | Необязательный флаг для `factory-check`: `false` означает профиль, который задач не ведёт. В сочетании с `route-v2` это ошибка. Движок запусков не использует флаг как альтернативу capability. |

Топология новых запусков берётся из опубликованного bundle. Следующие старые поля могут
сохраняться для просмотра исторических реестров и посева библиотеки стадий; они не меняют
закреплённый маршрут route v2:

| Поле | Назначение исторического представления |
|---|---|
| `nodes` | Переопределения узлов: `id → [вид, подпись, дополнительный текст]`. |
| `keys` | Соответствие визуального node ID ключу статуса реестра. |
| `optional` | Списки необязательных узлов по маршрутам; `*` добавляется всем. |
| `runner_keys` | Соответствие визуальных узлов ключам исполняемых ролей; объединяются `*` и выбранный маршрут. |
| `default_route` | Имя запасной исторической разметки. Не задаёт default route нового каталога. |
| `routes.<route>.vb` | SVG viewBox исторической схемы. |
| `routes.<route>.pos` | Координаты узлов: `id → [x, y]`. |
| `routes.<route>.edges` | Рёбра `[источник, цель, подпись, класс, трассировка]`. |

## `dashboard.env`: панель и постоянный стенд

Файл содержит доверенные настройки проекта. Shell-команда `dashboard` загружает его через
`source`, а Python-панель читает простые пары `KEY=VALUE`, снимая внешние кавычки. Чтобы
значения совпадали у обоих потребителей, нужны буквальные строки без shell-подстановок.
Значение с пробелами берётся в кавычки.

| Параметр | Назначение и поведение без значения |
|---|---|
| `FACTORY_BE_ROOT` | Корень backend для сведений Git в панели и исторического поиска `worktree-t<TASK>`; без значения проектный путь не задан. Не заменяет `profile_repositories`. |
| `FACTORY_FE_ROOT` | Аналогичный корень frontend. Необязателен для проекта с одним репозиторием. |
| `FACTORY_MYSQL_CONTAINER` | Контейнер данных MySQL для диагностических сведений панели; пусто — контейнер не задан. |
| `FACTORY_REDIS_CONTAINER` | Контейнер Redis для чтения очередей; пусто — очереди не опрашиваются. |
| `FACTORY_SANDBOX_PREFIX` | Запасной префикс контейнеров, умолчание `sandbox-t`: панель добавляет `<TASK>-application-1` и `<TASK>-frontend-1`. |
| `FACTORY_STAND_CONTAINER` | Явный шаблон имени стенда/backend; `{task}` заменяется номером задачи, без маркера имя постоянное. Сильнее префикса. |
| `FACTORY_STAND_FE_CONTAINER` | Шаблон frontend-контейнера при явном `FACTORY_STAND_CONTAINER`; пусто — отдельного frontend-контейнера не объявлено. |
| `FACTORY_STAND_URL` | Полный HTTP(S) URL постоянного стенда, в том числе для «Презентаций». Пусто — постоянного URL нет. Не заменяет URL песочницы задачи из её портов и хоста. |
| `FACTORY_TIMER_CMD` | Команда трекера времени, например `node /absolute/path/timer.mjs`; панель добавляет action и TASK. Делится по пробелам без shell; пусто — трекера нет. |
| `FACTORY_TASK_BASE_URL` | База ссылок на задачи внешнего трекера; пусто — проектная база ссылок не задана. |

Для большинства полей Python-панель использует одноимённые переменные окружения как
резерв. У `FACTORY_TIMER_CMD` при чтении конкретного профиля отсутствие ключа означает
отсутствие трекера, чтобы не вызвать чужой трекер по совпавшему номеру задачи.

## `routes/`: параметры маршрута

В режиме `profile-script` источниками служат проектные модули и промпты. В режиме
`editor` источником служит черновик редактора. Опубликованный результат у обоих —
неизменяемый bundle `schema=2` и каталог с указателем `current`. Переключение current
выполняется с проверкой ожидаемого хеша и не переписывает пины начатых попыток.

Поля исполняемой машины, которые настраивает автор маршрута:

| Параметр | Смысл |
|---|---|
| `schema`, `kind`, `profile`, `id` | Версия `2`, вид `route` либо `bootstrap`, профиль и уникальный ID машины; должны совпадать с bundle. |
| `title` | Необязательное непустое название, до 200 символов. |
| `bootstrap` | У маршрута `required` по умолчанию или `skip`. `skip` убирает отдельный SCOUT, но не подготовку workspace и health стенда. |
| `entry` | ID первого исполняемого узла основной части; может отличаться от первого элемента `sequence.main`. |
| `sequence.main`, `sequence.tail` | Основной и завершающий порядок узлов для переходов и reset. У bootstrap вместо них `sequence.bootstrap`. |
| `nodes` | Описания узлов машины. Все исполняемые узлы должны быть достижимы от entry. |
| `escalation[].from` | ID исполняемого узла, которому разрешена эскалация. |
| `escalation[].allowedRoutes` | Непустой список разрешённых route ID для этого источника. |
| `escalation[].requiresHumanWhenPinned` | Признак обязательного решения человека при эскалации вручную закреплённого маршрута. |
| `loop.lead`, `loop.worker` | Необязательная пара ведущего и исполнителя. Вход — ведущий; исполнитель стоит перед ним в sequence. Бюджет кругов берётся из `PROFILE_LOOP_MAX_ROUNDS`, не из моделей. |

Поля узла:

| Параметр | Смысл и ограничения |
|---|---|
| `id`, `runKey` | ID узла и ключ роли. У исполняемого узла `id == runKey.toLowerCase()`; runKey выбирает политику исполнителя и модели. |
| `executor` | `agent` — ИИ, `command` — доверенная команда профиля, `gate` — решение человека, `status` — отображаемый статус. |
| `phase` | `bootstrap`, `main` или `tail`, согласованная с sequence. |
| `label`, `description` | Необязательные подпись и описание, каждое до 500 символов. |
| `emits` | Список ID дополнительных status-узлов, которыми владеет этот узел. Это не список исходов выполнения; исходы задаёт `on`. |
| `commandId` | Только у command: ID, который принимает `profile_route_command`; не shell-команда. |
| `key`, `owner` | Только у status: ключ статуса и узел-владелец, чьи события его обновляют. |
| `prompt.blocks[].file` | Файл блока промпта внутри bundle; отсутствующий или неиспользуемый файл отклоняется. |
| `prompt.blocks[].when.context`, `.equals` | Необязательное условие включения блока: путь в объявленном контексте и точное скалярное JSON-значение для сравнения. |
| `prompt.requiredContext` | Непустой список корневых секций контекста, которые нужны агенту, например `task`, `workspace`, `evidence`. |
| `policy.filesystem` | `state-only`, `workspace-write` или `transactional-write`: запись только результатов, работа с кодом либо контролируемая инструментация. |
| `policy.browser` | `forbid` по умолчанию либо `allow`. Разрешение браузера независимо от файловой политики. |
| `policy.timeoutClass` | Класс времени из таблицы выше; неизвестный класс запрещён. |
| `policy.budgetClass` | Необязательная метка класса бюджета. Текущая схема проверяет её формат; сама метка не вводит отдельного лимита runtime, не задаёт provider/model/effort и не подменяет timeout. |
| `fanout.mode` | `single` или `parallel`; parallel допускается только для agent с `state-only`. |
| `fanout.maxExecutors` | Целое 1..16; для single ровно 1, для parallel минимум 2. |
| `fanout.degrade` | `forbid` требует native fanout, `allow-single` допускает последовательный разбор зон. Для single всегда `forbid`. |
| `retry.noResult` | Число повторов без принятого результата, 0..10. |
| `retry.productFailure` | Повторы самого узла при продуктовом отказе, 0..10. Положительное число несовместимо с возвратом failed к автору: сначала требуется исправить вход проверки. |
| `retry.providerFailure.attempts` | Повторы отказа исполнителя, 0..10. |
| `retry.providerFailure.strategy` | `none`, `same-runner` или `runner-failover`; `none` эквивалентен нулю attempts. У command все retry нулевые. |
| `on.<исход>` | Полная карта переходов: у agent/command `done`, `skipped`, `failed`, `exhausted`; у gate `approved`, `rejected`. Один переход содержит только один вид действия из таблицы ниже. |
| `onFailure.<владелец>` | Необязательные переходы typed failed для всех пяти владельцев: `build`, `tests`, `environment`, `plan`, `human`. Без них действует `on.failed`. |

| Поле перехода | Действие |
|---|---|
| `next` | Перейти вперёд к указанному узлу. |
| `rewind`, `reset` | Вернуться к узлу и сбросить весь непрерывный участок от цели до текущего узла включительно. |
| `stop` | Остановиться: `human`, `failed` или `done`. |
| `escalate.routes` | Разрешённые route ID для эскалации, объявленные машиной. |

`ship` — канонический завершающий узел публикации. Без него маршрут получает
`delivery.mode=disabled` и не получает delivery actions/targets. Реальное действие
публикации реализует профиль в пределах разрешений: наличие `ship` само по себе не
доказывает, что проект делает push или PR.

Полная семантика bundle, каталога, контекста и переходов — в
[документации движка](../../engine/ENGINE.md#бандлы-маршрутов-v2), работа с черновиком —
в [руководстве редактора](../guide/routes.md).

### `routes/editor-capabilities.json`

Декларация — данные, редактор не исполняет её содержимое. Файл необязателен: без него
остаются встроенные секции контекста и agent-маршруты, но собственные command ID не
проходят редакторскую публикацию.

| Поле | Смысл |
|---|---|
| `schema` | Версия декларации, сейчас `1`. |
| `commands[].id` | ID разрешённой команды; тот же ID обязан проверять trusted hook. |
| `commands[].label` | Понятное человеку название команды. |
| `commands[].filesystem` | Допустимые файловые политики этой команды: `state-only` и/или `workspace-write`. |
| `contextSections[].id` | ID дополнительной секции контекста профиля. |
| `contextSections[].label` | Понятное человеку название секции. |

Лишние поля, shell, аргументы команд и секреты запрещены. Декларация подтверждает
допустимость структуры, а не успешность реальной проверки проекта.

## Изменения профиля и проверки

| Изменение | Как применяется |
|---|---|
| Промпт, topology, ворота или политика узла | Проверка и публикация новой версии; начатая попытка сохраняет прежний bundle. |
| Исполнитель, модель, effort | CLI-запись `runners.env`, metadata-only preflight; политика читается при следующем решении о запуске. |
| Репозитории, режим, ветки, стенд, порты, ресурсы или `profile_project_context` | Эти данные закреплены в попытке. Дрейф блокирует resume; публикация маршрута их не перепривязывает. |
| `PROFILE_LOOP_MAX_ROUNDS` | Можно поднять для продолжения остановки на потолке; resume без подъёма не запускает ещё один круг. |
| Debug-профиль | Отдельная настройка `factory profile <PROFILE> debug ...`, не runner config. Не меняет routing revision и права агента. |

Общий безопасный порядок: проверить исходники и промпты → опубликовать во временное
хранилище и перечитать → проверить профиль и runner readiness → переключить live current
через CAS → отдельным последним действием включить `route-v2` у нового профиля.

```bash
engine/bin/factory-check <PROFILE> --quick
RUN_HOST_PREFLIGHT=1 engine/bin/factory-check <PROFILE> --host-preflight
```

Обе проверки обходятся без model prompt. `--quick` не доказывает, что lifecycle умеет
поднять живую песочницу; реальные проверки стенда выполняются отдельно на ресурсах пробы.

Источники справочника: `engine/lib/profile-config.sh`, `routing.sh`, `multi-runner.sh`,
`dispatcher.sh`, `core.sh`, `route_model.py`, `dashboard.py`, `engine/bin/factory`,
`factory-check`, `server/src/lib/analysis/profile.ts`, `analysis/routePolicy.ts`,
`runtimeLayout.ts`, `factoryGraph.ts`, `profiles.ts` и `server/src/modules/factory/index.ts`.
