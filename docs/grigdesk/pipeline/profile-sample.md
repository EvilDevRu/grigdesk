# Образец профиля с тремя маршрутами

Общий ресурс лежит в `server/seed/pipeline-sample/` и по тому же адресу внутри комплекта
сервера. `config.pipelineSampleDir` получает его от `RuntimePaths.root`, без зависимости
от cwd, папки данных и каталога установки. На старте сервер профиль не устанавливает.
В комплект не попадают пользовательские конфигурации из `profiles/`.

Решение задачи №93033: приняты короткий `debug` и сдача локальным `commit` по умолчанию.
Полного диагностического маршрута в образце нет; остальные способы сдачи выбираются
явно в описании проекта. Эти значения относятся к новым копиям образца, существующие
конфигурации машины не меняются.

## Общее и проектное

`profile/project.json` — единственный проектный ввод. Его закрытая схема версии 1 задаёт:

| Поле | Что заполнить |
| --- | --- |
| `id` | Имя нового локального каталога конфигурации. |
| `repositories` | `name`, абсолютный Git `source`, локальная `baseBranch`, `targetBranch`, относительный `productRules`. |
| `workspace` | `mode`, абсолютный отдельный `root`, явные команды `prepare` для isolated. |
| `checks` | Адаптеры `tests`, `style`, `build`; для каждого repo, argv и timeoutSeconds. |
| `stand` | `hasInterface`, frontendUrl/apiUrl, health-команды, entryInstructions. |
| `stack`, `guardrails` | Стек, правила и проектные запреты для typed context. |
| `permissions` | Дополнительные allow/deny; команды сдачи выдаются только SHIP. |
| `volatilePaths` | Только относительные untracked runtime-пути внутри своих repo. |
| `delivery` | strategy, remote и argv pullRequestCommand. |
| `executors` | author/reviewer: provider, точный model, effort, явный failover. |

Пути с пробелами, двоеточиями и другими неподдерживаемыми символами transport отвергаются.
Все репозитории и файлы правил должны существовать до настройки; команды не угадываются.
Хотя бы один адаптер тестов обязателен: `match` задаёт glob, `argv` содержит ровно один
`{files}`. Используйте безопасную обёртку проекта, ограничивающую память и охват тестов.
Стиль возвращает JSONL `{path,line,rule,message}`, `format` равен `jsonl`. Остальные группы
проверок могут быть пустыми. Команды — массивы аргументов, без shell, с timeoutSeconds.

`configure.py` создаёт настройки исполнителей через `factory profile … runner/model set`,
не пишет canonical env собственным форматом. Авторские роли: PLAN/TESTS/BUILD/REPRO/DIAGNOSE;
проверяющие: SKEPTIC/REVIEW/BROWSER/AUDIT/SHIP. Один поставщик поддерживается, у автора и
скептика должны различаться сочетания provider/model. Если доступна только одна модель,
настройка отказывает с диагностикой; другой поставщик рекомендуется, но не обязателен.

Инструкции этапов не содержат команд стека, локальных адресов и настроек исполнителей.
Hooks проецируют описание в поддержанный контракт; typed project содержит только
stack/guardrails, включая адрес описания, правил продукта и обёртки проверок.

## Режимы и приёмка

`isolated` готовит независимые Git-копии под `workspace.root/id/task/repo`, от заданной
локальной baseBranch, в ветке `task-<номер>`. Нет сети, hardlinks и автоматического стенда.
`stand-mode=none` закреплён в попытке, оба ключа портов существуют и пусты, services имеют
значение `unavailable`. Приёмка проекта без интерфейса выполняется командами.
BUILD получает services в контексте и видит отсутствие стенда до начала реализации.
`down.sh` снимает свою env-проекцию и сохраняет копии с локальными коммитами для человека.
Незавершённую или чужую папку helper не перезаписывает. Копии расходуют дисковое место;
после получения результата их удаляет владелец.

Если есть интерфейс, браузерная приёмка обязательна. Сочетание интерфейса и `isolated`
без стенда на приёмке останавливается у человека; configure предупреждает об этом заранее.
Для такого проекта выбирают `shared`: checkout и стенд заранее готовит владелец.
Начальный checkout должен быть чистым по index/tracked/untracked, игнорируемые runtime-файлы
не мешают. Ни up/down, ни prepare в shared не вызываются. Ветки каждого repo закрепляются
по фактической текущей ветке; стенд и рабочие папки защищены общей durable lease.

Текущий transport принимает только оба адреса `http://<host>:<port>` с одним хостом,
портами 1000..65535, без пути, query и fragment. HTTPS и URL без порта отвергаются.
Это ограничение распространяется и на shared без интерфейса. Health только проверяет
объявленные команды и не управляет чужими процессами.

Приёмка всех маршрутов проверяет постановку целиком, критерии и решения, соседей и режимы.
В `t<номер>.acceptance.json` требуется schema=1, taskId, attemptId, runId, mode и запись
criteria `{criterion,status:"passed",evidence:<абсолютный файл>}` для каждого критерия.
При пустом списке критериев нужна запись для каждого пункта постановки по
[правилам разбиения и проверок](profile-sample-checks.md). Для mode=browser нужны также
url заданного стенда и browserEvidence. Пропуск и недоступный обязательный стенд не дают done.
В small действует предел 15 минут, после него непроверенные пункты передаются человеку.
Вся постановка обязательна; дополнительный обзор ограничен одной мобильной шириной,
консолью, журналом и ближайшим соседом. Границы мелких исправлений ревью и сдачи описаны
в [контракте короткого маршрута и сдачи](profile-sample-boundaries.md).

## Проверка и сдача

VERIFY/RECHECK — command-узлы. Diff включает коммиты задачи, index, рабочие и новые файлы;
удалённые тесты не запускаются. Стиль спрашивает только за добавленные строки. Исходная
ревизия и bytes TESTS закрепляются хостом в artifacts точной попытки. Неверный manifest
возвращается TESTS, изменение закреплённых тестов после сдачи — BUILD. RECHECK замечает
новые правки REVIEW; при неизменном дереве использует проверенный снимок той же попытки.
Отказы сборки сравниваются с отдельной копией базы без отката рабочего дерева.

Способ сдачи закрепляется в immutable `delivery.tsv` при старте и переживает изменение
описания на resume. `commit` разрешает только commit, `merge` — commit+merge,
`pull-request` — commit+push+pull-request. Старые профили без нового hook сохраняют прежний
контракт. Нет ship — нет действий сдачи. Human/environment всегда останавливают у человека.

SHIP принимает только утверждённую человеком работу, точные permissions и поимённые пути.
Каталоги отвергаются, Git-шаблоны не разворачиваются; удалённый tracked-файл можно назвать явно.
В shared `pull-request` отказывает до stage, commit или push: этот режим использует рабочую
ветку владельца. Для ветки и PR нужен isolated; образец сам ветку в shared не создаёт.
`commit` оставляет ветку в сохранённой копии: в source эта ветка автоматически не появляется.
`merge` переносит объекты локально и делает fast-forward рабочей ветки без PR; грязный target
или необходимость конфликтного слияния требуют человека. `pull-request` использует remote
исходного проекта и объявленную argv-команду PR, без force и комментариев в трекер.
PR-команда может использовать аргументы `{branch}`, `{target}`, `{repo}` и должна находить
уже созданный PR после прерванного вызова. Завершённые действия записываются хостовым снимком;
обычный повтор их не дублирует. Отчёт сообщает коммит, ветку и сохранённую копию.

## Как завести профиль вручную

1. Скопировать `server/seed/pipeline-sample/profile/` в новый локальный `profiles/<name>/`.
   Оставить в graph.json `capabilities: []`; отредактировать только project.json.
2. Установить `FACTORY_PROFILES_DIR`, если конфигурации лежат вне обычного каталога движка.
   Выполнить `python3 <profile-dir>/configure.py --factory <absolute-engine-bin-factory>`.
   Ошибка описания возвращает 64 и называет project.json; source profile.sh не запускает команды проекта.
3. Задать абсолютный `GRIGDESK_ROUTES_KIT`: в исходниках
   `server/src/modules/routes/publishKit.ts`, в комплекте
   `server/runtime/helpers/routes-publish-kit.mjs`. Использовать Node из runtime комплекта.
4. Проверить `node <profile-dir>/routes/publish.mjs --validate`; прогнать
   `<profile-dir>/routes/definition.test.mjs` безопасной тестовой обёрткой проекта.
5. Опубликовать сначала в пустой временный store:
   `node <profile-dir>/routes/publish.mjs --publish --base-dir <absolute-temp-store> --expected-catalog-hash null`.
   Publisher валидирует три маршрута и bootstrap, затем перечитывает каждый hash.
6. Временно включить capability `route-v2` в проверочной копии. Выполнить
   `engine/bin/factory-check <name> --quick` и
   `engine/bin/factory check --profile <name> --route <small|feature|debug> --routes-dir <absolute-temp-store>`
   отдельно для каждого маршрута. Рендерить agent-узлы с полным synthetic typed context,
   переходы command/gate проверять через factory-route describe-route/transition.
7. После offline-проверок опубликовать в выбранный store с фактическим expected catalog hash
   (null только для нового каталога), перечитать current и включить capability в рабочем профиле последней.
   Пройти metadata-only host preflight; live-пилот требует отдельного разрешения человека.

Маршруты уже содержат bootstrap/scout.json для валидности каталога, но каждый объявляет
bootstrap=skip. Пункты постановки и карту пишет первый агент PLAN/BUILD/REPRO.
Схемы, тест определений и hooks входят в ресурс, существующие профили на него не переводятся.
