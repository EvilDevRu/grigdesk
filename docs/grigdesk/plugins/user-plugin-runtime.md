# Runtime пользовательского плагина и долгие задания

Оконный модуль `api: 2` описан отдельно: [модульные панели](plugin-ui-modules.md).
Серверные lifecycle и prefix сохраняют прежний контракт; установка api2 из Git не добавлена.

Проверено по реализации реестра и загрузчика. Пользовательский плагин — доверенный локальный
код, исполняющийся с правами процесса GrigDesk; это не изолированный runtime расширений ИИ.

## Загрузка и интерфейс

[Конфигурация](../../../server/src/config.ts) берёт каталог из `GRIGDESK_PLUGINS_DIR`,
иначе использует `<папка данных>/plugins/`. [Scanner](../../../server/src/lib/pluginsRegistry.ts)
читает `<id>/plugin.json`, единственный вход `server.js` или `server.ts` и страницу `web/index.html`.
Если есть оба входа, карточка сохраняется с `serverError`, код и страница не подключаются.
ID манифеста обязан совпадать с именем каталога. Поле `web` — относительный каталог;
`api: 1` — поддерживаемая версия серверного контракта.

[Загрузчик](../../../server/src/modules/plugins/index.ts) сканирует каталог при
старте, регистрирует только включённые пользовательские модули и страницы. В default-export
серверного входа передаются `config`, `prefs`, `plugin`, prefix `/api/ext/<id>`,
mutable `lifecycle`, настроенный `dataDir` и [набор ядра `core`](server-core-api.md).
Контракт остановки для замены и данных —
[в отдельном документе](plugin-install-runtime.md).
Installer refresh перечитывает каталог целиком без нового import runtime.
Обычный Fastify plugin должен сохранять encapsulation; не снимать её через
`fastify-plugin`. Исполняемый доверенный модуль не является границей безопасности ОС.

Страница доступна под `/api/ext/<id>/web/`, оболочка — `/ext/<id>`.
Same-origin iframe использует сессию GrigDesk; Vue-компоненты и controls основного приложения
внутрь не передаются. Подробнее — [контракт страницы](../guide/plugins.md).
Для прогресса самостоятельной страницы достаточно опроса своего API; отдельный SSE не нужен.

Пользовательский plugin по умолчанию выключен. Функция `isEnabled` поддерживает
`defaultEnabled`, однако нынешний `scanUserPlugins` не переносит это поле из JSON
в пользовательский manifest. Поэтому автору user plugin нельзя рассчитывать на него
как на способ автоматического включения.

После установки через git каталог перечитывается сразу: человек включает новый id
и один раз перезапускает GrigDesk для подключения кода. Ручная первая установка папки
по-прежнему требует сначала перезапуска для обнаружения manifest, затем включения и
второго перезапуска для загрузки. Если manifest уже обнаружен, достаточно последнего
перезапуска. Версии, recovery и откат описаны в [контракте установки](user-plugin-install.md). Правка только статических файлов страницы видна при обновлении.
Агент из чата сервер самостоятельно не перезапускает.

## Авторизация и настройки

[Общий auth guard](../../../server/src/plugins/auth.ts) закрывает API, включая страницы
расширений, и устанавливает `request.authKind`: session, cli или internal.
Задача плагина, допускающая действия только человека, должна дополнительно проверять
`authKind === "session"`; один общий guard такого ограничения не задаёт.

Существуют `GET /api/plugins`, `POST /api/plugins/:id/toggle` и
`PUT /api/plugins/:id/settings`. Переданные `values` **заменяют** значения настроек
плагина; отсутствие `values` сохраняет их. Credentials не следует хранить в обычных
plugin settings: значения возвращаются в каталоге API.

У загруженного плагина общий admission gate сразу запрещает новые API/static/upgrade запросы
после выключения: 404 `plugin_disabled`. Повторное включение открывает тот же runtime.
Уже принятые streams/WS не обрываются, код не выгружается. Необязательные lifecycle
`onDisable`/`onEnable` уведомляют о реальной смене, но не управляют внешними процессами
автоматически. Для подготовки настроек и тумблера служит `prepareChange` с таймаутом и откатом;
контракт и ограничение вечной подготовки — [серверный набор](server-core-api.md).

Выключенный при boot плагин не исполняется: его первое включение требует перезапуска,
отмена включения снимает ожидание. GET и toggle возвращают актуальный `needsRestart`;
у здорового загруженного плагина он false. Через ручную правку prefs пользовательский gate
меняется лишь после рестарта; живое переключение выполняется через API.

## Песочницы и длительное выполнение

[API песочниц](../../../server/src/modules/sandboxes/index.ts) требует сессию также для чтения.
Его обзор описан [общим контрактом](../../../shared/plugins/sandboxes/sandboxContracts.ts). Открытый порт
не доказывает готовность данных или соответствие кода ожидаемой версии.

[Activity guard](../../../server/src/lib/sandboxes/activityGuard.ts) использует настоящий
kernel flock на `stateDir/.sandbox-activity/t<task>.lock`: lifecycle берёт exclusive,
Showcase и действия профиля — shared. Два shared читателя могут идти одновременно;
это не готовая очередь последовательных нагрузочных измерений.
Профильные процессы [наследуют fd](../../../server/src/lib/sandboxes/service.ts) lease,
а [kernelLock](../../../server/src/lib/kernelLock.ts) проверяет inode. Файл lock не удаляют.

Эта гарантия относится к участникам протокола. Прямой скрипт профиля, наливка данных
или внешний измеритель не становятся участниками автоматически: перед обещанием взаимного
исключения нужно проверить их код и тестировать оба направления блокировки.
`orch.lock` принадлежит другому протоколу.

Загрузчик пользовательского плагина не предоставляет готовую очередь, отмену,
восстановление задания или реестр его артефактов. Для длительного измерителя это отдельный
контракт самого инструмента: самостоятельный процесс, состояние на диске, адресная отмена
своих ресурсов и проверка identity при восстановлении. Наличие отчёта либо PID не является
доказательством успешного завершения. Артефакты по правилам проекта хранятся в папке
артефактов `~/.grigdesk/artifacts/`; доступ к ним должен оставаться авторизованным.
