# Установка плагина с модулем интерфейса

Git installer принимает числовые `api: 1` и `api: 2`; отсутствие `api` означает прежний
формат. Api2 без `webModule` устанавливается как обычный плагин. Api1 игнорирует
`webModule`, неизвестные поля внутри объявления api2 не отвергаются.

## Проверка и доверие

Установка использует тот же `resolvePluginWebModule`, что загрузчик, но ошибка
объявления завершает подготовку кодом `manifest_invalid` с понятным пояснением.
Мягкий runtime scan по-прежнему пишет предупреждение и пропускает неверный модуль.
Установщик не импортирует код плагина.

`dir` — собственный подкаталог пакета, `entry` — готовый `.js` или `.mjs`.
CSS и переводы ru/en необязательны; их пути считаются от `dir`. Все объявленные
ресурсы должны существовать и быть обычными файлами. Выход за пределы пакета,
ссылки, скрытые компоненты, URL-схемы, query и fragment запрещены.
Любой сегмент `node_modules` в известных путях модуля запрещён и после подготовки
npm. Зависимости рядом с модулем допустимы; исходные `node_modules` по-прежнему
отвергаются общей проверкой пакета до npm.

Предпросмотр сообщает: «Модуль интерфейса исполняется в главном окне GrigDesk с вашей
сессией и может обращаться к любому API GrigDesk.». Это обычная строка `warnings`,
как предупреждение о серверном коде; после повторного открытия она сохраняется.
Плагину нужно доверять. Модуль не получает изоляцию от главного окна.

В списке изменений все файлы новой и прежней папок модуля отмечаются как код,
исполняемый GrigDesk: JS, CSS, переводы и вспомогательные ресурсы. Это действует
также внутри `web/` и `docs/`, включая удалённые файлы при переносе модуля.
Ручная правка любого файла обнаруживается общим payload digest, блокирует обычное
обновление и сохраняется в резерв при явной принудительной замене.

## Обновление, откат и совместимость

Обновление и откат используют прежние snapshots и runtime lease. После применения
нужно перезапустить GrigDesk и перезагрузить каждое подключённое окно, включая
телефон: импортированный ESM остаётся в кеше окна. Автоматической подмены модуля нет.
Итоги обновления и отката напоминают об обоих действиях на русском и английском.

`webModuleDir` существует только во внутреннем результате проверки пакета.
Схема сохранённого состояния, ключи preview и перечень кодов ошибок не расширены:
состояние установщика остаётся читаемым прежней версией приложения.

## Публикация каталога

Решение задачи 93036: публикация разделяется на два канала; старый каталог сохраняет
прежние api1-релизы. Изменение сайта выполняется отдельно, этот контракт описывает
поддержку со стороны GrigDesk.

На каждой площадке `/api/plugins/v1/index.json` и карточки `<id>.json` содержат
только api1: и `latest`, и все `versions`. Старший api2 не вытесняет прежний api1
того же плагина. `/api/plugins/v2/index.json` и его карточки содержат api1/2,
сохраняя форму JSON и `schemaVersion: 1`. V2 — надмножество v1; пустую заглушку
v2 не публикуют, пока v1 непуст: корректный пустой ответ считается успешным.
Неподдерживаемый api отвергает весь документ; следующее повышение api требует
отдельного канала, чтобы не ломать прежних читателей.

Новое окно запрашивает локальный каталог с `api=2`. Новый сервер пробует основной
v2, резервный v2, основной v1 и резервный v1; старые локальные запросы без `api`
читают только v1. Кеши и карточки режимов независимы. Со старым сервером только
HTTP 400 на первом новом запросе выбирает прежний режим до закрытия store;
сеть, ошибки авторизации и повреждённый JSON не вызывают понижения.

Одна попытка источника занимает до пяти секунд: modern index — до двадцати,
ожидание окна — двадцать пять. Legacy окно ждёт пятнадцать секунд; общий deadline
карточки остаётся двенадцать секунд на сервере и пятнадцать в окне. При fallback
карточки зеркало обязано вернуть тот же полный снимок индекса, иначе возникает 409.

[выбор источника каталога](catalog-failover.md) и [runtime модуля](plugin-ui-modules.md).
