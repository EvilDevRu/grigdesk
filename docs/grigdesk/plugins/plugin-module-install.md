# Установка плагина с модулем интерфейса

Git installer принимает единый [манифест v1](manifest-v1.md) с api=1,
entrypoints и contributes. Сервер и модуль интерфейса независимы и необязательны.
Старая структура получает manifest_incompatible до npm, неизвестное поколение — api_unsupported.

## Проверка и доверие

Установка использует тот же `resolvePluginWebModule`, что загрузчик, но ошибка
объявления завершает подготовку кодом `manifest_invalid` с понятным пояснением.
Scanner сохраняет неверный пакет как несовместимую карточку с причиной.
Подготовка установщика не импортирует код плагина. После подтверждённого применения
включённая версия загружается управляемым runtime.

`dir` — собственный подкаталог пакета, `entry` — готовый `.js` или `.mjs`.
CSS и переводы ru/en необязательны; их пути считаются от `dir`. Все объявленные
ресурсы должны существовать и быть обычными файлами. Выход за пределы пакета,
ссылки, скрытые компоненты, URL-схемы, query и fragment запрещены.
Любой сегмент `node_modules` в известных путях модуля запрещён и после подготовки
npm. Зависимости рядом с модулем допустимы; исходные `node_modules` по-прежнему
отвергаются общей проверкой пакета до npm.

Предпросмотр сообщает: «Модуль интерфейса исполняется в главном окне GrigDesk с вашей
сессией и может обращаться к любому API GrigDesk.». Это обычная строка `warnings`,
как предупреждение о серверном коде; после повторного открытия она сохраняется.
Плагину нужно доверять. Модуль не получает изоляцию от главного окна.

В списке изменений все файлы новой и прежней папок модуля отмечаются как код,
исполняемый GrigDesk: JS, CSS, переводы и вспомогательные ресурсы. Это действует
также внутри `docs/`, включая удалённые файлы при переносе модуля.
Полный [список чувствительных файлов](plugin-sensitive-files.md) учитывает также
объявленные серверные входы и метаданные пакета; обычные файлы вне этих зон не отмечаются.
Ручная правка любого файла обнаруживается общим payload digest, блокирует обычное
обновление и сохраняется в резерв при явной принудительной замене.

## Обновление, откат и совместимость

Обновление и откат используют прежние snapshots и runtime lease. После применения
[управляемый runtime](plugin-hot-runtime.md) подключает новый сервер и поколение адресов
модуля. Подключённые окна получают свежий каталог через общий SSE и заменяют панель.
Перезапуск GrigDesk или обновление окна для обычной замены не требуются.

`webModuleDir` существует только во внутреннем результате проверки пакета.
Схема состояния и ключи preview сохраняются. Старые disk-коды ошибок читаются как диагностика.
Откат проверяет контракт кандидата до lease; несовместимый backup сохраняется без исполнения.

## Публикация каталога

Каталог сохраняет schemaVersion=1, историю api1/2 и прежние адреса v1.
Совместимые исполняемые версии выбираются по api=1, installer проверяет структуру пакета.
Icon/gallery передаются только в detail; сайт обновляется отдельно.

Окно запрашивает локальные `/api/plugin-catalog` и `/api/plugin-catalog/:id`
без query `api`. Сервер читает основной, резервный и локальный сайты по одним
путям v1. Индекс и карточки имеют общий кеш для всех потребителей.

Одна попытка источника занимает до пяти секунд: индекс — до пятнадцати,
ожидание окна — двадцать. Общий deadline карточки — двенадцать секунд на сервере
и пятнадцать в окне. При fallback карточки зеркало обязано вернуть тот же полный
снимок индекса, иначе возникает 409.

См. [единый каталог](catalog-schema.md), [проверку пакета](user-plugin-package-validation.md),
[выбор источника каталога](catalog-failover.md) и [runtime модуля](plugin-ui-modules.md).
