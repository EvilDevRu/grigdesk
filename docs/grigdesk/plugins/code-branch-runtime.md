# Переключение ветки единственного стенда

«Код» управляет одним стендом в основной папке выбранного репозитория проекта.
В этой папке одновременно активна одна ветка. Worktree не создаётся; существующий
селектор рабочей копии сохраняет просмотр отдельных деревьев. У проекта с несколькими
репозиториями действие затрагивает выбранный репозиторий, а не переключает все разом.

## Выбор и настройки

Кнопка ветки в шапке основной копии открывает `CodeBranchControl.vue`: поиск в списке
локальных и remote-tracking веток, «Переключить и собрать», возврат на настраиваемую
ветку (по умолчанию `dev`), фактический checkout, задание и хвост журнала до 64 КиБ.
Символические remote HEAD исключены; полный ref различает одинаковые имена remotes.
Список использует уже известные Git refs, сеть сам не обновляет. Для свежих refs
нужно предварительно выполнить fetch существующей кнопкой «Проверить удалённый репозиторий».

Команды задаются в этом же диалоге отдельно для основной папки репозитория:
`stop`, необязательный `prepare`, `build`, `start`, `check`, необязательный HTTP(S) `url`
и `returnBranch`. Настройки лежат вне checkout в `<dataStateDir>/code-branches/<hash>/`.
Если папка данных находится внутри checkout, возможность отклоняется. Сохранение
команд ничего не запускает. Текущий worker использует снимок настроек своего задания.
Команды не извлекаются из проверяемой ветки или файлов репозитория.

Команды запускаются через `bash --noprofile --norc -c` в основной папке, получают
`GRIGDESK_BRANCH` и `GRIGDESK_COMMIT`, должны завершиться за 20 минут каждая.
Обязательны stop/build/start/check; `start` должен запустить фоновой процесс и выйти
(Docker Compose, менеджер процессов или явный фоновый запуск). `check` сам дожидается
готовности и возвращает 0. URL не служит проверкой готовности. Ссылка приложения
появляется после успеха, если фактические ветка и коммит всё ещё совпадают с заданием;
URL закреплён за настройками именно этого запуска.

## Допуск и последовательность

`GET …/branches`, `POST …/branch-settings`, `POST …/switch-branch` используют общий auth,
живой plugin gate и дополнительно требуют `authKind: session`. CLI-токен не получает
доступ к командам и их выводу. Рабочая папка проверяется по каталогу проекта и
`git worktree list`; переключение возможно только для основного дерева.

Запуск подтверждается общим диалогом с конкретной папкой, веткой и коммитом.
POST несёт полный ref, показанный target SHA, исходный HEAD и `confirmed: true`.
Перед внешними эффектами сервер проверяет:

- отсутствие активного задания и других Git-мутаций этой папки;
- отсутствие принятого/активного/фонового хода чата в пересекающейся рабочей области;
- обычную ветку HEAD, чистые индекс, tracked и untracked-файлы, отсутствие merge/rebase;
- существование целевого ref и неизменность подтверждённых коммитов;
- отсутствие другой worktree на целевой ветке и коллизии локального имени remote-ветки.

Worker повторяет проверку перед `stop` и перед checkout. Дальше этапы идут строго:
stop → switch → prepare → build → start → check. Локальная ветка открывается через
`git switch --no-guess`, remote-ветка создаётся локально с tracking. Hooks и рекурсивная
обработка submodules отключены, игнорируемые файлы защищены `--no-overwrite-ignore`.
Ни force, ни stash, ни reset здесь нет. Возврат на `dev` проходит те же этапы;
если локальной ветки возврата нет, допустима единственная совпадающая remote-ветка.

При неуспехе следующие этапы не выполняются: текущий checkout и изменения остаются
на достигнутом шаге. Автоматический откат не запускается. После отказа сборки приложение
может оставаться остановленным; человек читает журнал, устраняет причину и повторяет
запуск либо возвращается на базовую ветку.

## Жизненный цикл и агенты

Сервер фиксирует вход задания в папке данных и копирует туда standalone worker
из helper `code-branch-worker`. Его runtime imports — только Node built-ins:
checkout может удалить исходную реализацию без потери следующих этапов.
Worker наследует fd kernel lock; обычные Git-мутации получают `git_busy` до его конца.
Файл замка не удаляется. Новый ход чата проверяет занятую папку до запуска исполнителя;
уже принятые ходы мешают началу переключения. Внешние агенты и ручные Git-команды
за пределами GrigDesk общему lock не подчиняются; worker перепроверяет refs и итоговый HEAD.

При доступном пользовательском systemd worker запускается в отдельном scope, чтобы
остановка cgroup стенда не убила его. Без user manager обычный проект использует
detached-процесс; переключение checkout самого работающего GrigDesk отклоняется
до stop. Команды всё равно должны корректно управлять своим конкретным стендом.
Во время перезапуска самого GrigDesk UI теряет соединение до подъёма новой версии.
Старая проверяемая ветка может ещё не содержать API просмотра задания.

Журнал задания пишет только worker через atomic rename. Сервер читает PID/starttime/cmdline
владельца и kernel lock: умерший исполнитель становится отказом вместо вечного progress.
Закрытие диалога не отменяет запуск; polling продолжает читать его итог, пока компонент
жив. Повторное открытие читает текущее задание с сервера. После конца панель перечитывает
код и Git. Собственного EventSource нет.

## Проверка

`tests/server/code-branches.test.js` выполняет настоящие Git-switch на временных репозиториях
с конечными командами-двойниками: этапы, возврат, remote tracking, грязный checkout,
занятая ветка, агент, stale SHA, отказ сборки и lock. Сценарии нового хода и определения
папки активного агента — в `chat-workdir-transition.test.js`; диалог, подтверждение,
отмена, возврат и сохранение команд — в `code-view.component.test.js`.
Реальные сборки, Docker и перезапуск работающего GrigDesk этой проверкой не выполняются.
Запуск через настоящий user scope и упакованный helper требует отдельной ручной проверки.
