# Установка пользовательских плагинов из git

В «Настройки → Плагины» общая кнопка «Установить из Git…» принимает адрес репозитория.
Каталог и установленные находятся во вкладках одного раздела; старый адрес установки
открывает общий раздел без автоматического запуска диалога.
Человек выбирает версию, скачивает и проверяет пакет, читает карточку подтверждения
и отдельно применяет установку. Подготовка не импортирует серверный код или модуль интерфейса.
Код установленного плагина выполняется внутри GrigDesk с его правами; источник
должен быть доверенным. Это не изоляция расширения средствами ОС.

Новый id сразу появляется в списке установленных выключенным. Настройки существующего id
сохраняются. Первое включение, обновление и откат подключают новый сервер и панель
без перезапуска GrigDesk или окон; [контракт runtime](plugin-hot-runtime.md).
Рабочая установленная копия не является папкой разработки: правки
делают в репозитории плагина и выпускают следующую версию.

## Источник и версии

Поддержаны `https://`, `ssh://`, короткий SSH-адрес `git@хост:путь` и абсолютный
`file:///путь`. Адрес ограничен 512 символами; credentials в HTTPS URL, query,
fragment, управляющие символы, пустой путь и неподдерживаемые протоколы запрещены.
Git использует заранее настроенный вход владельца машины. Окно установки не
спрашивает пароль и не передаёт credentials браузеру.

Для GitHub по HTTPS заранее выполните `gh auth login` и `gh auth setup-git`:
одного входа в CLI недостаточно без credential helper. Для SSH нужен ключ,
доступный без запроса пароля, и уже доверенный host key. Проверка host key
не отключается; неизвестный хост требует отдельной настройки владельцем.

Выбор — стабильные теги `vX.Y.Z`, простые или аннотированные; предпочтителен
аннотированный тег. Версия в корневом `plugin.json` должна совпадать с тегом.
Pre-release и произвольные branches не являются версиями установки. Checkout
выполняется по полному SHA выбранного тега, а не по его изменяемому имени.
Карточка показывает kind/URL источника, тег и полный SHA. Выбор из каталога передаёт
expectedId и expectedSha; ожидаемый SHA допускается только вместе с version и проверяется
до fetch/npm. Несовпадение даёт checkout_mismatch. Готовый пакет вне свежего каталога
получает предупреждение перед явным apply; сбой проверки источника обозначается отдельно.
Происхождение установленных определяется по ID и source вместе, без догадки по имени.
Подробности — [каталог и установка](plugin-marketplace.md).

Git запускается с закрытой конфигурацией. Hooks, templates, внешние filters,
submodules/gitlinks, symlinks, спецфайлы и Git LFS pointers в пакете запрещены.
Installed metadata проверяется перед Git inspection; неизвестная конфигурация
не становится разрешением запустить внешнюю программу. Подробности —
[политика источника](user-plugin-git-source.md).

## Пакет и зависимости

Корневой `plugin.json` обязателен. Id должен быть безопасным, не совпадать с
SYSTEM id и при привязке совпадать с id выбранной карточки. `api`, если указан,
равен числу 1 или 2. `minGrigDeskVersion` — стабильная версия `X.Y.Z`, сравниваемая с `VERSION`
GrigDesk. Серверный вход необязателен: ровно один `server.js` или `server.ts`.
Оба файла дают `manifest_invalid` с понятным объяснением; TypeScript использует native
стирание типов Node и явные расширения imports. `web` — относительный каталог с `index.html`.

Api2 может объявить `webModule`: существующая строгая проверка путей и ресурсов
при ошибке отказывает с `manifest_invalid`. Ресурсы внутри `node_modules` запрещены.
Api2 без модуля допустим, api1 игнорирует это поле. Предпросмотр предупреждает о
главном окне, сессии человека и доступе к любому API; файлы новой и прежней папок
модуля помечаются как исполняемый код. Подробности — [установка api2](plugin-module-install.md).

До npm проверяется дерево: максимум 5000 файлов, 50 МиБ содержимого и 64 КиБ
манифеста. Переходы по ссылкам, включая предков корня, не допускаются. После npm
допустимы только известные generated каталоги и проверенные внутренние ссылки
зависимостей. Payload digest учитывает пути, тип, executable bit и содержимое,
включая подготовленные зависимости; корневая `.git` проверяется отдельно.

`install.npm` — массив относительных каталогов с `package.json` и
`package-lock.json`; `"."` обозначает корень. При отсутствии поля корневой lockfile
выбирает корень автоматически. Каждый выбранный каталог требует lockfile.
Runtime dependencies корневого package.json требуют включения корня в установку;
пустой `install.npm` не обходит эту проверку.
JSON package/lock ограничен 2 МиБ. Поддержаны lockfile v2/v3
с integrity и HTTPS tarballs только `registry.npmjs.org`.

Проверяются dependencies, devDependencies, optionalDependencies и peerDependencies
всего graph. Не поддержаны Git/URL/file dependencies, links, workspaces,
shrinkwrap и привезённые `.npmrc`. Обычные registry версии и диапазоны допустимы.
Npm ci устанавливает production graph с `omit=dev`, `ignore-scripts`, без audit/fund.
Trusted Node/npm, отдельные пустые configs, prefix, cache и собранный заново env
закрывают выбор executable и project/parent config. Один `ignore-scripts` этой
изоляции не обеспечивает. Подготовка повторно проверяет пакет перед ready.
Реальный offline npm и marker controls описаны в
[контракте npm](user-plugin-npm-state.md).

Подготовка ограничена 20 минутами, общим staging budget 1 ГиБ и минимумом 256 МиБ
свободного места. Budget проверяется во время команд и между шагами; это мягкий
предел, допускающий превышение между замерами, а не квота ОС. Вывод команд имеет
bounded tails; обрезанный structured Git output вызывает отказ, а не пустой diff.

## Задание, подтверждение и неизвестный исход

Изменяющее задание одно на installer: running → ready → applying → done.
Для загруженного legacy-плагина после подтверждения возможен `awaiting_restart`:
[замена при следующем запуске](plugin-update-on-restart.md) без выключения и повторного включения.
Другие итоги — failed, cancelled, interrupted и recovery_required.
Ready ещё не меняет installed tree. Карточка содержит warnings, признак замены
managed/manual копии и ограниченную историю: до 50 коммитов и 200 файлов с
явным truncated. Sensitive files — эвристическая подсказка о сервере/зависимостях.
Процент измеряется только во время Git fetch; npm и apply показываются без процента.

Apply использует job id и reviewToken. Перед эффектами повторно проверяются
baseline revision, current/previous, source metadata и полный подготовленный
payload. Изменившиеся файлы или исходник дают безопасный отказ до замены.
Повтор уже законченного apply с исходной capability возвращает тот же результат.

Обрыв HTTP или 5xx не доказывает отмену операции. Браузер уточняет исход по
исходному job id, даже если current уже относится к другой операции. Он не
отправляет apply автоматически повторно. История хранит последние 32 terminal
summaries; вытесненный id даёт 404 и видимое сообщение о неизвестном результате.
Закрытие диалога active/ready не отменяет работу. Непрочитанный terminal показывается
при повторном открытии; только явное закрытие результата отмечает его прочитанным.

Ошибка scanner refresh после commit не отменяет достоверный done. Каталог
сохраняет прежний снимок и отдельно публикует предупреждение. Следующий GET
повторяет refresh и загрузку включённой новой версии.

## Диск и восстановление

Все пути в таблице считаются от [папки данных](../server/data-home.md).

| Данные | Расположение по умолчанию |
|---|---|
| Installed пакет | `plugins/<id>/` |
| Подготовка | `plugins/.grigdesk-install/jobs/` |
| Intent и перемещения | `plugins/.grigdesk-install/transactions/` |
| Предыдущая версия | `plugins/.grigdesk-install/previous/<id>/` |
| Отложенная ручная копия | `plugins/.grigdesk-install/replaced/` |
| Рабочие данные плагина | `state/plugins/<id>/` |
| Durable installer state | `state/plugin-installs.json` |

`GRIGDESK_PLUGINS_DIR`, `GRIGDESK_PLUGINS_DATA_DIR` и
`GRIGDESK_PLUGIN_INSTALLS_STATE_PATH` меняют соответствующие пути. Корни должны
быть абсолютными, не пересекаться и иметь реальные предки без ссылок. User dataDir
создаётся с 0700 вне дерева установки и не переезжает при update/rollback.

Один kernel owner lock защищает installer. Worker registry публикует process
identity до разрешения executable. Supervisor находится вне target process group;
при аварии владельца он останавливает потомков. Startup сначала валидирует state,
останавливает подтверждённые workers, затем восстанавливает файловую транзакцию;
только после этого scanner/import может загрузить user plugins.

Immutable intent сохраняется до первого rename. Identity каталогов, а не одно
имя фазы, определяет восстановление. State с новой версией, done и rollback receipt
публикуются атомарно до cleanup. Записи и переименования синхронизируют файлы и
родительские каталоги. Close закрывает допуск, ждёт команды, reads, scanner refresh,
мутации и их записи; owner освобождается после окончания эффектов.

Неоднозначные копии, неизвестная worker identity и повреждённый state дают
recovery_required. Копии и intent сохраняются для разбора; блокируются затронутые
user ids, а при повреждении общего state — все user plugins. SYSTEM и ядро остаются
доступны. Recovery нельзя забыть кнопкой retry и начать новую замену поверх него.

Протестирована аварийная остановка процесса после файловых эффектов, durable commit
и потери ответа. Это граница process-crash. Исчезновение питания, повреждение диска
и произвольная внешняя порча не объявляются проверенным восстановлением. Детали —
[транзакция и recovery](user-plugin-apply-recovery.md) и
[boot](plugin-install-boot.md).

## Runtime и длительные работы

`server.js` или `server.ts` получает `options.dataDir`, mutable `options.lifecycle` и
[набор ядра `options.core`](server-core-api.md). Диагностический
`busyReason()` возвращает причину занятости или отсутствие причины. Он не
останавливает работу и не предоставляет право заменить папку.

`prepareReplace(signal)` обязан атомарно закрыть новый допуск плагина, остановить
и дождаться его фона/внешних CLI, затем вернуть удерживаемый lease с
`finish(outcome)`. `installed` удерживает остановку прежнего сервера до его закрытия, `reverted` возвращает
прежнюю работу, `blocked` сохраняет остановку. Abort/timeout не разрешает запустить
второй hook до cleanup; поздний lease получает reverted.

Ядро закрывает user admission и ждёт принятые HTTP streams/WebSockets до пяти секунд,
не обрывая их насильно. Busy/ошибка hook запрещает замену. Если prepareReplace отсутствует,
управляемый runtime закрывает свой Fastify и дожидается авторского onClose. Неудачный
import/register сохраняет резервное обновление при следующем запуске GrigDesk.
Даже неудачный import мог оставить timer/child и не считается выгруженным runtime.
После замены прежние routes/static отвечают 409 plugin_restart_required; во время
замены — plugin_replacing; при blocked — recovery_required. После успешного refresh
новый код подключается сразу. Подробнее — [runtime lease](plugin-install-runtime.md).

## Ручные правки и откат

LocalChanges запрещает обычное обновление. Явное «Отложить правки в резерв и поставить
версию начисто» сохраняет полную прежнюю копию под уникальным archiveKey без перезаписи;
результат содержит безопасный basename backupRef. Recovery использует то же имя.
Проверка включает код, стили и переводы модуля интерфейса.

Откат восстанавливает полный previous snapshot, включая источник, SHA, зависимости
и digest. Он проходит тот же runtime lease и preflight. Повреждённая previous
остаётся видимой с rollbackError и недоступной кнопкой. Подтверждение выполняется
через общий диалог. Браузер до POST сохраняет request UUID, expectedRevision и
expectedPreviousDigest. Replay после reload использует тот же body и durable receipt;
неизвестный исход не создаёт новый intent. После применения runtime и адреса поколения
оконного модуля обновляются автоматически, включая относительные ESM-зависимости.

## HTTP API

Все ручки находятся под общим auth guard. GET разрешены session/CLI/internal;
все POST, включая список версий и проверку обновлений, — только session, JSON
и same-origin при наличии Origin. Session cookie
доказывает способ входа, а не физический клик человека. Закрытые схемы запрещают
лишние поля и coercion; выходные DTO не содержат stderr, абсолютных рабочих путей
и credentials. Браузер валидирует unknown ответы перед публикацией capabilities.

| Метод и путь | Назначение |
|---|---|
| `POST /api/plugin-installs/versions` | Список тегов источника |
| `POST /api/plugin-installs/jobs` | Подготовить установку/привязку |
| `GET /api/plugin-installs/jobs/current` | Current job и отдельный recoveryError |
| `GET /api/plugin-installs/jobs/:jobId` | Исход конкретного задания |
| `POST /api/plugin-installs/jobs/:jobId/apply` | Подтвердить reviewToken |
| `POST /api/plugin-installs/jobs/:jobId/cancel` | Явно отменить подготовку/ready |
| `POST /api/plugin-installs/check` | Проверить обновления managed плагинов |
| `POST /api/plugin-installs/plugins/:id/update` | Подготовить обновление |
| `POST /api/plugin-installs/plugins/:id/rollback` | Откат с persisted request UUID |
| `GET /api/plugins` | Каталог и optional install; SYSTEM/manual — null |

Автоматических проверок обновлений, удаления плагина, кнопки перезапуска и
GitHub-надстройки нет. Установка не управляет разработкой или публикацией репозитория.
Проверки охватывают реальные Git/npm, native process-crash, HTTP streams/WebSockets,
конкурентные операции и браузерные сценарии; [контракт интерфейса](../web/plugin-install-ui.md).
