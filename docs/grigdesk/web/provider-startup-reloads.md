# Повторное чтение исполнителей после старта

Повторный `GET /api/providers` после готового интерфейса может приходить из нескольких
независимых цепочек. Сам запрос не доказывает перезапуск процессов исполнителей.
Штатное объединение читателей описано в [чтении реестра](providers-registry-load.md).

## Переход истории обслуживания с V1 на V2

Пока каталог исполнителей не получен, `providerInstall.load()` использует
`/api/providers/installations/current`. После появления `lifecycleProtocol: 2` watcher
перечитывает `/api/providers/installations/v2/current`.

`projectLifecycleV1` исключает непредставимые старым протоколом результаты, например
удаление CLI. Поэтому у одной серверной revision V1 может иметь пустой `recent`,
а V2 — сохранённый завершённый результат. Первый V2 той же revision раскрывает историю
без `providers.load(true)`. Более высокая revision означает, что после прежнего снимка
произошло изменение: ранее не замеченный финал сохраняет принудительное обновление.

Изолированное воспроизведение на настоящих Pinia stores подтверждает различие:
первый V2 с сохранённым удалением и V1 → V2 той же revision дают ноль refresh.
Новый финал следующей revision перечитывает карточки один раз, в том числе после
пропущенного `active`. Раньше общий `receivedSnapshot` ошибочно считал первый V2
после V1 новым финалом даже без изменения revision.

## Сброс снимка при фоновой проверке версий

Через 30 секунд после старта сервер запускает `checkUpdates()`. Если метаданные версий
изменились, он вызывает `registryCache.expire()` и отправляет `providers-update`.
При первом заполнении карты версий изменение возможно и без выхода нового релиза.

`expire()` начинает новое поколение сбора и помечает прежний успешный снимок устаревшим,
сохраняя его для обычного GET. Позднее завершение сбора отправляет `providers-update`
и заменяет карточки готовым снимком. Декоратор `providerRegistry` и явный refresh
продолжают ждать свежие данные; результат прежнего незавершённого сбора отсекается.

Прежний `clear()` полностью убирал снимок и при сборе дольше 1200 мс возвращал пустой
список, который клиент принимал вместо карточек. Полный сброс остаётся для изменений
настроек и runtime, где старые данные возвращать нельзя. Обычное истечение TTL также
сохраняет [прежний снимок](../server/providers-background-read.md).

Проверки: `tests/web/provider-install-store.test.js` — переход V1/V2 с одинаковой
и растущей revision; `tests/server/providers-background-read.test.js` — сохранность
карточек после проверки версий, позднее уведомление и поколения `expire()`.

## Как отличить по журналам

Сопоставлять серверные начало и завершение запросов, историю V1/V2, `refresh=1`,
время старта сервера и `sse.open`/`sse.hello`/ошибки окна. Журнал окна нормализует
API-путь и удаляет query, поэтому его `api.slow` для `/api/providers` сам по себе
не отличает обычный запрос от принудительного. Тело ответа также не сохраняется:
пустой список в конкретном эпизоде нельзя объявлять доказанным только по длительности.
