# Флап браузерного хоста стирает гранты агентов

Симптом: команды агента во вкладке внезапно получают `outcome_unknown`, затем
`browser_access_denied`/`access_revoked`; список вкладок пустеет; доступ сессии к
браузеру в прежней реализации не восстанавливался сам. Исправление описано ниже.

Механика (по `server/src/modules/browser/index.ts`): браузерное окно представлено
одним «хостом», который регистрируется через `POST /api/browser/hosts` и живёт на
lease-heartbeat. Каждая регистрация вызывает `broker.register()` и затем
**`access.clear()`** — все выданные агентам гранты вкладок стираются; `DELETE` хоста
тоже чистит доступ. Перезапуск хост-компонента (краш, сторож, takeover) для агентов
выглядит как миграция: вкладки теряются, грант отозван, нового никто не выдаёт.

Отдельная причина воспроизведена и исправлена: [продление long-poll при ACK и
JSON-заголовок у пустого DELETE](browser-poll-deadline.md). В этом живом случае
heartbeat оставался исправным до снятия host самим клиентом.

Наблюдения 03.11.2026 (лог `grigdesk-server.log`):

- регистрации хоста: 07:55:28; 08:04:33 (DELETE+POST) и повторная 08:04:58 через ~25 с;
  08:19:15 (перезапуск окна); 08:20:32 (DELETE+POST) и повторная 08:20:57 через ~25 с;
- флап двойной: вторая регистрация приходит ровно через ~25 с после первой;
- хост, зарегистрировавшийся в 08:04:58, умер молча в простое в 08:16:50 — без DELETE
  и без перерегистрации (окно не подняло хост заново до рестарта);
- запрос `screenshot` коррелирует с флапом: скриншот в 08:20:0x вернул
  `outcome_unknown`, хост перерегистрировался в 08:20:32. Подозреваемый путь —
  `capturePage` на скрытом виде (`browserView.ts`, `stayHidden: true`) может
  повиснуть без ответа.

Практика:

- в прежней реализации после флапа требовался ручной повторный грант; теперь
  собственную вкладку после технической потери host восстанавливает новый open;
- прежний неограниченный захват мог исчерпать срок транспорта; теперь снимок
  ограничен отдельным сроком и не отзывает grant при отказе чтения;
- при диагностике «клики не работают» сначала смотри карту DELETE/POST
  `/api/browser/hosts` в `~/.grigdesk/state/grigdesk-server.log`: отказы доступа
  могут быть последствием флапа, а не правки ввода.

Отсутствие DELETE/POST регистрации не доказывает наличие доступа у отдельной
вкладки. `navigating`, пауза, epoch, origin и потеря renderer проверяются в native
runtime независимо. Отменённая загрузка завершается по `did-stop-loading` с
фактическим URL, даже когда Chromium не прислал `did-navigate`. Это не выдаёт
новый grant и не восстанавливает ранее отозванный.

В отдельной живой сессии отказ `open` после прежней успешной работы сопоставлен
с DELETE/POST хоста за минуту до команды. Между соседними heartbeat был разрыв
24,3 секунды при lease 15 секунд; screenshot в проверенной последовательности
не выполнялся. Это подтверждает ещё один случай утраты grants при перерегистрации,
но причина задержки heartbeat не установлена. Автоматическая повторная выдача
доступа не является допустимым способом скрыть эту ошибку. В том же интервале
найдены [длительные задержки UI](browser-host-ui-stall.md); их первопричина пока
не установлена.

Подтверждение `close` учитывает heartbeat, который уже увидел отсутствие закрытой
вкладки. Только ожидающий запрос закрытия сохраняет право получить ACK; явный
revoke, regrant, смена host или proof всё ещё запрещают ответ. Регрессия —
`BR13-close` в `tests/server/browser-access.test.mts`.

## Восстановление собственной вкладки

Техническая потеря host отзывает старые команды, но запоминает origin собственной
вкладки агента. Новый авторизованный open того же владельца на тот же URL выдаёт
новую эпоху доступа; до open вкладка остаётся невидимой в list. Это устраняет
ловушку дедупликации, когда open находил старую отозванную вкладку и всегда падал.
Ручной revoke/pause, передача другому владельцу, смена origin, документа или машины
стирают право восстановления. Human-вкладки автоматически не перевыдаются.
Регрессии: BR-N-reconnect, BR-N-reconnect-deny, BR-N-reconnect-origin.
