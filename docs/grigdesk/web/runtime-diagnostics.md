# Диагностика ожиданий и некорректных переходов

Штатный [журнал окна](../guide/web-log.md) сохраняет механизмы сбоев, включая случаи,
где Promise ещё не завершился или ошибка была перехвачена приложением. Запись ожидания,
пустого списка или отклонённого ответа сама по себе не доказывает ошибку продукта.

## Запросы API

При уровне «Подробно» `api.slow` фиксирует попытки от 1000 мс. `api.pending` один раз
через 3000 мс показывает ещё незавершённую попытку, включая мутации без таймаута.
`api.recovered` сообщает успешный исход повторной попытки. Поведение таймаутов,
отмены и повторов транспорт не меняет.

| Поле | Смысл |
| --- | --- |
| `request`, `attempt` | Числовой номер попытки внутри документа и номер повтора; связывают ожидание с исходом. |
| `phase` | `headers`, `body`, `parse`, `done`; у двоичных методов и upload — общий `request`. |
| `headersMs` | Время от начала попытки до получения заголовков. Включает очередь транспорта и работу сервера. |
| `bodyMs` | Чтение тела до синхронного JSON.parse. |
| `parseMs`, `chars` | Время разбора и длина строки; содержимое не сохраняется. |
| `serverMs` | Метрика `grigdesk` из Server-Timing: время сервера до onSend, без последующей передачи тела. |
| `refresh` | Был ли явный параметр `refresh=1`; query целиком не записывается. |

Сервер добавляет числовую метрику только при общем verbose. Старый сервер и ответы
без Server-Timing остаются работоспособными. Нельзя считать разницу `headersMs-serverMs`
точным сетевым временем: туда входят очередь соединений, мост приложения и планирование
главного потока. Синтаксическая ошибка успешного JSON-ответа имеет имя `SyntaxError`
и этап `parse`; текст некорректного ответа отбрасывается.
Ограничение сетевых отказов Б24 не скрывает отдельные ошибки синтаксиса JSON;
они остаются под общим ограничением одинаковых ошибок журнала.

Одновременно допускается не более 128 таймеров ожидания API. Успех, ошибка и отмена
снимают свой таймер; смена политики снимает все и отсеивает подробности прежнего поколения.
Быстрые успешные запросы не порождают запись на каждый вызов.

## Действия stores и SSE

Общий `$onAction` при verbose пишет `store.slow` от 500 мс с исходом `success`/`error`,
а через 3000 мс — однократную `store.pending`. Это время действия целиком, включая сеть,
а не CPU-профиль. Синхронные действия не создают таймер: ожидание ставится в микрозадаче
только для ещё незавершённого действия. Предел — 128 таймеров. Dispose и смена уровня
освобождают наблюдения; поздний исход прежнего поколения их не возрождает.
Аргументы и возвращённые значения не читаются.
Собственный store `webLog` не наблюдается, чтобы обновление статуса журнала не порождало
рекурсивные диагностические события.

`sse.fault` сохраняется уже при уровне «Только ошибки»: закрытое имя сигнала, этап
`parse`/`subscriber`/`relay`, имя исключения и очищенные кадры JS-файлов сборки.
Синхронный throw и отклонённый Promise
подписчика фиксируются одинаково. Остальные подписчики продолжают получать событие.
Пустое тело события не считается ошибкой JSON; непустое неразбираемое тело отмечается.
Содержимое события, текст исключения и аргументы подписчика не сохраняются.

## Переходы реестра исполнителей

`providers.registry` при verbose различает `start`, `joined`, `cached`, `applied`,
`discarded`, `invalid`, `failed`. Причина задаётся вызывающим кодом: запуск, монтирование,
минутный таймер, SSE, reconnect, credentials или завершение установки. Неуказанная
причина остаётся `other`. Записываются длительность, номер чтения, refresh и количества.
Числовой номер чтения store отличается от номера попытки API.

`state.anomaly` доступна уже при «Только ошибки»: `empty-snapshot` отмечает замену
непустого реестра пустым, `invalid-snapshot` — неправильную форму ответа. Список
исполнителей, модели и credentials в события не входят. Отброшенный поздний ответ
фиксируется отдельно от принятого; принятие данных и защита поколений остаются прежними.

Ошибки SSE, аномалии, медленные действия и ожидания используют общее подавление:
пять одинаковых событий в минуту, затем сводка `log.suppressed`. Разные этапы, сигналы,
виды аномалий и actions имеют разные сигнатуры. Идентификатор попытки в сигнатуру
не входит, поэтому поток новых запросов не обходит ограничение.

## Проверка

`tests/web/runtime-diagnostics.test.js`, `web-log-sse.test.js`, `web-log-capture.test.js`
проверяют этапы, ожидание без завершения, отмену, политику, скрытые ошибки, пустой снимок
и отсутствие приватных данных. `tests/server/http-diagnostics.test.js` проверяет
Server-Timing и смену уровня; `web-log-performance.test.js` — auth, повторную проекцию
новых событий, политику и запись на диск. Каталог маршрутов включает `/onboarding`.

Нужна пересборка сервера и окна: оба проверяют закрытый каталог событий. Изменение
исходников не добавляет эти сведения в уже запущенное прежнее приложение.
