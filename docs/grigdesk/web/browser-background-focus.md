# Фоновая вкладка и клавиатурный фокус интерфейса

Фоновая страница встроенного браузера не должна входить в native-дерево главного
окна. `WebContentsView.setVisible(false)` управляет рисованием, но не изолирует
прикреплённый WebContents от клавиатурного фокуса.

До исправления создание вкладки сразу вызывало `contentView.addChildView` для
невидимой страницы. В живом опыте с `grigdesk_browser.open` во время набора в чате
зафиксированы два состояния: поле чата осталось подключённым и не disabled,
главный документ остался видимым, но `hasFocus()` стал false; новая страница
получила `hasFocus() === true` при `visibilityState === 'hidden'`. Пользователь
подтвердил совпадение с исходной потерей курсора. Это было открытие страницы,
без команд синтетического ввода.

`createNativeBrowserView` теперь создаёт guest отсоединённым. Навигация, CDP,
snapshot и снимки не добавляют guest в дерево главного окна. `show` прикрепляет view
один раз, `hide` отсоединяет его, сохраняя WebContents и состояние страницы.
Закрытие также снимает только существующее прикрепление.

При показе сохраняется фокус основного WebContents, если интерфейс уже владел
им в активном окне. Повторный layout не отнимает фокус у сайта. При скрытии или
закрытии фокус возвращается основному WebContents только из текущего guest
и только при активном окне; другое приложение не активируется принудительно.
DOM-фокус и выделение текста поля чата не меняются вызовом `textarea.focus()`.

Проверки `BR-V-focus-*` в `tests/desktop/browser-native-view.test.mts` покрывают
фоновые команды, смену геометрии, повторные show/hide, закрытие и другое активное
приложение. Профиль native runtime дополнительно сохраняет проверки навигации,
grant/epoch, снимков и запрета позднего layout. Проверка исправления в настоящем
окне требует нового пакета приложения и повторения исходного живого опыта.

## Грабли: синтетический ввод не доходит до отсоединённого guest

Отсоединение фоновой вкладки сломало ввод агента: `Input.dispatchMouseEvent` по
никогда не показанному view не достигает страницы — `click`/`fill` возвращают `ok`
без эффекта (ночь 02–03.11.2026, «клики в пустоту» браузерных этапов фабрики).
После первого показа вкладки ввод работает и в скрытом состоянии.

Исправление (проверки `BR-N31` в `tests/desktop/browser-native-runtime.test.mts`,
`BR-V01`/`BR-V01D` в `tests/desktop/browser-native-view.test.mts`):

- при смонтированной панели ввод активирует вкладку и идёт системными событиями;
- без панели команда исполняется в DOM страницы (`DOM_ACT_SOURCE` в изолированном
  мире: `click()`, `insertText`, `scrollBy`) — ввод работает на любой вкладке
  и не касается фокуса окна;
- `backgroundThrottling: false` в `browserViewOptions` держит рендерер фоновой
  вкладки активным: приостановленная страница не отдаёт кадр для снимка (захват
  мог висеть до таймаута транспорта; причина наблюдавшегося чёрного экрана
  отдельно разобрана в [диагностике](browser-capture-lifecycle.md));
- снимок скрытой вкладки использует служебную невидимую поверхность без фокуса;
  подготовительный `capturePage` и итоговый CDP-захват имеют собственные таймауты.
  Устройство описано в [контракте захвата](browser-ready-capture.md).

Захват не вызывает временный `show/hide` главного окна. Он не меняет выбранную вкладку,
геометрию и фокус; завершение снимка не отменяет layout, пришедший во время ожидания.
CDP-чтение и вся команда снимка ограничены 5 секундами; общий срок включает
подготовку поверхности. Таймаут
чтения возвращает `browser_capture_failed`, сохраняя grant; таймаут мутации
по-прежнему отзывает доступ с `outcome_unknown`.
