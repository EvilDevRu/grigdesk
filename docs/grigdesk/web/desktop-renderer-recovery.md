# Потеря renderer и доставка событий браузера

Окно Electron может оставаться живым после уничтожения его главного frame. Поэтому
`BrowserWindow.isDestroyed()` недостаточно для безопасного чтения `mainFrame.url`.
Событие `did-start-loading` фоновой браузерной вкладки раньше доходило через metadata
до публикации состояния UI и вызывало необработанное исключение главного процесса.

## Доставка в главный документ

`desktop/src/browser/browserEvents.ts` объединяет callbacks state/intent. Доставка
проверяет окно, WebContents, renderer, загрузку, уничтожение и detached-состояние frame,
текущий origin и принадлежность frame главному документу. Сообщение отправляется через
`frame.send` именно в проверенный frame, а не через повторный выбор адресата в WebContents.

Во время потери документа события пропускаются без отложенного повтора. Ожидаемые
исключения Electron о разрушенном объекте/фрейме перехватываются локально; другие ошибки
остаются наблюдаемыми. Runtime продолжает обновлять metadata и остальных подписчиков.
Новый документ получает актуальное состояние штатным запросом browser API.

## Восстановление главного интерфейса

`mainRendererRecovery.ts` обрабатывает `render-process-gone` главного окна. Сначала main
инвалидирует эпоху browser IPC, скрывает guest и отзывает прежний host через
`browserApi.documentChanged()`. В stderr записываются роль `main`, reason, exitCode,
версии Electron и Chromium. URL, настройки, payload, переписка и текст исключения
в эти диагностические записи не входят.

После показа окна нативный диалог предлагает «Перезагрузить интерфейс» или «Оставить окно».
Перезагрузка выполняется только после ответа человека и загружает корень текущей трубы
через `loadDocument`. Она не перезапускает сервер и задания. Несохранённый текст страницы
может быть потерян. Автоматического цикла повторов нет; повторное падение требует нового ответа.
Одновременные сигналы не размножают диалоги. Навигация главного документа, закрытие и выход
отменяют ожидающий вопрос; поздний ответ после смены origin ничего не загружает.

До показа главного окна падение проходит обычный отказ старта. Во время выхода новый
вопрос не открывается. Отказы native-диалога и перезагрузки фиксируются отдельной записью
`renderer-recovery-failed` с фазой `prompt` либо `reload` без автоматического повтора.

## Проверка и ограничения

Профильные `browser-events.test.js` и `main-renderer-recovery.test.js` проверяют потерю
frame при живом окне, отказ getter/IPC, смену адресата, сохранность runtime-подписчиков,
доставку в восстановленный документ и жизненный цикл ручного восстановления.

Это исправление обработки уничтоженного frame, а не установленная причина нативного
SIGTRAP Chromium. Для причины нативной аварии нужны её stderr/FATAL либо дамп.
Сообщение `No space left on device` при сохранении coredump относится к сохранению
диагностики и само по себе не доказывает причину падения renderer.
Внешний вид нативного диалога и восстановление настоящего рабочего окна проверяет человек;
рабочее приложение при изолированной проверке не перезапускается.

Контракты Electron: [frame.send и состояние frame](https://www.electronjs.org/docs/latest/api/web-frame-main),
[render-process-gone](https://www.electronjs.org/docs/latest/api/web-contents#event-render-process-gone).
