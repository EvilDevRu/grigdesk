# Сообщения Linux-окна и учёт keep-alive-сокетов

Сообщения Mesa, Node о числе слушателей и Chromium об atom cache имеют разные источники.
Общая причина для трёх групп не установлена. Сетевой дефект воспроизводится без окна.

## Подтверждённое накопление слушателей

В `desktop/src/pipe/upstream.ts` HTTP Agent повторно выдаёт живой keep-alive-сокет запросам
и `probe()`. Прежние обработчики обеих операций каждый раз добавляли `once('close')` для
удаления сокета из `streams`. Повторный `Set.add` не создавал новой записи, но новый callback
оставался до закрытия сокета. Завершение ответа его не снимало.

Источник доказан стеком `--trace-warnings`, прямыми счётчиками и опытом с возвратом исходника.
Контроль без перехвата регистрации слушателей воспроизводил тот же рост. На Node 22.22.1
и Node 24.21.0 внутри dev Electron 44.7.0 получены одинаковые исходные значения:

| Серия на одном живом сокете | Все `close`, HTTP | Все `close`, pinned TLS 1.3 |
|---|---:|---:|
| 30 GET | 2 → 31 | 6 → 35 |
| 30 `probe()` | 2 → 31 | 6 → 35 |
| 30 пар GET + `probe()` | 3 → 61 | 7 → 65 |

При 11 слушателях Node выдавал `MaxListenersExceededWarning`. Ответы оставались успешными;
рост памяти в байтах и утечка после уничтожения сокета не доказаны. Четыре строки исходного
журнала без стека и версии пакета нельзя точно сопоставить с объектами воспроизведения.

Общий `trackStream` внутри `createUpstream` проверяет `streams.has(socket)` и назначает
единственный cleanup при первом учёте сокета. Его разделяют запросы и `probe()`. Три
однократных TLS callback в `pinnedAgent` сохранены: их накопление не подтверждено.
При общем учёте полное число `close` в проверенной среде постоянно: HTTP 2, TLS 6.
Эти абсолютные числа зависят от среды и не являются контрактом других версий Node.

Регрессии в `tests/desktop/pipe-upstream.test.js` проверяют 30 GET, 30 `probe()` и их
чередование для HTTP и настоящего pinned TLS 1.3: один живой сокет, постоянное число
слушателей после каждой операции, штатный лимит, отсутствие предупреждения и очистку при
закрытии. Вместе с `pipe-server.test.js` и `connection-lifecycle.test.js` они проверяют
потоки SSE, бинарный WebSocket, файл 5 МиБ, отмену, auth, pin, version gate и запрет повтора POST.
Удалённый транспорт проверен через loopback TLS-стенд; внешняя сеть этим не проверяется.

## Mesa: исходный отказ доступа не объяснён

Первое сообщение loader означает отказ `drmGetDevice2` получить сведения об устройстве.
Но причина последующих четырёх EACCES в окружении исходного окна не установлена.
В изолированном окружении три библиотеки DRI загрузились через `dlopen`, четвёртая
отсутствовала с ENOENT; исходный EACCES не повторился. Устройство `/dev/dri` отсутствовало,
GLX-контекст не создавался. Это ограничения стенда, а не доказанный дефект приложения.

Минимальное окно с настоящими `secureWebPreferences`, без отключения GPU и sandbox,
загрузило DOM. Диагностика показала software compositing и отключённый WebGL; захват
изображения завершился `UnknownVizError`. Видимая картинка и графический режим рабочего
приложения не подтверждены. Виртуальный X11-дисплей этого ограничения не снимает.

Владельцу диагностики нужен отдельный изолированный экземпляр того же пакета в исходном
графическом окружении. Нужно записать версию, `getGPUFeatureStatus`/`getGPUInfo` и трассу
открытия/отображения DRI: конкретные syscall, путь, errno и правило доступа при отказе.
До этих данных нельзя назначить изменение прав, драйверов или политик изоляции.

## Chromium atom cache и передача файлов

В Chromium 152.0.7977.130 `AtomCache::GetAtom` пишет ERROR с предложением добавить
`application/vnd.portal.filetransfer` и `application/vnd.portal.files` в `kAtomsToCache`
после успешного `InternAtom`, затем сохраняет и возвращает atom. Источник — кэш X11-имён
Chromium; запись сама по себе не означает отказ передачи файла.

Оба точных сообщения воспроизведены дважды на собственном виртуальном X11-дисплее.
После них для каждого MIME успешно записаны и прочитаны одинаковые 33 синтетических байта.
Это проверка raw clipboard; настоящий portal key и DnD файла из файлового менеджера
не проверены. Успешная HTTP-передача 5 МиБ также не заменяет проверку системного портала.
Прикладной дефект этими сообщениями не доказан; нужен графический стенд с рабочим portal.

## Ограничения диагностики пакета

`--trace-warnings` через argv проверен на dev Electron без `NODE_OPTIONS`. E2E launcher
удаляет `NODE_OPTIONS`, а `cli/window.ts` передаёт окну только адрес GrigDesk. Применимость
trace argv к готовому установленному ELF не проверена; защитные fuses не менялись.
Лимиты слушателей, предупреждения, GPU и sandbox не меняются ради сокрытия этих сообщений.
Диагностика использует синтетические данные без секретов и переписки. Установку пакета
и перезапуск рабочего приложения выполняет человек.
