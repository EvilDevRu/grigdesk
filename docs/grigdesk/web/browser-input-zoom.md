# Клики агента мимо элементов при зуме вкладки

Симптом: снапшот отдаёт правильные refs, команды `click`/`fill` возвращают `ok`, но
страница не реагирует: форма входа «не отправляется», обработчики не вызываются,
`insertText` не попадает в поле. На прогретой странице и на базовой ревизии стенда
поведение то же — код продукта не при чём.

Причина: `resolve()` (browserProtocol → pageSnapshot) возвращает координаты центра
элемента в CSS-пикселях страницы, а `Input.dispatchMouseEvent` принимает DIP-координаты
ввода. Зум вкладки (`view.zoom`, 25–300% из UI окна браузера) масштабирует отрисовку:
при 200% элемент на CSS (10, 10) виден в DIP (20, 20), и кнопка «Войти» получает mousedown
мимо себя. Скриншоты и layout уже умножали координаты на `bounds.zoom`, путь ввода — нет.

Исправление: send-обёртка browserApi для `Input.dispatchMouseEvent` приводит точку к DIP
через текущий `view.state().zoom` (проценты, 100 = 1:1). Regression-тест:
`BR-N30` в `tests/desktop/browser-native-runtime.test.mts` — при zoom 200% координаты
mousePressed/mouseReleased удваиваются, при 100% не меняются.

Пример диагностики: клик по ссылке «Забыли
пароль?» не менял URL, submit формы не вызывал обработчик (нет POST в логе API),
instrumentation-лог в mounted-компоненте подтверждал живой Vue. Проверяй в первую
очередь зум вкладки, прежде чем обвинять продукт или транспорт фабрики.

Уточнение от 03.11 (день): зум оказался второй, независимой причиной промахов.
Главной причиной «кликов в пустоту» ночи 02–03.11 был отсоединённый от окна view —
ввод не доходит до никогда не показанной вкладки (см.
[фоновой фокус](browser-background-focus.md) и проверку BR-N31). После первого
показа вкладки ввод работает и в скрытом состоянии; зум-фикс BR-N30 остаётся
нужным для вкладок с zoom ≠ 100%.
