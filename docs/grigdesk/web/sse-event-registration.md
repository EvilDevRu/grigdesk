# Событие есть на сервере, ветка есть во фронте, а не работает — забыли EVENT_NAMES

Продолжение той же грабли и её обратная сторона. `EventSource` доставляет ИМЕНОВАННЫЕ
события только тем, кто на них подписался (`addEventListener(name)`), поэтому пара
«`broadcast('chat-turn-start')` на сервере + `if (name === 'chat-turn-start')` в сторе»
сама по себе не значит ничего: без имени в `EVENT_NAMES` (`web/src/composables/useSse.ts`)
ветка не выполняется НИКОГДА.

Отказ молчаливый и потому долгий: ошибок нет, событие «просто иногда не приходит», а
часть случаев прикрыта другими путями и выглядит работающей. Живой случай:
`chat-turn-start` рассылался и обрабатывался, но подписки не было — метка «ждёт очереди»
на своём сообщении и признак идущего сжатия на ВТОРОМ устройстве держались только на
`_loadActive()` при `hello`, то есть появлялись после переподключения SSE, а не в момент
события. Ровно та беда, ради которой признак `compact` вообще вынесли на сервер.

Сторож — `tests/web/sse-event-names.contract.test.js`: собирает имена из `broadcast(...)`
по `server/src` и все ветки `name === '…'` по `web/src`, и требует, чтобы пересечение
целиком лежало в `EVENT_NAMES`. Обратное направление намеренно не проверяется: сервер
вправе слать событие, которого фронт пока не слушает (`chat-queued`).

Уточнения используют в том же общем `EventSource` события `chat-in-turn` и
`chat-assistant-message`. Они зарегистрированы в `EVENT_NAMES`, а store после сигнала
сверяет каноническую запись через постраничный `GET /api/chat/in-turn`. Сигнал сам по
себе не заменяет журнал при пропуске событий или после F5.
