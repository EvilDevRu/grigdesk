# Фризы при обновлении списка и ответе агента

**История.** Ниже зафиксированы причины задержек исходной версии до исправлений.
Текущие механизмы и способ сравнения описаны в
[методике проверки производительности](chat-performance-checks.md).
Скорость текущей сборки подтверждается новым прогоном; полный fallback и холодная
загрузка измеряются отдельно.

Список чатов поднимает разговор по `updatedAt`, а ожидающие ответа человека — по
`waiting`. Перестановка строки может совпадать с несколькими тяжёлыми операциями
главного потока. Отключение сортировки не устраняет весь механизм.

## Проверенные причины

В `web/src/stores/chat.ts`, getter `list`, каждое вычисление строит строки всех
чатов выбранного списка. Для каждой строки `mdToText(snippet)` разбирает полный
текст последнего сообщения или черновика через `marked.lexer`. Превью визуально
обрезается стилями, но объём разбираемого Markdown не ограничен и результат не
кэшируется. Даже изменение только `updatedAt` одного чата повторяет эту работу
для всех строк. `ChatList.vue` затем заново дополняет строки данными модели.

Завершённая реплика из `chat-assistant-message` вызывает `_materializeInTurn`.
`materializeInTurnMessages` сохраняет сообщения других запусков, но создаёт новый
массив и объекты текущей группы. Store проверяет его равенство двумя полными
`JSON.stringify`, включая `message.steps` всех прошлых ходов. Это противоречит
уже принятому правилу исключать шаги из служебных сравнений: они исключены из
`fingerprintOf`, но попадают в эту отдельную проверку.

После первого завершённого блока того же запуска проверка повторяется и для
обновлений незавершённого блока: видимая историческая группа не изменилась, но
обе сериализации всё равно выполняются. Повтор неизменённого завершённого блока
также проходит `_materializeInTurn`, потому что SSE-handler игнорирует результат
`mergeInTurnEntry`.

При изменении группы store заменяет `messages`, обновляет `updatedAt` и вызывает
`_persist`. Поэтому одновременно обновляются список и открытая сессия.
`ChatSession.vue` вызывает `mdToHtml(m.text, ...)` прямо в родительском шаблоне:
повторный рендер разбирает и неизменённые старые ответы. Это происходит даже на
`chat-progress`, когда меняется только счётчик токенов. При изменении шагов или
блоков `chatTimeline` дополнительно заново разворачивает все прошлые запуски;
новые массивы `steps` заставляют старые `StepList` пересчитать свои строки.

Через 300 мс `_persist` запускает отдельную запись. Страховочный снимок и отпечатки
уже исключают тела шагов, но `_putChat` отправляет полную историю изменённого чата.
`apiClient.request` сериализует её на главном потоке. Поэтому после завершённого
блока возможна ещё одна пауза с задержкой относительно перестановки строки.

## Воспроизведение и ограничения

Проверка 01.10.2026 использовала отдельную production-сборку fixture с настоящими
Vue, Pinia, `chat.js`, `ChatList`, `ChatSession`, Markdown, хронологией и `StepList`.
История генерировалась с нуля; рабочие переписки и приватное состояние не читались.
Внешние службы заменены заглушками, сеть не участвовала. Заглушка PUT сохраняла
синхронный `JSON.stringify(body)`, чтобы учитывать реальную стоимость тела запроса.
Сборка fixture не меняла используемый `web/dist`.

Большой сценарий: 80 чатов, у открытого разговора 50 прошлых ходов, по 150 шагов
примерно по 1000 символов, ответы по 6000 символов. Сериализованная история открытого
разговора занимала 8,37 млн символов. Ниже — медианы трёх событий одного вида,
синхронный обработчик плюс ближайший рендер Vue, без отложенного сохранения.

| Событие | Исходный код, мс | Контрольный прототип, мс |
| --- | ---: | ---: |
| Изменение `updatedAt` и пересортировка списка | 57 | 2,1 |
| Обновление счётчика токенов | 45 | 4,4 |
| Новый шаг инструмента | 65 | 8,1 |
| Новый завершённый блок ответа | 300 | 8,3 |
| Незавершённый блок после завершённых реплик | 185 | 6,4 |
| Повтор неизменённого завершённого блока | 172 | 0,3 |

Контрольный прототип действовал только внутри fixture: кэшировал Markdown,
сравнивал поля проекции без обхода тел шагов и повторно использовал проекции
неизменённых исторических запусков. Это эксперимент по локализации стоимости,
а не готовое продуктовое исправление. Отдельная сериализация тела PUT оставалась:
около 63 мс в исходном варианте и 57 мс в прототипе. Observer фиксировал длинные
задачи на обработке блоков и отложенной записи; ошибок браузера не было.

Контроль без исторических шагов уменьшал историю до 0,32 млн символов: обработчик
нового блока сокращался примерно со 138 до 5 мс, но рендер всё ещё занимал около
114 мс из-за Markdown. Контроль с одним только списком сохранял задержку обновления
превью, а без списка исключал её. Эти сравнения отделяют три источника стоимости.

Время зависит от компьютера и нагрузки. Этот сценарий подтверждает воспроизводимый
механизм фронтенда; он не является профилем конкретного пользовательского окна.
Ошибки API и SSE в общем журнале окна сами по себе не измеряют такую блокировку
главного потока.

## Порядок исправления

1. Убрать полную сериализацию из `_materializeInTurn`: учитывать результат слияния,
   ревизии и поля изменённой группы, сохранять ссылки на неизменённые сообщения.
   Обновление чернового блока не должно сравнивать всю завершённую историю.
2. Кэшировать превью отдельно для каждого чата по исходному тексту, ограничить
   объём Markdown для однострочного сниппета. Изменение порядка не должно заново
   разбирать тексты остальных чатов. Кэш очищается при удалении чата.
3. Отделить старые сообщения от рендера активного хода: Markdown пересчитывается
   по изменению текста, историческая проекция — по изменению её сообщений и шагов.
   Счётчик токенов не должен обновлять старые ответы и ленты инструментов.
4. Отдельно устранить паузу записи: служебные изменения и активный поток не должны
   сериализовать всю накопленную историю. Для неизбежного полного снимка нужен
   путь, который не блокирует главный поток; для канонических блоков — узкая
   синхронизация с уже устойчивой серверной записью. Простое удаление `_persist`
   требует проверки гарантий доставки и восстановления и не считается исправлением.

При реализации сохранить порядок по времени и ожиданию человека, финализацию того
же блока без дубля, актуальность индексов сообщений при вставках, восстановление
после F5 и повторной доставки, защиту от поздних ревизий и страховку последнего
ответа. Проверять производительность на большой синтетической истории отдельно
от функциональных тестов; уменьшение только числа PUT не доказывает отсутствие
фризов рендера.
