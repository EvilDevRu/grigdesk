# Захват, отмена навигации и сохранение доступа

## Воспроизведённые ошибки

Прежняя ветка `screenshot` безусловно показывала guest в главном окне, а после
ожидания скрывала его по сохранённому `wasShown`. Это объясняет вспышку над чатом.
Кроме того, если во время захвата человек активировал эту вкладку или смонтировал
панель, старый `finally` скрывал уже выбранную страницу. Проверка `BR-N32`
воспроизвела оба нарушения: непустой rect при скрытой панели и потерю нового layout.
Захват не управляет видимостью главного окна; только реестр вкладок применяет layout.
Скрытая служебная поверхность описана в [контракте захвата](browser-ready-capture.md).

Отменённая навигация присылала `did-start-navigation`, `did-fail-load(-3)` и
`did-stop-loading` без `did-navigate`. Обработчик игнорировал -3 и оставлял
`navigating=true`: все дальнейшие команды получали `access_revoked` при прежних
origin и grantEpoch. Проверка `BR-V-abort` фиксирует эту последовательность.
После остановки загрузки реестр получает фактический URL. Переход на другой
origin по-прежнему снимает разрешение; явный отзыв не отменяется.

Срок снимка отделён от срока мутации. Зависшее чтение возвращает
`browser_capture_failed`, не отзывает grant и не удерживает очередь до сторожа
транспорта. `BR-N33` проверяет доступ после timeout, `BR-N34` — 48 команд по трём
вкладкам с навигациями. Ручной отзыв между CDP-чтениями остаётся запрещающим.

## Пределы диагноза чёрного экрана

Сообщение о двух чёрных вкладках после серии зависших захватов не содержит
состояния compositor или причины завершения GPU-процесса. В исследованном
интервале журнал UI содержит сообщения API и производительности; crash dump
не найден. Эти данные не подтверждают GPU-reset и не позволяют объявить его
причиной. Отмена нового layout доказана отдельно; тождество этой гонки исходному
случаю с двумя вкладками не установлено.

Electron исправлял пустой WebContentsView после отключения background throttling
у скрытого окна в [PR 52844](https://github.com/electron/electron/pull/52844).
Исправление вошло в ветку 44 до используемой версии 44.7.0. Сходство симптома
не является доказательством той же причины на Linux.

## Отказ доступа без смены хоста

В исследованном длинном прогоне регистрации хоста отсутствовали, heartbeat
продолжался. Последний успешный снимок DOM проблемной вкладки и последующий
отказ разделены несколькими минутами и командами по другим вкладкам.
Журнал ввода не записывал причины revoke, navigation и grantEpoch: по нему нельзя
выбрать между незавершённой навигацией, потерей renderer и ручным изменением прав.
Последовательность отменённой навигации изолирована тестом, но её наличие именно
в историческом прогоне не доказано. Показ/скрытие само по себе не меняет grantEpoch.

Отдельная гонка `close` и heartbeat воспроизведена серверным тестом `BR13-close`:
сервер раньше отвергал ACK, поскольку закрытая вкладка уже исчезла из проекции.
Ожидающий close сохраняет только право завершения; другие запросы не получают
доступ через отсутствующую вкладку.

## Живое уточнение после первой сборки

Полностью отсоединённый guest вернул `browser_capture_failed` на
`Page.captureScreenshot(fromSurface: false)` при отключённом throttling.
Последующий snapshot прошёл: новый срок чтения сохранил grant и живой хост.
Избавление от вспышки за счёт одного отказа захвата не считается исправлением.
В следующем варианте guest получает native-родителя в скрытом служебном
`BaseWindow`, который не показывается и не входит в дерево главного окна.

Этот вариант отдал JPEG и сохранил доступ в длинной серии, но сравнение с DOM
выявило устаревшие кадры native capture. Следующее изменение требует итогового
CDP-захвата с перерисовкой; детали и состояние проверки —
[свежесть снимка](browser-capture-freshness.md).
