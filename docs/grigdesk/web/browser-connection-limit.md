# «GrigDesk завис, все запросы (ожидает)» = съеден лимит соединений браузера

Симптом: все fetch в Network стоят «(ожидает)» вечно, SSE `/api/events` при этом жив,
сервер отвечает curl'ом за миллисекунды. Причина: HTTP/1.1 — максимум 6 соединений на
хост во всём браузере; каждый лишний EventSource занимает соединение НАВСЕГДА. Было:
useSse() открывал свой EventSource на каждый вызов (AppShell + PipelineView + пермишены
чата = 3 на вкладку), две вкладки GrigDesk выедали весь пул. Правило: ОДИН EventSource на
вкладку в браузере и Android — синглтон в composables/useSse.ts (sseSubscribe).
В desktop постоянный SSE и long-poll принадлежат только главному документу; карточки
получают закрытый набор событий и снимки через [межоконные каналы](window-relay.md).
Они не создают EventSource, не опрашивают dashboard и пассивно принимают полку без
гидратации деталей и оповещений. Dashboard читается карточкой только после её действия.
Новые SSE-события добавлять
в его EVENT_NAMES, свои EventSource НЕ создавать. Смежное: GET в api-client — таймаут
30с + один повтор (docker-манипуляции со стендами рвут сеть, Chrome вешает fetch); вызывающий
может задать свой таймаут и выключить повтор (`api.get(path, { timeoutMs, retry: false })`).
Долгий запрос на время работы — тот же расход пула: ход чата поэтому принимается коротким
POST по `turnId`, а опрос метрик идёт по одному за раз
(`docs/grigdesk/chat/concurrent-send-transport.md`).
