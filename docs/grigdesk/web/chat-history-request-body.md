# Передача JSON истории через Blob

Проверено 01.10.2026 при завершении [исправления фризов](chat-freeze-fix-results.md).
На большой синтетической истории оставалась стоимость самого `fetch`, даже после
сокращения JSON через refs. В изолированной проверке строковое тело около 650 тысяч
символов давало примерно 30 мс синхронной работы `fetch`; такой же JSON через Blob
готовился и передавался примерно за 6 мс. Проверка с Playwright routing и без него
показала тот же эффект. Это результат конкретного Chromium, не гарантия для всех браузеров.

`web/src/shared/apiClient.ts` использует Blob только для
`PUT /api/chat/store/chat` и `PUT /api/chat/store/chat/step-reuse`, включая query.
Сначала прежний `JSON.stringify` фиксирует тело, затем создаётся Blob с типом
`application/json`. На сервер приезжают прежние UTF-8 JSON-байты; credentials,
заголовки, обработка ответа, ошибок и правила повторов сохраняются.

Сериализация происходит до первого ожидания сети: изменение объекта во время
запроса не меняет уже сформированное тело. Blob не добавляет автоматический повтор
мутации и не меняет CAS или контракт refs. PUT метаданных и другие API используют
свой прежний транспорт. `tests/web/api-chat-history-body.test.js` проверяет эти
условия, кириллицу, переносы строк, кавычки и Unicode.

В браузерном стенде `stats.put.ms` измеряет только `JSON.stringify`, а `prepareMs`
добавляет создание Blob. Длинные задачи учитываются до ACK, поэтому стоимость
подготовки байтов не скрыта за замером быстрого рендера.

Blob сокращает синхронные копии при передаче готового тела. Он не ускоряет
`JSON.stringify` впервые отправляемой большой ленты или полного fallback:
эти граничные задержки отдельно приведены в [отчёте](chat-freeze-fix-results.md).
