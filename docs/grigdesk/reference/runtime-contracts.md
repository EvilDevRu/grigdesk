# Дополнительные runtime-контракты

Основные знания читаются по живым ссылкам карт `docs/grigdesk/*.md`; этот файл сохраняет
короткие runtime-инварианты, которым недостаточно одного заголовка карты.

## Хранение истории чатов

После однократной миграции чтение, сохранение и удаление одного чата обращаются только к
его файлу. Каталог месяца определяется поиском имени `<id>.json` от новых месяцев к
старым; содержимое соседних чатов не читается. Полное сканирование остаётся для загрузки
всей истории, миграции и поиска companion по логической идентичности.

Сохранение и удаление перечитывают файл внутри очереди по id. Слияние сообщений, проверка
ревизии и атомарная запись используют свежую серверную копию: ускорение не должно терять
ответы из другого окна или возвращать удалённый чат.

## SSH-плагин

Ручной raw connect с паролем отправляет `application/octet-stream` только на localhost
или через HTTPS; пароль не хранится и не попадает в JSON. Human shell и agent exec —
разные режимы, SFTP доступен только человеку. Для подтверждений действует одна общая
очередь; origin-aware ответ идёт через `/api/ssh/approvals/:pid`.

Bridge-провайдеры — Claude, Codex, Kimi и DeepSeek. Доступ агента привязан к доверенному
attempt (trusted attempt), а у свободного чата task scope равен null. Вывод сервера
недоверенный: prompt injection не получает инструментов. Один ToolHost обслуживает все
сессии; Telegram fail-closed не видит SSH-подтверждения, старый PWA bundle также
fail-closed и не разрешает новое действие.

Публичные endpoints: `/api/ssh/connections`, `/api/ssh/host-key/:challengeId`,
`/api/ssh/sessions`, `/api/ssh/sessions/:sid/agent-access`,
`/api/ssh/sessions/:sid/terminal`, `/api/ssh/sessions/:sid/files`, `/api/ssh/audit` и
`/api/ssh/approvals/:pid`. Host key проверяется через TOFU/known-host; недоверенный вывод
сервера остаётся риском prompt injection.

## Запрет прямого SSH исполнителям

Настройка `blockDirectSsh` хранится как `providerSettings.<id>.blockDirectSsh` и меняется
существующим `POST /api/providers/:id/settings` с `confirmed: true`. При отсутствии ключа
запрет по умолчанию включён (`true`). Claude использует command-hook, Codex — command-hook,
DeepSeek — command-hook, Kimi — network-sandbox в contained и command-broker в host server. После изменения
`providerSettings` сессию надо переоткрыть или restart.

Это граница для кооперативного агента, не защита от намеренного обхода через base64/sh или
собственный SSH-клиент. Она не зависит от permission mode и не отменяется режимом прав.
`SSH_AUTH_SOCK` остаётся доступен; Git по SSH не блокируется. После выключения запрета
журнал подтверждений не создаётся. Старый PWA получает `confirmation_required`.
Пользовательский `permissions.deny` сохраняется: оба ограничения действуют совместно.
Проверка выполняется с временным `CLAUDE_CONFIG_DIR` и отдельным config, включая deny.

Kimi host server закрывает native Bash глобально и проверяет отдельную команду в
[канале GrigDesk](../chat/kimi-command-policy.md); сбой проверки не запускает команду.
Внутренний ACP host сохраняет typed-отказ `direct_ssh_policy_unavailable` до запуска. Режим contained даже при `blockDirectSsh: false` остаётся
закрыт network/egress-песочницей.

## Надзорный доступ к базам

Системный плагин `db` выключен по умолчанию. Профили хранят описание соединения в
приватном DB namespace, а пароль передаётся raw bytes, живёт только в памяти
server-owned сессии и не попадает в prefs, argv, env или audit. Соединение `via: ssh`
использует `forwardOut` живой SSH-сессии без локального порта; её закрытие немедленно
закрывает все зависимые DB-сессии и ожидания.

Один `supervised_db` доставляется всем исполнителям из общего work-tools registry.
`list` раскрывает только label, role и engine. Каждая попытка schema/query получает
решение общей очереди с `origin: 'db'`: внутренний отказ для отсутствующей сессии,
допуска, unknown и закрытых DDL/admin; внутреннее разрешение для доказанно безопасного
автопрочтения; иначе решение человека. Режим прав, remember и provider auto-allow этот
рубеж не обходят. Результат помечается недоверенным, снимает управляющие
последовательности и честно ограничивается по целым строкам и байтам. Allowlist-аудит
ведётся для всех исходов и хранится 30 дней.

Движки сканируются из `server/src/lib/db/engines/` и сами объявляют capabilities,
анализ, фактические права, read-only, оценку, исполнение и отмену. Ядро и Vue не
ветвятся по имени СУБД. HTTP-модуль session-only и live-gated, UI живёт в единственном
ToolHost и использует общий EventSource.

Проверки, которые сами исполняются на сервере БД, идут только там, где способны
изменить решение: оценка (`EXPLAIN`) и запрос прав снимаются с запроса, прошедшего
формальный фильтр, и никогда — с текста, где найдена табличная функция или запрещённая
конструкция; при выключенном авто-чтении их нет вовсе. Иначе ClickHouse ради структуры
`url()`, `s3()` или `remote()` сходил бы в сеть ещё до решения человека. Найденные
конструкции показываются в карточке отдельной строкой, разбор движка не может вынести
исключение мимо журнала, а текст длиннее 20 000 символов отклоняется до живой записи.

Отмена принадлежит движку, но её последствие описано общим правилом: `cancel` называет
способ — `query` (снят сам запрос), `wait` (команда атомарна и снимать нечего) либо
`connection` (запрос снят только вместе с соединением). Последнее закрывает сессию:
показывать в панели живой ту, по которой уже не пройдёт ни один запрос, нельзя. Служебным
командам — `KILL QUERY`, `SCRIPT KILL`, сторож времени пишущего запроса — нужен свой
канал: рабочий занят самим ответом, поэтому сессия выдаёт движку `openStream`, а второй
сокет мимо туннеля ушёл бы напрямую и обошёл рубеж. Все каналы сессии закрываются вместе
с ней.

Host-aware Bash policy запрещает штатный DB-клиент с внешним host, но сохраняет
localhost, loopback и unix socket; неизвестная форма блокируется только строгим
тумблером. Список имён покрывает и штатные алиасы — `mariadb`, `valkey-cli` и единый
бинарь `clickhouse` с подкомандой `client`; `clickhouse local` сети не открывает и
разрешён. Обёртки запуска снимаются до разбора: кроме `command`, `exec`, `nohup`, `env` и
`sudo` — это `setsid`, `time`, `nice`, `ionice`, `stdbuf` и `timeout` вместе с его
длительностью. Claude/Codex/DeepSeek применяют server-owned command-hook. Kimi host server использует command-broker с тем же разбором до запуска команды;
обычный текст проходит при включённом плагине БД. Внутренний ACP host при активной
DB-политике возвращает `direct_db_policy_unavailable` до build/spawn во всех режимах прав;
contained по-прежнему закрыт network/egress-песочницей.

## Telegram-пульт и companion

Телеграм-пульт **смотрит, разблокирует и поручает**. Постоянная клавиатура задаётся как
`ReplyKeyboardMarkup` с `is_persistent` и `resize_keyboard`: 📋 Конвейер, 💬 Агент,
📥 Задачи, ⚙️ Ещё. `setMyCommands` использует scope `BotCommandScopeChat` только в личке.

Общий companion создаётся через `store/ensure` с `purpose: companion` и `taskId: null`.
Обычный ход имеет `mode: auto`; `dontAsk` и `bypassPermissions` никогда не обходят запрос
решения. Тихий прогресс использует `sendChatAction` со значением `typing` каждые 30 секунд
и кнопку «Стоп». Память управляется через `/api/chat/compact` и
`/api/chat/session/reset`; голос отвечает «услышал: …» в одном ответе. `/api/chat/active`
показывает обрыв при перезапуске.

Companion-чат — обычная запись истории с server-owned `logicalIdentity`
(`companion:global` или `companion:task:<id>`): её создаёт только `store/ensure`, обычный
PUT не вправе назначить или перепривязать `purpose`/`taskId`, а ход по такому чату обязан
идти тем же маршрутом, что его identity (`/api/chat` для общего, `/api/tasks/<id>/chat`
для задачного). Отдельной компактной поверхности, быстрого хода `companionTurn` и
браузерной озвучки у GrigDesk больше нет: разговор ведут страница «Чаты» и пульт, модель и
усилие принадлежат самой записи чата. Недоверенный текст не получает инструменты или
сессию.

## Остановка и перезапуск сервера

Сервер ловит SIGTERM и SIGINT; остановку ведёт координатор (`server/src/lib/shutdown.ts`),
в него же уходит кнопка «Настройки → Сервер → Перезапустить» под systemd. Порядок один для
всех путей: сначала шаги слива при ещё работающем сервере, затем штатное `app.close()`,
затем выход. Общий бюджет — `GRIGDESK_SHUTDOWN_TIMEOUT_MS` (по умолчанию 30 с); по его
истечении процесс выходит с кодом 1, повторный сигнал завершает его немедленно.

Слив чата: новые ходы получают `503 server_restarting`, в том числе сообщения, дождавшиеся
очереди уже на остановке. Идущим ходам даётся 5 с закончить самим, потом их прерывают тем
же путём, что кнопка «стоп»; ответ такого хода помечен `stopped` и
`interruptedBy: server_shutdown`, несёт ленту шагов и id сессии и доезжает окну обычным
ответом или через `chats/pending`. Ход, не ответивший на прерывание за 10 с, записывается в
`chats/pending` сервером с той же меткой. Процессы исполнителей пул закрывает уже в
`onClose`, после слива.

Id сессии исполнителя сообщается с первого события хода, а не только с итогом: сервер держит
его в записи активного хода и рассылает SSE `chat-session {chatKey, sessionId}`; окно
применяет его только к идущему ходу. Следующее сообщение после перезапуска продолжает ту же
сессию исполнителя (`--resume`, `thread/resume`): транскрипт CLI живёт на диске отдельно от
GrigDesk. У сообщения с меткой прерывания чат предлагает «Продолжить ход» — обычное
сообщение в ту же сессию, только когда чат свободен.

Та же метка, но со значением `interruptedBy: delivery_failure`, стоит у ответа, который
оборвал сам CLI, не дойдя до модели (сеть, TLS, 529, недельный лимит): исполнитель отдаёт
`deliveryFailure`, сервер кладёт ход в историю плашкой ошибки с лентой и id сессии, а чат
рисует ту же кнопку. Текст продолжения зависит от метки: после перезапуска агенту говорят о
перезапуске, после обрыва CLI — что ответ не дошёл; хвост один — сверить сделанное и довести
работу. Ответа без известной метки кнопка не касается.

Юнит systemd работает с `KillMode=mixed` и `TimeoutStopSec=45`: SIGTERM получает только
главный процесс, исполнителей закрывает он сам. `deploy/restart.sh` после SIGTERM ждёт
освобождения порта до 45 с и лишь потом бьёт SIGKILL. Правка юнита применяется
`deploy/install.sh` (перерисовка шаблона и `daemon-reload`).

## Автозапуск и ярлык

Автозапуск — состояние самого юнита плюс linger: `enable` без linger поднимает сервер только
при входе в сессию, с linger — при включении машины, до входа. Оба читает и переключает
`server/src/lib/launcher.ts` (`GET /api/system/launcher`, `PUT /api/system/launcher/autostart`),
а показывает карточка «Настройки → Сервер». Переключение идёт `enable`/`disable` БЕЗ `--now`:
решение о старте после перезагрузки не трогает живой процесс. `loginctl enable-linger`
вызывается только когда linger ещё нет, и его отказ (без сессии право не выдаётся) не
отменяет операцию — режим честно остаётся «при входе», о чём карточка и говорит. Состояние
`unit: missing` означает, что юнита нет вовсе: переключать нечего, нужен `deploy/install.sh`.

Ярлык GrigDesk — один `.desktop` на рабочем столе и в меню приложений; обе копии пишет
`deploy/shortcut.sh` (`install`/`remove`/`status`), и это единственная реализация: её зовут и
установщик по ответу человека, и кнопка в настройках через
`POST`/`DELETE /api/system/launcher/shortcut`. Если установлены AppImage окна и его
`runtime.json`, `Exec` ведёт прямо в AppImage: окно само проверяет и при необходимости
запускает [свой сервер](../server/desktop-owned-server.md), Node в PATH не нужен. До установки
новой сборки (переходный режим) `Exec` ведёт в `deploy/shortcut.sh open` и несёт
`GRIGDESK_NODE_DIR` — сессия рабочего стола не знает nvm-каталог Node. Действие `open` ставит этот
каталог первым в PATH и
вызывает `bin/grigdesk-ctl open`: команда запускает установленное
[локальное окно](../web/desktop-window.md) с адресом `127.0.0.1`, а без `runtime.json` затем
запрашивает `systemctl --user start --no-block`. Отказ единой команды показывает уведомление с
причиной из stderr; отсутствие окна даёт подсказку `grigdesk-ctl desktop install`. Ярлык,
созданный до установки, ведёт в `deploy/shortcut.sh open`; установка окна сама переписывает его
Exec (`deploy/shortcut.sh refresh`), вручную — `deploy/shortcut.sh install` или кнопка в настройках.

`grigdesk-ctl desktop install` пишет `runtime.json` (корень копии и Node), затем атомарно копирует
готовый AppImage в `bin/grigdesk-app` копии; сборку команда не запускает.
`grigdesk-ctl desktop remove` удаляет окно и `runtime.json`, профиль и настройки окна сохраняются. [Единая команда](../server/grigdesk-cli.md) описывает
состояния, коды и защиту хода агента.
