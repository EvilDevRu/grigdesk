# Собственные задачи GrigDesk

Собственные задачи включены в общий список «Мои задачи» и отмечены чипом GrigDesk.
Порядок, фильтры и личные метки описаны в [контракте общей доски](unified-board.md).
«Новая задача» в общей шапке открывает форму названия,
обычного текстового описания и проекта с доступным конвейером. Оценка начинается
только по кнопке в карточке; сохранение не расходует ресурсы оценщика.

Без подключённого трекера доска показывает общий список и баннер настройки.
Ошибка подключённого портала не закрывает задачи GrigDesk.
Вложения, редактирование сохранённого текста и импорт старых ручных тикетов сюда не входят.
Входящие, «Видео» и мобильный фасад продолжают создавать задачи Б24.

## API и хранение

Все маршруты закрыты общим auth guard:

- `GET /api/grigdesk-tasks` → `{tasks,revision,trackerConfigured,personalStateVersion:1}`; summaries без описания.
- `GET /api/grigdesk-tasks/projects` → `{projects:[{id,title}]}`: существующий профиль,
  неархивный проект и непустой опубликованный каталог маршрутов.
- `POST /api/grigdesk-tasks` принимает только `{title,description,projectId,clientOrigin}`;
  ответ 201 `{task,revision}`. Проект повторно проверяется под `withReferences`.
- `GET /api/grigdesk-tasks/:id` возвращает собственную запись либо точный
  `404 {error:'grigdesk_task_not_found'}`. Этот маршрут никогда не читает Б24;
  неисправное хранилище даёт 503.

Запись содержит `id,source:'grigdesk',title,description,projectId,projectTitle,sourceUrl,createdAt`.
Документ `{schemaVersion:1,revision,nextId,tasks}` лежит в `config.grigdeskTasksPath`
(по умолчанию файл `grigdesk-tasks.json` в каталоге состояния данных;
переопределение `GRIGDESK_TASKS_PATH`). Только ENOENT означает новое пустое хранилище.
Межпроцессный directory lock охватывает чтение, резерв номера и публикацию уникального
временного файла через rename; новый файл имеет mode 0600. Успех возвращается после записи.
После commit сервер публикует `grigdesk-tasks-changed` в общий SSE. POST сразу обновляет
список клиента, а чтения сериализуются с повтором после события в полёте. Ревизия не даёт
старому GET откатить подтверждённое создание.

## Номер

Диапазон монотонный: `100000000000..999999999999`. Он проходит контракт тикета,
карточки арбитра и окна задачи. Наличие диапазона не заменяет проверку занятости.
Проверяются собственные записи, служебный диапазон песочниц и технические имена в корнях
состояния и его архива, оценок, тикетов, песочниц, slots, protocol-v2/tasks и артефактов.
Содержимое чатов, логов и рабочих деревьев распределитель не читает.

Резерв совместим с ручным протоколом: `analysisDir/t<ID>.status.json`, `wx`, `null\n`.
Он не является queued/running/failed оценкой. EEXIST заставляет выбрать следующий номер;
после неудачной записи свой резерв остаётся занятым. Неизвестная ошибка корня запрещает выдачу.

Номер проверяют все сохранённые включённые внешние драйверы через общий фасад.
Недоступный включённый пакет означает unknown, а не отключённую проверку; exists
хотя бы одного имеет приоритет. Без включённых внешних own-создание полностью локально.
Только совпавший ID означает exists,
а явный `success:false` с точным `Задача не найдена` или `TASK_NOT_FOUND` — absent.
Сеть, авторизация, доступ, пустые детали, чужой ID и неизвестный формат означают unknown:
создание возвращает `503 task_number_unverified`. Выключенные драйверы не опрашиваются.

## Карточка и ссылка

Источник собственной задачи подтверждается записью, а не существованием тикета.
Для номера вне 12-значного диапазона клиент сразу читает прежний `/api/tracker/task/:id`.
Внутри диапазона сначала выполняется собственный GET; только ApiError 404 с точным кодом
отсутствия разрешает прежний запрос Б24. Ошибки и неверный DTO не разрешают fallback.
Оба запроса идут обычным транспортом устройства; серверного inject и внутреннего токена нет.
Карточка кешируется 30 секунд с учётом источника. Ответ предыдущей карточки не меняет текущий источник.

Собственная карточка показывает исходный plain text, проект, оценку и конвейер.
Таймер, редактирование, комментарии портала, завершение/возобновление скрыты. Избранное, полка, markSeen и acknowledge
используют постоянное собственное пространство grigdesk.
Общий `ui.openTask` сохраняет отдельное окно desktop и диалог браузера/Android.

`clientOrigin` передаётся формой явно: только http(s) origin без credentials, пути,
query и hash. Host/Origin транспортной трубы не подходят. Сервер не загружает этот адрес,
а сохраняет ссылку для авторизованной установки создания. Новый клиент с sources=1
получает openTask=grigdesk:<id>, прежний — числовой openTask=<id>.
Ссылку обрабатывает существующий общий обработчик openTask.

Подробности совместимости и ограничения внутри диапазона — в
[контракте маршрутизации чтения](task-source-routing.md).
