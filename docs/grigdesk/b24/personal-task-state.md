# Личное состояние задач: избранное, полка и просмотренное

Все три механизма — **свойство человека, а не задачи**: в портал они не пишутся вовсе, живут в
state GrigDesk и потому одинаковы на всех его окнах. Открыл задачу на компьютере — на
планшете она перестала быть новой; localStorage такого не умеет, отсюда серверное
хранение.

| метка | API | файл state |
|---|---|---|
| избранное («звезда») | `GET /api/b24/task-favorites`, `PUT`/`DELETE .../:taskId` | `task-favorites.json` |
| полка («жду событие») | `GET /api/b24/task-shelf`, `PUT`/`DELETE .../:taskId` | `task-shelf.json` |
| просмотрено («новая») | `GET`/`POST /api/b24/task-seen` | `task-seen.json` |

Общее устройство (`lib/task-{favorites,shelf,seen}-{store,service}.js`, модули
`modules/task-{favorites,shelf,seen}/`):

- **scope клиент не выбирает** — он выводится из текущей портальной сессии
  (`b24AccountScope` = sha256 от нормализованного адреса портала и id пользователя) и
  наружу отдаётся только opaque-хешем. Попросить чужой набор нечем; смена аккаунта
  портала сама даёт другой набор, а не подмешивает метки прежнего.
- Файл — `{schemaVersion, scopes: {<scope>: {revision, …}}}` в `<папка данных>/state` (0600),
  запись атомарная (tmp+rename) и под общей promise-очередью: rename защищает от обрыва,
  но не от lost update при двух окнах разом.
- Ответ всегда полный снимок с `revision`; клиент применяет его только если снимок
  свежее (`applySnapshot`), иначе поздний ответ уже неактуального запроса вернул бы
  стёртую метку. Оба чтения отдаются с `Cache-Control: no-store`.
- Отказы названы поимённо: `400 bad_task_id`/`bad_request`, `503 b24_identity_unavailable`
  (не смогли определить пользователя портала), `503 task_seen_unavailable` (сохранённое
  не изменено), `503 task_shelf_unavailable` (полка не прочитана и не перезаписана).
  Кап набора отметок — 2000 задач, кап одного запроса — 1000 id; к полке эти два
  лимита не относятся, её entry ограничен собственной строгой схемой.

Полка хранит entry `{taskId,title,addedAt,reason,snapshot}`. `addedAt`, scope и revision
назначает сервер; PUT принимает `createIfMissing`, поэтому ручная/автоматическая постановка
создаёт запись, а acknowledge карточки обновляет только существующую. Удаляет запись только
DELETE: событие и просмотр ничего не снимают, а поздний acknowledge после DELETE её не
воскрешает. Ответ каждого GET/PUT/DELETE — полный `{scope,revision,entries}` с `no-store`.
Состояние готового триажа в `snapshot.analysis.state` называется `done`, как в самом
`Analyzer`; `finished` оставлен для совместимости с ранними снимками полки.
Запись и временный файл имеют режим 0600, commit идёт атомарным tmp+rename под одной
promise-очередью. Выключение плагина закрывает API живым `plugin_disabled`, но файл не
меняет; после включения прежний список возвращается. Полка не читает и не меняет
`task-favorites`: звезда и ожидание законно существуют одновременно.

**Базовая линия `initialized` — главный инвариант «новых».** Пустой набор отметок означает
«сервер ещё не ответил», а не «ни одной задачи не открывали»: без этого различия первое
же появление метки объявило бы новыми все давние задачи разом. Поэтому `initialized`
поднимает ТОЛЬКО запрос с `baseline: true`, и делает его ровно одно место — `board.load()`
после первого успешного ответа портала (`markBaselineSeen`; пустая доска тоже базовая
линия — иначе флаг не поднялся бы никогда). Во фронте это геттер `ready = loaded &&
initialized`, и от него зависит всё: метка «новая» в строке, счётчик «новые N», фильтр
«только новые» (кнопка `disabled`, пока отметки грузятся) и `unseenCount` сводки активности и счётчика навигации
(`shared/boardActivity.ts` принимает `{ ready }` третьим аргументом).

Снимается метка **только открытием карточки задачи** (`TaskModal` → `seen.markSeen([id])`) —
заход на доску не считается просмотром, иначе метка гасла бы у всего списка сразу.
Отказ отметки на показ задачи не влияет: действие возвращает `false` и не бросает, а
человек видит плашку с кнопкой «Повторить» над списком.
