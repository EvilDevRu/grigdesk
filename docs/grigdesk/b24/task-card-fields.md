# Необязательные поля карточки задачи

Карточка читает нейтральный DTO драйвера контракта 1. Все перечисленные расширения
необязательны: собственные задачи и другие драйверы, включая Jira, продолжают работать
без них. Версия общего контракта не меняется. Поля Б24 интерпретирует пакет,
ядро отображает готовые данные и проверяет контейнеры.

## Детали задачи

| Ключ | Формат и поведение карточки |
| --- | --- |
| `statusText`, `status_label` | Статус: первая непустая подпись в указанном порядке |
| `priority_label`, `priority` | Готовая подпись либо перевод числового 0/1/2 |
| `deadline` | ISO со смещением или `null`; авторитетнее снимка доски, даже при снятии срока |
| `creator`, `responsible` | Объекты с `name` и необязательным `icon`; HTTPS-аватар с no-referrer, ошибка скрывает изображение |
| `accomplicesData`, `auditorsData` | Массив объектов `{name}` или карта таких объектов; имена через запятую |
| `checklist` | Карта id → пункт; дерево по `parentId`, сортировка соседей по `sortIndex` |
| `parentId` | Положительный номер родителя; переход через общий `ui.openTask` |
| `replicate` | Строка `Y` включает бейдж «Регулярная» |

Пункт чек-листа содержит `id`, `parentId`, `title`, `sortIndex`, `isComplete`, `isImportant`.
Корень имеет `parentId` 0 или `"0"` и означает именованный список без чекбокса.
У вложенного пункта только `isComplete === "Y"` отмечает чекбокс;
`isImportant === "Y"` показывает звезду. Раздел показывает число завершённых пунктов из общего количества,
исключая корневые заголовки. Без возможности `checklist` он остаётся доступен только
для чтения. Сироты и повреждённые циклы отображаются один раз без зацикливания.
Пустой раздел чек-листов скрыт только без возможности редактирования; при её наличии
остаётся кнопка создания первого списка.

`formatDateTime` использует язык UI и часовой пояс устройства; например,
«5 ноя 2026, 19:00». Невалидная или не ISO-строка даёт пустую строку. `deadlineState` определяет
просрочку по моменту, затем сегодняшний срок по локальным суткам, без UTC-границы.
Если ISO-поля деталей нет, прежняя готовая подпись срока доски сохраняется даже без
распознаваемой даты; её `overdue` остаётся запасным состоянием старого драйвера.
Явный `null` или ошибочная дата в деталях не подменяются устаревшим сроком доски.
Просроченное время сегодня тоже означает «Просрочена». Огонёк обозначает горящий
дедлайн: сегодня или уже прошёл. Поля срочности `urgent` в REST Б24 нет.

Форма правки хранит местные дату и время в `datetime-local`. Только изменённый срок
уходит через HTTP как ISO-строка; очистка даёт `deadline: null`. Нетронутый срок
не пересериализуется, сохраняя исходные секунды. HTTP-валидатор принимает ISO с поясом
либо `null`, пакет переводит ключ в `DEADLINE`.

## Page-ответ

`taskPageData(id)` может вернуть дополнительно:

- `tags: string[]`;
- `subtasks: Array<{id, title, statusText?}>`.

`GET /api/tracker/task/:id/comments` сохраняет прежний `comments` без системных записей
и аддитивно передаёт эти массивы, если они присутствуют. Карточка с поддержкой комментариев
читает один page-ответ после деталей и capabilities: теги и подзадачи появляются уже
на вкладке описания. Переключение к комментариям использует тот же результат.
При обновлении карточки page-ответ перечитывается. Смена задачи или драйвера очищает
дополнения и отсекает поздний ответ предыдущего запроса.

## Таймер и доска

Поля `timerRunning: boolean`, `timerStartedAt: number | null` (Unix-секунды),
`timerElapsed: number` (секунды) и `overdue: boolean` остаются необязательными.
В драйвере Б24 список выбирает `TIME_SPENT_IN_LOGS`; `overdue` истинен, когда срок
задан, прошёл и статус меньше 5. Строковые `group` и `responsible` списка сохраняют
[прежнюю проекцию](stock-board-projection.md), объекты деталей не сворачиваются.

## Проверенные REST-факты облачного Б24

`tasks.task.get` возвращает полную задачу: ISO `deadline` со смещением, `createdBy`,
`creator`, `responsible` как объекты `{id, name, link, icon, workPosition}`, участников,
`parentId`, `timeSpentInLogs`, `timeEstimate`, `allowTimeTracking`, `replicate`, `mark`
и карту чек-листа. `timeSpentInLogs` — строковое число **секунд**; `null` означает 0.

Старт — `tasks.task.starttimer {taskId}`; он также переводит статус 2 → 3.
Пауза и останов — `tasks.task.pausetimer {taskId}` с записью в elapsed-лог.
`stoptimer` и `gettimer` не существуют (22002). Портал вообще не отдаёт состояние
«идёт»: пакет знает только собственные успешные старты в локальной карте сессии.
Пауза удаляет запись; отказ REST не меняет карту, перезапуск и смена реквизитов её очищают.
Накопленное время берётся из портала, без догадок по возрасту сессии.

Тегов в `tasks.task.get` нет. Их возвращает старый `task.item.gettags {TASKID}`
массивом строк. Любая ошибка этого необязательного API даёт `tags: []` и не срывает
основной page-ответ. Подзадачи читаются `tasks.task.list` с фильтром
`{PARENT_ID: id}` и select `ID,TITLE,STATUS`, со всеми страницами по `next`
(проверено живьём: фильтр и select возвращают подзадачу; создание подзадачи
через `tasks.task.add` с `PARENT_ID` работает, но портал требует `RESPONSIBLE_ID`).

## Мутации чек-листа, тегов и приёмки

Контракт остаётся версии 1: необязательные возможности `checklist`, `tags`, `review`
по умолчанию выключены. Legacy fallback тоже оставляет их выключенными: прежние
драйверы не обязаны иметь новые методы. В драйвере Б24 0.1.6 эти возможности и `renew`
включены. Ядро не выбирает REST-метод по имени драйвера.

Мутации карточки проходят общий HTTP wrap с проверкой `x-grigdesk-tracker-generation`:

| HTTP | Тело | Метод драйвера |
| --- | --- | --- |
| `POST /api/tracker/task/:id/checklist` | `{title, parentId?}` | `addChecklistItem` |
| `PUT /api/tracker/task/:id/checklist/:itemId` | `{title?, complete?}` | `updateChecklistItem` |
| `DELETE /api/tracker/task/:id/checklist/:itemId` | — | `deleteChecklistItem` |
| `PUT /api/tracker/task/:id/tags` | `{tags: string[]}` | `updateTaskTags` |
| `POST /api/tracker/task/:id/approve` | — | `approveTask` |
| `POST /api/tracker/task/:id/disapprove` | — | `disapproveTask` |

Номер пункта и родителя состоит из цифр. Название — непустая обрезанная строка до
255 символов; `complete` строго boolean. Тегов не более 50, каждый — непустая
обрезанная строка до 100 символов; пустой массив означает очистку всех тегов.
PUT самой задачи принимает `accomplices` и `auditors`: массив положительных id,
`''` или `null` для очистки. Отсутствующий метод драйвера даёт понятный отказ без сети.

Проверено живьём на облачном портале:

- Старый `task.checklistitem.add {TASKID, FIELDS:{TITLE, PARENT_ID?}}` возвращает
  скалярный id пункта. Переименование — `.update {TASKID, ITEMID, FIELDS:{TITLE}}`.
  Отметка — `.complete {TASKID, ITEMID}` с `result: true`, снятие — `.renew`;
  удаление — `.delete {TASKID, ITEMID}` с `result: true`.
- Теги меняет только старый `task.item.update {TASKID, FIELDS:{TAGS:[...]}}`.
  В urlencoded пустой массив теряется целиком: для очистки отправляется `TAGS: ['']`.
  `UF_TASK_TAGS` нового модуля молча игнорируется.
- Возобновление — `tasks.task.renew {taskId}`, переход 5 → 2.
  `task.item.renew` не работает.
- Приёмка — `tasks.task.approve {taskId}`, переход 4 → 5; возврат —
  `tasks.task.disapprove {taskId}`, переход 4 → 2. Драйвер проверяет новый статус
  в возвращённой задаче. `tasks.task.defer` недоступен («Действие не доступно»),
  отложение не реализовано.
- Соисполнители и наблюдатели меняются через `tasks.task.update` с
  `fields.ACCOMPLICES` / `fields.AUDITORS`. Очистка отправляется строкой `''`,
  поскольку пустой массив также исчезает при urlencoded-сериализации.
  `accomplicesData` и `auditorsData` приходят **картой по id пользователя**.

Карточка блокирует действия на время запроса и показывает ошибки в общем сообщении.
Чек-лист после записи перечитывается из деталей, теги — из page-ответа; приёмка и
возврат обновляют детали и доску. Кеш не подменяется оптимистично. Если исходные теги не прочитаны, их полная замена
блокируется до успешного обновления карточки. Переименование
выполняется inline, удаление требует общего confirmDialog, добавление хранит родителя
своего списка. Участники выбираются множественно из уже загруженного справочника users.
Собственные задачи и драйверы без новых возможностей сохраняют прежний вид.

## UX чек-листов и тегов

Корневой узел Б24 — **название списка**, например «Чек-лист 1», без чекбокса:
это [живая семантика портала](checklist-roots.md). Карточка рисует строки глубины 0
заголовками с прогрессом «X из Y» по всем вложенным пунктам. Заголовки не учитываются
ни в своём прогрессе, ни в общей шапке секции; пустой список показывает «0 из 0».
Отметка завершения самого корня не влияет на прогресс.
Списки отделены рамками; название и прогресс находятся слева, действия — справа.
Завершённый пункт зачёркнут, его отметка остаётся доступной для снятия.

При `caps.checklist` рядом с заголовком доступны ✎ и ✕. Переименование открывает
inline-поле и явные «Сохранить» / «Отмена»; Enter сохраняет, Esc отменяет ввод.
Удаление списка проходит через общий `confirmDialog` с предупреждением «вместе с пунктами».
До подтверждения серверная команда не отправляется.

Внизу секции есть отдельная кнопка «+ Новый чек-лист»
(`data-role="checklist-add-list"`), доступная и при пустом дереве. Она открывает поле
«Название чек-листа», «Создать» (`data-role="checklist-create"`) и «Отмена».
Кнопка или Enter вызывает `addChecklistItem` **без `parentId`**. Отмена и Esc закрывают
форму без записи. Ошибка сохраняет введённое имя для повторной попытки.

Внутри каждого списка кнопка «+ Добавить пункт» открывает форму «Новый пункт»:
поле «Название пункта», явные «Сохранить» и «Отмена». Кнопка «Сохранить» или Enter
сразу записывает **текущий** пункт с `parentId` его списка; следующий пустой пункт
не создаётся. После успешного перечитывания форма закрывается, пункт появляется
в списке и показывается «Пункт «…» сохранён». Отмена и Esc очищают ввод без запроса.
Ошибка оставляет форму и текст для повторной попытки; запрос блокирует повторную запись.
Небольшой «+» у строки открывает такую же форму подпункта с подписью родителя.
Детали — в [контракте ввода пункта](checklist-item-editor.md).

При `caps.tags` рядом с полем «Название тега» есть кнопка «Добавить»
(`data-role="task-tag-add"`). Пустой ввод блокирует кнопку; Enter добавляет так же,
как нажатие. После успешного добавления поле очищается и получает фокус для следующего
тега. Чипы расположены отдельной строкой над компактной формой ввода.
Ошибка сохраняет ввод. Крестики удаления на чипах работают как прежде.
Запись блокирует повторные действия; отсутствие capabilities оставляет данные только
для чтения и скрывает формы мутаций.
