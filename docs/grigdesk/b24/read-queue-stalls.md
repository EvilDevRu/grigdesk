# Доступность интерфейса при медленном Б24

Раньше готовая identity проверялась внутри физической очереди портала. Избранное,
просмотренные задачи и полка ждали внешнее чтение, хотя их данные находятся локально.
Теперь подтверждённая identity текущих credentials возвращается до очереди.
Неизвестная identity определяется общим управляемым чтением; её ошибка сохраняет
прежний именованный отказ, а не подменяет данные пустым набором.

Чтение имеет общий срок 25 секунд от постановки в очередь до разбора тела fetch.
Одинаковые чтения объединяются только в одном экземпляре сессионного драйвера и версии операций;
постановка мутации меняет версию. Подписчики отменяются независимо, последний уход
прерывает работу. HTTP-отключение снимает подписку GET, включая холодную identity.
Таймаут не освобождает физическую очередь поверх ещё выполняющейся операции.

`invalidate()` отменяет старые чтения и identity. Поздние результаты проверяют signal
перед публикацией. Cookie-файлы разделены хешем нормализованного портала и логина;
прежний общий файл не импортируется. Готовый scope не сохраняется между запусками
и не выбирается клиентским запросом. Подробности — [жизненный цикл чтения](read-operation-lifecycle.md).

## Соединения телефона

Android ClientPipe обслуживает WebView по локальному HTTP/1.1. SSE и long-poll оболочки
занимают по соединению. Общий web-клиент допускает ещё два GET Б24: один портал и один
из трёх локальных маршрутов меток. Обычному API остаются соединения даже при удержанном
портале. Пауза backoff не занимает разрешение; мутации не получают новых повторов.

Механизм проверяется в изолированном Chromium с настоящим apiClient и синтетически
удержанными portal/SSE/shell: providers и избранное завершаются до освобождения портала.
Это не проверка конкретного телефона, Wi-Fi или причины недоступности настоящего портала.

Большой headersMs при маленьком serverMs сам по себе не доказывает проблему Wi-Fi/TLS.
Нужно сопоставлять старт попытки окна, incoming request, завершение и соседние чтения.
Сервер различает queued/started/request/headers/settled безопасным debug-журналом,
но не видит запросов, ещё ожидающих соединение в WebView. Отсутствие записи completed
не доказывает количество живых работ. Для состава соединений телефона нужен его Network/NetLog.

Серверные изменения требуют ручного перезапуска владельцем. Две клиентские полосы и
показ последнего снимка требуют сборки и установки нового совместимо подписанного APK.
Снимок остаётся только в текущей сессии интерфейса, без записи на диск.
