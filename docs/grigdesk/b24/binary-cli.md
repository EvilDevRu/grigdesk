# Команда tracker: один исполняемый файл, настройки, коды выхода и установка

Команда `tracker` нужна навыкам, хукам агентов и этапу SHIP фабрики. Исходник — TypeScript-пакет
`tracker/` (код в `tracker/src`); сборка превращает его в один исполняемый файл Node SEA `bin/tracker` —
ELF для Linux x64 на закреплённом официальном Node 24.21.0. Готовому файлу не нужны
установленные Node, curl и jq; лицензия Node вшита в него (`tracker --license`). С порталом команда
не говорит: каждый запрос идёт в локальный HTTP API GrigDesk
([граница B24](integration-boundary.md)). Команды и поля задачи — в
[CLI для агента и оператора](agent-and-operator-cli.md).

## Целевая доска

Команды `boards`, `analyze <id>`, `launch-options <id>`, `launch <id>` и флаг `--board <id>`
доступны в исходниках CLI. Новые команды с --board подтверждают полный source через context.
Без флага оценка и запуск сохраняют own-first/default, source из launch stdin не теряется.
Прежние команды, навыки и хуки сохраняют HTTP-контракт дефолтной доски и байты stdin create.
Адресный HTTP 404 не вызывает повтор на дефолте. Дубликат или пустой `--board` — код 2
до stdin и HTTP; остальные коды, сроки и запрет автоматического повтора сохраняются.
Обновление установленного бинарного файла требует отдельной сборки при поставке;
проверки задачи не пересобирают установленный CLI.

## Сборка

`npm --prefix tracker run build` собирает `<код>/bin/tracker`; нужны esbuild и postject из
devDependencies пакета (`npm --prefix tracker ci --include=dev`). Порядок шагов:

1. Платформа, кроме Linux x64, — отказ.
2. Архив Node берётся из кэша `tracker/.cache` и при каждой сборке сверяется с SHA256 из
   `tracker/build/node-runtime.json`. Нет архива или сумма не совпала — загрузка с nodejs.org:
   до пяти попыток с паузой 10 с, срок одной загрузки 120 с; в кэш попадает только архив с
   верной суммой.
3. Путь назначения ещё отслеживается git — отказ: файл около 120 МиБ ушёл бы в коммит.
4. esbuild собирает один CommonJS-bundle; любое предупреждение — отказ.
5. Закреплённый Node готовит blob SEA, postject внедряет его в копию того же Node. Конфигурация
   SEA запрещает расширять аргументы Node (`execArgvExtension: none`): `NODE_OPTIONS` готовый
   файл не применяет.
6. Готовый файл запускается с `--version` в пустом окружении; вывод обязан совпасть с версией
   пакета и закреплённого Node.
7. Публикация атомарна: копия рядом с целью, права 0755, rename. При любом отказе прежний
   `bin/tracker` остаётся целым.

Сборщик печатает путь, размер и SHA256 результата. Неверные аргументы — код 2, отказ сборки —
код 1 и `Сборка tracker не удалась: <причина>`. Флаги `--out-dir <каталог>` и
`--cache-dir <каталог>` заменяют умолчания `bin/` и `tracker/.cache/`; относительный путь считается
от текущего каталога процесса, а `npm run` запускает сборщик из `tracker/`. Промежуточные файлы
живут в `<кэш>/build-*` и удаляются после сборки. git не отслеживает `bin/tracker`, временные
`bin/.tracker-*.tmp` и `tracker/.cache/`.

## Запуск из дерева кода

`bin/grigdesk-ctl tracker …` исполняет собранный `bin/tracker`, если он есть и исполняемый, а без него —
исходник `node tracker/src/main.ts …` на Node из PATH (^22.19.0 либо >=24.0.0). Готовый файл
запускается через `exec`: если он завершился с ошибкой, исходник не запускается, и мутация не
повторяется.

Агенты получают `<код>/bin` первым в PATH и зовут `tracker` по имени; ссылка `~/.local/bin/tracker`
ведёт на тот же файл. Пока файл не собран, команды `tracker` по имени нет, а `bin/grigdesk-ctl tracker …`
работает через исходник.

`--help` (`-h`), `--version` и `--license` допустимы только единственным аргументом и не читают
настройки. `tracker --version` печатает версию пакета и исполняющего Node.

## Адрес и токен

- Заданы оба `GRIGDESK_URL` и `GRIGDESK_TOKEN` — папка данных и файлы не читаются; даже неверная
  `GRIGDESK_HOME` не мешает.
- Иначе читается файл настроек `GRIGDESK_ENV_FILE`, без неё — `<папка данных>/.env`
  (по умолчанию `~/.grigdesk/.env`). Файл разбирается как данные (`util.parseEnv`): нет файла —
  пустой набор, другой отказ чтения — код 1 с путём. Ключи `GRIGDESK_HOME` и `GRIGDESK_ENV_FILE`
  в файле запрещены.
- Адрес — `GRIGDESK_URL`, иначе `http://localhost:<порт>`, где порт — `GRIGDESK_PORT`,
  по умолчанию 8140. `GRIGDESK_URL` — HTTP(S) без учётных данных, query и fragment; конечные `/`
  убираются. Неверный адрес или порт — код 1 до HTTP.
- Токен — `GRIGDESK_TOKEN`, иначе содержимое файла `GRIGDESK_CLI_TOKEN_PATH`, по умолчанию
  `<папка данных>/state/cli-token`; пробелы и переводы строк по краям файла обрезаются.
- Экспортированные переменные важнее файла. Пустые `GRIGDESK_PORT` и `GRIGDESK_CLI_TOKEN_PATH`
  в окружении тоже перекрывают файл и дают умолчание; `GRIGDESK_URL` и `GRIGDESK_TOKEN` из файла
  не берутся.
- Правило общее с `grigdesk-ctl status`: `resolveRuntimeSettings` в `shared/runtime/runtimeSettings.ts`,
  папка данных — `shared/runtime/dataHome.ts` ([единая папка данных](../server/data-home.md)).
- Старую раскладку (`<код>/.env`, `<код>/server/.state/cli-token`) tracker не читает; у CLI
  `grigdesk-ctl` переходное чтение пока осталось.

## Запросы, вывод и коды выхода

Чтения и мутации доски идут в `/api/tracker/…` с заголовком `X-GrigDesk-Token`.
Оценка и запуск идут в `/api/tasks/<id>/analyze|launch-options|launch`; с --board перед ними
выполняется GET адресного context. Launch читает JSON-объект stdin один раз; неверный JSON,
не-объект и конфликт source дают код 2 до POST. `start <id>` —
renew с подавлением его ошибки, затем timer/start. Транспорт — `node:http` / `node:https` с
собственным агентом на каждый запрос, созданным без `proxyEnv`. Прокси не используются:
`HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, их варианты в нижнем регистре и `NODE_USE_ENV_PROXY`
не влияют на запрос. Повторов и переходов по redirect нет. Собственный срок простоя сокета —
300 с, столько же, сколько прежнее ожидание заголовков и очередной порции тела во fetch Node.
После ответа или отказа агент закрывается, процесс не ждёт освобождения соединений.

| Исход | Код | Вывод |
| --- | --- | --- |
| HTTP 2xx | 0 | тело ответа в stdout байт в байт |
| HTTP вне 2xx, в том числе 3xx | 22 | `Запрос к GrigDesk завершился ошибкой HTTP <код>: <причина>` |
| Сетевой отказ, обрыв тела ответа | 22 | `Не удалось связаться с GrigDesk.` |
| Заголовки или порция тела не пришли за 300 с | 22 | операция могла выполниться: проверить результат перед повтором |
| Нет токена | 1 | `Нет токена: <путь>.` до HTTP |
| Неверные настройки, не прочитан stdin `create` | 1 | причина до HTTP |
| Неверные аргументы | 2 | причина и справка |

При отказе stdout пуст, а причина по-русски — в stderr. Причина HTTP-отказа — поле `message`
JSON-тела сервера: читается не больше 64 КиБ тела, каждое вхождение токена соединения заменяется
на `***` до обрезки, управляющие символы C0, DEL и C1 — пробелом. Причина ограничена 500 знаками
с многоточием при обрезке. Неверный JSON, другой Content-Type и тело больше 64 КиБ дают пустую
причину. Без поля `message` сообщение кончается кодом HTTP (`… ошибкой HTTP <код>.`);
остальное тело не показывается. Простой 300 с, в том числе при чтении тела HTTP-отказа,
даёт предупреждение о возможно выполненной операции: мутация уже могла выполниться на сервере.
Успешное тело читается целиком до записи, поэтому обрыв после статуса
200 даёт пустой stdout и код 22. Закрытый получатель stdout (EPIPE) отказом не считается, другая
ошибка записи — код 1.

Прежняя bash-обёртка на `curl -sf` давала 22 только на HTTP ≥ 400, 7 на отказ соединения и 0 с
телом на 3xx; неизвестная команда завершалась кодом 1.

## Установка и обновление

`deploy/install.sh` вызывает `grigdesk_install_b24_cli` из `deploy/lib/tracker-cli.sh`:

- `npm ci --include=dev` в `tracker/` выполняется, если нет `tracker/node_modules/esbuild` или
  `tracker/node_modules/postject`: до пяти попыток с паузой 10 с;
- сборка выполняется всегда, даже при готовом `bin/tracker`;
- если пакеты уже были и сборка не удалась, helper предупреждает, выполняет `ci` с теми же
  пятью попытками и повторяет сборку один раз. После `ci`, уже выполненного в этом вызове,
  нового повтора нет; окончательный отказ `ci` или сборки возвращает код 1;
- после проверки, что `bin/tracker` появился и исполняемый, ссылка `~/.local/bin/tracker → <код>/bin/tracker`
  заменяется атомарно; обычный файл или каталог на её месте не перезаписывается — предупреждение;
- отказ шага tracker не прерывает установку: прежняя ссылка остаётся, установщик печатает команду
  повтора `bash "<код>/deploy/lib/tracker-cli.sh" "<код>" ~/.local/bin`, которая собирает файл
  и создаёт ссылку. В напечатанной команде все пути абсолютные и экранированы через `printf %q`,
  поэтому её можно выполнить из любого каталога, в том числе при пробелах в путях;
- `--unit-only` tracker не трогает.

Здесь `<код>` — абсолютный путь к корню GrigDesk. Прямой запуск `deploy/lib/tracker-cli.sh`
вызывает helper с переданными аргументами и возвращает его код; `source` только определяет функции.

Встроенное обновление (кнопка «Обновить», `grigdesk-update-worker`) tracker не собирает. Переход на
выпуск с собранным tracker убирает из дерева прежнюю bash-обёртку, поэтому после такого обновления
нужен `deploy/install.sh` или `bash "<код>/deploy/lib/tracker-cli.sh" "<код>" ~/.local/bin`.
Последующие обновления тоже оставляют прежний `bin/tracker` до пересборки.

tracker — часть серверной поставки: навыки и хуки агентов работают там, где сервер. Установщик окна
tracker не собирает.

## Проверки

- `npm --prefix tracker test` — проверка типов пакета вместе с `tests/tracker`, затем
  `tests/tracker/*.test.mts` через сторож памяти. Входит в `tests/run-all.sh`; нужны devDependencies
  пакета (`npm --prefix tracker ci --include=dev`).
- `npm --prefix tracker run test:sea` — медленный набор `tests/tracker/sea`, в run-all не входит. Он
  собирает свежий файл во временный каталог (архив Node копируется из `tracker/.cache` или
  скачивается) и проверяет его: запуск копии без исходников с пустым PATH, игнорирование
  `NODE_OPTIONS`, обход прокси при `NODE_USE_ENV_PROXY=1`, запросы через loopback, настройки
  папки данных, коды отказов и сохранность
  прежнего результата при неудачной сборке.
- `GRIGDESK_B24_TEST_BINARY=<файл>` — абсолютный путь к исполняемому файлу — проверяет его
  вместо свежей сборки; после прогона сверяется, что файл не изменился.
- Ветки `bin/grigdesk-ctl tracker` проверяет `tests/cli/entry.test.mts`
  ([песочница единой команды](../testing/cli-sandbox.md)), шаг установщика —
  `tests/tracker/install.test.mts` с заглушкой npm, состав `bin/` — `tests/docs/bin-layout.test.mts`.
