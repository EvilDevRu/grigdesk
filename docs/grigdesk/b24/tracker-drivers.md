# Принятые границы драйверов трекера

Задача №100000000000: драйверы трекера отделены от пользовательских плагинов.
Контракт допускает несколько активных драйверов; настройка доски ограничивает
выбор одним внешним рядом с постоянно доступными собственными задачами.

## Правила поставки, принятые владельцем

- Для установки использовать существующий полный git-установщик с целью
  `drivers/<id>` и независимым журналом. Механизм и проверенная часть подключения
  описаны в [политике установщика](../plugins/driver-installer-policy.md).
- Кастомный Б24 готовится отдельным внутренним репозиторием в выделенном корне
  драйверов, каждый драйвер — своя подпапка-репозиторий. Первый коммит, тег и
  публикацию после приёмки выполняет человек.
- Стоковый Б24 использует только исходящий REST с access token; регистрации
  inbound-webhook нет. Его приёмка проводится эмуляцией ответов облака,
  без живого портала.

Сессия и credentials остаются на сервере. Capabilities и сериализуемые числовые
виджеты входят в контракт трекера; код или HTML виджета в интерфейс не передаются.
HTTP `/api/b24/*` и CLI `b24`, собственные задачи и личные подборки остаются
границами ядра. Этот документ фиксирует принятый контракт задачи; факт завершения
всей миграции устанавливается приёмкой реализации.

## Реестр и выбор подключения

Общий bootstrap — `createTrackerRuntime` в `server/src/lib/trackers/runtime.ts`.
Приложение передаёт один экземпляр фасада потребителям и один сервис собственных задач
HTTP-модулю. Реестр допускает несколько активных id, а настройки доски оставляют own
и один выбранный внешний. Числовой `/api/b24/*` всегда адресует внешний источник.

`GET /api/trackers` возвращает drivers, activeIds, externalId и revision. Настройки
читаются через `/api/trackers/settings`; запись требует сессию браузера, JSON, свой Origin
и expectedRevision. Секреты живут в серверном CredsStore отдельно от файла выбора;
пустое поле секрета сохраняет прежнее значение. У custom сохраняется legacy-файл реквизитов.

Смена выбора публикует `trackers-changed` в существующий SSE. Подготовленное действие
Inbox фиксирует поколение до чтения обращения и проверяет его перед созданием задачи.
Новый web передаёт `x-grigdesk-tracker-generation` для мутаций карточки. Старые клиенты
без заголовка используют текущий выбор. Личные scope по-прежнему принадлежат ядру.

До импорта проверяются manifest, версия контракта, id папки, системные имена, дубликаты
и файловое дерево. Неудачный import тоже остаётся loaded: refresh не исполняет его повторно.
Lease установщика закрывает новые вызовы и ждёт принятые; reverted возобновляет допуск,
installed у загруженного модуля требует ручного рестарта, blocked оставляет его недоступным.
Recovery установщика выполняется перед scan/import. Отсутствующий выбранный драйвер
не доказывает отсутствие внешнего номера: own-создание отвечает task_number_unverified.

## Возможности и виджеты

Контракты данных находятся в `shared/trackers/`. Виджет содержит числовые KPI либо
ряды по периодам; подписи — буквальный текст или явные descriptors каталога переводов.
Общий renderer не выбирает виджеты по id поставщика. Пустой widgets не создаёт показатели
из compatibility-полей. Metadata карточки читается независимо от details: неизвестные
возможности закрывают действия, только HTTP 404 старого metadata API разрешает legacy fallback.

Own имеет create/projects. Встроенный stock имеет create/complete/users/projects;
остальные операции, включая вложения в create, отклоняются до сети. REST использует
только HTTPS origin, POST auth в теле, ограничение 30 секунд и запрет redirects.
Мутации не повторяются; внешний текст ошибки не публикуется, чтобы не раскрыть токен.

## Кастомный пакет и совместимость

`b24-custom` реализует прежний session/CSRF/upload протокол, разбор комментариев и вложений
HTML, таймер, complete/renew и показатели портала. Его runtime импортирует только Node
builtins и собственные модули. Type-only снимок контракта и копия чистого status helper
находятся в самом пакете. Ядро сохраняет только credentials, чистую валидацию полей задачи
и свой status helper для stock/mobile; портальных endpoints в `server/src` нет.

Протокольные проверки используют настоящий отдельный пакет. Если он подготовлен вне
стандартного соседнего репозитория, запуску явно передаётся `GRIGDESK_CUSTOM_DRIVER_DIR`;
см. [подготовку пакета для проверок](../testing/tracker-driver-package.md).

Compatibility-поля custom dashboard сохраняют прежние today/month/charts для HTTP и CLI.
Виджеты строятся пакетом из тех же данных; месячное completed_tasks берётся из явного итога,
а три графика сохраняют пользовательский и средний по отделу ряды по всем доступным периодам.
Own и stock не объявляют виджетов. UI рендерит только widgets, без вычислений полей портала.

Legacy `/api/settings/b24` читает и сохраняет реквизиты custom; проверка авторизации
обращается именно к нему, независимо от текущего выбора stock. Драйвер при такой проверке
не становится вторым активным внешним источником. Смена credentials закрывает допуск до
завершения старых вызовов, затем синхронно меняет secrets и поколение. Личные scope сохраняют
прежнюю формулу portal/user без добавления driver id.

Установка обновляет каталог, публикует trackers-changed и активирует вновь установленный
выбранный пакет. Загруженный заменённый runtime остаётся restartRequired до ручного рестарта.
Обновление не делает второй SSE и не перезапускает сервер автоматически.
