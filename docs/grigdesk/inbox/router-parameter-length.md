# Кнопки «Входящих» мертвы, а автомат работает = роутер режет :param на 100 символов

Симптом: в `/inbox` любая ручная кнопка («Поставить задачу», «Пропустить», «Вернуть на
разбор») отвечает ошибкой `is exceeding the max param length`, при этом автоматические
задачи создаются исправно. Расхождение сбивает с толку: очередь читается, автомат живой,
значит «Входящие работают» — а человек не может решить ни одного обращения.

Причина: дефолт `maxParamLength` у find-my-way (роутер fastify) — **100 символов**, а
`itemRef` обычной Telegram-карточки — около **220** (versioned tuple → JSON → base64url,
внутри `channel`, `accountRef` и вложенный `localBundleId`). Отказ приходит из роутера
**до** обработчика: `414 FST_ERR_MAX_PARAM_LENGTH`, гейт плагина не спрашивается, лог
модуля пуст. Автомат этого не видит, потому что `InboxAutoTasks` зовёт `InboxTaskService`
внутри процесса, мимо HTTP.

Правила:

- потолок задаётся один раз в `app.js` и **выражается константой кодека**
  (`INBOX_REF_LIMITS.encodedChars`, 8192). Число, вписанное руками, разошлось бы с тем,
  что кодек уже разрешает выдавать;
- **тест с коротким ref ничего не доказывает.** Баг прожил в наборе именно потому, что
  фикстуры дёргали `/api/inbox/items/item-ref/dismiss` — 8 символов вместо 220. Проверка
  обязана строить ref настоящим `encodeInboxRef`, а не выдумывать строку;
- симптом «автомат работает, кнопки нет» вообще стоит читать как «отказ раньше
  обработчика»: гейт плагина, авторизация, роутер. Смотреть `curl -i` на сам путь,
  а не логи модуля.

Сторож — `tests/server/inbox-api.test.js` (пара тестов: тот же запрос даёт 414 на дефолте
и доезжает до `taskService.dismiss` с поднятым лимитом; плюс статическая сверка `app.js`).
