# Activation и решения

Channel marker содержит нативную монотонную позицию и provider-time boundary. Message
eligible лишь внутри сохранённой epoch одновременно по обеим границам. Это не даёт поздней
доставке старого Telegram update или GitHub webhook перескочить activation за счёт новой
локальной sequence.

`inbox-state.json` имеет строгую owner-bound schema v1. Decision содержит collision-resistant
`decisionId`, version, activation epoch и sorted unique `messageRefs`; пересекающиеся
assignments запрещены. Пересборка bundle не меняет смысл решения: полный coverage даёт
`task`/`skipped`, частичный — `mixed`, отсутствие coverage — `new`.

Task/dismiss принимают только непустой точный subset текущих `new` сообщений. Silent
intersection запрещён. Reset возможен только для `skipped` и требует CAS по
`decisionId + version`; task reset невозможен, потому что B24-задача уже существует.
В интерфейсе это действие называется «Вернуть на разбор»: оно переносит выбранные
пропущенные сообщения из «Истории» обратно в «К разбору» и никогда не удаляет B24-задачу.
При stale CAS клиент перечитывает снимок и показывает обновлённую карточку вместо общей
необъяснимой ошибки.

Перед созданием задачи service проверяет B24 readiness ещё до чтения текста канала, затем
непосредственно перед вызовом B24 повторяет plugin/channel gates, generation, revision,
message contents, assignments, project и policy. Durable task decision записывается только
после B24 success. Если B24 ответил успехом, а commit решения стал неопределённым,
автоматический retry блокируется fail-closed до operator reconciliation.

Вложения выбранных сообщений проходят локальный `InboxAttachmentAnalyzer` до model triage
и до вызова B24. Voice/audio распознаются общим `SpeechRuntime`; video/video note дают
транскрипт и ровно `maxFrames` кадров (по умолчанию четыре).

**Кадры берутся по всей длительности, а не только по сменам сцены.** Детектор сцен
оставлен приоритетом ради смонтированных роликов, но его недобор ВСЕГДА дополняется
равномерной выборкой из середин интервалов (`extractSpanFrames` в
`lib/media/ingest.ts`). На записи экрана — а это основной формат багрепорта — детектор
бесполезен: изменение занимает крошечную долю кадра, и порог не помогает (замер на
записи «таблица → активный чекбокс»: `gt(scene,0.4)` и даже `gt(scene,0.1)` дают ноль
кадров). Прежняя схема падала оттуда в «хотя бы первый кадр», то есть модель видела
начало ролика, где действие ещё не началось, и про видео не узнавала ничего: задача
получалась пересказом текста сообщения с упоминанием имени файла. Первый кадр остался
только на случай нечитаемой длительности. Смена алгоритма производных артефактов
обязана поднимать `SCHEMA` анализатора — иначе уже разобранное вложение навсегда
осталось бы с результатом прежнего алгоритма.
Photo/image и растровые BMP/GIF/JPEG/PNG/WebP document/sticker становятся visual inputs
модели. TXT/MD/Markdown/LOG/CSV/JSON/XML/YAML читаются только как bounded strict UTF-8.
PDF, Office, animation, бинарный текст и прочие неподдерживаемые форматы не считаются
разобранными.

Текст Inbox и содержимое вложений считаются недоверенными. Триаж никогда не вызывает
обычный coding `executor.run`: режим `plan` не является sandbox от prompt injection.
Допускается только явно объявленный `runUntrusted` — одноразовый model-only transport без
coding tools, project/user rules, MCP, hooks, session и workspace. Claude запускается в
отдельном временном cwd с пустым набором tools и strict/safe config. Codex использует
свой безопасный model-only transport. Kimi/DeepSeek без объявленного безопасного
transport остаются fail-closed (`unsafe_model_provider`).

Visual path не попадает ни в prompt, ни в executor. Сервер разрешает realpath только внутри
`mediaDir/inbox-attachment-analysis`, открывает обычный файл без symlink, проверяет размер,
формат и сигнатуру и передаёт адаптеру лишь `{mediaType, base64}`. Выбранная модель обязана
объявить image modality, а transport — конкретный media type и предел изображений; иначе
результат `unsupported_media`, без молчаливого отбрасывания кадров. Эти capability входят и
в живую readiness автомата: несовместимая выбранная модель не показывается как `ready`.

Лимит одного обращения — 12 вложений и 80 МБ суммарно; Telegram дополнительно ограничивает
один файл 20 МБ. Успешный производный результат кэшируется под hash в `mediaDir`, provider
refs, token и native IDs в prompt, B24 и cache не попадают. Fingerprint учитывает текущие
speech-настройки, поэтому смена модели, языка или hotwords не возвращает старый транскрипт.
Cache ограничен 512 МБ и TTL 30 дней; старые временные каталоги удаляются, а key защищён
от GC до завершения анализа и чтения visual inputs моделью. Автомат всегда fail-closed:
неполный разбор оставляет item человеку.

**Причина неразбора обязана быть названа.** Канал возвращает по каждому пропущенному
вложению МАШИННЫЙ код (`file_too_large`, `attachments_too_large`, `too_many_attachments`,
`not_connected`, `download_failed`) плюс числа `sizeBytes`/`limitBytes`, а человеческую
фразу собирает GrigDesk (`lib/inbox/skipReason.ts`). Свободный текст ошибки провайдера
наружу не идёт вовсе: в него попадает URL с токеном, а показывать его предстоит в браузере
и в описании задачи; подробности остаются в журнале сервера. Список неразобранных вложений
уезжает и в отказ HTTP (`attachments: [{label, reason}]` при `attachment_analysis_required`
и `attachments_skipped`), и в публичное состояние автомата
(`worker.analysisRequired[].attachments`). Без этого «не удалось разобрать» одинаково
выглядело у потолка Bot API в 20 МБ (ожиданием не лечится) и у сетевого сбоя (лечится),
и человек не знал, ждать ли повтора. По той же причине разные тексты: у
`download_failed` фраза прямо зовёт повторить позже.

**До кода `download_failed` дело доходит только после повторов.** Скачивание вложения
идемпотентно (`getFile` и байты ничего не меняют на стороне Телеграма), поэтому канал
выдаёт этим вызовам право на две дополнительные попытки с паузами 0,5 и 1,5 с
(`retries` в `lib/telegram/api.ts`). Отказ самого Телеграма (`kind: 'telegram'`:
неверный токен, файл сверх предела) не повторяется никогда — ожиданием он не лечится, а
человек тем временем ждёт ответа формы. Отправка сообщений этого права не получает:
у неё нет idempotency key, и повтор означал бы дубль в чужом чате.

**Ручное создание при неполном разборе идёт через пояснение оператора.** Кнопка «Создать
задачу» отвечает отказом, карточка сразу открывает поле «что имелось в виду», и текст
уезжает полем `operatorNote`. Дальше обращение проходит обычный разбор: пояснение попадает
в prompt триажа отдельным блоком как достоверный источник (человек видел вложение в самом
канале), модель формулирует постановку, и только после этого создаётся задача. Само
пояснение всегда попадает в описание отдельной секцией, рядом с перечнем неразобранных
вложений — исполнитель обязан видеть, что видео не расшифровано и пересказ человека
является единственным источником его содержимого. Пустое пояснение не принимается, автомату
поле запрещено (`invalid_service_call`), а отказ или отсутствие модели ручную постановку не
запирают: суть уже сказана словами. Прежний булев `allowUnanalyzedAttachments` удалён — он
ставил задачу из голого текста сообщений, и обращение «на видео предложение по доработке»
превращалось в задачу без сути.

Автоматическая B24-задача после успешного разбора получает сформулированную моделью
постановку и source URL (для Telegram — ссылку на сообщение, если Telegram позволяет её
построить). Сырой transcript, имя модели и служебная подпись Inbox в описание не попадают;
модель, confidence и причина решения остаются в audit-записи decision.

**Что уезжает файлом на портал, решают две галки плагина Inbox** — `attachPhotos`
(по умолчанию включена) и `attachVideos` (выключена). Разбора вложений они не касаются
вовсе: речь, кадры видео и текстовые документы модель читает всегда, настройка ограничивает
только загрузку исходных байтов в B24. Стороны у неё разные по смыслу: **автомату выдаётся
ТОЛЬКО разрешённое** — человеческого суждения за ним нет, поэтому документы и голосовые он
на портал не отправляет ни при каких галках; **у человека настройка снимает запрещённое**, а
остальные выбранные им файлы прикладываются как раньше, в том числе при постановке задачи
с пояснением оператора. Пояснение — это согласие поставить задачу без машинного пересказа
содержимого, а не согласие залить видео на портал.

Группы считаются по `kind` вложения: фотографии — `photo`/`image` плюс `document`/`sticker`
с растровым расширением (картинка, присланная файлом, остаётся картинкой), видео — `video`,
`video_note` и `animation`. Настройка читается непосредственно перед загрузкой, а не в начале
хода: между materialize и порталом успевают отработать Whisper и model call, и из двух
прочтений верно то, что ближе к side effect.
