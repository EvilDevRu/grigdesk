# Telegram

Страница `/telegram` управляет bot token, `recheck`, `disconnect`, long polling, служебным
личным чатом, нативным архивом и allowlist `чат/тема → проект`. Telegram группирует сообщения
по МЕСТУ разговора — тема форума, а где тем нет, сам чат; окно тишины — 600 секунд. Байты вложений
materialize через Bot API лениво: перед автоматическим разбором либо при ручном создании
задачи. До этого в архиве остаётся только provider-owned ссылка на файл.

**Одно обращение = переписка одного места за окно тишины, а не реплика одного участника.**
Автора в ключе склейки нет намеренно (`inboxBundleKeyOf`): просьба и уточнение соседа
принадлежат одному поводу, и разведение их по карточкам ставило бы две задачи там, где
повод один. Живой случай: «когда сделаем пересчёт» и ответ «не раньше ПН» через сорок
секунд в одной теме форума приезжали двумя карточками — ключ нёс автора. Отдельных веток
у reply и media group тоже нет: и ответ, и части альбома лежат в том же месте, а своя ветка
у альбома, наоборот, ОТРЫВАЛА его от текста, отправленного рядом. Прежние ветки
`parent`/`thread-author` вдобавок разъезжались сами: reply на сообщение старше activation
или на остывшую связку получал уникальный ключ `['parent', <старый id>]`, который не
склеивал ничего и при этом отменял склейку по месту — три подряд идущих реплая давали три
карточки и три B24-задачи с потерянным между ними уточнением.

Цена решения названа честно: окно тишины скользящее, поэтому в живой теме, где пишут чаще
чем раз в десять минут, карточка растёт и приезжает длинной. Против этого работает то, что
уже есть, — модель отвечает планом разбиения на несколько задач, а человек выбирает
подмножество сообщений чекбоксами; нерешённые сообщения остаются в очереди.

Границу разговора держит только окно тишины: ответ на сообщение остывшей связки начинает
новое обращение и не дописывается в уже разобранную человеком карточку.

У каждого allowlist-правила есть выключенный по умолчанию opt-in
`notifyTaskCreated`. После успешного создания B24-задачи и durable commit решения общий
`InboxTaskService` просит Telegram channel отправить в exact исходный чат/тему plain-text
ответ с номером задачи, её названием и безопасной ссылкой на портал. Название обязательно:
номер не говорит, ЧТО из разговора уехало в задачу, а после разбиения карточки таких номеров
в чате появляется несколько подряд. Собрала его модель по недоверенному тексту, поэтому оно
схлопывается в одну строку (управляющие символы и переносы — в пробел) и режется по 200
символам; `parse_mode` не отправляется вовсе. При переполнении сообщения первой отбрасывается
ссылка, следом название — номер задачи остаётся всегда.
Это один post-commit path для ручной
и автоматической постановки. Сообщение отвечает на первое выбранное в authoritative порядке
сообщение (`reply_parameters`, для форума также `message_thread_id`); удалённый оригинал не
мешает отправке. Ошибка или timeout Telegram не отменяют уже созданную
задачу. Автоматического retry нет: Bot API не даёт idempotency key, поэтому после
неопределённого timeout повтор мог бы прислать дубль. Гарантированная доставка потребовала бы
отдельного durable outbox; текущий контракт — best effort, at most once.

**Но неудача доставки обязана быть видимой.** Раз повтора нет, сообщить в чат придётся
человеку — а он узнавал об этом только из журнала сервера. Поэтому успешный ответ `task`
несёт `notification: {enabled, sent, reason}`: `enabled: false` значит «правило ответа не
обещало», `sent: false` — «задача создана, ответ не ушёл». Причина словарная
(`unreachable` — не доехали, `rejected` — канал отказал, `failed` — прочее): свободный текст
отказа провайдера несёт URL с токеном и наружу не идёт вовсе. Карточка `/inbox` показывает
это жёлтой плашкой рядом с «Задача создана». Единственный рычаг против моргнувшей сети у
самой отправки — дать первой попытке дойти, поэтому её таймаут равен клиентским 15 с.

У того же rule есть отдельный additive opt-in `agentSearch`.

Он относится только к будущему внешнему корпусу канала.

Новый strict store сохраняет
exact owner-bound schema v2 с `accountRef` и verified `botId`. Старый ownerless файл
остаётся рабочим human allowlist, но любой сохранённый в нём `agentSearch` принудительно
читается как `false`: прежнее или пересаженное разрешение нельзя унаследовать. Первый новый
human write либо отдельный explicit agent-search CAS переписывает файл в schema v2;
несовпадение account/bot и malformed v2 дают fail-closed отказ. Новое правило также
нормализуется в `agentSearch: false`; human allowlist и обычный разворот ссылок от него не
зависят. Обычный `PUT /api/telegram/rules` не принимает это поле и при правке
остальных настроек сохраняет opt-in только для exact того же `project + chat/topic` scope.
Переключение доступно отдельной ручкой `PUT /api/telegram/rules/agent-search` с exact rule
ref, boolean `enabled`, `botId` и CAS по `expectedPolicyFingerprint`; включение в UI требует
отдельного подтверждения. Canonical SHA-256 fingerprint включает `accountRef` и всю
нормализованную policy, включая `agentSearch`. Fingerprint/CAS не подменяет будущие durable
policy epoch и `PolicyScopeFence`: до них отзыв не обещает дренирование уже начатого ответа.

Тот же allowlist защищает разворот `t.me`-ссылок в B24, тикете конвейера, чате агента и
триаже. Поддерживаются public `t.me/<username>/<message>`, forum-вариант с thread,
private `t.me/c/<internal>/<message>` и comment links; парсер не угадывает тип чата по
одному URL. Resolution идёт в строгом порядке: account archive → временный
`forwardMessage` в служебную личку с немедленным удалением → именованный отказ без текста
и имени запрещённого чата. Scope проверяется до network и ещё раз по найденному message;
ссылка разрешена только для чата/темы, привязанных к требуемому project.

Служебный чат хранится в namespace конкретного bot. Disconnect его не удаляет; возврат к
тому же bot восстанавливает настройку, новый bot ничего не наследует.

Архивные строки без position journal остаются доступной для разворота ссылок историей,
но не попадают в Inbox. Даже поздняя правка такой строки не превращает её в новое
post-activation обращение.
