# Релизы GrigDesk

Версия продукта хранится в корневом `VERSION` и имеет строгий формат SemVer
`MAJOR.MINOR.PATCH`. Версии `server/package.json` и `web/package.json` описывают
технические npm-пакеты и не являются версией продукта.

Стабильный релиз — аннотированный тег `v<VERSION>` на ветке `main`. Тег после
публикации не перемещается и не переиспользуется; исправление выпускается новым
patch-релизом. Теги с prerelease/build-суффиксами и lightweight-теги не входят в
стабильный канал обновлений.

Перед публикацией `tools/release-check` проверяет чистоту `main`, соответствие
`VERSION` тегу, синхронизацию с `origin/main`, тесты и production-сборку. Сам helper
не создаёт и не отправляет тег: аннотированный тег и GitHub Release публикуются
отдельным явным действием после успешной проверки — командой `tools/release` или руками.

Первый baseline-тег следует поставить на проверенный commit `main` после того, как
локальная история будет осознанно синхронизирована с `origin/main`. WIP-ветка для
этого не подходит. Версия baseline уже записана в `VERSION`, поэтому его ставит
`tools/release <VERSION> --push` без нового коммита.

## Выпуск одной командой

`tools/release patch|minor|major` поднимает `VERSION`, делает release-коммит
«GrigDesk: релиз vX.Y.Z», прогоняет те же тесты и production-сборку, что и
`tools/release-check`, и ставит аннотированный тег на проверенный commit. Явная версия
`tools/release X.Y.Z` работает так же; версия, равная текущему `VERSION`, выпускается без
нового коммита — так ставится baseline и повторяется выпуск после исправления.

Между релизами `VERSION` не трогают: число коммитов сверху последнего тега GrigDesk
показывает сам, в виде `vX.Y.Z+N.g<sha>`. Разряд выбирают по содержанию: patch — только
исправления, minor — новые возможности, major — несовместимые изменения контрактов.

До `tools/release publish` (или флага `--push`) наружу ничего не уходит: `main` и тег
отправляются одним атомарным push, затем через `gh` создаётся GitHub Release, если он
установлен и авторизован. `publish` можно повторять: уже отправленный тег и уже
существующий Release пропускаются, чужой тег с тем же именем — ошибка.

Условия те же, что у preflight: ветка `main`, чистое дерево, `origin/main` — предок
`HEAD`, тег `v<VERSION>` отсутствует локально и в origin, версия строго выше последнего
стабильного тега. `--dry-run` печатает план и заметки релиза, ничего не меняя;
`--notes FILE` задаёт текст тега и Release вместо списка коммитов с прошлого релиза;
`--no-github` пропускает Release.

Отказ тестов не создаёт тег и ничего не отправляет; release-коммит остаётся локально,
скрипт печатает команду отката и команду повтора. После публикации checkout стоит на
commit релиза, а запущенный процесс — на предыдущем: примените checkout в
«Настройки → Сервер» или перезапустите сервер, чтобы `running` совпал с релизом.

## Совместимость Node перед обновлением

Worker проверяет Node в распакованном целевом релизе до установки зависимостей,
fast-forward, замены действующего web-бандла и перезапуска. Отдельный процесс вызывает
`assertSupportedNode()` из целевого `server/src/lib/nodeVersion.ts` обычным Node,
без флагов родителя и `NODE_OPTIONS`. Так проверяются и требуемая версия, и возможность
исполнить TypeScript штатным запуском. Минимум версии берётся из целевого gate.

Старый worker получает ту же защиту через сохранённый JS smoke
`tests/server/grigdesk-release.test.js`, который он запускает в новом дереве до применения.
Этот вход должен оставаться JavaScript и требовать наличия gate. У старых релизов,
которые ещё не имели `nodeVersion.ts`, новый worker сохраняет прежний путь проверки.
При несовместимом Node обновление останавливается до стадии `applying`; сначала нужно
обновить Node, затем повторить установку релиза.

## Восстановление после ошибки

Подробный локальный статус задания хранится в
`server/.state/grigdesk-update.json`, краткий журнал без command output — в
`server/.state/grigdesk-update.json.log`.

- Ошибка dependency/build/smoke до стадии `applying` не меняет main, рабочие файлы
  и действующий web-бандл. После исправления причины проверку можно повторить.
- Если main уже fast-forward-нута, автоматического destructive rollback нет.
  Безопасный путь восстановления — собрать уже находящийся в checkout релиз через
  `deploy/install.sh` либо `bin/grigdesk-ctl build`, затем явно перезапустить GrigDesk.
- Резервные каталоги `web/dist.grigdesk-backup-<job>` и
  `server/node_modules.grigdesk-backup-<job>` удаляются только после того, как новый
  сервер подтвердил целевой SHA и новый process-instance. До подтверждения их не
  следует удалять.

Для отката версии не следует перемещать опубликованный тег или использовать
автоматический `reset --hard`. Выпускается новый patch-релиз либо выполняется
отдельная осознанная ручная операция с предварительной резервной копией.
