# Релизы GrigDesk

Версия продукта хранится в корневом `VERSION` и имеет строгий формат SemVer
`MAJOR.MINOR.PATCH`. Версии `server/package.json` и `web/package.json` описывают
технические npm-пакеты и не являются версией продукта.

Стабильный релиз — аннотированный тег `v<VERSION>` на ветке `main`. Тег после
публикации не перемещается и не переиспользуется; исправление выпускается новым
patch-релизом. Теги с prerelease/build-суффиксами и lightweight-теги не входят в
стабильный канал обновлений.

## Подготовка исходников

`tools/release-check` проверяет чистоту `main`, соответствие версии, синхронизацию
с `origin/main`, тесты и production-сборку. `tools/release patch|minor|major`
или `tools/release X.Y.Z` готовит release-коммит после проверок. `--dry-run`
печатает план, `--notes FILE` передаёт текст заметок. Публичные пакеты идут
по процедуре ниже. `--no-github` разрешён для явной отправки только исходников
и тега. Для пакетного выпуска тег создаётся после проверки сайта.

Между релизами `VERSION` не меняется. Patch предназначен для исправлений,
minor — для новых возможностей, major — для несовместимых изменений.

## Серверный SEA-комплект

Обычные `tools/release` и `tools/release-check` не собирают серверный SEA и не запускают
его тяжёлую приёмку. Для готового Linux-комплекта есть отдельная явная команда:

```bash
bash tools/server-sea-check /path/to/releases /path/to/cache
```

Она выполняет `build:sea`, затем весь `test:sea` по полученному `build-result.json`,
сохраняет код отказа и ничего не публикует. Архив Node с закреплённым SHA256 готовится
заранее; production npm staging использует отдельный cache. Команды и prerequisites —
[выпуск SEA](grigdesk/server/sea-release.md),
[контракт отдельной проверки](grigdesk/server/sea-release-gate.md).

## Совместимость Node перед обновлением

Worker проверяет Node в распакованном целевом релизе до установки зависимостей,
fast-forward, замены действующего web-бандла и перезапуска. Отдельный процесс вызывает
`assertSupportedNode()` из целевого `server/src/lib/nodeVersion.ts` обычным Node,
без флагов родителя и `NODE_OPTIONS`. Так проверяются и требуемая версия, и возможность
исполнить TypeScript штатным запуском. Минимум версии берётся из целевого gate.

Старый worker получает ту же защиту через сохранённый JS smoke
`tests/server/grigdesk-release.test.js`, который он запускает в новом дереве до применения.
Этот вход должен оставаться JavaScript и требовать наличия gate. У старых релизов,
которые ещё не имели `nodeVersion.ts`, новый worker сохраняет прежний путь проверки.
При несовместимом Node обновление останавливается до стадии `applying`; сначала нужно
обновить Node, затем повторить установку релиза.

## Восстановление после ошибки

Подробный локальный статус задания хранится в
`server/.state/grigdesk-update.json`, краткий журнал без command output — в
`server/.state/grigdesk-update.json.log`.

- Ошибка dependency/build/smoke до стадии `applying` не меняет main, рабочие файлы
  и действующий web-бандл. После исправления причины проверку можно повторить.
- Если main уже fast-forward-нута, автоматического destructive rollback нет.
  Безопасный путь восстановления — собрать уже находящийся в checkout релиз через
  `deploy/install.sh` либо `bin/grigdesk-ctl build`, затем явно перезапустить GrigDesk.
- Резервные каталоги `web/dist.grigdesk-backup-<job>` и
  `server/node_modules.grigdesk-backup-<job>` удаляются только после того, как новый
  сервер подтвердил целевой SHA и новый process-instance. До подтверждения их не
  следует удалять.

Для отката версии не следует перемещать опубликованный тег или использовать
автоматический `reset --hard`. Выпускается новый patch-релиз либо выполняется
отдельная осознанная ручная операция с предварительной резервной копией.

## CI-выпуск и публикация на сайт

Workflow `grigdesk-release.yml` запускается вручную. Отправка коммитов и тегов
сама по себе не начинает выпуск. Build Linux x64 собирает подписанный комплект
и отдельный .deb. При `channel=release` .deb и ZIP содержат полную локальную опись,
включая `control.tar.gz`. В dev .deb содержит лёгкий сетевой установщик.
Чтение и приёмка build artifact идут по ID. Публичный стабильный выпуск
продвигается через `grigdesk-promote.yml` после общей проверки всех целей.

Владельцу до первого stable dispatch нужно добавить `RELEASE_SIGNING_KEY`
в GitHub Environment `platform-candidate`. До stable publish SSH-ключ
для записи переносится в `RELEASE_SITE_STABLE_KEY` окружения `release-site-stable` для `main`.
После переноса владелец отзывает прежнее право записи из старых workflow
и проверяет допуск только нового ключа на сайте. Dev использует отдельный ключ.
См. [раскладку сайта и настройки](grigdesk/server/site-release-channel.md).

## Публичные загрузки GitHub

Процедура открывается после нативной приёмки и появления проверенного
`stable_assets`. Маршрут общего комплекта подключён в Actions. Для его
выполнения нативные сборщики и проверяющие должны предоставить файлы по
[контракту workflow](grigdesk/server/release-workflow-validation.md#контракт-нативных-сборщиков).
При успешном запуске девять файлов лежат в `grigdesk-stable-downloads-<run>-1`,
а ID отдельного proof указан в итогах того же workflow. Для каждого пакетного
выпуска применяются параметры и allowlist ниже. Перечень локального навыка `grigdesk-release` для старого
checkout применяется только к соответствующему старому checkout.

1. Оператор запускает `grigdesk-release.yml` из main на точном SHA с
   `linux=true`, `macos=true`, `linux-arm64=true`, `windows-x64=true`,
   `windows-arm64=true`, `android=true`, `channel=release`, `publish=false`,
   `test_mode=full`, пустыми skip и validation_run.
   До сборки сохранить в файле подписываемые release notes `{"ru":"…","en":"…"}` из
   утверждённого списка изменений. При dispatch передать через `-f notes="$(cat "$signed_notes")"`.
   Поля Notes в signed channel остаются пользовательскими изменениями этого выпуска. Записать run, commit, version,
   digest плана, ID каталога девяти файлов и отдельный ID общего proof
   `grigdesk-stable-proof-<run_id>-1`. Из verify взять доказательства и соответствующие ID. Чужой repo, другой SHA, отсутствие одного целевого verify
   или failure исходного run останавливают публикацию. Полный all run с publish=false
   должен завершиться успешно, чтобы штатный promote принял его.
2. В корне репозитория вывести `node tools/prepareGithubRelease.mts "$asset_dir"
   "$proof_file" "$release_sha" "$release_version" "$repo_slug" "$run_id"
   "$plan_digest" > "$asset_plan"`. Команда возвращает 0. Выходные пути — из того же
   download ID, не из checkout. До публикации владелец принимает целевые ОС по разделу «Приёмка владельцем».
   Для acceptance использовать точные файлы, а не пересобирать или менять их ключи.
   Подготовить англоязычный блок и русский details, затем существующие пользовательские
   «New» / «Fixed» и «Новое» / «Исправления». Ссылки идут в начале соответствующей локали,
   а текст изменений сохраняется в обоих языках. Затем добавить краткую установку:
   `sh ./grigdesk-install` для одиночного сетевого скрипта и
   `sh ./grigdesk-install --source-dir "$PWD"` из распакованного офлайн-ZIP на Linux/macOS,
   PowerShell-вызов `.\grigdesk-install.ps1 -SourceDir $PWD` из распакованного ZIP на Windows, apt для .deb
   и Android APK. Сетевому скрипту `--source-dir` не передают: без подписанных архивов
   рядом установщик отказывает `install_online_source_invalid`. Рядом с Windows сообщить
   о WSL2, с Android x86_64 — о проверке
   на эмуляторе. Технический блок содержит ссылку на run и область фактической приёмки.
3. До сетевой записи выполнить только читающие проверки пунктов 4–5 (состояние
   releases API, тег, уже загруженные assets) и сверить официальный активный
   индекс сайта; создающие действия этих пунктов (`gh release create`, upload)
   выполняются после promote в порядке пунктов. До записи на сайт также сверить
   локальный и remote tag, тип и разыменованный SHA.
   Для remote опросить точные `refs/tags/$tag` и `refs/tags/$tag^{}`: допустимо их
   совместное отсутствие либо наличие peeled-записи `^{}`, равной `release_sha`;
   unpeeled-запись аннотированного тега содержит SHA объекта тега и с commit
   не сверяется. Lightweight или другой peeled SHA останавливает
   выпуск до promote. Локальный тег при наличии должен быть объектом tag и разыменоваться
   в `release_sha`. Read-only preflight также проверяет draft и все уже загруженные файлы
   правилами пунктов 4–5. Недостающие файлы допустимы, чужой asset или несовпадающие notes
   останавливают операцию до promote. Уже публичный совпадающий GitHub-выпуск завершить
   без записи на сайт. Более новая активная версия останавливает операцию. По
   успешному общему run и `linuxBuildArtifactId` из proof запустить существующий
   `grigdesk-promote.yml` с `channel=release` и `publish=true`, передав точные source_run_id,
   artifact_id, version, commit, `digest=linuxManifestDigest` и `stable_proof_id`. Повтор упавшего promote после
   устранения причины использует эти же параметры. Затем проверить подписанный индекс сайта
   и HTTPS сетевой скрипт с прежнего version URL, сравнить SHA/размер с `assets[0]`.
   Аннотированный стабильный тег `tag="v$release_version"` создать только после проверки.
   Создавать тег только при отсутствии локального и удалённого тега. Если есть проверенный
   локальный-only тег, отправить его как есть. Если уже есть совпадающий remote, отправка
   не выполняется. Первичное создание и отправка, только в авторизованном выпуске:

   ~~~bash
   git tag -a "$tag" "$release_sha" -F "$notes_file"
   git push origin "refs/tags/$tag:refs/tags/$tag"
   ~~~

   Если существует, разыменовать и сверить `git ls-remote --tags origin "refs/tags/$tag^{}"`.
   Ровно одна запись должна содержать `release_sha`. При несовпадении остановиться.
4. Получить состояние releases API со всеми страницами и доступом на запись, отобрать запись
   ровно этого тега. Ошибка API отличается от отсутствия записи. При отсутствии записи
   `gh release create "$tag" -R "$repo_slug" --draft --verify-tag --title "GrigDesk $tag"
   --notes-file "$notes_file"`. При опубликованной записи только сверить и завершить без записи.
   При draft убедиться, что `prerelease=false` и notes совпадают с ожидаемым финальным файлом.
   Узнать ID по ответу API. Вести выпуск одному оператору, повторное чтение обязательно.
5. Получить все страницы `gh api --paginate "repos/$repo_slug/releases/$release_id/assets?per_page=100"`.
   Сравнить по `name`. Для имеющихся проверить `state=uploaded`, `size`, `label` и SHA в
   `digest` вида `sha256:<hex>`. При отсутствии digest сравнить скачанные байты из asset API
   по ID с `Accept: application/octet-stream`, без вывода токена. При пустом или частично
   обработанном файле остановить выпуск и оставить draft для отдельного восстановления.
   Для каждого отсутствующего файла использовать один кавычечный аргумент
   `gh release upload "$tag" -R "$repo_slug" "$asset_dir/$name#$label"`.
   Различие, чужое имя или лишний remote asset останавливает процедуру, `--clobber` не используется.
   После каждого отказа читать фактическое состояние удалённой записи перед повтором.
6. Повторно проверить SHA/size/labels, ровно девять частей, notes, состояние draft и тот же tag SHA.
   После успешных ворот `gh release edit "$tag" -R "$repo_slug" --draft=false --latest`.
   Проверить тем же API, что release публичный и latest. При сбое после вызова сначала
   прочитать факт публикации. В новую попытку не пересобирать байты и не переносить тег.
   Автоматический исходный ZIP и tar.gz GitHub отсутствуют в JSON API assets и проверяются
   в UI только как две дополнительные строки.

### Приёмка владельцем

Проверить нативные сборки на Apple Silicon, Windows x64/ARM64 с WSL2,
Linux ARM64, Android ARM64 и эмуляторе Android x86_64. Android использует
действующий prod-сертификат. При отказе штатного запуска весь выпуск ждёт
исправления. Перед первым dispatch прогнать actionlint для обоих workflow.

В одноразовой Linux VM с подготовленными зависимостями отключить сеть и
проверить чистую установку из ZIP и через `sudo apt install ./<file>.deb`.
Ярлык открывает обычный пользователь. Проверить профиль, режим, окно, службу,
повторный запуск и сохранность данных при удалении .deb. Проверить обновление
вторым ZIP в изоляции и официальным каналом после возврата сети. Повтор
старого ZIP после применения обновления не должен возвращать версию.
После авторизованного выпуска сверить девять файлов, подписи к ним, bilingual
notes, две строки исходников и переход по прежней ссылке latest.
