# Пользовательские плагины

Плагин = папка `<папка данных>/plugins/<id>/`:

- `plugin.json` — манифест: `{ "id", "api": 1, "name", "description", "version", "nav": {"path","label","icon","group?","order?"}, "web": "web", "settings": [{"key","label","type","options?","default"}] }`
- `server.js` — опционально: default-экспорт fastify-плагина, роуты под `/api/ext/<id>/…`. Регистрируется на старте сервера (вкл/выкл — рестарт).
- `web/` — опционально: своя страница (`index.html` и что угодно рядом, без сборки). Кокпит
  раздаёт папку под `/api/ext/<id>/web/` только включённому плагину и показывает страницу
  панелью-iframe в правой рейке (`nav.group: "dock"`) или страницей по ссылке в сайдбаре.
  Адрес страницы всегда `/ext/<id>` — `nav.path` у такого плагина не участвует. Страница
  живёт на том же origin с той же сессией и ходит в `/api/…` сама: в свои роуты из
  `server.js` и в общие ручки кокпита. Ядро её код не исполняет; снёс папку — пункт исчез.
- `docs/README.md` — опционально: документация плагина для агентов кокпита (раздел
  «Документация» ниже). Место постоянное, манифест его не настраивает.

Включение — «Настройки → Плагины» (по умолчанию пользовательский плагин выключен).

`placements` — `[{"slot","default?"}]`: слоты интерфейса, которые плагин умеет занимать
(контракт — `docs/cockpit/guide/plugins.md`); незнакомый слот пропускается с предупреждением.
Тумблеры мест — в настройках плагина. Пока у пользовательских плагинов нет кода веба,
размещения только объявляются.

Роуты `server.js` автоматически заперты в префикс `/api/ext/<id>/` (перекрыть системные пути
нельзя). Поле `api` — версия контракта (сейчас `1`); несовместимый плагин не поднимается.
Код плагина исполняется в процессе кокпита с его правами — устанавливай только доверенный.

`nav.group` выбирает размещение ссылки: `rail` — основная навигация (и значение по
умолчанию для отсутствующего/невалидного поля), `tools` — агрегатор «Инструменты»,
`dock` — правая рейка встроенных панелей. `nav.order` задаёт порядок внутри группы;
при равенстве элементы сортируются стабильно по подписи и id.

Пункт появляется только у ВКЛЮЧЁННОГО плагина, чья страница существует во фронте.
Страницы системных плагинов собраны в бандл; у пользовательского плагина страница — его
папка `web/` (выше). Плагин без `web` пункта в навигации не получает: ссылка вела бы в
никуда, и клиент честно её скрывает. Vue-код плагина в SPA не загружается: панель — общий
iframe, а произвольный код из JSON в реестр `shared/tools/registry.ts` не попадает.

## Документация

Документация плагина живёт в нём самом, а не в кокпите: она приезжает с пакетом и
уходит вместе с ним. Структура всегда одна:

```text
docs/
  README.md        — оглавление
  <тема>.md        — документы
```

Кокпит сам находит `docs/README.md` у включённых плагинов и в каждом ходе чата
называет агенту путь к оглавлению вместе с именем и описанием из манифеста. Выключил
или удалил плагин — его документация из подсказки исчезла. Агент Claude получает
право читать `docs/` без вопроса человеку, даже если разговор идёт в другой папке.

Оглавление устроено как README областей `docs/cockpit/`: заголовок, строка о том, что
делает плагин, затем разделы «Контракты», «Устройство», «Грабли» — по строке-ссылке
на документ. Документ — один факт или контракт, имя — короткое английское
`kebab-case.md`, текст — русский. Ссылки только относительные: установленная копия
лежит не там, где репозиторий. Документация едет на любую установку, поэтому в ней
нет секретов, путей и имён конкретной машины. `docs/` — обычная папка, `README.md` —
обычный файл: ссылка на их месте не принимается. Устройство —
[документация плагина](../docs/cockpit/plugins/plugin-docs.md).

## Версия для установки из git

Манифест может указать `minCockpitVersion: "X.Y.Z"` и
`install: { "npm": [".", "server"] }`. Каждый выбранный каталог содержит
`package.json` и `package-lock.json` v2/v3. Без `install.npm` корневой lockfile
выбирает корень автоматически. Runtime dependencies требуют lockfile; Git/file/URL
зависимости и workspaces не поддержаны. Npm scripts при подготовке не исполняются.
Пакет повторно проверяется после npm; подробности и пределы —
[контракт установки](../docs/cockpit/plugins/user-plugin-install.md).

Публикуйте тег `vX.Y.Z`, совпадающий с `version` в `plugin.json`; предпочтителен
аннотированный тег. Установленную копию не правят: разработка и выпуск версии
происходят в репозитории плагина. Рекомендуемый `.gitignore`:

```gitignore
node_modules/
__pycache__/
.runtime/
.env
.env.*
```

## Данные и остановка для замены

`options.dataDir` — отдельный каталог для долговечных данных, браузеров и cache.
Он остаётся на месте при update/rollback. `options.lifecycle` — mutable объект:
`busyReason` служит диагностикой, `prepareReplace(signal)` возвращает удерживаемый
lease. Плагин с фоновой работой обязан закрыть новый допуск, остановить своих
workers/внешних CLI и дождаться завершения до возврата lease. Один busyReason
этого не делает; legacy server без hook требует выключения и ручного рестарта.

Пример для плагина **без фоновых работ**; `replacing` также проверяют его изменяющие
handlers перед новым действием:

```js
let replacing = false;

options.lifecycle.busyReason = () => null;
options.lifecycle.prepareReplace = async (signal) => {
  if (signal.aborted || replacing) {
    throw new Error('Замена сейчас недоступна.');
  }

  replacing = true;

  return {
    async finish(outcome) {
      if (outcome === 'reverted') {
        replacing = false;
      }
    },
  };
};
```

`installed` и `blocked` сохраняют остановку до перезапуска. Не переносите этот
пример на измеритель с процессами: его атомарная остановка и восстановление —
отдельный контракт. Подробнее — [runtime lease](../docs/cockpit/plugins/plugin-install-runtime.md).
