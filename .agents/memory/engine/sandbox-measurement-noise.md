Замер wall-clock внутри песочницы задачи (`ars-sb-tNNNN-*`) не является доказательством
производительности. Измерено 2026-08-01: одинаковая работа при простое — разброс 5%,
при восьми занятых потоках из шестнадцати — разброс 76%, CV 22.7%, max/min = 1.76×.
Стенды (до восьми слотов) делят один mysqld/clickhouse/redis, буферный пул на всех общий,
лимита CPU у контейнеров нет; хост при этом уже держит ~14 ГБ в swap. Плюс в контейнере
загружен Xdebug (JIT выключен), включён Debugbar, фронт — vite dev-server, а не прод-сборка.
Данных в эталонной песочнице ~1.25 ГБ / 2.5 млн строк против 58 ГБ / 142 млн у донора —
кардинальности другие, планы запросов MySQL другие.

**Почему:** доказательство ускорения, снятое временем, на деле измеряет соседний стенд
и объём данных, которого в проде нет.

**Как применять:** primary-метрика — детерминированный счётчик, но перед выбором проверить,
что он вообще наблюдаем. Замерено 2026-08-02: `performance_schema.events_statements_summary_by_digest`
**не видит запросов приложения** (нативный prepared-протокол: тяжёлый запрос дал
`Com_stmt_execute` +340 и ноль SELECT приложения в дайджесте) — туда попадают только текстовые
запросы самого измеряющего. Побитово воспроизводимы: Debugbar `queries.nb_statements`,
`EXPLAIN ANALYZE actual rows`, `EXPLAIN FORMAT=JSON.rows_examined_per_scan`, байты бандла.
Не воспроизводимы: `memory_get_peak_usage` (первый прогон всегда другой), глобальные `Com_*`
(соседние стенды — ~145 запросов/с фона). Замеру предшествуют предвыданный токен и один
прогревочный запрос: логин пишет в `personal_access_tokens`, а `CACHE_STORE=database` на
холодном кэше добавляет лишний запрос. Бракет `baseline → правка → повторный baseline`
**невыполним**: песочница одна, после `build` в ней уже B, а `state-only` не может вернуть A —
вместо бракета фиксированный dataset и три идентичные выборки B. Связано
с [[route-v2-motivation]].
