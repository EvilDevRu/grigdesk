# Контракт профиля проекта

Движок фабрики (`factory`) ничего не знает о конкретном проекте: стек, БД, как поднять
стенд, чем тестировать — всё это даёт **профиль**. Профиль — это bash-файл в `profiles/<name>.sh`,
который движок подгружает (`source`) и вызывает его функции-хуки.

Добавить новый проект = написать `profiles/<name>.sh`. Движок при этом НЕ меняется.

Профиль может быть не одним файлом, а **файлом + каталогом `profiles/<name>/`** — туда кладут
проектное хозяйство, которое сам профиль только вызывает: скрипты подъёма/сноса стенда, озвучку,
склейку демо. Так устроен `arsenkin` (`profiles/arsenkin/up.sh|down.sh|lib.sh|prep-etalon.sh`).
Держать эти скрипты в репозитории проекта, а не здесь, — уже пробовали: рядом с ними завелись
копии движка со своим каталогом состояния, и отметки этапов уходили мимо дашборда.

Как перечитывается: **профиль подгружается заново перед КАЖДЫМ этапом** (`_reload_profile`
в `lib/core.sh`). Правка промпта, модели или бюджета подхватывается на следующем этапе живой
задачи — демона перезапускать не нужно. Битый файл (ошибка синтаксиса) игнорируется, работает
предыдущая загрузка, в журнал идёт запись.

## Обязательные переменные (профиль объявляет)

| Переменная | Смысл | Пример (arsenkin) |
|---|---|---|
| `PROFILE_NAME` | имя профиля | `arsenkin` |
| `PROFILE_CTX` | контекст стека для промптов агентов (стек, конвенции, запреты) | «Laravel 12 + Vue, мультитенант…» |
| `PROFILE_ROUTE_STAGES_feature` | список этапов маршрута feature (bash-массив имён статусов) | `(PLAN GATE_PLAN TESTS …)` |
| `PROFILE_ROUTE_STAGES_debug` | … debug (все баги: понять → доказать → чинить) | |
| `PROFILE_ROUTE_STAGES_trivial` | … trivial | `(BUILD REVIEW PHPCHECK LINT)` |

## Обязательные функции-хуки (профиль реализует)

Все получают `$1 = TASK` (номер/идентификатор задачи). Статусы пишутся движком; профиль
только выполняет проектную работу.

- `profile_sandbox_up <TASK>` — поднять изолированный стенд задачи (worktree, контейнеры, данные).
  Возврат 0 = успех. Идемпотентно (если стенд уже есть — ничего не делать).
- `profile_sandbox_down <TASK>` — снести стенд бесследно (чистый worktree удалить, схемы дропнуть).
  Сам движок его НЕ зовёт: стенд нужен человеку и после отгрузки (посмотреть результат, переснять
  демо), поэтому снос — только по кнопке «⏻ Снести стенд» на карточке задачи в дашборде.
- `profile_sandbox_exists <TASK>` — echo `1` если стенд поднят, иначе пусто.
- `profile_stage_prompt <TASK> <STAGE>` — вернуть (echo) ПОЛНЫЙ промпт для агента этого этапа
  (проектные команды: чем тестировать/линтить/строить, пути worktree, порты). Движок оборачивает
  его общим протоколом (правило «сделай ТОЛЬКО этот этап синхронно, выстави статус»).

## Опциональные хуки (движок имеет дефолт)

- `profile_route <TASK>` — если задан, вызывается вместо агента-роутера (echo `feature|debug|trivial`).
  Маршрут, которого нет в профиле, движок молча не примет: он логирует и ведёт задачу как `feature`.
- `profile_slots` — занятость слотов стенда для внешнего распределителя (`factory slots --profile <name>`
  печатает из этого JSON). Нужен, только если стенд проекта существует в нескольких экземплярах и
  индекс распределяется снаружи. Формат вывода — построчно:
  `RANGE <min> <max>` и `USED <k> <кто> <task|port|ip>`. Считать занятость обязан ТОТ ЖЕ код, что
  и подъём стенда: два независимых счётчика разойдутся, и распределитель отдаст занятый порт.
  Если занятость считается по файлу-реестру, снос стенда обязан снимать его ВЕЗДЕ, откуда его
  читает хук: пережившая снос копия держит индекс вечно, и слоты утекают по одному до нуля
  (так `arsenkin` 28.07.2026 потерял пять слотов из восьми — снос убирал симлинк, а не файл).
  Без хука `factory slots` выходит с кодом 2 — это нормально для проекта с единственным стендом.
- `PROFILE_ARCHIVE_ON_FINISH=1` — переменная: после финиша задачи движок сам уносит её реестр
  в архив. Для проектов без трекера, где карточка после отгрузки не нужна (так у `rdesigner`).

Хуков `profile_run_id` и `profile_report` **больше нет** — движок их не вызывает (были в раннем
дашборде). Если видишь их в профиле — это мёртвый код, `factory-check` о таком предупреждает.

## Что даёт движок (профиль на это опирается)

- `set_st <TASK> KEY VAL …` — менять реестр статусов (единственный способ).
- `get <TASK> KEY` — прочитать статус.
- `$STATE_DIR` — директория реестров (по умолчанию `~/.factory/state`; профиль может переопределить).
- Реестр этапов, ворота, resume, flock, таймауты, дашборд, watchdog — общие.

## Границы

- Провижн стенда (`up`/`down`) по своей природе проектный — он живёт в каталоге профиля
  (`profiles/arsenkin/up.sh`), а сам профиль — тонкий адаптер, который его вызывает.
- Движок никогда не хардкодит имена БД, контейнеров, команды стека, пути проекта.

## Что читает внешний потребитель (кокпит)

Дашборд задач в кокпите (`~/Workspace/cockpit`) грузит профиль сам и опирается на:

| Что | Зачем |
|---|---|
| `PROFILE_CTX`, `PROFILE_AGENT_CWD`, `PROFILE_AGENT_DIRS` | триаж задачи без стенда — агенту нужен контекст стека и доступы |
| `PROFILE_TRIAGE_REPOS` | корни git-репозиториев в виде `префикс:путь` (`be:/…/html fe:/…/www`); по префиксам считается протухание анализа |
| `PROFILE_TRIAGE_MARKERS` | проектные маркеры риска: каждый найденный в тексте задачи поднимает оценку |
| `factory slots --profile <name>` → `profile_slots` | резервирование индекса стенда ДО запуска |
| `profiles/<имя>.graph.json` | схема конвейера: узлы, координаты, рёбра, `optional` |

Движок эти переменные не использует — они контракт с кокпитом. Убирать их из профиля нельзя,
не проверив, кто ещё читает: `grep -rn PROFILE_TRIAGE ~/Workspace/cockpit/server/src`.

**Схема обязательна.** Кокпит строит по ней и список профилей, и граф прогона, а запасного
варианта у него нет: профиль без `graph.json` в кокпите просто не виден — запрос графа падает,
карточка задачи молча отфильтровывается. (Автосхему из этапов умел только старый дашборд
`lib/dashboard.py`, он выключен.) Заготовку делает `bin/factory-graph-new <имя>`.

Отдельно про **`optional`** — список этапов, чей `skipped` не аномалия. Движок это поле
**не читает вообще**: он принимает `skipped` от любого этапа и идёт дальше. По нему кокпит
решает, покрасить узел серым «пропущен осознанно» или красным «пропущен без причины — аномалия».
Вписывать туда стоит ровно те этапы, для которых пропуск разрешает промпт самого профиля;
пустой список — нормальный ответ («все этапы обязательны»). Причину пропуска движок требует
в любом случае — см. «Протокол статус-файла» ниже.

## Доступ агента (обязательно проверить при заведении проекта)

Агент фабрики запускается неинтерактивно: любой запрос «одобри действие» = этап не завершён
и повтор с нуля. Поэтому доступ выдаётся заранее, двумя РАЗНЫМИ механизмами.

| Что | Чем выдаётся | Кто отвечает |
|---|---|---|
| Каталоги, куда агент пишет | `--add-dir` | движок даёт `STATE_DIR` и свой каталог; проект — через `PROFILE_AGENT_DIRS` |
| Команды, которые агент выполняет | слой `--settings` | движок разрешает `pipeline-set.sh`; проект — через `PROFILE_AGENT_ALLOW` |

- **`PROFILE_AGENT_CWD`** — рабочий каталог агента. Всё внутри него доступно по умолчанию.
- **`PROFILE_AGENT_DIRS`** — каталоги ВНЕ cwd, куда агент обязан писать (у arsenkin это
  `be` и `fe`: worktree задач лежат рядом с cwd, а не внутри него). Строка, пути через пробел.
- **`PROFILE_AGENT_ALLOW`** — массив дополнительных разрешённых команд в формате правил
  Claude Code, например `PROFILE_AGENT_ALLOW=("Bash(docker exec ars-sb-t:*)")`. Слой
  добавляется ПОВЕРХ личных настроек пользователя, не заменяя их.
- **`profile_stage_model <STAGE>`** — модель этапа (пусто = модель сессии). Без неё весь
  конвейер идёт на самой тяжёлой модели: разведка одной задачи стоила 19 минут и $4.65.
  Разумно: поиск, прогон сценариев, скриншоты, линт — на быстрых моделях; планирование,
  диагноз, сборка, ревью — на сильной.

Проверить перед первым прогоном:

```bash
python3 tests/profile-access.py <профиль>    # статически: пути промптов покрыты доступом
bash    tests/agent-can-write.sh <профиль>   # вживую: агент реально выставляет статус этапа
```

## Хуки скорости и качества (необязательные, но без них конвейер дорог и медлен)

| Хук | Что задаёт | Если не объявлен |
|---|---|---|
| `profile_stage_model <STAGE>` | модель этапа (пусто = модель сессии) | всё идёт на самой тяжёлой модели |
| `profile_stage_budget <STAGE>` | ориентир времени, мин | агент копает до таймаута |
| `profile_stage_timeout <STAGE>` | жёсткий лимит, сек | общий `FACTORY_STAGE_TIMEOUT` (1800) |
| `profile_stage_fanout <STAGE>` | `AUTO <min>-<max>` + подсказка, либо список зон | этап идёт одним агентом последовательно |

Движок сам дописывает в промпт требования (распараллелить, уложиться в бюджет, назвать
непроверенное) и пишет факты в реестр: `DUR_<STAGE>` — длительность в минутах,
`FANOUT_<STAGE>` — сколько субагентов реально запущено.

## Хуки безопасности (появились после инцидентов 21–22.07)

| Хук | Что задаёт | Если не объявлен |
|---|---|---|
| `profile_agent_cwd <TASK>` | рабочий каталог агента — **worktree задачи** | агент работает в общем репозитории и складывает туда скриншоты, правит код мимо ветки, гоняет линтер по всему проекту |
| `profile_stage_readonly <STAGE>` | этап только проверяет и не должен менять файлы | побочные правки проверочного этапа (автофикс линтера) уезжают в дифф задачи |
| `profile_dirty_files <TASK>` | список изменённых файлов рабочих копий, строки вида `BE:path` / `FE:path` | контроль побочных правок не работает (проверять нечего) |
| `profile_revert_files <TASK> <список>` | как вернуть перечисленные файлы | движок ничего не откатывает (это и есть поведение по умолчанию) |
| `PROFILE_AGENT_DENY` | команды, запрещённые агенту наглухо | остаются только общие запреты движка (`eslint --fix`, `prettier --write` и подобные) |

**Как работает контроль побочных правок.** Перед этапом движок снимает список изменённых файлов,
после — сравнивает. Если этап объявлен `readonly` и что-то тронул: пишет поимённо в журнал,
помечает этап `failed` и **файлы не трогает**. Откат — только при `FACTORY_AUTOREVERT=1`, и тогда
неотслеживаемые файлы уходят в карантин `~/.factory/state/quarantine/tNNNN/`, а не удаляются.

**Почему запрет в тексте промпта не считается защитой.** «Линт без авто-фиксов» было написано
в контексте профиля — агент всё равно запустил `eslint --fix` и переформатировал 277 файлов
основного репозитория и 235 файлов в ветке задачи. Правила, нарушение которых дорого, должны
держаться механикой (запрет команды + проверка результата), а не формулировкой.

## Протокол статус-файла и маршрут (отладка 24.07, прогон #7803)

**Статус-файл этапа** `state/tNNNN.<STAGE>.status` (пишется агентом инструментом Write):
- первая строка — статус этапа: `done` / `failed` / `skipped`, у разведки допускается `done ROUTE=<маршрут>`;
- хвост первой строки после статуса — **причина**: `skipped правка целиком фронтовая, Pest тут
  ничего не сторожит`. Движок кладёт её в реестр как `<STAGE>_COMMENT`, кокпит показывает
  в модалке этапа. Тот же ключ можно передать командой:
  `pipeline-set.sh <TASK> <STAGE> skipped <STAGE>_COMMENT "<причина>"`;
- строки со второй — подэтапы, которые агент вёл внутри этапа: `KEY=done|skipped` по строке
  (план ведёт `PLANS/SKEPTIC/VALIDATE/TRANSLATOR`). Другого канала у headless-агента нет:
  bash ему не разрешён, а без этих статусов схема не красится и ворота показывают
  ложное «хвост не доделан».

**Пропуск без причины** движок дописывает сам: `<STAGE>_COMMENT=причина не указана — агент не
объяснил пропуск` плюс строка в журнале этапов. Комментарий этапа гасится на его старте, чтобы
замечание прошлого круга не сошло за объяснение нового пропуска. Прогон #7804: агент пропустил
`TESTS` на маршруте feature (правка была чисто фронтовая, Pest нечего было проверять) —
обоснование осталось в семимегабайтном журнале прогона, а человек видел на схеме голое
«пропущен без причины — аномалия» и не мог отличить его от «агент сдался».

**Приоритет маршрута** — `ROUTE_BY` в реестре: `human` > `escalation` > `scout`.
Скаутское `ROUTE=` из маркера применяется, только пока маршрут никем не закреплён; человек
(resume с `--route`) и эскалация сборки перебивают его насовсем. Без этого повторный скаут
на resume/replan откатывал `feature` обратно в `trivial` посреди работы.

**Эскалация маршрута этапом** (`pipeline-set ROUTE <новый> <STAGE> pending`): движок видит смену
маршрута в «этап без статуса», НЕ повторяет этап, а пересобирает цепочку нового маршрута
и идёт с первого несделанного этапа. Повтор этапа при смене маршрута — это баг #7803:
сборка feature-цепочки без плана и тестов.

**`--replan`** (reject ворот плана) сбрасывает план и весь хвост, но НЕ разведку; сбрасывает
оба ключа плана — движковый `PLAN` и агентский `PLANS` (stale `PLAN=done` пропускал
перепланирование).

**Ожидание ворот** (`gate_wait`) возвращает решение через переменную `GATE_DECISION`,
НЕ через `$(...)`: сабшелл блокирует TERM-trap демона — демона на воротах было не остановить.
