# Как менять кодовую базу фабрики

Инструкция для того, кто правит **сам движок** (человек или агент). Про заведение нового
проекта — соседний документ [NEW-PROJECT.md](NEW-PROJECT.md); про то, что движок ждёт от
профиля, — [PROFILE-CONTRACT.md](PROFILE-CONTRACT.md).

---

## Главный инвариант: движок не знает ни одного проекта

Ни имён контейнеров, ни команд стека, ни путей репозиториев в логике. Всё это приходит из профиля.
Если правка требует проектного знания — её место в `profiles/<имя>.sh`, даже когда «так быстрее».
Каждый раз, когда это правило нарушали, следующий проект упирался в чужой хардкод.

Самопроверка перед коммитом:

```bash
grep -rniE 'laravel|pest|pint|vue|arsenkin|rdesigner|ars-sb' lib/ bin/
```

Вывод не обязан быть пустым — есть три известные уступки, и новых добавлять не нужно:

- `lib/dashboard.py` — дефолты путей/контейнеров (`FACTORY_BE_ROOT` и соседи) указывают на arsenkin,
  но всё берётся из env `<имя>.dashboard.env`;
- `bin/dashboard` — профиль по умолчанию `arsenkin`;
- `lib/core.sh` — базовый allow-лист агента содержит ходовой фронтовый инструментарий
  (`npx eslint`, `npm run`, `python3`, `curl`); проекту без ноды он просто не нужен.

Всё, что попало в вывод сверх этого (кроме совпадений внутри слов и примеров в комментариях), —
новый хардкод: убирай в профиль.

Второе следствие: **новый проект не должен требовать правки движка**. Если требует — значит
не хватает хука; добавляй хук (с дефолтом для тех, кто его не объявил), а не ветку `if profile == …`.

## Карта репозитория: кто что читает

| Файл | Роль | Кто зависит |
|---|---|---|
| `bin/factory` | CLI и демон задачи: разбор аргументов, демонизация, загрузка ядра и профиля, хвост после конвейера (SHIP → RETRO), режим `demo` (одиночный прогон демо-агента по кнопке) | кокпит запускает именно его |
| `bin/dashboard` | старый веб-дашборд с env профиля | `factory-dashboard.service` |
| `bin/factory-new` | генератор скелета профиля | человек/агент при заведении проекта |
| `bin/factory-graph-new` | заготовка схемы `profiles/<имя>.graph.json` из маршрутов профиля | `factory-new`; человек после смены состава этапов |
| `bin/factory-check` | все проверки профиля разом | обязателен перед первым прогоном |
| `lib/core.sh` | **ядро**: реестр, ворота, resume-цикл, запуск этапов, таймауты, контроль побочных правок | всё остальное |
| `lib/pipeline-set.sh` | единственный способ менять статусы (+телеметрия, `--init/--replan/--reject-accept`) | агенты этапов, кокпит |
| `lib/dashboard.py` | веб-дашборд :8070 (граф, ворота, статистика) | `factory-dashboard.service` |
| `lib/watchdog.sh` | пассивный сторож | `factory-watchdog.timer` |
| `profiles/<имя>.sh` | профиль проекта | движок + кокпит |
| `profiles/<имя>/` | проектное хозяйство профиля (провижн стенда, озвучка, склейка демо) | только свой профиль |
| `profiles/<имя>.dashboard.env` | пути/контейнеры/трекер для дашборда | дашборд, кокпит |
| `profiles/<имя>.graph.json` | нарисованная схема маршрутов (необязательна) | дашборд, `tests/routes-sync.py` |
| `tests/` | проверки: контракт, доступы, схема, скорость, DOM дашборда | `factory-check` |

**Данные живут вне репозитория** — `~/.factory/state/`: `tNNNN.pipeline` (реестр задачи,
единственный источник истины), `logs/`, `archive/`, `shots/`, `demo/`, `quarantine/`.
Путь задаётся `FACTORY_STATE` / `STATE_DIR`; в коде никогда не хардкодить.

**Внешние потребители, которые ломаются молча:**

- **кокпит** (`~/Workspace/cockpit`, сервис `cockpit-server.service`) — запускает `factory … start|resume`,
  читает реестры задач, грузит профиль ради `PROFILE_CTX`/`PROFILE_TRIAGE_*`, зовёт `factory slots`;
- **systemd**: `factory-dashboard.service`, `factory-watchdog.service|.timer` (сейчас оба выключены —
  их роль забрал кокпит на :8140);
- **точка входа из B24**: `~/.claude/hooks/arsenkin-b24-factory.sh`.

Меняешь формат реестра, имена ключей или вывод `factory slots` — проверь этих троих, а не только тесты.

## Когда изменение вступает в силу

| Что изменил | Когда подействует | Что делать с живыми задачами |
|---|---|---|
| `profiles/<имя>.sh` — промпты, модели, бюджеты, веер, readonly | **со следующего этапа**: профиль перечитывается перед каждым этапом (`_reload_profile`) | ничего не делать, демона НЕ убивать |
| `profiles/<имя>/*.sh` — провижн стенда | при следующем подъёме стенда | — |
| `lib/core.sh`, `bin/factory` | только для новых процессов: демон держит уже загруженный код | остановить демона (`ORCH_PID` из реестра) и `factory <TASK> resume --profile <имя>` |
| `lib/pipeline-set.sh` | сразу (запускается как отдельный процесс на каждый вызов) | — |
| `lib/dashboard.py` | после `systemctl --user restart factory-dashboard` | — |
| кокпит (его собственный код) | после рестарта его сервиса | при ручной разработке кокпит держать **остановленным**: иначе crashloop по EADDRINUSE и запуски уезжают в его cgroup |

Перечитывание профиля сделано специально: раньше ради правки промпта убивали демона, и 6 из 9
«смертей фабрики» за сессию оказались этими самыми `kill`.

## Правила, которые нельзя нарушать

1. **Статус этапа меняется только через `lib/pipeline-set.sh`.** Прямая запись в `.pipeline`
   мимо него теряет телеметрию (`KEY_AT`, `KEY_FAILS`) и ломает санити графа.
2. **Ворота — только этапы `GATE_*`.** Это единственное имя, которое движок понимает сам.
   Этап с другим именем движок запустит как агента — «вопрос человеку» превратится в прогон агента.
3. **Хвост движка (`SHIP`, `RETRO`) не кладётся в `PROFILE_ROUTE_STAGES_*`.** Он гоняется
   после конвейера в `bin/factory` по своим правилам; положишь в маршрут — прогонится дважды.
   `DEMO` не кладётся тем более: демо убрано из цепочки (2026-07-27) и снимается отдельным
   прогоном `factory <TASK> demo` по кнопке плагина «Демо» в кокпите. Ключ `DEMO` в реестре
   есть, но этапом конвейера он не является: ни `run_pipeline`, ни дашборд его не ведут.
4. **Новый хук профиля обязан иметь дефолт.** Все вызовы обёрнуты `declare -F … >/dev/null`:
   профиль, который хук не объявил, должен продолжать работать.
5. **Правка графа и правка этапов — одна правка.** Разошлись — на дашборде каша из чужих узлов;
   ловится `tests/routes-sync.py`.
6. **Документация — часть контракта.** Добавил/убрал хук или переменную — в тот же заход правь
   `docs/PROFILE-CONTRACT.md`. Мёртвые хуки в доке (`profile_run_id`, `profile_report`) прожили
   так несколько месяцев и попали в реальный профиль как карго-культ.
7. **Исторические пояснения в комментариях не удалять.** Строки вида «так столкнулись #7789 и #7804»
   — это оплаченный инцидентами контекст, а не мусор. Меняешь поведение — обнови объяснение.

## Чем проверяться перед коммитом

```bash
cd ~/Workspace/factory

bash -n bin/factory bin/factory-check bin/factory-new lib/*.sh profiles/*.sh   # синтаксис
python3 -m py_compile lib/dashboard.py bin/factory-graph-new                     # синтаксис python-частей

bin/factory-check --quick                  # все профили: контракт, промпты, доступы, схема, скорость
bin/factory-check <имя>                    # + живой прогон агента (копейки, но реальные)

python3 tests/routes-sync.py <имя>         # схема дашборда == этапы профиля
python3 tests/profile-access.py <имя>      # пути из промптов покрыты доступом агента
bash    tests/profile-speed.sh <имя>       # объявлены ли веер/бюджеты/модели
node    tests/dom-patch.mjs                # точечное обновление DOM дашборда (нужен запущенный дашборд + jsdom)
```

`factory-check` без аргументов проверяет **все** профили — так ловится «поправил ядро, сломал соседний
проект». Ноль на выходе = профили можно запускать.

Коммит и пуш — **только по явной просьбе человека**. Репозиторий локальный, ветка `master`, remote нет.

## Ловушки, каждая из которых уже стоила прогона

- **Запуск фабрики из сервиса — только `systemd-run --user --scope --collect --unit=factory-tNNNN`.**
  Процесс-потомок живёт в cgroup вызвавшего сервиса: рестарт кокпита убивал демона и агента посреди сборки.
  `nohup`/`setsid` от cgroup-kill не спасают.
- **`gate_wait` возвращает решение через переменную, а не `$(...)`.** Сабшелл блокирует TERM-trap —
  демона на воротах было не остановить ничем, кроме `kill -9`.
- **Агенту нужны ДВА разных разрешения:** `--add-dir` (каталоги вне cwd) и слой `--settings`
  (bash-команды). Одного мало: разведка отработала 18.8 мин и $4.65, не смогла записать статус —
  и движок прогнал её заново трижды.
- **Просьба «сделай через субагентов» в тексте промпта не работает.** За 15 прогонов — ни одного
  субагента. Веер объявляется хуком `profile_stage_fanout`, тогда требование вставляет движок.
- **Проверочные этапы обязаны быть `readonly`.** `eslint --fix` из этапа линта однажды
  переформатировал 277 файлов основного репозитория и 235 в ветке задачи.
- **Смена маршрута этапом — не повод повторить этап.** Движок пересобирает цепочку нового маршрута
  и идёт с первого несделанного (иначе сборка бежит по feature-цепочке без плана и тестов, #7803).
- **«Стенд поднимается вечно» — сначала проверь СУБД стенда, а не движок и не профиль.** `lib/core.sh`
  ждёт подъём через `wait` без таймаута: если провижн проекта увяз в своей БД, все конвейеры молча
  стоят на «жду стенд» и выглядят как поломка фабрики. 28.07.2026 четыре задачи простояли так 80 минут
  из-за дефолтного redo-лога MySQL проекта (разбор — `arsenkin/be/html/.claude/knowledge/gotchas.md`).
  Признак, что виноват не движок: `tNNNN.stage` замер на одном шаге, а процессы `up.sh` живы.

## Добавить новый проект (коротко)

```bash
bin/factory-new <имя> [корень проекта]   # скелет: profiles/<имя>.sh + .dashboard.env + .graph.json
# заполнить TODO — вопросы, которые надо задать человеку, в docs/NEW-PROJECT.md
# схему довести руками (подписи, петли возврата, optional); после смены этапов:
bin/factory-graph-new <имя> --force      # перегенерировать заготовку схемы
bin/factory-check <имя>                  # всё зелёное
bin/factory 1 start --profile <имя> --ticket "пробная задача"
```

Движок при этом не меняется. Если кажется, что без правки движка не обойтись, — сначала перечитай
первый раздел: скорее всего, не хватает хука с дефолтом.
