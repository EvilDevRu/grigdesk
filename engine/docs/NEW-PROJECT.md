# Как завести конвейер под новый проект

Инструкция для агента (и человека), который добавляет проект на фабрику. Движок трогать не нужно:
он не знает ни одного проекта — всё живёт в профиле. Если всё же тянет поправить движок — сначала
[ENGINE.md](ENGINE.md), раздел про инвариант.

```bash
bin/factory-new <имя> [корень проекта]   # скелет по контракту
# заполнить TODO в profiles/<имя>.sh
bin/factory-check <имя>                  # все проверки разом (без --quick — с живым агентом)
bin/factory <TASK> start --profile <имя> --ticket "…"
```

**Три готовых образца — списывай с того, что ближе:**

| Профиль | Стенд | Трекер | Чем полезен как пример |
|---|---|---|---|
| `arsenkin` | своя песочница на задачу (контейнеры + копии схем), несколько параллельных | B24 | провижн в каталоге профиля, `profile_slots`, контроль побочных правок, демо с озвучкой |
| `rdesigner` | один общий постоянный стенд | нет | минимальный профиль: `sandbox_down` пустой, `PROFILE_ARCHIVE_ON_FINISH=1`, два коротких маршрута |
| `cockpit` | git worktree на задачу + дев-экземпляр systemd-юнитом на своём порту, без Docker | нет | конвейер по коду хост-сервиса, который нельзя ронять (это пульт самой фабрики): изоляция кода worktree'ем, данных — снапшотом, власти — заглушкой `COCKPIT_FACTORY_BIN=/bin/false`; авторизация стенда через первичный setup |

---

## Шаг 1. Спросить человека, а не догадываться

Прежде чем писать профиль, выясни — иначе конвейер будет красивым и бесполезным:

1. **Что такое «задача» в этом проекте?** Тикет из трекера? Прогон по промпту («мебель выглядит
   коробками»)? От этого зависит, откуда берётся название и нужен ли трекер.
2. **Чем проверяется результат?** Тесты? Числовые метрики? Глаз человека на скриншотах?
   Если проверить нечем — конвейер выродится в «агент сказал, что сделал».
3. **Есть ли изоляция?** Своя песочница на задачу (контейнеры + копия БД) или один общий стенд?
   Если стенд общий — параллельные задачи по этому проекту запускать нельзя, и это надо знать.
4. **Что агенту запрещено?** Команды, которые ломают данные, стоят денег или занимают
   единственный ресурс (одна GPU, прод-БД, платное API).
5. **Где человек обязан участвовать?** Минимум одни ворота — приёмка. Ворота плана нужны там,
   где ошибка направления дорога.

## Шаг 2. Маршруты — по типам работы, а не «на всякий случай»

Маршрут = последовательность этапов. Их придумывает проект.

```bash
PROFILE_ROUTE_STAGES_dev=(SCOUT IDEAS SKEPTIC SYNTH BUILD REGRESS SHOTS GATE_ACCEPT SHIP)
PROFILE_ROUTE_STAGES_quick=(SCOUT BUILD REGRESS SHOTS GATE_ACCEPT SHIP)
```

- Этапы `GATE_*` — **ворота человека**: движок останавливается и ждёт решения на дашборде.
  Это единственный этап, который движок понимает по имени.
- Маршрут выбирает первый этап (обычно разведка), выставляя `ROUTE`. Правила выбора пиши
  в промпте разведки — по тому, что видно в коде, а не по формулировке тикета.
- Не плоди похожие маршруты: два маршрута, отличающиеся одним этапом, — это один маршрут.
  (На arsenkin так убрали `bugfix`: он повторял `feature`, а «причина понятна» оказывалась догадкой.)

## Шаг 3. Промпты этапов

Промпт — это ТЗ агенту на один этап. Требования:

- **Что сделать и чем проверить** — с конкретными командами проекта (не «прогони тесты»,
  а `docker exec <контейнер> ./vendor/bin/pest`).
- **Где взять вход и куда положить выход** — файлы в `$STATE_DIR/t<TASK>.*` (разведка, план,
  диагноз, отчёт). Следующий этап читает файл, а не сканирует всё заново.
- **Как отчитаться**: движок сам требует выставить статус через `pipeline-set.sh`, но в промпте
  полезно назвать ключ и условия: `BUILD done`, а при провале `BUILD failed`.
- Провал этапа — это `failed`, а не молчание. Молчание движок трактует как «агент не справился»
  и повторяет этап (до трёх раз), сжигая время.

Один этап может выставлять статус соседнего (у arsenkin `TESTS` ставит и `TCRITIC`) — тогда
у соседа промпта нет, и `factory-check` предупредит: убедись, что это осознанно.

## Шаг 4. Доступ агента (самая частая мина)

Агент работает неинтерактивно: любой вопрос «одобри действие» = этап не завершён и повтор с нуля.
Доступ выдаётся заранее, **двумя разными механизмами**:

| Что нужно | Чем даётся | Кто отвечает |
|---|---|---|
| писать в каталог вне cwd | `--add-dir` | движок даёт реестр и свой каталог; проект — `PROFILE_AGENT_DIRS` |
| выполнить bash-команду | слой `--settings` | движок разрешает `pipeline-set.sh`; проект — `PROFILE_AGENT_ALLOW` |

```bash
PROFILE_AGENT_CWD="/home/user/Workspace/proj"          # всё внутри доступно по умолчанию
PROFILE_AGENT_DIRS="/home/user/Workspace/proj-worktrees /home/user/Workspace/proj-fe"
PROFILE_AGENT_ALLOW=("Bash(docker exec proj-app:*)")   # поверх личных настроек пользователя
```

Проверяется командой `bin/factory-check <имя>` — она гоняет и статическую сверку путей,
и живой прогон агента (копейки на дешёвой модели), который реально пишет статус.

## Шаг 5. Параллельность: веер субагентов

Мягкая просьба «сделай через субагентов» в тексте промпта **не работает** — проверено на двух
проектах: за 15 прогонов агенты не запустили ни одного субагента. Веер объявляется отдельным хуком,
и тогда движок вставляет требование сам.

```bash
profile_stage_fanout() {
  case "$1" in
    SCOUT) cat <<'ZONES'
AUTO 5-10
Ориентиры, что считать зоной в этом проекте: …
ZONES
;;
    REVIEW) cat <<'ZONES'          # фиксированное деление, когда состав известен заранее
КОРРЕКТНОСТЬ: …
РЕГРЕССИИ: …
ZONES
;;
    *) echo '' ;;
  esac
}
```

**`AUTO <min>-<max>` (динамика)** — агент сам строит карту под конкретную задачу и делит её.
Лучше для разведки, диагноза, ревью: состав работы каждый раз разный, шаблон из трёх вечных зон
либо не покрывает нужное, либо плодит пустые.

**Перечисление зон (фиксированно)** — когда деление известно заранее и не зависит от задачи
(два конкурирующих плана, две проверки варианта: числами и логикой).

**Верхняя граница — не формальность.** Параллельно реально бежит около десятка субагентов,
остальные ждут очереди, а сводить отчёты всё равно одному агенту. На десятках отчётов он теряет
детали — это потеря качества, а не выигрыш скорости. Разумный потолок: 8-10 зон.

**Где веер НЕ объявлять:** прогон сценариев и замеры на одном стенде (параллельная нагрузка
исказит цифры — а цифры и есть смысл этапа), правка кода (агенты подерутся за файлы), сведение
результатов воедино (по определению работа одного).

Движок пишет в реестр, сколько субагентов реально запущено (`FANOUT_SCOUT=6`), и предупреждает
в журнале, если веер объявлен, а запущено ноль.

## Шаг 6. Бюджет времени этапа

```bash
profile_stage_budget() { case "$1" in SCOUT) echo 8 ;; BUILD) echo 20 ;; *) echo '' ;; esac; }
```

Ориентир глубины, а не жёсткий лимит: без него агент копает, пока не упрётся в таймаут.
Цель — 5-10 минут на этап; больше только там, где этого требует природа работы.
Движок сам добавляет к бюджету правило: *не укладываешься — сужай охват и отчитывайся тем, что
есть*, и требует раздел **«НЕ ПРОВЕРЕНО»** — сокращать охват можно, скрывать сокращение нельзя.

Фактическая длительность пишется в реестр (`DUR_REVIEW=7`); превышение бюджета вдвое попадает
в журнал. Отдельно есть `profile_stage_timeout` (сек) — жёсткая страховка от вечного агента.

## Шаг 7. Модели по этапам

```bash
profile_stage_model() {
  case "$1" in
    SCOUT|SHOTS|REGRESS) echo sonnet ;;   # поиск, прогон, скриншоты, линтеры
    *) echo '' ;;                         # думать (план, диагноз, сборка, ревью) — модель сессии
  esac
}
```

Без этого весь конвейер идёт на самой тяжёлой модели: одна разведка arsenkin стоила
19 минут и $4.65 там, где хватило бы минут.

## Шаг 8. Защита от побочных правок (обязательно)

Агент работает в **worktree задачи**, а не в общем репозитории — иначе он складывает туда файлы
и правит чужой код:

```bash
profile_agent_cwd() { local w="/path/worktree-t${1}"; [[ -d "$w" ]] && echo "$w"; }
```

Проверочные этапы объявляются read-only, и движок ловит их побочные правки:

```bash
profile_stage_readonly() { case "$1" in LINT|CHECK|MEASURE) echo 1 ;; *) echo '' ;; esac; }
profile_dirty_files()    { git -C "/path/worktree-t${1}" status --porcelain | awk '{print "BE:"$NF}'; }
```

Движок при нарушении **не трогает файлы**: пишет, что именно тронуто, и валит этап. Плюс команды
автоформатирования запрещены на уровне разрешений — добавь проектные в `PROFILE_AGENT_DENY`.

## Шаг 9. Стенд

```bash
profile_sandbox_up()     { … }   # поднять окружение задачи (или ничего, если стенд общий)
profile_sandbox_down()   { … }   # снести по кнопке человека (движок сам не зовёт)
profile_sandbox_exists() { … }   # непусто = уже есть
```

Провижн по природе проектный, но живёт он **здесь, в каталоге профиля** `profiles/<имя>/`, а не в
репозитории проекта. Хуки — тонкие адаптеры (`bash "$SB/up.sh" "$1"`). Почему не в проекте: когда
скрипты лежали там, рядом с ними завелись копии движка со своим каталогом состояния, и отметки
этапов уходили мимо дашборда.

В `<имя>.dashboard.env` опиши, как дашборду показывать стенд:
`FACTORY_STAND_CONTAINER` с `{task}` — песочница на задачу, без `{task}` — общий стенд.

Если стендов несколько и индекс (порты, IP, номер базы) распределяется снаружи — объяви
`profile_slots`: он печатает занятость (`RANGE`/`USED`), а `factory slots --profile <имя>` отдаёт
её JSON'ом кокпиту, который резервирует индекс ДО запуска. Считать занятость обязан тот же код,
что и подъём стенда: два независимых счётчика разошлись, и две задачи взяли один индекс — вторая
умерла на «Address already in use», потеряв 24 минуты провижининга.

## Шаг 10. Схема конвейера — обязательна

`factory-new` кладёт заготовку `profiles/<имя>.graph.json` сразу: узлы = этапы маршрута,
раскладка змейкой, ворота нарисованы человеческими. Файл нужен **обязательно**: кокпит (:8140)
автосхему строить не умеет — без схемы запрос графа падает, карточка задачи молча
отфильтровывается из списка, и выглядит это как «фабрика не запустилась». (Автосхему из этапов
умеет только старый дашборд `lib/dashboard.py` на :8070, а он выключен.)

Что доводить руками: подписи узлов вместо машинных `Gate accept`, координаты `pos` под свою
схему, петли возврата (`"fail"`-рёбра «ревью → сборка», «регресс → сборка») и подписи вроде
«✗ дыры». Остальные поля: `keys` (узел → ключ реестра, если отличается от `UPPER(id)`),
`optional` — про него ниже. Сверка со списком этапов — `tests/routes-sync.py <имя>`
(входит в `factory-check`): узлы схемы обязаны совпадать с `PROFILE_ROUTE_STAGES_*`.

Поменял состав этапов — перегенерируй заготовку и перенеси в неё свои подписи:

```bash
bin/factory-graph-new <имя>            # схема из маршрутов профиля (все сразу)
bin/factory-graph-new <имя> --force    # перезаписать существующую
```

### `optional` — единственное место, где объявляется законный пропуск

Движок принимает `skipped` от любого этапа и идёт дальше: `optional` он **не читает вообще**
(это поле для кокпита). Кокпит по нему решает, как покрасить узел: этап из списка — «пропущен
осознанно», не из списка — красное «пропущен без причины — аномалия».

Заполняй его ровно теми этапами, для которых **промпт самого профиля разрешает пропуск**.
Пример из arsenkin: `{"*": ["simplify", "browser"], "debug": ["tests"]}` — симплифаер
не нужен на мелком диффе, браузерная проверка бессмысленна без изменений во фронте, а на
маршруте debug тесты фиксируют не фичу, а найденную причину, и не всякую причину можно
зафиксировать честным тестом. Пусто (`{"*": []}`) — тоже нормальный ответ: у rdesigner все
этапы обязательны, и любой пропуск там должен краснеть.

Причину пропуска движок с агента спрашивает всегда, независимо от `optional`: она попадает
в реестр как `<STAGE>_COMMENT` и видна в модалке узла. Прогон #7804 показал, зачем: агент
пропустил тесты на фронтовой задаче (Pest нечего было проверять), обоснование осталось
в журнале прогона на семь мегабайт, а человек видел на схеме одно слово «пропущен».

## Шаг 11. Что увидит кокпит

Дашборд задач (кокпит, `~/Workspace/cockpit`) грузит профиль сам. Чтобы задачи этого проекта можно
было триажить и запускать кнопкой, добавь:

```bash
PROFILE_TRIAGE_REPOS="be:/путь/к/репо fe:/путь/к/фронту"   # префикс:путь; по префиксам считается протухание анализа
PROFILE_TRIAGE_MARKERS="что в этом проекте дорого сломать — по строке на маркер риска"
PROFILE_ARCHIVE_ON_FINISH=1                                # если карточка после отгрузки не нужна
```

Без `PROFILE_TRIAGE_*` триаж всё равно работает, но оценивает риск вслепую: он не знает, что в
этом проекте необратимо (списания, миграции тенантных баз, схема аналитики).

## Чек-лист приёмки нового профиля

```bash
bin/factory-check <имя>          # всё зелёное
bin/factory 1 start --profile <имя> --ticket "пробная задача"
```

Смотри на дашборде: карточка появилась, стенд определился, этапы меняют статус, ворота ждут
решения. Если этап «крутится» — открой `~/.factory/state/logs/t1.orch.log`: там видно, что
именно агент не смог сделать.
